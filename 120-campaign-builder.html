第一百二十部分 · 活动搭建与投放闭环——低代码、AB 与回收 ​

🧭 返回总目录｜上一篇：第一百一十九部分 · 大型 Vue 3 双端项目实战——从需求到上线｜关联章节：第三十八部分 · 低代码表单引擎 · 第三十三部分 · Zod · 第六十九部分 · 前端埋点体系 · 第五十九部分 · 监控与可观测

本部分内容 ​

这一册讲营销活动从搭建到回收的链路：运营搭页面 → Schema 落库校验 → 投放决定「给谁看、看几次」→ AB 分流 → 曝光与转化回收 → 风控降级。边界是：38 册讲表单字段模型，本册讲页面/组件/物料三层；69 册讲埋点 SDK，本册只讲活动口径与归因；110 册讲玩法，本册讲玩法页如何生产、发布和度量。读完你能设计一套「配置可回滚、分流可复现、投放可止损」的活动系统。

120.1 活动页模型：页面、组件、物料 ​

概念解析 ​

活动搭建的核心不是拖拽，而是把页面拆成三层可独立演进的对象：

层职责变更频率维护者
页面 Page路由、投放位、版本、生效时间每次活动运营
组件 Node结构树：type + props + children每天运营
物料 Material渲染实现 + 资源依赖随代码发版前端

依赖必须单向：Schema 只能引用注册表里存在的 type，物料不认识具体活动。反过来把活动专用渲染函数 import 进组件，活动下线后仓库就堆满一次性物料，没人敢删。

Schema 是唯一事实来源：可序列化（纯 JSON，不含函数/DOM/循环引用）、有版本（version 是协议版本，revision 是内容修订号）、可迁移（升级提供 migrate，旧配置读取时升级而不是重搭）。把组件实例存成运行时对象（带方法、响应式代理）会导致序列化失败、跨版本报错、审核读不了。

完整代码示例 ​

examples/120-01-schema-validation.ts 实现组件白名单、嵌套层级、必填/类型校验与 v1→v2 迁移。校验返回带路径的问题列表，而不是抛第一个错误：

ts
const issues: Issue[] = [];
validateNode(schema.root, 'root', 1, issues);
// 例: root.children[0].props.image: 缺少必填属性

运行方式：npx tsx examples/120-01-schema-validation.ts

应用实践 ​

  • 活动复制只复制 Schema；复制后强制重跑校验，老活动可能引用已下线物料。
  • 图片/字体/视频走 CDN 带 hash，Schema 只存 URL；否则资源清理后回滚裂图。
  • 海外文案存 i18n key 或按 locale 分字段，不要硬编码英文。

最佳实践 ​

  • 每份 Schema 带 schemaVersion + revision + updatedBy，便于追溯。
  • 单页节点数与深度做硬上限（200 / 5 层），防止运营复制出渲染灾难。

120.2 Schema 驱动渲染 ​

概念解析 ​

渲染 = 注册表（type → renderer）+ 递归遍历 + 边界处理。难点不在递归，而在「配置错了会怎样」。处理顺序：查注册表 → 未命中降级占位 → 命中则调用 renderer（捕获异常）→ renderer 递归 children。

三条红线：

  1. 发布前校验，运行时兜底。校验放保存/发布接口和 CI；运行时仍要处理未知组件，因为物料发版与配置发布是两条流水线。
  2. 错误隔离到节点级。一个物料抛异常不能让整页 render 抛出，否则错误边界卸载整棵树，用户看到白屏。
  3. 默认值与类型收窄。size 缺失给 14，image 非字符串按空串并告警。
规则拦截的错误不拦截的后果
组件白名单拼错 type、引用下线物料区块空白或渲染报错
嵌套/子节点上限超深树、单页几百卡片栈溢出、长任务掉帧
必填属性缺图、缺跳转链接裂图、按钮无响应
类型校验"28" 传给字号样式失效、URL 拼接错误
链接白名单javascript: 伪协议XSS、开放重定向

完整代码示例 ​

examples/120-02-component-registry-render.ts 实现物料注册、递归渲染、未知组件占位与单组件异常隔离；注册表拒绝重复注册，避免后注册者静默覆盖：

ts
register(type: string, renderer: MaterialRenderer): void {
    if (this.renderers.has(type)) throw new Error(`物料重复注册: ${type}`);
    this.renderers.set(type, renderer);
}

运行方式：npx tsx examples/120-02-component-registry-render.ts

应用实践 ​

真实场景：某出海电商黑五大促页复制去年配置，含已下线的 countdown 物料。发布接口只查 JSON 语法，渲染时抛 renderer is not a function，整页白屏 40 分钟。修复要两层：发布接口补白名单（上线前拦截），渲染层补异常隔离（漏网也只损失一个区块）。

最佳实践 ​

  • 预览环境使用与线上同一份注册表和 Schema，不要另写「预览专用渲染」。
  • 占位带 data-type/data-id，监控按 type 聚合，直接看出缺哪个物料。
  • 渲染器保持 props → 输出的纯逻辑，请求与分流放在容器层。

120.3 编辑器与画布 ​

概念解析 ​

编辑器状态分两类，混在一起是卡顿与 undo 错乱的根源：

状态内容进 Schema进历史栈
文档态组件树、props、样式是是
会话态选中节点、缩放、拖拽临时坐标否否

撤销/重做用命令模式：每个操作带 apply/invert（新增↔删除、移动↔移回、改属性↔改回旧值），执行新命令时清空重做栈。相比整树快照，命令栈内存小、能合并连续输入、还能当协同操作日志。

画布用 iframe 隔离：编辑器与预览共享注册表，但 CSS、全局变量、第三方脚本互不污染。拖拽要解决命中测试、坐标换算、边缘自动滚动。属性面板由 120.1 的 PropRule 自动生成，校验规则与编辑控件同源，才不会「编辑器允许填、发布校验拒绝」。

应用实践 ​

  • 每次编辑后防抖保存草稿，带 revision 做乐观锁；冲突时让运营选「覆盖/另存」，不要静默覆盖。
  • 预览链接用短期 token 绑定 draft revision，避免未发布内容被外部抓到。
  • 画布只渲染视口内节点，属性面板按选中节点懒渲染；否则 200 节点每次输入都全树重排。
  • 编辑器与运行时共用同一套 Schema 类型和注册表，避免两边漂移。

120.4 投放与人群定向 ​

概念解析 ​

投放按固定优先级判定，顺序不能乱：

顺序判定原因码典型配置
1人群命中audience国家、分层、标签、排除包
2投放时间窗window活动起止、每日时段、时区
3频次上限frequency日限 3 次、周限 10 次
4预算余量budget总预算、分渠道预算

先判人群再扣预算，避免非目标用户吃光预算；先判时间再判频次，跨天重置才算得对。频次计数、预算余额、曝光去重必须放服务端，前端只拿结论——本地计数刷新、清缓存、改时间就能绕过。

时区分两个口径：活动时区结算预算与排期（如 UTC+8）；用户时区计算每日 9~22 点免打扰。黑五从美国时间周五 0 点开始，但欧洲用户的免打扰不能用美国时间判断，否则凌晨推给德国用户。

完整代码示例 ​

examples/120-04-delivery-frequency.ts 实现人群匹配、日频上限、每日时段、总预算与曝光幂等。关键是先扣额度再曝光：

ts
if (used >= maxPerDay) return { served: false, reason: 'frequency' };
if (this.remainingBudget <= 0) return { served: false, reason: 'budget' };
this.dayCount.set(key, used + 1); // 宁可少投一次，不可超发一次

运行方式：npx tsx examples/120-04-delivery-frequency.ts

应用实践 ​

真实场景：东南亚电商双 11 配置日限 3 次、总预算 100 万曝光，但弹窗与页内 banner 用了两套 impressionId，一次访问触发两次曝光，预算下午 3 点耗尽，晚间高峰无曝光。修复是统一幂等键 hash(userId + campaignId + slotId + 时间窗)。

最佳实践 ​

  • 频控 key 精确到「用户 + 活动 + 位置 + 时间窗」，不要只用 userId，否则不同位置互挤。
  • 预算用服务端账本扣减，偏差超 5% 告警；拒绝返回原因码供前端提示「今日已达上限」。

120.5 AB 实验与分流 ​

概念解析 ​

AB 分流本质是一个确定性函数：bucket = hash(salt + userId) % 10000。salt、算法、用户 ID 不变，结果永远不变，这是跨端、跨天、跨发版一致的前提。

概念做法不这样做的后果
稳定哈希FNV-1a / Murmur，含 userId刷新换组，样本被污染
流量分层每层不同 salt多层实验相互干扰
同层互斥10000 桶切不重叠区间同一位置被两个实验同时改
扩量单调只扩大区间上界老用户翻组，指标突变

完整代码示例 ​

examples/120-03-ab-bucketing.ts 用 FNV-1a + 固定 salt 分桶，并校验同层互斥与扩量单调：

ts
function bucketOf(userId: string, salt: string): number {
    return fnv1a(`${salt}:${userId}`) % 10000;
}
function ramp(experiment: Experiment, percent: number): Experiment {
    return { ...experiment, start: 0, end: Math.round(10000 * percent / 100) };
}

运行方式：npx tsx examples/120-03-ab-bucketing.ts

应用实践 ​

反例一：客户端用 Math.random() 分流，刷新就换版本，同一人既算实验组又算对照组，指标被平均化，得出「无显著差异」的错误结论。反例二：扩量时换实验 ID 或重排区间，10%→30% 时老用户被重新洗牌，短期出现「扩量即下跌」。正确做法是保留实验 ID 与 salt，只改区间上界，并校验 10% ⊂ 30% ⊂ 50%。

最佳实践 ​

  • 分流在服务端或网关完成，客户端只接收 variant；至少保证会话内 sticky。
  • 曝光在组件真正渲染后上报，分流时上报会把未曝光用户算进实验组。
  • 上线前查 SRM（分流比例偏差），超阈值（如 1%）告警，通常是分桶或埋点 bug。

120.6 数据回收与归因 ​

概念解析 ​

活动回收三条流缺一不可：

流事件关键字段用途
曝光campaign_exposurecampaignId、variant、slotId、impressionIdUV、频次、实验分母
点击campaign_clickimpressionId、targetUrl、positionCTR、跳转链路
转化order_paiduserId、campaignId、attributionTokenCVR、ROI、归因

曝光幂等键取 hash(userId + campaignId + slotId + variant + 时间窗)。没有它，弱网重发、重渲染、页面回退都会重复计数，CTR 被系统性低估。

归因窗口先定：常见「点击 7 天、曝光 1 天」，跨境还要考虑时区与支付延迟。模型至少区分 last click（简单但高估渠道）与增量 incrementality（对照组差值，对 ROI 最诚实但成本最高）。每条事件带 eventId、campaignId、variant、impressionId、pageRevision，否则既无法去重，也无法定位版本。

应用实践 ​

真实场景：黑五期间 A 版 CTR 比 B 高 30%，准备全量。复核发现 A 的曝光埋在图片 onload 后，弱网大量丢失，分母偏小、CTR 虚高；改成挂载即上报 + 服务端按 impressionId 去重后，差距收敛到 4%。埋点口径错误比设计错误更常见。

最佳实践 ​

  • 曝光用 sendBeacon 或批量队列上报，卸载前 flush，失败进离线队列带 eventId 重试。
  • 事件带 pageRevision 与 variant；前端只报行为事实，订单与退款以服务端回调为准。

120.7 风控、审核与降级 ​

概念解析 ​

活动系统把配置权开放给非研发，风险面远大于普通业务。四道闸门：

闸门检查失败动作
内容审核敏感词、图片、落地页域名拒绝发布并定位字段
Schema 审核白名单、深度、必填、链接协议422 + 问题路径
权限审核编辑/发布/下线权限审批流、双人复核
运行时风控频率、预算、异常流量自动停投或降级

降级按故障分级，而不是一句「做好兜底」：

故障降级动作用户感知
单物料渲染失败节点占位，其余正常少一个区块
物料包加载失败上一版 CDN 快照内容略旧，页面可用
投放接口超时静态兜底页/默认活动无个性化，能下单
配置错误回滚上一 revision短暂旧版
刷量异常关闭活动入口，保留订单入口消失，订单不受影响

内容安全额外防三类：link 只允许 https 白名单（防开放重定向与 javascript:）、文本必须转义、UGC 不能直接进 DOM。

应用实践 ​

反例：某活动发布接口只存不校验，渲染层也不隔离异常。运营把 type 写成 baner，上线白屏又无 kill switch，只能紧急回滚，历时 25 分钟。发布白名单、运行时占位、revision 回滚三层任一生效都不会白屏。

最佳实践 ​

  • 灰度按 revision：1% → 10% → 50% → 100%，每档看白屏率、JS 错误率、曝光量。
  • 静态快照兜底；预算 80% 告警、100% 自动停投。

120.8 自测题 ​

先自己作答，再展开参考答案。

1. 活动页为什么拆成页面、组件、物料三层？【基础】

页面管路由、投放位、版本与时间，最低频；组件是 Schema 结构节点，运营每天改；物料是渲染实现与资源，随代码发版、跨活动复用。拆开后改内容不动代码，物料下线可全局扫描引用。

2. Schema 校验为什么返回「带路径的问题列表」而不是抛第一个错误？【基础】

配置错误往往不止一处。抛首个错误会让运营「改一个、发一次、再报一个」。带路径可直接定位组件与属性，配合面板高亮，修复效率高一个量级。

3. 未知组件在渲染层怎么处理？为什么不能只靠发布前校验？【基础】

降级为带 data-type/data-id 的占位并告警，绝不能让整页抛出。配置发布与物料发版是两条流水线：物料先下线、旧配置仍在线，缓存与回滚也会遇到注册表里没有的物料。

4. 投放为什么按「人群 → 时间 → 频次 → 预算」判定？【进阶】

先判人群，避免非目标用户消耗频次与预算；再判时间，保证跨天/跨时段计数口径正确；频次在预算前，避免高频用户吃光预算；预算最后扣，只有真正要曝光的请求才扣。顺序颠倒会导致预算被非目标用户耗尽、跨天频次未重置。

5. AB 分桶为什么不能用 Math.random() 或自增 ID？【进阶】

Math.random() 每次结果不同，刷新即换组，同一批人同时污染两组。自增 ID 依赖请求顺序，设备、网络、并发都会改变分组，多实例自增也不连续。正确做法是 hash(salt + userId) 映射固定桶位，保证任何端、任何时间同组。

6. 实验从 10% 扩到 30%，为什么不能换 salt 或重分桶？【进阶】

换 salt 会让原实验组用户被重新洗牌，一部分翻到对照组，扩量瞬间人群构成突变，出现「扩量即下跌」，历史数据也无法合并。正确做法是保留实验 ID 与 salt，只把区间上界从 1000 扩到 3000，原 10% 用户必然是子集。

7. 曝光为什么必须做 impressionId 幂等？【进阶】

弱网重发、重复渲染、页面回退、SDK 重试都会重复上报。没有幂等键，UV/PV 虚高，CTR 分母偏大而偏低，频控计数提前打满导致少投。键通常取 hash(userId + campaignId + slotId + variant + 时间窗)，服务端去重后落库。

8. 活动页白屏，按什么顺序排查与止损？【挑战】

止损优先：kill switch 或回滚上一 revision 恢复页面，再定位。排查：① JS 错误与资源加载失败；② Schema 是否引用未注册物料或超深嵌套；③ 投放接口是否超时导致骨架未渲染；④ 实验是否分到未发布的 variant。根因修复补三层：发布校验、节点级异常隔离、静态快照。

9. 设计黑五活动的投放与实验方案，说明时区、频控、预算与归因口径。【挑战】

时区：排期与预算按活动时区结算，免打扰按用户本地时区 9~22 点。频控：单用户单活动日限 3 次、周限 10 次，key 含 slotId；曝光幂等键含时间窗。预算：服务端账本扣减，80% 告警、100% 停投，分渠道独立。实验：同层互斥、salt 固定、只扩区间，渲染后报曝光，上线前查 SRM。归因：点击 7 天、曝光 1 天，订单以服务端回调为准按 orderId 对账，ROI 用增量口径。
