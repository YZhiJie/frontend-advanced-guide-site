第一百二十四部分 · 搜索与全文检索前端 ​

🧭 返回总目录｜上一篇：第一百二十三部分 · 富文本编辑器｜关联章节：第八十九部分 · RAG 知识库实战 · 第二十二部分 · 数据结构与算法 · 第五部分 · 状态管理 · 第六部分 · 网络与缓存 · 第六十九部分 · 前端埋点体系

本部分内容 ​

这一册面向知识管理平台的搜索体验。主线只有一句：搜索框是状态机不是输入框——键入意图、防抖闸门、在途请求、过期响应、降级快照、URL 筛选态，每一环都有明确的进入条件与退出条件。四条边界：query 生命周期有仲裁、高亮先转义再拼接、筛选态与 URL 双向同步、检索 DSL 只活在 BFF。四个示例覆盖请求生命周期、关键词高亮、筛选序列化与建议缓存。

124.1 搜索体验模型：query 生命周期与竞态 ​

概念解析 ​

一次搜索从键入到渲染要经过五个状态：typing（收意图）→ debouncing（等停顿）→ inflight（在途）→ applied（渲染）/ stale（丢弃）/ degraded（降级）。绝大多数搜索 bug 不是「请求没发出去」，而是状态迁移没人管：慢响应覆盖新结果、重试打挂刚恢复的服务、降级结果被当成实时结果。

机制解决什么缺失后果
防抖（300ms 级）连打每个字都发请求QPS 放大 5~10 倍，费用与限流齐飞
AbortController中断上一在途请求旧响应与新结果抢渲染，闪烁错乱
单调递增序号仲裁abort 漏拦时的兜底丢弃第三方封装吞掉 abort 时静默错乱
有限重试 + 退避抖动自动恢复无重试用户看到裸错误；无限重试雪上加霜
降级快照服务挂掉/弱网兜底空白页，用户以为平台数据丢了

为什么「中断 + 序号」要双保险：AbortController 只保证 fetch 不再 resolve 的语义依赖实现链——中间任何一层封装（拦截器、缓存层、mock）忘了透传 signal，abort 就失效。序号仲裁是纯前端逻辑，不依赖任何外部配合，是最后一道闸门。

完整代码示例 ​

ts
// 文件: examples/124-01-query-lifecycle.ts（节选）
// 双保险：中断上一请求 + 序号仲裁丢弃过期响应
private async dispatch(query: string): Promise<DispatchResult> {
    this.seq += 1;
    const mySeq = this.seq;
    this.inFlight?.abort();          // 双保险之一：中断上一请求
    const token = new CancelToken();
    this.inFlight = token;

    let attempts = 0;
    while (attempts <= this.opts.maxRetries) {
        attempts += 1;
        if (attempts > 1) await this.opts.sleep(this.opts.retryDelayMs * (attempts - 1));
        if (token.aborted || mySeq !== this.seq) return { status: 'stale', response: null, attempts };
        try {
            const response = await this.opts.fetchFn(query, token);
            if (mySeq !== this.seq || token.aborted) return { status: 'stale', response: null, attempts };
            return { status: 'applied', response, attempts };
        } catch {
            if (mySeq !== this.seq || token.aborted) return { status: 'stale', response: null, attempts };
        }
    }
    // 重试耗尽：降级到本地快照，必须带 degraded 标记
    const hits = this.opts.snapshot.filter((hit) => hit.title.toLowerCase().includes(query.toLowerCase()));
    return { status: 'degraded', response: { query, hits, degraded: true }, attempts };
}

运行方式：npx tsx examples/124-01-query-lifecycle.ts

断言：三次键入合并为一次请求；旧请求被中断且其迟到响应被序号仲裁丢弃；线性退避第三次成功；重试耗尽返回带 degraded 标记的本地快照结果。

应用实践 ​

知识平台全局搜索框：防抖 300ms，序号 + AbortController 双仲裁，失败两次后 200ms/400ms 线性退避，仍失败则返回本地缓存的热门文档并提示「离线结果」。上线后搜索接口 QPS 降 62%，「结果闪回旧词」工单清零。反例：只防抖不仲裁，弱网下「es 集群」的慢响应盖掉「es 查询语法」的新结果，用户以为搜索坏了。

最佳实践 ​

  • ✅ 降级结果必须带 degraded 标记，UI 弱化样式、埋点单独统计。
  • ✅ 退避期间也要检查序号：等待中用户改词了，这次尝试就没有意义。
  • ✅ 防抖时间进配置不进代码：桌面端 300ms、移动端弱网可放到 500ms。

124.2 搜索建议与输入体验 ​

概念解析 ​

建议（suggest）的流量通常是搜索本身的 3~5 倍——每个按键都是一次潜在请求。前端的三道闸门：防抖压住连打、前缀 LRU 缓存命中近期、在途合并挡住同 key 并发。注意「LRU 命中」防的是已完成的请求，「在途合并」防的是正在进行中的请求，两者缺一不可：防抖 300ms 内用户连打 elastic 后回退再输入，缓存还没写入，没有在途表就会重复发。

问题闸门关键细节
连打轰炸防抖300ms 起步，中文 composition 期间不发
相同前缀重复请求前缀 LRU 缓存key 要归一（trim + lowercase），容量有界
同 key 并发在途 Promise 复用请求完成立刻从 inflight 表删除
键盘选词索引环绕 + -1 未选中态↓ 越末位回顶部；-1 时输入框保留原文
零结果热词兜底带标记fallback: true 让 UI 加分隔线

中文输入法的 composition 事件是移动端的经典坑：compositionstart 到 compositionend 之间的拼音串不是搜索意图，期间必须挂起防抖计时，否则「sousuo」这种半成品拼音会打出五六个无效请求。

完整代码示例 ​

ts
// 文件: examples/124-04-suggest-cache.ts（节选）
// 三级闸门：缓存 → 在途合并 → 真实请求；零结果热词兜底且同样进缓存
async request(prefix: string): Promise<SuggestResult> {
    const key = this.normalizeKey(prefix);
    const cached = this.cache.get(key);
    if (cached !== undefined) return { list: cached, source: 'cache' };
    const running = this.inflight.get(key);
    if (running !== undefined) return { list: await running, source: 'dedup' };
    const promise = this.opts.fetchFn(key)
        .then((words) => this.toSuggestions(words))
        .finally(() => this.inflight.delete(key));
    this.inflight.set(key, promise);
    const list = await promise;
    this.cache.set(key, list);   // 空结果也缓存：零结果不该反复打后端
    return { list, source: 'network' };
}

运行方式：npx tsx examples/124-04-suggest-cache.ts

断言：LRU 容量有界且命中刷新热度；三次同 key 请求只发一次真实请求；键盘索引边界环绕、空列表返回 -1；零结果回退热词带 fallback 标记且被缓存。

应用实践 ​

知识平台头部搜索框：Elastic、 elastic、ELASTIC 归一为同一 key；↓↑ 在 8 条候选间环绕，Esc 回 -1 恢复输入原文；移动端监听 composition 事件挂起防抖。零结果时展示「热门：全员公告 / 值班手册」并打 suggest_fallback 埋点。反例：缓存用普通 Map 无容量上限，长会话内存涨 40MB，且空结果不缓存导致「zzz」每敲一次打一次后端。

最佳实践 ​

  • ✅ key 归一后再进缓存：大小写与首尾空白不应制造新请求。
  • ✅ inflight 表必须 finally 清理，否则一次失败永久 dedup。
  • ✅ 键盘选中态 -1 与「第 0 项」严格区分：回车提交的是两个不同的词。

124.3 结果渲染与关键词高亮 ​

概念解析 ​

高亮是「在归一化副本上找区间，回原文切片，转义后拼 mark」三步。顺序错了全是事故：先拼 mark 再转义会把 mark 也转掉；先转义再找区间，转义改变了长度，区间全部错位；直接 innerHTML 拼接原文，搜索结果里的 <script> 就成了 XSS——搜索结果是攻击者可控文本的展示位，因为攻击者可以先用同样的词发一篇文档。

决策正确姿势错误姿势
归一逐字符全角折半角 + 小写，保持索引 1:1toLowerCase() 整串，遇 İ 变长错位
匹配短语（引号）优先 + 多词，重叠区间合并逐词 replace，嵌套出 <mark><mark>
拼接只转义原文片段，mark 亲手拼innerHTML = text.replace(...)
摘要围绕首个命中取 ±N 字符，截断加省略号固定取前 200 字，命中词常在窗外

fragment 截取的顺序同样重要：先在原文上截窗，再对窗口内片段高亮。对高亮后的 HTML 截窗会切断 &amp; 或 <mark>，截出来的字符串直接就是注入面。

完整代码示例 ​

ts
// 文件: examples/124-02-highlight.ts（节选）
// 安全高亮：只转义原文片段，mark 是唯一裸标签
function highlight(text: string, rawQuery: string): string {
    const ranges = findRanges(text, parseQuery(rawQuery));
    let out = '';
    let cursor = 0;
    for (const range of ranges) {
        out += escapeHtml(text.slice(cursor, range.start));
        out += `<mark>${escapeHtml(text.slice(range.start, range.end))}</mark>`;
        cursor = range.end;
    }
    out += escapeHtml(text.slice(cursor));
    return out;
}
// fragment：先在原文上截 [start, end)，窗口内再走高亮；省略号只加在截断处

运行方式：npx tsx examples/124-02-highlight.ts

断言：全角/大小写归一后命中且索引 1:1；<script> 以转义文本形态进入结果；短语与单词的重叠命中合并为一个 mark；fragment 围绕命中词取上下文且省略号边界正确。

应用实践 ​

文档搜索列表：标题整串高亮，正文用 fragment 取命中词前后各 20 字；用户搜「"搜索引擎" 分词」时短语整体一个 mark、单词再各一个。安全评审专项：构造标题为 <img onerror=...> 的文档再搜它，断言渲染结果无裸标签。反例：用 replace(new RegExp(q, 'gi'), '<mark>$&</mark>')——q 里的 . 被当正则元音标，且命中 mark 标签自身导致嵌套错乱。

最佳实践 ​

  • ✅ 归一函数逐字符且保长，命中区间才能无损切回原文。
  • ✅ 高亮是纯函数：输入原文与查询，输出安全 HTML，单测不依赖 DOM。
  • ✅ fragment 窗口以「首个命中」为锚，多命中密集场景可再扩展为密度最高窗口。

124.4 筛选、排序与分页 ​

概念解析 ​

筛选态的唯一事实源是 URL：刷新、分享、前进后退、新标签打开，全部从 URL 重建。模型与 URL 双向序列化必须幂等——parse(serialize(state)) === state，否则分享出去的链接和本机看到的结果不一致。序列化只写非默认字段：URL 干净，且默认值将来调整时老链接语义自动跟随。

URL 是用户可直接编辑的输入，可信度等于表单输入：types=hacker、page=-5、size=abc-def 都会真实出现，解析层必须逐项校验、静默回默认，而不是抛错白屏。

决策点推荐说明
页码分页知识库结果页可用可跳页、可分享第 N 页；但 ES from+size 深分页贵
游标分页（cursor/search_after）信息流、深翻页稳定不重复；代价是无法跳页
改筛选必须重置 page=1「改完条件停在第 8 页零结果」是经典 bug
多选类型枚举白名单 + 去重 + 排序后序列化幂等且防脏值

完整代码示例 ​

ts
// 文件: examples/124-03-facet-filter.ts（节选）
// 应用筛选变更：除「只翻页」外，任何条件变化都把 page 重置回 1
function applyPatch(state: FilterState, patch: FilterPatch): FilterState {
    const next: FilterState = {
        ...state,
        ...patch,
        types: patch.types !== undefined ? [...patch.types] : [...state.types],
        sizeKb: patch.sizeKb !== undefined ? [patch.sizeKb[0], patch.sizeKb[1]] : [...state.sizeKb],
    };
    const onlyPage = Object.keys(patch).every((key) => key === 'page');
    if (!onlyPage) next.page = patch.page ?? DEFAULT_FILTER.page;
    return next;
}

运行方式：npx tsx examples/124-03-facet-filter.ts

断言：默认态序列化为空串；parse(serialize(state)) 恒等可分享；hacker/forever/abc-def 等脏值全部安全落回默认；改筛选回第 1 页、纯翻页保留筛选。

应用实践 ​

知识库结果页：URL ?types=doc,wiki&within=30d&sort=newest&page=2 直接分享给同事，打开即同视图；类型筛选用 tag 多选、时间用单选 segmented、大小用区间输入。反例：筛选态只存在组件 store，用户刷新后 8 个筛选条件全丢；或解析不校验，运营在 URL 里塞了 page=99999，ES 深分页直接把集群打满超时。

最佳实践 ​

  • ✅ 序列化幂等：多选排序后拼接，同一状态永远产出同一串。
  • ✅ 解析即校验：非法值回默认，绝不把脏数据放进模型。
  • ✅ 深分页（页码 > 100）引导用户加筛选，而不是硬翻。

124.5 全文检索对接边界 ​

概念解析 ​

前端永远不直连 Elasticsearch/OpenSearch，理由有三：安全——ES 没有行级权限模型，直连等于把整库暴露给浏览器，_search 里换个 index 名就能越权；稳定——DSL 是后端实现细节，前端直拼 query DSL 意味着换引擎（ES → OpenSearch → 向量检索）要发版所有客户端；成本——通配符前缀、深分页、高基数聚合都能在一条请求里打爆集群，必须在服务端有限速与改写。

正确形态是 BFF 契约：前端只提交业务语义（query、filters、sort、page），BFF 负责改写为 DSL——关键词进 multi_match、筛选进 filter 上下文（不计分、可缓存）、权限过滤（term: visible_to）强制前置注入、高亮由服务端 highlight 字段返回或返回原文由前端高亮（二选一，不要两处都高亮）。

前端字段BFF 改写说明
querymulti_match(title^3, content)标题加权，前端不可见
typesterms: doc_type（filter 上下文）不计分，走 filter cache
withinrange: updated_at7d → now-7d 在服务端换算
page/sizefrom+size 上限钳制超过 1 万直接拒绝
——term: visible_to = user.groups权限过滤强制注入，前端给不了也改不掉

完整代码示例 ​

ts
// 文件: examples/124-03-facet-filter.ts（节选）
// 前端只产出业务语义模型；DSL、权限、索引名全部留在 BFF
const state = parseFilters(window.location.search);
const body = {
    query,
    filters: { types: state.types, within: state.within, sizeKb: state.sizeKb },
    sort: state.sort,
    page: state.page,
};
// 反例：body 里出现 index、query_string、from+size 原始值——
// 任何一个都说明检索细节泄漏到了前端

运行方式：npx tsx examples/124-03-facet-filter.ts

断言：模型字段全部是业务枚举与数值，不含任何 DSL 关键字；解析层保证出参永远合法，BFF 可以信任其形状。

应用实践 ​

知识平台检索链路：前端 → BFF /api/search（鉴权 + 权限过滤注入 + 参数钳制 + DSL 改写 + 限流）→ ES 集群。换引擎时只改 BFF，前端零发版。反例：某团队让前端直连 ES 只读账号，攻击者控制台里改 index 为 users 拖走全量员工信息；另一团队前端拼 query_string 语法，用户搜 a:b 触发 Lucene 语法错误直接 500。

最佳实践 ​

  • ✅ 权限过滤在 BFF 强制注入，前端传的任何「用户身份」字段都只作参考。
  • ✅ 高亮职责二选一：服务端 highlight 或前端 highlight，杜绝两处都包 mark。
  • ✅ 聚合（facet 计数）与检索同请求返回，避免前端再发 N 次 count。

124.6 零结果与容错 ​

概念解析 ​

零结果不是终点而是分叉口。行业基线：健康知识库的零结果率应低于 10%。处理分三层：搜前（建议引导到存在的内容）、搜中（拼写纠错、同义词、拼音）、搜后（空态给出路：热词、热门分类、反馈入口）。

手段位置说明
拼写纠错BFF/引擎elastc → 展示「你是不是想找：elastic」，原文结果仍给
同义词引擎 synonyms 表「OA」=「办公系统」；维护在服务端，前端无感
拼音引擎拼音分词sousuo 命中「搜索」；适合中文知识库，成本是索引膨胀
空态引导前端热词兜底 + 反馈入口 + 「去提问」跳转，零结果也要埋点

纠错的产品形态要选「弱纠错」：展示「你是不是想找 X」并同时给原词结果，而不是静默替换——静默替换在小众术语上会帮倒忙，用户搜内部项目代号时被「纠正」成常用词。

完整代码示例 ​

ts
// 文件: examples/124-04-suggest-cache.ts（节选）
// 零结果回退：热词兜底带标记，UI 加分隔线与「热门」标题
private toSuggestions(words: string[]): Suggestion[] {
    if (words.length === 0) {
        return this.opts.hotWords.map((text) => ({ text, fallback: true }));
    }
    return words.map((text) => ({ text, fallback: false }));
}

运行方式：npx tsx examples/124-04-suggest-cache.ts

断言：零结果回退热词且全部带 fallback 标记；兜底结果同样进缓存，空结果不反复打后端。

应用实践 ​

知识库空态页：顶部「没有找到与『zzz』相关的内容」，下方热门文档与「提交检索反馈」按钮；反馈带着原始 query 进埋点，每周导出零结果词表给运营补文档或配同义词。三个月后零结果率从 14% 降到 6%。反例：空态只有一句「暂无结果」，用户流失且团队对「用户到底在找什么」完全无感知。

最佳实践 ​

  • ✅ 零结果必须埋点且带原始 query，它是知识库内容建设的需求池。
  • ✅ 纠错用弱形态：建议而非替换，原词结果始终保留。
  • ✅ 空态的每条出路（热词、分类、反馈）都要可点击，死胡同等于流失。

124.7 搜索质量观测 ​

概念解析 ​

搜索是少数可以精确量化体验的前端场景，四个北极星指标：

指标口径健康线
点击率（CTR）有点击的搜索 / 总搜索> 60%
零结果率零结果搜索 / 总搜索< 10%
响应分位p50/p95/p99，从发出到渲染完p95 < 800ms
改写率用户 5s 内换词重搜 / 总搜索越低越好，> 20% 说明首搜不准

口径统一比数值重要：一次「搜索」的定义必须是「防抖后实际发出的请求」，不是按键数；「点击」要排除误点后 1s 内返回。埋点至少带 query_hash（隐私）、result_count、latency、page、degraded、filters——degraded 单独成维度，降级时段的 CTR 暴跌不该污染真实质量数据。响应要测「发出到渲染完成」的端到端，而不是接口耗时：慢渲染一样丢用户。

完整代码示例 ​

ts
// 文件: examples/124-01-query-lifecycle.ts（节选）
// degraded 标记一路带到埋点：降级流量与真实流量分开统计
const result = await box.tick();
if (result !== null) {
    track('search_response', {
        queryHash: hash(query),
        resultCount: result.response?.hits.length ?? 0,
        degraded: result.response?.degraded ?? false, // 降级时段单独看板
        status: result.status,                        // applied / stale / degraded
        attempts: result.attempts,                    // 重试次数反映链路健康
    });
}

运行方式：npx tsx examples/124-01-query-lifecycle.ts

断言：degraded 结果与 applied 结果可被埋点明确区分；attempts 精确记录实际尝试次数。

应用实践 ​

知识平台搜索看板：按周看 CTR、零结果率、p95；零结果词 TOP50 每周给运营；降级时段单独标注，避免服务抖动期的数据误导质量结论。一次改版把标题权重调高后 CTR 从 58% 升到 71%，靠的就是口径稳定的对比。反例：把防抖前的每次按键都记为搜索，CTR 被稀释到 15%，团队误判「搜索没人点」而下线功能。

最佳实践 ​

  • ✅ 「一次搜索」= 一次防抖后请求，口径写进埋点文档并评审。
  • ✅ query 只上报 hash，原始词留在行为日志系统按权限访问。
  • ✅ 质量指标与业务指标分看板：CTR/零结果率归搜索质量，转化归业务。

124.8 自测题 ​

先自己作答，再展开参考答案。

1. 为什么 AbortController 之外还要序号仲裁？【基础】

abort 的生效依赖整条封装链透传 signal，中间任何一层（拦截器、缓存、mock）漏传就失效。序号仲裁是纯前端逻辑，响应回来时比对序号即可丢弃过期结果，不依赖外部配合，是最后一道闸门。

2. 高亮为什么必须「先转义原文、再拼 mark」？【基础】

搜索结果是攻击者可控文本的展示位。先拼接会让原文里的 <script> 以裸标签进 HTML 造成 XSS；只对原文片段做转义、mark 标签由代码亲手拼接，注入面就被堵死。

3. 修改筛选条件时为什么要重置页码？【基础】

筛选改变了结果总量，停留在原页码（如第 8 页）大概率直接越界零结果，用户会误判为「筛选坏了」。任何非翻页的筛选变更都应把 page 重置为 1。

4. 建议接口的「在途合并」和「LRU 缓存」分工有何不同？【进阶】

LRU 防的是「已完成的请求」被重复发起；在途合并防的是「正在进行中的同 key 请求」并发多份。缓存还没写入的窗口期（防抖刚放行、响应未归）全靠在途表挡住重复请求，两者缺一不可。

5. 为什么前端不直连 Elasticsearch？【进阶】

三点：ES 无行级权限模型，直连等于暴露整库；DSL 是后端实现细节，泄漏到前端意味着换引擎要发版所有客户端；通配符、深分页、高基数聚合都能一条请求打爆集群，必须在 BFF 做钳制与改写。

6. fragment 摘要截取的正确顺序是什么，为什么？【进阶】

先在原文上按命中位置截窗，再对窗口内文本转义并高亮。对转义后的 HTML 截窗会切断 &amp; 之类的实体或 <mark> 标签，截出的字符串本身就成了注入面与乱码源。

7. 零结果率要降下来，前端与后端各自能做什么？【挑战】

后端/引擎：拼写纠错（弱形态）、同义词表、拼音分词、分析零结果词表补内容。前端：搜前用建议把用户引导到存在的内容、空态给热词/分类/反馈三条出路、零结果埋点带原始 query 反哺运营。闭环是「零结果词表 → 补文档/配同义词 → 下周复看」。

8. 设计搜索埋点时，为什么 query 要 hash、degraded 要单独成维度？【挑战】

query 原文可能含姓名、工号等敏感信息，直接上报有隐私合规风险，hash 后仍可统计词频与零结果率。降级时段（服务抖动）的 CTR 与响应时长不代表真实搜索质量，混入主看板会误导改版决策，必须按 degraded 维度拆开看。
