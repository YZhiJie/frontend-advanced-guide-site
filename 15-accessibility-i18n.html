第十五部分：可访问性与国际化 ​

a11y（可访问性）与 i18n（国际化）是高级工程师的分内事：欧盟 EN 301 549、中国适老化改造政策都已有硬性要求，而出海产品从第一天就要面对多语言与 RTL。更现实的好处是——可访问的组件往往就是工程质量更高的组件。

15.1 可访问性基础：语义化优先 ​

概念解析 ​

可访问性的四大原则（POUR）：可感知（有替代文本）、可操作（键盘可达）、可理解（可预测、容错）、健壮（能被辅助技术解析）。

最重要的心智模型：读屏软件看到的 DOM,与搜索引擎看到的 DOM,是同一个。语义化 HTML 是零成本的可访问性；ARIA 是"原生语义无法表达时"的补充——第一条规则就是：能用原生元素就不要用 ARIA 修补。

典型应用场景 ​

  • 组件库开发：每个组件要过键盘走查与读屏测试；
  • 中后台表单：label 关联、错误提示可感知；
  • 出海产品：读屏支持是欧美市场的合规底线。

完整代码示例 ​

html
<!-- 文件: examples/15-01-semantic.html —— [浏览器] div 汤 vs 语义化:同一个界面的两种写法 -->

<!-- ❌ div 汤:读屏软件只能逐个朗读"可点击,无标签",用户无法按标题导航 -->
<div class="page">
    <div class="header"><div class="logo"></div></div>
    <div class="title" onclick="go()">商品详情</div>
    <div class="btn" onclick="buy()">立即购买</div>
</div>

<!-- ✅ 语义化:免费获得 —— 标题层级导航(读屏 H 键跳转)、按钮回车/空格触发、
     焦点自动可达、SEO 抓取结构化信息。一行 ARIA 都不用写 -->
<div class="page">
    <header><img class="logo" alt="站点 Logo" /></header>
    <main>
        <h1>商品详情</h1>            <!-- 标题提供文档大纲 -->
        <button onclick="buy()">立即购买</button>  <!-- 原生 button 自带键盘与角色 -->
    </main>
</div>
tsx
// 文件: examples/15-02-native-vs-aria.tsx —— 原生优先的第二课:别用 div 造按钮
// ❌ 反例:div 造按钮 —— 键盘无法聚焦,读屏不报"按钮",需要补一堆 ARIA + 键盘事件
// <div role="button" tabIndex={0} onClick={save}
//      onKeyDown={(e) => (e.key === 'Enter' || e.key === ' ') && save()}>保存</div>

// ✅ 正例:一行原生 button,上述能力全部免费
export function SaveButton() {
    return <button onClick={save}>保存</button>;
}
declare function save(): void;

// ARIA 只在原生语义不存在时使用:比如"用 div 组合出的树形控件/标签页组"
// 记住公式:原生元素 > 原生元素 + 属性增强 > ARIA + 手写交互

运行方式：open examples/15-01-semantic.html 后开启读屏（macOS: VoiceOver Cmd+F5）对比两种写法的朗读结果；用 Tab 键体验"div 按钮"无法聚焦。

最佳实践 ​

  • ✅ HTML 审查三问：这该是什么元素？标题层级连续吗？这个可点的东西是 <button> 或 <a> 吗？
  • ✅ 图片 alt 是内容就写内容、是装饰就写 alt=""（读屏跳过），缺省不写才是最差的；
  • ⚠️ tabindex 只用两个值：0（纳入焦点序）与 -1（编程聚焦）；正数 tabindex 是反模式（打乱自然顺序）；
  • 📖 面试高频：POUR 原则、ARIA 第一规则（no ARIA is better than bad ARIA）、alt 的三种取值策略。

15.2 键盘可达与焦点管理 ​

概念解析 ​

键盘用户的核心诉求：焦点永远可见、顺序符合直觉、不进"黑洞"。SPA 最容易踩的坑有两个：路由切换后焦点还留在已销毁的元素上；模态框关闭后焦点丢回 body（要从头再 Tab 一遍）。

完整代码示例 ​

tsx
// 文件: examples/15-03-focus-trap.tsx —— 模态框焦点陷阱:可访问组件的标配
import { useEffect, useRef } from 'react';

export function Modal({ open, onClose, title, children }: {
    open: boolean; onClose: () => void; title: string; children: React.ReactNode;
}) {
    const dialogRef = useRef<HTMLDivElement>(null);

    useEffect(() => {
        if (!open) return;
        const dialog = dialogRef.current!;
        const previousFocus = document.activeElement as HTMLElement; // 记住打开前的焦点位置

        // 打开时把焦点移进对话框(键盘用户从第一个控件开始操作)
        const focusables = dialog.querySelectorAll<HTMLElement>(
            'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])',
        );
        focusables[0]?.focus();

        const onKeyDown = (e: KeyboardEvent) => {
            if (e.key === 'Escape') return onClose();
            if (e.key !== 'Tab') return;
            // Tab 循环:焦点始终困在对话框内(focus trap)
            const list = [...dialog.querySelectorAll<HTMLElement>(
                'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])',
            )];
            const first = list[0];
            const last = list[list.length - 1];
            if (e.shiftKey && document.activeElement === first) {
                e.preventDefault();
                last.focus();               // Shift+Tab 在第一个元素 → 跳到最后
            } else if (!e.shiftKey && document.activeElement === last) {
                e.preventDefault();
                first.focus();              // Tab 在最后一个元素 → 跳回第一个
            }
        };

        document.addEventListener('keydown', onKeyDown);
        return () => {
            document.removeEventListener('keydown', onKeyDown);
            previousFocus?.focus();         // 关闭后焦点归位 —— 这是"黑洞"问题的解药
        };
    }, [open, onClose]);

    if (!open) return null;
    return (
        // role="dialog" + aria-modal:读屏宣布"进入了对话框",并屏蔽背后内容
        <div ref={dialogRef} role="dialog" aria-modal="true" aria-label={title}>
            <h2>{title}</h2>
            {children}
            <button onClick={onClose}>关闭</button>
        </div>
    );
}

最佳实践 ​

  • ✅ 交互组件走查三件套：Tab 顺序、Esc 退出、焦点归位——模态框/抽屉/下拉的必修课；
  • ✅ 路由切换后把焦点移到新页面主标题（mainHeadingRef.current?.focus() 配 tabIndex={-1}）；
  • ⚠️ 用 :focus-visible 替代 :focus 定制样式，别一刀切 outline: none；
  • 📖 面试高频：焦点陷阱的实现原理、为什么模态框要 aria-modal、tabindex 的正确用法。

15.3 ARIA 实战模式 ​

概念解析 ​

三个最高频的 ARIA 场景：状态告知（aria-expanded/aria-selected）、错误关联（aria-describedby + aria-invalid）、动态内容播报（aria-live region——toast、搜索结果数、AI 流式输出进度）。

完整代码示例 ​

tsx
// 文件: examples/15-05-aria-patterns.tsx —— 三个高频 ARIA 模式
import { useState } from 'react';

// ---- 模式一:折叠面板 —— 状态必须可感知 ----
export function Collapse({ title, children }: { title: string; children: React.ReactNode }) {
    const [open, setOpen] = useState(false);
    return (
        <div>
            <button
                aria-expanded={open}                       // 读屏朗读"已展开/已折叠"
                aria-controls="collapse-panel"             // 与受控区域关联
                onClick={() => setOpen(!open)}
            >
                {title} {open ? '▲' : '▼'}
            </button>
            {open && <div id="collapse-panel">{children}</div>}
        </div>
    );
}

// ---- 模式二:表单校验 —— 错误与输入框关联,读屏用户才能听到错误 ----
export function EmailField() {
    const [email, setEmail] = useState('');
    const [error, setError] = useState<string | null>(null);

    return (
        <div>
            <label htmlFor="email">邮箱</label>
            <input
                id="email"
                type="email"
                value={email}
                aria-invalid={error ? true : undefined}          // 标记无效状态
                aria-describedby={error ? 'email-error' : undefined} // 关联错误描述
                onChange={(e) => setEmail(e.target.value)}
            />
            {error && (
                <p id="email-error" role="alert">                {/* role=alert:立即播报 */}
                    {error}
                </p>
            )}
        </div>
    );
}

// ---- 模式三:live region —— 动态内容主动播报(toast/搜索结果/AI 生成进度) ----
export function SearchStatus({ count, done }: { count: number; done: boolean }) {
    return (
        // aria-live=polite:内容变化时等读屏空闲再播报(不打断);assertive 会打断,慎用
        <p aria-live="polite">
            {done ? `搜索完成,共 ${count} 条结果` : '搜索中...'}
        </p>
    );
}

运行方式：放入 React 项目，开启 VoiceOver/NVDA 操作体验：折叠按钮的展开播报、表单错误的自动朗读、搜索状态的变化播报。

最佳实践 ​

  • ✅ 每写一个自定义交互组件，问三个问题：状态变化读屏能听到吗？键盘能完成全部操作吗？焦点会丢吗？
  • ✅ toast 容器挂 aria-live="polite"，一次播报一条，避免堆叠刷屏；
  • ⚠️ aria-live 区域必须初始就渲染在 DOM 里再更新内容，动态插入的区域不播报；
  • 📖 面试高频：aria-expanded/aria-controls/aria-describedby 各自解决什么、role="alert" 与 aria-live 的关系（alert 是 live=assertive 的预设角色）。

15.4 国际化工程与 Intl API ​

概念解析 ​

i18n 三层：文案翻译（键值管理与运行时替换）、格式本地化（日期/数字/货币——用原生 Intl，不要手写格式化）、布局适配（RTL 镜像、文案长度弹性——德语比英语长 30%）。

方案生态特点
react-i18next / vue-i18n通用 SPA 事实标准命名空间、复数、插值、懒加载语言包
next-intlNext.js App Router与 RSC/路由段配置深度集成
FormatJS(react-intl)老牌ICU MessageFormat 表达力最强

完整代码示例 ​

typescript
// 文件: examples/15-06-intl.ts —— Intl API:零依赖的本地化格式(纯 Node 可运行)
// ============ 日期、数字、货币、相对时间、复数 —— 全部原生支持 ============

const now = new Date('2026-09-15T10:30:00Z');

// ---- 日期时间:不要手写 yyy-MM-dd 拼接 ----
console.log(new Intl.DateTimeFormat('zh-CN', { dateStyle: 'long', timeStyle: 'short' }).format(now));
// 2026年9月15日 GMT+8 下午6:30
console.log(new Intl.DateTimeFormat('en-US', { dateStyle: 'long' }).format(now));
// September 15, 2026

// ---- 货币:自动处理小数位与符号位置(日元没有小数!) ----
console.log(new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(1234567.891));
// ¥1,234,567.89
console.log(new Intl.NumberFormat('ja-JP', { style: 'currency', currency: 'JPY' }).format(1234567.891));
// ￥1,234,568 —— 自动取整

// ---- 相对时间(列表"3 天前") ----
const rtf = new Intl.RelativeTimeFormat('zh-CN', { numeric: 'auto' });
console.log(rtf.format(-3, 'day'));  // 3 天前
console.log(rtf.format(1, 'hour'));  // 1 小时后

// ---- 复数:阿拉伯语有 6 种复数形式,手写 if 根本覆盖不了 ----
const pf = new Intl.PluralRules('en-US');
for (const n of [1, 2, 5]) {
    const category = pf.select(n); // 'one' | 'other'
    const template = category === 'one' ? `${n} item` : `${n} items`;
    console.log(template); // 1 item / 2 items / 5 items
}
tsx
// 文件: examples/15-07-i18n-component.tsx —— i18n 组件层:插值、复数、语言包懒加载
import { useTranslation } from 'react-i18next';

export function OrderCard({ count, date }: { count: number; date: Date }) {
    const { t, i18n } = useTranslation('orders'); // 命名空间:语言包按需加载

    return (
        <div dir={i18n.dir()}> {/* rtl 语言返回 'rtl',配合 12.1 的逻辑属性自动镜像布局 */}
            {/* 插值:语言包 "{{count}} 件商品" */}
            <p>{t('summary', { count })}</p>
            {/* 复数:语言包用 _one/_other 后缀,交给 Intl.PluralRules 选择 */}
            <p>{t('itemCount', { count })}</p>
            {/* 格式化委托给 Intl:t 里声明 {{date, datetime}} 即可 */}
            <time>{t('createdAt', { date, formatParams: { date: { dateStyle: 'medium' } } })}</time>
        </div>
    );
}
// 语言包(en.json): { "itemCount_one": "{{count}} item", "itemCount_other": "{{count}} items" }
// 💡 工程要点:语言包按命名空间 code-split;切语言只下载当前命名空间,不是全量语言包

运行方式：npx tsx examples/15-06-intl.ts 直接运行（Node 13+ 自带完整 ICU 数据）；15-07 放入 npm i react-i18next i18next 后的项目。

最佳实践 ​

  • ✅ 一切格式化走 Intl：日期、货币、相对时间、复数——浏览器和 Node 都内置，零体积成本；
  • ✅ 文案键按业务域命名空间组织并 code-split；上线前用"伪本地化"（把文案全部加长 + 加标记）测布局弹性；
  • ✅ RTL 支持 = dir 属性 + 逻辑属性（margin-inline-start，见 12.1）+ 图标方向镜像，从第一天就别写死 left/right；
  • ⚠️ 中文产品出海常见的坑：复数（俄语/阿拉伯语）、姓名排序（Intl.Collator）、时区存储（数据库一律 UTC，展示层本地化）；
  • 📖 面试高频：Intl 有哪些能力、复数为什么必须用 PluralRules、RTL 适配的三个层面。

15.5 自动化检测与测试 ​

概念解析 ​

a11y 的自动化分层：Lint 期（eslint-plugin-jsx-a11y 拦截低级错误）→ 测试期（axe-core 规则引擎跑在单测/E2E）→ CI 期（Lighthouse a11y 评分门禁）→ 人工期（键盘走查 + 读屏抽查,自动化只能覆盖 ~50% 问题）。

完整代码示例 ​

typescript
// 文件: tests/a11y.test.tsx —— axe 自动化:组件测试里顺手做 a11y 断言
import { describe, expect, it } from 'vitest';
import { render } from '@testing-library/react';
import { axe, toHaveNoViolations } from 'jest-axe'; // npm i -D jest-axe (兼容 vitest)
import { EmailField } from '@/examples/15-05-aria-patterns';

expect.extend(toHaveNoViolations); // 注册 toHaveNoViolations 断言

describe('可访问性', () => {
    it('EmailField 无 axe 违规', async () => {
        const { container } = render(<EmailField />);
        // axe 扫描:对比度、label 关联、ARIA 用法、标题层级等 50+ 规则
        const results = await axe(container);
        expect(results).toHaveNoViolations();
    });
});

最佳实践 ​

  • ✅ 分层防线：jsx-a11y（写错即报）→ axe（提交前发现）→ Lighthouse 门禁（CI 阻断）→ 键盘走查（发布前抽查）；
  • ✅ 把"新组件必须过 axe"写进团队 DoD（完成的定义），存量页面按流量 Top N 逐步治理；
  • ⚠️ 自动化只覆盖约一半规则（对比度、label、ARIA 语法），焦点管理、读屏播报质量必须人工；
  • 📖 面试加分项：能说出 axe 扫描了哪些规则类别，以及"为什么不能只靠自动化"。

15.6 自测题 ​

先自己作答，再展开参考答案。

1. 【基础】ARIA 的第一规则是什么？为什么？

"没有 ARIA 比坏的 ARIA 更好"(no ARIA is better than bad ARIA)。原生 button/select/dialog 自带键盘行为、焦点管理、角色语义；用 div + ARIA 修补要手写全部交互且极易遗漏。正确顺序:原生元素 > 原生元素 + 属性增强 > ARIA + 手写交互。

2. 【进阶】模态框的可访问性清单有哪些？焦点陷阱解决什么问题？

清单:打开时焦点移入、Tab/Shift+Tab 在框内循环(焦点陷阱)、Esc 关闭、role="dialog" + aria-modal、关闭后焦点归位到触发元素。焦点陷阱解决的是键盘用户"Tab 出了对话框,在看不见的背景里操作"的黑洞问题。

3. 【进阶】为什么表单错误要用 aria-describedby 关联而不是只把错误文字放在输入框附近？

视觉上的"附近"对读屏用户没有意义 —— 读屏按 DOM 与焦点朗读,不会自动念输入框旁边的文字。aria-describedby 把错误文本显式关联到输入框,聚焦输入框时错误会被一起朗读;aria-invalid 标记无效状态,role="alert" 保证错误出现时立即播报。

4. 【进阶】为什么日期和货币格式化必须用 Intl 而不是手写模板？

格式差异远超直觉:日元无小数位、阿拉伯语数字系统不同、德语小数是逗号、相对时间(3 天前)各语言语法完全不同、复数英语只有 2 种而阿拉伯语有 6 种。Intl 由 ICU 提供,浏览器与 Node 内置,零体积零维护;手写模板只对中文+英语大致成立。

5. 【挑战】a11y 自动化测试能覆盖所有问题吗？你的分层防线是什么？

不能,自动化只能覆盖约 50%(对比度、label 关联、ARIA 语法等结构性问题);焦点顺序合理性、读屏播报质量、操作流程是否顺畅必须人工键盘走查与读屏抽查。分层:eslint-plugin-jsx-a11y(写码期) → axe(测试期) → Lighthouse 门禁(CI) → 键盘+读屏走查(发布前)。

15.7 本章避坑清单 ​

把本章散落在各节的原则收口成一份可检索清单，按日常出现频率排序；详情回上方对应小节。

场景高频坑一句话避法
颜色传达只用颜色区分状态（成功绿、错误红），色盲与低视力用户无法分辨颜色之外叠加图标或文字（如红字 +「必填」），并保证前景/背景对比度不低于 4.5:1
图片替代文本图片缺 alt，或把文件名直接当 alt内容性图片写清用途，装饰性图片写 alt=""，纯图标按钮用 aria-label 而非靠图说话
焦点管理弹层打开不移入焦点、关闭不归还，Tab 逃逸到看不见的背景里操作打开时保存触发元素并移入焦点、用焦点陷阱把 Tab 圈在弹层内，关闭后归还焦点（呼应 15.2）
ARIA 误用给 div 硬套 role="button" 却没有键盘行为与焦点支持优先用原生元素；ARIA 只补语义不补行为，一旦用 role 就要补全键盘、焦点、状态属性
时区漂移Intl.DateTimeFormat 不显式传 timeZone，CI 与本机输出不同、快照测试随机失败显式传 timeZone（如 Asia/Shanghai），测试里固定 locale 与时区再断言
文案拼接把句子拆成 "共 " + n + " 条" 拼接，语序与复数在其他语言里全错整句作为一条翻译，变量用占位符（{count}），复数交给 Intl.PluralRules 或 ICU 规则
语义结构用 div 加粗代替 h1~h6，读屏无法按标题跳转、页面结构不可导航用真实层级标题，结构交给 header/main/nav/footer 表达，保证读屏可跳转（呼应 15.1）
测试盲区认为过了 axe/Lighthouse 就算无障碍达标，跳过人工验证自动化只覆盖约 50% 的结构问题；焦点顺序、读屏播报、操作流程必须人工键盘+读屏走查
