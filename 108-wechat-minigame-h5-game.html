第一百零八部分 · 微信小游戏与 H5 游戏开发基础 ​

🧭 返回总目录｜上一篇：第一百零七部分 · AI 项目 0→1 落地方法论｜关联章节：第九十四部分 · 微信小程序原生开发 · 第十部分 · 浏览器原理与渲染性能 · 第七十七部分 · 企业级性能优化 · 第十七部分 · Web 平台新能力

本部分内容 ​

游戏前端和日常业务前端是两套思维：业务前端是「事件驱动」——用户点什么就更新什么；游戏是「时间驱动」——不管用户动不动，每 16.7ms 世界都要向前推进一步。本部分讲 H5 / 微信小游戏开发的四大基石：游戏循环（固定时间步长）、精灵动画（图集与帧调度）、对象池（GC 防控）、平台适配（H5 与微信小游戏差异归一），最后给一份性能优化清单。全部示例不依赖任何游戏引擎，纯 TypeScript 可实跑——这些内核搞懂了，再学 Cocos/Laya 就是看 API 文档的事。

108.1 游戏循环：rAF 与固定时间步长 ​

概念解析 ​

游戏循环的最朴素写法是「每帧按流逝时间推进」：

// 反模式：变步长
requestAnimationFrame(function frame(now) {
  const dt = now - lastTime;
  player.x += player.vx * dt;   // dt 每帧都不一样
  requestAnimationFrame(frame);
});

问题出在 dt 不稳定：120Hz 屏 dt≈8ms，60Hz 屏 dt≈16ms，卡顿时 dt 可能 200ms。同样的代码在三台设备上，物理行为完全不同——子弹穿透墙壁（dt 太大一步跨过碰撞体）、高刷屏游戏速度快一倍。固定时间步长（Fixed Timestep） 是标准解：逻辑永远按恒定步长推进，帧时间攒够一步才更新，攒不够就渲染插值。

渲染帧（rAF，不定间隔）      逻辑帧（固定 1/60s）
      │                        │
  ┌───┴───┐                ┌───┼───┬───┬───┐
  │ 16ms  │  → 累积器 →    │步1│步2│步3│...│  攒够 16.67ms 走 1 步
  └───────┘                └───┴───┴───┴───┘
                                   余数 → render(alpha) 插值

三个必须处理的边界：

  1. 死亡螺旋：切后台 10 秒回来，累积器攒了 600 步，每步都 update 导致更卡、攒更多——单帧补步数必须钳制上限，积压时间直接丢弃（宁可慢动作）。
  2. 首帧无 lastTime：第一帧没有「上一帧」，dt 当 0 处理，只渲染不更新。
  3. 浮点累积误差：1/60 不可精确表示，长期累积导致漂移——断言容忍 ±1 步，不要追求绝对精确。

完整代码示例 ​

ts
// 文件: examples/108-01-game-loop-fixed-timestep.ts
// 游戏主循环：固定时间步长 update + 插值 render，死亡螺旋钳制，帧率统计
// 目标：逻辑帧率与渲染帧率解耦——低端机掉帧时游戏速度不变慢

import assert from "node:assert";

interface LoopHooks {
  update(dt: number): void; // 固定步长逻辑更新，dt 恒等于 step（秒）
  render(alpha: number): void; // 渲染，alpha 为插值因子 [0,1)，用于平滑动画
}

class GameLoop {
  readonly step: number; // 固定步长（秒），物理/逻辑一律按它推进
  private acc = 0; // 时间累积器：没攒够一个 step 就不 update
  private last: number | null = null; // 上一帧时间戳
  private readonly maxStepsPerFrame = 5; // 单帧最多补的步数：死亡螺旋钳制
  frames = 0; // render 调用次数
  updates = 0; // update 调用次数
  clampedFrames = 0; // 触发钳制的帧数（用于监控卡顿）

  constructor(step: number, private hooks: LoopHooks) {
    this.step = step;
  }

  /** 由 requestAnimationFrame 每帧驱动，now 单位秒 */
  tick(now: number): void {
    if (this.last === null) {
      this.last = now;
      this.hooks.render(0);
      this.frames++;
      return;
    }
    this.acc += now - this.last;
    this.last = now;

    let steps = 0;
    while (this.acc >= this.step && steps < this.maxStepsPerFrame) {
      this.hooks.update(this.step);
      this.acc -= this.step;
      steps++;
      this.updates++;
    }
    // 帧时间过长（切后台回来/卡顿）：丢弃积压时间，宁可慢动作也不追帧
    if (steps === this.maxStepsPerFrame && this.acc >= this.step) {
      this.acc = 0;
      this.clampedFrames++;
    }
    this.hooks.render(this.acc / this.step);
    this.frames++;
  }
}

/** 滑动窗口帧率统计：近 windowSec 秒内的实际 FPS */
class FpsMeter {
  private stamps: number[] = [];
  constructor(private windowSec = 1) {}
  push(now: number): void {
    this.stamps.push(now);
    while (this.stamps.length && this.stamps[0] <= now - this.windowSec) {
      this.stamps.shift();
    }
  }
  get fps(): number {
    return this.stamps.length / this.windowSec;
  }
}

function runAssertions() {
  // ---------- 测试 1：稳定 60fps 下 update 与 render 次数 ----------
  const positions: number[] = [];
  let x = 0;
  const loop = new GameLoop(1 / 60, {
    update: (dt) => {
      x += dt * 100; // 100 单位/秒匀速
    },
    render: (alpha) => positions.push(x + alpha * (100 / 60)),
  });
  // 模拟 61 帧（t=0 到 t=1s，每 16.667ms 一帧）
  for (let i = 0; i <= 60; i++) loop.tick(i / 60);
  assert.equal(loop.frames, 61);
  assert.ok(loop.updates >= 59 && loop.updates <= 61, `updates=${loop.updates}`);
  assert.ok(Math.abs(x - 100) < 2, `1 秒应前进 ~100 单位，实际 ${x}`);
  console.log("[1/4] 稳定 60fps OK, updates:", loop.updates, "x:", x.toFixed(2));

  // ---------- 测试 2：低端机 30fps，游戏速度不变慢 ----------
  const loop2 = new GameLoop(1 / 60, { update: (dt) => { x2 += dt * 100; }, render: () => {} });
  let x2 = 0;
  for (let i = 0; i <= 30; i++) loop2.tick(i / 30); // 30fps 跑 1 秒
  assert.ok(Math.abs(x2 - 100) < 2, `30fps 下 1 秒仍应前进 ~100，实际 ${x2}`);
  assert.ok(loop2.updates > loop2.frames, "每帧补 2 步，updates 应多于 frames");
  console.log("[2/4] 30fps 速度一致 OK, updates:", loop2.updates, "frames:", loop2.frames);

  // ---------- 测试 3：切后台 10 秒回来，死亡螺旋被钳制 ----------
  const loop3 = new GameLoop(1 / 60, { update: () => {}, render: () => {} });
  loop3.tick(0);
  loop3.tick(10); // 切后台 10 秒
  assert.equal(loop3.updates, 5, "单帧最多补 5 步");
  assert.equal(loop3.clampedFrames, 1);
  console.log("[3/4] 死亡螺旋钳制 OK, 补步:", loop3.updates);

  // ---------- 测试 4：帧率统计 ----------
  const meter = new FpsMeter(1);
  for (let i = 0; i <= 120; i++) meter.push(i / 60);
  assert.ok(Math.abs(meter.fps - 60) < 2, `fps 应约 60，实际 ${meter.fps}`);
  console.log("[4/4] 帧率统计 OK, fps:", meter.fps.toFixed(1));

  console.log("\n✅ 108-01 游戏主循环 全部断言通过");
}

runAssertions();

运行方式：npx tsx examples/108-01-game-loop-fixed-timestep.ts

应用实践 ​

  • 步长选型：动作/射击游戏 1/60；回合制/放置类 1/30 足够且省电；物理模拟（碰撞、刚体）建议 1/120，物理对步长最敏感。
  • 插值渲染：render(alpha) 里绘制位置 = 上一逻辑位置 + (当前位置 - 上一逻辑位置) × alpha。不插值会有轻微抖动，快节奏游戏（跑酷、射击）必做；慢节奏（卡牌、消除）可以省略。
  • rAF 替代 setInterval：setInterval(fn, 16) 不跟屏幕刷新对齐，掉帧时还会继续触发（后台标签页照样跑，白耗 CPU）。rAF 在后台自动暂停——但微信小游戏的 rAF 在 onHide 后照样回调，这是平台差异，见 108.5。

108.2 精灵动画与资源加载 ​

概念解析 ​

精灵图（Sprite Sheet / Atlas）：把动画的全部帧拼在一张大图上，绘制时用 drawImage 的九宫格参数（源矩形 → 目标矩形）取其中一帧。为什么不用一张图一帧？两个原因：① HTTP 请求数——100 帧就是 100 个请求，加载面板卡死；② GPU 纹理切换——每换一次纹理就是一次状态切换，图集让同批绘制共享纹理。

帧调度的核心原则：动画进度只由时间驱动，不由帧数驱动。 错误写法是「每帧 render 推进一帧动画」——60fps 设备动画快一倍，30fps 设备慢一倍。正确写法是记录动画已播放时长，按 fps 换算当前帧。

资源加载三件套：

  1. 预加载清单：游戏启动时加载全部必需资源，显示进度条；不预加载的话，战斗中首次加载一张图就是一次卡顿。
  2. 音频特殊处理：浏览器自动播放策略要求音频必须由用户手势激活——首次 touch/click 后才允许 audio.play()，微信小游戏无此限制但有 InnerAudioContext 自己的坑（见避坑清单）。
  3. 失败重试与降级：CDN 图加载失败重试 2 次后换占位图，游戏不能因为一张图挂了就黑屏。

完整代码示例 ​

ts
// 文件: examples/108-02-sprite-animation.ts
// 精灵图集 + 动画帧调度器：按 fps 取帧、循环/单次播放、完成回调
// 目标：动画进度只由时间驱动，与帧率无关——30fps 和 60fps 播放速度一致

import assert from "node:assert";

interface Frame {
  x: number;
  y: number;
  w: number;
  h: number;
}

/** 精灵图集：一张大图上按网格切出全部帧，drawImage 九宫格取帧 */
class SpriteSheet {
  constructor(
    public image: string,
    public frames: Frame[],
  ) {}

  /** 按等宽网格生成图集：cols 列 rows 行，每帧 frameW × frameH */
  static grid(image: string, frameW: number, frameH: number, cols: number, rows: number): SpriteSheet {
    const frames: Frame[] = [];
    for (let r = 0; r < rows; r++) {
      for (let c = 0; c < cols; c++) {
        frames.push({ x: c * frameW, y: r * frameH, w: frameW, h: frameH });
      }
    }
    return new SpriteSheet(image, frames);
  }

  frame(i: number): Frame {
    return this.frames[i];
  }
}

/** 动画剪辑：一组帧序号 + 播放速率 + 循环模式 */
class Animation {
  private time = 0;
  private finished = false;
  onComplete: (() => void) | null = null;

  constructor(
    private frameIndices: number[],
    private fps: number,
    private loop = true,
  ) {
    assert.ok(frameIndices.length > 0, "动画至少 1 帧");
    assert.ok(fps > 0, "fps 必须为正");
  }

  /** 推进 dt 秒，返回当前应显示的图集帧序号 */
  update(dt: number): number {
    if (this.finished) return this.frameIndices[this.frameIndices.length - 1];
    this.time += dt;
    const total = this.frameIndices.length / this.fps; // 一轮总时长
    if (this.time >= total) {
      if (this.loop) {
        this.time %= total;
      } else {
        this.finished = true;
        this.onComplete?.();
        return this.frameIndices[this.frameIndices.length - 1];
      }
    }
    const idx = Math.floor(this.time * this.fps) % this.frameIndices.length;
    return this.frameIndices[idx];
  }

  get isFinished(): boolean {
    return this.finished;
  }
}

function runAssertions() {
  // ---------- 测试 1：网格图集切帧 ----------
  const sheet = SpriteSheet.grid("hero.png", 32, 32, 4, 2); // 4 列 2 行共 8 帧
  assert.equal(sheet.frames.length, 8);
  assert.deepEqual(sheet.frame(5), { x: 32, y: 32, w: 32, h: 32 }); // 第 2 行第 2 列
  console.log("[1/4] 图集切帧 OK:", JSON.stringify(sheet.frame(5)));

  // ---------- 测试 2：循环动画按时间取帧 ----------
  const walk = new Animation([0, 1, 2, 3], 8, true); // 8fps 循环
  assert.equal(walk.update(0), 0);
  assert.equal(walk.update(1 / 8), 1); // 0.125s → 第 1 帧
  assert.equal(walk.update(1 / 8), 2); // 0.25s → 第 2 帧
  walk.update(1 / 8); // → 3
  assert.equal(walk.update(1 / 8), 0); // 0.5s 一轮结束，回绕到 0
  console.log("[2/4] 循环动画 OK");

  // ---------- 测试 3：单次动画停在末帧并回调 ----------
  const die = new Animation([4, 5, 6, 7], 8, false);
  let completed = 0;
  die.onComplete = () => completed++;
  die.update(0.1); // 第 1 帧区间
  die.update(0.5); // 直接越过一轮（总时长 0.5s）→ 结束
  assert.equal(completed, 1);
  assert.ok(die.isFinished);
  assert.equal(die.update(1), 7); // 结束后永远停在末帧
  assert.equal(completed, 1, "回调只触发一次");
  console.log("[3/4] 单次动画 OK, 停留帧:", die.update(0));

  // ---------- 测试 4：帧率无关——两种采样粒度同刻同帧 ----------
  const a = new Animation([0, 1, 2, 3, 4, 5, 6, 7], 8, true);
  const b = new Animation([0, 1, 2, 3, 4, 5, 6, 7], 8, true);
  for (let i = 0; i < 20; i++) a.update(1 / 60); // 60fps 喂 0.333s
  for (let i = 0; i < 10; i++) b.update(1 / 30); // 30fps 喂 0.333s
  const fa = a.update(0);
  const fb = b.update(0);
  assert.ok(Math.abs(fa - fb) <= 1, `帧率无关性: ${fa} vs ${fb}`);
  console.log("[4/4] 帧率无关 OK, 60fps 帧:", fa, "30fps 帧:", fb);

  console.log("\n✅ 108-02 精灵动画帧调度器 全部断言通过");
}

108.3 对象池与 GC 防控 ​

概念解析 ​

游戏里最常见的性能杀手不是渲染，是 GC 抖动。子弹、粒子、伤害飘字——60fps 下每帧 new 几十个短命对象，几秒就触发一次 minor GC，主线程停 5-10ms，表现为规律性掉帧（每 N 秒卡一下）。对象池把「创建/销毁」改成「获取/归还」：对象永久存活，只是状态在「使用中」和「空闲」之间流转。

三个设计要点：

  1. reset 必须彻底：归还时把对象所有字段重置。脏数据泄漏到下次使用是对象池最高频 bug——子弹带着上一条弹道飞出去。
  2. 池要有上限：瞬时峰值（全屏爆炸 1000 个粒子）后空闲队列不能永远保留 1000 个对象，超上限的部分丢给 GC。
  3. 重复归还防呆：同一对象 release 两次会进空闲队列两次，之后被 acquire 两次——两个系统同时操作同一对象，bug 极难查。用 inUse 集合显式记录。

完整代码示例 ​

ts
// 文件: examples/108-03-object-pool.ts
// 对象池：高频创建/销毁对象（子弹、粒子、伤害数字）的复用容器
// 目标：消灭 GC 抖动——60fps 下每帧 new 几百个对象会触发频繁 minor GC，表现为规律性掉帧

import assert from "node:assert";

class ObjectPool<T> {
  private free: T[] = []; // 空闲队列
  private inUse = new Set<T>(); // 使用中集合（防重复归还）
  created = 0; // 真正 new 的次数
  reused = 0; // 复用次数
  constructor(
    private factory: () => T,
    private reset: (obj: T) => void, // 回收时重置状态，防止脏数据泄漏到下次使用
    private max = 128, // 池上限：防内存无限膨胀
  ) {}

  acquire(): T {
    let obj: T;
    if (this.free.length > 0) {
      obj = this.free.pop()!;
      this.reused++;
    } else {
      obj = this.factory();
      this.created++;
    }
    this.inUse.add(obj);
    return obj;
  }

  release(obj: T): void {
    if (!this.inUse.has(obj)) return; // 重复归还直接忽略（防呆）
    this.inUse.delete(obj);
    this.reset(obj);
    if (this.free.length < this.max) this.free.push(obj); // 超上限就丢给 GC
  }

  get activeCount(): number {
    return this.inUse.size;
  }
  get idleCount(): number {
    return this.free.length;
  }
}

interface Bullet {
  x: number;
  y: number;
  vx: number;
  vy: number;
  alive: boolean;
}

function runAssertions() {
  // ---------- 测试 1：基本获取/归还 ----------
  const pool = new ObjectPool<Bullet>(
    () => ({ x: 0, y: 0, vx: 0, vy: 0, alive: false }),
    (b) => {
      b.alive = false;
      b.x = b.y = b.vx = b.vy = 0;
    },
    64,
  );
  const b1 = pool.acquire();
  b1.alive = true;
  b1.x = 100;
  assert.equal(pool.activeCount, 1);
  pool.release(b1);
  assert.equal(pool.activeCount, 0);
  assert.equal(pool.idleCount, 1);
  const b2 = pool.acquire();
  assert.equal(b2, b1, "应复用同一对象");
  assert.equal(b2.x, 0, "reset 应清空脏数据");
  console.log("[1/4] 获取/归还 OK, created:", pool.created, "reused:", pool.reused);

  // ---------- 测试 2：高频发射 200 发子弹，创建数受上限约束 ----------
  const bullets: Bullet[] = [];
  for (let wave = 0; wave < 200; wave++) {
    const b = pool.acquire();
    b.alive = true;
    bullets.push(b);
    if (bullets.length >= 10) pool.release(bullets.shift()!); // 同屏最多 10 发
  }
  assert.ok(pool.created <= 11, `真实创建应 ≤11，实际 ${pool.created}`);
  assert.ok(pool.reused >= 180, `复用应 ≥180，实际 ${pool.reused}`);
  console.log("[2/4] 高频复用 OK, created:", pool.created, "reused:", pool.reused);

  // ---------- 测试 3：重复归还防呆 ----------
  const b3 = pool.acquire();
  pool.release(b3);
  const idleBefore = pool.idleCount;
  pool.release(b3); // 第二次归还应被忽略
  assert.equal(pool.idleCount, idleBefore, "重复归还不应入池两次");
  console.log("[3/4] 重复归还防呆 OK");

  // ---------- 测试 4：池上限——空闲对象超 max 后丢弃 ----------
  const small = new ObjectPool<{ n: number }>(() => ({ n: 0 }), (o) => (o.n = 0), 4);
  const objs = Array.from({ length: 10 }, () => small.acquire());
  objs.forEach((o) => small.release(o));
  assert.equal(small.idleCount, 4, "空闲池应封顶在 max=4");
  console.log("[4/4] 池上限 OK, idle:", small.idleCount);

  console.log("\n✅ 108-03 对象池 全部断言通过");
}

runAssertions();

运行方式：npx tsx examples/108-03-object-pool.ts

应用实践 ​

  • 什么该入池：生命周期 < 1 秒且同屏数量 > 20 的对象（子弹、粒子、飘字、敌人）。主角、UI、常驻场景对象不要池化——徒增复杂度。
  • 预热：启动时预创建预估峰值 80% 的对象，避免第一波弹幕时集中 new。
  • 遍历中归还的坑：update 循环里边遍历子弹数组边 release 会跳过元素——标准做法是「反向遍历 + swap-remove」，或者标记 alive=false 由下一帧统一清扫。

108.4 触摸输入与高清屏适配 ​

概念解析 ​

H5 游戏输入的两个坐标系问题是新手必踩坑：

1. CSS 像素 ≠ 画布像素。 高清屏（dpr=3）上，375×667 的 CSS 尺寸 canvas 实际 backing store 是 1125×2001。正确初始化：

ts
// 节选：canvas 高清适配标准三行
const dpr = window.devicePixelRatio || 1;
canvas.width = cssWidth * dpr;   // 物理像素
canvas.height = cssHeight * dpr;
ctx.scale(dpr, dpr);             // 之后全部用 CSS 像素坐标绘制

2. 触摸坐标要换算。 touch.clientX 是视口 CSS 像素，要转成画布内坐标：(clientX - rect.left) * (canvas.width / rect.width)。漏掉 canvas 被 CSS 缩放（比如等比适配留了黑边）这一步，点击判定就会整体偏移。

触摸事件 vs 鼠标事件：移动端优先用 Pointer Events（pointerdown/move/up），一套代码同时覆盖触摸、鼠标、触控笔。注意 touchstart 要 { passive: false } 才能 preventDefault() 阻止页面滚动——Chrome 73+ 默认 passive，直接 preventDefault 会报警告且无效。

虚拟摇杆是移动游戏标配：touchstart 记录原点，touchmove 算偏移向量（限幅在摇杆半径内），touchend 归零。偏移向量归一化后就是角色的移动方向。

应用实践 ​

  • 多点触控：每个触摸点有独立 identifier，虚拟摇杆要锁定按下那一刻的 id，后续 move 只响应同一 id——否则两根手指会抢摇杆。
  • 安全区适配：iPhone 刘海屏用 env(safe-area-inset-*) 给 UI 留白，不然血条被刘海遮住。
  • 横竖屏：H5 用 screen.orientation.lock()（需要全屏态）；小游戏在 game.json 配 deviceOrientation。

108.5 微信小游戏平台差异与适配层 ​

概念解析 ​

微信小游戏不是小程序：没有 WXML/WXSS，入口是 game.js，唯一的 UI 就是一块 canvas。它和 H5 的差异集中在五个方面：

维度H5 浏览器微信小游戏
画布获取document.querySelector("canvas")wx.createCanvas()（首次调用为主画布）
生命周期visibilitychangewx.onShow / wx.onHide
存储localStorage（键值字符串）wx.setStorageSync（可存对象，空值返回 "" 而非 null）
包体积无硬性限制主包 4MB，整包分包后 ≤ 30MB（普通分包）
音频Audio / WebAudio（有自动播放限制）wx.createInnerAudioContext()

**开放数据域（Open Data Context）**是微信独有的排行榜机制：好友关系链数据不能进主域，必须在独立的开放数据域里用 wx.getFriendCloudStorage() 拉取并绘制到一块共享 canvas 上，主域只能把这块 canvas 当图片贴上来——所以排行榜不能响应主域的点击事件，交互按钮要么做在主域、要么用 wx.getOpenDataContext().postMessage() 通信。

分包加载：game.json 里配 subpackages，wx.loadSubpackage() 回调后再 require 分包代码。首屏只放主包（启动页 + 核心玩法），美术资源走 CDN + wx.getFileSystemManager() 本地缓存。

适配层是把以上差异收敛到一处的架构手段：游戏逻辑只面向抽象接口编程，构建/启动时按环境注入实现。

完整代码示例 ​

ts
// 文件: examples/108-04-platform-adapter.ts
// 平台适配层：同一份游戏逻辑跑在 H5 浏览器与微信小游戏
// 目标：游戏代码只依赖抽象接口，环境差异（canvas 获取、存储、生命周期）收敛到一处

import assert from "node:assert";

/** 游戏代码只面向这个接口编程 */
interface PlatformAdapter {
  readonly name: "h5" | "wxgame";
  getScreenSize(): { width: number; height: number; dpr: number };
  storageGet(key: string): string | null;
  storageSet(key: string, value: string): void;
  onShow(cb: () => void): void; // 回到前台（小游戏 onShow / H5 visibilitychange）
  onHide(cb: () => void): void; // 切到后台
}

/** 环境探测：小游戏的标志是全局 wx 对象且带 createCanvas */
function detectPlatform(env: Record<string, unknown>): "h5" | "wxgame" {
  const wx = env.wx as { createCanvas?: unknown } | undefined;
  if (wx && typeof wx.createCanvas === "function") return "wxgame";
  if (typeof env.document !== "undefined") return "h5";
  throw new Error("未知运行环境：既没有 wx.createCanvas 也没有 document");
}

/** H5 实现：localStorage + visibilitychange */
function createH5Adapter(env: {
  document: { hidden: boolean; addEventListener: (t: string, cb: () => void) => void };
  localStorage: { getItem: (k: string) => string | null; setItem: (k: string, v: string) => void };
  innerWidth: number;
  innerHeight: number;
  devicePixelRatio: number;
}): PlatformAdapter {
  return {
    name: "h5",
    getScreenSize: () => ({
      width: env.innerWidth,
      height: env.innerHeight,
      dpr: env.devicePixelRatio,
    }),
    storageGet: (k) => env.localStorage.getItem(k),
    storageSet: (k, v) => env.localStorage.setItem(k, v),
    onShow: (cb) =>
      env.document.addEventListener("visibilitychange", () => {
        if (!env.document.hidden) cb();
      }),
    onHide: (cb) =>
      env.document.addEventListener("visibilitychange", () => {
        if (env.document.hidden) cb();
      }),
  };
}

/** 微信小游戏实现：wx API */
function createWxAdapter(wx: {
  getSystemInfoSync(): { windowWidth: number; windowHeight: number; pixelRatio: number };
  getStorageSync(k: string): string;
  setStorageSync(k: string, v: string): void;
  onShow(cb: () => void): void;
  onHide(cb: () => void): void;
}): PlatformAdapter {
  return {
    name: "wxgame",
    getScreenSize: () => {
      const info = wx.getSystemInfoSync();
      return { width: info.windowWidth, height: info.windowHeight, dpr: info.pixelRatio };
    },
    // 小游戏 getStorageSync 无值时返回空字符串而非 null，这里统一成 null
    storageGet: (k) => {
      const v = wx.getStorageSync(k);
      return v === "" ? null : v;
    },
    storageSet: (k, v) => wx.setStorageSync(k, v),
    onShow: (cb) => wx.onShow(cb),
    onHide: (cb) => wx.onHide(cb),
  };
}

/** 游戏逻辑：只面向 PlatformAdapter，不知道自己在哪个平台 */
function saveHighScore(platform: PlatformAdapter, score: number): number {
  const prev = Number(platform.storageGet("high_score") ?? 0);
  const best = Math.max(prev, score);
  platform.storageSet("high_score", String(best));
  return best;
}

function runAssertions() {
  // ---------- 测试 1：环境探测 ----------
  const fakeWx = {
    createCanvas: () => ({}),
    getSystemInfoSync: () => ({ windowWidth: 375, windowHeight: 667, pixelRatio: 3 }),
    _store: new Map<string, string>(),
    getStorageSync(k: string) { return this._store.get(k) ?? ""; },
    setStorageSync(k: string, v: string) { this._store.set(k, v); },
    onShow(_cb: () => void) {},
    onHide(_cb: () => void) {},
  };
  const fakeH5Env = {
    document: { hidden: false, addEventListener: (_t: string, _cb: () => void) => {} },
    localStorage: {
      _m: new Map<string, string>(),
      getItem(k: string) { return this._m.get(k) ?? null; },
      setItem(k: string, v: string) { this._m.set(k, v); },
    },
    innerWidth: 390,
    innerHeight: 844,
    devicePixelRatio: 2,
  };
  assert.equal(detectPlatform({ wx: fakeWx }), "wxgame");
  assert.equal(detectPlatform(fakeH5Env as unknown as Record<string, unknown>), "h5");
  assert.throws(() => detectPlatform({}), /未知运行环境/);
  console.log("[1/4] 环境探测 OK");

  // ---------- 测试 2：同一游戏逻辑在两个平台行为一致 ----------
  const wxAdapter = createWxAdapter(fakeWx);
  const h5Adapter = createH5Adapter(fakeH5Env);
  assert.equal(saveHighScore(wxAdapter, 800), 800);
  assert.equal(saveHighScore(wxAdapter, 500), 800); // 不覆盖更高分
  assert.equal(saveHighScore(h5Adapter, 1200), 1200);
  assert.equal(saveHighScore(h5Adapter, 300), 1200);
  console.log("[2/4] 跨平台逻辑一致 OK, wx best:", saveHighScore(wxAdapter, 0), "h5 best:", saveHighScore(h5Adapter, 0));

  // ---------- 测试 3：存储差异归一化（空串 vs null） ----------
  assert.equal(wxAdapter.storageGet("not_exist"), null, "小游戏空值应统一为 null");

  // ---------- 测试 4：屏幕尺寸含 DPR（高清屏适配必需） ----------

应用实践 ​

  • 适配层只包「有差异」的能力：rAF、canvas 2D 上下文、触摸事件两边几乎一致，不必抽象；存储、生命周期、分享、支付差异大，必须抽象。抽象面越大维护成本越高。
  • 小游戏 onHide 后 rAF 照样回调：H5 切后台 rAF 自动暂停，小游戏不会——onHide 里要手动停循环，onShow 里恢复，否则后台空跑耗电。
  • wx.createCanvas 只有第一次返回主画布：之后再调用返回的是离屏 canvas。主画布尺寸等于屏幕尺寸，改宽高会清空内容。
  • 真机差异远大于文档：iOS 微信和 Android 微信的 JS 引擎不同（JSCore vs V8），Date 解析、正则、BigInt 都有差异——上线前两端真机各跑一遍。

108.6 H5 游戏性能优化清单 ​

掉帧归因顺序 ​

掉帧先分类再优化，别上来就改代码：

类型特征定位工具常见根因
JS 长任务帧间隔规律性突刺Performance 面板长任务红标GC、大数组遍历、同步解码大图
渲染过载整体帧率低但平稳drawImage 计数、引擎统计同屏精灵太多、全屏重绘
内存爬坡玩越久越卡Memory 面板快照对比闭包引用、事件监听未解绑、纹理未释放

优化清单（按收益排序） ​

  1. 只画脏区域：背景静止时别每帧全屏 clearRect + 重绘，只重绘变化的矩形区域。收益最大，改动也最大——分层 canvas（背景层 + 动态层）是更常见的折中。
  2. 减少 draw 调用数：同图集的精灵连续绘制（纹理不切换）；静态文字/分数预渲染到离屏 canvas，每帧一次 drawImage 贴上去，代替每帧 fillText。
  3. 对象池：见 108.3，消灭 GC 抖动。
  4. 整数坐标绘制：drawImage 传小数坐标触发浏览器亚像素采样，慢且糊——Math.round 后再画（像素游戏尤其明显）。
  5. 离屏 canvas 缓存：复杂矢量图形（圆角血条、渐变技能图标）每帧重算路径太贵，预渲染一次缓存成位图。
  6. 事件委托 + 被动监听：canvas 上只有一个触摸监听，内部按区域分发；不阻止滚动的监听加 { passive: true }。
  7. 资源瘦身：图片压 WebP/压缩 PNG（TinyPNG），音效限 44.1kHz 单声道，背景音乐用流式而不是全量解码。

108.7 自测题 ​

1. 为什么游戏逻辑要用固定时间步长，而不是每帧用真实 dt？切后台 10 秒回来会发生什么？【基础】

真实 dt 不稳定：120Hz 屏 dt≈8ms、60Hz 屏 dt≈16ms、卡顿时可达数百 ms。同样的代码在不同设备上物理行为不同——高刷屏游戏速度快一倍，大 dt 一步跨过碰撞体导致穿墙。固定步长保证「同样的输入序列，任何设备上得到同样的世界状态」，这是可复现性的基础。

切后台 10 秒回来，累积器攒了 600 步：不设上限会触发死亡螺旋（补步导致更卡、攒更多）。正确做法是单帧补步数钳制（如最多 5 步），积压时间直接丢弃，宁可慢动作也不追帧。

2. 精灵动画为什么不能「每渲染一帧推进一帧」？正确的帧调度怎么写？【基础】

因为渲染帧率因设备而异：60fps 设备动画快一倍，30fps 设备慢一倍，卡顿时动画一顿一顿。正确写法是动画进度只由时间驱动：记录已播放时长 time，当前帧 = floor(time × fps) % 帧数。这样 30fps 和 60fps 设备在任意相同时刻看到同一帧，只是采样密度不同。

单次播放的剪辑（死亡动画）要 loop=false：播完停在末帧、回调只触发一次，后续 update 永远返回末帧。

3. 对象池解决什么问题？三个必须做的设计点是什么？【进阶】

解决 GC 抖动：游戏里子弹/粒子/飘字每帧 new 几十个短命对象，几秒触发一次 minor GC，主线程停 5-10ms，表现为规律性掉帧。对象池把创建/销毁改成获取/归还，对象永久存活。

三个设计点：① reset 必须彻底——归还时重置全部字段，脏数据泄漏到下次使用是最高频 bug；② 池要有上限——瞬时峰值后空闲队列不能无限膨胀，超上限丢给 GC；③ 重复归还防呆——用 inUse 集合记录，同一对象 release 两次不能入池两次。

4. H5 游戏在 dpr=3 的手机上画面模糊、点击判定偏移，根因和修复分别是什么？【进阶】

模糊：canvas 的 CSS 尺寸（375×667）和 backing store 尺寸混用——默认 canvas.width 等于 CSS 尺寸，dpr=3 屏被放大 3 倍显示导致模糊。修复：canvas.width = cssWidth * dpr，再 ctx.scale(dpr, dpr)，之后全部用 CSS 像素坐标绘制。

点击偏移：touch.clientX 是视口坐标，要转成画布内坐标：(clientX - rect.left) * (canvas.width / rect.width)。漏掉 canvas 被 CSS 缩放（等比适配留黑边）这步换算，判定就会整体偏移。

5. 微信小游戏与 H5 在生命周期和存储上的关键差异是什么？适配层应该抽象哪些能力？【进阶】

生命周期：H5 切后台 rAF 自动暂停；小游戏 onHide 后 rAF 照样回调——必须 onHide 手动停循环、onShow 恢复，否则后台空跑耗电。

存储：localStorage 只存字符串、无值返回 null；wx.setStorageSync 可存对象、getStorageSync 无值返回空字符串 ""。适配层要归一化（空串统一成 null），否则 storageGet("x") ?? 0 在两端行为不同。

抽象面：只包有差异的能力——存储、生命周期、分享、支付、画布获取。rAF、触摸事件、2D 上下文两端几乎一致，不必抽象。抽象面越大维护成本越高。

6. 一个 H5 弹幕射击游戏，玩家反馈「每玩 30 秒左右规律卡一下，越玩越卡」，按归因顺序怎么排查？【挑战】

先分类：「规律性卡 + 越玩越卡」是两个独立症状的叠加——规律性卡顿指向 GC 抖动或定时任务；越玩越卡指向内存泄漏（内存爬坡逼近 GC 阈值，GC 越来越频繁）。

排查顺序：

  1. Performance 面板录 30 秒：卡顿帧是长任务红标（JS 问题）还是渲染紫色块（绘制问题）？规律长任务且火焰图底部是 GC → 确认 GC 抖动。
  2. 检查每帧分配：子弹/粒子/伤害数字是不是每帧 new？上对象池，预热到峰值 80%。
  3. Memory 面板两次快照对比（玩 1 分钟 vs 玩 5 分钟）：哪个对象计数只涨不跌？常见是事件监听未解绑（敌人死了但监听还在）、粒子纹理未释放、闭包引用已销毁对象。
  4. 检查数组清理：死亡敌人是 splice 掉了还是只标记 alive=false 但永远留在数组里遍历？后者同屏遍历成本随时间线性涨，也会造成「越玩越卡」。

修复后验证：同一场景玩 10 分钟，内存曲线应是锯齿形（GC 后回落）而非斜坡形，帧时间方差应显著下降。
