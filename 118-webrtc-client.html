第一百一十八部分 · WebRTC 客户端实战——信令、协商与弱网 ​

🧭 返回总目录｜上一篇：第一百一十七部分 · 移动端输入法与软键盘适配｜关联章节：第六十八部分 · 音视频架构 · 第一百一十六部分 · IM 弱网与高并发治理 · 第六部分 · 网络协议

本部分内容 ​

WebRTC 不是调一个 RTCPeerConnection 就能通话：信令要自己传，协商要自己排，弱网要自己扛。这一册按一通呼叫的生命周期展开——信令状态机、采集与设备切换、offer/answer/ICE 协商、弱网自适应、多人布局与排障。与 68 册的分工是：那一册回答「该不该用 RTC」，这一册回答「用 RTC 时客户端每一行怎么写」。四个示例都是纯 TypeScript 模型，真正难的不是 addIceCandidate，而是它之前的等待、缓冲与超时。

118.1 链路与信令 ​

概念解析 ​

WebRTC 标准只定义媒体面（SRTP）与数据面（SCTP/DTLS），信令不在标准里，必须业务用 WebSocket/HTTP 传输。「连不上」的第一嫌疑人永远是信令。

平面载体断了的后果
信令WS / HTTPS无法建立与重连，状态停在旧值
媒体SRTP over UDP（可回落 TCP/TLS）画面卡住、ICE 失败
数据SCTP over DTLS文字、文件、控制消息不通

拓扑决定工程量：mesh 每两人一条流，N 人需 N×(N-1)/2 条，只适合 3~4 人；SFU 每人只上行一路、服务端按需转发，是会议标配；MCU 服务端混流，兼容好但延迟与成本高。

信令客户端的最小职责是状态机而非一堆布尔开关：idle → calling → connected，任一步失败进 failed。三条硬约束：超时兜底（8~12 秒无应答即 failed 并释放媒体）、迟到消息不得复活会话、定时器必须带会话代号。

真实场景：出海 1v1 视频社交 App，用户在印尼、越南用 4G 匹配，媒体经新加坡 TURN 中转。产品要求「15 秒无人接听自动跳过」，于是应答超时 8 秒、ICE 预算 7 秒。出过的事故：挂断后立刻重拨，上一通遗留的 setTimeout 在新通话第 8 秒把它打成 failed，表现为「刚接通就断线」——根因是定时器没有代号。

完整代码示例 ​

ts
// 文件: examples/118-01-signaling-state.ts（核心片段）
const TRANSITIONS: Record<CallState, Partial<Record<CallEvent, CallState>>> = {
    idle: { dial: 'calling' },
    calling: { answer: 'connected', iceFailed: 'failed', timeout: 'failed', remoteHangup: 'idle' },
    connected: { remoteHangup: 'idle', iceFailed: 'failed' },
    failed: { reset: 'idle' }, // failed 只允许显式 reset
};

transition(event: CallEvent, nowMs: number): boolean {
    const next = TRANSITIONS[this._state][event];
    if (next === undefined) return false; // 非法迁移：拒绝且状态不变
    this._state = next;
    if (event === 'dial') { this.dialedAt = nowMs; this.generation += 1; }
    else if (next === 'idle' || next === 'failed') this.dialedAt = null;
    return true;
}

/** 超时回调必须带发起时的 generation，旧会话的定时器直接忽略 */
tick(nowMs: number, generation: number): void {
    if (generation !== this.generation) return;
    if (this._state !== 'calling' || this.dialedAt === null) return;
    if (nowMs - this.dialedAt >= this.answerTimeoutMs) this.transition('timeout', nowMs);
}

运行方式：npx tsx examples/118-01-signaling-state.ts

应用实践 ​

  • 所有 SDP/ICE/挂断消息都带 callId，客户端只处理当前 callId，比状态机代号更外层。
  • failed 后 UI 只给「重试 / 挂断」两个出口；无限自动重拨会把用户困在「连接中」。
  • ⚠️ connected 前不要展示「通话中」：SDP 协商完成不等于媒体已流动，首帧到达才算接通。

118.2 媒体采集与设备切换 ​

概念解析 ​

采集参数是带宽预算、设备能力、场景的交集，不是越清晰越好。

场景分辨率/帧率目标码率音频
1v1 视频社交640×480 @24600~900kbps单声道，3A 全开
会议小格640×360 @15250~400kbps单声道，3A 全开
屏幕共享1920×1080 @10~151.2~2Mbps系统声可选，关 3A
音乐场景640×360 @30400kbps立体声，关降噪与 AGC

echoCancellation、noiseSuppression、autoGainControl 对 1v1 是刚需，不开回声消除对方会听到自己延迟返回的声音；音乐场景则必须关掉，降噪会把伴奏当噪声削掉。设备切换用 replaceTrack() 而不是重新协商：先拿新 track，await sender.replaceTrack(next) 成功后再 oldTrack.stop()。顺序反了会黑帧 100~300ms；不 stop 会占住设备，iOS 上切几次后彻底打不开。改分辨率或摄像头切屏幕共享时编码档位变了，必须重新协商。

完整代码示例 ​

ts
// 浏览器侧写法（示例文件为状态机模型，无此段）
async function switchCamera(pc: RTCPeerConnection, oldTrack: MediaStreamTrack) {
    const stream = await navigator.mediaDevices.getUserMedia({
        video: { facingMode: 'environment', width: { ideal: 640 }, height: { ideal: 480 } },
        audio: false,
    });
    const next = stream.getVideoTracks()[0];
    const sender = pc.getSenders().find((s) => s.track?.kind === 'video');
    if (!sender) { next.stop(); throw new Error('缺少视频 sender'); }
    try {
        await sender.replaceTrack(next);
        oldTrack.stop(); // 替换成功后才释放旧设备
    } catch (error) {
        next.stop(); // 失败：释放新轨道，继续用旧轨道
        throw error;
    }
}

应用实践 ​

  • 采集失败分级：NotAllowedError 引导授权，NotFoundError 降级纯文字，NotReadableError 提示关闭占用设备的 App。
  • 切前后摄重新 getUserMedia，不要对旧 track 调 applyConstraints——Android 厂商实现差异大，常静默不生效。
  • ⚠️ 切后台暂停本地视频 track，回前台恢复；iOS 后台会直接掐断采集。

118.3 协商（offer/answer/ICE/trickle） ​

概念解析 ​

协商分两步：SDP 描述「支持什么、要什么」，ICE 描述「怎么找到对方」。trickle 指候选发现一个发一个，把建连从秒级压到几百毫秒。

候选类型来源缺失的后果
host本机网卡同网段都失败，多为 mDNS/防火墙
srflxSTUN 反射跨公网只能走 TURN，成本上升
prflx连通检查中发现特殊 NAT 时补位
relayTURN 中转对称 NAT / UDP 被封时无兜底

最常见的错：收到候选就立刻 addIceCandidate，没等 setRemoteDescription 完成。浏览器抛 InvalidStateError，实现用 try/catch 吞掉——先到的 host 能加，后到的 srflx/relay 全丢，于是「局域网通、跨网必挂、日志还安静」。正确做法是候选缓冲：描述未就绪入队、按字符串去重，就绪后按到达顺序冲刷；end-of-candidates 也要排队，冲刷后再收口。第二个坑是 glare（双方同时 offer），标准解法是 perfect negotiation：固定一端 polite（收到对方 offer 就 rollback），另一端 impolite。

真实反例：某海外 1v1 App 的 iOS 端拿到 host 候选立即调用，Android 端尚未设置远端描述，异常被吞；relay 同样被丢。办公室 Wi-Fi 全通，上线后印尼 4G 跨网 10 秒 ICE failed，故障率约 18%。

完整代码示例 ​

ts
// 文件: examples/118-02-ice-trickle.ts（核心片段）
addRemoteCandidate(candidate: IceCandidate): 'buffered' | 'applied' | 'duplicate' | 'rejected' {
    if (this.closed || this.endQueued) return 'rejected';
    const key = `${this.generation}|${candidateKey(candidate)}`;
    if (this.seen.has(key)) return 'duplicate';
    this.seen.add(key);
    if (!this.remoteDescriptionSet) {
        this.buffer.push(candidate); // 描述未就绪：排队，绝不丢
        return 'buffered';
    }
    this.applied.push(candidate);
    return 'applied';
}

/** 描述就绪：按到达顺序冲刷；结束标记若已排队，立即收口 */
setRemoteDescription(): number {
    this.remoteDescriptionSet = true;
    const count = this.buffer.length;
    this.applied.push(...this.buffer);
    this.buffer = [];
    if (this.endQueued) this.closeCandidateStream();
    return count;
}

运行方式：npx tsx examples/118-02-ice-trickle.ts

应用实践 ​

  • ICE restart 后 ufrag 变了，对端会重发同批候选，去重集合必须按 generation 清空。
  • SFU 订阅新主播会触发服务端 re-offer，用一条 Promise 队列串行执行 SDP 操作，不能并发 setRemoteDescription。
  • ⚠️ 候选日志只记类型与协议，不打印完整 IP 与端口，避免隐私合规问题。

118.4 弱网（Simulcast/SVC、码率自适应、断线重连） ​

概念解析 ​

弱网是带宽波动、丢包、抖动、延迟同时发生，客户端分三层应对：

  1. 编码层：Simulcast 同时编三档（1080p/720p/360p），SFU 按订阅端网络选层；SVC 编一条可分层码流（VP9 L1T3、AV1），服务端按需截取。Simulcast 简单但上行×3，SVC 省带宽但 Safari 支持有限，跨端产品通常先上 Simulcast。
  2. 发送层：按 getStats 的丢包/RTT 调 maxBitrate，核心是滞回：坏样本快降（×0.7）、好样本慢升（×1.1 且需连续 3 个干净窗口）、灰区不动、降档后冷却 2 个窗口。
  3. 连接层：disconnected 先等 3~5 秒（多为瞬时抖动会自愈），确认 failed 后 restartIce()；只有信令断了才重建 RTCPeerConnection。

经验阈值：丢包 ≥10% 或 RTT ≥400ms 立即降档；丢包 2%~10% 是死区；丢包 <2% 且连续 3 窗口才升；下限 150kbps 保证人脸轮廓可辨。

反例一：把「丢包 >3% 降、❤️% 升」写成每窗口都执行，目标码率每 2 秒在 300~900kbps 间跳，用户反馈画面一直清晰/模糊闪烁。加死区与冷却后曲线变成阶梯。反例二：一 disconnected 就重建 PC，弱网下 30 秒重建 5 次、每次都黑屏；正确路径是观察 5 秒 → failed → restartIce() → 仍失败才重建，且复用本地 track。

完整代码示例 ​

ts
// 文件: examples/118-03-bitrate-adapt.ts（核心片段）
sample(input: NetworkSample): Decision {
    const congested = input.lossRate >= cfg.lossHigh || input.rttMs >= cfg.rttHigh;
    if (congested) {
        const next = Math.max(cfg.minKbps, Math.round(this.target * cfg.decreaseFactor));
        this.goodStreak = 0;
        this.cooldown = cfg.cooldownTicks; // 降档后冷却，禁止立刻回升
        return this.commit(next, 'lower', 'congested');
    }
    if (this.cooldown > 0) {
        this.cooldown -= 1;
        this.goodStreak = 0;
        return this.commit(this.target, 'hold', 'cooldown');
    }
    if (input.lossRate >= cfg.lossLow) { // 死区：2%~10%，不动
        this.goodStreak = 0;
        return this.commit(this.target, 'hold', 'deadband');
    }
    this.goodStreak += 1;
    if (this.goodStreak >= cfg.goodTicksToRaise && this.target < cfg.maxKbps) {
        this.goodStreak = 0;
        return this.commit(Math.min(cfg.maxKbps, Math.round(this.target * 1.1)), 'raise', 'good-streak');
    }
    return this.commit(this.target, 'hold', 'good-wait');
}

运行方式：npx tsx examples/118-03-bitrate-adapt.ts

应用实践 ​

  • 降档要同时降分辨率与帧率：只降码率会让 720p 在 200kbps 下糊成马赛克。
  • 丢包恢复后主动请求关键帧（PLI），否则接收端会花屏到下一个自然关键帧。
  • ⚠️ 不要用 bytesSent 瞬时差值算带宽：stats 时间戳不等间隔，必须按 timestamp 差分。

118.5 多人会议布局与性能 ​

概念解析 ​

布局是纯数学：给定容器宽高、N 个 16:9 格子与间距，选使单格面积最大的列数。

N列×行1280×720、gap=8 下单格
42×2632×355
63×2416×234
93×3416×234
164×4308×173

真正的边界是性能：移动端同时硬解 720p 通常只撑 4~6 路，超了掉帧、发热、耗电。三条策略：只给可视区格子挂 srcObject，离屏置 null（隐藏的 video 元素仍可能解码）；小格子向 SFU 订阅低层；音频全部保留、画面按需，用 audioLevel 选发言人放大。

完整代码示例 ​

ts
// 宫格布局：枚举列数，取单格面积最大者，格子按 16:9 内切
function computeGrid(count: number, width: number, height: number, gap = 8) {
    let best = { cols: 1, rows: count, tileW: 0, tileH: 0 };
    for (let cols = 1; cols <= count; cols++) {
        const rows = Math.ceil(count / cols);
        const cellW = (width - gap * (cols - 1)) / cols;
        const cellH = (height - gap * (rows - 1)) / rows;
        const tileW = Math.min(cellW, (cellH * 16) / 9);
        const tileH = (tileW * 9) / 16;
        if (tileW * tileH > best.tileW * best.tileH) best = { cols, rows, tileW, tileH };
    }
    return best;
}

应用实践 ​

  • ≤9 人全量渲染；>9 人只渲染「发言者 + 前 8 个」，其余头像占位，点击才订阅；发言人切换加 2 秒防抖。
  • ⚠️ 布局用 CSS Grid + aspect-ratio，不要 JS 逐个绝对定位；Vue 里别在 watch 中重建整棵视频 DOM，diff 会短暂销毁 srcObject，表现为集体闪黑。

118.6 录制/屏幕共享 ​

概念解析 ​

录制用 MediaRecorder，第一道坎是容器与编码的浏览器差异：

浏览器可用 mimeType备注
Chrome/Edgevideo/webm;codecs=vp9,opus首选 VP9，体积小
Firefoxvideo/webm;codecs=vp8,opusVP9 不稳定
Safarivideo/mp4;codecs=avc1,mp4a不支持 WebM，必须探测

流程是 MediaRecorder.isTypeSupported() 逐个探测取第一个可用；都不支持就降级只录音频或禁用按钮。直接传 WebM 给 Safari 会抛 NotSupportedError，异常没捕获，用户看到的就是「点了录制没反应」。录双端通话要混流：视频用 Canvas 逐帧合成，音频用 AudioContext + MediaStreamDestination 混合。屏幕共享用 getDisplayMedia，必须由用户手势触发，用户可在浏览器 UI 随时停止，必须监听 track.onended 切回摄像头。timeslice 建议 1000ms，崩溃最多丢 1 秒，但分片不是独立可播文件，服务端要按序号拼接。

完整代码示例 ​

ts
// 录制器选型：按浏览器能力挑 mimeType，避免 Safari 直接抛 NotSupportedError
const CANDIDATES = [
    'video/webm;codecs=vp9,opus',
    'video/webm;codecs=vp8,opus',
    'video/mp4;codecs=avc1,mp4a',
];

function pickMimeType(): string | null {
    if (typeof MediaRecorder === 'undefined') return null;
    return CANDIDATES.find((type) => MediaRecorder.isTypeSupported(type)) ?? null;
}

function startRecording(stream: MediaStream, onChunk: (blob: Blob) => void): MediaRecorder {
    const mimeType = pickMimeType();
    if (!mimeType) throw new Error('当前浏览器不支持录制');
    const recorder = new MediaRecorder(stream, { mimeType, videoBitsPerSecond: 2_000_000 });
    recorder.ondataavailable = (event) => {
        if (event.data.size > 0) onChunk(event.data); // 分片上传，崩溃最多丢 1 秒
    };
    recorder.start(1000);
    return recorder;
}

应用实践 ​

  • 共享前给 track 设 contentHint：文档/代码用 'text'，视频用 'motion'，直接影响清晰度与流畅度的取舍；共享期间本地摄像头降到 15fps。
  • ⚠️ 录制前提示并取得双方同意（海外市场尤其敏感），文件设保留期与权限；不要录 4K 屏，编码器吃满 CPU 会先卡死通话。

118.7 排障（getStats、ICE 失败） ​

概念解析 ​

getStats() 返回累计计数器，必须按 timestamp 做区间差分，直接看累计值毫无意义。

字段健康线异常含义
packetsLost丢包率 <5%上行拥塞或无线质量差
jitter<30ms抖动大，音频断续
roundTripTime<300ms跨区域或中转绕路
framesDropped丢帧率 <10%解码/渲染跟不上
qualityLimitationReasonnonecpu 是本机瓶颈，bandwidth 才是网络
frameWidth/Height接近订阅档位突降说明自适应已降档

诊断顺序：先丢包与 RTT（网络），再 framesDropped / qualityLimitation（本机），最后看分辨率是否降级。qualityLimitationReason = 'cpu' 是分水岭：网络没问题，降码率无用，必须降分辨率或帧率。

ICE 失败分诊：只有 host 无 srflx/relay → STUN/TURN 未配或被拦，配 TURN 并查 3478/443；有 srflx 但跨网失败 → 对称 NAT，打洞失败，用 iceTransportPolicy: 'relay' 兜底；卡在 checking 超 10s → UDP 被封，部署 turns:443；restart 后仍失败 → 信令已断，重建 PC。

真实场景：某海外会议产品「印度用户 90% 通话失败」，埋点显示失败通话 relay 候选占比 0、成功通话 62%——TURN 只开 UDP 3478，当地运营商封 UDP。加开 TLS 443 后失败率降到 4%。

完整代码示例 ​

ts
// 文件: examples/118-04-stats-diagnosis.ts（核心片段）
function deriveMetrics(prev: OutboundStats, cur: OutboundStats, baseline: Baseline) {
    const dtSec = (cur.timestampMs - prev.timestampMs) / 1000;
    if (dtSec <= 0) return null;
    if (cur.packetsSent < prev.packetsSent || cur.packetsLost < prev.packetsLost) return null; // 计数器重置
    const sent = cur.packetsSent - prev.packetsSent;
    const lost = cur.packetsLost - prev.packetsLost;
    if (sent <= 0) return null;
    const lostFrames = cur.framesDropped - prev.framesDropped;
    const areaRatio = (cur.frameWidth * cur.frameHeight) / (baseline.width * baseline.height);
    return {
        lossRate: lost / (sent + lost), // 分母含丢失包，避免高丢包时低估
        rttMs: cur.roundTripTimeMs,
        jitterMs: cur.jitterMs,
        dropRate: lostFrames / (Math.round(cur.framesPerSecond * dtSec) + lostFrames),
        resolutionDegraded: areaRatio < 0.5 || cur.frameHeight < baseline.height * 0.6,
    };
}

运行方式：npx tsx examples/118-04-stats-diagnosis.ts

应用实践 ​

  • 每 2 秒采一次、保留最近 30 个窗口，随 callId 上报；只报最终值分不清「一直差」还是「某一刻崩」。
  • 两端都采：上行丢包看发送端 remote-inbound-rtp，下行看接收端 inbound-rtp，单端会误判责任方。
  • ⚠️ 不要每帧调 getStats，1~2 秒一次足够，且避免与协商并发。

118.8 自测题 ​

先自己作答，再展开参考答案。

1. WebRTC 为什么必须自己实现信令？【基础】

标准只定义媒体面与数据面，offer/answer/ICE 的传输没有标准化，浏览器不提供「连接对方」的入口。信令断了媒体可能继续，但无法重连、新增订阅或正常挂断，ICE 一失败就没有恢复通道。

2. 信令状态机为什么必须带超时与会话代号？【基础】

超时防止「一直呼叫中」，8~12 秒无应答就转 failed 并释放媒体。代号防止旧回调误伤：setTimeout 属于发起它的那一通电话，重拨后旧回调仍会触发，不校验就会在新通话第 8 秒把它打成 failed。

3. 切摄像头为什么用 replaceTrack？顺序有什么讲究？【基础】

replaceTrack 不改 SDP 编码参数，只换同规格的源，不重收集 ICE、不黑屏。顺序：新 track → await replaceTrack → 成功后 stop 旧 track。先 stop 会黑帧；不 stop 会占设备，iOS 上切几次后打不开。

4. 远端描述未设置就 addIceCandidate 会发生什么？为什么「局域网通、跨网不通」？【进阶】

浏览器抛 InvalidStateError，实现里 try/catch 吞掉后丢弃。先到的 host 也被丢，局域网靠 host 直连能通；跨网需要 srflx/relay，正是被丢的那批，于是跨网必失败且日志安静。解法是缓冲 + 去重 + 就绪后保序冲刷。

5. host、srflx、prflx、relay 的优先级与适用场景？【进阶】

优先级 host(126) > srflx/prflx(110) > relay(0)。host 同局域网直连；srflx 用 STUN 反射做 NAT 打洞；prflx 在连通检查中发现，补位特殊 NAT；relay 是 TURN 中转，对称 NAT 或 UDP 被封时唯一兜底。生产必须部署 TURN。

6. 码率自适应为什么要「快降慢升 + 死区 + 冷却」？【进阶】

快降避免持续丢包花屏；慢升避免恢复后立刻再拥塞；死区避免阈值附近的小波动导致锯齿；冷却避免「降—升—再降」的呼吸效应。去掉死区与冷却，画面会每 2 秒清晰/模糊一次。

7. disconnected 时做什么？何时重建 PC？【进阶】

先观察 3~5 秒，多数是瞬时抖动会自愈；持续不恢复转 failed 后先 restartIce()（复用同一 PC 与本地 track）。restart 后仍失败、或信令已断，才重建 RTCPeerConnection。一 disconnected 就重建会反复黑屏。

8. 9 人以上会议如何控制解码与渲染开销？【挑战】

只给可视区 video 挂 srcObject，离屏置 null；小格子订阅 Simulcast 低层；超过 9 人只渲染发言者 + 前 8 个；页面隐藏时关远端视频只留音频。音频必须全保留，「听不见」比「看不清」严重得多。

9. 如何用 getStats 区分「网络差」与「本机编码扛不住」？【挑战】

看 qualityLimitationReason：bandwidth 或高丢包/高 RTT 指向网络；cpu 指向本机，此时 framesDropped 上升、分辨率可能已降，但网络指标正常。处置不同：网络差降码率/切层，CPU 差必须降分辨率或帧率。

10. 设计一次海外 1v1 视频通话的失败兜底链路。【挑战】

信令 8 秒应答超时 → failed 并释放采集；ICE 预算 7 秒，必要时强制 relay；码率 150kbps~1.5Mbps 自适应，连续劣化降分辨率；failed 先 restartIce 再重建 PC；每 2 秒 stats 随 callId 上报，记录候选类型与 qualityLimitationReason；失败页提供重试与「复制诊断信息」。
