43.1 SKU 选择器：组合置灰的判定算法 ​

43.1.1 概念解析 ​

选了「红色」之后「蓝色」要不要置灰？规则只有一条：

候选值 (维度, 值) 可选 ⟺ 存在一个有库存的 SKU，其规格完全包含「当前已选 ∪ {候选值}」。

这是超集判定，复杂度 O(SKU 数 × 规格维数)——SKU 几百个毫无压力，不必枚举 2^n 组合（规格一多立刻组合爆炸）。交互三规则：

  • 同维换选：点另一个颜色直接替换；
  • 再点取消：点已选中的值取消该维选择；
  • 联动置灰：任一维变化后重算所有候选值的可选性（红 L 无货 → 选红后 L 置灰；换蓝后 L 恢复）。

选满全部维度后用 findMatchedSku 精确命中唯一 SKU，价格随之确定。

43.1.2 核心代码 ​

ts
// 文件: examples/43-01-sku-selector.ts
export function isSelectable(skus, selected, dim, value): boolean; // 超集判定
export function findMatchedSku(skus, selected): Sku | null;        // 精确命中
export function toggleSpec(selected, dim, value): Selected;        // 换选/取消

运行方式：npx tsx examples/43-01-sku-selector.ts。

43.1.3 应用实践 ​

  • 更快的数据结构：把每个 SKU 的规格组合建成「已售状态无向图」，判定降为 O(1) 查边；规格多、SKU 数千以上才值得预计算；
  • 库存实时性：置灰基于快照库存，秒级轮询刷新；下单时服务端最终校验——前端置灰是体验，不是库存锁；
  • 无货文案：置灰按钮 hover 显示「到货通知」，比单纯 disabled 多一层转化。

43.2 购物车：价格计算管道 ​

43.2.1 概念解析 ​

购物车价格是一条有序管道：原价小计 → 满减 → 折扣 → 优惠券 → 兜底校验。三个铁律：

  • 顺序即规则：先满减再折扣（350.75 → 310.75 → 279.68）≠ 先折扣再满减（→ 288.68）。顺序是定价规则的一部分，必须显式固定并让用户可解释（明细 breakdown 逐步展示每步优惠多少）；
  • 分是唯一真源：金额一律用整数「分」运算，展示层才转元。0.1 + 0.2 !== 0.3，浮点算价账永远对不平；toFixed 是四舍五入到字符串的展示函数，不是精度修复工具；
  • 优惠要分摊：总优惠按金额占比摊到每个 item（末项用「总额 − 已分摊」兜底，保证 Σ分摊 = 总优惠）。退款按实付退——不分摊，部分退款时优惠就蒸发了。

43.2.2 核心代码 ​

ts
// 文件: examples/43-02-cart-pipeline.ts
export function subtotalFen(items): number;                       // 分整数小计
export function checkout(items, promos): { payableFen, steps };   // 有序管道 + 明细
export function apportion(items, totalDiscountFen): number[];     // 占比分摊 + 末项兜底
// Promotion: fullcut（每满减）| percent（折扣）| coupon（定额券，不超过应付）

运行方式：npx tsx examples/43-02-cart-pipeline.ts（示例演示了顺序敏感：同一组优惠不同顺序差 39 元）。

43.2.3 应用实践 ​

  • 明细展示是信任工程：价格页展示「原价 → 满减 −40 → 9 折 −31.07 → 券 −30 → 应付」，每一步可点击追溯规则——电商客诉大头是「为什么这个价」；
  • 服务端复算：前端算的应付只是预览，下单时服务端按同一管道复算——价格计算必须是单一权威源；
  • 券叠加规则产品化：哪些券可叠、满减与折扣的先后由营销策略定，管道只是把策略变成可配置的有序列表。

43.3 秒杀：按钮状态机与请求治理 ​

43.3.1 概念解析 ​

秒杀的前端战场不在「抢」，在治理自家用户：

  • 按钮状态机：idle → countdown → ready → submitting →（success | soldout | error）。submitting 是一把状态锁——锁住期间所有点击直接返回。比节流好的原因：节流在时间窗口内仍会放行多个请求，锁把「处理中」表达为状态，天然一次一个请求在途；
  • 服务器时钟校准：本地时钟不可信（用户可改），开屏取一次「服务器当前时间 − 本地当前时间」的偏移量，之后倒计时全部用 本地时间 + offset；
  • soldout 冻结：库存为 0 立即进入终态不再变化——抢不到的库存再怎么刷也刷不出来，刷的只是服务器和用户电量；
  • 失败克制：自动重试有上限（示例 3 次），超过停在 error 让用户手动决定，绝不无限循环。

43.3.2 核心代码 ​

ts
// 文件: examples/43-03-seckill.ts
export class SeckillPanel {
  syncTime(serverNow, localNow): void;      // 偏移校准
  tick(localNow, startAt, stockHint): void; // 每秒驱动状态机
  buy(): Promise<boolean>;                  // 仅 ready 放行，submitting 防连点
}

运行方式：npx tsx examples/43-03-seckill.ts（示例验证：连点 5 次只发 1 个请求、soldout 冻结、失败 3 次封顶）。

43.3.3 应用实践 ​

  • 真正的库存控制在后端：Redis 预扣 + 消息队列削峰 + 单用户限购——前端状态机只是把无效流量挡在网关之前；
  • 答题/滑块验证：高并发场景在 ready → submitting 之间插入人机验证，把机器人流量拦下；
  • 排队页：瞬时流量超阈值时进排队（前端轮询排队序号），体验比转圈报错好得多。

43.4 曝光埋点：可见性判定与批量上报 ​

43.4.1 概念解析 ​

埋点的价值取决于数据可信度，两个决定性设计：

  • 曝光标准：可见面积 ≥ 50% 且持续停留 ≥ 500ms 才算曝光（IntersectionObserver 给比例，计时器给停留）。滑过就算曝光的埋点，报表全是噪声，运营会据此做出错误决策；
  • 会话内去重：同一 target 只报一次（Set 记录）——刷新可见重复曝光不重复计费。

上报链路三件套：凑批（满 10 条或 5s 定时触发，请求数降一个量级）、失败回队（发送失败的事件放回队列头部，下次优先重发）、卸载兜底（visibilitychange → hidden 时用 navigator.sendBeacon 强制发出——页面卸载后普通 fetch 会被浏览器掐断）。

43.4.2 核心代码 ​

ts
// 文件: examples/43-04-exposure-tracking.ts
export function isQualifiedExposure(ratio, dwellMs): boolean; // ≥0.5 且 ≥500ms
export class ExposureTracker {
  track(targetId, ratio, dwellMs, at): void; // 判定 → 去重 → 入队 → 凑批
  flush(): Promise<void>;                    // 失败回队头
  flushOnHide(): void;                       // 卸载兜底（生产用 sendBeacon）
}

运行方式：npx tsx examples/43-04-exposure-tracking.ts。

43.4.3 应用实践 ​

  • 标准写进埋点文档：「曝光 = 50% 面积 + 500ms 停留」要成为全团队共识，客户端、服务端、分析侧三方对齐，否则数据口径打架；
  • 点击与曝光配对：点击事件带曝光序号，CTR = 点击/真实曝光——没有曝光门槛的 CTR 没有意义；
  • 采样与降级：超大盘流量按 userId 尾号采样；埋点 SDK 挂了不能拖死业务——try/catch 包裹一切埋点调用。

43.5 A/B 实验：稳定分桶与正交性 ​

43.5.1 概念解析 ​

A/B 实验前端要保证三件事：

  • 稳定性：hash(userId + "#" + experimentKey) 决定分组，同一用户永远同组——与请求次数、设备、时间无关；
  • 灰度放量：traffic ∈ (0,1]，哈希桶落在前 traffic 比例才进实验。分桶是前缀：放量 10% → 20% 时原用户分组不变，只新增用户（示例验证：扩量新增 88 人，原 10% 分组零变化）；
  • 正交性：不同实验（不同盐）的分组必须相互独立——用户在实验 A 的组别不影响他在实验 B 的组别。

正交性破灭的真实案例（本册示例踩过）：djb2 这类累乘哈希的最低位只由各字符奇偶性的异或累积决定——两个实验 key 不同但字符奇偶和相同，导致 bucket 奇偶完全同步，两个实验分组 100% 相关（control 全落在 v1，treatment 全落在 v2），实验结论互相污染。修复是加雪崩收尾（murmur3 fmix 风格：h ^= h >>> 15; h = imul(h, 大素数); h ^= h >>> 13），把高位信息混入低位。示例修复后四格 139/121/121/110，恢复独立。

43.5.2 核心代码 ​

ts
// 文件: examples/43-05-ab-experiment.ts
export function hashStr(input: string): number; // djb2 + fmix 雪崩收尾
export function assign(userId, cfg): Assignment; // bucket + traffic 灰度 + variants 均分
export function reportExposure(userId, cfg, sink): void; // 进实验即发曝光事件

运行方式：npx tsx examples/43-05-ab-experiment.ts（含均匀性、扩量一致性、正交性三组验证）。

43.5.3 应用实践 ​

  • 生产分桶在服务端：网关按规则下发实验分组，前端只消费 variant 渲染——前端分桶（本示例）用于理解原理和轻量本地实验；
  • 首屏前定分组：分组要在渲染前确定并缓存（localStorage），页面中途换组会闪变且污染指标；
  • SRM 检查：样本比偏差（预期 50:50 实际 70:30）说明分桶有 bug，分析侧要自动告警——本示例的均匀性验证就是 SRM 的雏形。

43.6 协同编辑入门与 H5 营销实践 ​

43.6.1 协同编辑：OT vs CRDT ​

多人同时编辑一份文档，核心难题是并发修改的收敛：A 把第 3 行删了，B 在第 3 行插入文字，合并结果必须两边都认可且各自看到一致。

OT（Operation Transform）CRDT（无冲突复制数据类型）
思路中心服务器对并发操作做变换（把 op 转换后再执行）每个操作设计成交换律成立的数据结构，任意顺序合并结果一致
代表Google Docs 早期路线Yjs、Automerge
依赖必须有中心服务器可去中心化（P2P 可行）
实现难度变换函数随操作类型组合爆炸库承担复杂度，接入简单

Yjs 是前端 CRDT 的事实标准，三层结构：

  1. Y.Doc：数据容器，变更自动编码成二进制更新（可增量同步）；
  2. 共享类型：Y.Text（富文本）、Y.Map（结构化数据）、Y.Array——像操作普通对象一样读写，变更自动广播与合并；
  3. Provider：同步通道——y-websocket（中心服务器中转）、y-webrtc（P2P）；Awareness 单独走轻量通道同步在线状态与光标位置（不进文档数据，不需要持久化）。

最小接入套路（描述版）：

ts
const doc = new Y.Doc();
const ytext = doc.getText("content");       // 共享文本
new WebsocketProvider(url, room, doc);      // 同步通道
new Awareness(doc);                          // 在线状态/光标
const binding = new yBinding(ytext, editor); // CodeMirror/ProseMirror 有官方 y- 绑定层
new UndoManager(ytext);                      // 撤销栈（跨用户的本地撤销）

为什么不能用 last-write-wins（每个客户端全量覆盖）？——键入级别会互相吞字：A 打的词被 B 一秒后的全量覆盖抹掉。CRDT 的合并单位是字符/元素级的插入删除标记，天然不丢。

43.6.2 H5 营销页工程要点 ​

  • 适配方案：营销页视觉要求「等比还原」，用 vw/rem 或 transform scale（第 41 册 contain 思路的移动端版）；与产品确认允许的适配偏差；
  • 性能预算：首屏可交互 < 1s——图片懒加载 + WebP/AVIF、动效 CSS 优先（JS 动画库失败降级 CSS）、长列表虚拟滚动；
  • 回流归因：分享卡片配置（title/desc/thumb）+ 分享链路埋点（谁分享 → 谁回流），与 43.4 曝光埋点同体系；
  • 降级与兜底：抽奖/动画等重交互在低端机降级（navigator.hardwareConcurrency 探测），接口失败展示兜底文案——营销页是纯转化漏斗，任何白屏都是直接损失。

43.7 自测题 ​

  1. SKU 置灰为什么用「超集判定」而不是枚举所有规格组合？
查看答案

枚举组合是 O(2^n)：3 维 × 3 值就是 27 种，维度再乘下去组合爆炸。超集判定只需对每个候选值扫一遍 SKU 列表（O(SKU × 维度)），检查是否存在有库存 SKU 的规格包含「已选 ∪ 候选」——SKU 几百个时毫秒级。只有 SKU 数千以上才值得预计算无向图/位图。

  1. 金额为什么用「分」整数运算？toFixed(2) 不是能修精度吗？
查看答案

toFixed 是四舍五入到字符串的展示函数，中间运算的浮点误差已经发生（0.1+0.2=0.30000000000000004，累计的 1e-15 在对账时分毫不差地暴露）。分整数运算让加减乘都在整数域（乘除只在优惠比例处出现，配合 Math.round），天然精确。展示层才做 (fen/100).toFixed(2)。

  1. 秒杀防连点为什么用 submitting 状态锁而不是节流？
查看答案

节流的语义是「N ms 内最多一次」，窗口过后仍会放行新请求——用户快速点 3 秒照样发出十几个请求，而每个请求都要后端扣库存判断。submitting 锁把「有一个请求在途」表达为状态：请求返回前所有点击直接拒绝，天然一次一个在途请求，且语义正确（响应没回来前，谁也不知道抢没抢到，多发无意义）。

  1. 曝光为什么要求「面积 ≥50% + 停留 ≥500ms」双门槛？只判可见会怎样？
查看答案

只判可见，列表快速滑动时每个 item 都闪现几十毫秒——全部计入曝光，曝光基数虚高一个数量级，CTR（点击/曝光）被稀释到毫无参考价值，运营据此低估素材质量。双门槛过滤「没真正看到」的伪曝光，让曝光与点击在同一个可信基数上。

  1. A/B 实验两个实验分组完全同步（control 全在 v1），可能的原因是什么？怎么发现、怎么避免？
查看答案

根因：分桶哈希的低位相关性——djb2 累乘哈希的最低位只由各字符奇偶性的异或累积决定，两个实验 key 字符奇偶和相同 → bucket 奇偶完全同步 → % 2 分组完全相关，实验结论互相污染。发现：SRM 检查与交叉四格分析（分组交叉表应均衡）。避免：哈希加雪崩收尾（fmix）、或两级分桶（进组与分组用不同哈希）、或生产直接用服务端成熟分桶（murmurhash + 随机盐）。
