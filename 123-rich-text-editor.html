第一百二十三部分 · 富文本编辑器 ​

🧭 返回总目录｜上一篇：第一百二十二部分 · AI 对话应用前端｜关联章节：第七十五部分 · 协同办公套件 · 第一百部分 · 前端安全实战 · 第七部分 · 安全基础 · 第六十四部分 · 复杂可编辑表格 · 第四十九部分 · 组件库工程

本部分内容 ​

富文本编辑器是知识管理平台的心脏，也是前端里「看起来最简单、做进去最深」的组件。这一册的主线只有一句：contentEditable 只借渲染与选区，数据模型必须自持——浏览器 DOM 差异、输入法临时串、粘贴板脏 HTML、协同远端变更，全都不可信，内核必须把文档、选区、历史握在自己手里。四个可运行示例覆盖内核四件套：文档模型与事务、选区映射与输入法冻结、粘贴清洗白名单、撤销历史栈。

123.1 编辑器内核：文档模型与事务 ​

概念解析 ​

新人最容易掉的坑是把 innerHTML 当文档模型：读回来的序列化结果因浏览器而异（<b> 还是 <strong>、属性顺序、自闭合写法各不相同），没有语义无法做协同变换，还直接张开 XSS 的面。正确架构是内核自持模型，DOM 只是渲染结果。

模型有两条主流路线：

路线代表优势代价
节点树ProseMirror / Lexical结构严谨、schema 可校验、适合复杂块（表格/嵌入卡片）op 变换要处理路径与父子指针，实现重
扁平 ΔQuill / 本册示例op 只有位置与区间，变换/反转/合并都简单深层嵌套表达力弱，需额外约定

知识平台以「段落 + 行内格式」为主，扁平 Δ 往往够用：块结构交给分块渲染层，内核只认文本与标记区间。所有修改收敛为三类 op——insert / delete / format，再以事务为最小提交单位：在克隆上试跑全部 op，任何一步校验失败整批丢弃，渲染层只会看到前后两个一致快照。op 应用前后跑一致性校验（长度守恒），把内核 bug 拦在开发期。

完整代码示例 ​

ts
// 文件: examples/123-01-document-model.ts（节选）
// 事务：在克隆上试跑全部 op，任何一步失败直接抛错，原文档保持不变
const draft: DocState = { text: this.state.text, marks: this.state.marks.map((m) => ({ ...m })) };
for (const op of ops) {
    validateOp(draft, op);                  // 越界/空操作立即拒绝
    const before = { text: draft.text, marks: draft.marks };
    applyOp(draft, op);
    checkConservation(before, draft, op);   // 长度必须恰好变化 lengthDelta
}
this.state = draft;                         // 全部通过才一次性提交

运行方式：npx tsx examples/123-01-document-model.ts

断言：insert/delete 长度守恒；format 区间切分与相邻合并；标记随编辑扩张/右移/收缩/清空；失败事务整批回滚；长度不守恒被守卫拦截。

应用实践 ​

知识平台的划线评论、AI 续写都作用于模型区间而不是 DOM：评论锚点存 {start, end}，文档变化时随 op 变换；AI 流式续写每个 chunk 是一个 insert op，合并成一个事务提交，用户撤销一次即整段回退。反例：直接改 DOM 再用 MutationObserver 反推模型——中文输入法下 DOM 变化与用户意图完全对不上，模型很快就脏了。

最佳实践 ​

  • ✅ 一切修改走事务，禁止插件直接改 state。
  • ✅ op 是内核唯一协议：undo、协同、回放都复用它。
  • ✅ 一致性校验（长度守恒、区间规范形态）留在内核，开发期尽早炸。

123.2 编辑器选型对照：Tiptap、Slate、Lexical 与 wangEditor ​

概念解析 ​

五个主流方案按五维对照：

维度ProseMirrorTiptapSlateLexicalwangEditor
内核模型节点树节点树（PM 封装）自定义树节点树自定义
框架耦合无无（官方 React/Vue 绑定）强绑 ReactReact 优先无
Schema 约束强强弱（自由度过高易失控）中中
协同生态成熟（Yjs 官方示例）成熟（Hocuspocus）需自行接入官方 collaboration较弱
学习曲线/中文资料陡/少中/中中/少中/少平缓/多

决策树：需要严格 schema、协同、长期演进选 Tiptap（拿 ProseMirror 的能力、少写胶水）；全 React 团队追求渲染性能与 DX 选 Lexical；内部工具快速上线、中文文档优先选 wangEditor，但架构上留替换面；已在 Slate 上且模型简单可以继续，复杂块结构迟早撞表达力墙；自研内核仅当业务模型极简且团队愿意长期维护。

完整代码示例 ​

ts
// 文件: examples/123-01-document-model.ts（节选）
// 扁平 Δ 的全部操作协议只有三类——协议越小，协同变换与 undo 反转越可靠
type Op =
    | { type: 'insert'; pos: number; text: string }
    | { type: 'delete'; pos: number; length: number }
    | { type: 'format'; pos: number; length: number; mark: string; value: boolean };

运行方式：npx tsx examples/123-01-document-model.ts

断言：三类 op 覆盖全部编辑行为；越界与空操作在 validateOp 统一拒绝；format 不改变文本长度。

应用实践 ​

知识管理平台选型时把「协同」当第一约束：一旦确定上 Yjs，可选项立刻收敛到 ProseMirror/Tiptap/Lexical。落地策略：先用 Tiptap 默认 schema 上线，再按业务加自定义节点（划线评论锚点、文档引用卡片），每个节点是独立插件，可单独卸载回滚。

最佳实践 ​

  • ✅ 选型 POC 必测三件事：中文输入、万行文档、Word 粘贴。
  • ✅ 编辑器外面包一层业务适配层，框架可替换。
  • ✅ 自定义节点数量设预算，schema 膨胀比代码膨胀更难收。

123.3 选区映射与输入法合成 ​

概念解析 ​

选区是双份的：DOM Selection（anchorNode/focusNode）与模型选区（{block, offset}）。内核必须维护双向映射：模型 op 应用后，用 transformOffset 让光标跟着变换——insert 右侧亲和（光标落在插入点则跟着新文本走，连续打字不被甩到文字前面），delete 夹取（落在被删区间内的点收拢到删除起点）。反向 DOM → 模型则依赖渲染时记录的「DOM 节点 ↔ 模型位置」映射表。

跨段落选区先归一化成 start <= end 再交给删除/复制逻辑，同时保留 backward 方向位——Shift+方向键从右往左选时，光标在起点，延展方向不能丢。

中文输入法是最大暗坑：compositionstart 后 IME 直接改写 DOM，期间任何重渲染都会打断上屏，selectionchange 报出的是临时串里的坐标。正确姿势是冻结：composition 期间输入 op 入队、拒绝 DOM 选区回写、不渲染，compositionend 统一结算。

完整代码示例 ​

ts
// 文件: examples/123-02-selection-mapping.ts（节选）
// compositionstart 后：输入 op 入队、拒绝外部选区回写；compositionend 统一结算
input(text: string): void {
    const offset = this.composing ? this.pendingOffset() : this.cursor;
    const op: InsertOp = { type: 'insert', block: 0, offset, text };
    if (this.composing) { this.pending.push(op); return; }
    this.applyLocal(op);
}

setCursorFromDom(offset: number): boolean {
    if (this.composing) return false; // IME 期间的 DOM Selection 不可信
    this.cursor = offset;
    return true;
}

运行方式：npx tsx examples/123-02-selection-mapping.ts

断言：插入点右侧亲和；删除区间内的点夹取到删除起点；选区被吞并时坍缩为光标；反向选区归一并保留 backward；composition 期间文档不改写、选区回写被拒，end 后按序结算。

应用实践 ​

知识平台移动端 H5 曾被「部分安卓输入法 compositionend 晚于 blur」折磨：onBlur 保存草稿时读到的是合成中的临时串。修复：冻结期间打 composing 标记，保存逻辑见到标记先强制结算队列再读模型。反例：不做冻结，微信内置浏览器里打字光标乱跳、拼音串残留在正文里。

最佳实践 ​

  • ✅ 模型选区是唯一真相，DOM Selection 只是投影。
  • ✅ selectionchange 监听必须防抖，且在 composition 期间短路。
  • ✅ 选区变换逻辑纯函数化，100% 可单测。

123.4 粘贴与导入清洗 ​

概念解析 ​

粘贴板里的 text/html 是完全不可信的输入：网页复制带着脚本与跟踪器，Word 复制带着几百个 mso-* 私有属性、<o:p> 占位与条件注释。清洗只有一条铁律：白名单优于黑名单——黑名单永远追不上新攻击面，白名单只放行你认识的。

三层过滤：

  1. 标签白名单：p/b/strong/a/ul/li/img 等；script/style 连内容一起丢弃；不在名单的剥壳保留内部文本。
  2. 属性白名单 + style 黑名单：属性按标签声明（a 只留 href，img 只留 src/alt），on* 事件属性天然全灭；style 按声明逐条过滤，剔掉 position/behavior/-moz-binding 与 mso-* 前缀，值里含 expression(/javascript: 整条剔除。
  3. 协议拦截：href/src 先剥离空白与控制符再判协议，javascript:、vbscript:、data: 一律拒绝——java\tscript: 控制符绕过是老把戏。

图片粘贴不要直接存 data:URL：清洗时换成占位节点，后台上传 blob，成功后用事务替换 src，失败移除占位。

完整代码示例 ​

ts
// 文件: examples/123-03-paste-sanitize.ts（节选）
// 唯一入口：内容级丢弃 → 标签白名单 → 属性白名单 + style 黑名单
if (DROP_WITH_CONTENT.has(token.name)) {
    if (token.kind === 'open') dropping += 1;
    else if (dropping > 0) dropping -= 1;
    continue;
}
if (dropping > 0) continue;
if (token.kind === 'open') {
    if (!ALLOWED_TAGS.has(token.name)) continue; // 不在白名单：剥壳，保留内部文本
    const attrs = sanitizeAttrs(token.name, token.attrs);
    // ...
}

运行方式：npx tsx examples/123-03-paste-sanitize.ts

断言：script/style 内容级丢弃；onclick 与危险协议拦截；mso-* 与条件注释剥离；文本转义、相邻 li 隐式闭合、未闭合标签自动补齐。

应用实践 ​

知识平台的 Word 导入场景：运营从 PRD 直接粘贴，未清洗的 mso 样式让编辑器行高全乱；清洗后只保留 color，版式回到平台主题。注意浏览器里应优先 DOMParser + 遍历白名单——本册示例用纯 TS 手写 tokenizer 是为了确定性单测；输出永远走序列化器而不是字符串拼接。

最佳实践 ​

  • ✅ 清洗器是纯函数：输入 HTML 字符串、输出安全 HTML，全量可单测。
  • ✅ 粘贴事件里同步读取 clipboardData，异步再读可能拿不到。
  • ✅ 清洗结果落库前再过服务端二次消毒（见 123.6）。

123.5 历史栈与协同边界 ​

概念解析 ​

本地 undo/redo 的核心是逆操作：insert ↔ delete 位置不变、文本互换——前提是删除 op 生成时就捕获被删文本，否则 undo 无米下锅。历史条目带 before/after 选区：undo 回到 before、redo 回到 after，用户才有「时间机器」的体感。

两个工程细节决定体验：合并窗口（800ms 内相邻同种输入合并为一步，撤销一次回退一个词而不是一个字符；insert 与 delete 永不合并）与容量上限（默认 100 步，超出丢弃最旧，长会话不爆内存；代价是最早的历史不可达，可接受）。

协同边界一句话讲清：本地 undo 栈只管本地操作。接入 Yjs 时用 UndoManager 的 trackedOrigins 只跟踪本地事务来源；远端 op 经 CRDT 变换后进文档但不进本地 undo 栈。OT 路线同理：undo 的是「经服务端变换后的本地逆操作」。千万别反转全局 diff 当 undo——会把同事刚写的段落一起回滚。

完整代码示例 ​

ts
// 文件: examples/123-04-undo-history.ts（节选）
// 撤销：逆序应用逆操作，选区回到 before，条目转入 redo 栈
undo(doc: DocState): number | null {
    const entry = this.undoStack.pop();
    if (entry === undefined) return null;
    for (let i = entry.ops.length - 1; i >= 0; i -= 1) applyOp(doc, invertOp(entry.ops[i]));
    this.redoStack.push(entry);
    return entry.before;
}

运行方式：npx tsx examples/123-04-undo-history.ts

断言：逆操作精确还原；时间窗内合并、超窗分步；insert/delete 不合并；选区随栈回放；容量超限丢弃最旧；新编辑清空 redo 栈。

应用实践 ​

知识平台把 undo 栈与自动保存联动：每次 record 打脏标记，undo 回到「已保存快照」对应条目时清掉脏标记——用户撤销到保存点，关闭按钮不再弹「未保存」提示。反例：合并窗口不分操作类型，打字中间按了一次退格，撤销一步把整段新文字全回滚，用户当场流失。

最佳实践 ​

  • ✅ 删除 op 自包含（带被删文本），逆操作是纯函数。
  • ✅ 合并窗口用注入时钟，单测不依赖真实时间。
  • ✅ 协同场景 undo 只跟踪本地 origin，远端变更永不进本地栈。

123.6 序列化与 XSS 防护 ​

概念解析 ​

模型进出系统经过两道序列化：导出（模型 → HTML/Markdown，用于分享、邮件、SEO 快照）与导入（HTML → 模型，用于粘贴与历史数据迁移）。导出侧规则：只从模型生成，序列化器是唯一出口，文本节点必转义、属性值必转义；导入侧规则：先过 123.4 的白名单清洗，再映射成模型节点。

安全铁律是客户端清洗不算数：攻击者绕过前端直接 POST 脏 HTML 即可。服务端落库前必须用同一套白名单策略二次消毒（如 DOMPurify 的服务端形态），渲染层再加 CSP 兜底。三层任何单层失效都不致命，才算纵深防御。

完整代码示例 ​

ts
// 文件: examples/123-03-paste-sanitize.ts（节选）
// 先剥离空白与控制符再判协议，防 'java\tscript:' 这类绕过
function sanitizeUrl(url: string): string | null {
    const compact = url.replace(/[\u0000-\u0020]+/g, '');
    if (/^(javascript|vbscript|data):/i.test(compact)) return null;
    return compact;
}

运行方式：npx tsx examples/123-03-paste-sanitize.ts

断言：控制符绕过的 javascript: 同样拦截；data: 协议拒绝；属性值引号转义为 "；mailto: 等安全协议放行。

应用实践 ​

知识平台导出邮件 HTML 时只输出行内样式白名单（邮件客户端不认 class）；Markdown 导出走「模型 → 中间 AST → Markdown」两段式，导入复用同一 AST，round-trip 不丢格式。反例：导出时字符串拼接忘了转义代码块内容，用户在文档里贴的 XSS 示例代码，在分享页真的执行了——教学文档变成攻击载荷。

最佳实践 ​

  • ✅ 导出与导入共用同一份标签/属性白名单常量。
  • ✅ 服务端消毒策略与前端同源发布，版本对齐。
  • ✅ CSP 禁 unsafe-inline，渲染层不留内联脚本口子。

123.7 大文档性能与工程化 ​

概念解析 ​

万行文档卡的不是编辑而是渲染：全量 DOM 重建一次就上百毫秒。标准解法是分块渲染——视口内块真实渲染，视口外块用占位高度，滚动时增量挂载（与第六十四部分表格虚拟滚动同源）。模型层配合：事务是渲染通知的最小单位，高频输入合并成一个事务提交，渲染层一帧只收一次变更。

工程化三件事：插件架构（schema 定义节点、插件挂行为、命令层收敛全部编辑入口，插件之间不直接通信只过事务）；SSR（服务端把模型渲染成静态 HTML，客户端 hydrate 前先只读，进入编辑模式再挂载内核）；打印（@media print 去掉工具栏与光标层，分页用 break-inside，长文档打印走导出管线而非屏幕截图）。

完整代码示例 ​

ts
// 文件: examples/123-01-document-model.ts（节选）
// 一次事务 = 一次渲染通知：多步 op 原子提交，渲染层只看到前后两个一致快照
function checkConservation(before: DocState, after: DocState, op: Op): void {
    const expected = before.text.length + lengthDelta(op);
    if (after.text.length !== expected) {
        throw new Error(`E_LENGTH_MISMATCH: ${op.type} 后期望 ${expected}，实际 ${after.text.length}`);
    }
}

运行方式：npx tsx examples/123-01-document-model.ts

断言：事务内多步 op 按序生效；失败事务不得留下半步；长度不守恒被守卫拦截——渲染层永远只见一致快照。

应用实践 ​

知识平台 5 万字产品手册：分块渲染后首屏挂载从 1.2s 降到 180ms；AI 批量改写 200 处合并为单事务提交，全程只重排一次。反例：每个 op 触发一次 React setState，长文档里打字掉到 10fps，用户以为应用卡死。

最佳实践 ​

  • ✅ 渲染订阅事务粒度，不订阅单个 op。
  • ✅ 占位高度用实测值缓存，滚动不跳。
  • ✅ 打印与导出共用同一序列化器，版式不分裂。

123.8 自测题 ​

先自己作答，再展开参考答案。

1. 为什么不能把 innerHTML 读回来当文档模型？【基础】

序列化结果因浏览器而异，同一文档读两次可能得到不同字符串；HTML 没有编辑语义，无法做 op 变换与协同；还直接张开 XSS 面。模型必须自持，DOM 只是渲染结果。

2. 扁平 Δ 与节点树模型各自适合什么场景？【基础】

扁平 Δ：段落 + 行内格式为主的文档，op 只有位置与区间，变换/反转/合并简单。节点树：表格、嵌套卡片等复杂块结构，schema 可强校验。知识平台正文选前者，块结构交给渲染层。

3. composition 期间为什么不能重渲染或回写选区？【进阶】

compositionstart 后 IME 直接改写 DOM 显示临时拼音串，重渲染会销毁临时串打断上屏；此时 DOM Selection 指向临时串内部，回写模型会把光标钉在错误位置。正确做法是冻结：op 入队、回写拒绝、end 统一结算。

4. 粘贴清洗为什么坚持白名单优于黑名单？【基础】

黑名单要枚举全部危险面，而攻击面持续增长（新标签、新协议、新编码绕过）；白名单只放行认识的标签与属性，未知即丢弃，默认安全。script/style 还要连内容丢弃，不能只剥标签。

5. 光标变换的「右侧亲和」解决什么问题？【进阶】

光标恰好落在插入点时，若不跟随新文本右移，连续打字光标会停在新文字前面，后续输入插到光标后导致字符倒序。右侧亲和让光标跟着新文本走，删除时则相反：落在被删区间内的点夹取到删除起点。

6. 删除类 op 为什么必须在生成时捕获被删文本？【进阶】

逆操作要在不查文档的情况下还原删除——undo 时文档早已变化，反查位置处的文本不一定是当时删掉的内容。op 自包含（delete 带 text）后，invert 是纯函数，回放与协同变换都不依赖上下文。

7. 协同编辑中，为什么不能用「反转全局 diff」实现 undo？【挑战】

全局 diff 混入了远端同事的 op，反转它会把别人的编辑一起回滚。正确做法是 undo 栈只跟踪本地 origin 的事务（如 Yjs UndoManager 的 trackedOrigins），远端 op 经 CRDT/OT 变换进文档但不进本地历史；undo 的是变换后的本地逆操作。

8. 前端已做粘贴清洗，服务端为什么还要二次消毒？【挑战】

前端校验可被绕过：攻击者直接 POST 脏 HTML 落库，之后任何渲染该文档的页面都会执行——存储型 XSS。服务端必须用同源白名单策略二次消毒，再加 CSP 兜底；单层失效不致命才是纵深防御。

心法：编辑器的一切不确定性都来自外部——DOM、输入法、粘贴板、协同网络；内核的应对永远是同一招：把它们全部翻译成自包含的 op，再让 op 过校验、进事务、上历史栈。守住这条单行道，复杂性就进不了内核。
