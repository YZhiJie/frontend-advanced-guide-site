第一百三十一部分 · 表单工程——RHF、VeeValidate 与 Schema 三层协作 ​

本册讲「表单」这一层的工程化：字段状态怎么组织、校验放在哪一层、Schema 如何成为单一事实来源、异步校验怎么防竞态、复杂结构与提交编排怎么收口。RHF 的基础用法（register/handleSubmit/formState）见 85 React Hook Form 表单工程，本册不重复；Zod 语法全景见 33 Zod 运行时校验；提交后的服务端状态管理见 05.5 服务端状态管理 TanStack Query；请求层与重试见 130 数据请求与缓存；长表单虚拟化见 10.4 高性能虚拟列表 与 64.1 虚拟滚动内核；表单内的快捷键作用域见 45.3.3 快捷键作用域；声明式校验片段与提交锁见 19.1 表单校验与声明式规则、19.2 输入格式化、提交锁与倒计时。

技术基线（2025-11）：react-hook-form 7.x、@hookform/resolvers 3.x/5.x、vee-validate 4.x、zod 3.25（仓库示例锁定该版本；Zod 4 已通过 zod/v4 子路径发布，差异在 131.4 标注）。库的大版本 API 变化处均标注「以安装版本为准」。

四个配套示例全部纯 TS、零 DOM，真实 import { z } from "zod"，node:assert 硬断言，可 npx tsx 实跑；React/Vue 组件片段标注「项目内运行」，不参与门禁实跑。

131.1 心智模型：表单是「状态机 + 校验图」 ​

多数表单事故不是「校验没写」，而是状态没有单一归属：DOM 里一份值、React state 里一份、URL 里一份、提交时再拼一份；错误消息由三处 if 分别生成，改一条规则要改五个地方。

把表单拆成五层，问题各归其位：

层职责常见实现
字段状态层值、touched、dirty、焦点非受控 ref（RHF）/ 响应式对象（VeeValidate）
校验层同步规则、异步规则、跨字段规则Schema（Zod）+ 字段级 validator
展示层错误何时可见、如何播报touched && submitAttempted 门控 + ARIA
提交编排层单飞、幂等、错误映射、重试状态机（131.6 示例 131-04）
数据层草稿、成功后的缓存失效localStorage/IDB + Query 失效

表单状态的六个维度 ​

维度含义容易搞错的地方
values当前值「输入中的字符串」与「提交时的数字」是两种类型
errors字段/表单级错误同一字段多条规则只展示一条，但要保留全部供调试
touched是否失焦过只 blur 不校验时，touched 不等于「已校验」
dirty是否偏离初始值改回原值应回到非脏；数组/对象要深比较
isSubmitting提交在途必须能挡住双击与回车连按
isValid整体是否合法多数库需要 mode 配合才会实时维护

校验时机矩阵 ​

时机用户体验适用
onSubmit提交前完全安静，一次报全部短表单、低频表单
onBlur离开字段才报，不打断输入大多数业务表单
onChange边输边报，反馈最快也最吵搜索、强实时校验
onTouched首次 blur 后转为 onChange推荐的默认值
allblur + change 都校验规则复杂、需要即时反馈

一个必须记住的体验原则：用户还没碰过的字段，不要在他第一次提交前标红。RHF 的 mode: 'onTouched'、VeeValidate 的 validateOnBlur + validateOnModelUpdate 都是围绕这个原则设计的。

131.2 React Hook Form 7.x：进阶用法与性能边界 ​

85 册讲清了「非受控 + 按需订阅」的原理，这里只讲工程里真正会踩的部分。

useForm 的关键选项 ​

tsx
// [项目内运行] npm i react-hook-form zod @hookform/resolvers
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  email: z.string().trim().email("邮箱格式不正确"),
  age: z.coerce.number().int().min(18, "需年满 18 岁"),
});

type FormValues = z.input<typeof schema>; // 注意是 input，不是 infer

export function ProfileForm() {
  const form = useForm<FormValues>({
    resolver: zodResolver(schema),
    mode: "onTouched",        // 首次 blur 后转 onChange
    reValidateMode: "onChange",
    criteriaMode: "all",      // 同一字段保留全部错误（默认 firstError）
    delayError: 300,          // 错误提示延迟，避免输入中闪烁
    shouldFocusError: true,   // 提交失败聚焦第一个错误字段
    defaultValues: { email: "", age: 18 },
  });

  return (
    <form onSubmit={form.handleSubmit(
      (values) => console.log("校验通过", values),
      (errors) => console.log("校验失败", errors),
    )}>
      <input {...form.register("email")} aria-invalid={!!form.formState.errors.email} />
      <p role="alert">{form.formState.errors.email?.message}</p>
      <button disabled={form.formState.isSubmitting}>保存</button>
    </form>
  );
}

三个容易忽略的点：

  1. useForm<T> 的类型要用 z.input。Schema 里有 z.coerce、default、transform 时，输入类型与输出类型不同；写 z.infer（等于 z.output）会让 defaultValues 与 register 的类型对不上。
  2. criteriaMode: 'all' 只在需要一次展示多条错误时开。默认 firstError 更省渲染。
  3. resolver 会让 isValid 实时可用，但前提是 mode 不是 onSubmit；mode: 'onSubmit' + resolver 时 isValid 只在提交后更新。

register 的选项比想象中多 ​

tsx
<input
  {...register("age", {
    valueAsNumber: true,              // 直接给 number，省掉提交时 Number()
    setValueAs: (v) => (v === "" ? undefined : v), // 空串 → undefined
    deps: ["birthday"],               // 该字段变化时，连带重新校验 birthday
    shouldUnregister: false,          // 卸载后保留值（默认 false，7.x）
    validate: {
      notFuture: (v) => v <= new Date().getFullYear() || "不能是未来年份",
    },
  })}
/>

valueAsNumber 与 z.coerce.number() 二选一即可：重复做转换会让「空字符串」的语义变得难以预测（Number("") === 0）。

Controller：第三方组件唯一的正确接法 ​

tsx
// [项目内运行] 受控组件（AntD DatePicker / Radix Select / 富文本）必须用 Controller
import { Controller } from "react-hook-form";

<Controller
  control={form.control}
  name="birthday"
  rules={{ required: "请选择生日" }}
  render={({ field, fieldState }) => (
    <>
      <DatePicker value={field.value} onChange={field.onChange} onBlur={field.onBlur} />
      {fieldState.error && <span role="alert">{fieldState.error.message}</span>}
    </>
  )}
/>

field 里包含 onChange/onBlur/ref/value/name。不要只写 value 和 onChange 而漏掉 onBlur，否则 touched 永远不更新，错误展示策略失效。

formState 是 Proxy：读什么才订阅什么 ​

formState 不是普通对象，RHF 用 Proxy 记录你读取了哪些属性，只在这些属性变化时触发重渲染。由此产生两条硬规则：

  • 不要在渲染里条件性读取：if (someFlag) { errors } 会让订阅关系随渲染变化，出现「有时不更新」；
  • 只需要单个字段时用 useWatch / useFormState，不要 watch() 整个表单：
tsx
// ✅ 只订阅一个字段，其他字段输入不触发本组件重渲染
const email = useWatch({ control: form.control, name: "email" });

// ❌ 订阅整个表单：任何字段输入都重渲染
const all = form.watch();

服务端错误映射：setError 的路径规则 ​

tsx
const onSubmit = form.handleSubmit(async (values) => {
  try {
    await api.save(values);
  } catch (error) {
    if (error instanceof HttpFieldError) {
      // 后端返回 [{ path: "items.0.qty", message: "库存不足" }]
      for (const item of error.fields) {
        form.setError(item.path as never, { type: "server", message: item.message }, { shouldFocus: false });
      }
      form.setError("root.server", { message: "部分字段需要修改" }); // 表单级错误
      return;
    }
    form.setError("root.server", { message: "网络异常，请重试" });
  }
});

路径必须与 register 的 name 完全一致（数组用 items.0.qty）。表单级错误用 root 前缀，读取时是 formState.errors.root?.server。

useFieldArray：稳定 key 是命门 ​

tsx
const { fields, append, remove, move, insert, replace } = useFieldArray({
  control: form.control,
  name: "items",
  keyName: "id", // 默认就是 id；不要用 index 当 key
});

{fields.map((field, index) => (
  <div key={field.id}>
    <input {...form.register(`items.${index}.name` as const)} />
    <button type="button" onClick={() => remove(index)}>删除</button>
  </div>
))}

fields 里的 id 是 RHF 生成的稳定标识；form.getValues("items") 里没有这个 id（它是 UI 层 key，不是业务数据）。删除/移动后下标会变，所以只能在下标对应的渲染闭包里用 index，不能把它存进 state。

131.3 VeeValidate 4.x：Vue 侧的表单工程 ​

VeeValidate 4 与 RHF 的模型不同：它基于响应式对象与「规则」而不是非受控 ref，因此天然适合 v-model，但性能靠 useField 的字段级隔离来保证。

useForm + useField 的最小闭环 ​

vue
<!-- [项目内运行] npm i vee-validate @vee-validate/zod zod -->
<script setup lang="ts">
import { useForm, useField } from "vee-validate";
import { toTypedSchema } from "@vee-validate/zod";
import { z } from "zod";

const schema = toTypedSchema(
  z.object({
    email: z.string().trim().email("邮箱格式不正确"),
    age: z.coerce.number().int().min(18, "需年满 18 岁"),
  }),
);

const { handleSubmit, errors, meta, resetForm } = useForm({
  validationSchema: schema,
  initialValues: { email: "", age: 18 },
  validateOnMount: false,
});

const { value: email, handleBlur } = useField<string>("email");
const { value: age } = useField<number>("age");

const onSubmit = handleSubmit(async (values) => {
  await api.save(values);
  resetForm(); // 提交成功后重置为 initialValues
});
</script>

<template>
  <form @submit="onSubmit">
    <input v-model="email" @blur="handleBlur" aria-invalid="!!errors.email" />
    <p role="alert">{{ errors.email }}</p>
    <input v-model.number="age" type="number" />
    <button :disabled="!meta.valid">保存</button>
  </form>
</template>

关键点：

  • useField 返回的 value 是 Ref，模板里自动解包；errors.email 是全局错误映射，字段级可用 useField 的 errorMessage 做更细的订阅；
  • meta.valid 是异步校验也完成后的整体状态；不要用 !errors.email 代替；
  • handleSubmit 的第一个参数只在全部校验通过时执行，第二个参数是 invalid 回调。

defineField：v-model 与校验绑定的语法糖 ​

vue
<script setup lang="ts">
import { useForm, defineField } from "vee-validate";
const { handleSubmit } = useForm({ validationSchema: schema });
const [email, emailAttrs] = defineField("email", { validateOnModelUpdate: true });
</script>

<template>
  <input v-model="email" v-bind="emailAttrs" />
</template>

defineField 返回 [model, attrs]，attrs 里带 onBlur（触发校验）与 aria-invalid 等。它适合字段多、但规则简单的表单；字段级异步校验仍建议 useField。

全局配置与规则注册 ​

ts
// [项目内运行] 入口文件
import { configure, defineRule } from "vee-validate";

configure({
  validateOnBlur: true,
  validateOnChange: false,      // 输入过程中不校验，避免吵
  validateOnModelUpdate: false, // v-model 更新不校验
});

defineRule("phone", (value: string) => {
  return /^1[3-9]\d{9}$/.test(value) || "手机号格式不正确";
});

configure 是全局的，改它会同时影响所有表单；需要按表单定制时，在 useForm 上传 validateOnBlur 等选项覆盖。

zod 集成与版本匹配 ​

ts
import { toTypedSchema } from "@vee-validate/zod";

toTypedSchema 把 Zod Schema 适配成 VeeValidate 的 TypedSchema：错误消息按 issue.path 映射到字段，异步 refine 会走异步校验通道。@vee-validate/zod 必须与 zod 主版本匹配：zod 3 用当前稳定版；zod 4 需要对应支持 zod/v4 的版本，安装前先看 peerDependencies，不要硬装。

数组字段：useFieldArray / FieldArray ​

vue
<script setup lang="ts">
import { useFieldArray } from "vee-validate";
const { fields, push, remove, move } = useFieldArray<{ name: string; qty: number }>("items");
</script>

<template>
  <div v-for="(field, index) in fields" :key="field.key">
    <input v-model="field.value.name" />
    <button type="button" @click="remove(index)">删除</button>
  </div>
  <button type="button" @click="push({ name: '', qty: 1 })">新增</button>
</template>

fields 里的 key 是稳定的，不要用 index 当 :key——删除中间行后，Vue 会复用错组件实例，输入框内容会「串行」。useFieldArray 在 vee-validate 4.10+ 提供；老版本用 <FieldArray> 组件或手写数组 + useField 路径（items[0].name），迁移时注意路径语法差异。

131.4 Schema 工程：Zod 作为单一事实来源 ​

Schema 不是「校验函数集合」，而是表单的数据契约：类型、默认值、归一化、错误消息、跨字段规则都在这一层。131.1 的示例 131-01-schema-form-model.ts 把这条链路完整跑了一遍。

运行方式：npx tsx examples/131-01-schema-form-model.ts（实跑；断言覆盖 trim/lowercase/coerce/default、z.input 与 z.output 的差异、错误路径扁平化、touched/dirty 与错误可见性）

归一化放在解析期，不要放在提交时 ​

ts
const schema = z.object({
  email: z.string().trim().toLowerCase().email(),
  age: z.coerce.number().int().min(18),
  coupon: z.string().trim().default(""),
});

trim/lowercase/coerce/default 都在 safeParse 时完成，所以：

  • 表单里可以放心用字符串（age: "20"），拿到的 data.age 一定是 number；
  • 提交给后端的是解析后的值，不是原始 getValues()；
  • z.input 与 z.output 不同，useForm<T> 要用 z.input（见 131.2）。

跨字段校验：superRefine 与 discriminatedUnion ​

ts
// 方案 A：superRefine —— 适合「A 字段依赖 B 字段」的少量规则
const schemaA = z.object({
  plan: z.enum(["free", "pro"]),
  company: z.string().optional(),
}).superRefine((v, ctx) => {
  if (v.plan === "pro" && !v.company) {
    ctx.addIssue({ code: z.ZodIssueCode.custom, path: ["company"], message: "Pro 套餐需填写公司名" });
  }
});

// 方案 B：discriminatedUnion —— 适合「整组字段随类型切换」
const schemaB = z.discriminatedUnion("type", [
  z.object({ type: z.literal("personal"), idCard: z.string().length(18) }),
  z.object({ type: z.literal("company"), taxNo: z.string().min(15) }),
]);

superRefine 只在基础对象解析成功后执行。上面 email 与 age 同时非法时，company 的跨字段错误不会出现——这不是 bug，而是校验顺序：先结构、后语义。UI 上表现为「先修字段错误，再看到跨字段错误」。

transform 的坑：输出类型变了，表单值没变 ​

ts
const amount = z.string().transform((s) => Math.round(Number(s) * 100)); // "12.34" → 1234

transform 之后，z.infer 是 number，但表单里用户输入仍然是字符串。RHF 的 resolver 返回的是输出值，handleSubmit 拿到的是 1234；而 watch("amount") 拿到的是 "12.34"。这类字段不要混用两种形态，要么在 Schema 里只做校验、提交时统一转换，要么明确「表单值 = 字符串，提交值 = 分」。

错误消息与国际化 ​

ts
// [项目内运行] 全局错误文案（zod 3）
z.setErrorMap((issue, ctx) => {
  if (issue.code === z.ZodIssueCode.too_small && issue.type === "string") {
    return { message: `至少 ${issue.minimum} 个字符` };
  }
  return { message: ctx.defaultError };
});

Zod 4 把全局配置换成了 z.config({ customError }) 与 z.locales，error.flatten() 也不再是推荐用法（改用 z.treeifyError / z.prettifyError）。跨大版本迁移时，先统一错误读取入口（本项目是 flattenIssues），再换实现。

Schema 性能：别把请求写进 refine ​

ts
// ❌ 不要这样：schema 会在每次校验时发请求，且无法取消
email: z.string().refine(async (v) => !(await api.exists(v)), "已被占用")

原因有三：Schema 可能被 isValid 高频触发、refine 无法感知竞态、错误无法区分「网络失败」与「已占用」。正确做法是字段级异步校验器（131.5），Schema 只保留纯函数规则。同理，大表单不要每次输入都 safeParse 整个对象：按字段拆 Schema，或用 pick 只校验当前步（131.6）。

131.5 异步校验：竞态、缓存与触发时机 ​

「用户名是否被占用」是表单里最典型的异步校验。它有三个独立问题：什么时候发、旧结果怎么丢弃、同值怎么复用。示例 131-02 用一个可注入的校验器把三者都断言了。

运行方式：npx tsx examples/131-02-async-validation-race.ts（实跑；断言覆盖旧请求作废、同值并发合并、成功/失败结果缓存、规则版本失效、提交前最后一次结果语义）

触发时机：blur 优先，输入只做防抖提示 ​

策略请求量体验建议
每次输入都校验高抖动、易误报不推荐
防抖 300ms + 最少 2 字符中较好搜索类字段
blur 时校验低稳定默认选择
提交前统一校验最低提交时才报强一致场景

竞态：只认最后一次「发起」 ​

ts
// 核心：每次发起递增 seq，返回时比对；不一致就丢弃
const seq = ++this.#seq;
this.#latestSeq.set(field, seq);
const result = await this.check(value);
return this.#latestSeq.get(field) === seq ? result : "stale";

这里的关键不是「取消请求」（取消是优化），而是结果归属判定：即使请求已经返回，只要期间该字段又发起了新校验，旧结果就必须丢弃。AbortController 只能省流量，不能替代这层判定。

缓存键要带「规则版本」 ​

ts
const key = `${ruleVersion}::${field}::${value}`;

只按 field + value 缓存，在规则变更（如密码强度升级）后会返回旧结论。把规则版本编进 key，升级时 bumpRuleVersion() + cache.clear()，旧结论自然失效。失败结果也要缓存——否则用户每次 blur 都会再打一次「已占用」的接口。

提交门禁 ​

异步校验最大的坑是「校验还在飞，用户已经点了提交」。提交前必须 await 所有在途校验，或者直接用提交后的服务端校验兜底：

ts
async function onSubmit(values: FormValues) {
  const pending = fields.filter((f) => validator.isPending(f));
  const results = await Promise.all(pending.map((f) => validator.lastResult(f)));
  if (results.some((r) => r && !r.ok)) return;
  await api.save(values);
}

服务端永远要再校验一次：客户端异步校验只是体验优化，不是安全边界。

131.6 复杂结构：数组字段、嵌套与多步向导 ​

数组字段：三件事决定成败 ​

  1. 稳定 key：删除/移动后不能复用旧 key，否则组件实例与输入状态会错位；
  2. 错误路径：行级错误是 items.<index>.<field>，下标会随移动变化，必须按「当前下标」实时生成；
  3. 索引口径：move(from, to) 的 to 是「移动前的目标下标」，与 129.3 arrayMove 的三种下标口径 完全一致，跨册复用同一套语义。

运行方式：npx tsx examples/131-03-field-array-model.ts（实跑；断言覆盖稳定 id 不复用、移动/删除后的 key 顺序、行级错误路径、coerce、空数组的数组级错误、越界操作安全）

RHF 的 useFieldArray 与 VeeValidate 的 useFieldArray 都替你维护了稳定 key；如果你手写数组渲染，必须自己生成只增不减的 id（示例里的 row_1、row_2）。永远不要用 index 当 key，也永远不要用 Math.random()（每次渲染都变，等于全量重建）。

嵌套对象 ​

ts
const schema = z.object({
  user: z.object({ name: z.string().min(1), email: z.string().email() }),
  address: z.object({ city: z.string().min(1) }).optional(),
});
  • RHF 用点路径：register("user.name")，错误在 errors.user?.name；
  • VeeValidate 同样用点路径，数组用 items[0].name；
  • 可选嵌套对象要注意「父对象不存在时子字段错误挂在哪」：Zod 会报 address 缺失，而不是 address.city，UI 要能展示对象级错误。

多步向导：分步校验 + 最后全量校验 ​

ts
// 每步只 pick 自己的字段，最后用完整 schema 兜底
const stepSchemas = [Step1, Step2, Step3];
const full = Step1.merge(Step2).merge(Step3);

三个必须处理的边界：

  1. 回退保留值：back() 只改步骤，不清值；
  2. 跨步依赖：第 3 步的规则依赖第 1 步的值时，分步校验会漏，最后必须 validateAll()；
  3. 离开确认：dirty && !isSubmitting 时拦截路由跳转（beforeunload + 路由守卫）。

运行方式：npx tsx examples/131-04-submit-orchestration.ts（实跑；断言覆盖分步拦截、回退保留、全量校验、幂等键复用与轮换、并发提交合并、服务端 422 字段映射）

提交编排状态机 ​

idle → submitting → success
              ↘ error →（改值）→ idle
边界处理
双击/回车连按在途 Promise 复用（单飞），不重复下单
网络失败保留幂等键重试；成功后换新键
422 字段错误映射到字段 + 换键（用户会改值）
429/5xx指数退避重试，仍用同一幂等键
成功后换键 + 重置表单 + 失效相关查询（见 130 册）

幂等键的正确语义：一次「提交意图」一个键。网络失败重试是同一意图，复用它；用户改了值再提交是新意图，必须换。

131.7 生产细节：草稿、无障碍、输入法与埋点 ​

草稿持久化 ​

  • 只存业务字段，不存密码、验证码、支付信息；
  • 存带版本的 envelope：{ version: 2, savedAt, values }，Schema 升级后旧草稿要么迁移、要么丢弃；
  • 写入防抖 500ms~1s，页面 visibilitychange 时强制落盘；
  • 恢复草稿要提示用户（「已恢复上次未提交的内容」），不要静默覆盖。

存储实现见 19.4 类型安全的本地存储封装 与 19.9 IndexedDB 结构化仓储。

无障碍：错误必须「可被听见」 ​

tsx
<label htmlFor="email">邮箱</label>
<input
  id="email"
  aria-invalid={!!errors.email}
  aria-describedby={errors.email ? "email-error" : undefined}
/>
{errors.email && <p id="email-error" role="alert">{errors.email.message}</p>}
  • aria-invalid 标记状态，aria-describedby 把错误与控件关联；
  • role="alert" 让屏幕阅读器立即播报；
  • 提交失败后聚焦第一个错误字段（RHF shouldFocusError 默认开）；
  • 不要只靠颜色区分错误。

输入法（IME）与校验时机 ​

中文输入过程中，compositionstart 到 compositionend 之间的值是不完整的。在 onChange 上做实时校验会把拼音当成非法输入。处理方式：

  • 校验等 compositionend 后再触发；
  • 或用 event.nativeEvent.isComposing 过滤（键盘事件同理，见 128.2 原生快捷键实现）；
  • 格式化（手机号分段、金额千分位）必须在 composition 结束后做，否则光标会跳。

表单内快捷键 ​

Ctrl/Cmd + S 保存、Esc 取消、Ctrl/Cmd + Enter 提交，都要挂在表单作用域内，且输入框里不能抢占浏览器默认行为。作用域栈与可编辑目标豁免见 45.3.3 快捷键作用域 与 128.4 作用域栈与冲突治理。

埋点：表单质量比转化率更有用 ​

指标用途

首次错误字段分布优化文案与默认值

autofill 与受控组件 ​

浏览器自动填充不会触发 input 事件（部分浏览器只触发 change），受控组件可能拿不到值。对策：

  • 非受控（RHF register）天然兼容 autofill；
  • 受控组件在 onChange 之外监听 onInput，或在 visibilitychange/focus 时回读 DOM 值；
  • 不要给密码框加 autocomplete="off" 就以为解决了问题。

Formik 的现状 ​

截至 2025-11，Formik 最新仍为 2.4.x，长期只有零星补丁，社区普遍按「维护模式」对待（未见 3.x 正式版）。新项目优先 RHF / VeeValidate；存量迁移不必一刀切，先把校验逻辑抽成 Schema，表单库替换才是可控的。

React 19 的 form actions ​

tsx
// [项目内运行] React 19
const [state, formAction, isPending] = useActionState(async (_prev, formData: FormData) => {
  const parsed = schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { errors: flattenIssues(parsed.error) };
  await api.save(parsed.data);
  return { ok: true };
}, {});

它解决了「提交中状态 + 服务端错误回填」的原生链路，但字段级即时校验、数组字段、dirty 跟踪仍然需要库或自己实现。适合营销页、简单设置项，不适合复杂业务表单。

迁移清单 ​

  1. 把校验规则从组件里抽到 Schema（Schema 先落地，库后换）；
  2. 统一错误读取入口（flattenIssues / setError 映射），保证 UI 不感知库；
  3. 数组字段先换稳定 key，再换库；
  4. 提交编排（单飞、幂等、错误映射）独立于表单库，迁移时不动；
  5. 用同一套自测题回归：必填、跨字段、异步、数组、多步、服务端 422。

131.9 自测题 ​

1. 为什么 RHF 的 `useForm` 泛型要用 `z.input` 而不是 `z.infer`？【基础】

z.infer 等于 z.output，是解析后的类型；而表单里存的是用户输入的原始形态（字符串、可选、缺省）。有 coerce/default/transform 时两者不同，用 z.output 会让 defaultValues、register 的类型对不上。

2. `mode: 'onTouched'` 与 `onBlur` 的区别？【基础】

onBlur 每次失焦都校验；onTouched 是首次失焦后转为 onChange，之后边输边校验。前者更安静，后者反馈更快，大多数业务表单用 onTouched。

3. 为什么不能用 `index` 作为数组字段的 key？【基础】

删除/移动后下标会重排，React/Vue 会复用错误的组件实例，导致输入框内容错位、焦点跳转、校验状态串行。必须用只增不减的稳定 id（RHF 的 field.id、VeeValidate 的 field.key）。

4. `superRefine` 里的跨字段错误为什么有时不出现？【进阶】

superRefine 只在基础对象解析成功后执行。如果同一对象里还有字段级错误，跨字段规则不会跑——校验顺序是「先结构、后语义」。UI 上要先修字段错误，才能看到跨字段错误。

5. `formState` 是 Proxy，这对写组件有什么约束？【进阶】

只有被读取的属性才会订阅更新。不要在渲染里条件性读取 formState 的属性，否则订阅关系随渲染变化，出现「有时不更新」；只关心单个字段时用 useWatch，不要 watch() 整个表单。

6. 异步校验只做 `AbortController` 取消，够不够？【进阶】

不够。请求可能已经返回并进入微任务队列，取消不能阻止回调执行；必须用「发起序号 + 字段最新序号」判定结果归属，旧结果直接丢弃。取消只是省流量。

7. 异步校验结果缓存的 key 为什么要带规则版本？【进阶】

只按「字段 + 值」缓存，规则升级后仍会命中旧结论（例如密码强度从 6 位改成 8 位）。把规则版本编进 key，升级时清缓存，旧结论自动失效。

8. 幂等键什么时候复用、什么时候轮换？【挑战】

一次「提交意图」一个键：网络失败/5xx 重试是同一意图，必须复用；成功后、或用户改值后（含 422 字段错误）是新意图，必须换新键。反过来会导致重复下单或误判重复。

9. 多步表单为什么分步校验之外还要全量校验？【挑战】

分步校验只覆盖当前步字段，跨步依赖（第 3 步规则依赖第 1 步的值）和跨字段规则会漏。最后一步必须用合并后的完整 Schema 再跑一次，提交前也要兜底。

10. 为什么 Schema 里不应该写发请求的 `refine`？【挑战】

Schema 可能被 isValid 高频触发，无法防抖；异步 refine 无法处理竞态与取消；错误也无法区分「网络失败」与「已占用」。请求应放在字段级异步校验器里，Schema 只保留纯函数规则。
