66.1 依赖风险全景与四层治理模型 ​

概念解析 ​

第三方依赖的风险有三类，治理手段完全不同：

风险类型典型表现主要后果治理手段
代码漏洞库本身存在 XSS、原型污染、命令注入、ReDoS数据泄露、RCE、服务不可用准入 + 监测 + 修复 SOP
供应链投毒维护者账号被盗、同名抢注、安装脚本执行恶意代码、传递依赖被篡改npm install 即中招，构建机与开发者机器沦陷锁定 + 安装脚本白名单 + 私有 registry
合规与许可GPL/AGPL 传染、许可证未知、包已废弃法律风险、无法跟进安全修复准入评分 + 法务评审 + SBOM

供应链攻击的入口比想象中多，按发生频率排序：

  1. 维护者账号被盗：攻击者发布恶意新版本，如 2018 年 event-stream 通过新增依赖 flatmap-stream 窃取钱包私钥；
  2. 同名抢注（dependency confusion）：内部私有包名被公网抢注，npm install 优先命中公网恶意版本；
  3. 安装脚本即执行：preinstall/postinstall 在安装阶段拥有与开发者相同的权限；
  4. 传递依赖：你只审了直接依赖，漏洞或恶意代码藏在第 5 层依赖里；
  5. CDN / 外链脚本：绕过包管理器，直接 <script src> 引入，篡改后无 lockfile 可查。

治理模型是四层闭环，缺一层都会漏：

text
准入(66.2) → 锁定(66.3) → 监测(66.4) → 响应(66.5)
   ↑                                        │
   └──────────── 复盘反哺准入规则 ←──────────┘
  • 准入回答「这个包能不能进来」；
  • 锁定回答「进来之后每次装出来是否完全一样」；
  • 监测回答「已经在用的包后来出事了怎么办」；
  • 响应回答「已经出事时，多快、按什么路径修」。

四层里最容易被跳过的是准入——大多数团队是「先装上再说」，等 audit 报警才治理，此时迁移成本已经很高。

典型应用场景 ​

  • 新项目起步：依赖清单还短，正是建立准入规则的最佳时机；
  • 存量项目接手：先跑 pnpm audit + pnpm why 摸清家底，再按本章的 SLA 排修复优先级；
  • monorepo / 多团队：私有 registry、统一 overrides、集中审批，避免各仓库各自为政；
  • 合规审计：需要输出 SBOM、许可证清单与漏洞处置记录时。

最佳实践 ​

  • ✅ 把依赖治理写进 Definition of Done：新增依赖必须过准入，漏洞修复必须留记录；
  • ✅ 区分「直接依赖」与「传递依赖」的责任人：直接依赖由引入者负责，传递依赖由上游库负责、由本项目兜底；
  • ✅ 治理指标只盯三个：高危漏洞存量、平均修复时长（MTTR）、豁免到期数；
  • ❌ 不要把「audit 通过」当成治理完成——audit 只覆盖已知漏洞，管不了投毒与许可证。

66.2 依赖准入：评分、硬门槛与白名单审批 ​

概念解析 ​

准入不是「凭感觉判断这个库靠不靠谱」，而是把判断拆成可复核的维度。五个维度足够覆盖大多数场景：

维度看什么高风险信号
生态验证周下载量、GitHub star、被哪些知名项目使用周下载 < 1 万且无知名使用者
维护活跃度最近发布时间、issue 响应、维护者数量超过一年未发布、单维护者
供应链权限是否有 install/postinstall 脚本、是否申请敏感权限安装脚本 + 无源码可审
依赖深度传递依赖数量、是否引入重复大依赖传递依赖 > 10 层/个
合规许可证类型、是否有类型声明、是否废弃许可证未知、GPL/AGPL、已废弃

硬门槛优先于分数：安装脚本必须人工复核、废弃包一票否决、copyleft 必须法务评审——这些不能因为「总分低」被放过。

审批流程建议做成轻量 RFC，避免变成官僚流程：

  1. 引入者在 PR 描述里贴出评分结果与理由；
  2. Owner（前端架构组/安全组）在 1 个工作日内批复；
  3. 批准后登记到依赖白名单（含引入人、用途、复审日期）；
  4. 每季度复审一次，无使用记录的依赖删除。

完整代码示例 ​

typescript
// 文件: examples/66-01-dependency-admission.ts（核心节选）
// 评分越高风险越大;硬门槛(安装脚本/废弃/copyleft)覆盖分数
function assess(c: Candidate): Assessment {
  let score = 0;
  const reasons: string[] = [];
  if (c.weeklyDownloads < 10_000) score += 25;       // 无人审计
  if (c.daysSinceLastPublish > 730) score += 25;     // 维护者离场
  if (c.hasInstallScript) score += 15;               // 安装即执行
  if (c.transitiveDeps > 10) score += 15;            // 攻击面过大
  if (c.deprecated) score += 30;
  score = Math.min(100, score);
  let decision = score <= 20 ? "approve" : score <= 45 ? "review" : "reject";
  if (c.hasInstallScript && decision === "approve") decision = "review";
  if (c.deprecated) decision = "reject";
  return { name: c.name, score, decision, reasons };
}

运行方式：npx tsx examples/66-01-dependency-admission.ts（下载量/维护度/许可证/安装脚本/依赖深度五维评分，硬门槛覆盖与 approve/review/reject 分级，共 6 组硬断言）。

最佳实践 ​

  • ✅ 优先复用已有依赖或平台原生能力，能用 fetch/Intl/structuredClone 就不新增包；
  • ✅ 引入前看 package.json 的 scripts：有 postinstall 的包必须读源码或改用 --ignore-scripts；
  • ✅ 大依赖（组件库、图表库、编辑器）单独走架构评审，因为它们决定未来几年的升级成本；
  • ✅ 私有包统一加 scope（@company/*），并在 .npmrc 为 scope 指定私有 registry，防同名抢注；
  • ❌ 不要用「下载量高」作为唯一理由——高下载量包也可能突然被投毒或转为 protestware；
  • ❌ 不要为了省事关闭 strict-peer-dependencies 或 shamefully-hoist 来「让装得上」，那会把依赖问题推迟到运行时。

66.3 可复现安装与供应链加固 ​

概念解析 ​

可复现安装的核心是：同一份代码，在任何机器、任何时间装出的依赖树完全一致。三件套缺一不可：

  1. 提交 lockfile（pnpm-lock.yaml），记录每个包的确切版本与 integrity 哈希；
  2. CI 使用 --frozen-lockfile，lockfile 与 package.json 不一致时直接失败，而不是偷偷升级；
  3. 锁定包管理器版本（packageManager 字段 + corepack），避免 pnpm/npm 解析差异。

供应链加固的常用手段：

手段解决什么配置示例
冻结 lockfile本地/CI 版本漂移pnpm install --frozen-lockfile
安装脚本白名单恶意 postinstallpnpm onlyBuiltDependencies 或 ignore-scripts=true
私有 registry + scope依赖混淆（同名抢注）.npmrc 中 @company:registry=...
强制版本覆盖传递依赖漏洞无上游修复pnpm.overrides
补丁依赖上游无补丁但必须修pnpm.patchedDependencies
最小发布年龄新版本被投毒后的冷却期pnpm 的 minimumReleaseAge（视版本支持）

依赖混淆值得单独说明：攻击者把内部包名（如 @company/utils）发布到公网 registry，如果你的 .npmrc 没有为 @company 指定私有 registry，安装时可能命中公网恶意版本。防御是三件事：scope 命名 + scope 级 registry 绑定 + lockfile 中 resolution.tarball 指向内部地址。

完整代码示例 ​

yaml
# 文件: .github/workflows/dependency-guard.yml（核心节选）
- name: Install (frozen)
  run: pnpm install --frozen-lockfile

- name: Audit (block high/critical)
  run: pnpm audit --prod --audit-level=high

- name: Verify lockfile unchanged
  run: git diff --exit-code pnpm-lock.yaml
jsonc
// 文件: package.json —— 传递依赖覆盖与补丁登记
{
  "pnpm": {
    "overrides": {
      // 传递依赖被锁在漏洞版本时,强制提升到已修复版本
      "minimist": ">=1.2.8",
      "cross-spawn": ">=7.0.5"
    },
    "onlyBuiltDependencies": ["esbuild", "sharp"] // 仅允许这些包执行安装脚本
  }
}

运行方式：以上为配置片段，复制到项目后由 pnpm install 生效。

最佳实践 ​

  • ✅ 依赖升级统一走机器人（Renovate/Dependabot）并配审核规则，禁止开发者本地随意 pnpm update --latest；
  • ✅ 每次升级单独 PR，lockfile diff 必须人工看一眼——异常新增的传递依赖是投毒信号；
  • ✅ CI 缓存 pnpm store 但不要缓存 node_modules/.vite，后者会掩盖依赖变更；
  • ⚠️ overrides 是双刃剑：强制提升可能引入不兼容，必须跑全量测试并在注释里写原因与移除条件；
  • ❌ 不要用 npm install --no-save 临时装包后照常提交代码——本地能跑、CI 装不出来是最常见的「灵异故障」。

66.4 持续监测：审计、SBOM 与漏洞情报 ​

概念解析 ​

依赖装进来只是开始，监测要解决的是「后来出事了，我们多久知道」。监测分三层：

层级工具/数据源作用落地位置
本地/提交前pnpm audit、depcheck快速反馈，拦住明显问题pre-push / 本地脚本
CI 门禁pnpm audit、Snyk、OSV-Scanner阻断 high/critical 进入主干PR 流水线
持续情报Dependabot、Renovate、GitHub Advisory、OSV.dev新漏洞出现时自动开 PR/告警仓库机器人 + 安全看板

审计工具的局限必须知道：

  • npm audit 依赖 npm 的 advisory 库，覆盖不全且对传递依赖的修复建议经常是「升级到不存在的版本」；
  • 不同工具对同一漏洞的定级可能不同，应以 CVSS + 可达性综合判断（66.5）；
  • audit 只覆盖「已知漏洞」，对投毒、许可证、废弃包无能为力——这些靠准入与 SBOM。

**SBOM（软件物料清单）**是合规与应急的基础设施：记录每个依赖的名称、版本、许可证、哈希、直接/传递关系。出事后可以 5 分钟内回答「我们有没有用这个包」，而不是全仓库 grep。常见格式是 CycloneDX / SPDX，可用 @cyclonedx/cyclonedx-npm、syft 等工具生成，产物随版本归档。

告警治理同样重要：如果每天 50 条 low 告警，团队很快会全部忽略。建议：

  • CI 只阻断 high/critical（与 9.9 的门禁一致）；
  • medium/low 进入周报，按批次处理；
  • 每条忽略必须带到期日与理由，到期自动重新告警；
  • 对「无法修复」的漏洞单独建台账，而不是让它反复出现。

典型应用场景 ​

  • PR 流水线：新依赖引入时同时跑准入检查与 audit；
  • 发版前：生成 SBOM 归档，作为交付物的一部分；
  • 安全事件响应：根据 SBOM 快速定位受影响的服务与版本；
  • 合规审计：输出许可证清单，识别 copyleft 传染风险。

最佳实践 ​

  • ✅ 审计结果接入 PR 评论，让引入者当场看到新增漏洞，而不是等安全周报；
  • ✅ 用 pnpm why <pkg> 追溯传递依赖来源，修复时优先改直接依赖而不是全局 overrides；
  • ✅ SBOM 与构建产物同版本归档，保留至少一个发布周期；
  • ⚠️ 不要同时开三套扫描器却没人看结果——工具数量不等于治理能力；
  • ❌ 不要用 audit fix --force 一键升级，它可能把主版本全部提升，破坏性变更无人评估。

66.5 高危漏洞修复 SOP ​

概念解析 ​

扫描器给出的 severity 只是声明严重度，真正决定修复优先级的是有效严重度：

text
有效严重度 = 声明严重度
           − 运行环境折减（仅构建期/开发依赖：降 2 级）
           − 可达性折减（运行时依赖但业务不可达：降 1 级）
           + 利用成熟度加成（已有活跃利用：升 1 级）

四个判断问题，缺一不可：

  1. 漏洞代码在哪里跑？ 运行时依赖、构建期依赖、还是仅开发依赖？
  2. 业务真的会走到漏洞路径吗？ 有调用链证据，还是「理论上可能」？
  3. 暴露面有多大？ 公网、内网、还是仅本地？
  4. 有没有现成利用？ 公开 PoC、在野利用、还是仅理论推演？

分级 SLA（可按团队调整，但必须写进制度）：

有效严重度止血时限修复时限典型动作
Critical24 小时72 小时功能开关/回滚/网关拦截 + 紧急升级
High72 小时7 天升级或 overrides，排入当前迭代
Medium—30 天常规迭代修复
Low—90 天随下次依赖升级处理

修复路径按成本从低到高，能走前一步就不要跳到后一步：

顺序路径适用条件风险
0止血Critical/High 且修复需要时间功能受限，需评估业务影响
1直接升级直接依赖，有 patch/minor 修复版低；major 需回归
2overrides传递依赖，上游已修复但未发版可能版本冲突/重复实例
3打补丁上游无补丁，漏洞可利用且必须修维护成本高，需跟踪上游
4替换库长期无维护或补丁不可行迁移成本与 API 差异
5隔离/下线无法修复且业务可暂时关闭业务损失
6风险接受不可达/仅开发依赖，且有证据必须限时、留痕、审批

无补丁时的决策：优先评估「替换」还是「隔离」，不要默认接受风险。接受风险必须满足三个条件：有不可达证据、有豁免期限、有审批人。豁免到期自动回到待办列表，而不是永久关闭。

修复后的验证清单：

  1. pnpm audit / OSV 复跑，目标漏洞清零；
  2. 全量测试 + 受影响模块的回归；
  3. lockfile diff 审查：只出现预期版本变化；
  4. 构建产物与体积检查（升级可能引入新依赖）；
  5. 灰度发布并观察错误率/性能；
  6. 更新依赖台账与 SBOM，记录修复版本与日期；
  7. 复盘：漏洞是如何进来的？准入规则要不要补一条？

完整代码示例 ​

typescript
// 文件: examples/66-02-vuln-remediation.ts（核心节选）
function effectiveSeverity(f: Finding): Severity {
  let s = f.declared;
  if (f.env !== "runtime") s = shift(s, -2);        // 只在构建期/开发依赖
  else if (!f.reachable) s = shift(s, -1);          // 运行时但业务不可达
  if (f.exploit === "active") s = shift(s, 1);      // 已有活跃利用
  return s;
}

function chooseAction(f: Finding, effective: Severity): Action {
  if (f.patchAvailable) return f.direct ? "upgrade" : "override";
  if (f.env !== "runtime" || !f.reachable) return "accept";
  if (f.canReplace) return "replace";
  return "isolate";
}

运行方式：npx tsx examples/66-02-vuln-remediation.ts（有效严重度折减/加成、分级 SLA、六种修复路径、审批门槛与截止时间，共 6 组硬断言）。

最佳实践 ​

  • ✅ 每个高危漏洞建一个跟踪单，字段固定：编号、包、声明/有效严重度、影响服务、修复路径、负责人、截止日、验证结果；
  • ✅ Critical 先止血再修复，顺序不能反——等 72 小时修完再止血，窗口期足够被利用；
  • ✅ major 版本升级必须审批并灰度，安全修复不能成为「跳过回归」的理由；
  • ⚠️ overrides 强制提升后一定要检查是否产生重复实例（同一包两个版本会让 instanceof、单例、类型判断全部失效）；
  • ❌ 不要把「devDependency 里的漏洞」直接忽略——构建机同样有源码与 CI 凭据，投毒目标往往就是构建链；
  • ❌ 不要用「这个漏洞利用条件很苛刻」作为长期不修的理由，条件会随业务变化而改变。

66.6 自测题 ​

1. 【基础】为什么「提交 lockfile + CI 用 --frozen-lockfile」是依赖治理的底线？

lockfile 记录了解析后的确切版本与 integrity 哈希，保证同一份代码在任何机器上装出相同的依赖树。--frozen-lockfile 让 CI 在 package.json 与 lockfile 不一致时直接失败，杜绝「本地偷偷装了新版本、CI 装出另一套」的漂移。没有这条底线，后面所有审计、复现、回滚都失去事实基础。

2. 【基础】安装脚本（preinstall/postinstall）为什么是高危信号？

安装脚本在 npm install 阶段执行，拥有与开发者/CI 相同的权限：可以读环境变量、读 SSH key、写文件、发起网络请求。攻击者只需在恶意版本里加一个 postinstall 就能窃取凭据。防御是白名单（onlyBuiltDependencies）、--ignore-scripts，或引入前人工读脚本源码。

3. 【基础】依赖混淆（dependency confusion）是什么？如何防？

攻击者把公司内部私有包名发布到公网 registry，利用包管理器「同名优先」的行为让安装命中恶意版本。防御三件套：内部包统一使用 scope（如 @company/*）、在 .npmrc 为 scope 绑定私有 registry、lockfile 校验 tarball 地址；必要时启用 registry 代理并禁止公网直连。

4. 【进阶】声明严重度与有效严重度有什么区别？为什么要折减？

声明严重度来自 CVSS/扫描器，描述漏洞本身的通用危害；有效严重度结合运行环境、可达性、暴露面与利用成熟度，描述「对当前项目实际的风险」。仅构建期依赖不进入用户浏览器、运行时依赖但业务不可达，都应折减；已有活跃利用则加成。不折减会导致大量不可达漏洞占用修复资源，真正高危反而被淹没。

5. 【进阶】传递依赖有漏洞、上游还没发修复版，有哪几种修复路径？怎么选？

按成本排序：① pnpm.overrides 强制传递依赖到已修复版本（若上游已发布但未提升）；② patchedDependencies/patch-package 打最小补丁（无修复版但必须修）；③ 替换直接依赖为维护更好的替代库；④ 隔离/下线调用该库的功能；⑤ 有不可达证据时限时风险接受。选择依据是「漏洞是否运行时可达 + 修复成本 + 业务影响」，不是「哪种最省事」。

6. 【进阶】为什么 CI 只阻断 high/critical，medium/low 走周报？

门禁的目标是拦住「必须马上处理」的风险，而不是把所有告警都变成阻断。medium/low 数量多、修复窗口长，全部阻断会让主干长期红色，团队最终学会绕过门禁。正确做法是分级：高危阻断、中低危进周报按批次处理，并对每条忽略设置到期日，避免「眼不见为净」。

7. 【挑战】设计一个前端团队的依赖治理闭环，要求覆盖新依赖引入、存量漏洞和应急响应。

四层闭环：① 准入——评分器 + 硬门槛 + RFC 审批 + 白名单登记；② 锁定——lockfile、packageManager、--frozen-lockfile、scope 级 registry、安装脚本白名单；③ 监测——CI audit 阻断 high/critical、Dependabot/Renovate 自动 PR、SBOM 归档、周报处理中低危；④ 响应——有效严重度定级、SLA 表、六种修复路径决策树、止血优先、验证清单、豁免台账与复盘。指标盯高危存量、MTTR、豁免到期数，复盘结论反哺准入规则。

8. 【挑战】Critical 漏洞修复需要 72 小时，为什么必须在 24 小时内先止血？止血手段有哪些？

高危漏洞的利用窗口以小时计，等修复完成再防护等于把窗口完全暴露。止血手段：功能开关关闭受影响路径、网关/WAF 规则拦截利用特征、CSP 收紧外链、回滚到未受影响版本、临时下线相关功能。止血先于根治，是因为「业务暂时受限」的代价通常远低于「数据泄露/被入侵」的代价；止血后仍要按 SLA 完成根治并验证。
