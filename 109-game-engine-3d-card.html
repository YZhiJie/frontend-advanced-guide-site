本部分内容 ​

上一册讲游戏内核（循环/动画/对象池），这一册解决两个问题：引擎怎么选，以及把内核知识用到一个真实品类——3D 卡牌。卡牌是前端游戏面试里出镜率最高的实战题：洗牌算法（公平性证明）、发牌调度（逻辑与动画分离）、3D 翻转（状态机 + 缓动 + 纹理切换）、场景管理（大厅/对局/结算栈）、相机与 MVP 矩阵。全部示例不依赖引擎、纯 TypeScript 可实跑——这些正是引擎替你做的事，看懂它们，Cocos/Laya/Three.js 只是换层皮。

决策树 ​

要做 3D？
├─ 是 → 重度 3D（动作/赛车）？
│   ├─ 是 → Cocos Creator（国内生态+小游戏一键发布）
│   └─ 否 → 轻 3D（卡牌/展示/可视化）→ Three.js（自由度高、资料最多）
└─ 否 → 纯 2D
    ├─ 要发微信小游戏 + 团队缺编辑器 → Cocos Creator
    ├─ 棋牌/买量品类 + FairyGUI UI 工作流 → Laya
    └─ 海外 H5 营销页/轻交互 → PixiJS（包体最小、API 最干净）

三条硬规则：

  1. 品类跟着引擎生态走：棋牌/卡牌看 Laya+Cocos 的存量项目最多，抄作业成本低；Web3D 展示 Three.js 一家独大。
  2. 发行渠道决定下限：要一键发小游戏就别选自搭管线的方案——PixiJS/Three.js 发小游戏要自己包适配层（见 108 册 108.5）。
  3. 团队已有资产 > 技术参数：团队有 FairyGUI 工作流沉淀就选 Laya/Cocos，有 Three.js 沉淀就别为了「引擎功能全」换 Cocos——迁移成本远超参数差异。

109.2 洗牌与发牌：公平性可证明 ​

概念解析 ​

洗牌是卡牌游戏的信任基石，两个要求：无偏（每种排列等概率）和可复现（回放、作弊审计、断线重连）。

array.sort(() => Math.random() - 0.5) 是经典错误：比较器不稳定导致排序结果依赖原顺序，52! 种排列不是等概率的。Fisher-Yates 是唯一标准答案：从后往前，每个位置 i 与 [0, i] 区间内的随机位置 j 交换。关键细节是 j 取自 [0, i] 而不是 [0, n)——后者会产生 n^n 种路径对 n! 种排列，除不尽就必有偏。

种子随机数解决复现问题：服务端洗牌只下发种子，客户端用同一种子 + 同一 PRNG 算法必然得到同一序列——回放系统、防作弊审计、断线重连恢复牌局全靠它。注意 PRNG 是「游戏可复现」用的，不能用于真钱赌博的安全场景（那种要 CSPRNG + 服务端权威）。

发牌的架构原则：逻辑瞬间完成，动画另行调度。 洗牌发牌的逻辑结果（每人手牌）在瞬间全部算完；发牌动画是表现层的事——用调度队列按时间戳逐张触发，动画延迟绝不阻塞逻辑。

完整代码示例 ​

ts
// 文件: examples/109-01-shuffle-deal.ts
// 洗牌与发牌：Fisher-Yates 洗牌 + 种子随机数（可复现回放）+ 发牌动画队列
// 目标：公平性可证明、对局可回放（同种子必同序列）、动画与逻辑分离

import assert from "node:assert";

/** mulberry32：32 位种子 PRNG，周期 2^32，质量足够游戏用（不要用于安全场景） */
function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

/** Fisher-Yates 洗牌：唯一无偏的原地洗牌算法，O(n) */
function shuffle<T>(arr: T[], rand: () => number): T[] {
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1)); // 关键：j 取自 [0, i]，不是 [0, n)
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}

interface Card {
  suit: "♠" | "♥" | "♣" | "♦";
  rank: number; // 1-13
}

function newDeck(): Card[] {
  const suits: Card["suit"][] = ["♠", "♥", "♣", "♦"];
  const deck: Card[] = [];
  for (const suit of suits) for (let rank = 1; rank <= 13; rank++) deck.push({ suit, rank });
  return deck;
}

/** 发牌调度器：逻辑瞬间完成，动画按时序逐个触发——二者必须分离 */
class DealScheduler {
  private queue: Array<{ card: Card; target: number; at: number }> = [];
  private t = 0;
  constructor(private intervalSec = 0.15) {}

  /** 轮流向 target 0..players-1 发 count 张 */
  schedule(deck: Card[], players: number, count: number): void {
    for (let n = 0; n < count; n++) {
      for (let p = 0; p < players; p++) {
        const card = deck.shift();
        if (!card) return;
        this.queue.push({ card, target: p, at: this.t });
        this.t += this.intervalSec;
      }
    }
  }

  /** 返回 now 时刻应已发出的全部牌（按 at 排序） */
  drainUntil(now: number): Array<{ card: Card; target: number }> {
    const due = this.queue.filter((e) => e.at <= now);
    this.queue = this.queue.filter((e) => e.at > now);
    return due;
  }

  get pending(): number {
    return this.queue.length;
  }
}

function runAssertions() {
  // ---------- 测试 1：同种子必同序列（回放根基） ----------
  const d1 = shuffle(newDeck(), mulberry32(42));
  const d2 = shuffle(newDeck(), mulberry32(42));
  const d3 = shuffle(newDeck(), mulberry32(43));
  assert.deepEqual(d1, d2, "同种子洗牌结果必须一致");
  assert.notDeepEqual(d1.slice(0, 5), d3.slice(0, 5), "不同种子应不同");
  console.log("[1/4] 种子可复现 OK, 首张:", `${d1[0].suit}${d1[0].rank}`);

  // ---------- 测试 2：无偏性粗检——每张牌出现在首位的频率应趋近 1/52 ----------
  const trials = 52000;
  const firstCount = new Map<string, number>();
  const rand = mulberry32(7);
  for (let i = 0; i < trials; i++) {
    const d = shuffle(newDeck(), rand);
    const key = `${d[0].suit}${d[0].rank}`;
    firstCount.set(key, (firstCount.get(key) ?? 0) + 1);
  }
  assert.equal(firstCount.size, 52, "52 张牌都应能出现在首位");
  for (const [, c] of firstCount) {
    // 期望 1000 次，±30% 容差内视为均匀（统计波动）
    assert.ok(c > 700 && c < 1300, `频率异常: ${c}`);
  }
  console.log("[2/4] 无偏性粗检 OK, 52 张均上榜, 频次区间:", Math.min(...firstCount.values()), "-", Math.max(...firstCount.values()));

  // ---------- 测试 3：发牌调度——时序与轮转 ----------
  const deck = shuffle(newDeck(), mulberry32(1));
  const sched = new DealScheduler(0.15);
  sched.schedule([...deck], 4, 2); // 4 人每人 2 张共 8 张
  assert.equal(sched.pending, 8);
  const t0 = sched.drainUntil(0.01); // 第 1 张
  assert.equal(t0.length, 1);
  assert.equal(t0[0].target, 0);
  const t1 = sched.drainUntil(0.61); // 应发完前 5 张中的剩余（0.15/0.3/0.45/0.6）
  assert.equal(t1.length, 4);
  assert.deepEqual(t1.map((e) => e.target), [1, 2, 3, 0], "轮转顺序");
  console.log("[3/4] 发牌调度 OK, 剩余:", sched.pending);

  // ---------- 测试 4：牌堆守恒——发出+剩余=52，无重复 ----------
  const deck2 = shuffle(newDeck(), mulberry32(99));
  const total = deck2.length;
  const sched2 = new DealScheduler(0.1);
  const working = [...deck2];
  sched2.schedule(working, 2, 5); // 发 10 张
  assert.equal(working.length, total - 10);
  const dealt = sched2.drainUntil(999);
  const keys = new Set(dealt.map((e) => `${e.card.suit}${e.card.rank}`));
  assert.equal(keys.size, 10, "发出的牌不得重复");
  console.log("[4/4] 牌堆守恒 OK, 发出:", dealt.length, "剩余:", working.length);

  console.log("\n✅ 109-01 洗牌与发牌 全部断言通过");
}

runAssertions();

运行方式：npx tsx examples/109-01-shuffle-deal.ts

应用实践 ​

  • 服务端权威：真人对局洗牌必须在服务端做，客户端只收种子或结果；客户端洗牌只能用于单机玩法。
  • 回放系统：存「种子 + 全部玩家操作序列」即可完整复现整局——这是最小成本的回放方案，不用录屏。
  • 抽卡概率：抽卡（gacha）是另一个话题，核心是「权重表 + 保底计数器」，概率必须服务端配置化，前端永不硬编码。

109.3 卡牌 3D 翻转：状态机 + 缓动 + 纹理切换 ​

概念解析 ​

卡牌翻转看着简单，写对的人不多——三个细节决定质感：

  1. 状态机管生命周期：faceDown → flippingUp → faceUp → flippingDown → faceDown。关键是动画进行中禁止反向触发——玩家连点时如果每次都从头反向，卡牌会鬼畜抖动。迁移表把非法跳转显式拒掉（返回 false 让调用方忽略这次点击）。
  2. 缓动选 easeInOutCubic：起步加速、过半减速，物理上接近真实翻牌的手感。线性插值的翻转像机器，别用。
  3. 90° 才换纹理：rotationY 从 0° 转到 180° 的过程中，卡牌侧面厚度在 90° 时视觉宽度为 0——这一刻把贴图从背面换成正面，人眼完全察觉不到。提前换会看到背面图案突然消失，延后换会看到背面图案镜像反转。

渲染层面，Three.js 里是 PlaneGeometry 双面贴图（或两个面片背靠背）+ rotation.y 插值；Cocos 里是 scaleX 从 1→-1 的伪 3D（2D 项目标准做法，90° 对应 scaleX=0 换贴图）。原理一模一样。

完整代码示例 ​

ts
// 文件: examples/109-02-card-flip-state-machine.ts
// 卡牌 3D 翻转：状态机（非法迁移拒绝）+ 缓动插值 + 正反面纹理切换时机
// 目标：连点不鬼畜（动画中禁止反向）、角度与时间解耦、过半帧切换纹理

import assert from "node:assert";

type FlipState = "faceDown" | "flippingUp" | "faceUp" | "flippingDown";

/** 合法迁移表：不在表里的迁移一律拒绝 */
const TRANSITIONS: Record<FlipState, FlipState[]> = {
  faceDown: ["flippingUp"],
  flippingUp: ["faceUp"], // 动画中不允许打断——连点不鬼畜的关键
  faceUp: ["flippingDown"],
  flippingDown: ["faceDown"],
};

/** easeInOutCubic：加速-减速，卡牌翻转最常用的缓动 */
function easeInOutCubic(t: number): number {
  return t < 0.5 ? 4 * t * t * t : 1 - Math.pow(-2 * t + 2, 3) / 2;
}

class CardFlip {
  state: FlipState = "faceDown";
  private progress = 0; // 0→1 动画进度
  private direction: 1 | -1 = 1; // 1=翻到正面 -1=翻到背面
  constructor(private durationSec = 0.4) {}

  /** 请求翻面；动画进行中返回 false（调用方据此忽略连点） */
  flip(): boolean {
    const next: FlipState | null =
      this.state === "faceDown" ? "flippingUp" : this.state === "faceUp" ? "flippingDown" : null;
    if (next === null) return false;
    assert.ok(TRANSITIONS[this.state].includes(next), `非法迁移 ${this.state} → ${next}`);
    this.direction = next === "flippingUp" ? 1 : -1;
    this.state = next;
    this.progress = 0;
    return true;
  }

  /** 每帧推进，返回当前 rotationY（度，0=背面朝上 180=正面朝上） */
  update(dt: number): number {
    if (this.state === "faceDown") return 0;
    if (this.state === "faceUp") return 180;
    this.progress = Math.min(1, this.progress + dt / this.durationSec);
    const eased = easeInOutCubic(this.progress);
    const done = this.progress >= 1;
    if (done) {
      this.state = this.direction === 1 ? "faceUp" : "faceDown";
      return this.direction === 1 ? 180 : 0;
    }
    return this.direction === 1 ? eased * 180 : 180 - eased * 180;
  }

  /** 当前应显示正面纹理吗？转过 90° 才切换——这是「翻面」视觉的核心 */
  get showFront(): boolean {
    if (this.state === "faceUp") return true;
    if (this.state === "faceDown") return false;
    // 动画中：过半切换
    return this.direction === 1 ? this.progress >= 0.5 : this.progress < 0.5;
  }
}

function runAssertions() {
  // ---------- 测试 1：完整翻面流程 ----------
  const card = new CardFlip(0.4);
  assert.equal(card.state, "faceDown");
  assert.equal(card.update(0), 0);
  assert.ok(card.flip());
  assert.equal(card.state, "flippingUp");
  const mid = card.update(0.2); // 走一半时间
  assert.ok(mid > 0 && mid < 180, `中途角度应在 0~180，实际 ${mid}`);
  const end = card.update(0.25); // 超时长，应钳到 180
  assert.equal(end, 180);
  assert.equal(card.state, "faceUp");
  console.log("[1/4] 完整翻面 OK, 中途角度:", mid.toFixed(1));

  // ---------- 测试 2：连点防鬼畜——动画中 flip 被拒绝 ----------
  const c2 = new CardFlip(0.4);
  assert.ok(c2.flip());
  assert.equal(c2.flip(), false, "flippingUp 中再次 flip 应返回 false");
  c2.update(0.5); // 播完
  assert.equal(c2.state, "faceUp");
  assert.ok(c2.flip(), "播完后才能反向");
  assert.equal(c2.state, "flippingDown");
  console.log("[2/4] 连点防鬼畜 OK");

  // ---------- 测试 3：纹理切换时机——过 90° 才换面 ----------
  const c3 = new CardFlip(0.4);
  c3.flip();
  c3.update(0.1); // 25%：仍应显示背面

  c3.update(0.15); // 87.5%：应显示正面

  console.log("[3/4] 纹理切换时机 OK");

  console.log("[4/4] 缓动对称性 OK, 半程角度:", halfAngle.toFixed(3));

  console.log("\n✅ 109-02 卡牌翻转状态机 全部断言通过");
}

109.4 WebGL 3D 数学：MVP 管线手推一遍 ​

概念解析 ​

3D 渲染的全部数学浓缩成一行：gl_Position = P × V × M × pos。三个矩阵各管一段：

pos (模型空间, 如卡牌顶点)
  │ M (Model：平移/旋转/缩放，把模型摆进世界)
  ▼
世界空间坐标
  │ V (View：lookAt，把世界搬到相机视角下，相机永远看向 -z)
  ▼
视图空间坐标
  │ P (Projection：perspective，视锥体压成标准立方体，近大远小)
  ▼
裁剪空间坐标 → 透视除法 (xyz/w) → NDC [-1,1]³ → 屏幕像素

必须记住的三条铁律：

  1. 矩阵乘法不可交换：T × R（先转后移）和 R × T（先移后转）结果完全不同。记法：列主序下最右边的变换最先作用于顶点。
  2. 列主序存储：WebGL/OpenGL 的 mat4 是列主序——m[12..14] 才是平移分量。按行主序写库，平移会跑到第四行，出来的画面全部错乱。
  3. 透视除法不在矩阵里：perspective 矩阵只是把 w 攒出来（m[11]=-1 让 w=-z），真正的「近大远小」发生在硬件做的 xyz/w 除法里。w≤0 的点（相机背后）直接被裁剪。

卡牌项目里相机通常固定（俯视 30-45° 的牌桌视角），M 矩阵管每张牌的位置/翻转，V/P 全局只算一次——这就是为什么 3D 卡牌是入门 3D 的最佳品类：矩阵用得浅，但每一步都是真功夫。

完整代码示例 ​

ts
// 文件: examples/109-03-mat4-mvp.ts
// 最小 4x4 矩阵库：MVP 管线（Model-View-Projection）手推一遍
// 目标：看懂 gl_Position = P × V × M × pos 每一步在干什么，列主序与 WebGL 一致

import assert from "node:assert";

type Mat4 = Float32Array; // 长度 16，列主序（WebGL/OpenGL 约定）
type Vec3 = [number, number, number];

function identity(): Mat4 {
  const m = new Float32Array(16);
  m[0] = m[5] = m[10] = m[15] = 1;
  return m;
}

/** 矩阵乘：out = a × b（先应用 b，再应用 a） */
function multiply(a: Mat4, b: Mat4): Mat4 {
  const out = new Float32Array(16);
  for (let col = 0; col < 4; col++) {
    for (let row = 0; row < 4; row++) {
      let sum = 0;
      for (let k = 0; k < 4; k++) sum += a[k * 4 + row] * b[col * 4 + k];
      out[col * 4 + row] = sum;
    }
  }
  return out;
}

function translate(x: number, y: number, z: number): Mat4 {
  const m = identity();
  m[12] = x;
  m[13] = y;
  m[14] = z;
  return m;
}

/** 绕 Y 轴旋转（右手系，弧度） */
function rotateY(rad: number): Mat4 {
  const c = Math.cos(rad);
  const s = Math.sin(rad);
  const m = identity();
  m[0] = c;
  m[2] = -s;
  m[8] = s;
  m[10] = c;
  return m;
}

/** 透视投影：fovY 弧度，aspect 宽高比 */
function perspective(fovY: number, aspect: number, near: number, far: number): Mat4 {
  const f = 1 / Math.tan(fovY / 2);
  const m = new Float32Array(16);
  m[0] = f / aspect;
  m[5] = f;
  m[10] = (far + near) / (near - far);
  m[11] = -1;
  m[14] = (2 * far * near) / (near - far);
  return m;
}

/** 视图矩阵：eye 看向 center，up 为上方向 */
function lookAt(eye: Vec3, center: Vec3, up: Vec3): Mat4 {
  const sub = (a: Vec3, b: Vec3): Vec3 => [a[0] - b[0], a[1] - b[1], a[2] - b[2]];
  const norm = (v: Vec3): Vec3 => {
    const l = Math.hypot(v[0], v[1], v[2]);
    return [v[0] / l, v[1] / l, v[2] / l];
  };
  const cross = (a: Vec3, b: Vec3): Vec3 => [
    a[1] * b[2] - a[2] * b[1],
    a[2] * b[0] - a[0] * b[2],
    a[0] * b[1] - a[1] * b[0],
  ];
  const dot = (a: Vec3, b: Vec3) => a[0] * b[0] + a[1] * b[1] + a[2] * b[2];

  const zc = norm(sub(eye, center)); // 相机朝 -z 看
  const xc = norm(cross(up, zc));
  const yc = cross(zc, xc);

  const m = identity();
  m[0] = xc[0];
  m[1] = yc[0];
  m[2] = zc[0];
  m[4] = xc[1];
  m[5] = yc[1];
  m[6] = zc[1];
  m[8] = xc[2];
  m[9] = yc[2];
  m[10] = zc[2];
  m[12] = -dot(xc, eye);
  m[13] = -dot(yc, eye);
  m[14] = -dot(zc, eye);
  return m;
}

/** 矩阵作用于点（w=1），返回 [x,y,z,w]；透视除法由调用方做 */
function transformPoint(m: Mat4, p: Vec3): [number, number, number, number] {
  const [x, y, z] = p;
  const out = [0, 0, 0, 0];
  for (let row = 0; row < 4; row++) {
    out[row] = m[row] * x + m[4 + row] * y + m[8 + row] * z + m[12 + row] * 1;
  }
  return out as [number, number, number, number];
}

const nearly = (a: number, b: number, eps = 1e-4) => Math.abs(a - b) < eps;

function runAssertions() {
  // ---------- 测试 1：单位矩阵性质 M × I = M ----------
  const t = translate(3, 4, 5);
  const ti = multiply(t, identity());
  assert.deepEqual([...ti], [...t]);
  console.log("[1/4] 单位矩阵性质 OK");

  // ---------- 测试 2：平移 + 旋转复合（先转后移） ----------
  const model = multiply(translate(10, 0, 0), rotateY(Math.PI / 2));
  const [x, , z] = transformPoint(model, [1, 0, 0]);
  // (1,0,0) 绕 Y 转 90° → (0,0,-1)，再平移 (10,0,0) → (10,0,-1)
  assert.ok(nearly(x, 10) && nearly(z, -1), `得到 (${x}, ${z})`);
  console.log("[2/4] 复合变换 OK:", `(${x.toFixed(3)}, ${z.toFixed(3)})`);

  // ---------- 测试 3：lookAt——eye(0,0,5) 看原点，原点在视图空间应为 (0,0,-5) ----------
  const view = lookAt([0, 0, 5], [0, 0, 0], [0, 1, 0]);
  const [vx, vy, vz] = transformPoint(view, [0, 0, 0]);
  assert.ok(nearly(vx, 0) && nearly(vy, 0) && nearly(vz, -5), `视图坐标 (${vx}, ${vy}, ${vz})`);
  console.log("[3/4] lookAt OK:", `(${vx.toFixed(2)}, ${vy.toFixed(2)}, ${vz.toFixed(2)})`);

  // ---------- 测试 4：完整 MVP——原点经 V 和 P 后落在 NDC 中心 ----------
  const proj = perspective(Math.PI / 3, 16 / 9, 0.1, 100);
  const pv = multiply(proj, view);
  const [cx, cy, cz, cw] = transformPoint(pv, [0, 0, 0]);
  const ndcX = cx / cw;
  const ndcY = cy / cw;
  const ndcZ = cz / cw;
  assert.ok(nearly(ndcX, 0) && nearly(ndcY, 0), "视线中心应映射到 NDC (0,0)");
  assert.ok(ndcZ > -1 && ndcZ < 1, `ndcZ 应在 (-1,1)，实际 ${ndcZ}`);
  assert.ok(cw > 0, "相机前方的点 w 应为正（否则被裁剪）");
  console.log("[4/4] MVP 管线 OK, NDC:", `(${ndcX.toFixed(3)}, ${ndcY.toFixed(3)}, ${ndcZ.toFixed(3)})`);

  console.log("\n✅ 109-03 最小矩阵库 MVP 全部断言通过");
}

runAssertions();

运行方式：npx tsx examples/109-03-mat4-mvp.ts

  • near/far 别乱给：near 给 0.001 会把深度缓冲精度吃光（z-fighting，共面闪烁）。卡牌桌面场景 near=0.1 / far=100 足够；原则是让 near/far 比值尽量小。
  • Three.js 里这些都不用写：new THREE.PerspectiveCamera + camera.lookAt 就是 V 和 P，mesh.position/rotation 组合成 M。但懂原理才能排查「为什么我的模型在相机背后/为什么是扁的」。

109.5 场景管理与 FairyGUI ​

概念解析 ​

游戏由场景流转构成：启动页 → 大厅 → 对局 → 结算 → 大厅。场景栈是比「场景切换」更贴切的模型——弹窗、结算页都是压在上面的临时场景，关掉后下层场景 resume 继续。

生命周期四条铁律：

  1. pause/resume 必须成对：压栈暂停音乐/动画/网络心跳，回栈恢复——漏了 resume 就是「回大厅后背景音乐没了」这类玄学 bug。
  2. enter/exit 必须成对：exit 里必须释放该场景独有资源（纹理、监听、定时器），不然场景多切几轮内存就爬坡。
  3. 每帧只驱动栈顶：下层场景不 update（但可被渲染，比如半透明结算页下的牌桌）。
  4. replace 用于同层替换：对局结束 → 结算用 replace（对局销毁），而不是 push（对局还留在栈里占内存）。

FairyGUI 是游戏 UI 的专业工作流：设计师在 FairyGUI 编辑器里拼 UI（血条/背包/弹窗），导出二进制包，Cocos/Laya 里代码绑定组件。它解决的核心矛盾是游戏 UI 不适合 DOM/CSS——血量条的九宫格拉伸、按钮的按下态帧动画、虚拟列表背包，用 DOM 做又慢又别扭。接入模式：游戏逻辑 → 事件总线 → UI 层监听刷新，UI 层永不反向调用逻辑（单向数据流，和 React 同理）。

完整代码示例 ​

ts
// 文件: examples/109-04-scene-stack.ts
// 场景管理栈：大厅 → 对局 → 结算 的 push/pop/replace 与生命周期编排
// 目标：生命周期调用顺序严格可断言——pause/resume 成对、enter/exit 成对

import assert from "node:assert";

interface Scene {
  readonly name: string;
  onEnter(): void; // 成为栈顶时调用
  onExit(): void; // 离开栈时调用（销毁）
  onPause(): void; // 被新场景压栈时调用（未销毁，音乐/动画暂停）
  onResume(): void; // 上方场景弹出、重新可见时调用
}

class SceneManager {
  private stack: Scene[] = [];
  readonly log: string[] = []; // 生命周期轨迹，测试断言用

  private track(scene: Scene, hook: keyof Scene): void {
    if (hook === "name") return;
    this.log.push(`${scene.name}.${hook}`);
  }

  get top(): Scene | null {
    return this.stack[this.stack.length - 1] ?? null;
  }
  get depth(): number {
    return this.stack.length;
  }

  push(scene: Scene): void {
    const top = this.top;
    if (top) {
      top.onPause();
      this.track(top, "onPause");
    }
    this.stack.push(scene);
    scene.onEnter();
    this.track(scene, "onEnter");
  }

  pop(): Scene {
    const top = this.stack.pop();
    assert.ok(top, "栈空时禁止 pop");
    top.onExit();
    this.track(top, "onExit");
    const newTop = this.top;
    if (newTop) {
      newTop.onResume();
      this.track(newTop, "onResume");
    }
    return top;
  }

  /** 替换栈顶：旧场景销毁、新场景进场，下层不动 */
  replace(scene: Scene): void {
    const top = this.stack.pop();
    if (top) {
      top.onExit();
      this.track(top, "onExit");
    }
    this.stack.push(scene);
    scene.onEnter();
    this.track(scene, "onEnter");
  }

  /** 每帧只驱动栈顶场景 */
  update(dt: number, tick: (scene: Scene, dt: number) => void): void {
    if (this.top) tick(this.top, dt);
  }
}

/** 测试用场景：生命周期只打日志 */
function makeScene(name: string): Scene {
  return {
    name,
    onEnter() {},
    onExit() {},
    onPause() {},
    onResume() {},
  };
}

function runAssertions() {
  // ---------- 测试 1：push 三层——pause/enter 交错顺序 ----------
  const mgr = new SceneManager();
  const lobby = makeScene("lobby");
  const battle = makeScene("battle");
  const result = makeScene("result");
  mgr.push(lobby);
  mgr.push(battle);
  mgr.push(result);
  assert.deepEqual(mgr.log, [
    "lobby.onEnter",
    "lobby.onPause",
    "battle.onEnter",
    "battle.onPause",
    "result.onEnter",
  ]);
  console.log("[1/4] push 顺序 OK:", mgr.log.join(" → "));

  // ---------- 测试 2：pop 回大厅——exit/resume 成对 ----------
  mgr.pop(); // result 出栈
  mgr.pop(); // battle 出栈
  assert.deepEqual(mgr.log.slice(-4), [
    "result.onExit",
    "battle.onResume",
    "battle.onExit",
    "lobby.onResume",
  ]);
  assert.equal(mgr.depth, 1);
  assert.equal(mgr.top?.name, "lobby");
  console.log("[2/4] pop 回退 OK, 深度:", mgr.depth);

  // ---------- 测试 3：replace——下层不 pause ----------
  mgr.push(battle); // lobby.pause, battle.enter
  const logBefore = mgr.log.length;
  mgr.replace(result); // battle.exit, result.enter（lobby 不动）
  assert.deepEqual(mgr.log.slice(logBefore), ["battle.onExit", "result.onEnter"]);
  assert.equal(mgr.depth, 2, "replace 深度不变");
  console.log("[3/4] replace OK, 深度:", mgr.depth);

  // ---------- 测试 4：守卫与栈顶驱动 ----------
  mgr.pop();
  mgr.pop();
  assert.equal(mgr.depth, 0);
  assert.throws(() => mgr.pop(), /禁止 pop/, "空栈 pop 应抛错");
  let ticked = "";
  mgr.update(0.016, (s) => (ticked = s.name));
  assert.equal(ticked, "", "空栈不驱动任何场景");
  mgr.push(lobby);
  mgr.push(battle);
  mgr.update(0.016, (s) => (ticked = s.name));
  assert.equal(ticked, "battle", "每帧只驱动栈顶");
  console.log("[4/4] 守卫与栈顶驱动 OK");

  console.log("\n✅ 109-04 场景管理栈 全部断言通过");
}

runAssertions();

应用实践 ​

  • UI 层独立更新：UI 刷新走事件总线（HP 变化、手牌变化发事件），不挂在游戏主循环里每帧刷 DOM/组件——帧率敏感场景，脏标记驱动刷新。
  • 结算页用半透明 push：让玩家看到牌桌背景，体验上「没离开对局」；但下层必须 pause，防止牌桌动画还在跑浪费帧预算。

109.6 游戏性能优化：DrawCall、纹理与降级 ​

核心指标 ​

DrawCall 合批四板斧 ​

  1. 图集：同图集精灵连续绘制不切换纹理（108 册已讲）。
  2. 静态合批：不动的物体合并成一个网格，一次 draw。
  3. 实例化渲染（InstancedMesh）：同模型不同位置的物体（棋子、树木）一次 draw 全画。
  4. 分层渲染顺序：按材质/纹理排序绘制列表，把状态切换压到最少。

纹理与 LOD ​

  • 纹理压缩格式：ASTC（现代移动首选）/ ETC2（安卓保底）/ PVRTC（老 iOS），体积是 RGBA 的 1/4~1/8，显存同理。
  • Mipmap：远处物体自动用缩小的纹理，既省带宽又防闪烁——必开，代价只是 33% 显存。
  • LOD（细节层级）：远处用低模低贴图，近处用高模。卡牌游戏 LOD 简单：牌桌上的牌全精度，牌堆里的牌用低精度剪影。

中档dpr<3 或 4 年内中端关实时阴影、粒子减半
低档帧率实测 < 40 持续 3 秒锁 30fps + 关粒子 + 静态背景

实测降级优于 UA 嗅探：跑 3 秒测实际帧率，比解析 UA 猜性能可靠得多——同一型号手机，发热降频后性能腰斩。

109.7 自测题 ​

1. 为什么 sort(() => Math.random() - 0.5) 洗牌有偏？Fisher-Yates 为什么无偏？【基础】

sort 洗牌的比较器不稳定：同一个 (a,b) 对在不同时刻的比较结果不一致，排序结果依赖数组原顺序，52! 种排列不等概率。

Fisher-Yates 从后往前遍历，位置 i 与 [0, i] 内均匀随机选出的 j 交换：第 i 位等概率得到剩余牌中的任意一张，n! 种排列每种概率恰为 1/n!，数学上可证明无偏。关键细节是 j 取自 [0, i] 而非 [0, n)——后者产生 n^n 种路径映射到 n! 种排列，除不尽必有偏。

2. 卡牌翻转为什么要在 90° 时切换纹理？为什么动画中要禁止反向触发？【基础】

90° 换纹理：卡牌转到 90° 时侧面正对相机，视觉宽度为 0——此刻换贴图人眼完全察觉不到。提前换会看到背面图案突然消失；延后换会看到背面图案被镜像反转。

禁止反向：如果动画进行中接受新指令并从头反向，玩家连点会让卡牌在半途反复抽搐（鬼畜）。状态机迁移表显式拒绝非法迁移（flippingUp 中 flip 返回 false），动画播完才允许反向。需要「可打断」的场景（如悬停预览）应作为可配置策略，不是默认行为。

3. 解释 MVP 管线三个矩阵各自的职责，以及为什么透视除法不在矩阵里？【进阶】
  • M（Model）：平移/旋转/缩放，把模型从模型空间摆进世界空间（每张卡牌的位置和翻转角度）。
  • V（View）：lookAt 构造，把世界搬到相机坐标系下，相机永远位于原点看向 -z。
  • P（Projection）：perspective 把视锥体压成标准立方体，矩阵里 m[11]=-1 的作用是把 -z 攒进 w 分量。

透视除法（xyz/w）由 GPU 硬件在裁剪阶段统一执行，「近大远小」真正发生在这里。矩阵只负责准备 w；w≤0 的点在相机背后，直接被裁剪掉，根本不进光栅化。

4. 场景栈中 push / pop / replace 的生命周期顺序分别是什么？「回大厅后背景音乐没了」最可能是什么 bug？【进阶】
  • push(A→B)：A.pause → B.enter（A 未销毁，停音乐/动画）。
  • pop(B→A)：B.exit → A.resume（B 销毁，A 恢复）。
  • replace(A→B)：A.exit → B.enter（同层替换，A 销毁，下层不 pause）。

「回大厅后音乐没了」是典型 pause/resume 不成对：压栈时 onPause 停了背景音乐，但 onResume 里忘了恢复（或根本没实现 resume）。生命周期成对性是场景栈的第一纪律：exit 释放资源、resume 恢复运行态，漏一个就是玄学 bug。

5. 3D 卡牌项目要在低端机保住流畅，按什么顺序做优化？【进阶】

按「收益/成本比」排序：

  1. DrawCall 合批：同图集连续绘制 + 静态牌桌合并网格 + 同类物体实例化——DrawCall 压到 100 以下，收益最大。
  2. 纹理瘦身：ASTC/ETC2 压缩（显存 1/4~1/8）+ Mipmap 必开 + 图集合并。
  3. 对象池：伤害数字/粒子/出牌特效池化（108 册），消灭 GC 抖动。
  4. 实测降级：跑 3 秒测帧率，<40fps 持续即降档（锁 30fps、关阴影、粒子减半）——实测优于 UA 嗅探，发热降频后同型号性能腰斩。
6. 设计一个线上真人对战的卡牌对战：从洗牌到结算，前端与服务端各自的职责边界在哪？【挑战】

服务端（权威方）：

  • 洗牌并生成种子（CSPRNG），牌序永不完整下发——每个客户端只收到自己的手牌
  • 全部规则判定（出牌合法性、伤害结算、胜负），客户端的一切输入都只是「请求」
  • 抽卡概率与保底计数器，概率配置化
  • 保存「种子 + 操作序列」用于回放与作弊审计

客户端：

  • 用种子 + 同一 PRNG 本地复现牌序动画（只用于表现，不用于判定）
  • 发牌动画调度（DealScheduler）、翻牌状态机、拖拽出牌的预测性表现
  • 预测与服务端裁定冲突时，以服务端快照为准回滚表现层
  • 断线重连：向服务端拉取当前牌局快照 + 种子，重建表现层状态

边界原则：一切影响结果的数据以服务端为准；客户端只做表现与预测。回放 = 种子 + 操作序列，断线重连 = 快照 + 增量。前端永远不该出现「本地算出对手手牌」的代码路径。
