第一百三十部分 · 数据请求与缓存——从 axios/ky 到 TanStack Query / SWR ​

本册讲「服务端状态」这一层：请求怎么发、错误怎么归一、缓存键怎么设计、失效怎么做、乐观更新怎么回滚。服务端状态与客户端状态的分界见 05.5 服务端状态管理；列表查询与 URL 同步见 19.3 列表查询状态与 URL 同步；离线队列与 IndexedDB 持久化见 19.9 IndexedDB 结构化仓储 与 56 离线缓存与同步；响应体的运行时校验可对照 33 Zod。

技术基线（2025-11）：axios 1.x、ky 1.x、@tanstack/react-query 5.x、swr 2.x。v5 相对 v4 有破坏性重命名（cacheTime → gcTime、keepPreviousData → placeholderData: keepPreviousData 等），正文按 v5 写，跨版本处均标注。

四个配套示例全部纯 TS、零网络，node:assert 硬断言，可 npx tsx 实跑；React 片段标注「项目内运行」。

130.1 心智模型：服务端状态不是「全局变量」 ​

把接口数据塞进 Redux/Pinia 当全局状态，通常会演变成：手动 loading/error、手动失效、手动去重、手动重试、切页回来数据过期。根因是把服务端状态当成了客户端状态。

维度客户端状态服务端状态
数据源用户交互产生远端数据库，可能被他人修改
新鲜度本地即真相本地只是某个时刻的快照
生命周期应用存活期需要过期、重验证、垃圾回收
典型弹窗开关、表单草稿、主题用户信息、列表、详情、统计

服务端状态有五个必备维度：

data（数据） / error（错误） / isPending（首次加载） / isFetching（任意请求中） / isStale（是否过期）

isPending 与 isFetching 必须分开：首次加载显示骨架屏，后台刷新只显示右上角小转圈；否则每次聚焦窗口整页闪一下。

staleTime 与 gcTime ​

配置含义典型值
staleTime数据多久内视为「新鲜」，新鲜期不发请求列表 30s、字典 5min、用户信息 1min
gcTime（v4 叫 cacheTime）没有组件订阅后，缓存保留多久5~10min
refetchOnWindowFocus窗口聚焦是否重验证后台系统 true，编辑器 false
refetchOnReconnect网络恢复是否重验证通常 true

关键直觉：staleTime 决定「要不要再请求」，gcTime 决定「没人用了还留多久」。staleTime 大于 gcTime 没有意义；把 staleTime 设成 Infinity 等于放弃新鲜度，只适合静态字典。

130.2 请求层：axios、ky 与 fetch 的分工 ​

不管上层用哪个缓存库，底层请求层都要解决四件事：错误归一、取消、超时、重试。

axios 1.x：拦截器与错误归一 ​

ts
// [项目内运行] npm i axios@1
import axios, { AxiosError } from 'axios';

export class HttpError extends Error {
  constructor(
    message: string,
    readonly status: number,
    readonly code: string,
    readonly detail?: unknown,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE ?? '/api',
  timeout: 10_000,
  headers: { 'Content-Type': 'application/json' },
  withCredentials: true,
});

// 请求拦截：统一注入 token、追踪 id
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  config.headers['X-Request-Id'] = crypto.randomUUID();
  return config;
});

// 响应拦截：把各种失败统一成 HttpError；只做「翻译」，不做「吞错」
api.interceptors.response.use(
  (response) => response,
  (error: AxiosError<{ message?: string; code?: string }>) => {
    if (axios.isCancel(error)) {
      // 取消不是业务错误，保持可识别
      return Promise.reject(new HttpError('请求已取消', 0, 'CANCELLED'));
    }
    if (error.code === 'ECONNABORTED') {
      return Promise.reject(new HttpError('请求超时', 0, 'TIMEOUT'));
    }
    const status = error.response?.status ?? 0;
    const message = error.response?.data?.message ?? error.message ?? '网络错误';
    const code = error.response?.data?.code ?? error.code ?? 'NETWORK_ERROR';
    return Promise.reject(new HttpError(message, status, code, error.response?.data));
  },
);

// 取消：AbortController 是标准，axios 的 CancelToken 已废弃
const controller = new AbortController();
api.get('/users', { params: { page: 1 }, signal: controller.signal });
controller.abort();

要点：

  • 不要在每个调用处 try/catch 后 toast 再 return null：错误被吞掉后，上层无法区分「空数据」与「失败」；
  • 401 刷新 token 要只刷新一次并排队重放，否则并发 401 会触发 N 次刷新；
  • 拦截器里不要做重试，重试交给上层（避免「拦截器重试 × 缓存库重试」指数放大）；
  • params 里 undefined 会被省略，null 会变成字符串，分页参数要显式归一。

ky 1.x：更轻的 fetch 封装 ​

ts
// [项目内运行] npm i ky@1
import ky, { HTTPError } from 'ky';

export const client = ky.create({
  prefixUrl: '/api',           // ⚠️ prefixUrl 不能以 / 开头（除了根路径）
  timeout: 10_000,
  retry: {
    limit: 2,
    methods: ['get', 'head'],
    statusCodes: [408, 413, 429, 500, 502, 503, 504],
    backoffLimit: 2_000,
  },
  hooks: {
    beforeRequest: [
      (request) => {
        const token = localStorage.getItem('token');
        if (token) request.headers.set('Authorization', `Bearer ${token}`);
      },
    ],
    afterResponse: [
      async (request, options, response) => {
        if (response.status === 401) {
          const token = await refreshTokenOnce();
          request.headers.set('Authorization', `Bearer ${token}`);
          return ky(request, options); // 重放一次
        }
      },
    ],
    beforeRetry: [
      ({ request, error, retryCount }) => {
        console.warn(`retry ${retryCount}`, request.url, error.message);
      },
    ],
  },
});

const users = await client.get('users', {
  searchParams: { page: 1, status: 'open' }, // 自动编码
  signal: controller.signal,
}).json<User[]>();

// 局部覆盖
const slow = client.extend({ timeout: 60_000, retry: 0 });

ky 的默认行为：非 2xx 抛 HTTPError；retry 默认只对幂等方法重试；prefixUrl 与相对路径拼接时不能写 /users（会抛错），应写 users。

fetch 本身 ​

原生 fetch 不会因 4xx/5xx reject，需要手动 if (!res.ok) throw；也没有超时，必须用 AbortSignal.timeout(ms)（现代浏览器/Node 18+）。简单项目可以封装 30 行，但重试、去重、缓存仍建议交给上层库。

130.3 缓存键：键设计错了，后面全是补丁 ​

缓存键就是查询的依赖数组。设计原则：

  1. 稳定：对象属性顺序不能影响键；用稳定序列化或库自带的深比较；
  2. 可枚举：所有资源从 ['todos'] 派生，方便前缀失效；
  3. 粒度合适：列表与详情分开；分页/筛选/排序都要进键；
  4. 不含非序列化值：函数、DOM、类实例不能进键；
  5. 类型一致：page: 1 与 page: '1' 是不同键。
ts
// 文件: examples/130-01-query-key.ts（节选）
export const queryKeys = {
  all: ['todos'] as const,
  lists: () => [...queryKeys.all, 'list'] as const,
  list: (filters: { status?: string; page: number }) => [...queryKeys.lists(), filters] as const,
  detail: (id: string) => [...queryKeys.all, 'detail', id] as const,
};

export function matchesPrefix(key: readonly unknown[], prefix: readonly unknown[]): boolean {
  if (prefix.length > key.length) return false;
  return prefix.every((part, i) => stableSerialize(part) === stableSerialize(key[i]));
}

运行方式：npx tsx examples/130-01-query-key.ts（实跑；断言覆盖对象键排序、类型敏感、key factory、前缀失效、数组保序）

失效策略：

操作失效范围写法
新增/删除 todo所有 todos 派生键invalidateQueries({ queryKey: ['todos'] })
修改某条详情 + 列表两个 key 分别失效，或只失效 ['todos'] 前缀
切换用户清空全部queryClient.clear()
退出登录移除敏感缓存queryClient.removeQueries()

⚠️ 常见错误：invalidateQueries({ queryKey: ['todos', 'list'] }) 只失效列表，详情仍是旧值；用户改完标题返回列表看到新值，进详情又变回旧值。写操作影响哪些读，就在设计键时想清楚。

130.4 TanStack Query v5：服务端状态的事实标准 ​

查询 ​

tsx
// [项目内运行] npm i @tanstack/react-query@5
import { useQuery, keepPreviousData } from '@tanstack/react-query';

function TodoList({ page, status }: { page: number; status?: string }) {
  const { data, error, isPending, isFetching, isPlaceholderData } = useQuery({
    queryKey: ['todos', 'list', { page, status }],
    queryFn: ({ signal }) => fetchTodos({ page, status }, signal),
    staleTime: 30_000,
    gcTime: 5 * 60_000,
    placeholderData: keepPreviousData, // 翻页时保留上一页，避免闪白
    retry: (failureCount, error) => {
      if (error instanceof HttpError && error.status >= 400 && error.status < 500) return false;
      return failureCount < 2;
    },
    select: (res) => res.items, // 只在渲染层裁剪，缓存仍存完整响应
  });

  if (isPending) return <Skeleton />;         // 首次加载
  if (error) return <ErrorView error={error} />;
  return (
    <div>
      {isFetching && <Spinner />}             {/* 后台刷新 */}
      <ul style={{ opacity: isPlaceholderData ? 0.6 : 1 }}>
        {data.map((t) => <li key={t.id}>{t.title}</li>)}
      </ul>
    </div>
  );
}

v5 关键变化：

  • isLoading → isPending（首次无数据）；isFetching 表示任意请求中；
  • cacheTime → gcTime；
  • keepPreviousData: true → placeholderData: keepPreviousData（从 @tanstack/react-query 导入函数）；
  • useQuery 的 onSuccess/onError/onSettled 被移除，副作用放到 useEffect 或 mutation；
  • queryFn 接收 { signal }，请求库必须把 signal 透传，否则组件卸载后请求仍在跑。

变更 + 乐观更新 ​

tsx
// [项目内运行] 切换 todo 完成状态
const queryClient = useQueryClient();

const toggle = useMutation({
  mutationFn: ({ id, done }: { id: string; done: boolean }) =>
    api.patch(`todos/${id}`, { done }).then((r) => r.data),

  onMutate: async ({ id, done }) => {
    await queryClient.cancelQueries({ queryKey: ['todos'] }); // 1) 取消在途查询
    const previous = queryClient.getQueryData<Todo[]>(['todos', 'list']); // 2) 快照
    queryClient.setQueryData<Todo[]>(['todos', 'list'], (old) =>
      old?.map((t) => (t.id === id ? { ...t, done } : t)),
    ); // 3) 乐观改
    return { previous };
  },

  onError: (_err, _vars, ctx) => {
    // 4) 失败回滚到快照
    if (ctx?.previous) queryClient.setQueryData(['todos', 'list'], ctx.previous);
  },

  onSettled: () => {
    // 5) 无论成败都重拉，保证最终一致
    queryClient.invalidateQueries({ queryKey: ['todos'] });
  },
});

onMutate 返回的 ctx 会传给 onError/onSettled。回滚必须用快照，不要在 onError 里「反向再改一次」——并发两次变更时反向操作会算错。

130.5 SWR 2.x：更轻的 stale-while-revalidate ​

SWR 的心智模型更简单：useSWR(key, fetcher, options)，key 为 null 时不请求。

tsx
// [项目内运行] npm i swr@2
import useSWR, { useSWRConfig } from 'swr';

function Profile({ id }: { id: string }) {
  const { data, error, isLoading, isValidating, mutate } = useSWR(
    ['/api/user', id],                       // 数组 key 会自动序列化
    ([url, userId]) => fetch(`${url}/${userId}`).then((r) => r.json()),
    {
      revalidateOnFocus: false,
      revalidateOnReconnect: true,
      dedupingInterval: 2_000,               // 2s 内相同 key 只请求一次
      keepPreviousData: true,                // 切 id 时保留旧数据
      refreshInterval: 0,
    },
  );

  if (isLoading) return <Skeleton />;
  if (error) return <ErrorView error={error} />;
  return <div>{data.name}</div>;
}

130.6 竞态、去重、取消：库替你做了什么 ​

去重（dedupe） ​

同一 key 在极短时间内被多个组件请求，缓存库只发一次。SWR 的 dedupingInterval、TanStack Query 的默认去重都是这个机制。自研时用一个 Map<key, Promise>：

ts
// 文件: examples/130-02-request-dedupe.ts（节选）
run<T>(key: string, fetcher: Fetcher<T>): Promise<T> {
  const existing = this.map.get(key);
  if (existing) { existing.refs++; return existing.promise as Promise<T>; }
  const controller = new AbortController();
  const promise = fetcher(controller.signal).finally(() => {
    if (this.map.get(key)?.promise === promise) this.map.delete(key);
  });
  this.map.set(key, { promise, controller, refs: 1 });
  return promise;
}

运行方式：npx tsx examples/130-02-request-dedupe.ts（实跑；断言覆盖共享 Promise、完成后清理、主动取消、竞态守卫、超时、可重试/不可重试错误）

三个容易漏的点：

  1. 清理时校验身份：旧请求结束时不能删掉新请求的条目；
  2. 取消要传播：组件卸载、搜索词变化时 controller.abort()，否则响应回来仍会写缓存；
  3. 竞态守卫：快速切换 tab 时，旧请求可能后返回；只接受最新 token 的结果（或依赖 queryKey 天然隔离）。

取消的边界 ​

  • AbortController 取消的是网络请求，不是「业务逻辑」；已经进入 then 的回调仍可能执行，需要 signal.aborted 再判断；
  • axios 用 signal，CancelToken 已废弃；ky 原生支持 signal；fetch 也支持；
  • TanStack Query 会把 signal 传给 queryFn，但你的 queryFn 必须把它透传给请求库，否则等于没取消。

重试的边界 ​

  • 只重试幂等请求（GET/HEAD/PUT/DELETE），POST 默认不重试；
  • 只重试可恢复错误：网络错误、408、429、5xx；4xx（除 429）不重试；
  • 指数退避 + 抖动，避免雪崩；
  • 不要多层重试：axios 拦截器、ky retry、Query retry 同时开，最坏会放大成 27 次。

130.7 分页、预取与水合 ​

分页三种模型 ​

模型键适合注意
页码分页['list', { page, size }]后台表格翻页保留上一页用 placeholderData
游标分页['feed', { cursor }]信息流游标必须进键；getNextPageParam 返回 undefined 表示结束
无限滚动useInfiniteQuery移动端列表记得 flatMap，并处理重复项

预取 ​

  • 悬停/聚焦时 prefetchQuery，staleTime 与正式查询一致；
  • 路由 loader 里预取（React Router / TanStack Router），避免瀑布流；
  • 预取要限量：列表悬停 100 行不要预取 100 个详情，防抖 + 只取当前行。

SSR 水合 ​

Next.js/Remix 里，服务端预取后把 dehydrate(queryClient) 传给客户端 HydrationBoundary；关键是服务端与客户端的 queryKey 必须完全一致，否则水合不命中，首屏又请求一次。SWR 用 fallback 提供初始数据。

130.8 性能、包体与可观测性 ​

  • select 裁剪：缓存存完整响应，组件只订阅需要的字段，减少重渲染；
  • 结构共享：TanStack Query 默认开启，数据未变时引用不变，配合 React.memo 有效；
  • 避免在 queryFn 里做重计算：把派生数据放 select 或 useMemo；
  • DevTools 只在开发环境引入：@tanstack/react-query-devtools 动态 import；
  • 包体：axios ~13KB gzip、ky ~4KB、TanStack Query core ~12KB、SWR ~4KB；小项目别为了「统一」引入两套；
  • 可观测：给请求加 X-Request-Id，错误上报带 queryKey、status、耗时；缓存命中率与 4xx/5xx 比例是排障第一指标；
  • 内存：gcTime 过长 + 大量不同 key（如每次搜索词都进 key）会导致缓存膨胀；搜索建议类查询用较短 gcTime 或 removeQueries。

130.9 自测题 ​

1. 为什么服务端数据不适合直接放进 Redux/Pinia？【基础】

服务端数据是「某个时刻的快照」，会过期、会被他人修改，需要重验证、去重、取消、GC；客户端状态是本地真相，不需要这些。把服务端状态当全局变量会导致手动管理 loading/error/失效，最终到处补丁。应由 TanStack Query/SWR 管理。

2. `isPending` 与 `isFetching` 的区别？【基础】

isPending 表示首次加载且还没有数据，适合骨架屏；isFetching 表示任意请求进行中（包括后台刷新），适合右上角小转圈。混用会让每次聚焦窗口整页闪。

3. `staleTime` 与 `gcTime` 各决定什么？【基础】

staleTime 决定数据多久内视为新鲜、不触发重新请求；gcTime 决定没有组件订阅后缓存保留多久。staleTime 大于 gcTime 没有意义；staleTime=Infinity 等于放弃新鲜度。

4. 缓存键为什么必须稳定且可枚举？【进阶】

键不稳定（对象属性顺序、类型不一致）会导致永远不命中、缓存膨胀；键不可枚举（散落字符串）会导致失效时漏掉派生查询，出现「列表新、详情旧」。应使用 key factory + 前缀失效。

5. 乐观更新为什么必须用快照回滚，而不是反向操作？【进阶】

并发两次变更时，反向操作会基于已变化的状态计算，结果错误；快照是变更前的确定状态，回滚无歧义。TanStack Query 的 onMutate 返回 context 就是为此设计。

6. 取消请求后，为什么回调还可能执行？【进阶】

AbortController 取消的是网络层；如果响应已经到达并进入微任务队列，then 仍可能执行。需要在回调里检查 signal.aborted，或依赖缓存库的 key 隔离丢弃旧结果。

7. 多层重试为什么会放大请求量？如何治理？【挑战】

axios 拦截器、ky retry、Query retry 各重试 2 次，最坏是 3×3×3=27 次。治理原则：只在一层做重试（通常缓存库或请求库二选一），其余层关闭；只重试幂等方法与可恢复状态码，使用指数退避 + 抖动。

8. v5 的 `placeholderData: keepPreviousData` 解决什么问题？【挑战】

翻页/切筛选时，新 key 还没有数据，直接渲染会闪白。keepPreviousData 让上一页数据暂时占位，同时标记 isPlaceholderData，UI 可降低透明度；新数据到达后自动替换，不污染缓存。

9. SSR 水合为什么常常「首屏又请求一次」？【挑战】

服务端与客户端使用的 queryKey 不一致（如服务端用了完整对象、客户端用了简化参数），或序列化后类型变化（Date → string），导致水合不命中。必须保证两端 key 完全一致，并只 dehydrate 需要的查询。

10. 搜索建议这类高频查询，缓存该怎么配？【挑战】

每次输入都产生新 key，缓存会膨胀。应做 150~300ms 防抖、staleTime 短、gcTime 短（如 1 分钟）、限制保留条数（removeQueries 清理旧 key），并用 AbortController 取消上一次请求；不要把每次击键都写进持久化缓存。
