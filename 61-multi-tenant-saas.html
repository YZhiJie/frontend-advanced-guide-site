61.1 多租户模型与前端职责边界 ​

概念解析 ​

多租户的数据隔离是后端架构问题，但隔离级别直接决定前端要做什么。先认清自家产品在哪一级：

隔离级别后端形态前端感知前端核心工作
独立部署（每租户一套）独立域名 + 独立应用 + 独立库最大：每租户可能有独立版本/主题构建期租户变体、独立域名部署
共享应用 + 独立库一套应用，按租户路由数据库中等：登录后才知道数据归属租户上下文传递、连接路由标识
共享库 + 行级隔离所有表带 tenant_id最小但最危险：串数据只差一个漏传的请求请求注入零遗漏、缓存键隔离

三条认知纪律：

  1. 行级隔离级别下，前端是最后一道防串闸门：后端漏判 tenant_id 是事故，前端漏传 X-Tenant-Id 同样是事故——两者后果一样（A 租户看到 B 租户数据），但前端的漏传更难被发现，因为它只在「某条手写的特殊请求」里才暴露。
  2. 租户上下文是运行时单例，不是组件 props：租户在会话生命周期内不变（切租户 = 重新加载），应放在应用级上下文里由请求层统一读取，禁止层层透传或各模块自行解析 URL。
  3. "白标（white-label）"是多租户的极端形态：logo、主题、文案、域名、登录页全可定制。这一需求必须在配置模型设计期就考虑（见 61.3 的三层合并），事后补会收获一堆 if (tenant === 'xxx') 私货。

典型应用场景 ​

  • SaaS CRM / ERP / OA：标准行级隔离，子域名识别（acme.crm.com）；
  • 平台型产品（有赞/Shopify 类）：商家是租户，C 端用户访问的是「租户页面」，租户识别来自路径或域名绑定；
  • 政企交付：独立部署 + 白标，同一套代码出多个租户变体包。

最佳实践 ​

  • ✅ 立项时把隔离级别写进架构文档——它决定前端缓存、路由、构建的全部设计；
  • ✅ 租户上下文只允许一个来源（61.2 的解析器），全应用统一从该处读；
  • ❌ 不要在前端用 tenantId 做权限判断——租户隔离是数据边界，权限是 RBAC/ABAC 的职责（见 35/37 册），两者正交。

61.2 租户识别与上下文注入 ​

概念解析 ​

租户识别的四种来源，必须有明确优先级，否则多来源不一致时行为不可预期：

来源示例优点风险
子域名acme.saas-app.com最直观，Cookie 可按子域隔离需泛域名证书与 DNS；保留子域（www/api）要排除
路径前缀/t/acme/orders部署简单，单域名与业务路由抢命名空间；深链分享带租户
请求 HeaderX-Tenant-Id: acmeAPI 层干净页面首跳（HTML 请求）带不了 Header，需配合前两种
Query 参数?tenant=acme分享链接兜底最易被篡改，只作兜底不作权威

优先级约定：子域名 > 路径 > Header > Query > 默认租户。关键规则：

  • 多来源同时存在且不一致时，取最高优先级来源，但应上报告警——不一致本身说明链接生成逻辑有 bug 或有人在试探越权；
  • 保留子域名（www、api、app、admin、cdn）必须显式排除，否则 app.saas-app.com 会被解析成租户 app；
  • 多级子域（a.b.saas-app.com）不识别为租户，防错判。

识别之后是注入：所有出站请求在统一拦截器里带 X-Tenant-Id。拦截器要做一件反直觉的事——拒绝调用方手动塞的租户头。业务代码自己塞头，说明有人绕过了统一上下文，这种「私货」是串租户事故的头号来源：要么放行时与上下文冲突，要么上下文切换后忘记更新。

完整代码示例 ​

typescript
// 文件: examples/61-01-tenant-context.ts（核心节选）
// 解析优先级：子域名 > 路径 > Header > Query > 默认租户
function resolveTenant(input: {
  host?: string; pathname?: string; headerTenant?: string; queryTenant?: string;
}): TenantCtx {
  // 1) 子域名（排除 www/api/app 等保留子域,多级子域不识别）
  // 2) 路径前缀 /t/:tenantId
  // 3) 显式 Header → 4) Query 兜底 → 5) default
}

// 请求注入：拦截器统一带头;调用方私塞不一致的头 → 直接抛错
function injectTenant(req: Req, ctx: TenantCtx): Req {
  const existing = req.headers["X-Tenant-Id"];
  if (existing && existing !== ctx.tenantId) {
    throw new Error(`租户冲突: 请求头=${existing} vs 上下文=${ctx.tenantId}`);
  }
  return { ...req, headers: { ...req.headers, "X-Tenant-Id": ctx.tenantId } };
}

运行方式：npx tsx examples/61-01-tenant-context.ts（解析优先级、保留子域排除、私货头拒绝、缓存键隔离，共 11 组硬断言）。

最佳实践 ​

  • ✅ 租户解析器在应用启动时执行一次并冻结，会话期内不变；切租户走完整重载（见 61.4）；
  • ✅ 解析不一致时上报监控（见 59 册），这是越权试探的早期信号；
  • ⚠️ Cookie 域名策略与子域名方案联动设计：想在租户间共享登录态用 .saas-app.com 域，想强制隔离用子域自有域；
  • ❌ 不要信任前端解析结果做服务端鉴权——服务端必须独立从 Token/Session 解析租户，前端头只是路由线索（36 册：前端一切输入可被伪造）。

61.3 租户级配置、主题与特性开关 ​

概念解析 ​

租户定制的本质是配置分层覆盖。三层模型是业界事实标准：

层维护者内容优先级
平台默认产品方全量配置的完整兜底最低
租户覆盖租户管理员品牌色、logo、功能开关、文案中
用户偏好终端用户分页大小、密度、个人主题最高

合并语义比结构更重要，三条纪律：

  1. undefined 与 null 必须区分：undefined = 这一层没配，保留下层值；null = 显式清除。混在一起会导致「想删掉租户的公告栏，结果下层平台的公告又冒出来」；
  2. 数组整体替换，不拼接：租户配了模块列表 ["crm"]，结果是只有 crm，而不是平台模块 + crm 的并集。拼接语义看起来「智能」，实际让租户无法关闭平台默认模块；
  3. 对象递归合并：theme.primary 被租户覆盖时，theme.radius 仍保留下层值——这是分层配置存在的意义。

特性开关（Feature Flag）在三层之上再加灰度维度：租户层开启某功能时可以带 rollout: 50（50% 用户可见），结合 43 册的稳定分桶哈希，同一用户每次判定结果一致。判定规则自顶向下找第一个显式配置：任一层显式 false 即最终关闭——禁用一个功能不需要每层都关，但开启需要显式授权。

主题下发的工程实现：Design Token → CSS Variables 是最佳载体（见 49 册）。租户配置接口返回 { primary: "#722ed1", radius: 8 }，前端映射为 document.documentElement.style.setProperty("--brand-primary", ...)，组件库全部消费 CSS Vars 即可热切换，不需要重新打包。白标的底线是构建期无租户分支——所有差异都走运行时配置，否则租户数量就是构建矩阵的乘数。

完整代码示例 ​

typescript
// 文件: examples/61-02-tenant-config.ts（核心节选）
// 深合并纪律：undefined 跳过 / null 显式清除 / 数组整体替换 / 对象递归
function deepMerge(base: Json, override: Json): Json {
  for (const [k, v] of Object.entries(override)) {
    if (v === undefined) continue;
    if (v === null) { delete out[k]; continue; }
    out[k] = isPlain(v) && isPlain(out[k]) ? deepMerge(out[k], v) : v;
  }
}

// 特性开关三级判定：用户 > 租户 > 平台;带灰度时看稳定分桶
function isFeatureOn(flag, layers, userIdHash): boolean {
  for (const layer of [layers.user, layers.tenant, layers.platform]) {
    if (layer.enabled === undefined) continue;
    if (layer.enabled === false) return false;
    if (layer.rollout !== undefined && userIdHash >= layer.rollout) return false;
    return true;
  }
  return false; // 未配置默认关,安全侧
}

运行方式：npx tsx examples/61-02-tenant-config.ts（合并语义、三层优先级、灰度分桶、显式关闭，共 8 组硬断言）。

最佳实践 ​

  • ✅ 配置接口加 ETag/版本号，租户改配置后客户端轮询到版本变化再拉取，避免每个请求都回源；
  • ✅ 首屏主题防闪（FOUC 的租户版）：主题 token 随 HTML 内联下发或进启动配置，不要等 JS 请求完才刷色；
  • ⚠️ 租户配置属敏感数据：B 租户的开关列表不应暴露给 A 租户，配置接口必须按当前租户裁剪；
  • ❌ 不要在代码里写 if (tenantId === "vip-tenant")——功能差异一律走配置，私货分支在白标场景会指数爆炸。

61.4 防串租户：缓存、状态与切换清理 ​

概念解析 ​

串租户事故的三个高发点，全部在前端有状态的地方：

状态位置事故形态防御
本地缓存（localStorage/IndexedDB）A 租户退出后 B 租户登录，读到 A 的缓存草稿/列表缓存键带租户命名空间 tenantId::biz::key
内存状态（Pinia/Redux）切租户后 store 残留旧租户数据切租户 = 完整重载页面，不重载就全量 reset
请求缓存（SWR/React Query）queryKey 不含租户，命中旧租户缓存queryKey 第一段恒为 tenantId
WebSocket/长连接切租户后旧连接还在推旧租户消息切换时显式断开重连，鉴权重做（39 册）

缓存键命名空间是最低成本的防线：acme::order-list::page1 与 beta::order-list::page1 天然不冲突。但命名空间防不住「同浏览器先后登录两个租户看到彼此的敏感缓存」——保密性要求高的场景，切租户/登出时应全量清空本地缓存，而不是依赖键隔离共存。

切租户的正确姿势是 location.reload() 级别的完整重建。试图「优雅地」在 SPA 内重置所有 store、断开所有连接、清空所有缓存，是对人性的考验——任何一个模块忘了注册清理钩子就是事故。完整重载用一次白屏换绝对干净，是业界标准做法（Notion、Slack 切 workspace 均为整页刷新）。

完整代码示例 ​

examples/61-01-tenant-context.ts 中的 TenantStorage 演示了命名空间键与全量清理两种策略的组合使用。

运行方式：npx tsx examples/61-01-tenant-context.ts

最佳实践 ​

  • ✅ 所有缓存层（本地、内存、请求）的键设计在第一版就带租户段，事后改造要迁移存量缓存；
  • ✅ 登出与切租户共用同一套清理管线：清缓存 → 断连接 → 清内存 → 跳转/重载；
  • ⚠️ Service Worker 缓存也按租户分 Cache 名（见 56 册），否则离线壳可能串版本；
  • ❌ 不要依赖「键隔离就够」——键隔离防的是数据错乱，防不了信息泄漏（B 租户用户能看到 A 租户残留的缓存内容）。

61.5 自测题 ​

1. 【基础】为什么租户识别必须定义来源优先级？多来源不一致时应该怎么处理？

子域名、路径、Header、Query 四种来源可能同时出现在一次访问中（例如子域名是 acme，分享链接里带着 ?tenant=beta）。没有优先级约定，不同模块各取一个来源就会在同一页面内出现两个租户上下文，这是串数据事故的直接原因。处理规则：取最高优先级来源生效，同时把不一致事件上报监控——不一致要么说明链接生成有 bug，要么说明有人在试探越权，两种情况都值得告警。

2. 【基础】请求拦截器为什么要"拒绝"调用方手动设置的租户头，而不是放行？

业务代码自己塞租户头，说明它绕过了统一租户上下文。这种私货有两个风险：一是与当前上下文不一致时形成静默越权（上下文是 A，私货带 B）；二是上下文切换后私货代码忘记更新，继续带旧租户。拦截器检测到不一致直接抛错，把"静默事故"变成"开发期报错"，是防御性设计。只有一条合法例外：显式签发的跨租户管理端 API，且应走独立请求实例而非通用拦截器。

3. 【基础】配置合并时 undefined 和 null 为什么必须区分语义？

undefined 表示"这一层没配置，继承下层值"，null 表示"显式清除该配置"。不区分的话：租户想清掉平台默认配置的公告栏（传 null），如果引擎把 null 当"没配"处理，平台公告又会穿透出来；反过来把 undefined 当清除处理，租户只改一个字段就会意外抹掉平台层的其他默认值。深合并引擎必须三态分明：undefined 跳过、null 删除、其余覆盖。

4. 【进阶】行级隔离级别下，前端缓存设计为什么必须带租户命名空间？只防了什么、防不了什么？

带命名空间（tenantId::biz::key）防的是"数据错乱"：A 租户和 B 租户的缓存互不覆盖，切租户后读到的列表是自己的。但它防不了"信息泄漏"：同一浏览器先登录 A 再登录 B，B 的用户仍能通过开发者工具翻到 A 的缓存内容。所以命名空间是底线，高保密场景必须叠加"切租户/登出时全量清空"。两者是互补关系，不是二选一。

5. 【进阶】为什么说"切租户 = location.reload() 完整重载"是业界标准，而不是 SPA 内优雅重置？

SPA 内重置要求：所有 store 注册清理钩子、所有 WebSocket 断开重连、所有请求缓存失效、所有定时器清理——任何一个模块漏注册就是串数据事故，而且这个清单随业务增长永远无法穷举。完整重载用一次白屏换"运行时绝对干净"，把不可枚举的清理问题变成浏览器的进程级保证。Notion、Slack 切 workspace 均采用整页刷新。工程上可以优化体验（骨架屏、预载新租户配置），但重置语义不应妥协。

6. 【进阶】白标（white-label）需求下，为什么不能接受构建期租户分支？正确做法是什么？

构建期分支（if tenant === 'x' 参与打包）意味着每加一个定制租户，构建矩阵乘一倍，且租户差异固化在产物里无法运营调整。正确做法是"构建期无租户、差异全走运行时配置"：品牌色/圆角走 Design Token → CSS Variables 热切换，功能差异走三层配置合并 + 特性开关，文案差异走 i18n 资源包（15 册）。构建产物对所有租户同一份，租户差异在启动时由配置接口下发。

7. 【挑战】设计一个 SaaS 产品的租户配置系统，要求：平台运营能改全局默认、租户管理员能覆盖、配置变更 1 分钟内全网生效，且首屏不闪租户色。给出关键设计点。

① 存储与下发：配置存平台库，接口按租户裁剪输出，带 ETag/版本号；② 生效时效：客户端每 60s 轮询版本号（或走 SSE/WS 推送变更事件），版本变化才拉全量；③ 防闪屏：首屏 HTML 内联当前租户的主题 token（服务端渲染或启动配置接口同步返回），JS 接管后消费 CSS Vars，不等异步请求；④ 合并语义：三层模型 + undefined/null 三态 + 数组整体替换；⑤ 灰度：租户层开关带 rollout 百分比，稳定分桶哈希判定；⑥ 审计：配置变更走 63 册审计链路（谁改的、改了什么、前后值 diff）。

8. 【挑战】多租户应用的 Service Worker 离线缓存（56 册）有哪些串租户风险？如何设计？

三个风险点：① 壳缓存——不同租户若构建产物不同（独立部署级），SW 预缓存清单必须按租户区分 Cache 名，否则 A 租户壳被 B 租户壳覆盖；② 数据缓存——IndexedDB 里的业务数据键必须带租户命名空间，且切租户时清空当前设备上不属于新租户的数据；③ 后台同步队列——离线写队列里的操作带的是旧租户上下文，重放时必须校验操作携带的 tenantId 与当前会话一致，不一致丢弃并告警（防切租户后旧操作写入新租户库）。设计原则：SW 层的租户意识与主线程同等严格，不能因为"在后台跑"就放松。
