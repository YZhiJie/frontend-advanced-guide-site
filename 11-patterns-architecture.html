11.1 前端常用设计模式 ​

概念解析 ​

前端真正高频使用的设计模式只有五六个，关键是认出"你天天在用而不知道名字"的那些：

观察者 vs 发布订阅：一张图分清 ​

两者最容易被混为一谈，区别在于是否有中间的事件中心：

mermaid
graph LR
    subgraph 观察者模式 - 耦合
        S[Subject 目标对象] -- 直接维护列表 --> O1[Observer A]
        S --> O2[Observer B]
    end
    subgraph 发布订阅模式 - 解耦
        P[发布者] -- 不知晓订阅者 --> E((事件中心 EventBus))
        E --> T1[订阅者 A]
        E --> T2[订阅者 B]
    end
  • 观察者：目标直接持有观察者列表并逐个通知（React 组件订阅 store 就是这种）；
  • 发布订阅：双方只认识事件中心，发布者与订阅者互不知晓（跨模块通信用这种）；
  • ⚠️ 面试高频：能说清"有没有中间人、双方是否感知彼此"就是合格答案。

// ---- 1. 单例:全局唯一的弹窗管理器(闭包 + 惰性创建)----
class ToastManager {
    private static instance: ToastManager | null = null;
    private container: HTMLElement | null = null;

    private constructor() {} // 禁止外部 new

    static getInstance(): ToastManager {
        if (!ToastManager.instance) {
            ToastManager.instance = new ToastManager();
        }
        return ToastManager.instance;
    }

    show(message: string) {
        // 惰性创建 DOM 容器
        this.container ??= document.createElement('div');
        const toast = document.createElement('div');
        toast.textContent = message;
        this.container.appendChild(toast);
        setTimeout(() => toast.remove(), 2000);
    }
}
// ToastManager.getInstance() === ToastManager.getInstance() // true

// ---- 2. 策略:消灭表单校验的 if 长链 ----
type ValidateFn = (value: string) => string | null; // 返回 null 表示通过

const validators: Record<string, ValidateFn> = {
    required: (v) => (v.trim() ? null : '必填项'),
    phone: (v) => (/^1[3-9]\d{9}$/.test(v) ? null : '手机号格式不正确'),
    password: (v) => (v.length >= 8 ? null : '密码至少 8 位'),

validators.email = (v) => (/^\S+@\S+\.\S+$/.test(v) ? null : '邮箱格式不正确');

function validateField(value: string, rules: ValidateFn[]): string | null {
    for (const rule of rules) {
        const error = rule(value);
        if (error) return error; // 返回第一个错误
    }
    return null;
}

console.log(validateField('13800138000', [validators.required, validators.phone])); // null
console.log(validateField('123', [validators.required, validators.password]));      // '密码至少 8 位'

// ---- 3. 代理:图片懒加载(IntersectionObserver + 缓存去重)----
function createLazyImageLoader(rootMargin = '200px') {
    const loaded = new WeakSet<HTMLImageElement>();
    const observer = new IntersectionObserver((entries, obs) => {
        entries.forEach((entry) => {
            if (!entry.isIntersecting) return;
            const img = entry.target as HTMLImageElement;
            if (loaded.has(img)) return;
            img.src = img.dataset.src ?? '';
            loaded.add(img);
            obs.unobserve(img); // 加载一次即停止观察
        });
    }, { rootMargin: `${rootMargin} 0px` }); // 提前 200px 预加载

    return (img: HTMLImageElement) => observer.observe(img);
}
// 所有 img[data-src] 交给它:const lazyLoad = createLazyImageLoader();

// ---- 4. 装饰器思想的高阶函数:给任意异步函数加缓存 + 去重 ----
function withCache<A extends unknown[], R>(
    fn: (...args: A) => Promise<R>,
    keyFn: (...args: A) => string = (...args) => JSON.stringify(args),
) {
    const cache = new Map<string, Promise<R>>();
    return (...args: A): Promise<R> => {
        const key = keyFn(...args);
        if (!cache.has(key)) {
            const promise = fn(...args).catch((e) => {
                cache.delete(key); // 失败不缓存,下次重试
                throw e;
            });
            cache.set(key, promise);
        }
        return cache.get(key)!; // 并发调用共享同一个 Promise(请求去重)
    };
}

let fetchCount = 0;
const fetchUserCached = withCache(async (id: string) => {
    fetchCount++;
    await new Promise((r) => setTimeout(r, 50));
    return { id, name: 'Alice' };
});

await Promise.all([fetchUserCached('1'), fetchUserCached('1')]); // 并发去重:实际只发一次
await fetchUserCached('1'); // 命中缓存
console.log('实际请求次数:', fetchCount); // 1
export {};

发布订阅 EventBus：类型安全的完整实现 ​

EventBus 是前端出镜率最高的模式，难点在 TypeScript 类型安全与 once/off 的清理语义：

typescript
// 文件: examples/11-04-eventbus.ts
// ============ 类型安全的 EventBus:on/once/off/emit 全语义 ============

type Handler<T = unknown> = (payload: T) => void;

class EventBus<Events extends Record<string, unknown>> {
    private map = new Map<keyof Events, Set<Handler>>();

    /** 订阅;返回取消函数(比手动存引用再 off 更不易泄漏) */
    on<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void {
        let set = this.map.get(event);
        if (!set) {
            set = new Set();
            this.map.set(event, set);
        }
        set.add(handler as Handler);
        return () => this.off(event, handler); // ✅ 返回解绑函数,组件卸载时直接调用
    }

    /** 一次性订阅:执行后自动移除 */
    once<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void {
        const wrap: Handler<Events[K]> = (payload) => {
            this.off(event, wrap); // 先移除再执行,防止 handler 内再次 emit 造成重入
            handler(payload);
        };
        return this.on(event, wrap);
    }

    off<K extends keyof Events>(event: K, handler: Handler<Events[K]>) {
        this.map.get(event)?.delete(handler as Handler);
    }

    emit<K extends keyof Events>(event: K, payload: Events[K]) {
        // 复制一份再遍历:防止 handler 内 on/off 修改集合导致遍历异常
        [...this.map.get(event) ?? []].forEach((h) => {
            try {
                h(payload);
            } catch (e) {
                // ✅ 单个订阅者出错不阻断其他订阅者(与 DOM 事件语义一致)
                console.error(`[EventBus] handler for "${String(event)}" failed:`, e);
            }
        });
    }
}

// ---- 使用:事件名与载荷类型强关联,emit 传错参数直接编译报错 ----
interface AppEvents {
    'user:login': { userId: string; from: 'email' | 'oauth' };
    'cart:changed': { count: number };
}

const bus = new EventBus<AppEvents>();

const offLogin = bus.on('user:login', (p) => console.log('欢迎', p.userId, '登录方式', p.from));
bus.once('cart:changed', (p) => console.log('首次加购,数量:', p.count));

bus.emit('user:login', { userId: 'u_1', from: 'oauth' }); // 欢迎登录
bus.emit('cart:changed', { count: 1 }); // 首次加购
bus.emit('cart:changed', { count: 2 }); // 已被 once 移除,无输出
offLogin(); // 组件卸载时解绑

// bus.emit('user:login', { userId: 'u_1', from: 'wechat' }); // ❌ 编译报错:from 类型不符

// ---- ⚠️ 坑:handler 引用必须一致才能 off —— 匿名函数解绑永远失败 ----
const h1 = (p: { count: number }) => console.log(p);
bus.on('cart:changed', h1);
bus.off('cart:changed', h1); // ✅ 同一引用,解绑成功
// bus.on('cart:changed', (p) => console.log(p)); bus.off(..., 同样字面量) // ❌ 不同引用
export {};

运行方式：npx tsx examples/11-04-eventbus.ts。

⚠️ EventBus 三大坑：

  1. 内存泄漏：常驻总线 + 页面级订阅，组件卸载忘记 off —— 订阅者闭包引用整个组件树，无法回收。✅ 统一用 on 返回的解绑函数，配合 useEffect cleanup / onUnmounted；
  2. 事件风暴：高频事件（scroll/input）直接上总线，每个 handler 同步串行执行 —— 先防抖/节流再 emit；
  3. 调试黑洞：事件链路过长后"谁发的、谁改的"无从查起 —— emit 处打日志或约定 payload 只读（Readonly<T>）。

命令模式：撤销与重做的标准解法 ​

把"一次操作"封装成 { do, undo } 对象，配合历史栈实现 undo/redo——编辑器、画板（Fabric.js 也有对应 API）、表格操作的通用架构：

typescript
// 文件: examples/11-05-command-undo.ts
// ============ 命令模式:画板/编辑器的撤销重做栈 ============

/** 命令抽象:do 与 undo 必须严格互逆 */
interface Command<T> {
    do(state: T): T;
    undo(state: T): T;
    label: string; // 便于调试与"撤销了 XX"提示
}

class History<T> {
    private past: Command<T>[] = [];
    private future: Command<T>[] = []; // redo 栈

    constructor(private state: T) {}

    /** 执行命令:清空 redo 栈(分叉后旧未来作废) */
    execute(cmd: Command<T>): T {
        this.state = cmd.do(this.state);
        this.past.push(cmd);
        this.future = []; // ⚠️ 忘记清空 redo 栈是 undo/redo 最常见的 bug
        return this.state;
    }

    undo(): T {
        const cmd = this.past.pop();
        if (!cmd) return this.state;
        this.state = cmd.undo(this.state);
        this.future.unshift(cmd);
        return this.state;
    }

    redo(): T {
        const cmd = this.future.shift();
        if (!cmd) return this.state;
        this.state = cmd.do(this.state);
        this.past.push(cmd);
        return this.state;
    }

    get current() { return this.state; }
}

// ---- 用不可变快照实现命令(比 diff 逆运算简单可靠,适合中小状态)----
type Doc = { lines: string[] };

const addLine = (text: string): Command<Doc> => ({
    label: `添加行:${text}`,
    do: (s) => ({ lines: [...s.lines, text] }),          // 不可变追加
    undo: (s) => ({ lines: s.lines.slice(0, -1) }),       // 逆操作:去掉最后一行
});

const history = new History<Doc>({ lines: [] });
history.execute(addLine('第一行'));
history.execute(addLine('第二行'));
console.log(history.current.lines);              // ['第一行', '第二行']
console.log(history.undo()!.lines);              // ['第一行']
console.log(history.undo()!.lines);              // []
console.log(history.redo()!.lines);              // ['第一行']

// ---- ⚠️ 大状态(如图像像素)快照太贵:改为记录"逆操作参数"(位置+旧值),即 diff 型命令 ----
// ⚠️ undo/redo 边界:undo 到头/redo 到头必须是无操作而非抛错;连续 undo 的 UI 按钮态用 canUndo 派生
export {};

运行方式：npx tsx examples/11-05-command-undo.ts。

状态模式：用状态机替代布尔标志位组合 ​

当逻辑出现 if (loading && !error && isLastPage) 这类标志位组合时，就该上有限状态机——状态互斥、转移显式、非法转移直接拒绝：

typescript
// 文件: examples/11-06-state-machine.ts
// ============ 状态模式:下拉加载的状态机(对比标志位写法) ============

// ❌ 反例:三个布尔值有 2^3 = 8 种组合,其中一半是非法态(loading && error 同时为 true?)
// let loading = false; let error = false; let hasMore = true;

// ✅ 正例:互斥状态 + 显式转移表
type LoadState =
    | { status: 'idle' }
    | { status: 'loading' }
    | { status: 'success'; hasMore: boolean }
    | { status: 'error'; retryable: true };

type LoadEvent =
    | { type: 'FETCH' }
    | { type: 'RESOLVE'; hasMore: boolean }
    | { type: 'REJECT' }
    | { type: 'RESET' };

function transition(state: LoadState, event: LoadEvent): LoadState {
    switch (event.type) {
        case 'FETCH':
            return state.status === 'loading' ? state : { status: 'loading' }; // loading 中忽略重复 FETCH(防重复请求)
        case 'RESOLVE':
            return state.status === 'loading' ? { status: 'success', hasMore: event.hasMore } : state;
        case 'REJECT':
            return state.status === 'loading' ? { status: 'error', retryable: true } : state;
        case 'RESET':
            return { status: 'idle' };
    }
}

let state: LoadState = { status: 'idle' };
const send = (e: LoadEvent) => { state = transition(state, e); console.log(state); };

send({ type: 'FETCH' });                    // { status: 'loading' }
send({ type: 'FETCH' });                    // 忽略:仍是 loading(天然防重复提交)
send({ type: 'RESOLVE', hasMore: true });   // { status: 'success', hasMore: true }
send({ type: 'FETCH' });
send({ type: 'REJECT' });                   // { status: 'error', retryable: true }
send({ type: 'FETCH' });                    // error 态允许重试

// ---- 视图层依据状态渲染,不再出现组合判断 ----
function render(s: LoadState) {
    switch (s.status) {
        case 'idle': return '点击加载';
        case 'loading': return '加载中...';
        case 'success': return s.hasMore ? '加载更多' : '没有更多了';
        case 'error': return '加载失败,点击重试';
    }
}
console.log(render(state));

// 生产中复杂交互流(播放器/审批流)推荐 XState:可视化转移图 + 完整 actor 模型,思路与本例一致
export {};

适配器模式：多渠道支付的统一封装 ​

业务依赖"稳定接口"，把各渠道的"多变实现"包成适配器——新增渠道不改业务代码：

// 文件: examples/11-07-adapter-pay.ts
// ============ 适配器:把三家支付 SDK 的异构 API 抹平成一个接口 ============

/** 业务侧依赖的稳定抽象(依赖倒置,见 11.4) */
interface PaymentGateway {
    pay(amountCents: number, orderId: string): Promise<{ transactionId: string }>;

        cb(null, `wx_${params.out_trade_no}`);

    pay(amountCents, orderId) {

从骨架到生产 SDK：批量队列、限流、指纹聚合 ​

上面的骨架"每错一次发一次请求"，生产上必须加三件事——批量合并、限流采样、错误指纹聚合。这是一个可直接抄进项目的精简版：

typescript
// 文件: examples/11-10-monitor-queue.ts —— [浏览器] 生产级上报队列
// ============ 核心:一个带兜底 flush 的批量上报队列 ============

interface MonitorItem {
    type: string;
    fingerprint?: string; // 聚合指纹
    payload: Record<string, unknown>;
    ts: number;
}

class MonitorQueue {
    private queue: MonitorItem[] = [];
    private sentCount = 0;               // 本周期已发送条数(限流用)
    private timer: ReturnType<typeof setInterval> | null = null;
    // 兜底 flush 必须存为成员:add/removeEventListener 传同一引用才能真正解绑
    private onHidden = () => {
        if (document.visibilityState === 'hidden') this.flush();
    };
    // 采样率:0.1 = 只上报 10% 的数据(错误类可不采样,性能类必采样)
    constructor(
        private readonly send: (items: MonitorItem[]) => void,
        private readonly opts = { batch: 10, intervalMs: 5000, maxPerMinute: 60, sampleRate: 1 },
    ) {
        this.start();
    }

    private start() {
        this.timer = setInterval(() => this.flush(), this.opts.intervalMs);
        // ⚠️ 关键兜底:页面隐藏/卸载时 setInterval 可能不再触发,必须主动 flush
        // visibilitychange 比 beforeunload 更可靠(移动端切后台、关闭页签都会触发)
        document.addEventListener('visibilitychange', this.onHidden);
    }

    /** 入队:采样 → 限流 → 批量 */
    push(type: string, payload: Record<string, unknown>, fingerprint?: string) {
        // 1) 采样:随机丢弃(哈希采样更公平,这里示意)
        if (Math.random() > this.opts.sampleRate) return;
        // 2) 限流:防止雪崩时监控请求把自己拖垮
        if (this.sentCount >= this.opts.maxPerMinute) return;
        this.queue.push({ type, payload, fingerprint, ts: Date.now() });
        // 3) 批量:攒够一批立即发,不必等 interval
        if (this.queue.length >= this.opts.batch) this.flush();
    }

    flush() {
        if (!this.queue.length) return;
        const items = this.queue.splice(0, this.opts.batch); // 一次最多发 batch 条
        this.sentCount += items.length;
        try {
            this.send(items);
        } catch {
            // ⚠️ 监控 SDK 自身的错误绝不能递归上报(否则死循环),只吞掉
        }
    }

    /** 每 60s 重置限流计数(真实实现里用滑动窗口更精确) */
    resetBudget = () => { this.sentCount = 0; };
    destroy() {
        this.timer && clearInterval(this.timer);
        document.removeEventListener('visibilitychange', this.onHidden); // 与 add 传同一引用才能解绑
        this.flush(); // 销毁前清空
    }
}

// ============ 错误指纹:同一 bug 聚合成一条 issue ============

/** 简单字符串 hash(比引依赖轻) */
function hash32(str: string): string {
    let h = 5381;
    for (let i = 0; i < str.length; i++) h = ((h << 5) + h + str.charCodeAt(i)) | 0;
    return (h >>> 0).toString(36);
}

/**
 * 指纹 = message + stack 前两帧(去掉行号/列号)
 * ⚠️ 只用 message 会把"undefined is not a function"所有错误混成一条;带行号会把同一 bug 的不同触发点拆成多条
 */
function errorFingerprint(message: string, stack?: string): string {
    const frames = (stack ?? '')
        .split('\n')
        .filter((l) => l.includes('at '))
        .slice(0, 2)                                     // 只取前两帧:根因通常在最内层
        .map((l) => l.replace(/:\d+:\d+/, ''))           // 去行列号:同函数不同行算同一个 issue
        .join('|');
    return hash32(`${message}::${frames}`);
}

// ---- 组装:错误走"不采样 + 指纹聚合",性能走"10% 采样" ----
const queue = new MonitorQueue((items) => {
    // navigator.sendBeacon('/api/monitor/batch', new Blob([JSON.stringify(items)], { type: 'application/json' }))
    console.log('批量上报', items.length, '条');
}, { batch: 10, intervalMs: 5000, maxPerMinute: 60, sampleRate: 1 });

window.addEventListener('error', (e) => {
    queue.push('js-error', { message: e.message }, errorFingerprint(e.message, e.error?.stack));
});

// setInterval(queue.resetBudget, 60_000); // 限流预算重置(生产实现)

接口耗时埋点与行为轨迹 ​

// 文件: examples/11-11-monitor-trace.ts —— [浏览器] 接口耗时 + 行为轨迹随错误上报

// ---- 1. 接口耗时:拦截 fetch(比拦截 XHR 简单,建议请求层统一用 fetch)----
type FetchLike = typeof fetch;
const rawFetch: FetchLike = globalThis.fetch;

globalThis.fetch = async function tracedFetch(input, init) {
    const url = typeof input === 'string' ? input : input instanceof Request ? input.url : input.toString();
    const start = performance.now();
    try {
        const res = await rawFetch.call(globalThis, input, init);
        monitorTrace.push({ kind: 'api', url, ms: Math.round(performance.now() - start), status: res.status });
        return res;
    } catch (err) {
        monitorTrace.push({ kind: 'api', url, ms: Math.round(performance.now() - start), status: 'network-error' });
        throw err;
    }
};

// ---- 2. 行为轨迹:环形缓冲区,只保留最近 20 步(内存可控)----
interface TraceItem { kind: string; url?: string; ms?: number; status?: number | string; label?: string; ts: number; }

const TRACE_LIMIT = 20;
const monitorTrace: TraceItem[] = [];

function pushTrace(item: Omit<TraceItem, 'ts'>) {
    monitorTrace.push({ ...item, ts: Date.now() });
    if (monitorTrace.length > TRACE_LIMIT) monitorTrace.shift(); // 满了丢最旧的
}

// 关键用户操作也入轨迹:点击用事件委托一次搞定

    const el = (e.target as HTMLElement).closest<HTMLElement>('[data-track]');

}, true); // 捕获阶段:防止业务 stopPropagation 后丢轨迹

// ---- 3. 错误发生时:报错 + 最近轨迹一起上报 ----

    // sendBeacon(JSON.stringify({ type: 'js-error', message: e.message, trace: [...monitorTrace] }))
    console.log('上报错误与轨迹:', e.message, monitorTrace.slice(-5));

最佳实践 ​

  • ✅ 上报必须采样 + 限流（如 10% 采样、每分钟最多 N 条），否则高峰期监控请求会拖垮自己；
  • ✅ 错误聚合维度：按 message + stack 首帧 聚类去重，避免同一 bug 刷爆存储；
  • ✅ 上报数据三要素齐全：sessionId（串联一次会话）、release/版本号（对应 sourcemap）、环境（prod/test 分流）——少了任何一个，线上问题都查不动；
  • ⚠️ 跨域脚本的报错信息只有 Script error.——需要给 <script> 加 crossorigin 且 CDN 返回 CORS 头；
  • ⚠️ 监控 SDK 自身报错不能递归上报（try/catch 包死），防止死循环；
  • ⚠️ sourcemap 只上传平台、绝不部署到公网；版本回滚时老版本的 map 也要保留，否则历史错误的堆栈无法还原。

// 文件: examples/11-03-sandbox.ts —— 简易 JS 沙箱:理解 qiankun 的核心机制
// ============ Proxy 沙箱:子应用的所有 window 操作被劫持到假 window 上 ============

function createSandbox() {
    const fakeWindow: Record<PropertyKey, unknown> = {};
    const sandbox = new Proxy(fakeWindow, {
        get(target, key) {
            // 子应用代码里的 window/self 应指向沙箱自身,嵌套取值才能继续走代理
            if (key === 'window' || key === 'self' || key === 'globalThis') return sandbox;
            // 先查子应用自己的命名空间,没有再回退到真实全局(只读共享)
            return key in target ? target[key] : (globalThis as any)[key];
        },
        set(target, key, value) {
            target[key] = value; // 写操作只落在沙箱里,不污染全局
            return true;
        },
        has(target, key) {
            return true; // 让 `xxx in window` 判断始终成立,兼容各种环境嗅探代码
        },
    });
    return sandbox;
}

// 用 Function 构造器把子应用代码跑在沙箱 window 中(与 qiankun 的 with/Proxy 方案同思路)
function runInSandbox(code: string) {
    const sandbox = createSandbox();
    // with(window){...}:子应用代码中的所有全局引用都会先经过沙箱代理
    const fn = new Function('window', 'self', `with (window) {\n${code}\n}`);
    fn(sandbox, sandbox);
    return sandbox;
}

什么时候"不需要"微前端 ​

先把这句话印在脑子里：微前端是组织问题的解药，不是技术问题的解药。以下情况不要上：

  • 单团队单仓库想"拆成多个小项目"——用 Monorepo + 路由级懒加载；
  • 只是想复用一个业务模块——抽 npm 包 / Git submodule / 直接 iframe 嵌；
  • 团队没有基建人力维护沙箱兼容性——qiankun 的坑（全局事件泄漏、polyfill 冲突、样式逃逸）需要专人兜底；
  • 性能极敏感的首屏页面——微前端每切一个子应用就多一次 entry 加载 + JS 沙箱开销。

最佳实践 ​

  • ✅ 先用决策流程图确认真的需要，再选型；存量聚合默认 qiankun，重隔离选 wujie，同栈大团队选 MF；
  • ✅ 子应用 unmount 清理清单：Vue/React 实例、路由实例、全局事件（window/document）、定时器、globalState 订阅——列成 checklist 逐一核对；
  • ✅ 子应用必须支持独立运行（!window.__POWERED_BY_QIANKUN__ 分支），联调效率天差地别；
  • ⚠️ qiankun 的 Proxy 沙箱不隔离 document（只有 wujie 的 iframe 方案彻底隔离）——子应用往 document 里塞的全局监听会互相影响；
  • ⚠️ 子应用 publicPath 必须运行时修正，否则"本地好好的，一上线资源 404"是最经典的翻车现场；
  • ⚠️ 主子应用的路由基座要提前约定（子应用 base = activeRule 前缀），后期改路由前缀是牵一发动全身。

11.4 前端架构设计方法 ​

前两节讲"点"（模式）与"面"（微前端聚合），本节回到日常：一个应用内部怎么分层、组件怎么设计、边界怎么划。架构能力 = 在变化的成本最低处做决策。

分层架构：依赖只能自上而下 ​

前端应用的经典四层，上层可以依赖下层，下层绝不感知上层（这条违反了就是架构腐化的开始）：

mermaid
graph TD
    V[视图层 Views<br/>页面组件 / 布局 / 路由出口] --> B[业务层 Features<br/>业务组件 / 状态 / 流程编排]
    B --> S[服务层 Services<br/>API 封装 / 领域模型 / 缓存策略]
    S --> I[基建层 Infra<br/>请求库 / 监控 SDK / 工具 / 常量]

层判断标准："这一行代码属于哪层"变更频率
视图层只做渲染与交互转发，不写业务判断最高
业务层出现了业务名词（订单/审批/库存）的业务流程高
服务层出现接口名/数据结构转换，但没有"业务流程"中
基建层换一个业务仍然成立（请求、埋点、工具）最低

⚠️ 最常见的腐化：视图层直接 fetch（跳过服务层）——接口一改，N 个组件要改 N 处；✅ 组件只调 service 函数，service 内部管 6.4 请求层 的实例与 5.5 服务端状态 的缓存键。

❌ 按类型分(改一个需求要跳 4 个目录):      ✅ 按功能分(一个 feature 自包含):

├── components/   (50 个组件混在一起)      ├── features/

  • ✅ shared/ 里的东西必须是"业务无关"的——一旦放进了业务组件，赶紧下放到对应 feature；
  • ⚠️ 跨域调用只有两条正路：父页面编排（各自渲染自己的 feature）、或被调域暴露纯函数 service，不允许直接 import 别的域的组件/store。

组件设计三条铁律 ​

  1. 受控与非受控双模：输入类组件内部值允许 v-model/value+onChange 外部接管，同时保留默认内部状态——只做单模的组件在第二次复用时必翻车；
  2. 组合优于配置：想加"带图标/带描述/带操作按钮"不是加第 5 个 boolean prop，而是用 slot/children 让调用方塞内容——boolean prop 组合爆炸是组件库腐化的头号信号；
  3. Headless 拆分：逻辑（分页、排序、选择）与 UI 分离，逻辑层做成 useTable() Hook / useTable() Composable，UI 层随便换皮——TanStack Table 就是这个思路的标杆（见 5.5）。
typescript
// 文件: examples/11-16-headless-use-list.ts —— Headless 列表逻辑:逻辑与 UI 彻底分离
// ============ 一个"零 UI"的分页列表 Hook,任何皮肤都能接 ============

interface UseListOptions<T> {
    fetcher: (page: number, pageSize: number) => Promise<{ items: T[]; total: number }>;
    pageSize?: number;
}

/** 只管"取数与翻页状态",不渲染任何东西 —— 可单测、可跨项目复用 */
function useList<T>(opts: UseListOptions<T>) {
    const page = { current: 1 };
    const items: { value: T[] } = { value: [] };
    const loading = { value: false };

    async function load(p = 1) {
        if (loading.value) return; // 状态机思想(11.1):loading 中忽略重复请求
        loading.value = true;
        try {
            const { items: list } = await opts.fetcher(p, opts.pageSize ?? 20);
            items.value = p === 1 ? list : [...items.value, ...list]; // 第 1 页重置,否则追加
            page.current = p;
        } finally {
            loading.value = false;
        }
    }
    return {
        items, loading,
        next: () => load(page.current + 1),
        reload: () => load(1), // 下拉刷新/筛选变化
    };
}

// ---- 演示:Node 环境直接跑通逻辑层(无 UI)----
const list = useList<{ id: number; name: string }>({
    fetcher: async (page, pageSize) => {
        console.log(`请求第 ${page} 页,每页 ${pageSize}`);
        return {
            items: Array.from({ length: pageSize }, (_, i) => ({ id: (page - 1) * pageSize + i + 1, name: `条目${(page - 1) * pageSize + i + 1}` })),
            total: 100,
        };
    },
    pageSize: 3,
});

await list.reload();
console.log('第 1 页:', list.items.value.map((i) => i.id));
await list.next();
console.log('追加后:', list.items.value.map((i) => i.id));
await list.reload();
console.log('刷新后(重置):', list.items.value.map((i) => i.id));

// UI 层(React/Vue 均可)只负责把 items 画出来 —— 逻辑可独立 vitest 单测,不用渲染组件
export {};

服务层的依赖倒置：换后端不动业务 ​

11.1 适配器模式 的支付例子放在架构视角就是依赖倒置：业务层 import 的是 interface PaymentGateway（抽象），具体渠道在应用入口注入一次：

typescript
// 文件: examples/11-17-di-composition-root.ts —— 组合根:全应用唯一"知道具体实现"的地方
// ============ 依赖注入最朴素的做法:入口组装,层层透传 ============

interface PaymentGateway { pay(cents: number, orderId: string): Promise<{ transactionId: string }> }
interface Logger { info(msg: string): void }

/** 业务服务:只依赖抽象参数,完全不知道支付渠道/日志实现 */
class CheckoutService {
    constructor(private gateway: PaymentGateway, private logger: Logger) {}
    async submit(cents: number, orderId: string) {
        const r = await this.gateway.pay(cents, orderId);
        this.logger.info(`订单 ${orderId} 支付成功 ${r.transactionId}`);
        return r;
    }
}

// ---- 生产环境组合根(main.ts)----
const logger: Logger = { info: (m) => console.log('[INFO]', m) };                 // 可换上报版
const gateway: PaymentGateway = { pay: (c, o) => Promise.resolve({ transactionId: `wx_${o}_${c}` }) }; // 可换渠道
const checkout = new CheckoutService(gateway, logger);

// ---- 测试环境:两行 mock,业务代码零改动(这就是倒置的回报)----
const fakeGateway: PaymentGateway = { pay: () => Promise.resolve({ transactionId: 'TEST_001' }) };
const testCheckout = new CheckoutService(fakeGateway, { info: () => {} });

await checkout.submit(9900, 'A_001');
await testCheckout.submit(9900, 'A_001');
console.log('✅ 同一份业务代码,两套依赖注入完成生产/测试切换');

架构演进的时机判断 ​

架构没有一步到位，关键是识别"该升级了"的信号：

信号升级动作

11.5 自测题 ​

先自己作答，再展开参考答案。

1. 【进阶】观察者模式与发布订阅模式的本质区别?

观察者:目标(Subject)直接维护观察者列表并通知,双方彼此知道对方(耦合)。发布订阅:双方只与事件中心通信,发布者与订阅者完全解耦互不知晓。EventBus 是后者的典型实现。

2. 【进阶】用策略模式重构多重 if-else 的核心思路?

把每个分支抽成独立策略函数,组织成注册表(Record<条件, 处理函数>),执行时查表调用。新增规则 = 注册一条新策略,不修改已有代码(开闭原则),每条规则还可独立测试。

3. 【进阶】前端监控上报为什么用 sendBeacon?还需要配套什么措施?

sendBeacon 在页面卸载(关闭/跳转)时也能异步可靠发送且不阻塞导航,普通请求会被浏览器取消。配套:采样率控制 + 频率限流(防止高峰期上报拖垮自己与后端),sendBeacon 失败降级 fetch keepalive,visibilitychange(hidden)时兜底 flush 队列。

4. 【基础】微前端的三大难题与主流解法?

① JS 沙箱:Proxy 代理 window(qiankun)或 iframe 天然隔离(wujie);② CSS 隔离:Shadow DOM、样式前缀、动态卸载;③ 应用通信与路由:自定义事件总线 + URL 同步。

5. 【挑战】EventBus 导致内存泄漏的完整链条是什么?怎么系统性防止?

链:常驻总线持有 handler 引用 → handler 闭包引用组件实例 → 组件卸载后实例无法回收。防:① on() 返回解绑函数,统一在 useEffect cleanup / onUnmounted 调用;② once 用于一次性事件;③ 排查手段:DevTools Memory 快照对比 detached 组件。另外 off 必须传同一函数引用,匿名函数永远解绑失败。

6. 【挑战】撤销/重做用什么模式实现?执行新操作时最容易漏掉什么?

命令模式:每条命令封装 do/undo,配 past/future 双栈。执行新命令必须清空 redo(future)栈——漏掉这一步,撤销后发新指令再点重做会出现"幽灵操作"。边界:undo/redo 到头应静默返回;大状态用 diff 型命令(记录逆操作参数)替代全量快照。

7. 【进阶】错误指纹为什么用"message + stack 前两帧并去掉行列号"?

只用 message:所有同类报错(如 undefined is not a function)混成一个 issue,无法区分根因。带完整 stack + 行列号:同一次发版同一 bug 因触发数据不同(不同行)被拆成多个 issue,聚合失效。取前两帧并抹去行列号 = "同一函数里出的同一类错"聚为一条,恰好对应"一个 bug"。

8. 【进阶】监控队列为什么用 visibilitychange 兜底而不是 beforeunload?

beforeunload 在移动端浏览器(切后台、被系统回收)和部分场景下不可靠且已被渐进废弃;visibilitychange → hidden 覆盖切后台、关闭页签、导航离开等所有"不再回来"的前兆,且此时 sendBeacon 仍可发出。双保险写法:visibilitychange(hidden) flush + pagehide 兜底。

9. 【挑战】qiankun 子应用"二进宫"(切走再切回)报错"app 已挂载"的根因?

unmount 里没有彻底销毁:Vue app.unmount() 没执行或实例没置空、路由实例没销毁、createRoot 没有 root.unmount()(React)。修复:unmount 中销毁实例并置 null、销毁路由、移除挂到全局的监听/定时器;开发环境另外注意 vite-plugin-qiankun 的 dev 模式热更新实例残留。

10. 【挑战】Module Federation 与 qiankun 的本质区别?shared 配置错误会出什么灵异问题?

qiankun 是"多个独立应用拼一页",核心价值是隔离(沙箱),可异构技术栈;MF 是"多个构建产物共享一个运行时",核心价值是共享依赖与独立部署,无沙箱、同技术栈才有意义。shared 配置两端不一致/版本不兼容 → 运行时加载出两份 React/Vue → Hooks 报 Invalid hook call、Vue 响应式对象跨实例不识别,这类问题不报配置错误、只在运行时灵异发作,是最难排查的一类。
