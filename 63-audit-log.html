63.1 审计五要素与前端职责 ​

概念解析 ​

一条合格的审计日志必须回答五个问题（5W 模型的工程版）：

要素字段前端职责后端职责
WHO 谁做的actor从会话上下文取，不接收业务手传以 Token 解析为准复核
WHEN 何时at上报时刻采集，以服务端校准为准服务端时间戳最终仲裁（32 册时钟偏差）
WHAT 对谁target业务调用点声明落库存档
HOW 做了什么action + changes字段级 diff 是前端的核心产出复核与长期存储
RESULT 结果success/failure依接口响应填报与自身执行结果对账

前端审计与服务端审计的分工原则：操作意图在前端，操作事实在服务端。用户点了「禁用账号」按钮但接口 500——前端记 user.disable / failure，服务端记自己真实执行了什么。两份日志用 traceId 关联（59 册），对不上就是问题：前端报了 success 而后端没执行，说明回执造假或链路中断。

哪些操作必须审计？判断标准是不可逆性与权益变更：删除、权限授予、金额修改、数据导出、配置变更必审；列表查询、翻页、筛选不审（那是行为埋点的地盘，43 册曝光埋点）。一条经验法则：问自己「三个月后有人投诉时，这条操作能不能帮我还原现场」。

典型应用场景 ​

  • 权限变更审计：谁把 viewer 提成了 admin（35/37 册的权限操作必须留痕）；
  • 数据导出审计：谁在什么时间导出了多少条客户数据（合规要求，导出即高危）；
  • 配置变更审计：租户管理员改了哪些配置项（与 61 册配置系统联动）。

最佳实践 ​

  • ✅ 审计采集做成独立 SDK 模块，业务代码只声明 audit({ action, target, before, after })，不感知上报细节；
  • ✅ 审计清单（哪些操作要审计）由安全/合规评审维护成配置文件，不靠开发者自觉；
  • ❌ 不要把审计和业务埋点共用一个管道——埋点可丢（采样、限流），审计一条都不能丢。

63.2 采集端：字段级 diff 与脱敏剔除 ​

概念解析 ​

审计的核心信息量不在「做了什么动作」，而在**「把什么从什么改成了什么」**。存全量快照（整个 before 对象 + 整个 after 对象）有两个问题：存储爆炸，且审阅者要自己肉眼找差异。字段级 diff 只记变化项：

json
{ "field": "role", "before": "viewer", "after": "admin", "kind": "modified" }

diff 生成的三条语义纪律：

  1. 嵌套对象递归到叶子路径：dept.level: 2 → 3 而不是 dept: {...} → {...}——审阅者要看的是路径化的变化清单；
  2. 数组按集合对比：记新增项与移除项，不记顺序变化。业务数组（标签、成员、权限点）多是无序集合，记顺序会产生大量无意义 diff；确实有序语义的数组（流程节点）应建模为带序号的结构另行处理；
  3. 三态变化分类：added（键新增）/ removed（键删除）/ modified（值变更）——三态决定了查询端 diff 视图的渲染形态。

脱敏是采集期的责任，不是展示期的：密码、身份证、银行卡、密钥这类字段，diff 引擎按字段名单整体剔除——不落盘才是真脱敏。「落盘时打码成 」的做法仍把原始值送出了浏览器，日志管道、中间存储、备份每一环都是泄漏面（47 册）。展示期打码只适用于「需要部分可见核对」的场景（如手机号 138*1234），审计 diff 场景一律剔除。

完整代码示例 ​

typescript
// 文件: examples/63-01-audit-diff.ts（核心节选）
const SENSITIVE_FIELDS = new Set(["password", "idCard", "bankCard", "token"]);

function diffObject(before: Json, after: Json, prefix = ""): FieldChange[] {
  for (const k of keys) {
    if (SENSITIVE_FIELDS.has(k)) continue; // 敏感字段整体剔除,不落盘
    if (isPlain(b) && isPlain(a)) {
      changes.push(...diffObject(b, a, path)); // 嵌套递归到叶子
    } else if (Array.isArray(b) && Array.isArray(a)) {
      // 数组按集合：记新增/移除项,不记顺序
    } else if (!Object.is(b, a)) {
      changes.push({ field: path, before: b, after: a, kind: "modified" });
    }
  }
}

运行方式：npx tsx examples/63-01-audit-diff.ts（字段 diff、嵌套路径、数组集合对比、键增删、脱敏剔除、幂等编号，共 8 组硬断言）。

最佳实践 ​

  • ✅ diff 在前端生成：before 取自表单初始快照（33 册 Zod 校验后的干净数据），after 取自提交值——服务端再做一次复核 diff 防前端造假；
  • ✅ 敏感字段名单集中维护，CI 门禁扫描新增字段是否漏登记（47 册三道防线思路）；
  • ⚠️ 大对象 diff 有性能成本：超过百字段的对象先做引用相等快路径（Object.is 直接返回空）；
  • ❌ 不要把 before/after 序列化成字符串存一个字段——查询端无法按 field 检索，diff 视图也无法结构化渲染。

63.3 防抵赖：幂等编号、时间与链路 ​

概念解析 ​

审计日志的价值在于事后可作为证据，这要求三个防抵赖设计：

  1. 幂等审计编号：auditId = hash(actor + at + action + traceId)。审计上报必须可靠（失败重试、离线暂存后补传），重试就会重复——服务端以 auditId 为唯一键去重，同一事件重试多次只落一条。没有幂等键的可靠上报 = 重复日志泛滥。
  2. 时间以服务端为准：客户端时钟可改（用户手动调时间、多时区设备），前端上报的 at 只是参考，服务端接收时刻才是仲裁时间。32 册的时钟偏差校正方案在此复用：启动时取一次服务端时间计算 offset，上报时间 = 本地时间 + offset。
  3. traceId 贯穿：一次「禁用账号」操作会产出前端审计（点击与意图）、服务端审计（真实执行）、服务端业务日志、监控 Trace——四者用同一 traceId 关联。排查「日志对不上」时，traceId 是把分散证据串成链的唯一线索（59 册）。

上报可靠性管道与 46 册错误上报同构：内存队列 → 批量发送 → sendBeacon 兜底（页面关闭时）→ 失败落 IndexedDB 下次启动补传（56 册离线写队列思路）。审计与埋点的分界线就在这里：埋点允许丢，审计必须最终送达。

最佳实践 ​

  • ✅ 审计 SDK 与业务请求共用 traceId 生成器，一次用户操作一个 traceId；
  • ✅ 失败审计持久化到 IndexedDB，应用启动时优先补传再开放操作；
  • ⚠️ 审计上报失败不能阻塞业务操作（用户不该为日志系统故障买单），但要告警——审计管道故障本身是安全事件；
  • ❌ 不要相信前端上报的 actor 与时间做最终存档——服务端必须用 Token 与时间服务复核，前端字段只是辅助。

63.4 查询端：组合筛选与 diff 视图 ​

概念解析 ​

审计查询页的用户是安全审计员与管理员，他们的典型问题是交集型的：「上个月谁对角色做了授权类操作且失败了」。这决定筛选模型是多条件 AND 组合：

条件形态说明
actor人员选择器谁做的
targetType / targetId对象类型 + 关键词对谁
action 前缀role.* 通配哪类操作（前缀匹配覆盖同族动作）
resultsuccess / failure失败操作是审计的重点关注对象
时间窗[from, to) 左闭右开左闭右开避免边界记录被两页各算一次
keywordtargetId + 变化字段名模糊兜底

diff 视图是审计详情页的核心呈现：把 changes 数组渲染成「字段路径 + 前后对照」的行列表，added 绿色、removed 红色、modified 中性色前后对照——审阅者 3 秒看懂改了什么。这比展示 JSON 快照友好一个数量级，也是 diff 生成期坚持叶子路径化的回报。

翻页用游标分页（62 册同型）：审计日志是只增不改的流式数据，页码分页在新日志写入时会错位。游标 = 当前页最旧一条的时间戳。

完整代码示例 ​

typescript
// 文件: examples/63-02-audit-query.ts（核心节选）
function toDiffView(r: AuditRow): DiffViewRow[] {
  return r.changes.map((c) => {
    if (c.kind === "added") return { ..., text: `新增 ${fmt(c.after)}`, tone: "green" };
    if (c.kind === "removed") return { ..., text: `删除 ${fmt(c.before)}`, tone: "red" };
    return { ..., text: `${fmt(c.before)} → ${fmt(c.after)}`, tone: "neutral" };
  });
}

运行方式：npx tsx examples/63-02-audit-query.ts（AND 组合筛选、action 前缀通配、时间窗左闭右开、diff 视图三态、游标翻页无重复，共 9 组硬断言）。

最佳实践 ​

  • ✅ 审计查询页本身的使用也要被审计（谁查了谁的日志）——查询即敏感操作；
  • ✅ 导出审计报告走异步任务 + 下载通知（62 册），不在请求里同步生成大文件；
  • ⚠️ 审计日志保留期按合规要求定（等保通常 ≥6 个月，金融可能数年），查询接口要为大数据量设计（索引、分区、冷热分层是后端课题，前端只需坚持游标分页）；
  • ❌ 不要给管理员提供「删除审计日志」功能——可删除的审计等于没有审计，到期清理由系统自动任务执行。

63.5 自测题 ​

1. 【基础】审计日志的五要素是什么？为什么 actor 和 at 不能只信前端上报值？

WHO（actor）、WHEN（at）、WHAT（target）、HOW（action + changes）、RESULT。actor 与 at 不能只信前端：前端一切数据可被伪造（36 册），攻击者改 Token 解析前的上报字段就能把操作嫁祸他人；客户端时钟可被用户手动修改，时间证据失效。正确分工：前端上报参考值，服务端以 Token 解析的 actor 和接收时刻的服务端时钟为最终存档值，两边对不上即触发安全告警。

2. 【基础】为什么审计 diff 要"嵌套递归到叶子路径"而不是整对象快照对比？

两个原因：① 可读性——审阅者要看的是「dept.level: 2 → 3」这样的路径化清单，整对象快照要自己肉眼找差异，大对象下基本不可用；② 检索性——叶子路径化后查询端可以按 field 精确检索「所有改过 role 字段的操作」，快照字符串无法结构化查询。附加收益是存储：只存变化字段比存两个全量快照小一个数量级。

3. 【基础】敏感字段脱敏为什么要在采集期剔除而不是展示期打码？

展示期打码意味着原始值已经离开浏览器，穿过了网络、日志管道、存储、备份——每一环都是泄漏面，且打码值与原始值在同一存储中往往并存可关联。采集期剔除（diff 引擎按字段名单整体跳过）让原始值从未离开浏览器，「不落盘才是真脱敏」。展示期打码只适用于「需要部分可见核对」的场景（手机号 138****1234 用于确认是本人），审计 diff 场景没有核对需求，一律剔除。

4. 【进阶】审计上报为什么必须有幂等编号？没有幂等键的可靠上报会发生什么？

审计要求「一条都不能丢」，于是要有失败重试、页面关闭时 sendBeacon 兜底、离线落 IndexedDB 启动补传——这些机制的共同副作用是同一事件可能到达多次。没有幂等键，可靠上报 = 重复日志泛滥，审计员看到三条相同的「授权 admin」记录，无法判断是三次操作还是一次重试，证据链可信度崩塌。幂等编号（hash(actor+at+action+traceId)）让服务端以唯一键去重：重试安全，证据链每条对应一次真实操作。

5. 【进阶】审计管道与行为埋点管道为什么必须分开？共用会发生什么？

两者的可靠性等级相反：埋点允许采样、限流、丢失（丢 5% 的曝光数据不影响结论），审计一条都不能丢（丢的那条可能正是违规操作）。共用管道会发生什么：埋点管道为了控制成本开启采样，审计事件被随机丢弃；或埋点管道大流量冲击时限流降级，审计跟着陪葬。分开的代价是多一套管道，收益是可靠性等级可以独立设计——审计管道甚至可以配更贵的存储（WORM 一次写入多次读取）与更严的告警。

6. 【进阶】为什么审计查询的时间窗要用 [from, to) 左闭右开？翻页为什么要游标而不是页码？

左闭右开保证相邻时间窗无缝无重叠：[1 月, 2 月) 与 [2 月, 3 月) 拼起来恰好全覆盖，一条 2 月 1 日 00:00 的记录不会被两个窗各算一次（闭区间会重复计入）。游标而非页码：审计日志只增不改，导出/查询期间新日志持续写入，页码分页会整体后移导致第 2 页重复第 1 页末尾的记录；游标（当前页最旧一条的时间戳）锚定位置，头部新增不影响已翻页（62 册同型）。

7. 【挑战】设计「数据导出审计」专项方案：要求能回答「谁在什么时间导出了什么范围的多少条数据，导出文件后来有没有被打开过」。

采集设计：① 导出触发时前端上报 audit({ action: 'data.export', target: { type: 'customer', id: filterHash }, changes: [{ field: 'filter', after: 筛选条件 }, { field: 'rowCount', after: 条数 }] })，filterHash 由服务端生成作为这次导出快照的指纹；② 导出任务异步化（62 册通知下发），任务完成事件与审计用 traceId 关联；③ 文件打开追踪：下载链接带一次性 token，每次下载/预览由服务端记 access 日志并与 export 审计关联；④ 防抵赖：导出文件内嵌隐形水印（操作人 + 时间，PDF 元数据或 Excel 隐藏 Sheet，31 册），泄漏后可溯源；⑤ 对账：定期比对导出审计与文件访问日志，有导出无访问属正常，有访问无导出记录是越权下载告警。整条链的关键是 filterHash + traceId + 一次性 token 三个锚点。

8. 【挑战】审计日志系统自身可能被攻击者利用做哪些事？如何防御？

四类攻击面：① 淹没攻击——伪造海量审计事件灌满存储，让真实违规淹没在噪声里；防御：按 actor 限流 + 异常频率告警（59 册错误聚合同款思路）。② 字段投毒——在 before/after 里注入 XSS payload，审计员打开详情页时执行；防御：diff 视图一律文本渲染不 innerHTML，服务端存储前转义。③ 重放攻击——抓包重放历史审计事件混淆时间线；防御：幂等键 + 服务端时间仲裁，重放的事件因 auditId 重复被去重。④ 查询探测——攻击者用审计查询页探测「哪些操作会被记录」以规划规避路径；防御：审计查询页本身是敏感操作，访问要授权、要留审计（谁查了日志）、要告警异常查询模式。审计系统自身的安全等级必须不低于它保护的业务系统。
