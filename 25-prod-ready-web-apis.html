本册定位：不是 API 大全，而是一本经过两道筛选的「口袋书」——兼容性筛（Baseline 已达成、两大引擎以上稳定支持、无需 flag）与踩坑筛（日常业务真的会踩的才收）。每节五段式：概念 → 场景 → 可运行示例 → 最佳实践 → 自测题。正文行内代码里的 API 名已自动挂上 MDN 官方文档链接，点击即跳。

25.1 选型标准与兼容性基线 ​

25.1.1 概念解析 ​

「生产可用」的判定标准不是「MDN 上有这个页面」，而是三条硬线：

  1. Baseline 已达成：MDN/Baseline 体系把 API 分为 Widely available（两大引擎 + 30 个月）、Newly available（刚全引擎可用）与 Limited（有引擎没实现/需 flag）。本册只收 Widely available 或已被主流业务验证的 Newly available。
  2. 无 flag、无 polyfill 也可用：需要 --enable-experimental-web-platform-features 的 API 一律不进生产。
  3. 有运行时能力检测兜底：再稳的 API 也要写「检测不可用时的降级路径」，而不是直接裸调。

自查工具链：caniuse 查具体 API 的版本覆盖率；MDN 页头直接标注 Baseline 状态；浏览器端用 in/typeof 做运行时检测。

一个常被忽略的事实：这批 Web API 的大半已被 Node 收编为全局——AbortController、structuredClone、BroadcastChannel、performance.mark、Intl.*、TextEncoder、crypto.randomUUID 都能在 Node 18+ 里直接跑。所以本册的示例是可以真实运行的（用 npx tsx 或 Node 22+ 的类型剥离），只有纯浏览器 API（观察者、剪贴板、存储配额）以「契约模拟 + 行内代码」的形式呈现。

25.1.2 典型应用场景 ​

  • 新项目技术选型：决定「要不要为了一个功能引入 polyfill/第三方库」
  • 旧项目评审：判断某个老写法（setInterval 轮询、UA 嗅探、手写深拷贝）能否替换成标准 API
  • Code Review：一眼判断同事引入的依赖里哪些是「平台已经内置的能力」

25.1.3 可运行代码示例 ​

能力检测的三种姿势：in 探宿主、typeof 探值、试金石探二级成员；并给出「UA 嗅探为什么永远不对」的反面对照。

运行方式：npx tsx examples/25-01-feature-detect.ts

25.1.4 最佳实践 ​

  • 检测顺序固定为：能力检测 → 降级路径，绝不先看 UA
  • 二级成员（如 navigator.storage.estimate）用「构造一次试试」的探针，in 只能探一层
  • 把检测结果模块级缓存成布尔常量，不要在每个请求里重复探测
  • 渐进增强：核心功能不依赖新 API，新 API 只做体验增强（如 AbortSignal.any 不可用就退回手动组合）

25.1.5 自测题 ​

1. 【基础】判断一个 API 是否「生产可用」，本章给出哪三条硬线？

①Baseline 已达成（或已被主流业务验证的 Newly available）；②无 flag、无 polyfill 也可用；③有运行时能力检测兜底、写好了降级路径。三条同时满足才算，MDN 上「有页面」不等于能上生产。

2. 【进阶】`in`、`typeof`、试金石三种能力检测各适合什么场景？为什么二级成员要用试金石？

in 适合检测宿主对象上「有没有这个键」（如 'AbortController' in globalThis）；typeof 适合值可能来自任意来源的场景，且对未声明变量安全；试金石（构造一次 try/catch）适合二级成员——in 只能探一层，'estimate' in navigator.storage 探不到方法是否存在，必须访问一次 navigator.storage?.estimate 看类型。UA 嗅探在任何场景都不做功能开关。

25.2 观察者家族 ​

25.2.1 概念解析 ​

四个「订阅式」观察者覆盖了前端 90% 的「监听 DOM/性能变化」需求，共同点是回调由引擎在合适的时机批量派发，替代手工轮询与高频事件：

观察者订阅什么典型替代品
IntersectionObserver元素与视口（或指定根）的交叉状态scroll 事件 + getBoundingClientRect
ResizeObserver元素自身尺寸变化window.resize + 手动比对
MutationObserverDOM 树结构/属性/文本变更MutationEvent（已废弃）
PerformanceObserver性能条目（LCP、长任务、资源计时）轮询 performance.getEntries

25.2.2 典型应用场景 ​

  • 懒加载图片/组件、曝光埋点、无限滚动（IO）
  • 容器查询之外的「组件级自适应」——组件根元素变宽时切换布局，不关心窗口尺寸（RO）
  • 防篡改水印、第三方组件渲染完成监听（MO）
  • 采集 LCP/INP/长任务指标上报（PO）

25.2.3 可运行代码示例 ​

Node 里没有真实 IO，示例按规范契约复刻了它的调度行为，验证三个最常被误解的点：observe() 后必然立即回调一次（哪怕元素不可见）、threshold 是「跨越档位才触发」、unobserve 后彻底静默。

运行方式：npx tsx examples/25-02-observer-contract.ts

25.2.4 最佳实践 ​

  • 曝光埋点必须判断 isIntersecting——首帧那次回调 intersectionRatio 可能是 0
  • threshold 用数组表达档位（[0, 0.5, 1]）；写 1 时注意浏览器会修正为略小于 1（浮点）
  • 一次性埋点在回调里立刻 unobserve（或干脆用 { once: true } 思路重建成新 observer）
  • 回调里不要做重活：把数据 push 进队列，requestIdleCallback 里再上报
  • RO 回调里改尺寸可能触发「Resize loop limit exceeded」报错——避免在回调里直接改自身尺寸

25.2.5 自测题 ​

3. 【进阶】为什么用 IntersectionObserver 做曝光埋点时，首帧就可能误报一次？怎么规避？

规范规定 observe() 后必须立即回调一次报告当前状态，此时元素可能在视口外（isIntersecting: false、intersectionRatio: 0）。规避：回调里先判断 isIntersecting === true 再计曝光，不要把「收到回调」当「发生曝光」。

4. 【进阶】IntersectionObserver 与 scroll 事件 + getBoundingClientRect 相比，省掉了什么开销？

scroll 是高频事件且 getBoundingClientRect 强制同步布局（layout thrashing 风险）；IO 把「交叉计算」交给引擎在合成/渲染管线里批量异步完成，回调按帧合并派发，不占主线程滚动路径，也不用自己算节流。

5. 【挑战】设计一个「列表项 50% 可见且持续 1s 才算有效曝光」的埋点方案。

IO 设 threshold: [0.5]；回调里 isIntersecting && ratio >= 0.5 时对该项启动 1s 定时器，期间任一项跌破 0.5（回调再次触发）就 clearTimeout 撤销；定时器到点才算曝光并 unobserve。要点：可见时长的判定不能只靠 IO（它只报「跨越」不报「持续」），需要 IO + 定时器组合，回调里做状态机。

25.3 中断与取消 ​

25.3.1 概念解析 ​

AbortController/AbortSignal 是浏览器与 Node 共通的统一取消协议：一个信号对象，谁挂上谁就能被取消。它已渗透进：fetch、事件监听（addEventListener 第三参的 { signal }）、Promise 工具、流（ReadableStream）、定时器（AbortSignal.timeout）。

两个静态构造器免掉了手写样板：AbortSignal.timeout(ms) 生成「到点自动 abort」的信号；AbortSignal.any([s1, s2]) 把多个信号合成一个（任一触发即触发，Node 20.3+/全引擎可用）。

25.3.2 典型应用场景 ​

  • 请求超时：fetch(url, { signal: AbortSignal.timeout(5000) })
  • 竞态控制：搜索框连打只保留最后一次（旧请求 abort）
  • 组件卸载清理：所有监听与请求挂同一个 signal，abort() 一次清干净
  • 用户主动取消：下载/上传的「取消」按钮

25.3.3 可运行代码示例 ​

超时（AbortSignal.timeout）、竞态（旧请求作废）、级联（一个 controller 同时撤掉任务与三个事件监听）三个场景，全部本地定时器模拟，离线可跑。

运行方式：npx tsx examples/25-03-abort-controller.ts

25.3.4 最佳实践 ​

  • 自定义请求封装时把 signal 透传给底层 fetch；第三方库先检测是否接受 signal，不接受就包一层 Promise.race
  • signal.addEventListener("abort", fn, { once: true })：用完即摘，防监听泄漏
  • abort 后信号不可复用（状态是终态）；每次新任务新建 controller
  • 取消不是错误：捕获时区分 signal.reason，AbortError 走静默分支不上报监控

25.3.5 自测题 ​

6. 【基础】AbortSignal.timeout(ms) 相当于手写哪三行？它比手写好在哪？

相当于 const ac = new AbortController(); setTimeout(() => ac.abort(), ms); return ac.signal;。好在定时器随信号生命周期自动清理——任务提前完成或信号被 abort 后不会留下悬挂定时器把进程/页面挂住。

7. 【进阶】fetch 超时抛出的错误叫什么名字？为什么不能把它当服务端超时上报？

AbortError（AbortSignal.timeout 产生的 reason 是 TimeoutError DOMException）。它表示客户端主动放弃，此时连接可能仍在服务端执行；把它当 5xx 上报会污染服务端监控。正确做法：区分 AbortError/TimeoutError 单独统计，或在上报里标注「客户端取消」。

8. 【挑战】一个页面里有请求、定时器、事件监听三类资源，如何用一套 signal 做到卸载时一行清理？有什么前置条件？

模块持有一个页面级 AbortController：请求传 { signal }、addEventListener(..., { signal })、自定义任务内部监听 signal 的 abort 事件清理定时器；卸载时 ac.abort() 一行全撤。前置条件：每个资源路径都真正接了 signal——定时器不会自动消失，必须自己在 abort 回调里 clearTimeout；第三方库若不支持 signal 要包取消壳。另外 abort 是一次性终态，「页面复用」场景（如 SPA 的页面栈）要按页面实例新建 controller。

25.4 结构化复制与深拷贝 ​

25.4.1 概念解析 ​

structuredClone 实现的是结构化克隆算法——postMessage、IndexedDB 存取、BroadcastChannel 消息底层用的同一套协议。它与 JSON 序列化的本质区别：类型保真（Date/Map/Set/RegExp/ArrayBuffer）、保留 undefined 与 NaN、原生支持循环引用。

值JSON.parse(JSON.stringify)structuredClone
Date变 ISO 字符串Date
Map/Set{}Map/Set
undefined 字段丢失保留
NaN/Infinitynull / nullNaN / Infinity
循环引用抛 TypeError原生支持
函数丢弃抛 DataCloneError

25.4.2 典型应用场景 ​

  • 状态管理里的深拷贝快照（undo/redo 栈）
  • Worker/iframe 之间传参的语义预期（到达的就是克隆）
  • 替代 immer/lodash.cloneDeep 里的轻量场景

25.4.3 可运行代码示例 ​

逐项对照两种拷贝的丢失清单（Date/Set/Map/undefined/NaN/循环引用/函数），并验证改副本不影响源。

运行方式：npx tsx examples/25-04-structured-clone.ts

25.4.4 最佳实践 ​

  • 纯数据对象优先 structuredClone；带方法/类的实例需要「 revival 」（还原原型）时才上类工厂
  • 跨上下文传错误对象不要依赖克隆后的自定义属性——把错误序列化成 { name, message, stack } 纯数据
  • 性能敏感路径注意：克隆 1MB 级对象也有毫秒级成本，高频热路径考虑不可变数据结构而非拷贝
  • JSON.parse(JSON.stringify()) 只在「确定是 JSON 安全数据」时使用（比如刚好要发 JSON 请求体）

25.4.5 自测题 ​

9. 【基础】structuredClone 遇到函数会怎样？JSON 方式呢？

structuredClone 抛 DataCloneError（函数根本不可克隆）；JSON 方式不报错但静默丢弃函数字段——后者更危险，因为类型变了没有任何提示。

10. 【进阶】为什么「从 BroadcastChannel 收到的消息改了之后，发送方不受影响」？这个特性对设计消息协议有什么要求？

消息投递走结构化克隆，接收方拿到的是深拷贝副本，与发送方断开引用。这要求消息协议里的数据必须是可克隆的纯数据（不能带函数、DOM 节点、类实例方法），且不要指望「传引用」来同步状态——想共享可变状态应该走 SharedArrayBuffer 或把状态放在单一持有方。

25.5 URL 与查询参数 ​

25.5.1 概念解析 ​

URL 处理的错误姿势集中在「把 URL 当字符串拼接」。标准库三层：URL 负责整体解析（协议/origin/路径规范化）、URLSearchParams 负责查询串（自动编码解码、重复键、增删改）、encodeURIComponent/encodeURI 负责手工编码（注意两者职责不同）。

25.5.2 典型应用场景 ​

  • 拼接带参数的 API 地址、分页/筛选状态写入地址栏
  • 解析回调 URL 里的 token/code
  • 防开放重定向：校验用户传入的跳转地址

25.5.3 可运行代码示例 ​

四个高频坑：encodeURI 与 encodeURIComponent 用错位、+ 号空格歧义、searchParams 重复键与自动解码、new URL 做防开放重定向校验。

运行方式：npx tsx examples/25-05-url-pitfalls.ts

25.5.4 最佳实践 ​

  • 参数值一律 encodeURIComponent（它连 &= 都转义）；encodeURI 只用于「整个地址」且几乎用不上
  • 查询串读写走 URLSearchParams，不手拼；空格会被编码成 + 或 %20，读取时自动还原
  • 重定向白名单用 new URL(input, base) 解析后比对 origin，同时校验协议是 http(s)——挡掉 //evil.com 与 javascript: 伪协议
  • URL 实例是可变对象，searchParams.set 之后要把实例的 href 用回去

25.5.5 自测题 ​

11. 【基础】encodeURIComponent 和 encodeURI 的核心区别是什么？参数值该用哪个？

encodeURI 保留 URL 结构字符（& = ? # /），用于整体地址；encodeURIComponent 把参数值里的所有保留字符都转义，参数值必须用它——否则值里的 & 会被服务端当成参数分隔符。

12. 【挑战】`new URL("//evil.com", "https://app.com")` 会得到什么？为什么它能绕过「只判断字符串前缀」的重定向校验？

得到 https://evil.com/——以 // 开头的「协议相对地址」会继承 base 的协议但指向外部主机。若校验只看 input.startsWith("/") 或 !input.includes("http")，这条输入会通过。正确校验是解析成 URL 实例后比对 origin 与协议白名单，而不是对原始字符串做模式匹配。

25.6 跨上下文通信 ​

25.6.1 概念解析 ​

四个通道各司其职，选错通道是这一域最大的坑：

通道拓扑同源要求典型用途
BroadcastChannel广播（发者不收自己的消息）同源同设备多 Tab 状态扇出（登录态/主题）
MessageChannel点对点管道（两个 MessagePort）无（可 transfer）两者间大数据流、移交控制权
Web Locks（navigator.locks）互斥/共享锁同源同设备Leader 选举、防重复任务
postMessage指定目标窗口可跨源（必须校验 origin）iframe/弹窗跨源通信

25.6.2 典型应用场景 ​

  • 登出后所有 Tab 立即跳登录页（BroadcastChannel）
  • Leader Tab 独占 WebSocket，其它 Tab 走扇出（Web Locks + BroadcastChannel，详见 18 册）
  • iframe 与宿主的跨源协作（postMessage + origin 双向校验）

25.6.3 可运行代码示例 ​

Node 18+ 内置 BroadcastChannel，双实例互发模拟两个 Tab：收发、结构化克隆语义、close 生命周期。

运行方式：npx tsx examples/25-06-broadcast-channel.ts

25.6.4 最佳实践 ​

  • 消息一律是可克隆的纯数据（见 25.4），协议带 type 字段便于版本演进
  • postMessage 的 targetOrigin 必须写确切 origin，写 '*' 等于把消息广播给任意宿主
  • BroadcastChannel 收不到自己发的消息（广播语义），需要回声就显式发给自己另一实例
  • Web Locks 的锁是同源同设备进程级的，跨设备同步不要指望它
  • 用完 close()，否则频道对象常驻内存并持续接收消息

25.6.5 自测题 ​

13. 【基础】BroadcastChannel、MessageChannel、Web Locks 三者一句话定位？

BroadcastChannel：同源同设备的「广播电台」，扇出状态用；MessageChannel：点对点「专线」，可 transfer 大数据；Web Locks：跨 Tab「互斥锁」，做 Leader 选举和防重复任务——它是锁不是消息通道。

14. 【进阶】postMessage 写 targetOrigin 为 '*' 有什么具体风险？正确的双向校验怎么做？

消息会被送达任意宿主下的目标窗口——若消息里带 token/业务数据，恶意页面把你的站点嵌进 iframe 后能收到。正确做法：发送方 targetOrigin 写确切 origin；接收方校验 event.origin 白名单后再处理，且 event.source 与预期窗口比对；只传必要最小数据。

15. 【挑战】为什么「Leader 持锁建 WebSocket + BroadcastChannel 扇出」比「每个 Tab 各自建连接」好？这个方案的失效模式是什么？

省 N-1 条连接与服务端连接数压力；上行去重；断线重连只有 Leader 一处逻辑。失效模式：Leader Tab 被冻结（后台 tab 节流）导致心跳超时——锁的 autoRelease 会让新 Leader 接管，但存在短暂「双 Leader 或无 Leader」窗口，消息协议需要带序号去重与重放（未确认消息落 IndexedDB）。详见 18 册 7.3。

25.7 微任务与调度 ​

25.7.1 概念解析 ​

事件循环的两层队列：微任务（queueMicrotask、Promise.then、MutationObserver）在当前同步代码结束后「清空到不能再清」；宏任务（setTimeout/消息/IO 事件）每轮循环只取一个。浏览器独有的帧调度层：requestAnimationFrame 在渲染前、requestIdleCallback 在空闲时（Node 没有这两者）。

25.7.2 典型应用场景 ​

  • queueMicrotask：把「本该同步的回调」异步化——保证订阅者异常不中断发布者、状态一致后再通知
  • setTimeout(0)：把重计算挪出当前任务，给渲染让路
  • requestIdleCallback：埋点上报、预取等低优任务
  • 长列表分片渲染：每帧处理一批（rAF + deadline）

25.7.3 可运行代码示例 ​

执行顺序实证：同步 → 微任务（含链式微任务）→ 宏任务；以及 queueMicrotask 在发布订阅里隔离异常的实战。

运行方式：npx tsx examples/25-07-task-ordering.ts

25.7.4 最佳实践 ​

  • 「下一个循环再执行」的语义用 queueMicrotask（比 setTimeout(0) 早且稳定）；需要「让出渲染」才用 setTimeout
  • 微任务里再发微任务仍属同一轮清空——递归微任务会饿死渲染（死循环就卡死页面），递归逻辑必须走宏任务
  • rAF 回调里读布局再改样式会强制同步布局，批量读写分离（先读后写）
  • setTimeout(fn, 0) 不是「立即」：被嵌套 5 层后浏览器强制最小 4ms，后台 Tab 被节流到 1s+

25.7.5 自测题 ​

16. 【基础】queueMicrotask 和 setTimeout(fn, 0) 的执行先后？各自语义是什么？

queueMicrotask 先——微任务在当前同步代码结束、宏任务开始之前清空。语义区别：queueMicrotask 是「本轮末尾、渲染之前」的微延迟；setTimeout(0) 是「下一轮宏任务」，且受 4ms 最小延迟与后台节流影响。

17. 【挑战】为什么「在微任务里递归调度微任务」会冻结页面，而递归 setTimeout 不会？给一个必须改写的历史事故示例。

微任务队列的清空规则是「处理到队列为空才让出」，处理中新增的微任务也属同一轮——递归微任务永远清不完，渲染与宏任务全部饿死。递归 setTimeout 每轮是独立宏任务，渲染有机会插入。事故示例：Promise 链里「resolve 后再 resolve 自己」或监听器里 queueMicrotask 重新入队自身，页面白屏但 CPU 正常——特征是控制台无报错、主线程满载。改写：把递归入口换成 setTimeout/requestIdleCallback，或加深度/时间片上限。

25.8 国际化格式化 Intl ​

25.8.1 概念解析 ​

Intl.* 是平台内置的本地化引擎：数字/货币/单位（NumberFormat）、日期（DateTimeFormat）、相对时间（RelativeTimeFormat）、列表连接（ListFormat）、本地化排序（Collator）、分词（Intl.Segmenter）。Node 13+ 默认 full-icu，服务端渲染与浏览器输出一致——格式化逻辑可以放共享层。

25.8.2 典型应用场景 ​

  • 千分位/货币/单位显示（别再手写正则千分位）
  • 「3 天前」类相对时间、多语言日期
  • 中文按拼音排序、无空格语言的词级统计与高亮

25.8.3 可运行代码示例 ​

NumberFormat（数字/货币/单位）、DateTimeFormat（锁 UTC 保证确定性）、RelativeTimeFormat、ListFormat、Segmenter（中文分词）、Collator（拼音序）一网打尽。

运行方式：npx tsx examples/25-08-intl-format.ts

25.8.4 最佳实践 ​

  • Intl 实例构造有成本：热路径模块级单例复用，绝不在 render/循环里 new
  • DateTimeFormat 必须显式 timeZone：默认「随宿主」，CI 与本地、用户与用户输出都会漂移
  • format 输出随 ICU 数据版本微调：测试断言锁 locale+时区，或只断言结构（包含年份）不断言全文案
  • 需要服务端/客户端一致的格式化时，把 Intl 调用放共享层并在两端锁同一 Node/浏览器 ICU 行为

25.8.5 自测题 ​

18. 【进阶】为什么「日期格式化不写 timeZone」在 CI 里是隐患？正确做法是什么？

不写 timeZone 默认用宿主时区：开发者机器是东八区，CI 是 UTC，同一时刻格式化出不同文案，快照测试随机红。做法：业务有明确地区就显式传 timeZone；需要跟随用户时区的场景在测试里固定 timeZone + 固定 UTC 时刻。

19. 【进阶】Intl.Segmenter 解决了中文场景的哪两类问题？与正则 \w 或 length 有何本质不同？

①词级统计/高亮：中文没有空格分隔，length 数的是码点、正则按字符切，Segmenter 按词典规则切出「词」（isWordLike 过滤标点助词）；②搜索输入预处理。本质不同：它加载了 ICU 词典与 locale 规则，是语言学切分而非字符切分——同一文本在不同 locale 下切分结果不同。

25.9 性能度量 ​

25.9.1 概念解析 ​

度量三件套：performance.mark 给时间点命名、performance.measure 把两个点连成命名区间、PerformanceObserver 异步订阅条目。命名后的区间进入性能时间线——DevTools Performance 面板直接可见，也可 getEntriesByName 取回上报。裸的 performance.now() 差值只适合临时调试，不进时间线。

25.9.2 典型应用场景 ​

  • 关键路径耗时打点（解析/请求/渲染分段）并上报
  • 采集 Core Web Vitals（浏览器端用 PO 订阅 paint/LCP/event 条目）
  • 长任务监控（entryTypes: ["longtask"]）

25.9.3 可运行代码示例 ​

mark/measure + PerformanceObserver 订阅、measure 带 detail 元数据、上报后的 disconnect 与 clear 收尾闭环。

运行方式：npx tsx examples/25-09-perf-measure.ts

25.9.4 最佳实践 ​

  • 区间度量一律 mark/measure（可观测），performance.now() 只做临时差值
  • PO 回调是异步的：measure 完成后别同步读条目，等 observer 送达
  • 长驻页面（SPA 常开一整天）必须 disconnect() + clearMarks/clearMeasures，否则条目缓冲无限增长
  • 上报用 navigator.sendBeacon（页面卸载也能送达），别用同步 XHR
  • 浏览器端算 FCP/LCP/INP 优先 web-vitals 库，手搓容易踩 buffered 与双重计数

25.9.5 自测题 ​

20. 【基础】mark/measure 相比裸打 performance.now() 差值，多得到了什么？

命名区间进入性能时间线：DevTools 面板可视化、getEntries 程序化读取、可携带 detail 元数据、可被 PerformanceObserver 订阅统一上报。裸差值只有 console 里那一个数字，什么设施都接不上。

21. 【挑战】为什么 PerformanceObserver 回调拿条目要判空/防重？长驻 SPA 不做清理会发生什么？

条目按「类型 + buffered」聚合批量送达，同一区间可能因多次 observe 或 buffered 回放重复出现，需按 name+startTime 去重。不清理的后果：性能条目缓冲持续增长（内存泄漏），重复订阅导致同一事件上报多次（数据虚高），监听器本身也常驻。规范做法：去重表 + 上报后 disconnect + 定期 clear。

25.10 浏览器专属高频 API 速览 ​

以下 API 无 Node 对照、示例无法实跑，给「最小可用片段 + 兼容性提示」。兼容性以 Baseline 为准，逐个查过：全部 Widely available 或接近达成。例外：Blob/TextEncoder/crypto.* 等二进制与安全条目已被 Node 18+ 收编为全局，示例可直接 npx tsx 验证。

25.10.1 剪贴板：Clipboard ​

js
// 复制：用户手势内调用（点击/键盘事件回调），无需权限即可写
await navigator.clipboard.writeText("要复制的文本");
// 粘贴：需要用户授权，失败走 catch（权限被拒 / 非安全上下文）
try {
  const text = await navigator.clipboard.readText();
} catch (e) {
  /* 降级:提示手动 Ctrl+V */
}

坑：非 HTTPS（除 localhost）下 navigator.clipboard 直接是 undefined——内网 HTTP 环境必须降级 document.execCommand("copy")；写剪贴板必须在用户手势调用栈内，setTimeout 里调用会失败。

25.10.2 存储配额：navigator.storage ​

js
const { usage, quota } = await navigator.storage.estimate();
console.log(`已用 ${(usage / 1048576).toFixed(1)} MB / 配额 ${(quota / 1073741824).toFixed(1)} GB`);
const granted = await navigator.storage.persist(); // 申请持久化,防被自动清理

坑：配额是「整站」的且按磁盘剩余空间浮动，别当固定值缓存；persist() 被拒是常态（PWA 安装 + 高站点参与度才容易批），写入前永远要有配额不足的降级。

25.10.3 页面可见性与上报：visibilitychange / navigator.sendBeacon ​

js
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") {
    navigator.sendBeacon("/api/report", JSON.stringify(pageStats)); // 卸载也能送达
  }
});

坑：移动端「切后台」是 visibilitychange 而不是 unload（iOS 上 unload 根本不触发）；sendBeacon 的响应拿不到、体积有限（一般 64KB 内），大数据分批或改用 fetch keepalive。

25.10.4 媒体查询与响应式偏好：matchMedia ​

js
const dark = matchMedia("(prefers-color-scheme: dark)");
dark.addEventListener("change", (e) => applyTheme(e.matches ? "dark" : "light"));

坑：matchMedia 返回的是活对象——状态变了要靠 change 事件，别缓存 matches 布尔值；断点字符串写错不报错只返回 false，上线前用 console.log(mql.media) 核对。

25.10.5 无窗口渲染与压缩流：OffscreenCanvas / CompressionStream ​

js
// 主线程之外压缩大 JSON(Chrome/Edge/Firefox/Safari 16.4+)
const cs = new CompressionStream("gzip");
const stream = new Blob([json]).stream().pipeThrough(cs);
const gz = await new Response(stream).arrayBuffer();

坑：OffscreenCanvas 的 2D 上下文能力是宿主子集（无 DOM 交互），Worker 里拿不到 canvas 元素只能用 transferControlToOffscreen 移交；CompressionStream 产出是流，小数据直接用，注意它不做分块缓存的内存管理，超大文件要分片。

25.10.6 二进制与编码：Blob / File / TextEncoder / objectURL ​

js
// 编码与字节长度：TextEncoder 只有 UTF-8 一种
const bytes = new TextEncoder().encode("中文 hi");
bytes.length; // 7 —— 字节数！字符串的 length 是 4
new TextDecoder("utf-8").decode(bytes); // "中文 hi"

// 浏览器侧文件下载三件套
const blob = new Blob([JSON.stringify(data)], { type: "application/json" });
const url = URL.createObjectURL(blob); // blob: 伪协议地址，指向内存中的数据
const a = document.createElement("a");
a.href = url;
a.download = "data.json";
a.click();
setTimeout(() => URL.revokeObjectURL(url), 1000); // 必须回收，且要延迟

坑：encode(...).length 是字节数不是字符数——中文 UTF-8 每字 3 字节，按它切包/截断会把多字节字符腰斩出乱码，字符级操作先过 Array.from（按码点拆）；createObjectURL 每次调用都新建引用，不 revoke 就是内存泄漏（SPA 长驻页面越用越卡的隐形来源）；但下载发起后同步 revoke 等于把资源抽走，部分浏览器会拿到空文件——等一轮事件循环再回收（详见 19 册避坑清单的「下载三坑」）；跨源 a.href 上 download 属性被忽略（变成导航打开），真下载要服务端 Content-Disposition: attachment 或先 fetch 成同源 Blob。

25.10.7 安全随机与唯一 ID：crypto.randomUUID / getRandomValues ​

js
crypto.randomUUID(); // RFC 4122 v4 UUID，"xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx"
crypto.getRandomValues(new Uint8Array(16)); // 填充式：写进传入的 TypedArray 并返回它

坑：Math.random() 是伪随机，不可用于 token/密钥/防重放等安全场景，crypto.* 才有密码学强度；randomUUID 仅安全上下文可用（HTTPS 或 localhost），HTTP 内网降级为 getRandomValues 手拼 v4（置位 version/variant 两位）；getRandomValues 是「填充传入数组」不是「返回新数组」，且单次上限 65536 字节，大数组分批；先 isSecureContext 检测再选用，与剪贴板同一套降级三板斧。

25.10.8 滚动定位与可见性：scrollIntoView / checkVisibility ​

js
// sticky 头会盖住目标：偏移交给 CSS scroll-margin-top: 64px，JS 零计算
target.scrollIntoView({ behavior: "smooth", block: "start" });
// 真可见性判断（display/visibility/opacity 一次查全，Baseline 2023）
el.checkVisibility({ checkVisibilityCSS: true, checkOpacity: true });

坑：定位偏移交给 CSS scroll-margin-* 而不是 JS 里减常量——sticky 头高度一变 JS 全废；scrollIntoView 滚的是最近可滚祖先，弹层/嵌套容器里可能滚错宿主，滚动链复杂时先 getComputedStyle 确认；offsetParent !== null 这类老式可见性判断在 position: fixed 下失真，checkVisibility 补齐了它，但它不查「被遮挡/滚出视口」——那是 IntersectionObserver 的活，别硬塞。

25.10.9 自测题 ​

22. 【进阶】为什么移动端监听页面「关闭/切后台」要用 visibilitychange + sendBeacon，而不是 unload + XHR？

iOS/移动浏览器切后台不触发 unload（且 unload 在 bfcache 场景被废弃），页面直接被杀，同步 XHR 来不及发。visibilitychange 的 hidden 是最后的可靠时机，sendBeacon 由浏览器保证「页面死了也把请求发出去」，且不阻塞卸载。大数据用 fetch + keepalive 兜底。

23. 【挑战】复制按钮在 HTTPS 生产环境正常，在内网 HTTP 测试环境失效，给出完整的降级链路设计。

检测 'clipboard' in navigator 且 isSecureContext：满足则走 navigator.clipboard.writeText（用户手势内调用）；不满足降级 document.execCommand("copy")（创建临时 textarea、选中、执行、移除）；两者都失败提示手动复制并把文本放进可选中区域。关键点：两条路径都必须在点击手势调用栈内同步发起；把检测函数模块级缓存,并在 UI 上对降级用户隐藏「已复制」的误导性提示。

24. 【进阶】下载按钮点击后「同步 revokeObjectURL」偶发拿到空文件，为什么？如何设计回收时机？

click() 触发的下载是浏览器异步读取 blob URL 的内容，同步 revoke 等于在它读取前把内存数据标记回收。回收时机：setTimeout(revoke, 1000) 等一轮事件循环即可（Blob 在磁盘落盘或网络请求发出后就不再依赖 URL）；SPA 里更稳的做法是把「创建 URL → 触发 → 延迟回收」封装成单个 downloadBlob 工具，杜绝调用方漏 revoke 造成的内存泄漏。跨源链接还要注意 download 属性失效的问题，先 fetch 成同源 Blob 再走同一工具。

25. 【挑战】防重放 token 生成：为什么不能用 Math.random？内网 HTTP 环境 randomUUID 不存在怎么办？

Math.random 是 xorshift 类伪随机，内部状态可被连续输出反推，安全敏感场景（token/密钥/幂等键碰撞攻击）必须用 CSPRNG：crypto.getRandomValues 或 crypto.randomUUID。HTTP 环境 randomUUID 不存在：先 isSecureContext 检测，降级为 getRandomValues(new Uint8Array(16)) 手拼 v4——把第 7 字节高 4 位置为 0x40（version）、第 9 字节高 2 位置为 0b10（variant），再用 hex 拼格式。两分支都要写单测（Node 18+ 两个 API 都是全局，npx tsx 可直接跑）。
