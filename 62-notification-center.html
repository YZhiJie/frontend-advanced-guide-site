62.1 通知模型：通知、待办与公告的边界 ​

概念解析 ​

B 端「消息」是三个不同物种，混在一张表里是通知中心腐烂的起点：

物种语义生命周期已读模型典型例子
通知「发生了某事」，告知性质读后即归档，有保留期读/未读二态「你的报销单已审批通过」
待办「需要你处理某事」，行动性质由业务状态驱动消亡，不是读掉的完成/未完成，展示在待办列表「有一笔报销单等你审批」
公告面向全员/分组的广播发布-下线，全员可见每人独立的已读关系表「系统本周日凌晨维护」

三条边界纪律：

  1. 待办的消亡由业务决定：审批单被处理后待办自动消失，用户「已读」不等于「完成」。把待办当通知做，会出现「点了已读但事情没办」的管理漏洞；把通知当待办做，会出现「读完还挂在那里逼用户点完成」的体验灾难。
  2. 公告的已读是关系表不是字段：公告本身没有 read 字段，已读状态在「公告 × 用户」关系上。新用户注册后不该看到三年前的公告——公告要有生效窗口与目标人群。
  3. 跳转回执与已读回执是两件事：点了通知跳转到业务页，是否标已读要看产品语义——「点进去就算读」会掩盖用户没看完的情况，「手动点已读」则多一步操作。主流做法是跳转即读 + 提供「标记未读」回退。

典型应用场景 ​

  • 审批系统：待办列表来自流程引擎（42 册），通知来自审批结果事件，两者分开展示；
  • SaaS 管理台：公告按租户/角色定向投放（61 册），已读关系按用户记录；
  • 协作工具：@提及（mention）单独成类，红点样式与普通数字未读区分。

最佳实践 ​

  • ✅ 建模时先问「这条消息的消亡条件是什么」——回答「用户读完」的是通知，回答「业务完成」的是待办；
  • ✅ 分类维度（system/todo/announcement/mention）在未读归约与列表筛选中保持一致，一处分类处处复用；
  • ❌ 不要在通知表里加 status: completed 字段模拟待办——待办状态必须与业务实体同源，否则状态漂移永远对不齐。

62.2 通道选型与降级链 ​

概念解析 ​

通知触达的三种通道，按实时性与成本排序：

通道实时性服务端成本适用
WebSocket毫秒级长连接占用高强实时（协同、IM 已共用连接时复用，见 39 册）
SSE秒级低于 WS（单向 HTTP）只需要服务端推、不需要客户端发的通知场景
轮询分钟级无连接态，QPS 可控弱实时、通知量少、或作为兜底

降级链设计：WS → SSE → 轮询，检测运行环境能力逐级降级。三个工程细节：

  1. 轮询也要讲策略：页面可见性（document.hidden）为 true 时暂停轮询；用户停留在通知列表页时轮询加密（30s → 10s）；连续 N 次空拉后指数退避。无脑定时轮询是移动端电量与服务器 QPS 的双重杀手。
  2. SSE 是被低估的选项：通知是天然单向流（服务端 → 客户端），SSE 自带断线重连与 Last-Event-ID 续传，比 WS 轻、比轮询实时。只在需要双向通信时才必须 WS。
  3. 降级不是一次性判定：网络环境变化（公司内网拦 WS）、连接持续失败时运行期降级；恢复后允许升回。通道状态机要有「探测 → 稳定 → 降级 → 恢复探测」四态，而不是连不上就永远轮询。

完整代码示例 ​

typescript
// 文件: examples/62-02-notification-channel.ts（核心节选）
function selectChannel(env: ChannelEnv): ChannelKind {
  if (env.wsAvailable) return "websocket";
  if (env.sseAvailable) return "sse";
  return "polling"; // 兜底,万物皆可轮询
}
// 轮询自适应：页面隐藏=暂停；停在列表页=加密
function pollingInterval(page: "list" | "other", hidden: boolean): number {
  if (hidden) return 0;
  return page === "list" ? 10_000 : 30_000;
}

运行方式：npx tsx examples/62-02-notification-channel.ts（降级链、轮询自适应、推拉去重、断线补偿，共 12 组硬断言）。

最佳实践 ​

  • ✅ 已有 IM/协同 WS 连接时通知通道直接复用，一个页面多条长连接是资源浪费（39 册连接治理）；
  • ✅ 通道降级与恢复要有监控埋点（59 册），线上 WS 连接成功率是基础设施健康度的晴雨表；
  • ⚠️ 企业内网/代理环境常拦 WS 升级请求，SSE 也走长连接可能被掐——轮询兜底必须永远可用；
  • ❌ 不要为「少 1 秒延迟」在纯通知场景上 WS——连接成本与运维复杂度换不来对等的用户价值。

62.3 未读数归约与已读回执 ​

概念解析 ​

未读数是通知中心最容易出 bug 的数字。它的本质是归约：总数 = Σ 各分类未读，分类数 = Σ 该分类下未读条目。难点在三个一致性：

  1. 幂等回执：用户双击、网络重试、多端同步都会让同一条已读回执到达多次。前端维护 readIds 集合，重复回执直接忽略——已读操作天然幂等，扣减计数不天然幂等，必须把前者转成后者。
  2. 乐观扣减与服务端对账：点已读后本地立即 -1（不等接口返回，否则有延迟感），后台发回执；若失败要回滚 +1。多端场景下他端的已读会改变真实未读数，所以每次拉列表时服务端返回权威计数，本地以对账方式重置——本地计数永远是预测值，服务端计数才是事实。
  3. 下限钳制：对账后计数归零，而推送通道可能迟到一条「对账前发出」的新通知，其已读回执会造成 -1。所有扣减操作钳制下界为 0，负数未读数比错误的正数更难看。

Badge 展示层也有自己的规则：超过 99 显示 99+（三位数会撑破布局）；mention 类用红点而非数字（@我的语义是「需要看一眼」而不是「有 N 条待处理」）；0 时不显示 Badge 而非显示 0。

完整代码示例 ​

typescript
// 文件: examples/62-01-unread-badge.ts（核心节选）
class UnreadReducer {
  private byCategory = new Map<Category, number>();
  private readIds = new Set<string>(); // 已读回执幂等集合

  markRead(n: Notification): boolean {
    if (this.readIds.has(n.id)) return false; // 重复回执忽略
    this.readIds.add(n.id);
    const cur = this.byCategory.get(n.category) ?? 0;
    this.byCategory.set(n.category, Math.max(0, cur - 1)); // 下限钳制
    return true;
  }

  // 本地是预测,服务端是事实:拉列表时以权威计数重置
  reconcile(serverCounts: Record<Category, number>) { /* ... */ }
}

运行方式：npx tsx examples/62-01-unread-badge.ts（归约、幂等回执、分类全清、对账、下限钳制、Badge 截断，共 9 组硬断言）。

最佳实践 ​

  • ✅ 多标签页未读数同步走 BroadcastChannel（18 册），A 标签已读后 B 标签的 Badge 立即更新；
  • ✅ 回执接口做服务端幂等（以 userId + noticeId 为唯一键），前端幂等是体验优化，服务端幂等是数据正确性；
  • ⚠️ 「全部已读」按钮要确认弹窗并传分类范围——误触全清待办类会掩盖未处理的审批；
  • ❌ 不要让前端通过「count = 总数 - 已读数」现算未读数——千万级通知下这是数据库灾难，未读数必须是服务端预计算字段。

62.4 列表工程：游标分页与推拉合并 ​

概念解析 ​

通知列表的流式特性决定了不能用页码分页：用户翻第 2 页时第 1 页头部插入了新通知，页码整体错位，第 2 页会重复出现第 1 页末尾的条目。标准解法是游标分页（cursor-based）：每页返回末尾条目的游标（通常是时间戳或自增 ID），下一页请求带 cursor=xxx 取该游标之前的数据，插入新通知不影响已翻页的位置（39 册 IM 消息同理）。

列表数据有两个来源：初始加载与翻页的「拉」，实时通道的「推」。两路数据必然交汇——推送到达的通知可能已在拉取的页里（重连补偿时尤其常见）。合并的唯一正确姿势是以 id 为键的唯一索引（Map<id, Notice>），两路写入同一索引，天然去重；已存在 id 的推送视为「状态更新」（可能是他端已读同步），不视为新增。

断线重连的缺口补偿：记录本地最新一条的时间戳 localNewestTs，重连后请求 since=localNewestTs 的增量，补入缺口。这个设计与 39 册 IM 的 seq 游标、56 册离线同步的幂等重放是同一个思想：流式数据的可靠性 = 游标 + 幂等 + 补偿。

完整代码示例 ​

typescript
// 文件: examples/62-02-notification-channel.ts（核心节选）
class NoticeFeed {
  private byId = new Map<string, Notice>(); // 推拉两路共用的唯一索引
  private cursor: number | null = null;

  ingestPage(page: Notice[]) {
    for (const n of page) this.byId.set(n.id, n);
    // 游标 = 当前最旧一条的 ts,翻页请求带它取更早的数据
  }
  ingestPush(n: Notice): boolean {
    const existed = this.byId.has(n.id);
    this.byId.set(n.id, n); // 存在=状态更新,不存在=新增
    return !existed;
  }
  // 断线补偿：只补 ts > 本地最新 的缺口
  catchup(latestServer: Notice[]): number { /* ... */ }
}

运行方式：npx tsx examples/62-02-notification-channel.ts

最佳实践 ​

  • ✅ 游标用服务端时间戳而非客户端时间——多设备时钟不齐会让游标错乱（32 册时钟偏差）；
  • ✅ 列表项点击跳转业务页后返回，列表位置与已读状态都要保持（57 册 keep-alive/缓存键）；
  • ⚠️ 通知要有 TTL 与归档策略：无限增长的列表既拖垮查询也让「全部已读」变成危险操作；
  • ❌ 不要把推送通道当数据源——推送是「提醒有变化」，数据永远以拉取为准；推送丢包是必然的，补偿拉取是兜底。

62.5 自测题 ​

1. 【基础】通知和待办的本质区别是什么？混用会带来什么问题？

消亡条件不同：通知被「读完」消亡，待办被「业务完成」消亡。混用的两个典型事故：把待办当通知做，用户点了已读但审批没处理，事情被掩盖；把通知当待办做，用户读完告知消息还被要求点「完成」，体验灾难。建模时先问「这条消息什么时候消失」——回答「用户读完」的是通知，回答「业务闭环」的是待办。待办状态必须与业务实体同源（如审批单状态），不能在消息表里自建 status 字段，否则两边状态永远漂移。

2. 【基础】为什么通知场景下 SSE 往往比 WebSocket 更合适？什么时候必须用 WS？

通知是天然的单向流（服务端→客户端），SSE 恰好只做单向：它基于普通 HTTP、自带断线重连和 Last-Event-ID 续传、服务端实现是长响应而非连接态升级，成本低于 WS。必须用 WS 的场景只有两类：需要客户端上行（如已读回执想走同一通道实时确认），或页面已有 IM/协同的 WS 连接可直接复用（多开一条 SSE 不如复用）。纯通知推送上 WS 是用连接成本换不来价值的过度设计。

3. 【基础】已读回执为什么需要前端幂等？「已读是天然幂等操作」这句话哪里不严谨？

不严谨之处在于：「把 id=X 标为已读」这个状态写操作天然幂等（写多次结果一样），但「未读数 -1」这个计数操作不幂等（执行多次扣多次）。用户双击、网络重试、多端同步都会让回执重复到达，如果每次到达都扣减计数，未读数会被扣成负数。前端维护 readIds 集合，重复 id 的回执直接忽略，就是把天然幂等的状态语义转换成不幂等的计数语义时的标准适配层。扣减还要钳制下界为 0，防对账与迟到推送的时序冲突。

4. 【进阶】通知列表为什么不能页码分页？游标分页的游标应该用什么值，为什么不能用客户端时间戳？

流式列表头部不断变化：用户翻第 2 页前，第 1 页顶部插入新通知会使所有页码整体后移，第 2 页重复出现第 1 页末尾的条目（或漏掉条目）。游标分页以「当前最旧一条的标识」为锚点请求更早的数据，头部插入不影响已翻页位置。游标必须用服务端时间戳或自增 ID：多设备客户端时钟不齐，用客户端时间会出现在 A 设备翻页正常、B 设备游标落到错误位置的问题；且客户端时间可被篡改，服务端游标是可信锚点。

5. 【进阶】「本地未读数是预测值，服务端是事实」——这个架构原则推导出哪几个具体设计？

三个设计：① 乐观扣减——点已读本地立即 -1 不等接口，保证手感；失败回滚 +1。② 权威对账——每次拉列表时服务端返回各分类权威计数，本地直接重置，不与服务端争辩（他端已读、管理端删除本地无从知晓）。③ 下限钳制——对账归零后，迟到推送的已读回执会造成 -1，所有扣减 Math.max(0, n-1)。推论：永远不要让用户看到负数未读，也永远不要为了「数字绝对准」牺牲点击响应速度。

6. 【进阶】多标签页场景下，A 标签页点了已读，B 标签页的 Badge 和列表如何同步？

同步通道用 BroadcastChannel（18 册）：A 标签已读成功后广播 { type: 'notice-read', id }，B 标签收到后更新本地归约器与列表项状态。三个细节：① 广播方自身不处理自己发的消息（channel 不回环，但代码上仍要防）；② B 标签若在通知列表页停留，收到广播只做状态更新不打断滚动位置；③ 跨标签页本质是「多端同步」的局部版，服务端仍是事实源——下次任一标签拉取时权威对账会修正一切广播遗漏。Safari 老版本无 BroadcastChannel 时降级 localStorage storage 事件。

7. 【挑战】设计通知中心的服务端推送与前端补偿协同方案，要求：推送丢包率 5% 时用户无感知，断网 10 分钟后重连不漏消息。

设计四层：① 推送层——WS/SSE 推送的是「通知到达事件」（带 id + ts），不承载完整数据，丢了不致命；② 游标层——前端持久化 localNewestTs，每条推送到达即更新，游标是补拉锚点；③ 补偿层——WS 重连成功、页面从隐藏变可见、轮询周期到达，三个时机都触发 since=localNewestTs 增量拉取，推拉共用 id 索引去重；④ 对账层——每次拉取返回权威未读数重置本地。推送丢包由补偿层兜住（用户下次可见性切换即补拉），断网 10 分钟由游标补漏，全程无感知的关键是「推送是提醒、拉取是数据」的定位分离。

8. 【挑战】某 SaaS 的通知中心上线后用户投诉「未读数总是对不上」，列出排查路径。

按可能性排序排查：① 多端一致性——用户是否多设备/多标签登录，他端已读本端未对账？查 reconcile 逻辑与触发时机；② 幂等漏洞——回执是否重复扣减，readIds 集合是否在刷新后丢失（应随会话重建但计数应从服务端重新 hydrate）；③ 分类口径——Badge 显示的总数是否含公告/待办，用户感知的「对不上」常是分类口径与视觉不一致；④ 推拉重复——推送到达未走 id 索引去重，同一通知计了两次；⑤ 服务端口径——未读数是否预计算字段，是否存在通知已删但未读数未减的漂移；⑥ 时序——对账与迟到推送的竞态是否产生负数钳制后的显示跳变。每一段都要有埋点日志（59 册），未读数这种「用户肉眼可验」的数字是全链路正确性的试金石。
