IM 的所有复杂度都来自一个事实：网络不可靠，而用户要求消息必达、有序、多端一致。HTTP 请求-响应模型可以「失败就重试」，IM 的长连接推送做不到——推送会丢、会乱序、会重复。所以 IM 前端的核心不是「发消息收消息」，而是围绕一条消息建立起可确认、可重发、可去重、可补拉的完整协议。

39.1 消息模型：状态机与 ID 设计 ​

39.1.1 概念解析 ​

一条消息的一生是五态状态机：

sending → sent → delivered → read
   ↘ failed（超时未 ACK，可重发回 sending）

状态只许前进（failed 例外），read → delivered 这种回退直接拒绝——渲染层才能放心根据状态画图标（转圈/单勾/双勾/已读）。

两个 ID 的分工是本节核心：

ID生成方时机用途
clientId客户端发送前界面占位、重发去重、端内定位
serverId + seq服务端ACK 时全局排序、幂等依据、会话内单调递增

seq 是会话内的单调递增序号，它比时间戳可靠得多——两台设备时钟不同步时，时间戳排序必然错乱，seq 不会。

39.1.2 核心代码 ​

ts
// 文件: examples/39-01-message-model.ts
export type MsgStatus = "sending" | "sent" | "delivered" | "read" | "failed";

/** 状态推进只允许前进（failed 除外，可回 sending 重发） */
export function transition(msg: Message, next: MsgStatus): Message | null;

/** 服务端确认：回填 serverId + seq，状态推进到 sent */
export function ackFromServer(msg: Message, serverId: string, seq: number): Message;

/** 渲染排序：未确认消息排尾部，已确认按 seq */
export function sortForRender(msgs: readonly Message[]): Message[];

运行方式：npx tsx examples/39-01-message-model.ts。

39.1.3 应用实践 ​

  • clientId 用 uuid v4：不要用自增——多端生成会撞、重装会重置。
  • 乐观渲染：消息发出立刻上屏（sending 态），ACK 后替换状态——用户感知延迟从 RTT 降为 0。
  • 排序只认 seq：时间戳只用于展示（「10:32」），绝不用作排序依据。

39.2 可靠投递：ACK / 超时重发 / 幂等去重 ​

39.2.1 概念解析 ​

可靠投递三件套，缺一不可：

  1. ACK：客户端发出后启动计时器，收到服务端确认才停。没有 ACK，「发没发出去」就只是猜测；
  2. 超时重发：超时未 ACK 重发，clientId 保持不变——这是整套机制的枢纽：服务端看到同一个 clientId，知道是重发不是新消息；
  3. 幂等去重：服务端按 clientId 去重（同一 clientId 只产生一条消息、返回同一份 ACK）；接收端同样按 clientId 去重，投递层重复也不至于显示两条。

少了幂等去重的重发是灾难：用户网络抖动一下，对方收到三条「在吗」。

39.2.2 核心代码 ​

ts
// 文件: examples/39-02-reliable-delivery.ts
/** 服务端：收消息 → 幂等去重 → 回 ACK（同 clientId 返回同一确认） */
export class Server {
    private seen = new Map<string, { serverId: string; seq: number }>();
    receive(clientId: string, content: string, wire: Wire): { serverId: string; seq: number } | null;
}

/** 客户端发送（带重发）：最多 maxAttempts 次，最终未 ACK 则 failed */
export function sendWithRetry(server, clientId, content, wire, maxAttempts = 3):
    { status: "sent" | "failed"; attempts: SendAttempt[]; serverId?: string };

运行方式：npx tsx examples/39-02-reliable-delivery.ts。

39.2.3 应用实践 ​

  • 指数退避：重发间隔 1s → 2s → 4s（封顶 30s），避免弱网下的请求风暴。
  • 重发与重连联动：连接恢复时优先补发 failed 队列，而不是等各自的计时器。
  • 幂等要兜到存储层：应用层 Map 去重之外，clientId 加数据库唯一索引——服务重启也不破防。

39.3 会话列表与未读数 ​

39.3.1 概念解析 ​

会话列表是 IM 首页，本质是一个事件归约器：列表状态 = fold(事件流)。消息、打开会话、已读回执都是事件，归约器消费事件产出新状态。这个模型的价值：可重放（崩溃恢复 = 重放事件）、可同步（多端各自归约同一份事件流）。

未读数的两条铁律：

  1. 只有「别人发的」才累计：自己发消息把未读清零是最经典的 bug（自己给自己发条消息，红点全消）；
  2. 清零时机 = 进入会话且窗口可见：只「点开」不可见（切后台）不该清零，所以清零由 open-conv + visibility 判定共同触发，服务端补发 read-ack 同步到其他端。

排序规则：置顶 > 最后消息时间倒序。免打扰不改变排序与未读计数，只影响通知形态（角标变灰、不弹横幅）。

39.3.2 核心代码 ​

ts
// 文件: examples/39-03-conversation-list.ts
export type IncomingEvent =
    | { type: "message" | "open-conv" | "read-ack" | "send"; convId: string; from?: string; at: number; device?: string };

/** 会话事件归约器：列表状态 = fold(事件流)，可重放、可多端同步 */
export function reduceConvList(state: Map<string, ConvMeta>, ev: IncomingEvent): Map<string, ConvMeta>;

/** 列表排序：置顶 > 最后消息时间倒序 */
export function sortConvs(convs: readonly ConvMeta[]): ConvMeta[];

运行方式：npx tsx examples/39-03-conversation-list.ts。

39.3.3 应用实践 ​

  • 列表状态放 store，不散在组件：多端同步、崩溃恢复都依赖「状态可从事件流重建」。
  • lastMsgAt 用服务端时间：客户端时钟漂移会让刚发完消息的会话沉底。
  • read-ack 用 min 语义防互踩：多端并发已读时，取最小的已读位置，迟到的事件不能把已读回退。

39.4 多端同步与离线消息：seq 游标 ​

39.4.1 概念解析 ​

手机和电脑同时在线，消息必须两端一致。方案是推拉结合：

  • 推送（WebSocket 实时下发）解决「在线时的实时性」——但推送可能丢、可能乱序；
  • 拉取（sync 增量接口）解决「离线/掉线期间的完整性」——每个端持久化一个游标（已同步到的最大 seq），上线后带游标补拉 seq > cursor 的消息。

推送丢了一条怎么办？靠空洞检测：时间线上出现 seq 不连续（cursor=2 却直接收到 5），立刻触发 sync 补拉。接收端对重复推送按 seq 去重，乱序到达靠最终排序兜底。

39.4.2 核心代码 ​

ts
// 文件: examples/39-04-multi-device-sync.ts
export class Device {
    cursor = 0;                          // 已同步到的最大 seq（持久化）
    /** 处理推送：dup 去重 / hole 空洞触发补拉 */
    onPush(msg: Msg): "accepted" | "dup" | "hole";
    /** 重连后补拉：拉到本地最大 seq 之后的全部消息 */
    syncFrom(server: ConvServer): Msg[];
    isContiguous(): boolean;             // 时间线连续性自检
}

运行方式：npx tsx examples/39-04-multi-device-sync.ts。

39.4.3 应用实践 ​

  • 游标持久化在本地：崩溃/重装后从服务端全量拉一次，然后游标接管。
  • 补拉批量返回：sync 接口按 seq 范围拉取（上限 500 条分页），不要一条一请求。
  • 连续性自检进监控：isContiguous() 为 false 时上报——时间线断裂是事故级缺陷，必须可观测。

39.5 群聊消息扩散：写扩散 vs 读扩散 ​

39.5.1 概念解析 ​

群消息如何到达每个成员？两条路线、一组权衡：

写扩散（fan-out on write）读扩散（fan-out on read）
写入一条消息 × 每个成员收件箱群时间线只写一份
读取只查自己的收件箱（1 次查询）逐群拉增量（N 群 = N 次查询）
已读收件箱级，天然多端同步每端各自维护游标
适用小群、职场 IM万人群、直播弹幕

成本模型（每小时写入量）：

  • 写扩散：消息速率 × 群成员数——5000 人群每小时 600 条 = 300 万次写；
  • 读扩散：消息速率 × 1——与群规模无关。

业界主流是混合：≤ 阈值（如 500 人）的群写扩散（读体验好），超大群读扩散（写成本可控）。决策依据就是这两个函数的交点。

39.5.2 核心代码 ​

ts
// 文件: examples/39-05-fanout-strategy.ts
export const writeDiffusion: Strategy = {
    name: "写扩散",
    writeCostPerMsg: (members) => members,
    readCostPerOpen: () => 1,
};

export const readDiffusion: Strategy = {
    name: "读扩散",
    writeCostPerMsg: () => 1,
    readCostPerOpen: (convs, newMsgs) => convs * newMsgs,
};

/** 混合策略：≤ 阈值走写扩散，超过走读扩散 */
export function hybrid(threshold: number): Strategy;

/** 决策：给定群画像，比较各策略每小时写入成本 */
export function decide(conv: Conv, candidates: readonly Strategy[]): { picked: string; costs: [...] };

运行方式：npx tsx examples/39-05-fanout-strategy.ts。

39.5.3 应用实践 ​

  • 前端感知差异在已读：写扩散的已读是收件箱级（天然多端同步）；读扩散的已读是每端游标（需 39.4 的同步机制显式上报）。
  • 超大群的推送要另设计：万人群的 WebSocket 广播配合扇出中间层（逐级分桶），前端只管消费推送 + 游标补拉，策略差异被服务端屏蔽。
  • 消息速率也是变量：同一个群，白天闲聊与活动峰值是两种画像，决策要按峰值算。

39.6 前端渲染与连接治理 ​

39.6.1 长列表渲染 ​

会话消息是「无限增长的流」，渲染三板斧：

  1. 虚拟滚动：视口外消息不渲染 DOM（几百条消息的会话全量渲染必卡）；
  2. 分页加载：向上滚动加载历史，按 seq 范围拉取，锚点定位防跳动；
  3. 图片/文件懒加载：消息流里的富媒体进入视口才加载，缩略图先行。

新消息插入时的滚动策略：用户在底部 → 追加并跟随；用户在翻历史 → 只出「有新消息」悬浮条，不抢滚动位置。

39.6.2 连接治理 ​

  1. 心跳：30s 一次 ping，2 次超时判定连接死亡（Websocket 的 close 事件在半开连接上可能永远不触发）；
  2. 指数退避重连：1s → 2s → 4s → … 封顶 60s，加随机抖动防雷群；
  3. 重连后统一动作：重发 failed 队列 → 全会话 sync 补拉 → 刷新会话列表——三步固定流程，不散在业务代码里；
  4. 多标签页共享连接：同域多 Tab 用 BroadcastChannel 或 SharedWorker 复用一条 WebSocket（第 18 册），避免 N 个 Tab N 条连接挤爆服务端配额。

39.6.3 与既有章节的衔接 ​

WebSocket 基础（握手、帧、心跳）在第六部分；SSE 与流式渲染见第 26/21 册（AI 对话场景同构：流式 token 也是「推送 + seq/offset 续传」的协议问题）。

  1. 为什么重发时必须保持 clientId 不变？换成每次生成新 ID 会怎样？
查看答案

服务端幂等去重依赖 clientId：同一个 ID 只产生一条消息。若每次重发换新 ID，服务端会当成新消息，对方在弱网下收到 N 条重复消息。clientId 唯一后，服务端首次收到即建幂等记录，重发只返回同一份 ACK。

  1. 消息排序为什么用 seq 而不用时间戳？
查看答案

客户端时钟不可信（可漂移、可被手动改），时间戳排序会乱序。seq 由服务端在会话内单调递增分配，是全序依据；时间戳只用于展示。

  1. 用户给自己发消息后所有会话未读数清零，最可能的原因是什么？
查看答案

未读数归约逻辑把「收到 message 事件」一律 +1、把「发送 message 事件」一律清零（或把 send 事件也当成 message 处理且没过滤 from）。正确规则：只有 from !== me 的 message 才累计未读；send 事件只更新 lastMsgAt 不动 unread。

  1. 推送通道丢了一条消息，接收端如何发现并恢复？
查看答案

空洞检测：每条推送带 seq，接收端维护时间线与游标。收到 seq 与本地游标不连续（跳号）即触发 sync 补拉（带游标拉增量），拉回后按 seq 排序去重合并。推送只保实时性，完整性靠拉取兜底。

  1. 一个 200 人的公司群和一个 10 万人的直播弹幕群，扩散策略怎么选？前端代码有差异吗？
查看答案

200 人群选写扩散：写入量 = 200/条，读侧一次收件箱查询，已读天然多端同步。10 万人群选读扩散：写扩散一条消息 10 万次写不可行。前端代码基本无差异——前端只消费「会话时间线 + seq 游标 + 推送」，策略差异被服务端屏蔽；差别在读扩散场景下已读游标要显式上报同步。
