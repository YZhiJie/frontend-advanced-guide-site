78.1 选型的第一性原理：约束、证据与可逆性 ​

概念解析 ​

选型不是「找到最强的技术」，而是在约束下找到最不坏、且能退出的技术。大多数失败选型不是选错了技术，而是三件事没做：

  1. 没澄清需求：把「要一个图表库」当成需求，真实需求是「5 万个数据点的折线图 + 钻取 + 导出 + 低端机不卡」；需求不清，候选清单一定跑偏。
  2. 没区分约束与偏好：个人熟悉度、社区热度、技术新奇感是偏好；合规、端支持、性能预算、团队存量、交付窗口是约束。偏好可以加权，约束必须一票否决。
  3. 没算退出成本：只算「接进来要几天」，没算「三年后换掉要几个月」。选型的真实成本 = 引入成本 + 迁移成本 + 认知成本 + 机会成本。

选型三问（任何候选都要回答）：

问题追问典型反例
不引入会怎样？原生 API、已有依赖、自研 20 行能不能解决？为一个日期格式化引入 3 个库
最坏情况是什么？停维护、许可证收紧、核心维护者离开、框架大版本不兼容选了一个单人维护的闭源编辑器内核
什么条件会让结论反转？哪个假设一变，冠军就易主？「以后可能要 SSR」直接选了最重的方案

约束分层建议写进团队选型规范：

层级内容处理方式
硬约束许可证可用性、信创/国密要求、目标浏览器与端、性能预算、上线窗口、团队存量技术栈一票否决，不参与打分
软约束生态成熟度、类型体验、包体、文档质量、招聘供给、维护活跃度加权打分，权重来自当下项目
个人偏好熟悉度、审美、社区热度、技术新奇感只能作为证据的一部分，不能单独决定

七步决策流程：

  1. 需求澄清：把形容词换成可测指标（数据量、并发、设备档位、交付日期、合规等级）；
  2. 硬约束筛选：先砍掉不合格的，避免在后面用分数「救」一个根本不能用的方案；
  3. 候选 2~4 个：必须包含「原生 / 自研 / 已有依赖」基线，否则容易误以为「只有引库一条路」；
  4. 对称打分：同一维度、同一证据标准、同一量纲；每个分数旁边写证据，禁止「A 的长板比 B 的短板」；
  5. 敏感性检查：逐个维度把权重翻倍，看冠军是否反转；易反转的维度就是评审最该挑战的假设；
  6. 限时试点（spike）：1~2 天，用 3 个真实场景（最复杂、最边角、最像线上）验证，量体积、测边界；
  7. ADR + 复审 + 退出预案：把决策、备选、反转条件、复审日期写进仓库，而不是留在聊天记录里。

可逆性比「最优」更重要。贝索斯把决策分成「双向门」与「单向门」：能低成本退回的是双向门，应该快速试；换框架、换组件库、换状态层是单向门，必须慢。判断可逆性看三个信号：

  • 第三方 API 是否只出现在适配层，还是泄漏到业务代码；
  • 数据与状态是否能导出/迁移，还是被私有格式锁死；
  • 升级是否跟得上大版本，还是已经冻结在旧版本。

ADR（Architecture Decision Record） 是选型的留痕方式。最小模板：

markdown
# ADR-0001：选择 Vue 3 + Pinia 作为中后台技术栈

## 状态
已接受（2026-10-31）· 复审日期：2027-04

## 背景与约束
- 团队 8 人，7 人有一年以上 Vue 经验；历史系统 30 万行 Vue 2；
- 交付窗口 4 个月；无 SSR/RSC 需求；需适配国产浏览器与内网部署；
- 组件库候选：Element Plus / Ant Design Vue；许可均为 MIT。

## 决策
采用 Vue 3（Composition API）+ Vite + Pinia + Element Plus；不引入 Nuxt。

## 备选与不选理由
- React 19 + Next.js：SSR 能力更强，但团队迁移与招聘成本高，当前无真实 SSR 需求；
- Angular：强规范适合大型多团队，但学习曲线与人才供给不匹配 4 个月窗口。

## 后果与反转条件
- 若 12 个月内出现强 SEO / RSC / 国际化协作需求，重新评估 Nuxt 或 Next.js；
- 若组件库升级阻塞超过 2 个迭代，触发替代方案评审；
- 退出预案：状态与请求层通过 adapter 隔离，替换预估 6 人周。

典型应用场景 ​

  • 新项目起步：硬约束少、可逆性高，适合快速试点，但要把 ADR 与退出预案一次做对；
  • 存量系统升级：先算迁移成本，再谈技术优劣；「团队存量」通常直接决定结论；
  • 合规敏感项目：政企、金融、出海，许可证与数据合规是硬约束，必须在候选阶段筛掉；
  • 多团队协作：选型要能被非作者维护，文档、类型、约定比「设计优雅」更重要。

最佳实践 ​

  • ✅ 先写约束，再写候选：约束清单没定之前，任何对比表都是「先有结论后找理由」；
  • ✅ 每个分数带证据：实测数据、官方文档、issue 记录、试点结果，禁止凭印象打分；
  • ✅ 保留「不引入」基线：原生 / 自研 / 已有依赖要和其他候选同台打分；
  • ✅ 做敏感性检查：冠军只领先 0.1 分时，要明确写出「哪个权重变化会反转」；
  • ✅ 决策落 ADR：背景、备选、后果、反转条件、复审日期，一个都不能少；
  • ⚠️ 不要用 star 数、下载量、别人都在用作为唯一证据——它们是生态信号，不是适配性证据；
  • ⚠️ 不要把「以后可能要」当成硬需求：为假想需求引入最重方案，是最常见的过度设计。

概念解析 ​

  1. 团队存量技术栈 > 框架本身差异（4.8 已给出结论）。30 万行 Vue 2 的团队换 React，收益是「理论更优」，成本是「半年交付空窗 + 全员重学 + 招聘重建」。
  2. 组件库绑定决定一半选型。Vue 项目换 React，真正的工作量不是重写页面，而是重写组件库适配、主题、权限、表格、表单、国际化（见 49.1）。
  3. 招聘与人才供给是长期成本。框架选型的隐性账单在第二年才出现：招不到人、现有成员不愿学、外包质量不可控。
  4. SSR/RSC 必须是真实需求。「以后可能要做 SEO」不足以支撑 Next.js 的复杂度；真有需求时，也要区分 SSG、ISR、RSC、边缘渲染的成本差异（见 第十三部分）。
  5. 国产生态与信创是硬约束。政企项目要核对国产浏览器/WebView、内网离线部署、国密改造（见 74.2），框架本身的「国际主流」不等于「环境可用」。

最佳实践 ​

  • ✅ 先确认「换框架」是不是真问题：很多痛点其实是状态层、组件库或构建链的问题，换框架是过度反应；
  • ✅ 框架与元框架一起选：选 React 就必须同时决定 Next.js / Remix / Vite SPA，SSR 成本在这一步产生；
  • ✅ 把组件库纳入同一张矩阵：框架与组件库是绑定决策，分开选会出现「框架合适、库不合适」的死局；
  • ✅ 写清反方风险：任何推荐都要附一条「它在什么情况下会害你」；
  • ⚠️ 不要用「前端趋势报告」替代团队约束：趋势描述的是平均项目，不是你的项目；
  • ⚠️ 不要在交付窗口内做框架迁移：迁移是单向门，应该独立立项、独立排期。

78.3 npm 库选型：从「有没有」到「该不该」 ​

概念解析 ​

找库操作步骤详解（从需求到候选入围） ​

第 0 步：先做原生与已有依赖体检。即上方「原生优先对照表」——能被平台能力或已有依赖覆盖的，直接结束，不进入下面的检索。

78.4 开源许可证：商用可用性速判 ​

概念解析 ​

开源不等于免费商用，npm 上架不等于开源。 前端尤其容易踩坑，因为：

  1. 打包即复制：把库打进 bundle 再发给浏览器，在版权法意义上就是「分发副本」，GPL 类义务会被触发；
  2. SaaS 也可能触发：AGPL-3.0 的第 13 条把「通过网络交互使用」视为触发条件，纯 SaaS 也逃不掉；
  3. 传递依赖同样受约束：你只审了直接依赖，GPL 可能藏在第 5 层；
  4. 资源另有许可：字体、图标、插画、地图数据、示例数据集，往往不跟随代码仓库的主许可证；
  5. AI 生成/复制粘贴也有许可：从 Stack Overflow 复制的代码是 CC BY-SA，可能污染你的代码库。

信息源优先级（冲突时以更权威者为准，并记录风险）：

  1. 仓库根目录的 LICENSE / LICENCE / COPYING 正文（事实来源）；
  2. package.json 的 license 字段（可能是 SEE LICENSE IN <file>，必须点进去）；
  3. npm registry 页面 / npm view <pkg> license 的元数据（可能过期）；
  4. 上游官网 FAQ / 商业授权页面；
  5. 直接向上游维护者书面确认（保留邮件/issue 记录）。

SPDX 表达式要会读：MIT OR Apache-2.0 表示二选一，选 MIT 即可；MIT AND GPL-3.0 表示两项义务都要满足，前端分发场景通常只能放弃；GPL-2.0-only WITH Classpath-exception-2.0 表示带例外条款，需按例外原文判断。不要看到「MIT」就以为整包都是 MIT——一个包可能包含多份不同许可的资源。

资源类许可单独核对：

  • 字体：SIL OFL 1.1 允许商用嵌入，但不得单独售卖字体、需保留许可、可能保留字体名；方正/汉仪等商业字体需授权（74.2 也提到这条红线）；
  • 图标：不同图标集许可差异大，有的要求署名，有的是 CC-BY-NC；
  • 插画/图片：免费图库也要看商用范围、署名要求、人物肖像权；
  • 地图/地理数据：国内地图需审图号，不能只看法务许可；
  • 示例数据/数据集：学术数据集常禁止商用或要求引用。

78.5 商用合规落地：扫描、门禁与法务留痕 ​

概念解析 ​

许可证治理如果只靠「引入时看一眼」，一定会在第 200 个依赖时失控。可落地的做法是把判定、扫描、门禁、留痕串成闭环，并与 66 册 的依赖治理共用一套流程。

第一步：能自动扫描。常用手段：

bash
# 1) 列出整棵依赖树的许可证（pnpm 原生）
pnpm licenses list --json > licenses.json

# 2) 逐包检查许可证与版权声明（license-checker-rsc 是 license-checker 的维护分支）
npx license-checker-rsc --summary --production

# 3) 生成 SBOM（CycloneDX），把许可证、版本、哈希、依赖关系一起归档
npx @cyclonedx/cyclonedx-npm --output-file sbom.cdx.json

# 4) 通用 SBOM 工具（可选，适合多语言仓库）
syft . -o cyclonedx-json > sbom.cdx.json

第二步：策略化门禁。把许可证分成三档，写进 CI：

档位许可类型门禁动作
allowMIT、ISC、BSD、Apache-2.0自动通过，保留声明

第四步：SBOM 与应急。每次发布归档一份 SBOM，出事后能 5 分钟内回答「我们有没有用这个包、什么版本、什么许可」。这与 66.4 的漏洞应急共用同一份物料清单。许可证事件同样需要响应：上游改许可、包被收购、维护者变更、商业授权条款调整，都要触发复审。

法务协作材料包（提交给法务时一次给全，避免来回）：

  1. 包名、版本、仓库地址、LICENSE 全文链接；
  2. 使用方式：直接/传递、静态打包/动态链接、是否修改；
  3. 分发形态：浏览器 bundle、桌面安装包、SaaS、仅内部；
  4. 业务必要性：替代方案、替换成本、下线影响；
  5. 已采取的措施：隔离、适配层、保留声明、NOTICE；
  6. 期望结论：可用 / 需授权 / 必须替换，以及需要的回复时限。

78.6 自测题 ​

1. 【基础】为什么说「团队存量技术栈」通常优先于框架本身的差异？

答案：框架差异影响的是「理论上限」，团队存量影响的是「交付下限」。换框架的真实成本包括页面重写、状态与请求层重构、组件库与主题重做、构建部署重来、测试基线失效、招聘与培训，通常以半年为单位；而框架之间的能力差异，在大多数业务里可以通过规范、组件库和架构分层弥补。除非现有框架触发了硬约束（如端支持、合规、性能上限），否则迁移的收益很难覆盖成本。选型应先问「不换会怎样」，再问「换哪个」。

2. 【基础】MIT 与 Apache-2.0 都能商用，关键差异是什么？

答案：两者都是宽松许可，但 Apache-2.0 多了三件事：① 明确的专利授权（以及专利报复条款），对专利敏感的业务更友好；② 若上游提供 NOTICE 文件，分发时必须保留；③ 修改过的文件需要标注修改。MIT 更短，只要求保留版权与许可声明，不包含显式专利条款。两者都允许商用、修改、再分发，也都不要求开源你的衍生代码；但都不能删除版权声明。

3. 【基础】为什么「npm 上架」不等于「开源可商用」？

答案：npm 只是分发渠道，不是许可证。一个包完全可以以 UNLICENSED 上架——这表示「保留所有权利」，默认不可商用；也可能是源码可见但非 OSI 认可的许可（SSPL、BUSL、Elastic License、CC-BY-NC），限制商业使用或托管服务。判断依据是 LICENSE 正文与 SPDX 标识，不是「能不能 npm install」，也不是「GitHub 是否公开」。

4. 【进阶】GPL 与 AGPL 的关键区别是什么？纯前端 SaaS 会不会触发？

答案：GPL 的触发点是「分发」——把衍生作品副本交给第三方；AGPL 在第 13 条额外规定「通过网络与用户交互使用」也视为触发，必须向这些用户提供对应源码。纯前端项目把库打进 bundle 发给浏览器，本身就是分发，GPL 通常会触发；SaaS 即使不分发二进制，只要用户通过网络交互使用，AGPL 也会触发。因此前端引入 GPL/AGPL 库通常按「阻断」处理，除非购买商业授权、替换，或经法务确认的隔离方案。

5. 【进阶】直接依赖是 MIT，但传递依赖里有 GPL，应该怎么处理？

答案：许可证义务看最终分发物，不看依赖层级。打包后 GPL 代码与你的代码共同构成一个分发物，传染性仍然成立。处理顺序：① 用 pnpm why 定位是哪条依赖链带进来的；② 看能否通过 overrides 换掉上游版本或改用替代包；③ 评估是否真的需要该功能，能否去掉；④ 若必须保留，走法务评审或购买商业授权；⑤ 在 SBOM 与白名单里登记结论。不能因为「不是我直接装的」就放过。

6. 【进阶】如何判断一个 npm 库「值不值得引」？给出可执行步骤。

答案：① 需求澄清：把形容词换成可测指标（数据量、设备档位、性能预算、交付时间）；② 先问原生/已有依赖/自研能不能覆盖，保留「不引入」基线；③ 选 2~4 个候选，按六维评估：需求契合度、维护治理、体积性能、类型 DX、可替换性、合规；④ 硬门槛先筛：许可不可商用、体积超预算、废弃、重复能力直接淘汰；⑤ 1~2 天试点，用 3 个真实场景验证并量体积；⑥ 写 ADR：结论、备选、失败点、退出成本、复审日期；⑦ 引入后用适配层隔离并锁版本。

7. 【挑战】业务坚持要引入一个 AGPL 的图表库，给出至少三条方案与取舍。

答案：方案一，购买商业授权：最直接，成本可预期，但要注意授权范围（版本、子公司、SaaS、再分发）与续费；方案二，替换为宽松许可的同类库（ECharts、D3、Chart.js 等）：无法律风险，但要评估功能缺口、迁移成本与性能；方案三，功能降级或服务端出图：用自研/服务端渲染生成静态图，牺牲交互性；方案四，隔离部署（独立服务/独立进程）并让法务确认边界：工程复杂度高，且 AGPL 的「网络交互」边界未必能靠进程隔离规避，不能自行拍板。推荐顺序通常是「替换 → 购买授权 → 降级 → 隔离」，并把成本、工期、风险写进 ADR。

8. 【挑战】设计一个许可证门禁与例外机制，如何避免它形同虚设？

答案：① 门禁与 lockfile 同源，每次 PR 对新增依赖做许可证 diff，deny 直接失败；② 策略分 allow/review/deny 三档，review 必须登记使用方式与责任人；③ 豁免必须有 owner、理由、退出计划和到期日，到期自动回到 deny，禁止「永久白名单」；④ 豁免审批与代码评审分离，避免引入人自己批自己；⑤ SBOM 随版本归档，季度复审上游许可变更与无使用记录的依赖；⑥ 指标化：豁免数量、平均存续时长、逾期未处理数量，纳入架构健康度；⑦ 与依赖安全门禁共用流程，避免两套白名单互相漂移。

4框架与组件库分开选框架合适但组件库不匹配，返工重做框架、组件库、元框架放进同一张矩阵
5迁移只算页面重写低估状态层、组件库、测试、招聘成本按六项成本拆解，迁移独立立项
6为 20 行代码引入一个长期依赖包体、漏洞面、升级负担全部增加原生优先，保留「不引入」基线
7只看 Bundlephobia 的单包体积忽略重复依赖、polyfill、双包实例，线上反而更大用打包分析工具看真实增量
8第三方 API 直接泄漏到业务代码替换时全站 grep，退出成本失控用 adapter 隔离，类型不外泄
9引入后不跑 pnpm why重依赖与重复版本被悄悄带进来新依赖必须检查传递依赖与体积
10把「npm 上架」当成「开源可商用」引入 UNLICENSED 或非商用许可，法律风险以 LICENSE 正文与 SPDX 标识判定
11只审直接依赖的许可证第 5 层 GPL 通过传递依赖传染扫描整棵依赖树，SBOM 归档
12认为 SaaS 不分发就与 AGPL 无关AGPL 网络交互条款直接触发SaaS 场景按 AGPL 阻断或购买授权处理
13豁免没有 owner 与到期日白名单越滚越大，门禁形同虚设豁免登记 owner、理由、退出计划与到期日
14忽略字体、图标、插画、数据集许可主许可证是 MIT，素材却是非商用资源单独核对许可，保留授权凭证
