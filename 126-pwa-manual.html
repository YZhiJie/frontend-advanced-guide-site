126.1 边界认知与可安装性前提 ​

PWA 不是「加个 manifest」 ​

PWA 的完整能力由三部分组成：Web App Manifest（身份与安装入口）、Service Worker（离线与后台能力）、安全上下文（HTTPS）。三者职责不同，缺一不可，但也不是「有 SW 就自动可安装」。

  • Manifest 决定应用名称、图标、启动地址、窗口形态与安装身份。
  • Service Worker 决定离线缓存、更新、推送、后台同步。
  • HTTPS 决定以上能力能否被浏览器授予（localhost 是开发期例外）。

可安装性判定：不同浏览器并不一致 ​

以 Chromium 系（Chrome / Edge）为例，截至 Chrome 官方 2023-12 的说明：

  • 从菜单安装：自 Chrome 108（移动端）与 Chrome 112（桌面端）起，不再强制要求 Service Worker 实现 fetch 处理。
  • 安装提示（install prompt）：仍要求存在带 fetch 处理的 Service Worker；该策略仍在演进，不能写死为永久契约。
  • 必要项仍是：HTTPS、可解析的 manifest、name 或 short_name、192 与 512 图标、start_url、display 为 standalone / fullscreen / minimal-ui 之一。

Safari 走另一套逻辑：iOS/iPadOS 没有 beforeinstallprompt，用户通过「分享 → 添加到主屏幕」完成安装；display、theme_color 等 manifest 字段只被支持子集消费，图标主要依赖 apple-touch-icon。因此不能用 Chrome 的判定代替 iOS 的验收。

结论：把「可安装」定义为「目标浏览器 + 目标入口（菜单安装 / 自定义引导 / A2HS）都能完成安装，且安装后以独立窗口启动」。最终判定以 DevTools Application > Manifest 的安装性提示、目标真机实测与第 126.9 节验收清单为准。

什么场景值得做 PWA ​

场景建议原因
高频回访的内容/工具站做安装提升回访效率，离线壳降低弱网白屏
有消息触达诉求（订单、IM、告警）做，但先确认平台Android/桌面 Web Push 可用；iOS 仅 16.4+ 且必须 A2HS
一次性营销页、活动页不做或只做轻量离线兜底缓存与更新成本高于收益，用户不会安装
强原生能力（蓝牙、文件系统、后台常驻）不把 PWA 当替代能力边界与系统集成仍弱于原生/桌面壳

最小落地检查表 ​

  • [ ] 全站 HTTPS，且 start_url、scope、manifest、SW 均同源。
  • [ ] manifest 可访问，Content-Type 为 application/manifest+json（或 application/json）。
  • [ ] start_url 落在 scope 内，id 稳定且不随查询参数变化。
  • [ ] 有 192×192 与 512×512 的 any 图标，另有 512×512 的 maskable 图标。
  • [ ] 目标浏览器能进入安装流程，安装后以独立窗口启动。
  • [ ] 断网后首屏与关键导航可用，未知路由落到离线兜底页。

字段语义与硬约束 ​

字段作用必须注意
id应用身份建议显式且稳定；改 id 等于换应用，安装记录、权限、存储都可能被视为另一个应用
name / short_name安装名称name 必填；short_name 建议 ≤ 12 字符，否则安装 UI 截断
start_url安装后启动地址必须与站点同源，且落在 scope 内；可带 ?source=pwa 做渠道归因
scope应用作用域省略时默认取 start_url 所在目录；start_url 越出 scope 会被判为外部导航
display窗口形态standalone 最常用；fullscreen 适合游戏/沉浸内容；browser 不具备安装窗口体验
display_override形态优先级链浏览器取第一个支持的项；Chromium 支持，Safari 不支持
orientation方向锁定内容站用 any；强制横屏只适合游戏/视频，移动端阅读场景慎用
theme_color状态栏/标题栏颜色需为合法 CSS 颜色；同时建议输出 <meta name="theme-color">
background_color启动闪屏底色Android 启动屏使用；与首屏背景一致可减少闪白
icons安装图标至少 192 与 512 的 any；maskable 单独一条；sizes: "any" 只用于 SVG
screenshots富安装预览form_factor 为 wide / narrow；Chrome Android 安装 UI 会消费
shortcuts长按快捷入口URL 必须同源且在 scope 内；常见入口只展示前 4 个
share_target接收系统分享action 同源且在 scope 内；POST 必须声明 enctype，接收端需在 SW 中处理
related_applications关联原生应用prefer_related_applications: true 时不能为空，否则安装入口可能被原生应用替代

图标矩阵：尺寸、用途与安全区 ​

  • 192×192 any：安装入口与主屏图标的基础尺寸，缺失会导致部分入口不出现。
  • 512×512 any：安装弹窗、应用商店物料与高分辨率屏幕使用。
  • 512×512 maskable：Android 自适应图标。图形主体应放在中心直径约为画布 80% 的安全区内，四角留白，否则被系统裁成圆形/ squircle 时会切掉内容。
  • purpose 不要写 "any maskable"：拆成两条图标更可控；混写会让浏览器按 maskable 处理，普通场景可能出现意外裁切。
  • sizes: "any" 只给 SVG：PNG/WebP 必须写具体像素；给 PNG 写 any 会被审计器判错。
  • iOS 额外输出 apple-touch-icon（180×180）：Safari 的主屏图标主要读这个链接，不保证消费 manifest 图标。
  • screenshots 不是可安装硬门槛，但影响 Chrome Android 富安装 UI 的转化；wide 与 narrow 各一张最稳。

服务方式与缓存头 ​

  • manifest 建议 Content-Type: application/manifest+json；至少保证 application/json 可解析。
  • manifest 不要长缓存：Cache-Control: no-cache 或较短 max-age，否则改名/换图标后用户长期看不到。
  • 图标可长缓存（文件名带哈希时 immutable），但换图标要换文件名，不能只覆盖同路径。
  • 具体 Nginx 写法见 53.3 HTTPS、安全头与缓存。

126.3 SW 注册与作用域 ​

注册：位置决定作用域 ​

ts
// 推荐：显式 scope + 禁用 SW 脚本的 HTTP 缓存
if ('serviceWorker' in navigator) {
  window.addEventListener('load', async () => {
    try {
      const registration = await navigator.serviceWorker.register('/sw.js', {
        scope: '/',
        updateViaCache: 'none',
      });
      console.log('SW registered:', registration.scope);
    } catch (error) {
      console.error('SW register failed:', error);
    }
  });
}

关键规则：

  • 脚本 URL 决定最大作用域：/sw.js 最大可控制 /；/app/sw.js 默认最大只能控制 /app/。
  • 想突破目录限制，需要服务端返回 Service-Worker-Allowed: /，并显式 scope；不要靠猜。
  • scope 只能比脚本允许的范围更窄，不能更宽。
  • updateViaCache: 'none' 让 SW 脚本及其 importScripts 绕过 HTTP 缓存；默认 imports 只对导入脚本生效，容易导致「发了新版但用户一直跑旧 SW」。
  • 注册时机：load 之后注册可避免和首屏资源抢带宽；但强离线诉求可以在首屏关键资源后再注册，不必盲目提前。
  • 注册失败常见原因：非 HTTPS、脚本 404、MIME 不是 JavaScript、scope 越权、SW 脚本语法错误。

生命周期与「谁在控制页面」 ​

阶段事件你可以做什么常见坑
installinginstall预缓存核心资源，失败则安装失败cache.addAll 含 404 会整体失败
installed / waiting无等待旧 SW 释放控制以为已经生效，实际还在 waiting
activatingactivate清理旧缓存、clients.claim()清理范围过大，误删其他缓存
activated无处理 fetch / message / push / sync以为 controller 一定存在
  • 首次安装：默认不会接管已经加载的页面，刷新后才受控；调用 clients.claim() 可立即接管。
  • 更新安装：旧 SW 仍在控制页面，新 SW 进入 waiting；需要 skipWaiting 或用户确认后才切换。
  • skipWaiting 的代价：新旧页面可能同时加载不同版本的 chunk，出现资源 404、样式错乱、状态不兼容。有无状态表单、长连接、编辑器时优先 prompt 更新，不要默认自动接管。
  • controllerchange 只刷新一次：用模块级布尔标记防止无限刷新；详见第 126.4 节状态机。

更新检查 ​

  • 浏览器在导航时检查 SW 更新，且通常最多每 24 小时检查一次；registration.update() 可主动触发。
  • updatefound → registration.installing → 监听 statechange；当状态为 installed 且 navigator.serviceWorker.controller 存在时，说明「新版本已就绪，等用户确认」。
  • registration.waiting.postMessage({ type: 'SKIP_WAITING' }) 是常见的确认更新通道；SW 内监听 message 后调用 self.skipWaiting()。

自毁 SW：回滚的最后一道闸 ​

当 SW 本身导致线上不可用（例如缓存策略写错、旧资源死循环），可临时发布一个「自毁 SW」：删除本应用缓存、注销自身、让页面重新导航。注意：注销不会自动删除 Cache Storage，必须显式 caches.delete()；已打开的页面可能要刷新后才彻底脱离控制。

js
// 回滚用 sw.js（仅应急，确认后尽快恢复正式 SW）
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const keys = await caches.keys();
    await Promise.all(keys.map((key) => caches.delete(key)));
    await self.registration.unregister();
    const clients = await self.clients.matchAll({ type: 'window' });
    await Promise.all(clients.map((client) => client.navigate(client.url)));
  })());
});

三条硬规则：

  1. 写请求绝不进 Cache API。Cache 只存 Request/Response，没有事务、没有冲突解决；写失败应进 IndexedDB 队列，用幂等键重放。
  2. 导航必须走 NetworkFirst + 离线兜底。全站 CacheFirst 会让发版后用户长期看到旧页面。
  3. 缓存名必须带版本前缀，且只清理自己前缀的缓存。caches.keys() 是全源共享的，误删其他应用/其他 scope 的缓存会造成难以排查的故障。

缓存键与查询参数 ​

  • 导航缓存键建议剔除 utm_*、fbclid、gclid、ref 等渠道参数，否则同一个页面会被缓存成多份。
  • 业务参数（如 ?page=2、?id=123）必须保留；不要用 ignoreSearch: true 一刀切。
  • 缓存键排序后再存储，避免 ?a=1&b=2 与 ?b=2&a=1 重复。
  • 需要区分登录态/租户的接口，必须把租户或用户维度放进缓存名或键，不能跨用户复用；参见 61 多租户 SaaS。

更新状态机：从「有新版本」到「只刷新一次」 ​

ts
// 状态：idle → checking → available → prompting → applying → applied
// 分支：available → deferred（脏表单）→ prompting
const registry = makeRegistry();
installVersion(registry, 'v1', { clientsClaim: true });

checkForUpdate(registry, 'v2');   // available：v2 进入 waiting
promptUpdate(registry, true);     // deferred：有未保存表单
resolveDeferred(registry, false); // prompting：用户保存后继续
applyUpdate(registry);            // applied：skipWaiting + controllerchange

实现要点：

  • updatefound 里拿 registration.installing，监听 statechange；只有 installed && navigator.serviceWorker.controller 才是「等待确认的更新」。
  • 用户点「更新」时 postMessage({ type: 'SKIP_WAITING' })；SW 内 self.skipWaiting()。
  • 页面监听 controllerchange，只刷新一次；用 let refreshing = false 防重。
  • 有脏表单时不要自动 skipWaiting；保存草稿或提示用户后再切换。
  • 初次安装没有 controller，不应进入更新提示流程；clientsClaim 只决定是否立即接管，不决定是否刷新。
  • autoUpdate 会强制 clientsClaim 与 skipWaiting，适合无状态页面；有表单/编辑器场景用 prompt。

配额、持久化与响应类型 ​

  • navigator.storage.estimate() 查看 usage / quota；不要假设固定配额。
  • navigator.storage.persist() 可申请持久化，但是否授予由浏览器决定，不能作为唯一保障。
  • 跨域 no-cors 资源返回 opaque 响应（status 0）：cache.addAll 会拒绝，cache.put 可存但读不到状态/头，且配额计量不透明；优先使用 CORS 资源。
  • 只缓存成功响应；cacheableResponse.statuses 明确限定 [0, 200] 或 [200]，不要把 500 缓存成「正常页」。
  • Cache-Control 与 SW 缓存是两层：SW 命中缓存时可能不发起网络请求；需要强制新鲜时用 fetch(request, { cache: 'reload' }) 或绕过 SW。

配置项语义与坑 ​

  • registerType：prompt（默认）适合有状态页面；autoUpdate 会强制 workbox.clientsClaim 与 workbox.skipWaiting，适合无状态页面，但仍需在入口调用 registerSW({ immediate: true }) 才会自动刷新页面。
  • injectRegister：null 表示完全手动注册，配合 virtual:pwa-register；auto（默认）会在你没有导入虚拟模块时自动注入注册脚本。
  • manifest：对象会被插件生成并注入 <link rel="manifest">；多端部署时 start_url、scope、id 必须带 base，否则安装后从站点根启动。
  • globPatterns：默认主要覆盖 js/css/html；字体、图片、webmanifest 要显式加入，否则不会被预缓存。
  • cleanupOutdatedCaches：generateSW 默认开启；只清理 Workbox 旧预缓存，不会清理你自定义命名的 runtime cache，自定义缓存仍需在 activate 里按版本清理。
  • maximumFileSizeToCacheInBytes：默认 2 MiB 左右；大文件（地图、模型、视频）不要硬塞预缓存，改为按需 runtime 缓存或完全不缓存。
  • navigateFallback：多端 base 下必须显式拼成 ${base}index.html，只写 index.html 在不同部署路径下会落到错误位置。
  • navigateFallbackDenylist：接口、后台、下载链接要排除，避免把 API 404 返回成首页 HTML。
  • devOptions.enabled 仅开发期开启；type: 'module' 用于 injectManifest 的 ESM 开发调试，别把开发配置带进生产。

126.6 离线兜底与 IDB 写队列 + Background Sync ​

离线兜底页的三条底线 ​

  1. 离线页自身不依赖网络资源：CSS 内联，图标用 data URI 或本地内联 SVG，不能引用 CDN 字体/样式。
  2. 导航失败必须返回 HTML：caches.match('/offline.html') 后返回 Response，明确 Content-Type: text/html; charset=utf-8；不要返回 undefined 让浏览器显示默认错误页。
  3. 离线页要有下一步动作：「重试」按钮、已缓存内容入口、网络状态提示；只写「你离线了」没有价值。
js
// sw.js 片段
self.addEventListener('fetch', (event) => {
  if (event.request.mode !== 'navigate') return;
  event.respondWith((async () => {
    try {
      return await fetch(event.request);
    } catch {
      const cached = await caches.match(event.request);
      if (cached) return cached;
      const offline = await caches.match('/offline.html');
      return offline ?? new Response('<h1>离线</h1>', {
        status: 200,
        headers: { 'Content-Type': 'text/html; charset=utf-8' },
      });
    }
  })());
});

IndexedDB 写队列：结构比重试更重要 ​

离线写队列不是「把请求存起来再发」这么简单，至少要包含：

字段作用
id本地唯一标识，便于调试与幂等
url / method / headers / body重放所需请求信息
idempotencyKey服务端幂等键，防重复下单/重复发奖
createdAt / attempts / nextAt退避调度与可观测
statuspending / inflight / failed / dead
conflictPolicykeep-server / overwrite，明确冲突时谁赢

重放规则：

  • 只重放幂等请求；非幂等写必须带幂等键，服务端去重。
  • 指数退避 + 抖动：min(maxDelay, base * 2 ** attempts) + random，避免整点雪崩。
  • 多标签页并发重放要用 Web Locks（或服务端幂等键兜底）；没有锁时至少把 status 置为 inflight 做租约。
  • 超过最大次数进入 dead，在 UI 里可见并可手动重试；不要静默丢弃。
  • 冲突策略要业务定：订单/支付类通常 keep-server，草稿类可 overwrite。

完整的离线同步队列实现见 56.2 PWA 离线：壳缓存与数据缓存分工 与 examples/56-01-offline-sync-queue.ts；本册只补充 PWA 侧的接入边界。

beforeinstallprompt：只捕获，不劫持 ​

type InstallPromptEvent = Event & {
  prompt: () => Promise<void>;
  userChoice: Promise<{ outcome: 'accepted' | 'dismissed'; platform: string }>;
};

let deferredPrompt: InstallPromptEvent | null = null;

window.addEventListener('beforeinstallprompt', (event) => {
  event.preventDefault();
  deferredPrompt = event as InstallPromptEvent;
  // 这里只更新「可安装」状态，不立刻弹窗
});

window.addEventListener('appinstalled', () => {
  deferredPrompt = null;
  // 隐藏自定义安装入口，记录安装成功
});

export async function installFromBanner(): Promise<'accepted' | 'dismissed' | 'unavailable'> {
  if (!deferredPrompt) return 'unavailable';
  const event = deferredPrompt;
  deferredPrompt = null; // 事件一次性，先清空再调用
  await event.prompt();
  const choice = await event.userChoice;
  return choice.outcome;
}

交互规则：

  • 首屏不弹；至少等用户完成一次有效操作或第二次访问。
  • 关闭后进入冷却期（例如 7 天），并设置最大关闭次数（例如 3 次），避免骚扰。
  • 事件只能用一次；prompt() 后必须清空，不能反复调用。
  • appinstalled 后立即隐藏入口；已以 standalone 启动时也不再引导。
  • 可用 matchMedia('(display-mode: standalone)').matches 与 iOS 的 navigator.standalone 判断是否已安装/独立启动。

  • iOS/iPadOS Safari 不支持 beforeinstallprompt，也不支持 getInstalledRelatedApps()。

Notification 权限：在价值时刻请求 ​

  • 不要在首屏加载时调用 Notification.requestPermission()；用户还不知道通知能带来什么，拒绝率最高。

  • Notification.permission 为 denied 时，浏览器通常不允许再次弹系统权限框；改为展示「去设置开启」的路径说明。
  • 用 navigator.permissions.query({ name: 'notifications' as PermissionName }) 监听权限变化，避免页面状态过期。
  • 推送内容必须对用户有价值；高频营销推送会加速用户关闭通知甚至卸载 PWA。

function urlBase64ToUint8Array(base64String: string): Uint8Array {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const normalized = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const raw = atob(normalized);
  return Uint8Array.from(raw, (char) => char.charCodeAt(0));
}

export async function subscribePush(publicKey: string) {
  if (!('serviceWorker' in navigator) || !('PushManager' in window)) return null;
  const permission = await Notification.requestPermission();
  if (permission !== 'granted') return null;

  const registration = await navigator.serviceWorker.ready;
  const existing = await registration.pushManager.getSubscription();
  if (existing) return existing;

  return registration.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(publicKey),
  });
}

// 服务端：web-push 投递与 410 清理
import webpush from 'web-push';

webpush.setVapidDetails('mailto:ops@example.com', process.env.VAPID_PUBLIC!, process.env.VAPID_PRIVATE!);

export async function send(subscription: webpush.PushSubscription, payload: unknown): Promise<void> {
  try {
    await webpush.sendNotification(subscription, JSON.stringify(payload), {
      TTL: 3600,
      headers: { Urgency: 'high', Topic: 'orders' },
    });
  } catch (error) {
    const statusCode = (error as { statusCode?: number }).statusCode;
    if (statusCode === 404 || statusCode === 410) {
      // 订阅已失效，必须从存储中删除，否则会持续重试
      await removeSubscription(subscription.endpoint);
      return;
    }
    throw error;
  }
}

契约要点：

  • VAPID 密钥用 npx web-push generate-vapid-keys 生成；公钥可下发，私钥只能放服务端。
  • userVisibleOnly: true 是 Chrome/Safari 的硬要求；不允许静默推送。
  • 每次推送都应产生用户可见通知；iOS 16.4+ 的主屏 Web App 同样要求。
  • tag 合并同类通知，renotify 决定是否再次提醒；不要用同一个 tag 覆盖重要告警。
  • notificationclick 要聚焦已有窗口而不是每次新开；注意 includeUncontrolled，否则可能找不到旧窗口。
  • 监听 pushsubscriptionchange 重新订阅并同步服务端；Safari 支持情况以实测为准，启动时校验订阅作为兜底。
  • 404/410 必须删除订阅；429/5xx 按退避重试；400/401/403 不要盲目重试，先查 payload 与密钥。
  • 推送 payload 不要放敏感信息：通知内容可能出现在锁屏。

平台检测与降级 ​

ts
export type InstallSurface = 'installed' | 'ios-guide' | 'native' | 'none';

export function detectInstallSurface(): InstallSurface {
  const standalone =
    window.matchMedia('(display-mode: standalone)').matches ||
    (navigator as Navigator & { standalone?: boolean }).standalone === true;
  if (standalone) return 'installed';

  const isIOS = /iPad|iPhone|iPod/.test(navigator.userAgent);
  if (isIOS) return 'ios-guide';

  return 'native';
}

注意：

  • UA 检测只用于「展示哪套引导」，不能用于能力判断；能力一律用特性检测。
  • iPadOS 13+ 可能伪装成 macOS，UA 检测不一定可靠；结合 navigator.maxTouchPoints > 1 与 platform 判断只能作为启发式。
  • 推送、后台同步、通知都必须先做特性检测，再决定是否展示入口。

Lighthouse：PWA 分类已经移除 ​

这一点必须写死，避免继续写过时断言：

  • Lighthouse 12 起已移除独立 PWA 分类，与 Chrome 简化安装性判定同步；categories.pwa 在 Lighthouse 12+ 不存在。
  • 现在应使用：DevTools Application > Manifest 的安装性提示、自定义 manifest/SW/离线断言、Lighthouse 的 Performance/Accessibility/Best Practices/SEO 分类作为辅助。
  • 如果团队仍需要旧版 PWA 评分，只能锁定 Lighthouse 11.x 并显式调用；不要在新版 CI 中假设该分类存在。
  • 不要用「PWA 分数 100」作为唯一发布门槛；安装性、离线 E2E、版本更新回归才是硬门槛。

可落地的 CI 思路：

  1. 构建产物里断言 manifest.webmanifest 存在且字段合法（可用 126-01 的审计器逻辑）。
  2. 断言 sw.js 存在、注册代码在入口、manifest 被 HTML 引用。
  3. 用 Playwright 跑离线与更新两条 E2E。
  4. 用 126-06 的验收引擎汇总为 ship / ship-with-warnings / hold。

Playwright 离线 E2E ​

ts
import { expect, test } from '@playwright/test';

test('离线导航落到兜底页', async ({ page, context }) => {
  await page.goto('/');
  await page.evaluate(() => navigator.serviceWorker.ready);
  await page.waitForFunction(() => navigator.serviceWorker.controller !== null);

  await context.setOffline(true);
  await page.goto('/docs/not-cached');
  await expect(page.locator('h1')).toContainText('离线');
});

要点：

  • 必须先等待 serviceWorker.controller，否则断网时页面还没被 SW 接管。
  • context.setOffline(true) 模拟断网，但 SW 仍可运行；这能验证缓存与兜底，不会验证真实运营商网络。
  • 再补一条「在线 → 断网 → 恢复在线」的用例，验证重连后的数据刷新。
  • 用 page.evaluate(() => caches.keys()) 断言版本缓存清理。

步骤操作期望

线上回滚 ​

  • 首选：发布自毁 SW（第 126.3 节），清缓存 + 注销 + 重新导航；确认后再发正式 SW。
  • 次选：把 sw.js 与 manifest.webmanifest 设置为 no-cache，让浏览器尽快拿到修复版本；缓存头落点见 53.3。
  • 不要用 Clear-Site-Data: "cache", "storage" 作为常规回滚：它会清掉用户本地数据（离线队列、草稿），只在极端故障时使用。
  • 回滚后要监控：SW 注册失败率、离线兜底命中率、首屏白屏率、更新提示点击率。

126.10 自测题 ​

1. PWA 的三件套是什么？「有 Service Worker」为什么不等于「可安装」？【基础】

三件套是 HTTPS 安全上下文、Web App Manifest、Service Worker。可安装性还要求 manifest 的关键字段（名称、start_url、scope、display、192/512 图标等）。Chromium 自 108/112 起菜单安装不再强制 SW 的 fetch 处理，但安装提示仍要求；Safari 根本没有 beforeinstallprompt。因此「有 SW」既不充分也不必要，必须按目标浏览器与目标入口分别验收。

2. `id`、`start_url`、`scope` 各自解决什么问题？改 `id` 会发生什么？【基础】

id 是应用身份，决定安装记录、权限与存储归属；start_url 是安装后的启动地址；scope 是 SW 控制与「是否属于本应用」的路径边界。start_url 必须同源且在 scope 内。修改 id 会让浏览器把它当成另一个应用，原安装记录、通知权限、本地存储都可能不连续。

3. 192、512、maskable、apple-touch-icon、screenshots 各解决什么问题？maskable 的安全区怎么留？【进阶】

192 是安装入口与主屏基础图标，512 用于安装弹窗/高清屏/商店物料，maskable 供 Android 自适应裁切，apple-touch-icon（180×180）供 iOS 主屏，screenshots 供 Chrome Android 富安装 UI 预览。maskable 主体应放在中心约 80% 直径的安全区内，四角留白；purpose 建议 any 与 maskable 拆成两条，sizes: "any" 只用于 SVG。

4. SW 注册在 `/app/sw.js`，却想控制 `/`，需要什么条件？`updateViaCache` 为什么建议设 `none`？【进阶】

脚本 URL 决定最大作用域，/app/sw.js 默认最多控制 /app/。要控制 /，服务端必须返回 Service-Worker-Allowed: /，并且显式 scope: '/'。updateViaCache: 'none' 让 SW 脚本与导入脚本绕过 HTTP 缓存，否则用户可能长期运行旧 SW，发版不生效。

5. 导航、带哈希静态资源、配置接口、订单接口、写请求分别该用什么缓存策略？【进阶】

导航用 NetworkFirst + 3s 超时 + 离线兜底；带哈希静态资源用 CacheFirst + 长有效期；配置接口用 StaleWhileRevalidate；订单接口用 NetworkFirst + 短超时；写请求用 NetworkOnly，失败进 IndexedDB 队列并用幂等键重放。核心原则是「写不缓存、导航要新、静态可久、接口按新鲜度分级」。

6. `generateSW` 与 `injectManifest` 怎么选？`cleanupOutdatedCaches` 能清理自定义 runtime cache 吗？多端 `base` 要注意什么？【挑战】

标准预缓存 + runtimeCaching 选 generateSW；需要自定义 push/notificationclick/sync/message 选 injectManifest。cleanupOutdatedCaches 只清理 Workbox 旧预缓存，不会清理自定义命名的 runtime cache，自定义缓存要在 activate 里按版本前缀清理。多端 base 下 start_url、scope、id 都要带 base，navigateFallback 要显式写成 ${base}index.html。

7. 描述一次完整的更新流程：waiting 如何出现、脏表单如何阻止刷新、为什么只能刷新一次？【挑战】

新 SW 安装完成后进入 waiting，旧 SW 继续控制页面；updatefound + installing.statechange 到 installed 且存在 controller 时判定「更新可用」。有脏表单时状态进入 deferred，保存后才进入 prompting；用户确认后 postMessage({ type: 'SKIP_WAITING' })，SW 调用 skipWaiting，页面在 controllerchange 中刷新。必须用布尔标记保证只刷新一次，重复点击 applyUpdate 要幂等。

8. 列出 iOS/Safari 的五条关键限制，并给出对应降级方案。【挑战】

1）无 beforeinstallprompt，只能做分享引导；2）Background Sync / Periodic Sync 不支持，用 online + visibilitychange + 启动重放兜底；3）Web Push 仅 iOS/iPadOS 16.4+ 且必须添加到主屏，先 A2HS 再请求权限，userVisibleOnly: true；4）未安装到主屏的站点脚本存储可能 7 天无交互后被 ITP 清理，主屏 Web App 域豁免，关键草稿双写服务端；5）manifest 仅支持子集，display_override/shortcuts/screenshots/share_target 不生效，图标走 apple-touch-icon。
