4.1 React 架构与 Fiber 原理 ​

概念解析 ​

JSX 与虚拟 DOM：JSX 在编译后是 jsx(type, props) 调用，产出普通的 JS 对象（虚拟 DOM）——它只是"描述"，真正的 DOM 操作由 React 协调后批量执行。

Fiber 架构（React 16+）：把渲染工作拆成以 Fiber 节点为单位的小任务：

React 15(Stack Reconciler)              React 16+(Fiber Reconciler)
─────────────────────────              ─────────────────────────
递归更新,一旦开始不可中断          →    每个组件对应一个 Fiber 节点(链表结构)
长任务霸占主线程 → 输入掉帧         →    可中断、可恢复、可按优先级调度
                                       beginWork → completeWork → commitWork

双缓存机制:
  current 树 —— 当前屏幕显示的 Fiber 树
  workInProgress 树 —— 正在内存中构建的新树
  构建完成后一次切换(commit),保证界面的连续性

渲染两个阶段：

阶段特点内容
Render（协调）可中断、可丢弃重算计算差异（Diff），构建 workInProgress 树
Commit（提交）同步不可中断执行 DOM 变更、触发生命周期/useEffect

Diff 策略（把 O(n³) 降到 O(n) 的三个假设）：① 不同类型的元素 → 直接重建子树；② 同层比较，不跨层移动；③ 列表通过 key 识别移动/复用——这就是 key 不能用数组下标的原因。

// 文件: src/demo/KeyDemo.tsx —— key 用下标的经典 bug 复现
import { useState } from 'react';

// ❌ 用 index 作为 key:删除中间项时,后面的输入框内容"串位"
export function BadList() {
    const [items, setItems] = useState(['a', 'b', 'c']);
    return (
        <>
            <button onClick={() => setItems(items.filter((_, i) => i !== 0))}>删除第一项</button>
            {items.map((item, index) => (
                <div key={index}>

                        React 以为只是"文本从 a 变成 b",输入框里的用户输入就错乱了 */}
                    <input defaultValue={item} /> <span>{item}</span>
                </div>
            ))}
        </>
    );
}

    );
}

// 文件: src/demo/ErrorBoundary.tsx —— 错误边界:渲染错误的兜底
import { Component, ReactNode } from 'react';

interface Props { children: ReactNode; fallback?: ReactNode }
interface State { error: Error | null }

export class ErrorBoundary extends Component<Props, State> {
    state: State = { error: null };

    // ① 渲染阶段兜底:返回降级 UI(此阶段不能有副作用)
    static getDerivedStateFromError(error: Error): State {
        return { error };
    }

    // ② 提交阶段:副作用(上报日志)放这里
    componentDidCatch(error: Error, info: React.ErrorInfo) {
        reportToSentry(error, info.componentStack);
    }

    render() {
        if (this.state.error) {
            return this.props.fallback ?? <h1>该模块出错了,请刷新重试</h1>;
        }
        return this.props.children;
    }
}

function reportToSentry(error: Error, stack: string | null | undefined) {
    console.error('[边界捕获]', error.message, stack);
}

最佳实践 ​

  • ✅ 列表 key 必须是稳定、唯一的业务 id；仅在"纯展示且永不重排"的列表可以退而求其次用 index；
  • ✅ 用 ErrorBoundary 包裹独立业务区块（图表卡片、富文本），避免单点错误白屏整站；
  • ✅ 理解"Render 可中断、Commit 同步"——componentDidCatch/useEffect 里的报错不会被 ErrorBoundary 捕获自身，但会冒泡到父级边界；
  • 📖 面试高频：Fiber 是什么（链表化的工作单元）、双缓存树、两阶段渲染、Diff 三策略、为何 key 不能用下标。

4.2 Hooks 原理与自定义 Hook ​

概念解析 ​

Hooks 存储机制：每个函数组件对应的 Fiber 节点上挂着一个 memoizedState 链表；组件渲染时按调用顺序依次取用。这就是"不能把 Hook 放进 if/循环"的根本原因——顺序乱了，取到的状态就错位了。

typescript
// 文件: examples/04-01-use-state-mechanism.ts
// ============ Hooks 原理示意:索引链表模型(极简教学版,非 React 源码)============

interface HookNode { state: unknown; queue: unknown[] }

// 模拟:每个组件实例在 Fiber 外部持有一个 hooks 链表 + 当前处理索引
const hooks: HookNode[] = [];
let hookIndex = 0;
let isRendering = false;

function useState<T>(initial: T): [T, (action: T | ((prev: T) => T)) => void] {
    const currentIndex = hookIndex;

    // 首次渲染:初始化节点;再次渲染:复用上一次的节点(状态得以跨渲染保存)
    if (!hooks[currentIndex]) {
        hooks[currentIndex] = { state: initial, queue: [] };
    }
    const hook = hooks[currentIndex];

    function dispatch(action: T | ((prev: T) => T)) {
        // React 中 dispatch 是异步批处理的;这里简化为直接更新并触发重渲染
        hook.state = typeof action === 'function' ? (action as (p: T) => T)(hook.state as T) : action;
        scheduleRerender();
    }

    hookIndex++; // 关键:每次调用 useState,索引前移 —— 顺序即身份
    return [hook.state as T, dispatch];
}

function useEffect(effect: () => void | (() => void), deps?: unknown[]) {
    const currentIndex = hookIndex++;
    if (!hooks[currentIndex]) hooks[currentIndex] = { state: undefined, queue: [] }; // 首次渲染初始化节点
    const prevDeps = (hooks[currentIndex].state as unknown[] | undefined) ?? [];
    const changed =
        deps === undefined ||
        deps.length !== prevDeps.length ||
        deps.some((d, i) => !Object.is(d, prevDeps[i]));

    if (changed) {
        queueMicrotask(() => {
            (hooks[currentIndex].queue as Array<() => void>).forEach((cleanup) => cleanup()); // 先执行上次清理
            hooks[currentIndex].queue = [];
            const cleanup = effect();
            if (typeof cleanup === 'function') hooks[currentIndex].queue.push(cleanup);       // 再保存新清理
        });
        hooks[currentIndex].state = deps ?? [];
    }
}

function render<T>(Component: () => T): T {
    hookIndex = 0;      // 每次渲染索引归零,按同样的顺序取用 Hook
    isRendering = true;
    const result = Component();
    isRendering = false;
    return result;
}

let rerenderScheduled = false;
function scheduleRerender() {
    if (rerenderScheduled) return; // 批处理:同一批的多次 setState 只触发一次重渲染
    rerenderScheduled = true;
    setTimeout(() => {
        rerenderScheduled = false;
        void render(App);
    }, 100);
}

// ---- 演示:顺序错乱会发生什么 ----
function App() {
    const [count, setCount] = useState(0);
    const [name, setName] = useState('Alice');
    useEffect(() => console.log('count 变了:', count), [count]);

    console.log(`渲染:count=${count}, name=${name}`);

    // ❌ 如果在条件分支里调用 useState,本次渲染 hookIndex 错位,
    //    setName 会拿到"count 的 hook" —— 这就是官方规则"不要在条件/循环中调用 Hook"的原理
    return { count, setCount, name, setName };
}

const app = render(App);
app.setCount(1); // 触发异步批处理重渲染(100ms 后),观察依赖变化日志

// 文件: src/hooks/usePrevious.ts —— 高频自定义 Hook 三件套
import { useEffect, useRef, useState } from 'react';

/** 1. usePrevious:获取上一轮渲染的值(对比、回退场景) */
export function usePrevious<T>(value: T): T | undefined {
    const ref = useRef<T | undefined>(undefined);
    useEffect(() => {
        ref.current = value; // effect 在渲染后执行 → ref 里存的是"上一次"
    }, [value]);
    return ref.current;
}

/** 2. useDebouncedValue:防抖值(搜索联想必备) */
export function useDebouncedValue<T>(value: T, delay = 300): T {
    const [debounced, setDebounced] = useState(value);
    useEffect(() => {
        const timer = setTimeout(() => setDebounced(value), delay);
        return () => clearTimeout(timer); // 每次变化先清掉旧定时器
    }, [value, delay]);
    return debounced;
}

/** 3. useEventListener:带自动清理的订阅 */
export function useEventListener(target: EventTarget, event: string, handler: (...args: never[]) => void) {
    const handlerRef = useRef(handler);
    handlerRef.current = handler; // 始终指向最新回调,避免闭包过期
    useEffect(() => {
        target.addEventListener(event, handlerRef.current as EventListener);
        return () => target.removeEventListener(event, handlerRef.current as EventListener);
    }, [target, event]);
}

最佳实践 ​

  • ✅ 理解规则背后的机制后再背规则：Hook 顺序即身份，所以条件/循环/嵌套函数中禁止调用 Hook；
  • ✅ 自定义 Hook 是逻辑复用的唯一正解（比 HOC、Render Props 干净一个量级）；
  • ⚠️ useRef 改值不会触发重渲染，它适合存"与渲染无关的可变数据"（定时器 id、DOM 引用、最新值镜像）；
  • ⚠️ 闭包陷阱：useEffect/定时器回调里的 state 是当次渲染的快照，需要最新值时用函数式更新 setX(x => ...) 或 ref 镜像；
  • 📖 面试高频：useState 与 useReducer 的关系、useEffect 清理函数执行时机（下次 effect 前 + 卸载时）、useLayoutEffect 与 useEffect 的差异（前者 DOM 变更后同步、绘制前，可防闪烁）。

4.3 React 性能优化与新特性 ​

概念解析 ​

React 默认策略是"父渲染 → 所有子组件跟着渲染"。优化三板斧：

  1. 减少渲染：memo（组件级缓存）+ useMemo/useCallback（值/回调缓存）——组合起来才能打破渲染链；
  2. 降低更新成本：状态下放、列表虚拟化、拆分动态/静态内容；
  3. 并发调度：useTransition/useDeferredValue 把非紧急更新标记为"可中断"。

渲染时机心智模型：setState 只是"预约"一次重渲染，React 会合并批次（自动批处理，React 18+ 覆盖 Promise/setTimeout 等场景），在微任务后统一处理。

完整代码示例 ​

tsx
// 文件: src/demo/MemoDemo.tsx —— memo + useCallback 组合拳
import { memo, useCallback, useMemo, useState } from 'react';

interface Props { items: string[]; onSelect: (item: string) => void }

// 只有 props 浅比较不变时才跳过重渲染
const ExpensiveList = memo(function ExpensiveList({ items, onSelect }: Props) {
    console.log('列表重渲染了(应只在 items 变化时出现)');
    return (
        <ul>
            {items.map((item) => (
                <li key={item} onClick={() => onSelect(item)}>{item}</li>
            ))}
        </ul>
    );
});

export function Parent() {
    const [count, setCount] = useState(0);
    const [keyword, setKeyword] = useState('');

    // ❌ 反例:内联箭头函数每次渲染都是新引用,memo 直接失效
    // const handleSelect = (item: string) => console.log(item);

    // ✅ useCallback 缓存函数引用:count 变化引起 Parent 重渲染时,列表不会重渲染
    const handleSelect = useCallback((item: string) => {
        console.log('选中:', item);
    }, []);

    // ✅ useMemo 缓存计算结果:keyword 不变时不重复过滤(昂贵计算才有必要)
    const filtered = useMemo(
        () => bigDataset.filter((item) => item.includes(keyword)),
        [keyword],
    );

    return (
        <>
            <button onClick={() => setCount((c) => c + 1)}>count: {count}</button>
            <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />
            {/* 只有 useMemo 的记忆生效,filtered 引用不变,memo 列表才会跳过 */}
            <ExpensiveList items={filtered} onSelect={handleSelect} />
        </>
    );
}

4.4 Vue 响应式系统原理 ​

概念解析 ​

Vue3 响应式三件套：Proxy 拦截 → 依赖收集（track）→ 派发更新（trigger）。

数据读取(get) ──track──> 记录"当前正在运行的 effect"到 targetMap(WeakMap)
                        target → key → Set<effect>
数据写入(set) ──trigger──> 取出该 target+key 的所有 effect,重新执行
effect = watch/watchEffect/渲染函数 的统一抽象

对比 Vue2：Object.defineProperty 只能拦截已存在的属性读写（新增/删除属性、数组下标都需要 $set 等特判），而 Proxy 拦截的是对象操作本身，13 种操作全覆盖。

完整代码示例 ​

typescript
// 文件: examples/04-02-mini-reactivity.ts
// ============ 手写 Vue3 迷你响应式系统(核心约 60 行)============

type EffectFn = (() => void) & { deps: Set<Set<EffectFn>> };

let activeEffect: EffectFn | null = null;
const effectStack: EffectFn[] = [];

// 全局依赖图:target → key → 依赖该 key 的 effect 集合
const targetMap = new WeakMap<object, Map<string | symbol, Set<EffectFn>>>();

function track(target: object, key: string | symbol) {
    if (!activeEffect) return; // 不在 effect 中读取,无需收集
    let depsMap = targetMap.get(target);
    if (!depsMap) targetMap.set(target, (depsMap = new Map()));
    let deps = depsMap.get(key);
    if (!deps) depsMap.set(key, (deps = new Set()));
    if (!deps.has(activeEffect)) {
        deps.add(activeEffect);
        activeEffect.deps.add(deps); // 双向记录,便于清理(解决分支切换的"脏依赖")
    }
}

function trigger(target: object, key: string | symbol) {
    const deps = targetMap.get(target)?.get(key);
    if (!deps) return;
    // 拷贝一份再遍历:防止 effect 执行中增删依赖导致死循环
    [...deps].forEach((fn) => {
        // 避免"effect 内部又触发了自己"(如 count++ 递归)
        if (fn !== activeEffect) fn();
    });
}

function cleanup(effectFn: EffectFn) {
    effectFn.deps.forEach((deps) => deps.delete(effectFn));
    effectFn.deps.clear();
}

/** effect:响应式的副作用,数据变化时自动重新执行 */
function effect(fn: () => void): EffectFn {
    const effectFn: EffectFn = (() => {
        cleanup(effectFn);             // 重新执行前清掉旧依赖,再按本次分支重新收集
        effectStack.push(effectFn);
        activeEffect = effectFn;
        fn();
        effectStack.pop();
        activeEffect = effectStack[effectStack.length - 1] ?? null; // 支持嵌套 effect
    }) as EffectFn;
    effectFn.deps = new Set();
    effectFn();
    return effectFn;
}

// ---- reactive:Proxy 拦截读写 ----
const proxyMap = new WeakMap<object, object>();

function reactive<T extends object>(obj: T): T {
    const existing = proxyMap.get(obj);
    if (existing) return existing as T; // 同一对象只代理一次,保证 === 相等

    const proxy = new Proxy(obj, {
        get(target, key, receiver) {
            track(target, key);
            const result = Reflect.get(target, key, receiver);
            // 深层响应式:嵌套对象继续代理
            return result !== null && typeof result === 'object' ? reactive(result as object) : result;
        },
        set(target, key, value, receiver) {
            const oldValue = (target as Record<string | symbol, unknown>)[key];
            const success = Reflect.set(target, key, value, receiver);
            // 值真正变化才触发,避免无意义的重渲染
            if (success && !Object.is(oldValue, value)) trigger(target, key);
            return success;
        },
        deleteProperty(target, key) {
            const hadKey = Reflect.has(target, key);
            const success = Reflect.deleteProperty(target, key);
            if (hadKey) trigger(target, key); // 删除属性也要触发(for...in 依赖 key 数量)
            return success;
        },
    }) as T;
    proxyMap.set(obj, proxy);
    return proxy;
}

// ---- 验证:与 Vue3 的 reactive 使用体验一致 ----
const state = reactive({ count: 0, user: { name: 'Alice' }, list: [1] });

effect(() => {
    console.log('effect 触发, count =', state.count); // 依赖收集:count

最佳实践 ​

  • ✅ 理解"谁读取了谁，谁就依赖谁"：effect 中不要提前解构响应式对象（const { count } = state 会丢失响应性，用 toRefs）；
  • ✅ 派生数据用 computed（带缓存、惰性求值），而不是在多个 effect 里重复计算；
  • ⚠️ 直接替换响应式对象的原型、往 Map/Set 的代理上混用原始对象，是响应性失效的常见根因；
  • 📖 面试高频：Vue2 vs Vue3 响应式差异、为什么 WeakMap 做依赖图、computed 与 watch 的区别（缓存 vs 副作用）、为什么需要 ref（基本类型无法被 Proxy 代理）。

概念解析 ​

// 文件: src/composables/useRequest.ts —— 带竞态防护的通用请求 composable
import { ref, watchEffect, type Ref } from 'vue';

export function useRequest<T>(url: Ref<string>) {
    const data = ref<T | null>(null);
    const loading = ref(false);
    const error = ref<Error | null>(null);
    let controller: AbortController | null = null;

    watchEffect(async (onCleanup) => {
        // url 变化 → 自动重新请求;上一次请求被取消 → 不会出现旧数据覆盖新数据
        controller?.abort();
        controller = new AbortController();
        loading.value = true;
        error.value = null;

        onCleanup(() => controller?.abort()); // 副作用清理:url 再变或组件卸载时取消请求

        try {
            const res = await fetch(url.value, { signal: controller.signal });
            data.value = (await res.json()) as T;
        } catch (e) {
            if ((e as Error).name !== 'AbortError') error.value = e as Error;
        } finally {
            loading.value = false;
        }
    });

    return { data, loading, error };
}

        this.itemsSignal.update((list) => [...list, item]);
    }

4.7 React 与 Vue 原理对照 ​

前六节把两个框架各自拆开讲，这一节回答"为什么长得不一样"：同一个需求（更新 UI、复用逻辑、缓存页面）在两种设计下走向了不同的实现。看懂这层，技术栈迁移和面试深挖都不用靠背。

4.7.1 一条更新链路的两种走法 ​

React（拉取式 pull）
setState ──标脏──> 调度器按 lane 优先级排队
                     │
                     ├─ Render 阶段：重新执行组件函数 → 新 vnode → diff（可中断）
                     └─ Commit 阶段：同步更新 DOM、执行 effect

Vue（推送式 push）
数据写入 ──Proxy set──> trigger → 精确通知依赖该 key 的 render effect
                                    │
                                    └─ patch：按编译期 patchFlag 只比对动态部分 → 更新 DOM
维度ReactVue 3
驱动方式拉取：状态变化只标脏，调度器统一重算，具体谁受影响由重新执行发现推送：读时收集依赖、写时精确通知，谁用了谁更新
更新单位组件函数整体重新执行组件 + 精确到具体响应式属性
可中断性Fiber 时间切片，可暂停/丢弃/续跑（并发特性的基础）无时间切片，靠依赖粒度本身避免长任务
优化责任开发者（memo/useMemo），React Compiler 正在收回框架（编译期标记 + 精确订阅）默认生效
状态载体不可变快照，每次渲染拿到新值可变容器（ref/reactive），跨渲染同一引用
UI 描述JSX（就是 JS，编译器难做静态分析）模板（可静态分析的受限 DSL）

两条最影响日常写码的语义差异，都源自上表最后两行：

  1. 组件函数执行次数不同。React 每渲染一次就调用一次组件函数，回调天然捕获"那次渲染的快照"；Vue 的 setup 只执行一次，之后更新走 render effect，闭包里的 ref 始终指向同一个容器。
  2. 状态是"值"还是"容器"不同。所以 React 存定时器 id、WebSocket 实例要 useRef 跨渲染保引用，Vue 里一个普通 let 变量就够了。

  timer = setInterval(() => console.log(count.value), 1000); // ✅ 始终是最新值
});
onUnmounted(() => clearInterval(timer)); // 普通变量也无需 useRef 承载
</script>

4.7.3 缓存组件实例：KeepAlive 与 React 的等价实现 ​

Vue 的 <keep-alive> 缓存的是什么

它是个抽象组件：自己不产出 DOM，只负责缓存管理。理解四个要点基本就懂了实现：

  • 缓存单元是组件 vnode + 组件实例（连带 DOM 子树、响应式状态、内部定时器），不是 HTML 字符串；
  • 命中键是 vnode.key ?? 组件 type——所以"同组件不同参数"必须显式写 :key，否则会共用同一份缓存；
  • 失活 ≠ 卸载：DOM 被移到内存中的隐藏容器，实例不销毁，触发 deactivated；激活时移回原位，触发 activated。所以滚动位置、表单输入、视频进度全都保留；
  • max 超出时按 LRU 淘汰最久未激活的；include/exclude 按组件的 name 匹配（<script setup> 里要用 defineOptions({ name })，否则匹配不上）；只接受单个子节点。

React 为什么没有对应物

React 的 state 属于组件实例内部，卸载即销毁；而"把 DOM 从文档挪走但保留 state"没有公开原语。Vue 能做是因为它自己掌控了 vnode → DOM 的挂载/移动全过程。四条替代路线：

路线保留什么代价适用
① 状态提升 / 外部 store纯数据（滚动、焦点、播放进度要手动存）需要把状态搬出组件默认首选
② display:none 常驻挂载全保：state + DOM + 滚动 + 焦点首次全量挂载、DOM 常驻内存表单页签、图表、富文本
③ <Activity>（原 Offscreen）全保 + 副作用暂停19.x 仍属实验能力，稳定版未公开等 API 稳定
④ react-activation / keepalive-for-react全保，API 接近 Vue（含路由级方案）额外依赖、与 StrictMode/并发渲染需验证存量代码迁移、路由级保活

路线 ② 是最接近 KeepAlive 语义、也最容易落地的：

tsx
// 文件: src/components/TabKeepAlive.tsx —— 懒挂载 + display:none 保活（等价 keep-alive）
import { useState, type ReactNode } from 'react';

interface Tab { key: string; label: string; render: () => ReactNode }

export function TabKeepAlive({ tabs, maxAlive = 5 }: { tabs: Tab[]; maxAlive?: number }) {
  const [active, setActive] = useState(tabs[0].key);
  const [visited, setVisited] = useState<string[]>([tabs[0].key]); // 首次访问才挂载，省首屏

  const switchTo = (key: string) => {
    setActive(key);
    setVisited((prev) => {
      const next = prev.includes(key) ? prev : [...prev, key];
      // 对齐 keep-alive 的 max：超出后淘汰最久未访问的（简易 LRU）
      return next.length > maxAlive ? next.slice(next.length - maxAlive) : next;
    });
  };

  return (
    <>
      <nav>{tabs.map((t) => <button key={t.key} onClick={() => switchTo(t.key)}>{t.label}</button>)}</nav>
      {tabs.filter((t) => visited.includes(t.key)).map((t) => (
        // hidden 等价 display:none：组件保持挂载，不触发卸载清理
        <div key={t.key} hidden={t.key !== active} style={{ display: t.key === active ? undefined : 'none' }}>
          {t.render()}
        </div>
      ))}
    </>
  );
}

落地时的五个坑：

  • ⚠️ 条件渲染不是保活：{active === 'a' && <A />} 会真正卸载、state 归零——这是对"React 没有 keep-alive"最常见的误判；
  • ⚠️ hidden 属性会被 CSS 的 display 覆盖：元素若写了 display:flex，hidden 的 display:none 会失效（属性选择器优先级低于类），要么用内联 style 兜底（上面示例），要么全局加 [hidden] { display: none !important; }；
  • ⚠️ 首屏全挂载：一次性渲染所有页签会让首屏变慢——用 visited 集合懒挂载；
  • ⚠️ 内存只增不减：DOM 与组件树常驻，重资源（地图、播放器、大表格）要在失活时主动释放数据，或靠 maxAlive 淘汰；
  • ⚠️ 没有 activated/deactivated，副作用不会自动停：KeepAlive 里的组件失活时定时器/轮询仍在跑，React 方案同理。必须把"是否激活"显式传下去，用 effect 依赖控制启停——这就是 Vue 那两个生命周期存在的意义：
tsx
function LiveChart({ active }: { active: boolean }) {
  const refresh = () => { /* 拉取最新数据，此处省略实现 */ };
  useEffect(() => {
    if (!active) return;                    // 失活：不建立连接
    const timer = setInterval(refresh, 5000);
    return () => clearInterval(timer);       // 重新激活或真正卸载时清理
  }, [active]);                              // 对齐 deactivated / activated 语义
  return <canvas />;
}

放到路由里：两个 Router 的接法完全不同

真实业务里的保活几乎都发生在路由切换：列表页进详情再返回，要求筛选条件、滚动位置、分页都不丢。这时框架层组件只是零件，关键看路由库怎么接。

Vue Router 4 是原生组合——<router-view> 的插槽把当前路由组件交出来，外面包 <keep-alive> 即可：

vue
<!-- 文件: src/App.vue —— 路由级保活的标准写法 -->
<script setup lang="ts">
import { computed } from 'vue';
import { useRoute, useRouter } from 'vue-router';
const router = useRouter();
const route = useRoute();

// 约定：路由 name 与页面组件 name 一致，且 meta.keepAlive 为 true 时进缓存
const cachedViews = computed(() =>
  router.getRoutes()
    .filter((r) => r.meta.keepAlive)
    .map((r) => r.name as string), // include 匹配组件 name，靠同名约定对齐
);
</script>

<template>
  <router-view v-slot="{ Component }">
    <keep-alive :include="cachedViews" :max="10">
      <!-- :key 用 route.name：防止不同路由复用同一组件时共享缓存 -->
      <component :is="Component" :key="String(route.name)" />
    </keep-alive>
  </router-view>
</template>

这里有三个容易混淆的点：

  • include 匹配的是组件 name（defineOptions({ name: 'UserList' })），而 :key 用的是路由 name——两个 name 是不同东西，写错任意一个都会"看起来没缓存"或"缓存串页"；
  • meta.keepAlive 是声明式开关，但组件被移出 include 时并不会立刻销毁，要等它下次失活才真正释放（想立即清缓存得配合 max 或改用动态 :include 强制失活）；
  • 滚动位置还有第二套机制：Vue Router 的 scrollBehavior 负责导航时恢复到 savedPosition，keep-alive 负责DOM 状态不被销毁，两者互补不替代。

React Router 6.4+/7 则完全没有这层能力：<Routes> 的 element 切走即卸载，<Outlet /> 也不保留任何东西。连 v7 的 loader + shouldRevalidate 都只是数据缓存（避免重复请求），不是组件实例保活——这是最容易误判的一点。所以 React 侧要么自己按上面的 display:none 思路包一层路由组件，要么直接用 react-activation：

tsx
// 文件: src/App.tsx —— React Router + react-activation 的路由级保活
import { BrowserRouter, Routes, Route } from 'react-router-dom';
import KeepAlive, { AliveScope, useAliveController } from 'react-activation';

export default function App() {
  return (
    // AliveScope 必须包住 Router、位于应用根部（包进 Routes 内部会静默失效）
    <AliveScope>
      <BrowserRouter>
        <Routes>
          {/* name 必须唯一且稳定，建议直接用路由 path */}
          <Route path="/list" element={
            <KeepAlive name="list" saveScrollPosition="screen">
              <ListPage />
            </KeepAlive>
          } />
          <Route path="/detail/:id" element={<DetailPage />} />
        </Routes>
      </BrowserRouter>
    </AliveScope>
  );
}

// 需要主动清缓存时（退出登录 / 提交成功后让列表重新拉数据）
function LogoutButton() {
  const { drop } = useAliveController();
  return <button onClick={async () => { await logout(); drop('list'); }}>退出登录</button>; // logout 为示例占位
}

对照着看，两边的职责划分差异一目了然：

维度Vue Router 4 + <keep-alive>React Router 6/7 + react-activation

react-activation 能绕过"卸载即销毁"的原理值得知道：<AliveScope> 在页面里创建一个离屏容器，<KeepAlive> 用 Portal 把子树渲染进去；路由切走时 KeepAlive 组件本身被卸载，但它先通过 portal 把子树（含真实 DOM 与组件实例）留在离屏容器里，下次挂载时再 portal 回原位。本质仍是"DOM 不销毁"，只是用 Portal 把搬运做得对使用者透明——所以它踩的坑也和 display:none 方案同源：

  • ⚠️ name 必须唯一且稳定：用随机值或自增 id 会导致缓存命中不了、内存无限增长；
  • ⚠️ 副作用不会暂停：被缓存页面的轮询、WebSocket、定时器仍在跑，离开时要在 effect 里按可见性停掉；
  • ⚠️ React 18/19 的兼容性要实测：并发渲染与 StrictMode 双调用下该库有已知问题，上线前必须关掉 StrictMode 对照验证，别把它当"官方能力"用；
  • ⚠️ drop 时机要设计：列表缓存后数据可能过期，通常配合"提交成功 / 退出登录 / 下拉刷新"手动清除，而不是指望 TTL；
  • ⚠️ AliveScope 的位置错了就静默失效：必须包住 Router 且在应用根部，包在 Routes 里面或每个页面各包一个都不对。

选型结论：新项目优先 ① 状态提升或 ② 自建 display:none 壳（可控、无依赖）；只有存量项目迁移成本高、且需要路由级开箱即用时，才引入 react-activation，并做好版本兼容验证。

迁移心智：Vue 把"保活"做成了组件能力（声明 <keep-alive> 即可），React 把"保活"当成状态管理问题（想清楚哪些状态必须活下来，再决定搬去哪）。前者省事，后者更可控。

最佳实践 ​

  • ✅ 迁移或面试时先讲驱动方式（pull vs push），再讲 API 差异——顺序反了会变成背单词；
  • ✅ React 里遇到"值不更新"，先怀疑闭包快照与 deps；Vue 里遇到"更新了但视图没变"，先怀疑解构丢响应性（const { count } = toRefs() 或直接读 obj.count）；
  • ✅ 需要"页面保活"先问一句：只需保数据，还是连 DOM 状态（滚动/焦点/播放进度）也要保？前者用状态提升，后者才上 display:none；
  • ⚠️ 不要在两套框架间生搬硬套：computed 不是 useMemo 的等价物（前者自动追踪、后者手动声明），watch 也不是 useEffect（前者有明确的"旧值/新值"，后者是渲染提交后的副作用钩子）。

4.9 自测题 ​

先自己作答，再展开参考答案。

1. 【基础】Fiber 架构解决了什么问题?渲染的两个阶段如何划分?

解决 React 15 递归渲染不可中断、长任务阻塞主线程导致掉帧的问题。两阶段:Render(协调)阶段构建 workInProgress 树,可中断可丢弃重算;Commit(提交)阶段执行 DOM 变更,同步不可中断。

2. 【挑战】为什么列表 key 不能用数组下标?用最小示例说明后果

下标与"内容"没有稳定对应关系:删除第一项后所有下标前移,React 认为只是内容变化而复用错误节点,非受控输入值、动画状态等 DOM 内部状态会串位。key 必须是稳定唯一的业务 id。

3. 【进阶】Vue2 与 Vue3 响应式的核心差异?

Vue2 用 Object.defineProperty,只能拦截已存在属性的读写,新增/删除属性和数组下标需要 $set 等特判。Vue3 用 Proxy 拦截对象操作本身(13 种),支持新增删除、惰性深层代理,依赖收集也更精细(分支切换自动清理脏依赖)。

4. 【挑战】什么时候 useMemo/useCallback 才真正有必要?

三种情况:① 计算确实昂贵(大列表过滤/变换);② 返回值作为 memo 子组件的 props(保持引用稳定才有意义);③ 作为其他 Hook 的依赖数组成员。否则只是徒增阅读成本。

5. 【进阶】React 没有 keep-alive，要在页签切换时保留表单输入与滚动位置，怎么实现？各方案代价是什么？

核心是"保持挂载、不触发卸载"：把已访问的页签全部渲染，用 hidden（display:none）切换可见性，state、DOM、滚动位置都会保留；配合"首次访问才挂载"的 visited 集合控制首屏成本，再用类似 max 的淘汰策略限制常驻数量。若只需保留数据而不需要 DOM 状态，则把状态提升到父层或外部 store 更轻。<Activity>（原 Offscreen）是官方方向，但 19.x 仍属实验能力。此外没有 activated/deactivated，必须显式传 active 给子组件，用 effect 依赖启停定时器与订阅。

6. 【挑战】为什么"React 里定时器回调读到的 state 永远是旧值"，而 Vue 里同样的写法却正确？

React 的组件函数每次渲染都会重新执行，回调闭包捕获的是创建它的那次渲染的 state 快照；空依赖 effect 只建一次定时器，闭包就永远停在首帧。Vue 的 setup 只执行一次，ref 是跨渲染不变的容器，读 .value 永远拿最新值。这不是"谁更先进"，而是驱动模型差异（pull 重新执行 vs push 精确通知）在语言层的投影——React 侧要用 useRef 承接最新值或函数式更新来绕过。

4.10 本章避坑清单 ​

把本章散落在各节的原则收口成一份可检索清单，按日常出现频率排序；详情回上方对应小节。

场景高频坑一句话避法
StrictMode 双调用开发环境 useEffect 跑两次、请求发两遍React 18 故意「挂载—卸载—再挂载」以暴露不干净的副作用；清理函数要与副作用成对（取消订阅、abort 请求），副作用写成幂等
闭包捕获旧 state定时器、异步回调里读到的 state 永远是旧值函数组件每次渲染都是新闭包，回调捕获的是那次渲染的快照；要读最新值用 ref，或改用函数式更新 setState(v => ...)
useEffect 依赖漏写依赖读到旧值，多写不稳定依赖导致无限循环依赖数组要覆盖 effect 内用到的全部响应式值；对象、函数依赖先用 useMemo、useCallback 稳定，或用 ref 承接
列表 key删除第一项后，输入框、动画状态莫名串位用数组下标作 key 会让「内容」与「节点」错配；key 必须是稳定唯一的业务 id
Vue 解构丢响应式const { count } = reactive(obj) 后，改 obj 而 count 不动直接解构会把代理属性读成普通值、断开响应式；用 toRefs、storeToRefs 解构，或把字段改成 ref
v-if 与 v-for 同元素条件里取到的变量是错的同元素上 v-for 优先级更高，v-if 拿不到当轮循环项；把 v-if 上移一层，或改用计算属性过滤列表
深 watch对一个巨大对象 deep: true，页面明显卡顿深层监听会递归遍历整个对象；改为只监听具体字段，或用返回值的 getter 只取关心的数据
nextTick 时序改完数据立刻读 DOM，拿到的还是旧值Vue 更新是异步批处理的；要等 DOM 更新后再读，用 await nextTick()，别用 setTimeout 拼时序
条件渲染当保活React 里以为 {active === 'a' && <A />} 能像 <keep-alive> 一样缓存页面，切回来数据全没了条件渲染就是卸载；要保活必须保持挂载、用 hidden/display:none 切可见性，并显式传 active 停掉失活组件的副作用
keep-alive 的 include 不生效写了 include="UserList" 却完全不缓存include/exclude 按组件 name 匹配（不是文件名）；<script setup> 要用 defineOptions({ name: 'UserList' }) 显式声明
