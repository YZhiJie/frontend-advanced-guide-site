101.1 迁移决策与路线选择 ​

概念解析 ​

为什么必须迁：Vue 2 于 2023-12-31 官方 EOL（End of Life），此后不再接收任何修复（含安全补丁）。继续停留在 Vue 2 意味着：安全漏洞无补丁、新生态（Vite / 新版组件库 / 官方工具链）无法使用、招聘与维护成本逐年上升。迁移不是"要不要"，而是"何时、怎么迁"。

三条路线对比：

路线适用场景成本风险
整体重写小项目（< 50 页面）、生命周期临近尾声、需求还在高速迭代高（等于新项目）重写期间双线作战，需求冻结难谈
渐进式迁移（Vue Compat）中大型存量项目、质量要求高、不能停业务中（分批可控）兼容层心智负担，需要严格门禁
原地升级 + 2.7 过渡暂时无法迁移，但需要 Composition API 写法低只是过渡，EOL 问题未根治

迁移前体检清单（决定路线的关键输入）：

  1. 依赖盘点：Element UI（仅 Vue 2）→ Element Plus；vue-router 3 → 4；vuex 3 → 4（再 → Pinia）；@vue/test-utils 1 → 2；vue-template-compiler → @vue/compiler-sfc。任何"仅 Vue 2"的深度依赖组件库都是最大成本项
  2. 不兼容 API 计数：用静态扫描器（见 101.4 与示例 101-02）统计 Vue.filter / $set / $on / functional / 过滤器管道 0 的使用量，量化改造面
  3. 自定义指令 / 渲染函数数量：指令钩子与 h() 第二参数结构都变了，逐个手改
  4. 测试覆盖：有 E2E 兜底的项目敢渐进式；零测试项目先补核心链路 E2E 再动
  5. IE11 是否还要支持：Vue 3 放弃 IE11，若还有 IE 需求必须先解决浏览器基线

应用实践 ​

  • 默认选渐进式：B 端中大型项目一律走 Vue Compat 渐进式，按路由 / 模块分批，业务不停线
  • 先升 Vue 2.7 再迁 3：Vue 2.7 内嵌了 Composition API（setup / ref / computed），可以先把新代码写成两版通用的组合式风格，迁移时这部分代码零改动
  • 迁移与重构分离：迁移期只做"等价改写"，忍住一切顺手重构的冲动——混在一起做，出了问题无法归因

最佳实践 ​

  • 迁移立项先出一页纸体检报告（依赖清单 / API 计数 / 测试覆盖 / 工期估算），向业务方对齐"分几个批次、每批风险"
  • 给代码库加防回退门禁：CI 里禁止新增 Vue.use(、$set(、filters: 等 Vue 2 专属写法（示例 101-02 的扫描规则可直接改成 lint 规则）

101.2 Vue 2 Options API 对等深度 ​

概念解析 ​

迁移的前提是真正理解 Vue 2 的运行模型。三个核心机制：

① 初始化时序与生命周期全景：

text
new Vue() → init injections & reactivity（data/computed/methods 递归响应式化）
  ├─ beforeCreate   ← 实例刚创建，data/methods 尚不可用（适合插件初始化）
  ├─ created        ← 响应式数据就绪，DOM 未生成（适合发首个请求）
  → 编译模板生成 render → 挂载 DOM
  ├─ beforeMount
  ├─ mounted        ← DOM 就绪（子组件 mounted 先于父组件执行！）
  → 数据变化时：beforeUpdate → 重新渲染 → updated
  → $destroy() 时：beforeDestroy → 拆 watchers/子实例/事件 → destroyed
  keep-alive 场景：activated / deactivated 取代反复挂载销毁
  错误捕获：errorCaptured（可返回 false 阻止继续向上传播）

② this 语义：Options API 的 this 是一个"代理对象"——Vue 把 data、props、methods、computed 的全部键平铺挂到实例上，并做了三层处理：data 属性经 Object.defineProperty 转成 getter/setter；methods 用 bind(this) 绑定上下文；属性名冲突按 props > data > methods > computed 优先级去重并告警。理解了这一点就理解了两个经典坑：箭头函数里的 this 不是组件实例（箭头函数捕获外层作用域）；methods 之间互相调用必须带 this.，因为它们只是挂在一个对象上的普通函数。

③ mixins 合并机制：mixin 不是"继承"，是选项级合并——data 递归浅合并（组件优先）、生命周期钩子合并成数组（mixin 先执行）、methods/computed 同名冲突时组件胜出且静默覆盖。这套机制是一切"mixins 之痛"的根源：来源不可见（模板里用的 this.formatTime 要全局搜索才知道来自哪个 mixin）、命名冲突静默吞掉、类型推导完全失效。

应用实践 ​

  • created 里发请求是 Vue 2 的惯例；迁移时直接平移到 setup() 顶层或 onMounted（涉及 DOM 的逻辑必须在 onMounted）
  • Vue 2 的 activated/deactivated、errorCaptured 在 Vue 3 一一对应 onActivated/onDeactivated/onErrorCaptured，迁移时改个名即可
  • 审计 mixins 时输出"mixin 提供了哪些键"的清单（示例 101-03 会模拟这个合并过程），作为拆解依据

最佳实践 ​

  • 把 mixin 合并规则当成面试必答题：data 递归合并组件优先、钩子数组化 mixin 先跑、普通选项组件覆盖 mixin
  • 用 2.7 的 setup() 改写 mixin 时，先写调用方兼容层：composable 返回与原 mixin 同名的键，保证模板与其他 mixin 零改动

101.3 两代核心差异系统对照 ​

概念解析 ​

① 响应式原理：Object.defineProperty vs Proxy

维度Vue 2（defineProperty）Vue 3（Proxy + Reflect）
转换时机初始化递归遍历全量转换惰性：访问到哪层才代理哪层
新增 / 删除属性检测不到，必须 Vue.set / Vue.delete原生拦截（set/deleteProperty trap）
数组索引赋值 / length检测不到（只重写 7 个变异方法）原生支持
Map / Set不支持支持
初始开销大对象递归转换明显卡顿惰性代理，首屏更快
兼容性IE9+不支持 IE11（Proxy 无法 polyfill）

本质差异：defineProperty 只能拦截已有属性的读写，所以 Vue 2 需要一堆"补丁 API"（$set/$delete/数组方法重写）；Proxy 拦截的是对象操作本身，补丁 API 全部失去存在意义——这就是 $set/$delete 在 Vue 3 被整体移除的原因。

② 生命周期映射表：

Vue 2Vue 3（组合式）说明
beforeCreate / createdsetup() 本身setup 执行时机即 created 之前
beforeMount / mountedonBeforeMount / onMountedDOM 逻辑放 onMounted
beforeUpdate / updatedonBeforeUpdate / onUpdated语义不变
beforeDestroy / destroyedonBeforeUnmount / onUnmounted改名，注意全局替换
activated / deactivatedonActivated / onDeactivatedkeep-alive
errorCapturedonErrorCaptured语义不变
—onRenderTracked / onRenderTriggered新增调试钩子

③ 组合式函数：逻辑组织范式变化：Vue 2 的逻辑复用只有 mixins / 高阶组件 / 作用域插槽三条路，全都有来源不清或嵌套地狱问题；Vue 3 的 composable 是普通函数——输入是参数，输出是显式的 ref/函数，来源可见、可重命名、可被 TypeScript 完整推导。响应式状态的"引用语义"是理解组合式的钥匙：ref 是包装对象，跨函数传递、解构都不会丢响应（丢的是 reactive 的解构，见 101.10 避坑 1）。

完整代码示例 ​

ts
// 文件: examples/101-01-reactivity-lifecycle-diff.ts（节选：defineProperty vs Proxy 能力边界）
// 用最小可运行的对照，证明 Vue 2 响应式的三个检测盲区在 Vue 3 中全部消失
function observeVue2(obj: Record<string, unknown>): Record<string, unknown> {
  for (const key of Object.keys(obj)) {
    let internal = obj[key];
    Object.defineProperty(obj, key, {
      enumerable: true,
      configurable: true,
      get() { return internal; },
      set(v) { internal = v; },
    });
  }
  return obj;
}
const touch = { log: [] as string[] };
const v2: any = observeVue2({ count: 1 }, touch);
v2.count = 2;                        // 已有属性：setter 可拦截
v2.newKey = 1;                       // 新增属性：defineProperty 无 trap，检测不到
assert.ok(touch.log.includes("set:count"));
assert.ok(!touch.log.includes("set:newKey")); // Vue.set 存在的根因

const touch3 = { log: [] as string[] };
const v3: any = new Proxy({}, {
  set(t, key, value) { touch3.log.push(`set:${String(key)}`); return Reflect.set(t, key, value); },
});
v3.newKey = 1;                       // 新增属性：原生可感知
assert.equal(touch3.log.includes("set:newKey"), true); // Vue3 无需 $set

运行方式：npx tsx examples/101-01-reactivity-lifecycle-diff.ts

应用实践 ​

  • 面试标准答案框架：先讲拦截对象不同（属性 → 对象操作），再讲派生结果（Vue 2 需要补丁 API、全量递归、数组方法重写；Vue 3 惰性代理、原生完备），最后讲代价（放弃 IE11、解构 reactive 丢响应）
  • 迁移期踩到"改了数据视图不更新"，先按 Vue 2 思维排查 $set 场景——迁移后这类 bug 应该整体消失，若还在说明代码里还有没迁干净的部分

101.4 Breaking Changes 全景与代码对照 ​

概念解析 ​

把不兼容变更分成四类，按"出现频率 × 改造难度"排序处理：

① 全局 API → 应用实例（几乎每个项目都中）：

js
// Vue 2：全局 API 挂在 Vue 构造函数上
Vue.use(router);
Vue.use(pinia);
Vue.component("AppHeader", AppHeader);
Vue.directive("focus", focusDirective);
Vue.prototype.$http = http;
Vue.mixin(authMixin);
new Vue({ render: (h) => h(App) }).$mount("#app");

// Vue 3：全部收拢到 app 实例，且支持多实例共存
const app = createApp(App);
app.use(router);
app.use(pinia);
app.component("AppHeader", AppHeader);
app.directive("focus", focusDirective);
app.config.globalProperties.$http = http; // 全局属性（更推荐 provide/inject 替代）
app.mixin(authMixin);                     // 兼容保留，但应迁移为 composable
app.mount("#app");

② 模板语法变更：

Vue 2 写法Vue 3 写法备注
0 过滤器计算属性或方法调用管道符 | 语法整体移除
:prop.sync="x"v-model:prop="x".sync 移除，v-model 支持多个
v-on:click.native直接 @click.native 移除，未声明 emit 的事件自动落到根元素
v-for 与 v-if 同元素（v-for 优先）v-if 优先优先级反转，同元素写法几乎都是 bug，应拆分
<transition> v-enterv-enter-from类名改名，CSS 全局替换
多根节点不允许Fragments 支持根元素不再强制单节点

③ 实例 API 变更：$on/$off/$once 移除（EventBus 模式失效，换 mitt）；$children 移除（换 refs）；$listeners 并入 $attrs；$set/$delete 移除；异步组件从 { component: () => import(...) } 改为 defineAsyncComponent(() => import(...))；函数式组件的 functional 选项移除。

④ 渲染函数与指令：h() 第二参数扁平化（attrs/props/onXxx 合一，事件变成 onXxx）；自定义指令钩子从 bind/inserted/update/componentUpdated/unbind 改名为 mounted/updated/... 生命周期同名钩子。

const RULES: Array<{ rule: string; re: RegExp; fix: string }> = [
  { rule: "global-use",      re: /(?<![.\w])Vue\.use\(/g,           fix: "改为 app.use()" },
  { rule: "vue-prototype",   re: /Vue\.prototype\./g,               fix: "改为 app.config.globalProperties 或 provide/inject" },
  { rule: "vue-filter",      re: /(?<![.\w])Vue\.filter\(/g,        fix: "过滤器移除：改计算属性/方法" },
  { rule: "this-set",        re: /\$set\(|\$delete\(/g,             fix: "Proxy 下直接赋值/delete，移除调用" },
  { rule: "event-bus",       re: /\$on\(|\$off\(|\$once\(/g,        fix: "EventBus 失效：换 mitt 实例" },
  { rule: "pipe-filter",     re: /\{\{[^}]*\|[^}|]+\}\}/g,          fix: "模板过滤器管道：改计算属性" },
  { rule: "sync-modifier",   re: /:[\w-]+\.sync=/g,                 fix: "改 v-model:prop" },
  { rule: "native-modifier", re: /@[\w.]+\.native/g,                fix: "移除 .native 修饰符" },
  { rule: "before-destroy",  re: /beforeDestroy|destroyed\b/g,      fix: "改 onBeforeUnmount/onUnmounted" },
  { rule: "functional-comp", re: /functional\s*:\s*true/g,          fix: "函数式组件选项移除，改纯函数组件" },
];

export function scanVue2(source: string): Finding[] {
  const findings: Finding[] = [];
  source.split("\n").forEach((line, i) => {
    for (const { rule, re, fix } of RULES) {
      if (re.test(line)) findings.push({ rule, line: i + 1, snippet: line.trim(), fix });
    }
  });
  return findings;
}

运行方式：npx tsx examples/101-02-breaking-changes-scanner.ts

应用实践 ​

  • 把扫描器的 10 条规则直接搬进 ESLint 自定义规则或 CI 脚本：迁移完成前拦截新增 Vue 2 写法，迁移完成后拦截存量复活
  • 全局替换顺序有讲究：先改纯改名类（beforeDestroy→onBeforeUnmount、v-enter→v-enter-from，机械安全），再改结构性类（EventBus、过滤器、.sync），最后改范式类（mixin、函数式组件）
  • v-if / v-for 优先级反转几乎不会报错、只会静默改变行为：全局搜索同元素写法逐一人工确认

最佳实践 ​

  • 迁移 PR 粒度：一个 PR 只处理一类变更（如"全局过滤器 → 计算属性"专项 PR），review 快、回滚易
  • 保留一份 BREAKING_CHANGES_CHECKLIST.md，每类变更记"总数 / 已改 / 遗留原因"，迁移进度可量化

101.5 Mixins 到组合式函数改造 ​

概念解析 ​

改造方法论分四步，核心原则是行为等价、来源显式：

  1. 盘点：列出每个 mixin 提供的全部键（data / computed / methods / 生命周期），标注被哪些组件使用
  2. 分类：把键按"状态（data）→ ref/reactive"、"派生（computed）→ computed"、"行为（methods）→ 普通函数"、"副作用（生命周期）→ onXxx 注册"四类映射
  3. 封装：一个 mixin 通常对应一个 composable 文件；内部互相调用的逻辑保持模块化组合，而不是造一个巨型 useEverything
  4. 接入：调用方 const { ... } = useXxx()，返回键名与原 mixin 保持一致，模板与其他 mixin 零改动

完整代码示例 ​

ts
// 文件: examples/101-03-mixin-to-composable.ts（节选：等价性断言）
// 同一个"分页 + 列表加载"逻辑，Vue2 mixin 形态与 Vue3 composable 形态行为必须一致
function createPaginationMixin() {
  return {
    data() { return { page: 1, pageSize: 10, list: [] as number[] }; },
    methods: {
      async load(fetcher: (p: number, s: number) => Promise<number[]>) {
        this.list = await fetcher(this.page, this.pageSize);
      },
      nextPage() { this.page += 1; },
    },
  };
}

function usePagination(fetcher: (p: number, s: number) => Promise<number[]>) {
  const page = ref(1), pageSize = ref(10), list = ref<number[]>([]);
  async function load() { list.value = await fetcher(page.value, pageSize.value); }
  function nextPage() { page.value += 1; }
  return { page, pageSize, list, load, nextPage };
}

// 等价性验收：同一 fetcher 序列下，两版产生完全一致的调用轨迹与状态
const calls: string[] = [];
const m = createPaginationMixin(); // mixin 版行为回放
m.nextPage();
await m.load((p, s) => { calls.push(`mixin p=${p} s=${s}`); return Promise.resolve([]); });
const c = usePagination((p, s) => { calls.push(`composable p=${p} s=${s}`); return Promise.resolve([]); });
c.nextPage();
await c.load();
assert.deepEqual(calls, ["mixin p=2 s=10", "composable p=2 s=10"]);

运行方式：npx tsx examples/101-03-mixin-to-composable.ts

应用实践 ​

  • 命名冲突是最先暴露的问题：mixin 静默覆盖，composable 解构时可自由重命名（const { page: orderPage } = usePagination()），把"隐式冲突"变成"显式决策"
  • 带 this.$refs / this.$emit 的 mixin 方法拆出来要补依赖注入：ref 通过参数传入 composable，事件通过回调传出
  • 建立映射文档：src/mixins/README.md 记录"每个 mixin → 对应 composable → 迁移状态"，防止迁移期出现"半 mixin 半 composable"的双轨混乱

最佳实践 ​

  • composable 只做一件事并返回显式 API；不要模仿 mixin 把十几个键全倒给调用方
  • 副作用注册（onMounted 等）必须写在 setup() 同步执行栈内——异步注册的钩子不会绑定到当前实例，这是 mixin 改造最高频的运行时错误

101.6 Vuex 到 Pinia 迁移路径 ​

概念解析 ​

为什么 Pinia 取代 Vuex：mutation 层被证明是纯样板（devtools 时间旅行靠 action 一样实现）；TypeScript 推导在 Vuex 的 string-typed commit("xxx") 上始终是二等公民；modules 嵌套 + 命名空间心智重。Pinia 用"多个平铺 store + 天然命名空间 + 直接改 state"解决了全部三点。

概念映射表：

Vuex (3/4)Pinia说明
new Vuex.Store({ modules })多个 defineStore("id", ...)模块 → 平铺 store，id 即命名空间
stateref() / state: () => ({})setup 风格或 options 风格
getterscomputed() / getters跨 store getter 直接引入其他 store
mutations移除action 里直接改 state.xxx
actions（context.commit）async 函数直接赋值this.count++ 或 store.count++
mapState/mapGettersstoreToRefs(store)注意：方法用 store 直接取，状态才需要 storeToRefs
子模块 registerModule动态 useXxxStore()Pinia 天然支持运行时创建

完整代码示例 ​

ts
// 文件: examples/101-04-vuex-to-pinia.ts（节选：行为等价映射）
// 用最小状态容器模拟 Vuex 模块与 Pinia store，断言迁移前后对外行为一致
function vuexCounterModule() {
  const state = { count: 0, loading: false };
  const getters = { double: () => state.count * 2 };
  return {
    state, getters,
    mutations: {
      INCREMENT(s: typeof state) { s.count += 1; },
      SET_LOADING(s: typeof state, v: boolean) { s.loading = v; },
    },
    actions: {
      async incrementAsync(ctx: any) {
        ctx.commit("SET_LOADING", true);
        ctx.commit("INCREMENT");
        ctx.commit("SET_LOADING", false);
      },
    },
  };
}

function piniaCounterStore() {
  const state = { count: 0, loading: false };
  const double = () => state.count * 2;          // getter：computed 语义
  async function incrementAsync() {              // action：无 mutation 中转
    state.loading = true;
    state.count += 1;                            // 直接改 state
    state.loading = false;
  }
  return { state, double, incrementAsync };
}

// 行为等价断言：两版对外暴露的状态轨迹一致
const v = vuexCounterModule();
await v.actions.incrementAsync({ commit: (t: string, p?: unknown) =>
  (v.mutations as any)[t]?.(v.state, p) });
const p = piniaCounterStore();
await p.incrementAsync();
assert.equal(v.state.count, p.state.count);
assert.equal(v.getters.double(), p.double());

运行方式：npx tsx examples/101-04-vuex-to-pinia.ts

应用实践 ​

  • 两段式迁移：先把 Vuex 3 升到 Vuex 4（API 几乎不变，只为兼容 Vue 3，一个版本发布），再按模块逐个搬到 Pinia；迁移期内两套状态库共存，用 storeToRefs 风格统一调用层
  • 每迁走一个模块，就在旧 Vuex 模块里留一行 @deprecated 已迁至 useXxxStore，IDE 悬浮提示防止新代码继续引用
  • 持久化：vuex-persistedstate → pinia-plugin-persistedstate，注意 storage key 与序列化格式保持一致，否则升级瞬间全员重新登录

最佳实践 ​

  • 迁移完成的判定不是"代码搬完"，而是 devtools 面板里看不到任何 Vuex store + 全局搜索 vuex 仅剩 package.json 历史
  • 新代码规则写进 lint：import 了 vuex 即报错

101.7 Vue Compat 渐进式迁移 ​

概念解析 ​

@vue/compat 是官方迁移构建版：一个"同时实现 Vue 2 与 Vue 3 行为"的 Vue 3 内核，按需开启 Vue 2 兼容特性，让存量代码在 Vue 3 运行时上跑起来，再用警告驱动的方式逐项修复。官方推荐四步走：

text
阶段 0 前置：依赖升级到 Vue 3 生态（router 4 / vuex 4 / 新版组件库 / compiler-sfc）
阶段 1 双语义运行：alias 三包（vue / @vue/xxx 编译器）指向 @vue/compat，
        compatConfig: { MODE: 2 }，项目在 Vue2 语义下正常跑通全部核心链路
阶段 2 警告清零：dev 环境逐条修复 compat 警告（每条警告对应一条 breaking change），
        可按特性开关（renderHelper / instanceEventBus 等）逐类开启 MODE 3 行为
阶段 3 去兼容层：警告清零后移除 alias 与 @vue/compat，运行在纯 Vue 3 语义，
        回归测试 + 灰度放量
阶段 4 清理：删除 compat 相关构建配置与临时 lint 豁免，补齐 Vue 3 惯用法文档

关键配置（Vite 为例）：

js
// vite.config.ts（阶段 1~2 期间）
export default defineConfig({
  resolve: {
    alias: {
      vue: "@vue/compat", // 三包 alias：vue → @vue/compat
    },
  },
  plugins: [vue({
    template: {
      compilerOptions: {
        compatConfig: { MODE: 2 }, // 先以 Vue2 语义编译，逐步切 3
      },
    },
  })],
});

完整代码示例 ​

ts
// 文件: examples/101-05-compat-migration-phases.ts（节选：阶段门槛判定）
// 把四步走固化为状态机：输入项目体检特征 → 判定当前阶段 + 阻塞项清单
type Phase = "P1_双语义运行" | "P2_警告清零" | "P3_去兼容层" | "P4_清理收尾";

interface Audit {
  depsUpgraded: boolean;        // router4 / vuex4 / 新组件库就绪
  e2eGreen: boolean;            // 核心链路 E2E 全绿
  openWarnings: number;         // 未修复的 compat 警告数
  unexplainedSilenced: number;  // 无注释说明的静默豁免数
  regressionPassed: boolean;    // 去兼容层后回归通过
  grayMetricsStable: boolean;   // 灰度监控无劣化
  compatAliasRemoved: boolean;  // 构建里 vue → @vue/compat 的 alias 已删
  lintExemptionsRemoved: boolean; // 临时 lint 豁免已清
}

const ORDER: Phase[] = ["P1_双语义运行", "P2_警告清零", "P3_去兼容层", "P4_清理收尾"];

function currentPhase(a: Audit): { phase: Phase; blockers: string[] } {
  const blockers: string[] = [];
  if (!a.depsUpgraded || !a.e2eGreen) {
    blockers.push(!a.depsUpgraded ? "依赖未升级到 Vue3 生态" : "核心链路 E2E 未全绿");
    return { phase: "P1_双语义运行", blockers };
  }
  if (a.openWarnings > 0 || a.unexplainedSilenced > 0) {
    if (a.openWarnings > 0) blockers.push(`仍有 ${a.openWarnings} 条 compat 警告未修复`);
    if (a.unexplainedSilenced > 0) blockers.push(`有 ${a.unexplainedSilenced} 条静默豁免缺注释说明`);
    return { phase: "P2_警告清零", blockers };
  }
  if (!a.regressionPassed || !a.grayMetricsStable) {
    blockers.push(!a.regressionPassed ? "回归测试未通过" : "灰度监控指标劣化");
    return { phase: "P3_去兼容层", blockers };
  }
  if (!a.compatAliasRemoved || !a.lintExemptionsRemoved) {
    blockers.push(!a.compatAliasRemoved ? "compat alias 未删除" : "临时 lint 豁免未清理");
    return { phase: "P4_清理收尾", blockers };
  }
  return { phase: "P4_清理收尾", blockers: [] };
}

运行方式：npx tsx examples/101-05-compat-migration-phases.ts

应用实践 ​

  • 按模块灰度切 MODE 3：compatConfig 支持组件级覆盖，把风险低的叶子模块先切到纯 Vue 3 行为，主链路最后切
  • 警告清零不能靠"压掉警告"：silenceWarnings 只允许对"确认无需处理"的特性使用，且必须留注释说明原因，否则阶段 3 一定炸
  • 阶段 1 的验收标准是核心链路 E2E 全绿，不是"页面能打开"

最佳实践 ​

  • Compat 是脚手架不是归宿：设定硬性时限（如 2 个月内完成阶段 3），长期停留在 compat 会让团队同时背负两代心智
  • 与微前端组合：如果是 qiankun 老主站，可以把新子应用直接写成 Vue 3，主子应用逐个升级，避免全站 compat

101.8 迁移质量保障与灰度策略 ​

概念解析 ​

迁移的本质风险是行为漂移（代码没报错但行为变了）。四层防线：

  1. 静态层：101.4 的扫描规则 + TypeScript 严格模式（迁移时顺手开 strict，让类型系统兜底 API 变更）
  2. 单测层：@vue/test-utils v1 → v2（mount 返回 wrapper 的 API 微调、createTestingPinia 取代手动 mock store）；不追求覆盖率数字，但核心交互用例必须先迁
  3. E2E 层：核心链路用例迁移前先录制基线，迁移后逐条回放对比——这是渐进式迁移敢"边跑业务边改"的底气
  4. 线上层：按路由 / 模块灰度放量 + 错误监控对照（迁移版 vs 存量版的报错率 / 性能指标分桶对比，复用 第五十九部分 的监控基建）

回滚预案：渐进式迁移按模块发布，每个模块保留"切回旧版"的路由开关（配置中心下发，参考 第八十二部分）；整包发布的项目至少保留上一版本镜像，秒级回滚。

应用实践 ​

  • 双跑对照：迁移期对同接口做新旧版本并行请求比对（shadow 模式），数据一致性差异即回归信号
  • 性能不退化验证：Vue 3 初始渲染更快，但包体积可能因双生态共存暂时膨胀，迁移完成前用 Lighthouse 预算卡口盯住（参考 第七十七部分）
  • 文档先行：给团队发"Vue 3 新写法速查"（setup / defineProps / v-model / store 写法），统一新代码风格，避免迁移期出现四种并存的写法

最佳实践 ​

  • 每个迁移批次收尾输出三件套：批次报告（改了什么 / 风险点 / 遗留）、监控看板（对照期数据）、复盘（下批次要改的流程）
  • 把"迁移期间不新增 mixins / 不新增 Vuex 模块"写进团队公约，防止雪球变大

101.9 自测题 ​

1. Vue 2 的响应式有哪些检测盲区？Vue 3 的 Proxy 如何解决？【基础】

Vue 2 基于 Object.defineProperty，只能拦截已有属性的读写，三个盲区：①对象新增/删除属性（需 Vue.set/Vue.delete）；②数组索引直接赋值与修改 length（需 splice 或重写后的 7 个变异方法）；③Map/Set 不支持。Vue 3 用 Proxy 拦截对象操作本身（set/deleteProperty/has 等 trap），新增删除、索引、length、Map/Set 全部原生可检测，且惰性代理把初始化的递归全量转换变成访问时按需代理。代价是 Proxy 无法 polyfill，放弃 IE11。

2. 写出 Vue 2 → Vue 3 的生命周期钩子映射关系。【基础】

beforeCreate/created → setup() 本身；beforeMount/mounted → onBeforeMount/onMounted；beforeUpdate/updated → onBeforeUpdate/onUpdated；beforeDestroy/destroyed → onBeforeUnmount/onUnmounted；activated/deactivated → onActivated/onDeactivated；errorCaptured → onErrorCaptured。新增调试用 onRenderTracked/onRenderTriggered。

3. Vue 2 中 `Vue.use()`、`Vue.prototype.xxx`、全局过滤器在 Vue 3 中分别对应什么？【基础】

Vue.use() → app.use()；Vue.prototype.xxx → app.config.globalProperties.xxx（更推荐 provide/inject 或组合式函数替代）；全局过滤器（Vue.filter 与模板管道 |）整体移除，无对应 API，迁移方向是计算属性、方法或全局属性函数。

4. 为什么说 mixins 的"静默覆盖"在生产中是危险的？组合式函数如何解决？【进阶】

mixin 合并规则是组件选项优先且不告警：两个 mixin 定义同名 methods 键时，后者静默失效，运行时才暴露为"方法行为不对"；模板里 this.formatTime 的来源需要全局搜索才能定位，重构与类型推导都困难。组合式函数把复用从"选项合并"变成"函数调用"：来源是显式 import，冲突在解构处显式重命名（const { page: orderPage } = usePagination()），TypeScript 可以完整推导返回类型，把隐式冲突变成显式决策。

5. Vuex 的 mutation 层为什么被 Pinia 移除？迁移时如何对应？【进阶】

mutation 的设计初衷是让 devtools 记录"同步状态变更点"以支持时间旅行，但 action 一样可以被记录，mutation 反而制造了"每个状态变更都要先定义 mutation 函数"的纯样板代码，且 string-typed commit("XXX") 无法被 TypeScript 推导。迁移对应关系：state → ref() 或 state: () => ({})；getters → computed()；actions → 直接 async function 并在函数体内直接修改 state（this.count++）；modules → 多个 defineStore，store id 即命名空间；mapState/mapGetters → storeToRefs(store)。

6. v-if 与 v-for 同元素时 Vue 2 与 Vue 3 的优先级差异会导致什么问题？如何处理？【进阶】

Vue 2 中 v-for 优先于 v-if（先循环再判断，v-if 里可以访问循环变量）；Vue 3 反转为 v-if 优先（v-if 里拿不到循环变量）。同元素写法在迁移后会静默改变行为甚至报"变量未定义"，且不会在编译期给出致命错误提示的旧代码场景下最容易漏改。正确处理：两者永不放在同一元素——外层 <template v-for> 内层 v-if，或用计算属性先过滤列表；迁移时全局搜索 v-for 与 v-if 同元素的写法逐一改造。

7. 描述 @vue/compat 渐进式迁移的四个阶段与每阶段的验收标准。【挑战】

阶段 0/1 双语义运行：依赖先升到 Vue 3 生态（router 4、vuex 4、新版组件库），构建 alias 把 vue 指向 @vue/compat，编译器 compatConfig: { MODE: 2 }，验收标准是核心链路 E2E 全绿（此时跑在 Vue 2 语义上）。阶段 2 警告清零：dev 环境逐条修复 compat 警告（每条警告对应一类 breaking change），可按特性逐类切到 MODE 3 行为，验收标准是零警告且无未经注释的静默豁免。阶段 3 去兼容层：移除 alias 与 @vue/compat，运行在纯 Vue 3 语义，验收标准是回归测试通过 + 灰度放量后监控指标无劣化。阶段 4 清理：删除 compat 配置与临时 lint 豁免，统一 Vue 3 惯用法。全程配套防回退门禁（禁止新增 Vue 2 专属写法）。

8. 一个 200 页面的 Vue 2 中后台要迁 Vue 3，请给出完整的迁移方案（路线、批次划分、风险控制）。【挑战】

路线选渐进式（Vue Compat），不停业务。前期：一页纸体检报告——依赖盘点（Element UI→Element Plus 是最大成本项）、静态扫描量化不兼容 API、测试覆盖评估，核心链路先补 E2E 基线。批次划分：①基建批（构建工具、alias、router 4 / vuex 4、全局 API→app 实例）；②机械替换批（生命周期改名、transition 类名、$set 移除等纯改名项，专项 PR）；③结构性批（EventBus→mitt、过滤器→计算属性、.sync→v-model、v-if/v-for 拆分）；④范式批（mixins→composables、Vuex→Pinia 按模块）；⑤组件库批（Element UI→Element Plus，样式回归）。风险控制：每批一个专项 PR + 核心链路 E2E 回放 + 按路由灰度放量 + 错误监控分桶对照 + 配置中心保留回滚开关；CI 加防回退门禁禁止新增 Vue 2 写法；迁移期禁止顺手重构。

101.10 本章避坑清单 ​

#坑点现象根因正确姿势
1解构 reactive 丢响应解构后的变量变了视图不更新reactive 是 Proxy 引用语义，解构取出的是当次快照值用 toRefs 再解构，或统一用 ref
2beforeDestroy 全局替换遗漏组件卸载不清理定时器/监听，内存泄漏改名为 onBeforeUnmount/onUnmounted，漏改不报错静态扫描器规则 + IDE 全局搜索确认清零
3v-if / v-for 同元素静默变行为迁移后列表渲染结果悄悄变了优先级从 v-for 高反转为 v-if 高两者拆分到不同元素，搜索存量逐一确认
4EventBus 迁移后事件"消失"$on 调用不报错但永远收不到事件实例方法 $on/$off/$once 在 Vue 3 被移除换 mitt 独立实例，事件名收敛为常量枚举
5过滤器管道正则误伤0 替换时把位运算 | 一起改了模板内 | 语法与 JS 位运算符形同只改插值表达式内的管道，逐个人工确认
6composable 里异步注册生命周期onMounted 回调永不执行生命周期钩子必须在 setup() 同步栈内注册异步逻辑先 await 再注册的写法重构为子组件/显式回调
7storeToRefs 用错范围方法解构后调用报 not a functionstoreToRefs 只解构状态与计算属性，方法直接从 store 取状态用 storeToRefs，方法用 store.xxx
8pinia 持久化 key 复用 vuex 旧格式升级后全员登录态丢失序列化格式/字段路径与 vuex-persistedstate 不一致迁移期保持同 key 同格式，或做一次性数据搬迁
9compat 警告被静默豁免后炸在阶段 3去掉 compat 后大面积运行时错误警告被 silenceWarnings 压掉而未真正修复豁免必须带注释说明原因，阶段 2 验收=零未处理警告
10迁移与重构混在一个 PR出问题无法归因，回滚整批报废顺手优化的冲动等价改写与重构严格分离，重构走独立批次
11忘记替换 vue-template-compiler构建报编译器版本不匹配Vue 3 用 @vue/compiler-sfc依赖盘点清单逐项替换，CI 里校验编译器一致
12Element UI 组件 API 直接套 Element Plus表单/弹层行为对不上两代组件库 API 并非 1:1（如 :visible.sync → v-model）按组件建"API 差异对照表"，逐个迁移 + 视觉回归
13多根节点后 $attrs 落点丢失父传样式/事件失效单根时 attrs 自动继承，多根（Fragments）需显式 v-bind="$attrs"根组件显式绑定 $attrs，或包一层容器元素
14全局属性滥用 globalPropertiesthis.$xxx 到处都是，类型推导失效从 Vue 2 的 prototype 习惯平移新代码用 provide/inject 或 composable，globalProperties 仅作迁移过渡

迁移心法一句话：机械替换先清零，结构变更按类分批，范式改造最后做；每一步都要有"如何证明没改坏"的验收手段。
