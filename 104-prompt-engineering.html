第一百零四部分 · Prompt Engineering 系统指南 ​

🧭 返回总目录｜上一篇：第一百零三部分 · LangChain 与 Dify 工具链｜关联章节：第三十三部分 · Zod Schema 校验 · 第十四部分 · 前端 AI 应用 · 第一百零三部分 · LangChain 与 Dify

本部分内容 ​

提示词（Prompt）是连接人类意图和 LLM 能力的唯一接口——它不是一门神秘艺术，而是一套可系统化的工程方法。好的提示词设计遵循明确的结构、可度量的效果、可版本化的迭代。本部分从「提示词应该长什么样」讲起，覆盖角色/约束/输出契约三件套、Few-shot 与 CoT 的正确打开方式、结构化输出的工程化实现（JSON Schema + 校验重试，衔接 33 册 Zod）、以及提示词版本管理与评测驱动迭代的完整闭环。

104.1 提示词的本质与设计范式 ​

提示词是什么 ​

提示词是给 LLM 设定「角色 + 目标 + 约束 + 输出格式」的组合指令。LLM 本质上是一个条件概率模型——它预测的是「给定前文，下一个 token 是什么」。提示词就是那个「前文」的关键部分。

好提示词的四要素：

角色（Who） + 任务（What） + 约束（How） + 输出契约（Output）
要素作用示例
角色锚定 LLM 的知识边界和语气风格"你是一名资深前端架构师，熟悉 Vue 3 / React 19 / TypeScript"
任务明确要做什么"帮我审查以下组件设计，指出潜在的性能问题"
约束限定怎么做"不要超过 3 条建议，每条必须有代码示例"
输出契约规定输出格式"输出 JSON，包含 code / issue / suggestion 三个字段"

常见反模式 ​

反模式问题正解
「你是 AI 助手」太泛，没有角色锚定具体到领域和职责：「你是专门做企业后台的前端架构师」
大段自然语言描述LLM 可能漏看约束结构化分段：角色段 + 任务段 + 约束段 + 输出段
没输出格式输出不稳定，前端解析困难明确指定：JSON Schema / Markdown 模板 / 分隔符
一次性塞全部需求LLM 注意力稀释拆分多轮对话，每轮聚焦一个子任务

104.2 系统提示词设计：角色/约束/输出契约 ​

系统提示词（System Prompt）是每轮对话都带的「人设」——LLM 在整个会话中都会遵循它。好的系统提示词遵循固定模板：

模板结构 ​

text
# Role（角色）
你是 [具体身份]，专长 [领域]。

# Capability（能力边界）
- 能做 A / B / C
- 不能做 X / Y / Z（遇到 XX 时，应该 YY）

# Constraints（约束）
1. 所有输出必须 [遵循规范]
2. 回答风格 [简洁/详细/正式/口语]
3. 不确定时说 "我不确定"，不编造

# Output Format（输出格式）
每次回答遵循：
## 问题理解 / ## 分析 / ## 建议

反例 vs 正例 ​

反例（生产环境 80% 的系统提示词是这种水平）：

你是一个 AI 助手，帮用户解答前端问题。

问题：角色模糊、没说能力边界、没输出格式、没约束。

正例（企业级系统提示词）：

text
# Role
你是「Frontend Architect Copilot」，一名 10 年前端架构师。
你擅长：组件库设计、性能优化、微前端架构、DevOps 工程化。

# Capability
- 能审查代码、设计组件 API、制定技术规范
- 不能运行代码、不能访问外部 API、不能获取实时数据
- 遇到不确定的 API 行为时，会说明「我需要验证」而不是编造

# Constraints
1. 建议必须有代码示例，不要空泛描述
2. 优先考虑可维护性 > 性能 > 炫技
3. 单个代码块不超过 30 行，超过先给思路

# Output Format
- 🔍 **问题**：一句话概括核心问题
- 💡 **根因**：为什么会出现
- ✅ **建议**：具体修复方案（含代码示例）

104.3 结构化输出：JSON Schema + 校验重试 ​

让 LLM 输出结构化 JSON 是 AI 应用工程化的核心需求——前端可以直接解析、存储、渲染。但 LLM 输出 JSON 时经常犯错（字段名不对、类型不对、枚举值不对），所以必须在校验失败时自动重试。

为什么 LLM 输出 JSON 会错 ​

LLM 没有「schema 合规」的硬约束——它只预测下一个 token。即使你在提示词里写了 "输出必须是 JSON"，它也可能：

  • 字段名拼写错误（scores vs score）
  • 类型错误（"score": "85" vs "score": 85）
  • 枚举值超范围（severity: "critical" 而 schema 只允许 "high|medium|low"）
  • 输出前加解释文字，不是纯 JSON

校验重试循环 ​

for attempt in 1..maxRetries:
  1. LLM 输出 → JSON.parse（捕获格式错误）
  2. parse 成功 → Schema 校验（捕获字段/类型错误）
  3. 校验成功 → 返回
  4. 校验失败 → 把错误信息喂回 LLM → 继续循环

104.4 Few-shot 与 Chain-of-Thought ​

Few-shot：给模型看例子 ​

Few-shot = 在提示词里给 LLM 看「输入-输出示例」，让它模仿格式。示例数量通常 3-5 个就够——太多会占用 token 预算，反而稀释效果。

何时用 Few-shot：

  • 输出格式很特殊（比如「前端代码审查」格式：问题 → 根因 → 建议 → 代码）
  • 风格很难用文字描述清楚（比如「模仿 Rust 编译器的错误提示风格」）
  • 任务有隐含规则（比如「判断这句话是不是讽刺」，光说规则不如看 3 个例子）

反模式：不要把 Few-shot 示例和系统提示词正文混在一起——用 # Few-shot Examples 单独标记，LLM 注意力会聚焦在明确分区内的内容上。

Chain-of-Thought（CoT）：让模型说出思考过程 ​

CoT = 让 LLM 先一步步推理，再给最终答案。对复杂推理任务（数学、逻辑、多步决策）效果显著提升。

两种写法：

  1. 显式触发：在提示词里写 "请一步步思考，先分析每个条件，再给出结论"
  2. 隐式触发：在示例里展示思考过程，让模型模仿
text
用户：小明有 5 个苹果，给了小红 3 个，又买了 2 个，现在有几个？
模型（显式 CoT）：
  1. 初始：5 个
  2. 给小红 3 个：5 - 3 = 2 个
  3. 又买了 2 个：2 + 2 = 4 个
  最终：4 个

注意：CoT 增加 token 消耗（大约 2-3 倍），简单任务（直接查表、简单分类）不要用。

反 CoT：直接要答案 ​

对结构化输出场景，应该明确拒绝思考过程——CoT 的中间推理文字会破坏 JSON 输出。

❌ "帮我审查这段代码，先分析问题再给出 JSON 结果"
✅ "帮我审查这段代码，直接输出 JSON 对象，不要包含分析过程"

104.5 提示词版本管理与评测驱动 ​

版本管理 ​

提示词不是"写好就不动"——它会随着业务迭代而变化。建议用以下策略：

策略做法
版本化每个提示词带版本号（v1.2.0），变更时递增
变更日志记录每次变更的原因、内容、效果
A/B 测试新提示词灰度放量，对比指标变化
Prompt 库把提示词当成代码管理：Git 仓库 + PR 评审

评测驱动迭代 ​

提示词效果需要量化指标，不能靠"我觉得更好了"：

指标含义度量方式
任务成功率输出是否通过 Schema 校验合格输出数 / 总请求数
人工评分专业人员对输出质量的评分（1-5 分）抽样 + 双盲评估
用户满意度最终用户的反馈（👍👎 按钮）埋点统计
Token 成本单次请求的 token 消耗sum(prompt_tokens + completion_tokens) / 请求数
延迟端到端响应时间p50 / p95 / p99

评测集构建：

  1. 找 50-200 条真实用户 query，覆盖正常 / 边界 / 异常场景
  2. 对每条 query 标注「期望输出」或「评分标准」
  3. 新提示词跑同一评测集，对比指标变化
  4. 如果「成功率 ↓」或「成本 ↑ 显著」，回滚或继续迭代

104.6 自测题 ​

1. 好提示词的四要素是什么？分别起什么作用？【基础】

角色（Who：锚定 LLM 知识边界和语气风格）、任务（What：明确要做什么）、约束（How：限定怎么做）、输出契约（Output：规定输出格式）。角色让 LLM 知道自己是谁、专长什么；任务让 LLM 知道目标；约束防止越界和走形；输出契约让前端能稳定解析。

2. 为什么 LLM 输出 JSON 会经常错？结构化输出应该怎么实现？【基础】

LLM 只预测下一个 token，没有 schema 合规的硬约束——即使提示词写了"输出 JSON"，也可能字段名拼错、类型不对、枚举值超范围、输出前加解释文字。实现方式：提示词里明确 JSON Schema → 拿 LLM 输出做 JSON.parse（捕获格式错误）→ 用 Zod/JSON Schema 做运行时校验（捕获字段/类型/枚举错误）→ 校验失败时把错误信息喂回 LLM 重试（通常 3 轮内收敛）→ 最终返回合法对象。

3. Few-shot 和 CoT 分别是什么？何时用、何时不该用？【进阶】

Few-shot = 给 LLM 看 3-5 个「输入-输出示例」让它模仿格式，用于输出格式特殊（代码审查格式）、风格难描述（模仿编译器报错）、任务有隐含规则（讽刺判断）的场景。示例数量 3-5 个够，太多浪费 token。

CoT（Chain-of-Thought）= 让 LLM 一步步推理再给答案，用于复杂推理（数学、多步决策、逻辑链）。不该用在：简单任务（查表、分类，直接要答案更快更省 token）、结构化输出场景（CoT 的推理文字会破坏 JSON，应该明确说"不要分析过程，直接输出 JSON"）。

4. 系统提示词应该怎么设计？反例和正例分别是什么？【进阶】

反例："你是一个 AI 助手，帮用户解答前端问题。" —— 角色模糊、没能力边界、没输出格式、没约束。

正例（四段落模板）：

# Role  具体身份 + 专长领域
# Capability  能做 / 不能做 + 遇到不能做的 fallback
# Constraints  具体规则（必须有代码、单个代码块 ≤ 30 行等）
# Output Format  明确的输出格式（JSON Schema 或 Markdown 模板）

可选追加 # Version 和 # Few-shot Examples。

5. 如何量化评估一个提示词的效果？评测集应该怎么构建？【进阶】

量化指标：① 任务成功率（输出通过 Schema 校验的比例）——最硬的指标，直接反映工程可用性；② 人工评分（抽样 + 双盲 1-5 分）；③ 用户满意度（👍👎 按钮埋点）；④ Token 成本（sum / 请求数）；⑤ 延迟 p50/p95/p99。

评测集构建：① 50-200 条真实用户 query，覆盖正常 / 边界 / 异常（比如"给我一个没有 bug 的 React 组件" → 这是不存在的，看 LLM 会不会编造）；② 每条标注期望输出或评分标准；③ 新提示词跑同一评测集，对比指标变化；④ 成功率 ↓ 或成本 ↑ 显著时回滚。

6. 一个 AI 代码审查应用，输出 JSON 包含 issues[] 和 summary，Schema 要求 issues[].severity 只能是 high|medium|low。LLM 第一轮输出 severity="critical"（不在枚举内），第二轮修复了 severity 但 issues 是字符串不是数组。完整描述校验重试的代码逻辑。【挑战】
async function extractStructured(llm, schema, systemPrompt, userMsg, maxRetries=3):
  messages = [systemPrompt, userMsg]

  for attempt in 1..maxRetries:
    response = await llm.generate(messages)

    // Step 1: JSON.parse（捕获 issues 是字符串的格式错误）
    try: parsed = JSON.parse(response.json)
    catch err:
      messages += [assistant: response.json, user: "不是合法 JSON，只输出 JSON"]
      continue

    // Step 2: Schema 校验（捕获 severity="critical" 的枚举错误）
    result = schema.safeParse(parsed)
    if result.success: return { data: result.data, attempts: attempt }

    // Step 3: 错误喂回 LLM（第二轮就修 severity，第三轮彻底修好）
    messages += [
      assistant: response.json,
      user: `校验错误：${result.error.message}\n请修复后重新输出 JSON`
    ]

  throw Error("超过最大重试次数")

实际执行：第 1 轮 issues 是字符串 → JSON.parse 通过但 Schema 检查 issues 应该是 array → 喂回；第 2 轮 issues 是 array 了但 severity="critical" 不在枚举内 → 喂回；第 3 轮 severity 修对、数组也对 → 通过，2 轮内收敛。关键：错误信息要精确到字段路径（issues[0].severity: 必须是 high|medium|low 之一），LLM 才能精确定位修复。

104.7 本章避坑清单 ​

#坑点现象根因正确姿势
1系统提示词太泛LLM 输出质量忽高忽低，同一个问题两次答案风格完全不同角色没锚定、没能力边界、没输出格式四段落模板：Role / Capability / Constraints / Output Format
2一次性塞全部需求LLM 注意力稀释，后半部分约束经常被忽略LLM 的有效注意力窗口有限拆分多轮对话，每轮聚焦一个子任务；长提示词分段标记 # 段落名
3结构化输出直接信任 LLM前端 JSON.parse 报错、字段缺失、类型错误LLM 只预测 token，不保证 schema 合规必须加 JSON.parse + Schema 校验 + 校验失败自动重试（通常 3 轮收敛）
4Few-shot 示例太多token 预算浪费、成本翻 2-3 倍、效果反而下降示例数量超过 5 个后，LLM 注意力被分散3-5 个精心挑选的示例足够，覆盖关键场景即可
5CoT 用在简单任务输出变慢 2-3 倍、成本翻倍但质量没提升直接查表/分类/格式化不需要推理CoT 只用于复杂推理（数学、多步决策），简单任务直接要答案
6CoT + 结构化输出混用JSON 输出里夹杂推理文字，破坏 JSON 格式推理过程和输出格式冲突明确告诉 LLM："不要分析过程，直接输出 JSON"
7提示词不版本化迭代后忘了改了什么、出问题无法回滚没有版本管理机制每个提示词带 vX.Y.Z 版本号 + 变更日志 + Git 管理
8用主观感觉评判效果"新版本好像好一点？" 但说不准哪里好没有量化指标用评测集跑新旧两个版本，对比成功率/成本/延迟三个硬指标
9校验错误信息不精确LLM 第二次还是输出同样的错误只说 "输出格式不对"，没说具体哪里不对把 Zod 的完整错误信息喂回：issues[0].severity: 必须是 high|medium|low 之一
10JSON Schema 用中文描述字段某些 LLM 对中文 JSON 描述解析有偏差LLM 训练数据主要是英文Schema 描述用英文，业务提示词可以中文
11Retry 次数无限循环坏的 LLM API Key 或 schema 设计错了，重试几十次还是失败没有上限保护maxRetries=3 足够，超过就抛出错误告警（应该修提示词不是重试）
12把用户输入直接拼进 system prompt用户输入超长、污染人设、触发安全过滤system prompt 应该稳定，用户输入单独放 user messagesystem prompt 永远固定，用户输入单独走 messages[-1]
13用 Few-shot 替代 Constraints示例里隐含了约束，但换个示例就漏了隐式规则比显式规则脆弱能用 Constraints 明确的就不用 Few-shot 隐含
14评测集只 10 条 query偶发问题测不出来、评分波动大样本量太小50-200 条真实用户 query，覆盖正常/边界/异常场景
15提示词变更没做 A/B改了系统提示词直接全量上线，质量可能暴跌灰度和对比新版本先灰度 5%，对比成功率/成本/延迟指标，至少 24 小时后再放量
16不同模型共用同一套系统提示词GPT-4o 效果很好，Claude 3.5 Sonnet 效果差模型行为差异大，同一句提示词在不同模型上解释不同系统提示词按模型分别调优，维护 prompt version × model 的二维矩阵

心法：提示词工程的本质是「约束 LLM 的自由度」——角色约束知识边界、Constraints 约束行为方式、Output Format 约束输出形态。你的约束越明确、越结构化，LLM 的表现越稳定。而稳定性的度量，永远靠量化指标 + A/B 对比，不是「我觉得好一点了」。
