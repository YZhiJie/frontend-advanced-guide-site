27.1 mini-vdom：虚拟 DOM 怎么 diff ​

27.1.1 概念解析 ​

虚拟 DOM（Virtual DOM / VNode）：用普通 JS 对象描述 UI 结构的技术。每个 VNode 只记录必要信息——标签类型、属性、子节点、key：

typescript
interface VNode {
  type: string;            // "div" / "span" / Symbol(TEXT)
  props: Record<string, any> & { key?: string | null };
  children: VNode[];
  key: string | null;
}

为什么需要 diff（Reconciliation / 协调）：

  • 每次状态变化都重新生成一棵新 VNode 树
  • Diff 算法比较新旧两棵树的差异，算出最小必要 DOM 操作
  • 真实 DOM 操作代价高（触发 reflow/repaint），所以先在内存里算好再一次性提交

Diff 的三大假设（把 O(n³) 降到 O(n)）：

  1. 不同类型的元素直接替换整棵子树：div → section，内部全销毁重建
  2. 同层比较，不跨层移动：只对同一父节点的子节点列表做 diff
  3. key 标识：列表项用稳定的 key 来识别"谁是谁"，从而正确处理移动、复用、新增、删除

keyed list diff 的核心算法（Vue 3 / React 通用）：

  • 先创建 oldKey → oldIndex 映射
  • 遍历新列表，对每个节点找它在旧列表里的位置 posInOld
  • 对 posInOld > 0 的子集跑最长上升子序列（LIS），找到不需要移动的节点
  • 不在 LIS 里的 → 需要移动；posInOld === -1 的 → 需要创建；旧列表里没被新列表引用的 → 需要删除

27.1.2 技术对比 ​

维度React FiberVue 3我们的 mini-vdom
Diff 策略同层 + key + LIS同层 + key + LIS同层 + key + LIS
是否有 DOM 依赖有（commit 阶段操作 DOM）有纯函数（只输出 diff 操作记录）
节点结构Fiber 链表VNode 对象VNode 对象
keyed list diffLIS + 贪心LIS + 贪心LIS (O(n log n))

27.1.3 应用实践 ​

真实项目中 key 不能用数组下标：

  • 删除列表中间项时，后面的下标都变了
  • React/Vue 以为只是"位置变化"，实际复用了错误的 DOM 节点
  • 典型症状：input 的用户输入"串位"到下一个 input

typescript
// 最长上升子序列 O(n log n)
function longestIncreasingSubsequence(idx: number[]): number[] {
  if (idx.length === 0) return [];
  const tails: number[] = [];      // 长度 i+1 的递增子序列的最小末尾值
  const tailIdx: number[] = [];
  const parent: number[] = new Array(idx.length).fill(-1);

  for (let i = 0; i < idx.length; i++) {
    const x = idx[i];
    if (tails.length === 0 || x > tails[tails.length - 1]) {
      parent[i] = tailIdx[tails.length - 1] ?? -1;
      tails.push(x); tailIdx.push(i);
    } else {
      // 二分找第一个 >= x 的位置
      let lo = 0, hi = tails.length - 1;
      while (lo < hi) { const mid = (lo + hi) >> 1; if (tails[mid] < x) lo = mid + 1; else hi = mid; }
      tails[lo] = x; tailIdx[lo] = i;
    }
  }
  // 重建 LIS
  const result: number[] = [];
  let cur = tailIdx[tailIdx.length - 1] ?? -1;
  while (cur !== -1) { result.unshift(cur); cur = parent[cur]; }
  return result;
}

27.2 mini-reactivity：依赖收集怎么玩 ​

27.2.1 概念解析 ​

响应式系统（Reactivity System）：数据变化时，自动执行依赖该数据的副作用函数。Vue 3 的 reactive / effect、MobX 的 observable / autorun、SolidJS 的 signal 都是这个模型的不同实现。

核心三件套：

  • Proxy（代理）：拦截对象的 get / set 操作，是 Vue 3 替代 Object.defineProperty 的升级方案
  • Dep（依赖单元 / Dependency）：一个 Set<EffectFn>，存放所有"读取过某个 key"的 effect
  • Effect（副作用函数）：包装用户代码，首次执行时收集依赖，下次数据变化时重新执行

收集时机（关键！——懒收集）：

effect(fn) 调用
  ↓
fn() 首次执行
  ↓
fn 内部读取 state.xxx → 触发 Proxy get
  ↓
Proxy get 里 track(target, key) → 把当前 activeEffect 加进 Dep
  ↓
下次 state.xxx = newValue → 触发 Proxy set
  ↓
Proxy set 里 trigger(target, key) → 执行 Dep 里的所有 effect

cleanup（脏依赖清理）：

  • Effect 每次执行前，把自己从之前收集到的所有 Dep 里移除
  • 这样可以正确处理分支切换：if (flag) state.text —— 当 flag 变 false 后，state.text 不再是依赖
  • Vue 2 没做 cleanup，所以 text 改变仍会触发 effect，性能浪费

27.2.2 技术对比 ​

维度Vue 3Vue 2我们的 mini-reactivity
代理方式ProxyObject.definePropertyProxy
深层响应递归 Proxy getter 里包裹需要 Vue.observable / Vue.setProxy getter 里递归 reactive
cleanupeffect 执行前自动清理❌ 无✅ deps 双向记录
嵌套 effecteffectStack 栈恢复❌ 只支持一层effectStack 栈
SchedulerPromise.resolve().then 合并nextTickscheduleBatch 微任务合并

27.2.3 应用实践 ​

真实项目中 computed / watch / effect 的区别：

  • computed：带缓存的 lazy effect，读取时才执行一次，之后缓存结果直到依赖变化
  • effect / watchEffect：立即执行一次，之后每次依赖变化都重新执行
  • watch(fn, callback)：不立即执行，只有数据变化时才执行 callback

核心代码摘要：

typescript
// 全局依赖图: target → key → Set<EffectFn>
const targetMap = new WeakMap<object, Map<string | symbol, Set<EffectFn>>>();
let activeEffect: EffectFn | null = null;

function track(target: object, key: string | symbol) {
  if (!activeEffect) return;
  // ... 找/建 Dep Set, 加 effect, effect.deps 反向记录
}
function trigger(target: object, key: string | symbol) {
  const deps = targetMap.get(target)?.get(key);
  if (!deps) return;
  // 拷贝一份遍历, 防止执行中增删导致死循环
  [...deps].forEach(fn => { if (fn !== activeEffect) fn(); });
}

// reactive: Proxy 拦截读写
export function reactive<T extends object>(obj: T): T {
  return new Proxy(obj, {
    get(t, k, r) {
      track(t, k);
      const v = Reflect.get(t, k, r);
      return v !== null && typeof v === 'object' ? reactive(v) : v; // 深层递归
    },
    set(t, k, v, r) {
      const ok = Reflect.set(t, k, v, r);
      if (ok && !Object.is((t as any)[k], v)) trigger(t, k); // 值变了才 trigger
      return ok;
    },
  }) as T;
}

27.3 mini-scheduler：事件循环的调度器 ​

27.3.1 概念解析 ​

事件循环（Event Loop） 中有两类任务队列：

  • 宏任务（Macro Task）：setTimeout(fn, 0)、script 标签、postMessage、I/O 回调
  • 微任务（Micro Task）：Promise.then、queueMicrotask、MutationObserver

浏览器调度优化的核心：React 16 Fiber 和 Vue 3 Scheduler 都在做三件事：

  1. 优先级队列：高优先级（如用户输入）立即执行，低优先级（如预渲染）放在空闲时间
  2. 批量合并：短时间内多次状态变化 → 合并成一次渲染，避免连续 re-render
  3. 时间切片（Time Slicing）：每帧最多工作 5ms（浏览器一帧 16.67ms），剩余时间留给用户交互

requestIdleCallback 的 Node 替代方案：Node 没有浏览器的 requestIdleCallback，用 setTimeout(fn, 0) + performance.now() 模拟。

27.3.2 技术对比 ​

维度React 16 SchedulerVue 3 nextTick我们的 mini-scheduler
优先级5 档（Immediate / User / Normal / Low / Idle）无显式优先级3 档（high / medium / low）
批量合并queueMicrotask 合并Promise.resolve().thenqueueMicrotask
时间切片requestIdleCallback 真切片❌ 无5ms budget 模拟
依赖 Node 特定 API否否否

27.3.3 应用实践 ​

真实项目中的典型场景：

  • 拖拽一个元素 → 每帧更新位置（medium 优先级）
  • 输入框打字 → 同步更新输入框（high 优先级，确保流畅）
  • 搜索联想 → debounce + low 优先级请求
  • 100 个 item 列表渲染 → 用 Scheduler 合并成 1 次 re-render

💡 为什么测试 1 的 "high 先出现 = false"？因为 high 和 medium 都在同一个微任务 tick 内注册，medium 先注册先执行。这是事件循环的自然顺序。在真实应用中 high 优先级通常来自不同的触发时机（如用户点击后立即排 high），不会和 medium 撞在同一个 tick。

核心代码摘要：

typescript
export class Scheduler {
  private high: Job[] = [];
  private medium: Job[] = [];
  private low: Job[] = [];
  private pending: Record<Priority, boolean> = { high: false, medium: false, low: false };

  schedule(fn: () => void, priority: Priority = 'medium'): number {
    // 同档优先级只排一个 flush 请求 —— 自动合并多次 schedule
    if (!this.pending[priority]) {
      this.pending[priority] = true;
      const flush = () => {
        const jobs = queue.splice(0, queue.length); // 一次取出所有
        jobs.forEach(j => j.fn());
        this.pending[priority] = false;
      };
      if (priority === 'high')      Promise.resolve().then(flush);
      else if (priority === 'medium') queueMicrotask(flush);
      else                          setTimeout(flush, 0);
    }
    queue.push({ fn, createdAt: Date.now() });
    return job.id;
  }
}

27.4 mini-fiber：为啥要长这样 ​

27.4.1 概念解析 ​

Fiber 架构（React 16 Reconciler）：把递归的 VNode 树"拍平"成链表结构，让渲染工作可以被拆分、中断、恢复。

VNode 树 vs Fiber 链表：

VNode 树（父节点持有 children 数组）          Fiber 链表（每个节点只记三个指针）
          div                                         div
         /   \                                       /
        p     section     →    p ← child  div → sibling → section
       / \                           ↓
      a   b                        return (指回 div)

Fiber 节点结构（最关键字段）：

typescript
export class Fiber {
  type: any;              // "div" / "span" / TEXT Symbol
  props: Record<string, any>;
  child: Fiber | null;    // 第一个子节点 ↓
  sibling: Fiber | null;  // 下一个兄弟 →
  return: Fiber | null;   // 父节点 ↑
  flags: number;          // Placement / Update / Deletion / Text
  alternate: Fiber | null;// 双缓存: 上一次渲染的 Fiber
  dom: any;               // 真实 DOM 节点（我们用 mock 对象）
}

双缓存机制（Double Buffering）：

  • current 树 —— 当前屏幕上显示的 Fiber 树
  • workInProgress 树 —— 正在内存中构建的新树
  • 构建完成后一次性切换，保证屏幕内容的连续性
  • 切换操作就是 current = workInProgress，O(1)！

两阶段渲染：

Render 阶段（可中断、可丢弃、可重算）
  beginWork    → 自顶向下遍历, 构建 workInProgress Fiber
  completeWork → 自底向上归并, 创建真实 DOM 节点、设置属性

Commit 阶段（同步、不可中断）
  mutation     → 执行 DOM 变更（插入、删除、更新）
  layout       → 触发 useLayoutEffect

时间切片（requestIdleCallback）：

  • 浏览器一帧约 16.67ms，React 最多用 5ms 做渲染工作
  • 超过预算 → 暂停并 scheduleIdleCallback，等下一次空闲再继续
  • 关键：切片发生在同一个 Fiber 节点内部不会中断，只在节点之间中断

27.4.2 技术对比 ​

维度React 16 FiberVue 3 VNode我们的 mini-fiber
渲染模型链表 + work loop递归 diff链表 + 递归构建
双缓存✅ current / WIP❌（直接 diff）✅ alternate
时间切片requestIdleCallback❌5ms budget 模拟
DOM 依赖真实 DOM真实 DOMmock DOM（纯函数）

27.4.3 应用实践 ​

为什么 React 要搞 Fiber 而不是维持 Stack Reconciler：

  • Stack Reconciler 递归一旦开始就无法中断
  • 渲染一棵 1000 节点的树可能霸占主线程 50ms+
  • 用户输入（如点击、滚动）必须等渲染完才能响应 → 掉帧
  • Fiber 的"可中断"特性让 React 在 16.67ms 一帧内既能完成大部分渲染，又能及时响应用户

// 同层比较 + key 复用（第一版渲染, 没有 alternate 就全部 Placement）
function reconcileChildren(parent: Fiber, vnodes: VNode[]): Fiber | null {
  let firstChild: Fiber | null = null;
  let prev: Fiber | null = null;
  const altMap = /* 父节点 alternate 的 child 链表 → key index */;

  for (let i = 0; i < vnodes.length; i++) {
    let fiber: Fiber;
    const vnode = vnodes[i];
    // 先尝试 key 复用, 否则 createFiber
    if (altMap.has(vnode.key)) fiber = altMap.get(vnode.key)!;
    else                       fiber = createFiber(vnode);
    // 连 child / sibling 链表
    fiber.return = parent;
    if (!firstChild) firstChild = fiber;
    else prev!.sibling = fiber;
    prev = fiber;
  }
  return firstChild;
}

// 简化 render: 一次 DFS 构建完整 Fiber 树
function build(fiber: Fiber) {
  if (fiber.type !== TEXT && fiber._rawChildren.length) {
    fiber.child = reconcileChildren(fiber, fiber._rawChildren);
    let c = fiber.child;
    while (c) { build(c); c = c.sibling; }
  }
}

💡 为什么用 _rawChildren 而不是 fiber.props.children？VNode 的 props 只存 DOM 属性（id / class 等），children 存在 VNode 自己的 children 字段。createFiber 时把 vnode.children 存到 _rawChildren，避免和 props 混淆。

27.5 mini-bundler：AST 里藏了什么 ​

27.5.1 概念解析 ​

打包器（Bundler）：把多个 ESM（ES Modules） 文件合并成一个 CJS（CommonJS） 文件（或 browser bundle），解决浏览器不支持 import 的问题。

核心三件事：

  1. AST 遍历（AST Traversal）：把源码解析成语法树，找到所有 import / export 声明
  2. 依赖图构建（Dependency Graph）：BFS 扫描所有 import，建立模块间的依赖关系
  3. 模块格式转换（ESM → CJS）：import x from 'y' → const x = require('y').default;

Tree Shaking（摇树）：

  • 标记哪些 export 被入口使用，哪些没被使用
  • 没被使用的 export 可以删除
  • 静态分析（ESM 的 import/export 都是静态的）让这个成为可能
  • 我们的 mini-bundler 做简化版标记，真正删除无用代码需要完整 DCE（Dead Code Elimination）

循环依赖处理：

  • 两个模块 A 和 B 互相 import 时，CJS 会出现 exports 对象还没填好就被 require 的情况
  • 解法：先预注册所有模块的占位 exports 对象，然后再逐个执行模块代码填充
  • 我们的 mini-bundler 正是这样做的

27.5.3 应用实践 ​

ESM → CJS 转换规则（我们的 bundler 核心）：

javascript
// === ESM 源码 ===
import util, { greet, add } from "./util";
export const MAGIC = 42;
export default { greet };

// === CJS 转换后 ===
const __t1 = require("./util");
const util = __t1.default;              // default import
const { greet, add } = __t1;            // named import
let __default__ = undefined;

let exports = {};
const module = { exports };

const MAGIC = 42;
__default__ = { greet };

module.exports.MAGIC = MAGIC;
module.exports.default = __default__;
// 无 named export 时: module.exports = __default__; module.exports.default = __default__;

拓扑排序（Topological Sort / Kahn 算法）：

  • 计算每个模块的入度（被多少个其他模块 import 了）
  • 入度为 0 的先执行（最底层的 util / lodash）
  • 执行完一个模块，减少它的依赖者的入度，入度变 0 的进队列
  • 这样确保每个模块被 import 时，它的 exports 已经填好

typescript
// Kahn 拓扑排序: 依赖先于被依赖执行
function buildGraph(entry: string): ParsedModule[] {
  // ... BFS 收集所有模块 ...

  const n = all.length;
  const inDegree = new Array(n).fill(0);
  const dependents: number[][] = all.map(() => []);

  for (let i = 0; i < n; i++) {
    for (const imp of all[i].imports) {
      const depIdx = /* imp.source 在哪个 module */;
      dependents[depIdx].push(i);  // dep → 被谁 import
      inDegree[i]++;
    }
  }

  const q: number[] = [];
  for (let i = 0; i < n; i++) if (inDegree[i] === 0) q.push(i);
  const order: number[] = [];
  while (q.length) {
    const cur = q.shift()!;
    order.push(cur);
    for (const dep of dependents[cur]) {
      if (--inDegree[dep] === 0) q.push(dep);
    }
  }
  return order.map(i => all[i]);
}

// Bundle 生成: 先预注册占位 exports, 再顺序执行模块代码
function bundle(mods: ParsedModule[]): string {
  const lines = [];
  // Step 1: 预注册占位
  mods.forEach((m, i) => lines.push(`const _M${i} = { exports: {} };`));
  // Step 2: registry 映射所有可能的 key
  lines.push(`const __R = {};`);
  mods.forEach((m, i) => {
    for (const key of [`./${bn}`, `./${bn}.js`, bn])
      lines.push(`__R[${JSON.stringify(key)}] = _M${i}.exports;`);
  });
  // Step 3: 模块 IIFE (按拓扑顺序)
  mods.forEach((m, i) => {
    lines.push(`(function(module) { let exports = module.exports; ... })(${`_M${i}`});`);
  });
  // Step 4: 入口
  lines.push(`module.exports = _M${mods.length - 1};`);
  return lines.join('\n');
}

27.6 自测题 ​

L1 · 基础概念 ​

Q1: React Fiber 中 child、sibling、return 三个指针分别指向什么？

📖 展开答案
  • child：指向第一个子节点
  • sibling：指向下一个兄弟节点
  • return：指向父节点

三者组合让 Fiber 链表可以用 O(1) 的空间表示任意深的树结构，遍历时像走二叉树一样 child → sibling（子优先）或 return → sibling（父节点回头）。

Q2: Vue 3 的 Proxy 相比 Vue 2 的 Object.defineProperty，在响应式收集上有哪些优势？

📖 展开答案
  1. 深层自动代理：Proxy 只需要拦截最外层对象，getter 返回值时递归 reactive(val) 即可深层代理；Vue 2 是展开递归，在 defineProperty 之前就要把所有嵌套属性遍历一遍
  2. 数组方法拦截：Vue 2 需要手动 patch push / splice 等方法；Proxy 天然能拦截
  3. 动态属性：Vue 2 无法响应新属性（需 Vue.set）；Proxy 天然支持
  4. 性能：一次 Proxy 包装比 N 次 defineProperty 调用更快

但 Proxy 的缺点是无法 polyfill（ES6 原生特性），不支持 IE11。

L2 · 原理理解 ​

Q3: mini-scheduler 里 high / medium / low 三档分别用 Promise.resolve().then / queueMicrotask / setTimeout(0)，这三者在事件循环中的执行顺序是什么？

📖 展开答案

全部属于微任务（microtask queue），在同一个 macro task 之后按注册顺序执行。setTimeout(0) 是 macro task。

但注意：本章中 high 用的是 Promise.resolve().then，medium 用的是 queueMicrotask——它们本质等价，都是进入同一个微任务队列。真正决定先后的是注册顺序，不是优先级名字。

在真实浏览器调度器中，high 优先级的任务会被放在独立的队列里，在同一个 tick 里先清空 high 队列再清空 medium。这需要额外的控制逻辑。

关键洞察：本章的 mini-scheduler 把优先级简化成"同一档只排一个 flush"，然后由注册顺序决定执行顺序。在真实场景中，high 优先级的调度请求通常来自独立的触发点（如用户点击），和 medium/low 自然会有时间差。

Q4: mini-vdom 的 keyed list diff 为什么要用 LIS（最长上升子序列）？不用 LIS 会怎样？

📖 展开答案

LIS 的作用：找到新列表中位置相对旧列表保持递增的那些节点——它们不需要移动。

举例：旧 [a, b, c, d] → 新 [a, d, b, c, e]

  • posInOld = [0, 3, 1, 2, -1] （a=0, d=3, b=1, c=2, e 没找到=-1）
  • LIS of [0, 3, 1, 2, -1] = [0, 1, 2]（对应 a, b, c）
  • 这三个不用移动：a 已经在开头，b 和 c 的相对位置没变
  • 不在 LIS 的 d 需要移动（从 old idx 3 移到 new idx 1）
  • -1（e）需要 CREATE

不用 LIS 的方案：

  • 按"旧节点在新列表里出现的顺序"贪心
  • 上面例子贪心会认为 d 的 pos=3 > b 的 pos=1？或者看旧 b=1 < c=2，然后 d=3 要不要算？
  • 不同策略会产生更多 move 操作，增加 DOM 开销

LIS 保证找到最多的"免移动"节点，整个 keyed list diff 的时间复杂度从纯贪心的 O(n²) 降到 O(n log n)。

Q5: mini-bundler 为什么要拓扑排序？如果没排序直接按入口 import 顺序执行会怎样？

📖 展开答案

为什么需要拓扑排序：被依赖的模块要先执行，这样它的 module.exports 才能在被 import 时已经填好。

没排序会怎样：假设 app.ts 先于 util.ts 执行（BFS 从入口开始时就是这个顺序）：

// _M0 (app.ts) 先执行
const __t1 = require("./util");  // __t1 = {} ← util 还没跑, exports 是空的!
const { greet, add } = __t1;     // greet = undefined

// _M1 (util.ts) 后执行
__bundle_registry["./util"].add = addFn; // 填好, 但 app 里已经是 undefined 了

运行时直接崩：TypeError: greet is not a function。

循环依赖：A → B 和 B → A 时，拓扑排序会把两者都排进去（因为有环），这时候 CJS 的占位预注册才起作用——两边的 exports 对象都是有效的 {}，只是属性可能还没填完（取决于谁先被读）。

L3 · 综合应用 ​

Q6: 假设你要在 mini-vdom 的基础上加一个 "真实 DOM 渲染" 能力，用什么方案最小成本实现？为什么？

📖 展开答案

方案选择：mini-vdom 是纯函数（只输出 DiffOp 操作记录），要渲染真实 DOM 有两个选择：

方案 A：jsdom（推荐） ​

typescript
// pnpm add -D jsdom
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!DOCTYPE html><body><div id="app"></div></body>');
const document = dom.window.document;
const root = document.getElementById('app')!;

然后遍历 diffVNode 输出的 DiffOp：

  • CREATE → root.appendChild(document.createElement(vnode.type))
  • PATCH-PROPS → Object.assign(el, op.add); op.remove.forEach(k => delete el[k])
  • PATCH-TEXT → el.textContent = op.newText
  • REPLACE / REMOVE → 用 DOM API 删除 / 替换

方案 B：Node 19+ 的 experimental-dom / undici ​

Node 19 开始有实验性的 DOM 实现，但功能有限。

方案 C：globalThis.document 模拟（不推荐） ​

自己造一个 document.createElement mock，工作量大且容易遗漏边界情况。

为什么 jsdom 最优：

  1. 浏览器 DOM API 的完整实现，不用自己 mock
  2. 和 mini-vdom 的 DiffOp 输出完美对接（DiffOp 里已经标记了 type / props / text）
  3. 可以在 Node 环境直接跑，不需要浏览器
  4. 社区成熟，pnpm add -D jsdom 一行解决
