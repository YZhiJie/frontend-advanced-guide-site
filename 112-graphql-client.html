第一百一十二部分 · GraphQL 客户端实战——Schema、缓存与订阅 ​

🧭 返回总目录｜上一篇：第一百一十一部分 · Serverless 架构｜关联章节：第六部分 · 网络请求优化 · 第三十三部分 · Zod 运行时校验 · 第三十九部分 · IM 实时通信系统 · 第五十二部分 · 数据库与 BFF 数据层

本部分内容 ​

GraphQL 把数据形状的决定权从服务端交给客户端，代价是客户端要承担查询成本、缓存一致性与实时连接。本册覆盖 REST 对照、Schema、查询接入、归一化缓存、游标分页、订阅与复杂度限流；示例纯 TypeScript，复刻 Apollo/urql 的核心机制。

112.1 心智与 REST 对照：over/under fetching 与 N+1 ​

概念解析 ​

REST 的响应形状由服务端定、需求由页面定，错位就产生两种浪费。over-fetching：商品卡只要 4 个字段，接口返回完整 SPU，海外弱网下多出的 200KB 直接变成 LCP 与流量成本。under-fetching：社交 feed 需要帖子、作者、点赞态、评论数，REST 拆成 3~4 个接口，首屏被最慢请求拖住。

N+1 是另一种问题：列表拿到 20 条后逐条请求作者（客户端 N+1），或 resolver 对每条各查一次库（服务端 N+1）。GraphQL 没消灭 N+1，只把它从网络搬进 resolver，还让客户端能写出成本爆炸的查询。客户端用 BFF 聚合，服务端用 DataLoader 按 key 批量，指标分开统计。

四组差异决定选型：形状（服务端定 vs 客户端声明）、请求次数（按资源拆分 vs 一次取多资源）、缓存（HTTP 缓存 vs 归一化缓存 + 持久化查询）、错误（状态码 vs 200 + errors[]）。GraphQL 省下的请求编排，会以成本控制与缓存基建的形式还回来。

完整代码示例 ​

结构化 AST 渲染查询串，最能看清「客户端决定形状」：只选卡片字段，一次取完。

ts
// 文件: examples/112-01-query-builder-validation.ts（节选）
const query = buildQuery({
    name: 'ProductDetail',
    vars: [{ name: 'id', type: 'ID', required: true, list: false }],
    fields: [{ name: 'product', args: { id: { var: 'id' } }, selection: [{ name: 'id' }, { name: 'title' }] }],
});
// query ProductDetail($id: ID!) { product(id: $id) { id title } }

运行方式：npx tsx examples/112-01-query-builder-validation.ts

应用实践 ​

  • 列表与详情用两套选择集，别写「万能 ProductFields」到处复用；片段按组件归属，不按实体归属。
  • 先量再换：统计首屏接口数与冗余字段，瀑布超过 2 个 RTT 或字段冗余超 40% 再考虑 GraphQL。

最佳实践 ​

  • 一个页面一个主 operation，命名唯一，便于日志、APM 与持久化查询归因。

112.2 Schema 与类型系统：SDL、标量、接口、联合与输入类型 ​

概念解析 ​

Schema 是客户端与服务端的契约，也是 GraphQL 相对 REST 的核心价值：可内省、可校验、可生成代码。构件分六类：Object（输出实体）、Scalar（叶子值）、Enum（有限取值）、Interface（共享字段的抽象类型）、Union（互斥结果）、Input（入参对象，不能与输出混用）。

! 表示非空。非空字段解析失败会向上冒泡到最近的可空父级：product 可空、price 非空而解析抛错，结果是 product: null 加一条 error，而非整个响应失败。这既解释了「200 响应里 data 缺一块」，也说明不该无脑加 !——非空越多，局部故障的爆炸半径越大。

graphql
scalar DateTime
type Money { amount: Float! currency: String! }
interface Node { id: ID! }
type Product implements Node { id: ID! title: String! price: Money! reviews(first: Int = 10): ReviewConnection! }
type User implements Node { id: ID! name: String! }
union SearchResult = Product | User
input ProductFilter { keyword: String, tags: [String!], first: Int = 20 }
type Query { product(id: ID!, locale: String = "en-US"): Product }

三条落地规则：输出与输入分离（Input 不暴露成本价、风控标记）；接口给共享字段、联合给互斥结果（搜索混合结果用 union，取分支必须内联片段）；演进靠 @deprecated 不靠删字段（删字段、改参数类型、可空改非空都是破坏性变更）。

应用实践 ​

  • 自定义标量（DateTime/URL）必须有服务端校验，否则等于把脏数据放进类型系统。
  • 用 graphql-codegen 从 operation 生成类型；运行时仍需校验，因为网络边界不可信（思路同 第三十三部分 · Zod）。

最佳实践 ​

  • 列表一律返回 Connection（edges + pageInfo），裸数组无法增量分页；客户端对未知枚举/union 成员必须兜底。

112.3 客户端接入：query / mutation / fragment / variables ​

概念解析 ​

一次请求的最小组成是 operationName + 文档 + variables。query 只读、可缓存、可重试；mutation 有副作用，不可盲目重试，必须带幂等键；fragment 是选择集复用单位，现代做法是片段与组件同址、父级拼装；variables 是唯一动态入口，用户输入拼进查询串既无法缓存又是注入面。

方案体积/复杂度缓存适合
Apollo Client大内置归一化缓存，功能最全多页面、需乐观更新/订阅
urql中，exchange 可裁剪文档缓存为主中小应用、想掌控链路
裸 fetch最小自建单页活动、简单只读

选型不是谁先进，而是缓存复杂度谁承担：同一实体在列表/详情/购物车多处出现，归一化缓存能省大量手工同步；只有几个只读查询，裸 fetch + HTTP 缓存更可控。

应用实践 ​

  • 变量校验前置到 link/exchange 层，错误直接抛给调用方；ID 允许数字入参时统一转字符串，避免同一实体两种 key。
  • 可选变量的默认值交给服务端，客户端省略即可；本地填充会让服务端改默认值后线上不生效。
  • mutation 必须返回被修改实体（likePost 返回 Post），缓存层才能直接合并；只返回 { success: true } 等于逼客户端重查。

最佳实践 ​

  • operation 命名唯一（ProductDetail、LikePost），禁止匿名查询；请求绑定 AbortController，取消必须传 signal。

112.4 缓存与规范化：归一化、失效与乐观更新 ​

概念解析 ​

文档缓存按「文档 + 变量」存整个响应，同一实体出现在两个查询里就各存一份：收藏页改了标题，详情页仍是旧的。归一化缓存把响应拆成实体表（Product:p1 = { __typename, id, title, price }）+ 字段引用表（ROOT_QUERY.featured → ["Product:p1", "Product:p2"]）。

三条规则决定可靠性。key 必须是 __typename:id：只用 id 会让 Product:1 与 User:1 串数据；只用列表下标更糟，重排后第 0 位指向另一个实体，UI 显示错人的昵称、错商品的价格。字段 key 必须含参数（product(id:"p1") 与 product(id:"p2") 是两个字段）。局部响应是合并不是覆盖：列表 4 个字段、详情 10 个字段，后写的详情要 merge 进同一实体。

失效分三档：实体级（删除 Product:p2，引用位置读成 null 并标记有洞）、字段级（清引用，下次读触发重取）、全局级（登出/切租户清空 store）。乐观更新是「快照 → 改本地 → 成功 commit / 失败 rollback」，快照必须深拷贝，浅拷贝会让 rollback 把改过的对象原样还回去。

完整代码示例 ​

ts
// 文件: examples/112-02-normalized-cache.ts（节选）
const key = `${entity.__typename}:${entity.id}`;
if (!entity.__typename || !entity.id) throw new Error('实体缺少 __typename 或 id');
const existing = this.entities.get(key);
this.entities.set(key, existing ? { ...existing, ...entity } : { ...entity }); // 合并，不覆盖

运行方式：npx tsx examples/112-02-normalized-cache.ts

应用实践 ​

  • 反例：按列表下标做 key。海外社交 App 的关注列表用 followed[0] 做缓存 key，取消关注后列表左移，第 0 位变成另一个人，头像昵称错位——这就是缓存串数据，正确 key 是 User:u_123。
  • mutation 后用 update 写缓存（createOrder 返回 Order 并前插订单引用），避免整页重取。
  • 登出、切账号、切站点必须清 store，不能只清 token。

最佳实践 ​

  • 默认 cache-first，价格/库存用 cache-and-network 加 loading 态；乐观更新只用于点赞、收藏、勾选，下单/支付必须等服务端确认。

112.5 分页与错误处理：cursor、partial errors 与重试 ​

概念解析 ​

标准形态是 Connection：edges { cursor node } + pageInfo { endCursor hasNextPage }。offset 翻页遇到插入/删除会重复或漏项，深分页还要扫 OFFSET；cursor 编码排序键，基本稳定，但不能跳页。

客户端合并三件事缺一不可：按实体 id 去重（页边界可能重叠）、按 cursor 排序（乱序到达或中间插入后仍保持时间序）、hasNextPage 只认最新响应（旧页的 true 不能把已到底的状态顶回去）。滚动触底还要用同一 endCursor 做 in-flight 去重。

错误处理最容易被 REST 思维带偏：HTTP 200 不等于成功。errors + data 是部分成功，按 error.path 定位并降级；只有 errors（data: null）是整体失败（鉴权、语法、变量校验）。只有网络错误、429、5xx 才退避重试；401 走刷新令牌，变量/业务错误不重试；mutation 重试必须带幂等键。

完整代码示例 ​

ts
// 文件: examples/112-03-cursor-pagination.ts（节选）
const byId = new Map<string, Edge<T>>();
for (const edge of [...this.edges, ...connection.edges]) {
    if (!byId.has(edge.node.id)) byId.set(edge.node.id, edge); // 按实体 id 去重
}
this.edges = [...byId.values()].sort((a, b) => a.cursor.localeCompare(b.cursor));
this.hasNextPage = connection.pageInfo.hasNextPage; // 只认最新一页

运行方式：npx tsx examples/112-03-cursor-pagination.ts

应用实践 ​

  • 筛选条件变化必须 reset()，清空 edges/endCursor/hasNextPage，否则新旧筛选混排。
  • 下拉刷新取新首页后合并去重、替换头部，不要清空列表造成白屏。
  • 部分错误按字段降级：价格失败显示「暂不可售」，评论失败隐藏评论区，主 CTA 仍可用；用 error.path 映射 UI 区块，而不是统一 toast。

最佳实践 ​

  • 列表 key 用实体 id；每个 tab/筛选维护独立游标；401 走刷新令牌，不进入重试队列。

112.6 Subscription 与实时：WS、断线、背压 ​

概念解析 ​

Subscription 把 GraphQL 推到长连接，但传输层不属于 GraphQL。协议要分清：subscriptions-transport-ws 已停止维护，新标准是 graphql-ws（子协议 graphql-transport-ws），接错直接握手失败。

生命周期：connection_init → connection_ack → subscribe → next* → complete/error。工程难点在后半段：

  • 断线：指数退避 + 抖动重连，重连后重新发起全部活跃订阅；服务端不补发断线期间的事件。
  • 事件缺口：重连后先用 query 按游标（lastSeenId/updatedAt）补齐，再恢复订阅，否则永久丢消息（参见 第三十九部分 · IM）。
  • 背压：推送快于渲染时不能无限堆积。同类合并（只保留最新价/最新在线状态）、按帧批量消费、低优先级可丢。
  • 生命周期：页面隐藏时暂停或降频，回前台补拉；同一 topic 共享一条连接，不能每个组件开一条 WS。
方式方向优点限制
WebSocket双向低延迟，高频双向需 Upgrade，连接数有上限
SSE服务端→客户端走 HTTP、自动重连单向，HTTP/1.1 连接数受限
轮询拉最稳、最简单延迟与成本高，只适合低频

应用实践 ​

  • 直播拍卖只推「最高价 + 版本号」，客户端丢弃旧版本帧；重连先拉快照再订阅，避免价格跳变。
  • 社交通知只推「未读数 + 最新 N 条」，完整列表走 query；已读 mutation 先本地减数，失败回滚。
  • 共享连接用引用计数：组件卸载只取消自己的 subscribe，活跃订阅归零后延迟关闭。
  • 监控连接初始化、重连次数、事件延迟、丢帧数——没有指标，弱网问题只能靠猜。

最佳实践 ​

  • 订阅载荷只带变更最小集 + 版本/游标；重连退避封顶（如 30s）并加抖动，避免全体客户端同时重连打垮网关。

112.7 性能与安全：复杂度、深度、持久化查询与 BFF ​

概念解析 ​

GraphQL 把「查多少」的权力交给客户端，服务端必须组合八道防线：深度上限（静态 AST 7~10 层）、字段权重成本（连接字段 × first 倍数）、分页钳制（强制 1..50/100）、同层同名字段计数（防 alias 放大）、持久化查询（只执行预注册 hash）、关闭内省（禁 __schema/__type）、字段级鉴权与租户隔离、BFF 收口私有凭证。

成本模型必须可解释：products(first:10){id title price} 成本 35，而 products(first:100){reviews(first:20){...}} 是 6605，差距 188 倍，人眼 review 看不出来。持久化查询（APQ/allowlist） 只发 hash + operationName，请求体更小、天然形成白名单，代价是发布流程要同步注册。BFF 负责隐藏上游凭证与 Schema、聚合多上游、租户隔离与限流。

完整代码示例 ​

ts
// 文件: examples/112-04-complexity-guard.ts（节选）
const multiplier = ctx.cfg.connections[field.name] ? pageSize(field) : 1;
const cost = weight + childCost * multiplier;
// products(first:10){id title price}     → 35
// products(first:100){reviews(first:20)} → 6605，直接拒绝

运行方式：npx tsx examples/112-04-complexity-guard.ts

应用实践 ​

  • 预算按页面分配：首屏主查询 500~1000，次要模块 100~300；超限就拆查询或减小 first。
  • CI 卡查询变更：operation 文档与成本报告一起跑，新增嵌套连接导致超限即失败。
  • 支付/下单 mutation 单独令牌桶限流 + 幂等键，防止重复提交。

最佳实践 ​

  • 深度与成本限制放网关/BFF 统一做；上线前用真实 Schema 跑最坏查询（最大分页 × 最深嵌套）。

112.8 自测题 ​

先自己作答，再展开参考答案。

1. GraphQL 解决了 over/under fetching，为什么还有 N+1？【基础】

它只解决接口形状，不解决 resolver 取数：20 条帖子的 author 仍可能各查一次库。客户端 N+1 用 BFF 聚合，服务端 N+1 用 DataLoader 按 key 批量；前者看请求数，后者看单请求 SQL 次数。

2. `String!` 与 `String` 的差别？非空字段解析失败会怎样？【基础】

String! 永不返回 null。非空字段抛错会向上冒泡到最近的可空父级：父级变 null 并附一条 error，响应仍是 200；整条链非空则 data: null。所以价格、库存应保持可空，留出降级空间。

3. interface 与 union 的适用场景？【进阶】

interface 用于共享字段的同类实体，取实现独有字段要 ... on Product { price } 或先取 __typename。union 用于互斥结果（商品/用户/评论混合搜索），只能内联片段取字段。两者都要对未知类型兜底。

4. 归一化缓存 key 为什么必须是 `__typename:id`？【进阶】

只用 id 会让 Product:1 与 User:1 互相覆盖；只用列表下标，重排后第 0 位指向另一实体，头像价格错位——最常见的缓存串数据。字段 key 还要带参数。

5. 乐观更新为什么必须保存深拷贝快照？【进阶】

浅拷贝只复制 Map 外壳，实体仍是同一引用：更新改的就是快照里那份对象，回滚等于把错误值写回去。实体要逐条 { ...entity }，引用数组也要复制，回滚后清空快照栈。

6. cursor 相比 offset 的优势？合并多页要做哪三件事？【进阶】

cursor 按排序键定位，数据插入/删除不重复不漏项，深分页不扫 OFFSET，但不能跳页。合并要：按实体 id 去重、按 cursor 排序、hasNextPage 只认最新响应；另用 endCursor 做 in-flight 去重。

7. HTTP 200 但响应有 `errors`，怎么分类处理？【进阶】

errors + data 是部分成功，按 error.path 降级（价格占位、评论隐藏），主流程继续；只有 errors（data: null）是整体失败，鉴权走刷新令牌，语法/变量错误不重试。只有网络/429/5xx 才退避重试。

8. Subscription 断线重连后，为什么不能只重新 subscribe？【挑战】

订阅只保证连接期间的事件，断线窗口不补发。正确顺序：重连 → 按游标 query 补齐缺口 → 恢复订阅；重叠部分用事件 id 幂等去重，并做同类合并、按帧消费的背压控制。

9. 为什么生产要用持久化查询/BFF？【挑战】

任意查询可被构造成超深/超宽/alias 放大刷爆 resolver，也能靠 introspection 摸清 Schema。持久化查询只执行已注册 hash，天然白名单；BFF 把 private token、跨租户聚合与上游 Schema 留在服务端。

112.9 本章避坑清单 ​

#坑点现象根因正确姿势
1把 GraphQL 当 REST 用每组件各发 query，首屏瀑布没按页面聚合一页一个主 operation
2无脑加 !单字段失败导致整块 data 为 null非空错误向上冒泡只给必然存在的字段加非空
3变量不前置校验一次往返后才报类型错误直接透传用户输入发请求前校验五类错误
4用户输入拼进查询串无法缓存、存在注入面字符串模板拼 query一律走 variables
5缓存 key 只用 id商品与用户同 id 字段互串缺 __typename 维度key 用 __typename:id
6缓存 key 用列表下标重排后头像/价格错位位置不是稳定身份用实体 id，列表只存引用
7字段 key 不带参数不同筛选列表互相污染忽略 arguments 是 key 的一部分key 含规范化参数
8局部响应覆盖实体详情查询后列表字段丢失写缓存用覆盖而非合并同实体 merge
9乐观更新浅拷贝快照回滚后仍是错误值快照共享实体引用实体与引用数组都深拷贝
10mutation 只返回 success缓存无法更新，整页重取响应没带被修改实体返回实体 + update 写缓存
11分页不按 id 去重触底加载出现重复卡片页边界重叠merge 时按 id 去重
12旧页 hasNextPage 覆盖新页已到底仍继续请求状态被过期响应改写只认最新 pageInfo
13把 200 当成功页面空白但无报错忽略 errors[]按 path 降级，区分整体/局部
14重试所有失败下单重复、越重试越糟没区分可重试错误只重试网络/429/5xx + 幂等键

心法：GraphQL 把「取什么」的自由给了客户端，也把「成本与一致性」的责任给了客户端。查询要算清成本，缓存要认准身份，实时要补齐缺口——这三件事想不明白，上 GraphQL 只会把 REST 的问题换一种形式重演。
