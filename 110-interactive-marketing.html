本部分内容 ​

这一册补齐「增长玩法」这条链路：任务、签到、抽奖、裂变、拼团在前端长什么样，以及它们共同的底座——状态机、额度账本、归因规则、风控决策。和相邻册的分工是：109 册讲游戏内核与 3D 表现，本册不碰渲染；69 册讲埋点 SDK 与数据质量，本册只讲玩法的漏斗与 AB 口径；43 册的场景偏电商交易，本册补的是交易之前的「拉新—促活—转化」。读完你能独立设计一套可上线、可对账、刷不穿的互动活动，并能回答面试里「抽奖怎么防超发」「裂变归因怎么算」这类问题。

110.1 玩法地图与业务模型 ​

概念解析 ​

互动玩法不是「做个转盘」，而是把业务目标翻译成一套可计算的行为激励。三类目标对应不同玩法：

目标典型玩法核心指标常见失败
拉新邀请返现、拼团、助力砍价邀请绑定率、K 因子、CAC归因被老用户薅穿、互刷
留存每日签到、成长任务、积分D1/D7/D30 留存、任务完成率奖励通胀、任务可脚本刷
转化抽奖券、下单返抽奖、盲盒支付转化率、ROI、复购概率不公示、库存超发

口径必须先定义再动手，否则前端做完页面才发现「数据对不上」：

  • CAC = 投放费用 ÷ 新增激活用户数；裂变带来的新增要单列，否则会把自然量算进投放效率。
  • ROI = 增量毛利 ÷ 获客成本。裂变活动必须用增量口径（有活动 vs 无活动的对照组），用总量会把老用户复购算成活动功劳。
  • K 因子 = 邀请转化率 × 人均成功邀请数。K < 1 时裂变只是「加速消耗预算」，不是自增长。
  • 留存 用同期群（cohort）算：某日新增用户在第 N 天仍活跃的比例，不能用「日活 ÷ 总用户」。

玩法的技术本质是三件事：进度（用户做了什么）、额度（能发多少、发过没有）、归属（这个新用户算谁的）。三者都必须在服务端收敛，前端只负责展示与采集事实。

应用实践 ​

以出海社交电商的「邀请返现」为例（Temu/SHEIN 类 invite-earn 的通用结构）：老用户分享邀请码 → 新用户落地页填写 → 首单后双方得券。业务上最容易翻车的是归因：如果允许「注册后任意时刻填码」，大量老用户会被重新归因一遍，CAC 报表瞬间失真。正确做法是先定窗口（如首次访问 7 天内可绑、绑定后 30 天内首单有效），再把规则写进接口而不是活动页文案。

最佳实践 ​

  • 每个玩法上线前先写清「奖励从哪来、上限多少、什么条件发、谁来审核」，这四件事决定后端模型，不是 UI。
  • 预算按「预算池 + 日限额 + 单用户上限」三层控制，任何一层打满即停，不靠运营盯盘。
  • 指标看板与玩法同批上线：没有漏斗数据的活动等于不可复盘。

110.2 任务体系 ​

概念解析 ​

任务是「行为 → 进度 → 奖励」的通用容器。把任务抽象成 DSL，运营配置而不是每次发版：

字段示例说明
iddaily_checkin任务唯一标识
metriccheckin_days进度来源的指标名
target10达标阈值
perioddaily / weekly / once周期，决定进度 key
reward{ coins: 10 }奖励内容，金额/券/积分
stackablefalse是否可与同类任务叠加

进度聚合的关键是事件溯源：客户端只上报「发生了什么」（eventId, userId, taskId, amount），服务端累加并封顶。上报必须带幂等键，因为移动端重试、弱网重发、消息队列至少一次投递都会造成重复。只靠「前端按钮禁用」防重是不够的——接口可以被直接调用。

发奖必须走账本（grant ledger），而不是「查进度 → 发币」两步判断。账本 key 用 userId:taskId:period 建唯一索引，先写入再发币：并发领奖时数据库唯一约束只会让一个请求成功，其余返回「已领取」。这就是幂等的物理保证，比分布式锁便宜且可靠。

状态机只有三态，且单向：

in_progress --进度达标--> claimable --领奖成功--> claimed
      ^                                        |
      +-------------- 新周期新 key -------------+

claimed 不能回退；跨周期不是「重置同一条记录」，而是换 key 产生新状态。把周期放进 key，历史账本天然可审计。

核心代码（节选，完整文件见 examples/110-01-task-reward.ts） ​

ts
// 文件: examples/110-01-task-reward.ts
// 任务体系：事件上报聚合进度 + 事件幂等 + 达标后幂等领奖 + 按周期重置

private key(userId: string, taskId: string, period: string): string {
    return `${userId}:${taskId}:${period}`;
}

report(e: ReportEvent): ReportResult {
    const def = this.defs.get(e.taskId);
    assert.ok(def, `未知任务 ${e.taskId}`);
    const state = this.getState(e.userId, e.taskId, e.period);
    if (this.seenEvents.has(e.eventId)) {
        // 重试/网络重发：直接返回当前状态，绝不二次加进度
        return { accepted: false, duplicated: true, state, progress: this.getProgress(e.userId, e.taskId, e.period) };
    }
    this.seenEvents.add(e.eventId);
    const k = this.key(e.userId, e.taskId, e.period);
    const next = Math.min(def.target, (this.progress.get(k) ?? 0) + e.amount);
    this.progress.set(k, next);
    return { accepted: true, duplicated: false, state: this.getState(e.userId, e.taskId, e.period), progress: next };
}

claim(userId: string, taskId: string, period: string): ClaimResult {
    const k = this.key(userId, taskId, period);
    const state = this.getState(userId, taskId, period);
    if (state !== 'claimable') {
        return { ok: false, duplicated: state === 'claimed', grantedCoins: 0, state };
    }
    const def = this.defs.get(taskId);
    assert.ok(def, `未知任务 ${taskId}`);
    if (this.grants.has(k)) {
        return { ok: false, duplicated: true, grantedCoins: 0, state: 'claimed' };
    }
    this.grants.set(k, def.rewardCoins); // 账本先落库，唯一索引兜住并发
    this.wallets.set(userId, this.getBalance(userId) + def.rewardCoins);
    return { ok: true, duplicated: false, grantedCoins: def.rewardCoins, state: 'claimed' };
}

运行方式：npx tsx examples/110-01-task-reward.ts

应用实践 ​

海外 App 的签到任务常配「连续签到 7 天翻倍」。实现上不要把「连续」写进前端计时器：前端在后台被挂起、跨时区、用户改系统时间都会让连续天数错乱。正确做法是服务端按用户所在时区计算「自然日」，存 lastCheckinDate 与 streak，断签时归零；前端只展示服务端返回的 streak。同一用户的签到请求用 userId + 日期 作为幂等键，重复点击只返回今天已签。

最佳实践 ​

  • 任务进度只信服务端聚合结果；前端本地进度用于即时反馈，失败时以服务端回包覆盖。
  • 奖励发放拆成「写账本」和「加余额」两个事务步骤，中间用消息队列重试，保证不丢奖也不重复。
  • 任务配置变更要版本化：老周期按旧版本结算，新周期才用新规则。

110.3 抽奖与概率 ​

概念解析 ​

抽奖的核心是权重表，不是百分比：把所有奖品权重相加得到总权重，单奖概率 = 权重 ÷ 总权重。用整数权重（如总量 10000）避免浮点误差，也让公示概率可精确推导。前端永远不参与抽奖计算——一旦随机数和奖池在客户端，改内存就能必中。

保底是体验补丁，也是对公示概率的二次修正。运营常写「10 抽必出稀有」，实现方式是给每个用户维护一个计数器，连续未出稀有就递增，达到阈值时强制走保底分支。注意两点：保底只应发「最低满足档」，不能把大奖当保底发，否则库存瞬间打穿；另外保底后的综合概率（自然概率 + 保底补正）也必须公示，否则「单抽 0.06%」与用户实际体验不符。

概率伪随机指 Math.random() 一类的 PRNG：可预测、可复现，适合客户端动画与测试，不适合作为生产随机源。生产环境应由服务端用 CSPRNG 出结果，客户端只做滚动动画，且动画时长要做成「不确定」——固定 2 秒必出结果等于告诉脚本何时抓包。

并发扣库存是最容易出事故的地方。正确顺序是「原子扣减 → 出奖 → 落发奖记录」，扣减用数据库条件更新或 Redis Lua 保证 stock > 0 才减一；错误顺序是「先查库存 → 发奖 → 再减库存」，两个并发请求都能查到 1，最后发出去 2 份。

核心代码（节选，完整文件见 examples/110-02-lottery-weight.ts） ​

ts
// 文件: examples/110-02-lottery-weight.ts
// 奖池：权重归一化 + 保底计数器 + 概率公示校验 + 库存耗尽后的降级回退

const TOTAL_WEIGHT = 10000;

validatePublished(): void {
    for (const p of this.prizes) {
        const actual = (p.weight / TOTAL_WEIGHT) * 100;
        assert.ok(Math.abs(actual - p.publishedRate) < 1e-9, `${p.id} 公示 ${p.publishedRate}% 与配置 ${actual}% 不符`);
    }
}

draw(userId: string, roll: number = Math.random()): string {
    const available = this.prizes.filter((p) => p.stock > 0);
    const sinceRare = this.pity.get(userId) ?? 0;
    let picked: Prize;

    if (sinceRare + 1 >= this.pityLimit) {
        // 保底只发「最低满足档」的稀有奖，大奖留给自然命中，避免库存被瞬间打穿
        const guaranteed = available.filter((p) => p.tier >= 1);
        picked = guaranteed.reduce((a, b) => (b.tier < a.tier ? b : a));
    } else {
        const total = available.reduce((acc, p) => acc + p.weight, 0);
        let threshold = roll * total;
        picked = available[available.length - 1];
        for (const p of available) {
            if (threshold < p.weight) {
                picked = p;
                break;
            }
            threshold -= p.weight;
        }
    }

    if (Number.isFinite(picked.stock)) picked.stock -= 1; // 库存不足的奖品已从 available 剔除
    if (picked.tier >= 1) this.pity.set(userId, 0);
    else this.pity.set(userId, sinceRare + 1);
    return picked.id;
}

运行方式：npx tsx examples/110-02-lottery-weight.ts

应用实践 ​

某出海电商的「转盘抽 100 美元券」曾把库存校验放在前端：按钮置灰 + 本地计数。结果脚本直接调抽奖接口，库存扣到负数，最终超发数千张券。修复方案是服务端原子扣减 + 每人每日次数限制 + 发奖流水与券码一一对应；同时把「未中奖」也记一条流水，方便对账。

最佳实践 ​

  • 奖池配置走后台 + 审批 + 变更留痕，禁止前端硬编码；上线后锁配置。
  • 公示区写清「单抽概率、保底规则、综合概率、剩余数量、活动时间」，并保留历史版本。
  • 抽奖接口用 drawId 幂等：网络重试返回同一结果，不重复扣次数、不重复发奖。

110.4 社交裂变 ​

概念解析 ​

裂变 = 关系链 + 归因 + 回流。三件事缺一不可：

  1. 关系链：邀请码/邀请链接是弱关系，真正的关系链要靠「绑定」落库。绑定必须发生在登录后、首单前，并把 inviterId → inviteeId 写成唯一记录。
  2. 归因：一个被邀请人只能归属一个邀请人。行业有 first-touch（首次触点）与 last-touch（末次触点）两种口径。拉新场景建议 first-touch + 短窗口（如 7 天），因为 last-touch 会让渠道在最后一步互相抢单，且用户可能被「注册后补填邀请码」洗走。
  3. 回流参数：分享链接带 inviter_code、share_id、channel、scene，落地页必须在登录前把参数落到 cookie/localStorage 并上报一次 share_landing，否则登录跳转丢参，归因断链。

分享回流还要处理「App 未安装」：H5 落地 → 应用商店/深链 → 首次打开 App。参数经 deferred deep link 或剪贴板口令恢复，但剪贴板读取在 iOS 有隐私提示，不能作为唯一路径。

黑产最常用的三种打法：自邀（自己邀请自己）、同设备小号（一台手机注册多个号互邀）、互刷（A 邀 B、B 再邀 A 形成环）。识别靠「账号 + 设备 + 支付工具 + 手机号/邮箱哈希」的多维去重，以及关系图的环检测。

核心代码（节选，完整文件见 examples/110-03-invite-attribution.ts） ​

ts
// 文件: examples/110-03-invite-attribution.ts
// 邀请裂变：邀请码绑定 + 首次触达归因窗口 + 防自邀/同设备小号/互刷 + 奖励只结一次

const BIND_WINDOW_DAYS = 7;   // 首次访问后 7 天内可绑定
const SETTLE_WINDOW_DAYS = 30; // 绑定后 30 天内首购才结算

bind(inviterId: string, inviteeId: string, code: string, firstVisitAt: number, bindAt: number): BindResult {
    const owner = this.codes.get(code);
    if (!owner || owner !== inviterId) return { ok: false, reason: 'UNKNOWN_CODE' };

    const invitee = this.users.get(inviteeId);
    const inviter = this.users.get(inviterId);
    assert.ok(invitee && inviter, '双方必须已注册');

    // 1. 自邀：同一账号，或同一台设备上开的小号
    if (inviterId === inviteeId) return { ok: false, reason: 'SELF_INVITE' };
    if (inviter.deviceId === invitee.deviceId) return { ok: false, reason: 'SELF_INVITE' };

    // 2. 一个被邀请人只认第一次有效绑定，后来者不能抢
    if (this.bindings.has(inviteeId)) {
        return { ok: false, reason: 'ALREADY_BOUND', inviterId: this.bindings.get(inviteeId)!.inviterId };
    }

    // 3. 互刷：B 已归因给 A，B 再邀 A 即构成环
    const inverse = this.bindings.get(inviterId);
    if (inverse && inverse.inviterId === inviteeId) return { ok: false, reason: 'MUTUAL_FARMING' };

    // 4. 小号集中：该设备已有别的账号完成绑定，新账号不参与归因
    for (const b of this.bindings.values()) {
        const boundUser = this.users.get(b.inviteeId);
        if (boundUser && boundUser.deviceId === invitee.deviceId) {
            return { ok: false, reason: 'DEVICE_CONFLICT' };
        }
    }

    // 5. 归因窗口：从首次访问算起，超过 7 天不予归因（防止捡漏老用户）
    if (bindAt - firstVisitAt > BIND_WINDOW_DAYS) return { ok: false, reason: 'EXPIRED' };

    this.bindings.set(inviteeId, { inviterId, inviteeId, bindAt, settled: false });
    return { ok: true, inviterId };
}

运行方式：npx tsx examples/110-03-invite-attribution.ts

应用实践 ​

某海外社交 App 的「邀 1 人得 5 美元」活动，第一版把结算条件写成「被邀请人注册」，且归因窗口 90 天。上线两周后邀请量暴涨但留存没变：大量老用户把邀请码发给自己的第二台设备，注册即拿奖；还有 A/B 互邀的环。修复是把结算条件改为「首单且实付 ≥ 门槛」、窗口压到 30 天、同设备同支付工具去重，并按增量口径重算 ROI，预算才回到可控区间。

最佳实践 ​

  • 绑定关系落库即不可变；要改归属只能走客服工单并留审计。
  • 奖励分期发放（注册给小额、首单给大头、复购再给尾款），比一次性发完更能抗刷。
  • 活动页展示「奖励规则与到账时间」，减少客服工单，也是合规要求的一部分。

110.5 防刷与风控 ​

概念解析 ​

风控不是一道校验，而是分层拦截：入口层（频控）→ 业务层（资格/次数/幂等）→ 决策层（风险评分）→ 处置层（放行/挑战/拒绝/事后追回）。

设备指纹是弱标识，不能当唯一身份。可用信号包括：UA、屏幕、时区、语言、Canvas/WebGL 哈希、安装 ID（iOS IDFV、Android 的 app set ID）。它在隐私政策收紧后越来越不稳定：iOS 卸载重装会变，Android 限制广告 ID，浏览器指纹可被伪造。工程上应「多信号加权 + 允许漂移」，而不是「指纹不等就拒绝」——那会误杀正常换机用户。

频控优先用滑动窗口而不是固定窗口。固定窗口在边界处会放过 2 倍流量：第 59 秒打满 10 次，第 61 秒又打满 10 次，实际 2 秒内 20 次。滑动窗口记录每次请求时间戳，只统计最近 N 秒；分布式环境用 Redis ZSET 或令牌桶，单机内存版只适合演示。

幂等要覆盖三个写操作：上报进度、抽奖扣次数、发奖。共同点是先落唯一键（eventId、drawId、grantKey），重复请求返回首次结果，而不是再执行一遍。

决策引擎输出三档而不是布尔值：allow 直接放行；challenge 拉验证码/滑块/人脸，正常用户一次通过，脚本成本上升；deny 直接拒绝并记录。黑名单设备、设备维度超限用 deny；同一设备短时间登录 3 个以上账号、同一账号短时间切换多台设备用 challenge——这两类信号有误杀可能，不能一刀切拒绝。

核心代码（节选，完整文件见 examples/110-04-anti-fraud-rate-limit.ts） ​

ts
// 文件: examples/110-04-anti-fraud-rate-limit.ts
// 风控决策器：滑动窗口频控（账号 + 设备双维度）+ 聚集识别 + 黑名单

check(userId: string, deviceId: string, now: number): CheckResult {
    if (this.blacklist.has(deviceId)) {
        return { decision: 'deny', reason: 'BLACKLIST_DEVICE', riskScore: 100 };
    }
    // 记录本次请求；被拒绝的请求也计数，防止换账号继续刷
    const accountCount = this.hit(this.accountHits, userId, now);
    const deviceCount = this.hit(this.deviceHits, deviceId, now);
    const accountsOnDevice = this.touchRelation(this.deviceAccounts, deviceId, userId, now);
    const devicesOnAccount = this.touchRelation(this.accountDevices, userId, deviceId, now);
    const riskScore = Math.min(
        100,
        (accountsOnDevice - 1) * 20 + (devicesOnAccount - 1) * 15 + Math.max(0, accountCount - 5) * 5,
    );

    // 硬限流优先：任一维度超限直接拒绝
    if (deviceCount > this.deviceLimit) {
        return { decision: 'deny', reason: 'DEVICE_RATE_LIMIT', riskScore: Math.max(riskScore, 80) };
    }
    if (accountCount > this.accountLimit) {
        return { decision: 'deny', reason: 'ACCOUNT_RATE_LIMIT', riskScore: Math.max(riskScore, 70) };
    }
    // 聚集行为：同一设备短时间登录大量账号 / 同一账号切换大量设备
    if (accountsOnDevice >= 5) return { decision: 'deny', reason: 'MULTI_ACCOUNT_DEVICE', riskScore: 100 };
    if (accountsOnDevice >= 3) {
        return { decision: 'challenge', reason: 'MULTI_ACCOUNT_DEVICE', riskScore: Math.max(riskScore, 60) };
    }
    if (devicesOnAccount >= 3) {
        return { decision: 'challenge', reason: 'MULTI_DEVICE_ACCOUNT', riskScore: Math.max(riskScore, 50) };
    }
    return { decision: 'allow', reason: 'OK', riskScore };
}

运行方式：npx tsx examples/110-04-anti-fraud-rate-limit.ts

应用实践 ​

海外投放买量期间，黑产会用「群控设备 + 接码平台」批量注册领新人券。单看 IP 拦不住（代理池），单看账号也拦不住（每个号都真实）。有效的组合是：设备维度限流（一台设备每天最多 N 个新账号领券）+ 支付工具去重（同一张卡/同一 Apple ID 不重复）+ 行为序列（注册后 10 秒内直接下单、收货地址高度集中）+ 事后追回（券未核销则冻结）。关键是不要把阈值写死在前端，也不要在活动页暴露完整规则。

最佳实践 ​

  • 风控规则可配置、可灰度：先观察（只记录不拦截）一周，确认误杀率再切 challenge，最后才 deny。
  • 每一条拦截都要有 reason 和 requestId，方便客服申诉与复盘。
  • 活动预算与风控联动：某渠道风险分异常升高时自动降预算，而不是等人发现。

110.6 合规红线 ​

概念解析 ​

互动营销的合规不是「法务最后看一眼」，而是产品模型的约束条件。几条高频红线：

红线具体要求工程落点
概率公示奖品、数量、概率、保底规则、活动时间可查；不得暗改奖池配置审批 + 前端公示组件读同一份配置 + 版本留痕
诱导分享/关注不得以奖励强制用户分享到群/朋友圈，不得「分享后才可领」奖励条件与分享动作解耦；分享是可选加分项，不是前置门槛
隐私与数据收集设备/通讯录/位置需告知并取得同意（GDPR/CCPA）同意管理 + 最小化采集 + 指纹字段脱敏 + 保留期限
未成年人抽奖、付费、邀请返现需年龄门槛（COPPA、GDPR Art 8）年龄门 + 未成年人禁用付费抽奖 + 家长同意流程
广告法/虚假宣传禁用「100% 中奖」「第一」「最佳」等绝对化或无法证实的表述文案审核词表 + 上线前自动扫描
博彩边界抽奖不得直接兑换现金、不得形成「投入—随机—变现」闭环奖品只能实物/券/积分；提现与抽奖物理隔离

特别提醒「概率公示」的细节：只写「稀有奖 1%」不够。若存在保底，用户实际获得稀有奖的概率高于单抽概率，必须同时公示综合概率及计算口径；若奖池分时段补库存，剩余数量也应可查。反过来，公示 1%、后台实际配置 0.6%，属于虚假宣传，风险远大于活动本身收益。

「诱导分享」在不同平台尺度不同：微信生态明确禁止利诱分享/关注，海外平台更多依赖开发者政策与反垃圾条款。通用安全做法是：分享带来「一次额外抽奖机会」可以，但分享失败不能扣减已有奖励，也不能检测「是否分享成功」来卡发奖——平台并不提供可信的分享成功回调，所谓检测本身就是违规信号。

应用实践 ​

出海产品要同时满足多地要求：面向欧盟用户时，设备指纹与归因参数属于个人数据，落地页需 Cookie/同意横幅，且拒绝非必要追踪时活动仍可参与（不能「不同意就不让玩」）。面向美国 13 岁以下用户，抽奖类玩法默认关闭或走家长同意。中国境内活动还要注意《反不正当竞争法》对抽奖式有奖销售最高奖金额的限制（现行上限 5 万元），以及《规范促销行为暂行规定》对促销规则明示的要求。

最佳实践 ​

  • 活动配置里加「合规字段」：概率公示文案、活动规则链接、隐私政策版本、年龄限制，缺失则不允许发布。
  • 文案与奖品清单走同一套审核流，避免「页面写 iPhone、后台配的是券」。
  • 留存活动快照（配置 + 页面 + 时间），监管问询时能自证。

110.7 数据闭环 ​

概念解析 ​

玩法上线只是开始，能不能复盘取决于漏斗埋点是否同口径。一次裂变活动的标准漏斗：

步骤事件关键属性健康线参考
曝光campaign_exposecampaignId、位置、人群包曝光去重按用户/日
点击campaign_clickcampaignId、素材、渠道点击率 3%~8%（信息流）
参与task_start / draw_start玩法类型、入口参与率 = 参与/点击
完成task_complete / draw_result是否中奖、奖品档位完成率骤降多为规则太复杂
领奖reward_claim奖励类型、金额领取率反映信任度
分享share_click渠道、shareId分享率
绑定invite_bind邀请人、渠道、窗口绑定率
结算invite_settle首单金额、归因方式结算/绑定 = 有效裂变率

所有事件必须带 campaignId、variant（AB 分组）、channel、userId（匿名期用 deviceId），否则跨活动无法比较。上报要防重复：同一 eventId 只计一次，曝光用「用户 + 素材 + 日」去重，点击不做去重但要做频控。

AB 实验的分桶要稳定且正交：用 hash(userId + experimentId) % 100 落在流量区间内决定分组，同一用户每次进来结果一致；多个实验按 layer 分层，避免互相干扰。只看提升不够，要看增量与显著性：样本量不足时先别下结论，尤其裂变类指标方差极大。

归因分三层：渠道层（UTM/投放平台 click id）、落地层（deep link 参数）、结算层（服务端按窗口与规则裁决）。前端只负责把参数无损透传并在登录前落库，归因裁决永远在服务端——否则改 localStorage 就能把自己算成邀请人。

ts
// AB 分桶：稳定哈希，同一用户在同一实验里永远同组
function bucket(userId: string, experimentId: string, traffic = 100): number {
    let h = 2166136261;
    const s = `${experimentId}:${userId}`;
    for (let i = 0; i < s.length; i++) {
        h ^= s.charCodeAt(i);
        h = Math.imul(h, 16777619);
    }
    return (h >>> 0) % 100 < traffic ? (h >>> 0) % 2 : -1; // -1 表示未进入实验
}

应用实践 ​

评估「邀请返现」是否值得继续投，正确做法是开一个 10% 持有组（eligible 但不展示活动），对比两组的 30 天增量首单与 CAC。若只看活动组的总 GMV，会把原本就会下单的用户算成活动效果，导致预算越投越亏。海外投放还要注意 iOS ATT 后归因信号缺失，需结合 SKAdNetwork 汇总值与后端自有归因做校准。

最佳实践 ​

  • 埋点方案与活动配置同源：campaignId、奖品档位、AB 分组由配置下发，前端不手写字符串。
  • 每天对账：发放流水条数 = 领奖事件数 = 券码核销预扣数，任一不等先停活动再查。
  • AB 实验先定指标与样本量，再看结果；禁止「跑完再挑一个显著指标」。

110.8 自测题 ​

先自己作答，再展开参考答案。

1. 任务体系为什么需要 eventId 和 grantKey 两层幂等？只做一层会怎样？【基础】

两层解决的是两个不同问题：

  • eventId 防的是进度重复累加：弱网重试、消息队列至少一次投递会让同一条行为上报两次，没有事件去重就会多加进度。
  • grantKey（userId + taskId + period）防的是奖励重复发放：用户连点领奖、接口重试、并发请求都会进入发奖逻辑，没有账本唯一键就会发两次。

只做 eventId：领奖接口被直接重试仍会重复发币。只做 grantKey：进度会被重复上报推高，虽然只发一次奖，但用户可能提前达标（例如「分享 1 次」被记成 3 次），活动成本与数据都失真。

2. 为什么任务进度必须服务端聚合，前端本地累加不行？【基础】

前端本地状态可被修改、可被清空、跨设备不同步，且接口可绕过页面直接调用。若以本地进度为准发奖，等于把发奖权限交给客户端。正确分工是：客户端只上报「行为事实 + 幂等键」，服务端聚合、封顶、判定达标；前端拿服务端返回值做即时反馈，冲突时以服务端为准。

3. 抽奖权重、保底与概率公示之间是什么关系？为什么还要公示「综合概率」？【进阶】

单抽概率由权重决定：weight / 总权重。保底会改变用户实际获得稀有奖的概率分布——连续未中会提高下一次命中率，因此长期看实际获得率高于单抽概率。只公示单抽概率，用户体感与公示不符，容易被认定为信息不明确；正确做法是同时公示单抽概率、保底触发条件（如「连续 10 抽必出稀有」）和含保底的综合概率及计算口径。

另外保底应只发「最低满足档」，不能把限量大奖作为保底奖品，否则大奖库存会被保底逻辑提前打穿。

4. 并发抽奖如何避免奖品超发？「先查后扣」错在哪？【进阶】

「先查库存 → 发奖 → 再减库存」在并发下两个请求都能读到 stock = 1，各自发奖，最后库存变负。正确链路是「原子预扣 → 出奖 → 落发奖流水」：

  • 数据库用条件更新 UPDATE prize SET stock = stock - 1 WHERE id = ? AND stock > 0，返回影响行数为 0 即失败；
  • 或 Redis Lua 脚本把「判断 + 扣减」合成一个原子操作；
  • 再用 drawId 幂等，避免重试重复扣次数与重复发奖。

库存为 0 的奖品要从候选池剔除并重新归一化权重，而不是继续参与随机。

5. 邀请归因为什么推荐「首次绑定 + 短窗口」，而不是 last-touch？【进阶】

last-touch 会让渠道/邀请人在用户临门一脚时互相抢单，且给「注册后补填邀请码」留下空间——大量老用户会被重新归因，CAC 与 ROI 报表虚高。首次绑定 + 7 天窗口明确「谁先带来用户谁拿奖励」，规则稳定、可审计，也能防止用户被反复「洗号」。

归因还必须限定在合格事件上（如首单实付达到门槛），而不是注册；否则接码平台批量注册即可套利。

6. 自邀、同设备小号和互刷分别怎么识别？【进阶】
  • 自邀：邀请人 ID 等于被邀请人 ID，或双方设备指纹相同。
  • 同设备小号：同一设备上已有账号完成绑定，则新账号不参与归因；再叠加支付工具、手机号/邮箱哈希去重。
  • 互刷：检查关系图是否存在反向边（A 邀 B 且 B 邀 A），以及更长的环（A→B→C→A）。上线时做一次环检测，运行时拦截一度反向边即可覆盖大部分场景。

单一信号都会误杀（例如家人共用设备），所以识别结果应分档：可疑进 challenge/人工审核，确证才 deny 并追回奖励。

7. 固定窗口频控和滑动窗口的区别？固定窗口的边界问题是什么？【基础】

固定窗口按自然分钟/小时计数，实现简单但边界处会放过约 2 倍流量：第 59 秒打满限额，第 61 秒进入新窗口又能打满，2 秒内实际请求翻倍。滑动窗口只统计「最近 N 秒」内的请求时间戳，任意时刻都严格满足限额，代价是要存时间戳/用 ZSET，内存更高。高并发场景可用令牌桶近似滑动窗口，兼顾内存与平滑度。

8. 设备指纹为什么不能作为唯一身份？工程上应如何使用？【挑战】

设备指纹由 UA、屏幕、时区、Canvas/WebGL 等信号拼成，天然存在三类问题：碰撞（同型号同系统设备可能算出相同值）、漂移（升级、卸载重装、隐私设置变化会改变指纹）、伪造（脚本可篡改信号）。因此它只能作为风险评分的一个特征，不能作为「是同一人就拒绝」的硬条件。

工程做法：多信号加权 + 允许漂移 + 组合账号/支付工具/手机号哈希；对指纹只存哈希并设置保留期，遵循数据最小化；误判走 challenge 而非直接 deny，并保留申诉通道。

9. 互动营销的合规红线中，概率公示和诱导分享各要注意什么？【进阶】

概率公示：奖品/数量/单抽概率/保底规则/综合概率/活动时间都要可查，且前端展示与后台配置读同一份数据；改配置要审批留痕，不能暗改。只写「有机会中大奖」或概率与实际不符，属于信息不明确甚至虚假宣传。

诱导分享：不得以奖励强制分享、不得「分享后才可领奖」、不得伪造「分享成功检测」。分享可以作为可选加分项，但分享失败不能扣减已有权益。微信生态对此有明确规范，违者可能被封链。

10. 如何用漏斗与 AB 实验判断一个裂变玩法是否真的有效？【挑战】

先定义同口径漏斗：曝光 → 点击 → 参与 → 完成 → 领奖 → 分享 → 绑定 → 结算，每步带 campaignId、variant、channel，并按 eventId 去重。核心看三个比值：参与率（点击→完成）、分享率、有效裂变率（绑定→首单结算）。

AB 上设置 10% 持有组（不展示活动），比较 30 天增量首单与 CAC；只有「增量毛利 > 获客成本」且样本量足够、结果显著，才判定有效。若只看活动组总量，会把自然转化算成活动功劳。iOS 归因信号缺失时，用后端自有归因 + SKAdNetwork 校准，不迷信单一渠道报表。

13频控只在前端直接调接口绕过限流不是服务端强制网关/接口层限流，前端只做体验

心法：互动玩法的技术难点从来不是页面，而是「额度」与「归属」。额度要有账本（唯一键 + 原子扣减 + 幂等），归属要有规则（窗口 + 唯一绑定 + 多维去重）。前端把这两件事当成后端契约来消费，而不是自己实现；产品把概率、规则、预算当成可审计的配置，而不是文案。做到这两点，玩法才既能跑量，也能对账，更不会一夜之间被黑产刷穿。
