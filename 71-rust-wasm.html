71.1 为什么前端要引入 Rust：性能边界与适用象限 ​

71.1.1 概念解析 ​

JS 引擎已经足够快，但它的快是「赌出来的」——JIT 靠运行时观察做投机优化。三个结构性边界决定了某些任务 JS 天然吃亏：

JS 性能边界机理后果
JIT 预热与反优化热点代码才被编译为机器码；类型反馈一旦失效（deopt），直接跌回解释执行冷启动阶段慢、性能不可预测，首帧/首次计算抖动明显
GC 停顿堆上对象由垃圾回收器管理，主线程存在 STW（Stop-The-World）窗口大量临时对象的计算循环里，延迟长尾被 GC 主导
数值类型贫瘠只有 f64（Number）与 BigInt；i32 要靠位运算截断的潜规则，无 i64、无显式 SIMD加密、编解码等位运算密集任务事倍功半

WASM 恰好补在这三个缺口上：AOT 编译（性能可预测，无预热期）、无 GC 的线性内存（Rust 所有权编译期管理内存）、明确的数值类型（i32/i64/f32/f64 + SIMD 提案）。Rust 则是最适合产出 WASM 的语言——无 GC 的运行时产物小、内存安全保证不怕裸指针、wasm-bindgen 生态最成熟。

两个边界细节值得展开。deopt 的隐蔽性：一个跑了一千次都很快的函数，第一千零一次传入了形状不同的对象（多了个字段、数组里混了类型），JIT 就丢弃已编译的机器码回炉重造——这类抖动在真实用户环境里无法复现、无法预测，监控上表现为 P99 长尾。GC 长尾：计算循环里每轮 new 出的临时数组都是 GC 债务，办公系统页面一挂一整天，债务终要偿还。WASM 的线性内存里没有「对象」，只有字节——这是它性能可预测的根本原因，也是它用起来比 JS「麻烦」的原因（71.3 的边界成本由此而来）。

WASM 适用象限表（背下来，面试和立项都用得上）：

计算密集计算轻量
调用低频、数据整块✅ 最佳象限：滤镜、哈希、解析⚪ 无所谓，别折腾
调用高频、数据细碎⚠️ 先合并调用再评估❌ 边界开销碾压收益

❌ 两个明确不适合的象限：DOM 频繁交互（WASM 碰 DOM 必须绕道 JS 胶水层，一次 DOM 操作的跨界成本远超操作本身）与 IO 密集（网络/文件等待时间与算力无关，WASM 帮不上忙）。

71.1.2 典型应用场景 ​

企业级移动办公/桌面办公场景里，真正值得上 Rust + WASM 的清单：

  1. 加解密：国密 SM2/SM4、argon2 密码哈希、端到端加密的消息体——位运算密集 + 算法有现成 Rust crate，且端上（桌面端 Tauri/移动端 SDK）可复用同一份 Rust 源码。
  2. 大文件解析：万行 Excel 导入、百 MB 日志文件检索、PDF 预解析——计算密集且数据可以整块搬运，边界开销被摊薄。
  3. 图像/音视频处理：证件照裁剪压缩、OCR 预处理、会议水印——像素级卷积，17.4 已给过判断口诀，本章给工程落地。
  4. 端上复用 C/Rust 库：ffmpeg.wasm、sql.js 是别人的；自研算法（压缩、风控特征提取）编译一次，Web 端与桌面端共用。

共同特征：输入输出都是二进制整块数据、算法有现成 Rust/C 实现、计算量随数据规模线性增长。三条都满足的场景，闭着眼睛评估也不会太离谱；缺一条就要谨慎（见 71.3 的边界成本）。

71.1.3 可运行代码示例 ​

立项前先算账。下面这个评估器输入任务画像（计算量、调用频率、数据规模、边界穿越次数），用边界成本模型预估 WASM 净收益并给出建议：

ts
// 节选自 examples/71-01-wasm-decision.ts —— 核心模型
const MODEL = {
  jsMopsPerMs: 0.2, // JS 数值吞吐：约 200 Mops/s（JIT 预热后）
  wasmSpeedup: 4, // WASM 相对 JS 的典型提速倍数（2~8 取中性）
  crossingUs: 0.7, // 单次 JS↔WASM 边界穿越开销（微秒）
  copyUsPerKB: 0.8, // 数据进出线性内存的拷贝开销（微秒/KB）
};
// 决策规则：任务亚毫秒级 → 不做；边界占比 > 40% → 先合并调用；
// 净收益 ≥ 50% → 强烈推荐；≥ 25% → 先 benchmark 再全量

运行方式：npx tsx examples/71-01-wasm-decision.ts

输出会给出三个对照场景的结论：实时图像滤镜（强烈推荐）、表单实时校验（不推荐——边界占比 96%）、大文件分块哈希（强烈推荐——分块摊薄边界成本）。

71.1.4 最佳实践 ​

  1. 先 Profiler 再 WASM：大多数页面卡顿源于布局、网络与渲染（第 10 册），与算力无关。Performance 面板确认热点是纯计算函数后再立项。
  2. 优先复用现成 wasm 包：argon2-browser、wasm-zstd、sql.js 已经踩过坑，自研是最后选项。
  3. 把「4 倍提速」当上限承诺：对外汇报留余量，真实收益取决于数据形态与边界设计，用 71.4 的基准协议实测后再写进 OKR。
  4. 评估移动端体积预算：wasm 产物常见 +100KB~500KB，弱网环境要折算下载时间与编译时间的总账（见 71.4 流式编译）。

71.2 工具链与构建集成：rustup、cargo、wasm-pack 与 wasm-bindgen ​

71.2.1 概念解析 ​

四个工具各管一段，别混：

工具角色类比前端世界
rustupRust 工具链管理器：装 rustc、切换版本、安装编译目标 wasm32-unknown-unknownnvm + 平台 SDK 管理
cargo构建系统 + 包管理：依赖解析、编译、测试npm + webpack 的合体
wasm-bindgen生成 JS 胶水层与 .d.ts：处理字符串/对象/类在边界两侧的编解码手写胶水代码的代码生成器
wasm-pack编排器：一条命令跑完 cargo build + wasm-bindgen + 生成 package.json，产出可发 npm 的 pkg/ 目录针对 WASM 场景的脚手架

再加一个可选的 wasm-opt（Binaryen 工具链）：对产物做体积与速度的二次优化，见 71.4。

关键概念是 crate 类型：产出 WASM 的 crate 必须是 cdylib（C 动态库 ABI），在 Cargo.toml 里声明 { crate-type = ["cdylib"] } 形式；普通 Rust 库默认是 rlib，浏览器用不了。

另一个前置认知是 wasm-bindgen 的类型映射边界：数字、布尔、TypedArray、字符串可以直传；Rust 的 struct/enum 需要 serde 序列化；生命周期、泛型在边界处全部消失——导出签名时把它们「拍平」成边界支持的类型，是 Rust 侧 API 设计的主要工作。遇到「编译通过但 JS 拿到的类型不对」，九成是这里没拍平。

71.2.2 典型应用场景 ​

最小可工作链路（Vite 项目）：

toml
# wasm-crate/Cargo.toml —— 教学示意
[package]
name = "office-crypto"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
wasm-bindgen = "0.2"
rust
// wasm-crate/src/lib.rs —— 教学示意：导出给 JS 的函数
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn sm4_digest(data: &[u8]) -> Vec<u8> {
    // 纯计算：入参是线性内存里的切片，出征收口为一次性返回
    data.iter().map(|b| b.rotate_left(3) ^ 0x5a).collect()
}
bash
# 一条命令产出 pkg/（含 .wasm、胶水 .js、.d.ts、package.json）
rustup target add wasm32-unknown-unknown   # 一次性
wasm-pack build --target web               # target=web 产出 ESM 胶水

产出的 pkg/ 目录结构（以 --target web 为例）：

pkg/
├── office_crypto_bg.wasm   # 编译产物本体（业务算法在这里）
├── office_crypto.js        # JS 胶水层：init() 加载 + 类型编解码
├── office_crypto.d.ts      # TS 类型：导出函数签名完整映射
├── office_crypto_bg.wasm.d.ts
└── package.json            # 可直接 npm publish 的清单

TS 类型是自动生成的——Rust 侧的函数签名被映射为 TS 声明：

ts
// pkg/office_crypto.d.ts —— wasm-bindgen 自动生成，教学示意
export default function init(input?: RequestInfo | URL): Promise<void>;
export function sm4_digest(data: Uint8Array): Uint8Array;
export function alloc(len: number): number; // 线性内存分配（高级用法）
export function dealloc(ptr: number, len: number): void;
export const memory: WebAssembly.Memory;

前端工程接入（Vite）：

ts
// vite.config.ts 无需特殊配置——--target web 产出的 ESM 直接 import
import init, { sm4_digest } from "office-crypto"; // 指向上面的 pkg/

await init(); // 内部走 instantiateStreaming，见 71.5 的加载器
const digest = sm4_digest(new Uint8Array([1, 2, 3]));
//           ^? Uint8Array —— wasm-bindgen 生成的 d.ts 让 TS 全程有类型

webpack 5 项目则用 experiments: { asyncWebAssembly: true } 开启原生 wasm 支持，胶水层由 webpack 接管，业务代码 import 时拿到的是异步模块——迁移老项目时注意这个差异，同步 import 会报错。

71.2.3 产物分发与缓存策略 ​

  • 产物指纹化：.wasm 走 Vite 资产管道（assetsInclude 或直接放 public/wasm/ 自行加 hash），URL 带内容指纹后配 Cache-Control: immutable。
  • 预加载：首屏必用的 wasm 用 <link rel="preload" as="fetch" type="application/wasm" crossorigin> 提前拉取，与 JS 解析并行。
  • npm 分发：wasm-pack publish 产出标准包；内部库建议发包到私有 registry，业务工程只依赖版本号，不依赖构建机上的 Rust 工具链。
  • MIME 必须正确：服务器对 .wasm 返回 application/wasm，否则 instantiateStreaming 直接拒绝（17.4 提过，这里强调它是部署事故高发点）。

71.2.4 最佳实践 ​

  1. crate 只导出必要 API：每个 #[wasm_bindgen] 导出都会膨胀胶水层，导出面越窄，产物越小、TS 类型越干净。
  2. --target web vs bundler：Vite 项目两者皆可，web 更直观（显式 init()）；bundler 适合 webpack 5 的 asyncWebAssembly 自动接管。
  3. 锁死 toolchain 版本：仓库根放 rust-toolchain.toml 固定 channel 与 target，CI 与本地产物才可复现。
  4. 别让业务工程编译 Rust：wasm 产物由库仓库的 CI 构建并发包，业务工程 npm i 即用——前端同学机器上不需要 Rust。

71.3 JS 与 WASM 的边界成本：调用开销与数据搬运 ​

71.3.1 概念解析 ​

WASM 与 JS 之间有一道边界（boundary），每次穿越都有成本。量级概念（现代引擎，数量级估计）：

  • 纯函数调用穿越：几十 ns ~ 1µs/次。数字传参最便宜；引擎已优化到接近普通函数调用，但高频（每帧数百次）仍会累积成毫秒级。
  • 字符串传递：必须 UTF-8 编码 → 拷贝进线性内存 → WASM 侧解码，一来一回两次拷贝 + 两次编解码。字符串密集的场景（如模板拼接）成本陡增。
  • 对象传递：WASM 看不懂 JS 对象图，serde 序列化为 JSON/二进制再反序列化——本质是 IPC 序列化成本，大对象极贵。

线性内存模型：WASM 的全部内存是一块 WebAssembly.Memory（可增长的 ArrayBuffer）。JS 侧通过 new Uint8Array(memory.buffer) 视图读写；WASM 侧通过指针（u32 偏移）访问。数据交换的唯一通道就是这块 buffer——17.4 的 Worker 示例已经演示过「写入 → 调用 → 读回 → 释放」五步曲，本章不再重复，重点是穿越次数的架构设计。

什么时候 WASM 反而更慢——三种典型翻车：

  1. 每帧调用几百次小函数（粒子物理逐个粒子调用）→ 穿越开销超过计算本身；
  2. 每次调用传几 MB 字符串做正则 → 编解码 + 拷贝比正则还慢；
  3. 频繁返回大对象 → 序列化成本把 4 倍提速吃成 0.5 倍。

不同数据形态的边界成本对照（1MB 数据、单次往返的量级估计）：

数据形态穿越方式成本量级说明
数字传参寄存器级传递可忽略最便宜的穿越
二进制（TypedArray）一次性 memcpy 进线性内存亚毫秒首选形态
字符串UTF-8 编码 ×2 + 拷贝 ×2毫秒级文本越长越亏
JS 对象/数组serde 序列化 + 反序列化毫秒级起最贵，能免则免

71.3.2 设计原则：批量进、一次出 ​

把循环挪进 WASM 内部，边界只穿越两次：

ts
// ❌ 反模式：循环在 JS 侧，每像素穿越一次边界
for (const px of pixels) out.push(wasm.sharpen_one(px));

// ✅ 正确形态：整批搬进线性内存 → WASM 内循环 → 一次读回
const ptr = wasm.alloc(pixels.byteLength);          // 1. WASM 侧分配
new Uint8Array(wasm.memory.buffer, ptr).set(pixels); // 2. 整批写入
wasm.sharpen_all(ptr, pixels.length);                // 3. 一次调用，循环在 Rust 里
const out = new Uint8Array(wasm.memory.buffer, ptr, pixels.length).slice(); // 4. 一次读回
wasm.dealloc(ptr, pixels.byteLength);                // 5. 释放，防内存泄漏

进阶形态：SharedArrayBuffer + Worker。普通模式下数据要拷贝进线性内存；用 SharedArrayBuffer 作为 WASM 内存（需开启 wasm threads 与跨域隔离响应头 COOP/COEP），主线程与 Worker 中的 WASM 实例共享同一块内存、零拷贝。这是实时音视频处理（每帧 8MB，拷贝不起）的标准做法，Worker 侧的通信骨架见第 18 册。注意两个前提：响应头 Cross-Origin-Opener-Policy: same-origin 与 Cross-Origin-Embedder-Policy: require-corp 必须同时配置（否则 SharedArrayBuffer 被禁用）；Rust 侧需开启 atomics 特性并用支持线程的 target 配置，构建复杂度明显上升——非零拷贝不能忍的场景再上。

71.3.3 典型应用场景 ​

  • 整块数据一次处理：图像滤镜、文件哈希——天然「批量进一次出」，收益最大。
  • 状态驻留 WASM 侧：解析器、加解密上下文——初始化时建立状态，后续调用只传小指令与大结果指针，边界流量最小化。
  • 必须高频调用的场景：先改接口粒度（一次传一帧而非一个样本），改不动就放弃 WASM。

71.3.4 最佳实践 ​

  1. 接口设计按「帧」不按「点」：导出 process_frame(buffer) 而不是 process_sample(x)——把 O(n) 次穿越压成 O(1) 次。
  2. 数值走 TypedArray，杜绝中间对象：Float64Array/Uint8Array 可以零序列化拷贝；JS 对象数组必须先扁平化。
  3. 字符串能不传就不传：必须的文本（如解析器输入）一次传入后驻留，别每轮重复编码。
  4. 记得 dealloc：WASM 线性内存没有 GC，JS 侧忘记释放就是泄漏，长跑页面（办公系统一挂一整天）必现 OOM。

71.4 性能工程与体积优化：基准方法学与编译开关 ​

71.4.1 概念解析 ​

先学测量，再谈优化。WASM 立项最容易自欺欺人的环节就是 benchmark——四个陷阱：不预热（JIT 未编译的样本混入）、取均值（一次 GC 尖刺污染全部）、无对照组（绝对耗时没有意义，相对 JS 基线的加速比才有）、微基准失真（玩具循环不代表真实数据规模）。标准协议四步：预热样本丢弃 → 逐次独立计时 → IQR 剔除异常值 → 报中位数与 P95。

编译开关（Cargo.toml 的 [profile.release]）对体积的影响是数量级的：

toml
[profile.release]
opt-level = "z"     # 体积优先（速度优先用 3）；'s' 是折中
lto = true          # 链接期优化：跨 crate 内联 + 死代码消除
codegen-units = 1   # 单个代码生成单元，优化更彻底（编译变慢）
panic = "abort"     # 不要 Rust 的 unwind 运行时，省一大块
strip = true        # 剥离符号表

再配合两件套：wee_alloc（约 1KB 的迷你分配器，替换默认的 dlmalloc 可省几十 KB——代价是极限分配性能略降）与 wasm-opt -Oz（Binaryen 二次优化，常见再省 10%~30%）。一个裸 hello-world 的 wasm 从默认 ~1.6MB 压到 ~100KB 量级，全靠这组开关。wee_alloc 的接入只需两行：

rust
// src/lib.rs 顶部 —— 教学示意：替换全局分配器
#[global_allocator]
static ALLOC: wee_alloc::WeeAlloc = wee_alloc::WeeAlloc::INIT;

注意 wee_alloc 仓库已归档（官方建议评估 lol_alloc 等继任者），选型时看一眼社区状态——这正是「Rust 经验优先」JD 想考察的生态判断力。

71.4.2 流式编译与懒加载 ​

  • instantiateStreaming：编译与下载并行，首字节到达即开始编译——大产物（>1MB）的必选，前提是服务器 MIME 为 application/wasm（17.4 有基本用法，71.5 的加载器演示了它的失败回退）。
  • 懒加载：wasm 走 import() 动态导入 + 路由级分包，进入「文件导入」页才拉取解析器 wasm——首屏零成本：
ts
// 路由组件内 —— 教学示意：按需加载 wasm 能力
async function loadParser() {
  const { default: init, parse_log } = await import("log-parser-wasm");
  await init(); // 编译产物命中 HTTP 缓存时几乎零耗时
  return { parse_log };
}
// 按钮点击或路由进入时才调用 loadParser()，首屏 bundle 不含 wasm
  • 按需编译：模块级缓存编译结果，二次进入页面时 WebAssembly.compile 命中 HTTP 缓存的已编译产物（浏览器内部有编译缓存，指纹不变即可复用）。

71.4.3 可运行代码示例 ​

下面这个示例把基准协议跑给你看：同一份负载，JS 基线 vs「模拟 WASM」（1/4 计算量模拟提速 + 0.3ms 边界开销），输出中位数/P95/加速比，并演示「不预热只测首轮」会得到什么数据：

ts

71.4.4 最佳实践 ​

  1. benchmark 用生产数据规模：拿 1MB 测试文件测出来的加速比，无法外推到 500MB 真实文件——缓存行为、内存分配压力完全不同。
  2. 对照组必须是优化后的 JS：和「随手写的 JS」比赢了不算赢，和 TypedArray + 算法优化后的 JS 比才是真实收益。
  3. 体积看板化：把 wasm 产物字节数纳入 CI 产物报告，超阈值告警——体积回退比性能回退更容易被忽视。
  4. opt-level 按场景选：计算核心用 3，胶水/解析类用 z；可以拆成多个 crate 分别配置。
  5. 优化后必须回归 benchmark：LTO 与 -Oz 偶尔会让特定热点变慢（内联策略变化），每一档开关都要用 71.4.3 的协议验证一遍再上线。

71.5 落地模式与降级：能力探测、调试与 CI 缓存 ​

71.5.1 概念解析 ​

三个经过验证的落地模式，按接入难度排序：

模式特征边界设计典型案例
加密计算纯函数、无状态整块进整块出，最理想国密 SM4、argon2、文件指纹
大文件解析数据超内存预算分块流式喂入 + Worker 防卡 UI，进度回调节流Excel 导入、日志检索
解析器移植有状态、复用 Rust 生态状态驻留 WASM 内存，JS 只发指令Markdown/DSL 解析、自研协议

三个模式的工程要点各补一句。加密计算：优先找现成 Rust crate（sm4、argon2 都有维护良好的实现），自己的工作只剩写边界胶水——这是投入产出比最高的 WASM 入门项目。大文件解析：核心是「分块协议」——JS 侧用 File.stream() 或切片 slice() 逐块喂入，Rust 侧维护增量状态（哈希上下文、解析器游标），每块一次边界穿越；进度回调要节流（每 16ms 最多一次），否则 postMessage 本身成了瓶颈。解析器移植：Rust 生态的解析器（pulldown-cmark、nom 系）编译为 WASM 后，把「整个文档」一次性传入，解析结果以结构化事件驻留在 WASM 内存，JS 按偏移量取用——切忌逐 token 往返。

能力探测与降级是生产级与玩具的分水岭：老内核浏览器（企业内网常见）、MIME 配置错误、CDN 产物损坏都会让 WASM 加载失败。原则——功能不能消失，只能变慢：任何 WASM 能力都必须有同语义的 JS 降级实现，业务代码面向抽象接口编程，对底层实现无感。能力探测本身只要几行，但要在编译前就完成：

ts
// 教学示意：加载前的能力探测
function detectWasmSupport() {
  if (typeof WebAssembly !== "object") return "none";
  if (typeof WebAssembly.instantiateStreaming !== "function") return "no-streaming";
  return "full"; // SIMD/threads 等进阶特性需再分别探测
}

调试：wasm-pack build --dev 保留 DWARF 调试信息，Chrome DevTools 可以把 wasm 栈帧映射回 Rust 源码行；console_error_panic_hook crate 把 Rust panic 转成带栈的 JS 异常——生产环境去掉它们（体积与信息泄漏），但 staging 必须保留。

CI 里的 Rust 工具链缓存：GitHub Actions 里三层缓存——~/.rustup（工具链）、~/.cargo/registry（依赖源码）、target/（编译中间产物），缓存 key 必须包含 Cargo.lock 的哈希与 toolchain 版本，否则依赖升级后命中脏缓存。可直接用社区封装好的 action：

yaml

- uses: dtolnay/rust-toolchain@stable
  with:
    targets: wasm32-unknown-unknown
- uses: Swatinem/rust-cache@v2   # 自动按 Cargo.lock 哈希缓存 registry 与 target/
- run: |
    cargo install wasm-pack
    wasm-pack build --release --target web

- uses: actions/upload-artifact@v4
  with:
    name: wasm-pkg
    path: pkg/                   # 产物交给后续发布 job 发 npm

71.5.3 最佳实践 ​

  1. 降级实现与 WASM 共用测试用例：同一份 fixture 跑两种实现，结果逐字节比对——否则降级路径上线即腐化。

  3. Worker 里加载 wasm：大产物编译是 CPU 密集操作，放 Worker 里实例化（18 册的通信骨架），主线程零卡顿。
  4. CI 缓存 key 三要素：{ os, rust-toolchain.toml 哈希, Cargo.lock 哈希 }，缺一个都会踩到「本地能编、CI 不能编」或反过来。

71.6 WASM 与 Tauri command 的选择：同在 Rust 生态的边界 ​

71.6.1 概念解析 ​

桌面端项目（70 册）里 Rust 有两个出场位置，经常傻傻分不清：

  • WASM：Rust 编到 wasm32，跑在渲染进程的沙箱里。只有纯计算能力，碰不到文件系统、剪贴板、通知。
  • Tauri command：Rust 跑在主进程，通过 #[tauri::command] 暴露给前端，拥有全部系统能力。

选择规则一句话：纯计算 → WASM（可移植）；系统能力 → command（只有它能干）。

拿不准时按这张清单走一遍：① 需要读文件系统/剪贴板/系统通知/钥匙串吗？→ 是，command；② 计算结果要回 Web 端复用吗？→ 是，WASM；③ 单次数据量超过几 MB 吗？→ 是，倾向 WASM（避开 JSON IPC）；④ 只是胶水编排、计算很少吗？→ 是，留在 JS/TS 别折腾。四个问题都「否」的纯计算小任务——通常不值得引入任何 Rust。

71.6.2 序列化成本对照 ​

两者的「跨界成本」形态完全不同，大 payload 场景差距悬殊：

维度WASM（渲染进程内）Tauri command（跨进程 IPC）
数据通道共享线性内存，TypedArray 直接拷贝JSON 序列化（默认）经 IPC 桥传递
1MB 数据单次调用一次 memcpy，亚毫秒级JSON 编码 + 传输 + 解码，毫秒级起
高频小调用几十 ns~1µs/次IPC 固定开销更高，且是异步
返回二进制指针 + 长度，零序列化需 base64 或自定义 raw 协议，更贵
能力边界纯计算文件/网络/系统 API 全能
可移植性同一份 wasm 跑 Web 与桌面锁死 Tauri，Web 端无法复用

实战推论：大文件哈希这类纯计算，在 Tauri 应用里也优先 WASM——command 的 JSON IPC 传 500MB 文件内容是灾难；而「读取系统钥匙串里的密钥」只能 command。

「一份代码两处复用」的具体形态——核心算法 crate 不带任何绑定注解，两个薄封装各管一端：

rust
// crates/core/src/lib.rs —— 纯算法，零绑定依赖（可单测、可复用）
pub fn sha256_chunks(chunks: impl Iterator<Item = Vec<u8>>) -> [u8; 32] {
    // 流式哈希实现，教学从略
    [0u8; 32]
}

// crates/wasm-bind/src/lib.rs —— WASM 封装
#[wasm_bindgen]
pub fn sha256_wasm(data: &[u8]) -> Vec<u8> {
    core::sha256_chunks(std::iter::once(data.to_vec())).to_vec()
}

// src-tauri/src/main.rs —— command 薄封装（只收路径，不收内容）
#[tauri::command]
fn sha256_file(path: String) -> Result<String, String> {
    // 主进程自己读盘分块，走同一个 core crate
    Ok(hex::encode(core::sha256_chunks(read_chunks(&path)?)))
}

这样 Web 端用 wasm 包、桌面端用 command，算法升级只改 core/——「部分非核心 Rust 重构」最舒服的切入点就是这种有清晰 crate 边界的模块。

71.6.3 最佳实践 ​

  1. 核心算法 crate 双目标编译：同一份 Rust 源码，wasm-pack 出 wasm 给渲染进程，#[tauri::command] 薄封装给主进程——一份代码两处复用，算法升级只改一处。
  2. command 只传引用不传数据：大文件场景 command 接收文件路径而非内容，让 Rust 主进程自己读盘——把 IPC 流量压到最小。
  3. WASM 优先，command 兜底：能用 WASM 解决的就不用 command——渲染进程内的计算没有 IPC 延迟，且 Web 端可平移。

71.7 自测题 ​

1. 【基础】JS 引擎的哪三个结构性边界让 WASM 在计算密集任务上占优？

答案：① JIT 预热与反优化——热点代码才被编译，类型反馈失效会跌回解释执行，性能不可预测；② GC 停顿——堆对象由垃圾回收器管理，主线程存在 STW 窗口；③ 数值类型贫瘠——只有 f64 与 BigInt，无 i64、无显式 SIMD。WASM 以 AOT 编译（无预热期）、无 GC 线性内存、明确数值类型 + SIMD 补上这三个缺口。

2. 【基础】rustup、cargo、wasm-bindgen、wasm-pack 四个工具各自负责什么？

答案：rustup 管理 Rust 工具链与编译目标（wasm32-unknown-unknown）；cargo 是构建系统与包管理；wasm-bindgen 生成 JS 胶水层与 .d.ts，处理边界两侧的类型编解码；wasm-pack 是编排器，一条命令串联 cargo build + wasm-bindgen 并产出可发 npm 的 pkg/ 目录。

3. 【基础】WASM 的线性内存模型是什么？JS 与 WASM 交换数据的唯一通道是什么？

答案：WASM 的全部内存是一块可增长的 WebAssembly.Memory（本质是 ArrayBuffer）。JS 侧通过 TypedArray 视图读写，WASM 侧通过 u32 指针偏移访问。数据交换的唯一通道就是这块 buffer——WASM 无法直接读写 JS 对象，对象必须序列化后拷入线性内存。

4. 【进阶】为什么「每帧调用 WASM 函数 500 次处理粒子」往往比纯 JS 还慢？给出修复方案。

答案：每次 JS↔WASM 边界穿越有几十 ns~1µs 的固定开销，500 次/帧累积成毫秒级，超过计算本身的收益。修复：把接口粒度从「点」改成「帧」——导出 process_frame(buffer)，整批粒子数据一次拷入线性内存，循环挪进 Rust 内部完成，结果一次读回，把 O(n) 次穿越压成 O(1) 次。

5. 【进阶】基准对比 JS 与 WASM 时，「预热 + 中位数 + 对照组」分别防什么坑？

答案：预热（丢弃前 N 次样本）防 JIT 未编译热路径导致的冷启动偏差；中位数（配合 IQR 剔除异常值）防 GC 停顿/系统调度尖刺污染均值——均值对离群值敏感；对照组（优化后的 JS 基线）防「绝对耗时自嗨」——只有相对真实 JS 方案的加速比才是决策依据。另注意微基准失真：要用生产数据规模测。

6. 【进阶】生产环境 WASM 加载失败有哪些来源？为什么降级实现必须与 WASM 结果逐字节一致？

答案：失败来源——老内核浏览器无 WebAssembly 对象、服务器 MIME 不是 application/wasm 导致 instantiateStreaming 拒绝、CDN 产物损坏或 404、跨域隔离头缺失导致 threads 不可用。降级实现必须同语义，因为降级路径一旦行为不同就是隐蔽的业务 bug（如加密结果不同导致数据无法解密）；二者应共用同一份测试 fixture 逐字节比对，否则降级路径上线即腐化。

7. 【挑战】设计一个「500MB 日志文件在浏览器端检索关键词」的方案，给出线程模型、边界设计与降级策略。

答案：

层设计
线程模型WASM 实例放 DedicatedWorker，主线程只收发消息——编译与检索都是 CPU 密集，不能堵 UI
数据进入File.stream() 分块（如 8MB/块）读入，逐块拷入线性内存调用 WASM 检索，避免一次性 500MB 入内存
边界设计状态驻留 WASM 侧（检索上下文初始化一次），每块一次穿越；命中结果累积在 WASM 内存，结束时一次读回
进度与取消进度回调按块节流上报（postMessage 自身也有成本）；取消通过标志位让 Rust 循环提前退出
降级策略无 WASM 时降级到 JS 正则检索（同分块协议，结果必须一致）；无 Worker 时降级到主线程分片 setTimeout 让帧

先按 71.1 的模型算账：500MB 检索是纯计算 + 整块数据，落在最佳象限；再用 71.4 的基准协议实测验证。

8. 【挑战】Tauri 桌面应用里有一个「大文件 SHA-256」需求，团队争论放 WASM 还是 Tauri command。分析两者的序列化成本并给出决策。

答案：WASM 在渲染进程内，数据经线性内存一次 memcpy，亚毫秒级，且是纯计算——500MB 文件内容走 Tauri command 的默认 JSON IPC 要经历编码 + 跨进程传输 + 解码，毫秒级起步且内存翻倍，是灾难。决策：计算逻辑放 WASM（渲染进程内分块流式喂入）；若文件在磁盘上而前端没有 File 句柄，则用 command 但只传文件路径不传内容，由 Rust 主进程自己读盘计算——把 IPC 流量压到路径字符串级别。进阶形态：核心哈希 crate 双目标编译，wasm 与 command 薄封装共用同一份源码。

#坑后果正确做法
