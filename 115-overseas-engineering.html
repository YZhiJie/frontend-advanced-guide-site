第一百一十五部分 · 海外化工程——多区域、支付、合规与本地化 ​

🧭 返回总目录｜上一篇：第一百一十四部分 · Vue Router 深度——守卫、权限与预取｜关联章节：第十五部分 · 无障碍与国际化 · 第七部分 · Web 安全 · 第六十一部分 · 多租户 SaaS · 第六部分 · 网络与 HTTP · 第六十九部分 · 前端埋点体系

本部分内容 ​

海外化不是「把文案翻译一遍」。语言、时区、货币、支付、合规、部署与增长是七个可独立组合的维度，任何一项硬编码，都会在某个市场变成资损或法律风险。本册以同一跨境 DTC 品牌在 EU/US/JP 售卖、并做海外社交投放为场景，给出可直接落地的模型：区域化数据结构、ICU 多语言、支付状态机与 webhook 幂等、GDPR/CCPA 同意、数据驻留与区域灰度、本地化体验与归因。示例纯 TypeScript 可跑，重点在边界与失败路径。

115.1 区域化模型：语言、时区、货币、地址、姓名 ​

概念解析 ​

五个维度必须分开存，它们不构成一个「locale」：

维度存储字段取值示例不能推断什么
语言languageen / de / ar国家、币种、时区
地区书写localeen-US / de-DE用户实际所在地
市场marketUS / DE / JP界面语言
货币currencyUSD / EUR / JPY支付方式
时区timeZoneAmerica/New_York不能靠 IP 稳定推断

德国的美国游客可能用英文界面、付欧元、在纽约时区；深圳卖家的店铺可能按洛杉矶时间营业。把它们绑成一个字段，等于假设「语言=国籍=币种=时区」，跨境必错。

金额存最小单位整数 + ISO 币种，如 USD 1999 表示 $19.99；浮点参与加减会出现 19.989999…。小数位由 ISO 4217 决定：JPY/KRW 为 0 位，KWD/BHD 为 3 位，不能统一按两位。地址/姓名没有全球统一模型：日本从都道府县到番地，欧美从门牌到城市。工程上要么结构化模板，要么「国家 + 自由文本 + 邮编」。

应用实践 ​

  • 反例：商品页写死 ¥99——日元与人民币共用符号；应存 currency，由 Intl 输出。
  • 反例：new Date('2026-03-08T09:00:00') 按浏览器本地时区解析，同一字符串在不同用户处得到不同瞬时；墙上时间必须带 IANA 时区。
  • 订单落库同时存 amountMinor、currency、market、timeZone、locale；退款、发票、对账都以这些字段为准。

115.2 多语言工程：ICU、复数、RTL 与字体子集 ​

概念解析 ​

n === 1 ? 'item' : 'items' 只适用于英语。CLDR 定义六种复数形态 zero/one/two/few/many/other：

语言01251121
英语otheroneotherotherotherother
法语oneoneotherotherotherother
俄语manyonefewmanymanyone
阿拉伯语zeroonetwofewmanymany
日语/中文otherotherotherotherotherother

ICU MessageFormat 是跨语言消息标准：{count, plural, =0 {No items} one {# item} other {# items}}。=0 精确匹配优先于类别；# 在分支体内替换为数字。只抽 key 不抽复数/性别结构，翻译到俄语、阿拉伯语必然语法错误。

RTL 不是整体镜像：用 <html dir="rtl"> + CSS 逻辑属性（margin-inline-start、inset-inline），数字、价格、代码仍保持 LTR。字体子集是首屏大头：CJK 字体动辄数 MB，按 unicode-range 切片、只打包当前 locale。德语文本通常比英语长 30%，按钮要留余量。

示例 ​

示例 examples/115-01-icu-plural-currency.ts 实现了完整解析：按 locale 选复数形态（selectPlural）、=0 精确分支优先、# 替换为数字，同时验证金额最小单位换算与 Intl 货币格式。

运行方式：npx tsx examples/115-01-icu-plural-currency.ts

应用实践 ​

  • 翻译键按语义命名（cart.itemCount），占位符进翻译资源，禁止 'Welcome, ' + name 这类语序拼接。
  • 开发期用伪 locale en-XA 跑一遍，提前暴露截断、硬编码宽度。
  • RTL 验收：箭头方向、标签对齐、进度条方向、电话号码/价格保持 LTR。

115.3 海外支付：Stripe/PayPal、3DS、订阅、退款与对账 ​

概念解析 ​

前端不持有支付凭证，支付是服务端权威 + 异步事件驱动的状态机：

状态含义前端动作服务端动作
created订单已建、未支付展示支付方式建 PaymentIntent，带幂等键
requires_action需 3DS/SCA调 confirmPayment 弹挑战等待 webhook
paid已捕获显示成功，仍以 webhook 为准入账、发货
partially_refunded部分退款展示退款进度记退款明细
refunded全额退款展示已退款冲正、回滚库存
failed / canceled失败/取消允许重试释放库存与优惠券

三类事故：① 重复入账：webhook 会重试，同一 event.id 多次到达，每次都加余额就会重复发货；需 event.id + paymentId/refundId 三层幂等。② 乱序：succeeded 可能早于 requires_action，状态机不能回退。③ 信任前端：3DS 后跳回 return_url 只说明浏览器回来了，钱未必到账。

订阅还要处理试用转正、按比例计费、扣款失败重试（dunning）、升降级与 VAT/GST；退款区分全额/部分、手续费与汇率差，并保留流水对账。

完整代码示例 ​

ts
// 文件: examples/115-03-payment-state-machine.ts（节选）
// 目标：重复事件不重复入账，乱序不回退，退款有上限
handleWebhook(event: ProviderWebhook): 'processed' | 'duplicate' | 'ignored' {
    if (this.processedEventIds.has(event.id)) return 'duplicate';
    this.processedEventIds.add(event.id);
    if (event.type === 'payment.requires_action') {
        if (this.state !== 'created') return 'ignored'; // 已支付后到达不回退
        this.state = 'requires_action';
        return 'processed';
    }
    if (event.type === 'payment.succeeded') {
        this.capture(); // paymentId 唯一键 + credited 标记
        this.state = this.refundedMinor > 0 ? 'partially_refunded' : 'paid';
        return 'processed';
    }
    if (this.processedRefundIds.has(event.refundId)) return 'duplicate';
    if (!this.refund(event.amountMinor)) return 'ignored'; // 超额退款拒绝
    this.processedRefundIds.add(event.refundId);
    return 'processed';
}

运行方式：npx tsx examples/115-03-payment-state-machine.ts

应用实践 ​

  • 创建支付/退款必须带 Idempotency-Key，同一订单重试复用同一键。
  • webhook 验签用原始请求体；先 JSON 解析再验签会永远失败。
  • 每日对账：网关结算报表 vs 本地 capture − refund；差额按漏 webhook、重复入账、汇率/手续费分类处理。
  • 反例：以 succeeded 为加积分唯一触发点却忽略重试——积分翻倍。积分流水应以 paymentId 为唯一键。

115.4 合规：GDPR / CCPA、Cookie 同意、数据出境 ​

概念解析 ​

模型代表默认前端要点
opt-inGDPR（EU/EEA + UK）非必要 Cookie 全拒先同意后加载；拒绝与接受同样显眼
opt-outCCPA/CPRA（加州）允许，可拒绝出售/共享“Do Not Sell/Share” 入口；尊重 GPC
opt-inLGPD（巴西）、PIPL原则需同意单独同意、目的限定

Cookie 分级：necessary（登录、购物车、防欺诈）无需同意；analytics 与 marketing 需同意。未同意前不得初始化 GA、Meta Pixel，不是加载后再停用。地域判定不能只看 IP（VPN/旅行会误判），应「IP 粗判 + 账号/账单国家 + 手动选择」，未知地域按最严格处理。同意记录存版本、时间、类别、地域、撤回状态，政策改版或超过再征询周期（常取 180 天）自动失效。数据出境靠区域存储 + SCCs/DPF，第三方处理者要写进隐私政策。

示例 ​

示例 examples/115-04-cookie-consent.ts 覆盖地域判定、横幅策略与脚本门禁：GDPR 默认全拒、CCPA 默认允许但尊重 GPC、同意记录按版本与 180 天有效期失效。

运行方式：npx tsx examples/115-04-cookie-consent.ts

应用实践 ​

  • 第三方脚本统一走 ConsentGate，按类别 load/revoke；撤销时同时清 Cookie 与本地存储。
  • 拒绝按钮不能藏，预勾选、仅“接受全部”、关闭即同意都属无效同意。
  • 反例：只记录“用户点过接受”，不存类别与版本；三个月后撤回营销同意，系统仍按旧记录投放。

115.5 多区域部署与 CDN：域名、数据驻留与灰度 ​

概念解析 ​

先回答三个问题：域名怎么分、数据放哪、流量怎么切。

域名策略示例优点代价
单一全球域名shop.example.comSEO 集中、运维简单难做法律/内容隔离
地区子域de.example.com隔离清晰、易分市场灰度证书/SEO/配置翻倍
ccTLDexample.de本地信任最高注册与合规成本高
数据分区EU 法兰克福 / US 弗吉尼亚 / APAC 新加坡满足数据驻留跨区同步成本

静态资源可全球 CDN 边缘缓存；含 PII 的接口必须回到对应驻留区。边缘函数只做无状态逻辑（地域判定、AB、302），不落库、不缓存个人数据。灰度按市场切，每市场独立开关，避免小语种 bug 扩散。

应用实践 ​

  • 边缘 302 到区域域名时，必须完整透传 query（UTM、深链参数）。
  • 区域 API 的 CORS 白名单覆盖所有前端域名；健康检查按区域独立。
  • 币种、税率、支付方式、合规横幅由服务端按市场配置下发，新增市场不改前端代码。

115.6 本地化体验：日期、数字、单位与时区 ​

概念解析 ​

底层是 Intl API + IANA 时区，难点在边界：

  • 日期：同一瞬时的墙上时间随时区变；存储用 UTC 瞬时或「墙上时间 + 时区」。周起始日、12/24 小时制、日期顺序都随 locale 变。
  • 数字/单位：de-DE 小数逗号、印度分组 12,34,567、英里/公里、华氏/摄氏；换算只在展示层做，订单存基准单位。
  • 时区预约：商家在纽约、用户在伦敦，DST 切换日会出现不存在的 02:30 和出现两次的 01:30。营业时间按商家时区墙上时间建模，逐槽解析成 UTC；缺口跳过，重叠取较早并去重。
  • 内容审核：医疗宣称、酒类、宗教内容、比较广告规则按市场不同；机翻文案必须母语审校。

完整代码示例 ​

ts
// 文件: examples/115-02-timezone-booking.ts（节选）
// 目标：DST 缺口返回 null、重叠取较早瞬时，时段不重复不重叠
function resolveWallTime(wall: WallClock, timeZone: string): { instant: number; ambiguous: boolean } | null {
    const guess = Date.UTC(wall.year, wall.month - 1, wall.day, wall.hour, wall.minute);
    // 取前后 48h 的偏移作为候选：DST 切换前后对应两个不同偏移
    const candidateOffsets = new Set([
        offsetMs(guess - 48 * 3600_000, timeZone),
        offsetMs(guess, timeZone),
        offsetMs(guess + 48 * 3600_000, timeZone),
    ]);
    const valid: number[] = [];
    for (const offset of candidateOffsets) {
        const candidate = guess - offset;
        const back = wallClockAt(candidate, timeZone);
        if (back.year === wall.year && back.month === wall.month && back.day === wall.day
            && back.hour === wall.hour && back.minute === wall.minute) valid.push(candidate);
    }
    if (valid.length === 0) return null;
    valid.sort((a, b) => a - b);
    return { instant: valid[0], ambiguous: valid.length > 1 };
}

运行方式：npx tsx examples/115-02-timezone-booking.ts

完整示例验证：春季 01:00–04:00 只生成 01:00、03:00，秋季不会生成重复瞬时，纽约 09:00 = 上海 21:00。

应用实践 ​

  • 反例：预约时间存字符串 2026-03-08 09:00，服务器按 UTC 解析，商家在纽约，用户看到的时间整体偏移 4~5 小时。
  • 营业时间存 { timeZone: 'America/New_York', open: '09:00', close: '17:00' }，不要存固定 UTC 时刻，否则 DST 后开门漂移。
  • 支付方式本地化：德国常用 SEPA/发票，巴西 Pix/Boleto，日本 Konbini；按市场排序比多语言更影响转化。
  • 审核清单按「市场 × 品类」维护，敏感词按语言建。

115.7 海外增长与归因：渠道、深链与 ATT ​

概念解析 ​

链路是投放 → 落地 → 归因。前端能控制落地参数完整性与隐私合规下的归因质量。

  • UTM：source/medium/campaign/term/content 必须在短链、302、区域跳转中逐层透传；丢一跳 query，归因就断。
  • 深链：Universal Links / App Links 直接开 App；未安装回落商店，需 deferred deep link 在首启后拉参数。
  • ATT：iOS 拒绝后无 IDFA，退化为 SKAdNetwork/AdAttributionKit 聚合归因（延迟、隐私阈值）。
  • 服务端事件：Meta CAPI / TikTok Events API 用哈希标识 + event_id 去重，弥补 Cookie 丢失；必须过营销同意。

代码示例 ​

ts
// 统一透传：地区重定向时保留全部归因参数
function appendParams(target: string, params: Record<string, string>): string {
    const url = new URL(target);
    for (const [key, value] of Object.entries(params)) url.searchParams.set(key, value);
    return url.toString();
}

应用实践 ​

  • 统一 appendParams 工具，短链 → 地区跳转 → 落地 → 注册 → 下单逐跳保留 utm_*、gclid、fbclid、深链参数。
  • 反例：example.com/de 302 到 de.example.com 时丢掉 query；或深链回落 App Store 未带参数，安装后全归为自然量。
  • ATT 在用户完成一次核心体验后再请求；拒绝后改用 SKAN + 服务端事件。
  • 渠道报表、服务端事件、订单表按 event_id/订单号三方对账，归因窗口写进报表口径。

115.8 自测题 ​

先自己作答，再展开参考答案。

1. 为什么不能用一个 locale 字段同时决定语言、币种和时区？【基础】

语言是用户偏好，币种由交易市场决定，时区由所在地或营业地决定。德国游客可能用英文界面、付欧元、在纽约时区；卖家可能在深圳办公但按洛杉矶时间营业。绑定三者会假设「语言=国籍=币种=时区」，跨境必错。应分开存 language/locale/market/currency/timeZone。

2. 为什么金额用最小单位整数？JPY 与 KWD 有何不同？【基础】

浮点无法精确表示 19.99，退款/累加会产生误差与资损；整数最小单位可精确对账。ISO 4217 规定小数位：JPY/KRW 为 0，KWD/BHD 为 3。统一按两位会让日元多乘 100、科威特丢一位。

3. ICU 的 `=0` 与 `zero` 有什么区别？俄语/阿拉伯语为何不能只写 one/other？【进阶】

=0 是精确数值匹配，任何语言 count=0 都命中；zero 是 CLDR 类别，仅阿拉伯语等把 0 归入 zero 的语言命中。俄语有 one/few/many，阿拉伯语六种形态；只写 one/other 会让 2/5/11 语法错误，必须有 other 兜底。

4. RTL 为什么不能整体镜像？列出四个检查点。【进阶】

整体镜像会把数字、图标、文字全反过来。正确做法是 dir="rtl" + 逻辑属性。检查点：箭头/导航方向、表单标签对齐、进度条与轮播方向、图标是否应镜像（播放键不镜像）、数字/价格/电话保持 LTR、图表坐标轴方向。

5. webhook 重复到达如何保证不重复入账？【进阶】

三层幂等：① 按 event.id 去重并落库；② capture 按 paymentId 只执行一次，数据库唯一索引兜底；③ 退款按 refundId 去重，换 event.id 也不能再退。再加币种校验与超额退款拒绝。所有副作用（发货、积分）都以幂等键为基础。

6. 3DS 后跳回 return_url，能立即显示支付成功吗？【基础】

不能。跳转只证明浏览器回来了，支付可能仍在处理、被风控挂起或失败。前端显示「处理中」，以 webhook 或服务端查单为准；确认 paid 后才发货/加权益。把跳转当成功是常见资损来源。

7. GDPR 与 CCPA 的默认策略、GPC 如何处理？【进阶】

GDPR 是 opt-in：非必要 Cookie 默认拒绝，明确同意后才加载，拒绝与接受同等显眼。CCPA 是 opt-out：默认允许，但必须提供 Do Not Sell/Share，用户拒绝后停止。GPC 是浏览器全局拒绝信号，在 CCPA 下自动等同 opt-out，营销脚本立即停用。未知地域按最严格处理。

8. DST 春季缺口与秋季重叠怎么处理？【挑战】

春季前跳，02:00–02:59 不存在：候选偏移都无法还原同一墙上时间，返回 null 并跳过该时段。秋季回拨，01:00–01:59 出现两次：两个候选都有效，标记 ambiguous，预约取较早瞬时并按瞬时去重。营业时间按商家时区墙上时间建模，再逐槽解析成 UTC。
