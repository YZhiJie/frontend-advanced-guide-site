## 60.1 差异从哪来：渲染引擎格局与碎片化

### 概念解析

浏览器「品牌」有几十个，**渲染引擎只有三个半**。兼容性问题本质是引擎差异，不是品牌差异：

| 引擎 | 背后厂商 | 覆盖浏览器 | 前端要点 |
| --- | --- | --- | --- |
| Blink | Google（Chromium） | Chrome、Edge、Opera、国产双核的「极速模式」、Android 系统 WebView | 新特性落地最快；国内桌面端实际份额最大 |
| WebKit | Apple | Safari、**iOS 上的一切浏览器与 WebView**（含 iOS 版 Chrome、微信内置浏览器） | 新特性落地最慢；iOS 平台策略限制多（自动播放、通知、后台任务） |
| Gecko | Mozilla | Firefox | 份额小但标准实现严谨，常作第三仲裁 |

三条必须记住的格局事实：

1. **iOS 没有「Chrome 内核」**：App Store 规则要求 iOS 浏览器一律用系统 WebKit。iOS 版 Chrome 只是套壳 Safari，调试 iOS 上的「Chrome 专属问题」本质是调 WebKit。（欧盟 DMA 后 Apple 已开放替代引擎，但实际份额可忽略。）
2. **IE 已退役**：IE11 于 2022 年 6 月终止支持，Edge 的「IE 模式」仅供企业内网遗留系统。本书不展开 IE hack（haslayout、`*html` 这类考古知识）；JD 里写 IE6-10 的，说明 JD 本身多年没更新。真要兼容政企 IE 内网，方案是「IE 模式 + 单独构建产物」，不是写 hack。
3. **碎片化在移动端**：Android 系统 WebView 虽可随 Google Play 升级，但国产 ROM（小米/华为/OPPO…）常定制或锁死内核版本；桌面端国产双核浏览器（360/QQ/搜狗/遨游）可在 Blink 与 IE 内核间切换（见 60.4）。

差异的三个来源，决定了三种不同的应对姿势：

- **引擎实现差异**：同一 API 落地节奏不同（如 flex `gap` Safari 14.1 才支持）→ 用特性检测 + Baseline 查询应对；
- **平台策略差异**：iOS 禁止非静音自动播放、`unload` 不可靠 → 这些是「策略」不是「bug」，只能改设计；
- **厂商定制差异**：双核切换、ROM 定制内核、微信字体强制放大 → 需要专属生存指南（60.4）。

### 典型应用场景

- 立项时定 **browserslist** 基线：面向 C 端（`> 0.5%, last 2 versions, not dead`）与面向企业内部（可钉死 Chrome）的兼容范围完全不同；
- 回答「这个需求要不要为 iOS Safari 改设计」——先查引擎格局，再查 caniuse；
- 做监控分桶时按「引擎 + OS」分而不是按品牌分（见 59 册），品牌几十个，引擎就三个。

### 可运行代码示例

UA 的正确用途是**环境画像与风险评估**，不是功能开关。示例 60-03 把 UA 解析成「引擎 / OS / 客户端」三元组，并挂上已验证的风险规则库：

```typescript
// 文件: examples/60-03-ua-risk-report.ts（核心节选）
// 引擎:iOS 上一切浏览器(含 Chrome/微信)都是 WebKit;Firefox 是 gecko;
// 其余带 chrome 标记的是 blink;裸 safari 是 webkit
const engine: UaProfile["engine"] =
  client === "firefox"
    ? "gecko"
    : os === "ios"
      ? "webkit"
      : s.includes("chrome") || s.includes("crios") || client === "edge"
        ? "blink"
        : s.includes("safari")
          ? "webkit"
          : "unknown";
```

> 运行方式：`npx tsx examples/60-03-ua-risk-report.ts`（四条真实 UA 的画像与风险命中；注意 iOS 微信 UA 里的 `like Gecko` 是历史兼容串，绝不能据此判 gecko）。

### 最佳实践

- ✅ 思考维度用「引擎」而非「品牌」：Chrome 能跑 ≠ Edge 有问题，它们同为 Blink；
- ✅ 把目标浏览器矩阵写进需求文档与测试计划，别等上线后补；
- ⚠️ 新能力上线前查 [caniuse](https://caniuse.com) 与 MDN 的 Baseline 标记（见 25 册），不要凭印象；
- ❌ 不要为「万一有人用 IE」预留兼容层——先查自家监控的真实 UA 分布，数据说话。

## 60.2 防御体系：特性检测、降级与构建管线

### 概念解析

兼容性防御分三层，各管一段，缺一不可：

| 层 | 时机 | 工具 | 管什么 |
| --- | --- | --- | --- |
| 契约层 | 选型/评审期 | caniuse、MDN Baseline、browserslist | 这个功能能不能进需求 |
| 构建层 | build 时 | Babel/SWC 转译语法、core-js 补 API、autoprefixer 补 CSS 前缀 | 让代码能在旧引擎上跑 |
| 运行层 | 用户浏览器里 | `typeof`/`in` 特性检测、CSS `@supports`、降级分支 | 补不了的给替代方案 |

两条铁律（01 册已详述，这里收口）：

1. **转译与 polyfill 是两条线**：Babel/SWC 只转译**语法**（可选链、class 字段），不补 **API**（`structuredClone`、`Promise.withResolvers`）——后者靠 core-js 等垫片。漏掉任何一条线，旧引擎上就是白屏或运行时报错。
2. **特性检测优于 UA 嗅探**：UA 串从 1990 年代起就互相撒谎（每个浏览器都自称 `Mozilla/5.0`），且规则永远追不上版本迭代。功能开关一律用 `typeof fn === 'function'`、`'key' in obj`、`CSS.supports()`；UA 只用于统计分桶与风险预警（60-03 的定位）。
3. 有少数特性**无法 polyfill**：`Proxy`（引擎级，27 册响应式因此不支持 IE11）、`WeakRef`、Tail Call Optimization。检测到缺失时只能换实现方案，没有第三条路。

降级决策应为四级而非二元：原生 → polyfill → 业务降级 → 明确不支持（提示升级浏览器）。「默默坏掉」是最差的第五种结局。

### 典型应用场景

- 新 API 上线前评估：查 Baseline → 看自家 UA 分布 → 决定「直接用 / 加垫片 / 写降级」；
- 老项目兼容方案：browserslist 收紧到真实用户分布，删掉为不存在的环境打的垫片，省体积；
- 组件库发版：对外声明 engines/peer 兼容范围，内部用特性检测做软降级。

### 可运行代码示例

示例 60-01 把「检测逻辑」做成注册表，输入环境剖面（不依赖真实浏览器，Node 可跑），输出四级决策与兼容矩阵报告：

```typescript
// 文件: examples/60-01-feature-detect.ts（核心节选）
export function resolveCapability(def: CapDef, env: Env) {
  if (def.detect(env)) return { tier: "native", note: `${def.name} 原生可用` };
  if (def.polyfilled?.(env))
    return { tier: "polyfill", note: `${def.name} 需引入 polyfill` };
  if (def.fallback)
    return { tier: "fallback", note: `${def.name} 不支持 → 降级:${def.fallback}` };
  return { tier: "unsupported", note: `${def.name} 不可用且无降级` };
}
```

> 运行方式：`npx tsx examples/60-01-feature-detect.ts`（Chrome Android / iOS Safari 15 / 老 Android WebView 三剖面输出能力矩阵；Proxy 在老内核上落 unsupported——不可 polyfill 只能换实现）。

### 最佳实践

- ✅ browserslist 写进 `package.json`，CI 与本地同一份（见 55 册），autoprefixer 以前缀依据为准、不要全量加前缀；
- ✅ CSS 新特性用 `@supports` 做渐进增强，关键交互路径必须有降级样式（见 45 册）；
- ✅ 降级分支要写进测试用例——用 Playwright 的 WebKit project 或在测试里注入「缺失能力」的 mock 环境跑一遍；
- ❌ 不要在代码里散落几十处 `if (isIOS)`——环境判断集中到一处工具模块，业务代码只问「能力有没有」，不问「你是谁」。

## 60.3 高频兼容性案例库

### 概念解析

下面这份清单按「JS / CSS / 移动端策略」分类，收录的是**今天仍然会咬人**的坑（已淘汰的 IE 问题不收录）。每行给出症状与一行方案，展开的原理在对应分册。

**JS 类**：

| 坑 | 症状 | 一行方案 |
| --- | --- | --- |
| Safari 日期解析 | `new Date("2024-01-01 00:00:00")` 在 WebKit 返回 Invalid Date（NaN），下游计算全线崩 | 逐字段构造或先归一化为 ISO，见示例 60-02 |
| Clipboard API 权限 | Safari 要求用户手势内调用，异步 await 后再写会静默失败 | 手势回调里先拿权限再异步，失败给「手动复制」兜底 |
| `scrollBehavior: "smooth"` | 老 Safari 不支持，直接报错中断路由 | 特性检测后退回 `auto` |
| `atob` 中文 | 任何浏览器都炸（Latin1 边界），但中文业务在 iOS WebView 里最先暴露 | `TextDecoder` + base64 → bytes 转换 |

**CSS 类**：

| 坑 | 症状 | 一行方案 |
| --- | --- | --- |
| flex `gap` | Safari < 14.1 完全不生效，布局挤在一起 | `@supports (gap: 8px)` 检测，降级用 margin |
| `backdrop-filter` | Safari 需要 `-webkit-` 前缀 | autoprefixer 自动补（55 册），别手写漏 |
| 1px 边框 | iOS 高清屏上 `1px` 变粗 | `transform: scaleY(0.5)` 伪元素或 `box-shadow` 描边 |
| `position: sticky` 在表格/overflow 容器 | 各内核祖先裁剪规则不一致，粘性失效 | 检查祖先 `overflow`，必要时换 IntersectionObserver 实现 |

**移动端策略类**（详述见 08 册，这里做索引）：

| 坑 | 一行方案 |
| --- | --- |
| iOS `100vh` 随地址栏伸缩抖动 | 用 `100dvh` / `svh`，兼容老系统监听 `visualViewport.resize` |
| 键盘弹起顶飞 `fixed` 弹层 | 监听 `visualViewport.resize` 动态修正 |
| 音视频自动播放被拦 | 静音自动播放是允许的；带声音必须等用户手势 |
| 输入框聚焦时页面自动放大 | 输入框 `font-size` 保持 ≥ 16px，或 viewport 锁 `maximum-scale=1`（后者牺牲可访问性，慎用） |
| 数字串被识别成电话号码变链接 | `<meta name="format-detection" content="telephone=no">` |
| `touchstart` 里 `preventDefault` 无效 | Chrome 56+ 文档级 touch 监听默认 passive，需显式 `passive: false` |
| 橡皮筋滚动穿透 | `overscroll-behavior: contain` + 弹层锁定 body 滚动 |

### 典型应用场景

- 移动端 H5 上线前的自查清单（本表直接当 checklist 用）；
- Code Review 时对照「本次改动涉及的能力，在 60.3 清单里有没有条目」；
- 把团队历史上踩过的兼容性 bug 持续追加进这张表——案例库是活文档。

### 可运行代码示例

日期解析是「引擎差异直接导致线上事故」的最经典案例：同一个字符串，V8 宽容、JavaScriptCore 严格按规范拒绝。示例 60-02 把解析收敛成纯函数，合法输入全引擎一致，非法输入返回 `null` 而不是让 NaN 污染下游：

```typescript
// 文件: examples/60-02-safe-date.ts（核心节选）
// 逐字段构造走本地时区:不经过引擎的字符串解析器,行为在所有内核一致
const date = new Date(+y, +mo - 1, +d, +h, +mi, +s);
// 防「2024-02-31」这类进位溢出:逐字段回验,溢出即判非法
const ok =
  date.getFullYear() === +y && date.getMonth() === +mo - 1 && date.getDate() === +d;
return ok ? date : null;
```

> 运行方式：`npx tsx examples/60-02-safe-date.ts`（Safari 会拒的 `2024-01-01 00:00:00`、斜杠/T 分隔、13 月、2 月 31 日、垃圾输入、时间戳，全量硬断言）。

### 最佳实践

- ✅ 修兼容性 bug 必须同时留下回归用例（单测 mock 环境，或 Playwright WebKit 任务），否则下个版本必复发；
- ✅ 后端下发的日期时间字段，接口契约直接定 ISO 8601，从源头规避解析分歧；
- ⚠️ 「polyfill 全量引入」会把现代浏览器也拖慢——按 browserslist 差异化打包（modern/legacy 双产物）；
- ❌ 不要用 `!!window.ActiveXObject` 这类考古探测判断任何现代环境——它只能证明你复制了十年前的代码。

## 60.4 国产浏览器与 WebView 生存指南

### 概念解析

国内 C 端产品的真实运行环境，比「Chrome/Safari/Firefox」复杂得多：

**1. 双核浏览器（360 / QQ / 搜狗 / 遨游）**：同一浏览器内置 Blink（极速模式）与 IE（兼容模式）两颗内核，站点被切到哪颗核，由浏览器的历史名单与用户手动选择决定。开发者可在 `<head>` **最前面**声明偏好：

```html
<!-- 双核浏览器内核锁定:必须放 head 最前,晚于它加载的资源已按旧内核解析 -->
<meta name="renderer" content="webkit" />
<meta name="force-rendering" content="webkit" />
<meta http-equiv="X-UA-Compatible" content="IE=edge,chrome=1" />
```

声明后仍可能被用户手动切走，所以底线仍是特性检测 + 降级。

**2. 微信内置浏览器**：国内 H5 的最大单一入口。要点：

- iOS 微信 = WKWebView，Android 微信 = 系统 WebView 或 X5（微信已逐步切换到系统内核，**版本碎片化严重**，勿信任何固定 UA 特征）；
- iOS 微信里用户调大字体后，页面字号会被强制放大、布局错乱——根容器加 `-webkit-text-size-adjust: 100% !important` 锁定；
- JSSDK 签名在 iOS 上必须用**首次进入的 URL**（SPA 切换路由后 iOS 端 `location.href` 不变，Android 端变），签名错了所有 JSSDK 能力静默失效；
- 微信内无法下载文件、不能拉起部分 scheme，关键转化路径要设计「右上角浏览器打开」引导。

**3. 国产 ROM 定制 WebView**：小米/华为等 ROM 可能冻结或替换系统 WebView，同一台手机「浏览器里正常、App 内 WebView 白屏」并不罕见。应对：Hybrid 容器内做特性检测探针，上报内核版本到监控（59 册），按引擎版本分桶告警。

### 典型应用场景

- 公众号/朋友圈 H5 活动页：微信环境 + 双核浏览器双重不确定性；
- 政企客户内网：可能真的是双核浏览器兼容模式（IE 内核）——这时候 IE 模式知识才有用武之地；
- App 内嵌 H5：WebView 内核碎片化排查。

### 可运行代码示例

示例 60-03 的风险规则库就内置了国产环境的命中项：UA 命中 360/遨游时提示「双核可能切 IE 模式」，命中微信时提示字体锁定与 JSSDK 签名坑：

```typescript
// 文件: examples/60-03-ua-risk-report.ts（核心节选）
if (p.client === "360" || p.client === "maxthon") {
  risks.push("双核浏览器可能被切到 IE 兼容模式 → 用 meta renderer=webkit 锁定极速内核");
}
```

> 运行方式：`npx tsx examples/60-03-ua-risk-report.ts`（含 `QihooBrowser` UA 的画像与双核风险命中断言）。

### 最佳实践

- ✅ 微信内调试用 vConsole / eruda（页面内悬浮面板），别指望连电脑；
- ✅ 内核锁定 meta 放 `<head>` 第一屏位置，且仍按「锁定失败」做降级设计；
- ✅ 微信内发版后清缓存验证：微信对 H5 资源缓存激进，灰度时先看命中率再放量；
- ❌ 不要在微信里用 `alert`/`confirm` 做关键交互——部分版本会被客户端拦截或样式不可控，用自定义弹层。

## 60.5 排查 SOP 与远程调试工具链

### 概念解析

「快速定位兼容性问题的能力」是 JD 的核心。把它落成可执行的六步 SOP：

```mermaid
flowchart LR
    A[收到问题反馈] --> B[① 环境画像]
    B --> C[② 最小复现]
    C --> D[③ 二分定位]
    D --> E[④ 规范查证]
    E --> F[⑤ 修复与降级]
    F --> G[⑥ 回归门禁]
```

1. **环境画像**：先拿 UA / 引擎 / 版本 / 设备 / 网络。线上问题从监控平台的 UA 分桶查（59 册）；用户反馈让客服按模板收集。60-03 的报告格式可直接贴进 issue。
2. **最小复现**：把页面剥离到「一个 HTML + 几十行代码」还能复现为止。很多「兼容性 bug」剥到最后是自己代码的时序假设，与环境无关。
3. **二分定位**：对可疑代码段做二分注释，或在问题环境插探针（特性检测矩阵的输出直接贴进页面角落）。
4. **规范查证**：caniuse 查版本覆盖、MDN 查 Baseline 与注意事项；怀疑是引擎 bug 就去 crbug.com（Blink）/ bugs.webkit.org（WebKit）搜——确认为引擎 bug 就别硬修，走降级并订阅 issue。
5. **修复与降级**：优先选「不依赖该能力也能用」的方案；必须用时按 60.2 的四级决策补降级。
6. **回归门禁**：修复进回归套件（Playwright 的 WebKit/Firefox project，见 09 册），CI 卡住复发。

**远程调试工具链**：

| 场景 | 工具 | 要点 |
| --- | --- | --- |
| iOS 真机 Safari / WebView | Mac Safari「开发」菜单 → Web Inspector | 数据线连接，Mac 独占方案 |
| Android Chrome / WebView | `chrome://inspect` + USB | WebView 需 `setWebContentsDebuggingEnabled(true)`（debug 包） |
| 微信内页面 | vConsole / eruda 悬浮面板 | 无电脑时唯一能看 console/network 的手段 |
| 无真机覆盖 | BrowserStack / 各厂云真机平台 | 按引擎版本选机，别按品牌选 |
| 遗留环境 | weinre | 纯 JS 注入，弱但全平台可用 |

### 典型应用场景

- 线上告警「只有 iOS 用户白屏」：59 册分桶确认范围 → BrowserStack 选同版 WebKit 复现 → 探针定位到 unsupported 能力 → 降级 → Playwright WebKit 加回归；
- 客户现场政企内网：双核兼容模式下 F12 都没有，用 weinre 或打包 vConsole 进页面。

## 60.6 自测题

<details>
<summary><b>1. 【基础】为什么不能靠 UA 嗅探做功能开关？UA 的正确用途是什么？</b></summary>

UA 串从浏览器诞生起就互相伪装（所有浏览器都自称 Mozilla/5.0，iOS 应用内还常带 like Gecko 等误导串），且规则永远追不上版本更新，误判率高。功能开关必须用特性检测（typeof/in/CSS.supports）。UA 的正确用途只有两个：统计分桶（监控按引擎+OS 分维度）与风险预警（命中已知问题清单），不参与功能分支。
</details>

<details>
<summary><b>2. 【基础】iOS 版 Chrome 用的是什么引擎？这个格局对兼容性排查意味着什么？</b></summary>

WebKit。App Store 规则要求 iOS 浏览器一律使用系统 WebKit（欧盟 DMA 后虽有开放，实际份额可忽略）。意味着：iOS 上「Chrome 有 bug」本质是 WebKit 问题；iOS 兼容性测试用 Safari 即可覆盖绝大部分场景，不必逐个品牌测；监控分桶按引擎分而不是按品牌分。
</details>

<details>
<summary><b>3. 【基础】Babel/SWC 转译与 core-js polyfill 的分工是什么？只做一个会怎样？</b></summary>

转译管语法（可选链、class 字段等解析层面的新写法），polyfill 管 API（structuredClone、Promise.withResolvers 等运行时新增能力）。只做转译：旧引擎解析通过但运行时 API  undefined 报错；只做 polyfill：旧引擎直接语法解析失败白屏。两条线必须同时按 browserslist 配置。
</details>

<details>
<summary><b>4. 【进阶】`new Date("2024-01-01 00:00:00")` 为什么在不同浏览器结果不同？正确写法是什么？</b></summary>

该格式（短横线日期 + 空格分隔时间）不属于 ECMAScript 规范的 Date Time String Format，规范只保证 ISO 8601 子集可解析；V8 做了宽容扩展，JavaScriptCore 严格返回 Invalid Date。正确写法：接口契约定 ISO 8601；必须解析宽松格式时像 60-02 那样用正则拆解后逐字段 new Date(y, m-1, d, ...)，并逐字段回验防 2 月 31 日进位。
</details>

<details>
<summary><b>5. 【进阶】360 浏览器的 meta renderer 内核锁定怎么写？为什么必须放 head 最前面？锁了就万无一失吗？</b></summary>

`<meta name="renderer" content="webkit">` + `<meta name="force-rendering" content="webkit">`。双核浏览器在解析文档早期就决定用哪颗内核，晚于 meta 加载的资源已按旧内核处理，所以必须放 head 最前。不是万无一失——用户可以手动切核，站点也可能在浏览器内置名单里被强制指定，因此底线仍是特性检测 + 降级分支。
</details>

<details>
<summary><b>6. 【进阶】为什么在 Chrome 里给 document 挂 touchstart 监听后 preventDefault 无效？怎么修？</b></summary>

Chrome 56+ 把 window/document/body 上的 touchstart/touchmove（以及 wheel）监听的 passive 默认值改成 true，滚动性能优化：浏览器不再等 JS 决定是否 preventDefault 就直接滚动。修复：addEventListener 第三参显式传 `{ passive: false }`；更好的做法是优先用 CSS touch-action 声明手势区域，避免 JS 拦截。
</details>

<details>
<summary><b>7. 【挑战】线上告警「只有 iOS 用户反馈下单页白屏」，按本章 SOP 走一遍排查路径。</b></summary>

① 环境画像：监控按引擎分桶确认是否 100% WebKit、是否有版本聚集（59 册）；② 最小复现：BrowserStack 或真机同版本 Safari 打开，剥离业务到最小页面；③ 二分定位：vConsole/远程 Web Inspector 看报错，大概率是某 API undefined——插 60-01 能力探针确认；④ 查证：caniuse/MDN 确认该 API 的 WebKit 落地版本；⑤ 修复：polyfill 或降级分支（四级决策）；⑥ 回归：Playwright 加 WebKit project 用例，CI 门禁。全程先降级止血再修根因。
</details>

<details>
<summary><b>8. 【挑战】如何给团队设计一套「兼容性预算」机制，让兼容范围不靠口头约定？</b></summary>

四层落地：① 契约——browserslist 写进 package.json 作为唯一事实来源，PR 改它要走评审；② 构建——Babel/core-js/autoprefixer 全部以 browserslist 为输入，禁止手工全量垫片；③ CI 门禁——产物扫描（如未转译的可选链残留、超范围 API 引用）+ Playwright 三引擎冒烟；④ 数据闭环——监控按引擎版本分桶，每季度用真实 UA 分布复审 browserslist，低于阈值的环境从预算中剔除并公告。预算的本质：兼容范围是可度量、可执行、可收缩的工程决策，不是情怀。
</details>

## 60.7 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 用 UA 嗅探做功能开关 | 误判串高发，新浏览器被误伤 | 特性检测（typeof/in/CSS.supports），UA 只用于分桶与预警 |
| 2 | 按品牌维度想兼容性 | 同引擎品牌重复劳动，漏掉壳浏览器 | 按 Blink/WebKit/Gecko 三引擎思考 |
| 3 | 以为 iOS Chrome 是 Blink | iOS 上排查方向全错 | iOS 一切浏览器皆 WebKit，按 Safari 查 |
| 4 | 只做转译不补 polyfill | 旧引擎运行时报 API undefined | 语法转译与 API 垫片两线并行（01 册） |
| 5 | 试图 polyfill Proxy | 永远失败，响应式方案在老内核白屏 | Proxy 不可垫片，检测缺失只能换实现（27 册） |
| 6 | Safari 里 new Date 非 ISO 字符串 | Invalid Date，NaN 污染下游全部计算 | 接口定 ISO 8601；宽松输入用 60-02 逐字段构造 |
| 7 | 100vh 写全屏弹层 | iOS 地址栏伸缩时内容抖动/截断 | dvh/svh + visualViewport 兜底（08 册） |
| 8 | 输入框字号小于 16px | iOS 聚焦自动放大，布局被撑乱 | 输入框 font-size ≥ 16px |
| 9 | 依赖 unload 上报数据 | iOS Safari 数据丢失 | 用 pagehide + sendBeacon（19 册） |
| 10 | touchstart 里 preventDefault 拦滚动 | Chrome 默认 passive，拦截无效还告警 | 显式 passive:false，优先 CSS touch-action |
| 11 | 双核浏览器不写 meta 锁定 | 被切到 IE 内核，现代语法白屏 | head 最前放 renderer=webkit，并做切核失败的降级 |
| 12 | 微信 iOS 端 JSSDK 用当前路由 URL 签名 | SPA 切换路由后 JSSDK 能力静默失效 | iOS 用首跳 URL 签名，Android 用当前 URL |
| 13 | 忽略微信字体放大 | 用户调大字体后布局错乱 | 根容器 -webkit-text-size-adjust:100% |
| 14 | 兼容修复不留回归用例 | 下个版本同一坑复发 | Playwright WebKit/Firefox project 固化（09 册） |
| 15 | 兼容范围靠口头约定 | 评审无法决策，线上被长尾用户击穿 | browserslist + CI 扫描 + UA 分桶季度复审的「兼容性预算」 |
