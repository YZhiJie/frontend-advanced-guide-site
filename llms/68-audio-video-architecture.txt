## 68.1 形态坐标：延迟预算、互动强度与成本三轴

### 概念解析

音视频产品千差万别，但选型只受三个变量支配。先把产品放进坐标系，技术方案几乎是推导出来的：

| 轴 | 取值 | 对方案的影响 |
| --- | --- | --- |
| 延迟预算 | 30s（点播）/ 3-10s（直播）/ <500ms（连麦） | 决定 CDN 还是 RTC |
| 互动强度 | 只看 / 主播连麦 / 多对多互见 | 决定 RTC 通道人数与分层转发 |
| 规模与预算 | 百人 / 万人 / 千万级 | 决定是否自建、是否多区域、是否降级 |

四种典型形态的默认答案：

| 形态 | 典型产品 | 默认通道 | 关键指标 |
| --- | --- | --- | --- |
| 点播 | 课程回放、视频站 | 纯 CDN（HLS/DASH） | 首帧时间、卡顿率、起播成功率 |
| 单向直播 | 秀场、发布会、带货围观 | CDN（HTTP-FLV / LL-HLS） | 延迟、卡顿、峰值带宽 |
| 互动直播 | 大班课、连麦 PK | 混合：主播 RTC + 观众 CDN | 端到端延迟、连麦成功率 |
| 实时互动 | 1v1 客服、多人会议 | 纯 RTC（WebRTC/SFU） | 抖动、丢包恢复、MOS 分 |

```mermaid
flowchart TD
    A["确定产品形态"] --> B{"是否需要实时互见"}
    B -- 是 --> C{"同房间人数是否不超过 50"}
    C -- 是 --> D["纯 RTC：SFU 分层转发"]
    C -- 否 --> E["RTC 上麦 + CDN 围观"]
    B -- 否 --> F{"延迟预算是否低于 3 秒"}
    F -- 否 --> G["纯 CDN：HLS / DASH"]
    F -- 是 --> H{"预算是否覆盖混合方案"}
    H -- 是 --> E
    H -- 否 --> I["纯 CDN，并接受秒级延迟"]
```

**框架选型：买还是自建？**

| 路线 | 适合谁 | 代价 |
| --- | --- | --- |
| 云厂商 PaaS（声网/腾讯云/火山/AWS IVS 等） | 绝大多数业务：要快、要全球覆盖、没有专职媒体团队 | 单价高、深度定制受限、被厂商锁定 |
| 开源自建（SRS / mediasoup / FFmpeg / Janus） | 有媒体团队、量大、需要深度定制（私有协议、特殊转码） | 运维复杂度高、弱网优化要自己扛 |
| 混合 | 生产用 PaaS + 核心链路自建旁路 | 需要双套监控与对账，边界要划清 |

判断标准很朴素：**如果音视频不是你的核心竞争力，买；如果带宽账单已经是公司前三大成本，自建或混合。**

### 典型应用场景

- **电商直播**：观众千万级、主播几十人，典型「主播 RTC + 观众 CDN」，成本与延迟必须同时控；
- **在线教育**：大班课万人围观 + 小班课 1v6 连麦，两套形态共用一套账号与课件；
- **泛娱乐点播**：回放为主，重点是首帧与 CDN 命中率，延迟不敏感；
- **远程医疗/客服**：1v1 实时，延迟与稳定优先，画质可降、通话不能断。

### 最佳实践

- ✅ 先把「延迟预算」写成产品指标（如「观众看到主播动作到画面更新 ≤ 1.5s」），再谈技术；
- ✅ 用「人均每小时成本」而不是「总账单」做预算，规模变化时才能快速外推；
- ✅ 同一产品内允许混合形态：直播用 CDN，连麦瞬间切 RTC，用户无感；
- ❌ 不要给所有场景都上 RTC——RTC 的单位成本通常是 CDN 的数倍，千万级并发会直接失控；
- ❌ 不要承诺「零延迟」：物理链路 + 编码 + 抖动缓冲决定了 100-300ms 就是现实下限。

## 68.2 媒体链路六段：采集、编码、封包、推流、转码、分发与播放

### 概念解析

一条视频从主播到观众要经过六段，每一段都有独立的失败点：

```text
采集(摄像头/麦克风) → 编码(H.264/H.265/AV1) → 封包(FLV/MP4/TS)
   → 推流(RTMP/SRT/WHIP) → 转码(多档位/多协议) → 分发(CDN/边缘)
   → 播放(HLS/FLV/WebRTC)
```

```mermaid
graph LR
    subgraph 主播端
        A["采集：摄像头 / 麦克风"]
        B["编码：H.264 / H.265 / AV1"]
        C["封包：FLV / MP4 / TS"]
        D["推流：RTMP / SRT / WHIP"]
    end
    subgraph 服务端
        E["接入网关与鉴权"]
        F["转码：多档位 + 多协议"]
    end
    subgraph 分发与播放
        G["CDN 边缘节点"]
        H["播放器：选档 / 缓冲 / 降级"]
    end
    A --> B --> C --> D --> E --> F --> G --> H
```

**① 采集**：分辨率、帧率、码率三件套要匹配场景。1080p30 在移动端已是上限，4K 只在特定场景有意义（大屏、医疗影像）。采集层还要处理权限、前后台切换、设备热插拔。

**② 编码**：H.264 兼容性最好，H.265 省 30-50% 带宽但专利与兼容性有坑，AV1 更省但编码成本与端侧支持仍在爬坡。**编码档位（profile/level）选错，低端机直接解不动。**

**③ 封包与协议**：这是选型里最容易被忽略的一层。

| 协议 | 延迟量级 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RTMP | 1-3s | 推流事实标准、生态成熟 | 基于 TCP，弱网恢复差；浏览器不支持播放 |
| SRT | 1-3s | 抗丢包、适合上行不稳定 | 需要额外部署，浏览器不原生支持 |
| HTTP-FLV | 1-3s | 浏览器可播、长连接、低延迟 | 依赖自建/厂商支持，移动端兼容需验证 |
| HLS | 10-30s | 兼容性最好、可缓存 | 分片导致高延迟 |
| LL-HLS | 2-5s | 兼容 HLS 生态、延迟大幅下降 | 服务端与 CDN 需支持分块传输 |
| WebRTC | <500ms | 端到端最低延迟、抗弱网 | 不适合超大规模分发，成本高 |

**④ 推流**：主播侧上行是整条链路最脆弱的一环。家庭宽带的上行、4G/5G 的信号抖动、Wi-Fi 漫游都会直接反映到观众端。推流端要做码率自适应与断线重连。

**⑤ 转码**：一路输入转出多档位（1080p/720p/480p）+ 多协议（FLV/HLS/WebRTC）。转码是**固定成本**（与观众数无关），档位越多越贵。

**⑥ 分发与播放**：CDN 负责水平扩展，播放器负责选档、缓冲与降级。播放器的三件事：**起播快、少卡顿、能自愈**。

### 典型应用场景

- **上行不稳的户外直播**：SRT 或带重传的 RTMP，配合推流端码率自适应；
- **需要浏览器零插件播放**：HTTP-FLV（低延迟）或 HLS（高兼容）；
- **多端一致**：同一场直播同时产出 FLV、HLS、WebRTC 三种出口，按端能力分发；
- **低成本回放**：只转 HLS 两档（720p/480p），存储按保留期分层。

### 最佳实践

- ✅ 首帧优化优先级最高：播放器预加载、DNS 预解析、封面图先行，用户感知的「快」来自首帧；
- ✅ 转码档位按真实分布裁剪：80% 观众只看 720p，就不要为 4K 付全量转码费；
- ✅ 推流端必须实现「断线重连 + 码率自适应 + 本地缓冲」，这是主播侧体验的三件套；
- ⚠️ H.265 只在确认端侧支持矩阵后启用，否则会出现「一部分用户黑屏」；
- ❌ 不要用 HLS 做「低延迟直播」：分片天然带 10s 级延迟，LL-HLS 也要服务端配套；
- ❌ 不要在播放器里写死单一档位，网络一变就只能卡着。

## 68.3 CDN 与 RTC 双通道：混合连麦与就近接入

### 概念解析

真实产品几乎都需要两条通道同时存在：

```mermaid
graph TD
    HOST["主播"] -- "RTC 上行约 200ms" --> GW["媒体网关 / SFU"]
    GUEST["连麦嘉宾"] <-- "RTC 转发，低延迟" --> GW
    GW -- 旁路 --> T["转码集群"]
    T --> CDN1["CDN 区域 A"]
    T --> CDN2["CDN 区域 B"]
    CDN1 --> V1["观众：就近接入，1-3 秒"]
    CDN2 --> V2["观众：跨区回源，成本更高"]
```

**混合方案的关键是「同一场直播、两种延迟」**：连麦的人看到的是 200ms 的画面，观众看到的是 1-3s 的画面。产品文案必须接受这个事实，否则运营会不断提「为什么观众比主播慢」。

**就近接入**是规模化的前提：

- 观众按地理区域调度到最近边缘节点；
- 主播上行接入就近的媒体网关，再回源到中心；
- 跨区域直播要区分「同区转发」与「跨区回源」，后者成本与延迟都更高。

**RTC 的容量边界**要提前算清：

| 场景 | 单房间上限（量级） | 扩容手段 |
| --- | --- | --- |
| 1v1 | 2 | 无 |
| 小班课 | 6-16 | 分层转发（SFU） |
| 多人会议 | 16-50 | 分房间 + 只转发活跃发言者 |
| 大型互动 | 50+ | 观众降级为 CDN 只读，仅少数人上麦 |

**前端播放器的双通道切换**要处理三件事：切换时的画面衔接（避免黑屏）、信令超时、以及「RTC 不可用自动退回 CDN」的兜底。

### 典型应用场景

- **直播带货连麦**：主播 + 嘉宾走 RTC，观众走 CDN，评论区实时性由长连接保证；
- **大班课**：老师 RTC 上行，学生 CDN 下行，少数学生申请上麦后切 RTC；
- **跨国会议**：多地就近接入 + 中心转发，必要时降低分辨率保连通；
- **赛事直播**：纯 CDN 多区域分发，互动靠弹幕与投票，不引入 RTC。

### 完整代码示例

选型不是拍脑袋，而是把「延迟预算 + 互动强度 + 成本」三个输入喂给一个决策器：

```typescript
// 文件: examples/68-01-channel-selector.ts（核心节选）
if (d.shape === "interactive-class") {
  reasons.push("师生需连麦,但大多数学生只看:主播走 RTC、观众走 CDN");
  if (d.viewers > 1000) risks.push("千人大班连麦需限制上台人数,否则 RTC 成本失控");
  return { transport: "hybrid", expectedLatencyMs: LATENCY.hybrid, reasons, risks };
}
const hybridCost = estimateHourlyCost(d, "hybrid");
if (hybridCost > d.budgetYuanPerHour) {
  risks.push("退化为纯 CDN 后延迟升至秒级,秒杀/抢购类话术会失效");
  return { transport: "cdn", expectedLatencyMs: LATENCY.cdn, reasons, risks };
}
```

> 运行方式：`npx tsx examples/68-01-channel-selector.ts`（五种形态的通道决策、延迟预算校验、预算不足时退化并给出业务后果，共 12 组硬断言）。

### 最佳实践

- ✅ 连麦人数在 UI 上明确限制（如「本场最多 4 位嘉宾」），别让 RTC 成本被运营无意放大；
- ✅ 双通道切换要有兜底：RTC 建连失败 3 秒内自动退回 CDN，并提示「已切换为流畅模式」；
- ✅ 跨区域直播先算回源成本，再决定「多地转码」还是「单点转码 + 跨区分发」；
- ✅ 观众侧的「低延迟模式」做成开关，让用户自己权衡延迟与流量；
- ⚠️ RTC 与 CDN 的时间轴要统一，否则连麦画面与观众画面会出现不同步的「时间差」；
- ❌ 不要用 RTC 承载千万级观众：SFU 的转发成本随人数线性上升，规模一大就不成立。

## 68.4 千万级并发：分层调度、限流与降级阶梯

### 概念解析

千万级并发的核心不是「服务器更强」，而是**把请求拆到不同的层，并让每一层都能独立限流**：

| 层 | 职责 | 扩容方式 | 失效表现 |
| --- | --- | --- | --- |
| 接入层 | 就近接入、鉴权、路由 | 多区域多可用区 | 建连失败、白屏 |
| 调度层 | 房间分配、区域选择、容量感知 | 无状态水平扩容 | 分配慢、错误区域 |
| 媒体层 | 转码、转发、混流 | 按房间/区域扩容 | 卡顿、花屏 |
| 分发层 | CDN 边缘缓存 | 厂商弹性 | 回源被打满 |
| 播放层 | 选档、缓冲、重试 | 客户端自治 | 起播慢、卡顿 |

**限流要分三层做**，只做网关限流会把真实用户和攻击流量一起挡住：

1. **入口限流**：按 IP/设备/账号的建连频率；
2. **房间限流**：单房间最大在线人数、最大连麦人数；
3. **回源限流**：源站按带宽与 QPS 保护，宁可让边缘降级，也不能让源站雪崩。

**降级阶梯**是千万级产品的必备件。原则是「**快降慢升、单步调整、滞回观察**」：

```text
L0 1080p60 → L1 1080p30 → L2 720p → L3 480p → L4 仅音频
```

- 降级条件：帧率 < 15、丢包 > 12%、RTT > 500ms、缓冲 < 0.4s，任一命中立即降；
- 升级条件：四项指标全部健康且连续 3 个窗口，才升一档；
- 永不一次跳到底：一步一档，避免在边界反复横跳（抖动）。

```mermaid
flowchart TD
    M["采集一个窗口：fps / RTT / 丢包 / 缓冲"] --> D{"任一劣化阈值命中"}
    D -- 是 --> DOWN["立即降一档，最低到仅音频"]
    D -- 否 --> H{"四项指标是否全部健康"}
    H -- 否 --> HOLD["保持档位，稳定计数清零"]
    H -- 是 --> U{"连续健康窗口是否达到 3 个"}
    U -- 否 --> HOLD
    U -- 是 --> UP["升一档，一次只升一档"]
```

### 典型应用场景

- **明星直播/大促**：峰值是平时的 100 倍，靠弹性 CDN + 入口限流扛住；
- **晚会级直播**：多区域多活，任何单区域故障都要能秒级切走；
- **弱网地区**：4G/城中村/地铁场景，降级阶梯决定「能不能看下去」；
- **成本敏感型产品**：用降级把「高画质」变成按网络与付费等级分层的权益。

### 完整代码示例

```typescript
// 文件: examples/68-02-quality-ladder.ts（核心节选）
function tick(state: LadderState, m: Metrics) {
  const down = shouldDown(m);
  if (down) return { next: { level: Math.min(4, state.level + 1), stableWindows: 0 }, action: "down" };
  if (!isHealthy(m)) return { next: { level: state.level, stableWindows: 0 }, action: "hold" };
  // 连续 3 个健康窗口才升一档:升级比降级保守得多
  if (state.stableWindows + 1 < 3) return { next: { ...state, stableWindows: state.stableWindows + 1 }, action: "hold" };
  return { next: { level: state.level - 1, stableWindows: 0 }, action: "up" };
}
```

> 运行方式：`npx tsx examples/68-02-quality-ladder.ts`（快降慢升、单步调整、滞回窗口、临界指标清零、最低档位不再下降，共 9 组硬断言）。

### 最佳实践

- ✅ 把「在线人数、建连成功率、卡顿率、首帧时间」做成实时大盘，峰值时按分钟看；
- ✅ 大促前做容量压测：按「峰值 × 1.5」预估建连 QPS 与转码路数，提前扩容；
- ✅ 降级策略放客户端执行，服务端只下发阈值，避免中心化决策成为瓶颈；
- ✅ 观众侧接 CDN、主播侧接 RTC 的分层要在架构图上写清楚，故障时才知道该切哪；
- ⚠️ 房间数暴涨会打爆调度层：调度必须无状态，且能按区域分片；
- ❌ 不要在源站做「智能限流」：源站只做硬保护，智能决策放边缘与客户端；
- ❌ 不要把降级阈值写死在前端包里：不同地区、不同机型的最优阈值不同，必须可下发。

## 68.5 质量指标与成本核算：把体验做成可算的账

### 概念解析

音视频的质量要能被量化，否则「有点卡」永远无法验收。五个核心指标：

| 指标 | 定义 | 目标（量级） |
| --- | --- | --- |
| 首帧时间 | 点击播放到第一帧渲染 | < 1s（直播）/< 0.5s（点播） |
| 卡顿率 | 卡顿次数 / 播放时长 | < 1 次/小时 |
| 卡顿时长占比 | 卡顿总时长 / 播放总时长 | < 0.5% |
| 起播成功率 | 成功起播 / 播放请求 | > 99% |
| 端到端延迟 | 采集到呈现 | 按形态定，连麦 < 500ms |

**成本四本账**，顺序固定：

1. **出口流量**（最大头）：并发 × 单观众码率 × 时长 × 区域系数；
2. **转码**（固定成本）：档位数 × 直播时长 × 单价，与观众数无关；
3. **存储**（长尾成本）：回放体积 × 保留天数；
4. **信令与调度**（通常最小，但房间数暴涨时会变显著）。

一个反直觉但重要的事实：**多转一档的边际成本很低，但一旦有观众看，出口流量会按该档码率线性放大**。所以「加个 4K 档位」的决策，必须同时看「有多少人会看」和「他们看多久」。

### 典型应用场景

- **成本复盘**：月度账单拆成四本账，定位是流量涨了还是转码档位加多了；
- **体验验收**：上线前用五个指标做基线，上线后按周对比；
- **定价设计**：高清/超清作为付费权益，用成本差额倒推定价；
- **容量规划**：用「人均 GB/小时」× 预估并发，快速估算峰值带宽。

### 完整代码示例

```typescript
// 文件: examples/68-03-media-cost.ts（核心节选）
const weightedMbps = p.renditions.reduce((s, r) => s + r.mbps * (p.mix[r.name] ?? 0), 0) + AUDIO_MBPS;
const egressGb = ((p.viewers * weightedMbps * p.hours * 3600) / 8 / 1024) * regions;
const transcodeYuan = p.renditions.length * p.hours * p.transcodePricePerHour * regions;
const storageGb = ((topMbps * p.hours * 3600) / 8 / 1024) * p.renditions.length;
```

> 运行方式：`npx tsx examples/68-03-media-cost.ts`（出口流量加权、转码固定成本、回放存储、跨境区域系数、新增档位边际成本、4K 占比放大，共 10 组硬断言）。

### 最佳实践

- ✅ 成本估算脚本进仓库，产品改档位时先跑一遍再评审；
- ✅ 监控里同时看「卡顿率」和「降级率」：降级率突然升高说明网络或源站出了问题；
- ✅ 回放保留期按业务分层（7 天 / 90 天 / 永久），别默认永久；
- ✅ 峰值带宽按「并发 × 加权码率 × 1.3 冗余」预留，CDN 也有回源上限；
- ⚠️ 跨境分发单价与合规成本都要计入，别只乘一个区域数；
- ❌ 不要用「总账单 ÷ 总播放时长」做决策：不同档位、不同区域的边际成本差异巨大；
- ❌ 不要只优化转码成本：转码通常只占小头，出口流量才是主战场。

## 68.6 自测题

<details>
<summary><b>1. 【基础】为什么点播和连麦不能共用同一套传输通道？</b></summary>

点播对延迟不敏感（30s 都可接受），要的是高并发与低成本，CDN + HLS/DASH 是最优解；连麦要求端到端 < 500ms，CDN 的分片机制天然做不到，必须走 RTC。两者的成本结构也不同：CDN 按流量、RTC 按并发与转发，混用会让成本和体验都失控。
</details>

<details>
<summary><b>2. 【基础】HTTP-FLV、HLS、WebRTC 的延迟量级分别是多少？分别适合什么场景？</b></summary>

HTTP-FLV 约 1-3s，适合浏览器低延迟直播；HLS 约 10-30s（LL-HLS 可到 2-5s），兼容性最好，适合点播与对兼容性要求高的直播；WebRTC < 500ms，适合连麦、会议等实时互动。选择依据是延迟预算，而不是「哪个更新」。
</details>

<details>
<summary><b>3. 【基础】为什么「多转一个 4K 档位」在没人看的时候几乎不花钱，但可能非常贵？</b></summary>

转码是固定成本（档位数 × 时长），无人观看时只增加少量转码与存储费用；但一旦有观众选择该档位，出口流量会按 4K 码率（约 15Mbps）线性放大，CDN 费用随观看人数和时长快速增长。所以决策必须同时看「渗透率」与「观看时长」。
</details>

<details>
<summary><b>4. 【进阶】千万级并发的直播，为什么要分「接入 / 调度 / 媒体 / 分发 / 播放」五层限流？</b></summary>

不同层的瓶颈完全不同：接入层怕建连风暴，调度层怕房间数暴涨，媒体层怕转码与转发打满，分发层怕回源被打穿，播放层怕集中重试。只在网关做限流会把正常用户和攻击流量一起挡住；分层限流才能做到「该保护的保护、该放行的放行」，并在单层故障时独立降级。
</details>

<details>
<summary><b>5. 【进阶】降级阶梯为什么必须「快降慢升、一次一档」？</b></summary>

卡顿对体验是断崖式的，必须立刻降级；但网络刚恢复就立刻升档，会在临界点反复横跳，造成画质闪烁与额外卡顿。一次只升一档 + 连续 N 个健康窗口才升级，本质是给系统加滞回（hysteresis），用少量画质换稳定。
</details>

<details>
<summary><b>6. 【进阶】混合连麦方案里，主播和观众的「两种延迟」如何向产品和运营解释？</b></summary>

把它定义成产品事实而不是缺陷：连麦嘉宾在 200ms 内互相看到，是为了互动；观众在 1-3s 内看到，是为了支撑千万级并发与低成本。运营话术要围绕「互动区」与「围观区」设计，例如「上麦需要申请，上麦后延迟降至实时」；同时统一两条通道的时间轴，避免出现明显的时间差穿帮。
</details>

<details>
<summary><b>7. 【挑战】请给出一个「千万级观众、几十位主播、需要连麦」直播间的架构草案，并说明每一层的降级手段。</b></summary>

架构：主播与嘉宾经就近接入进 RTC 媒体网关（SFU 分层转发）→ 网关旁路转码出 FLV/LL-HLS → 多区域 CDN 边缘分发 → 观众侧播放器按网络选档。分层降级：接入层限建连频率并按区域调度；调度层无状态分片，容量不足时引导到备用区域；媒体层限制单房间连麦人数、必要时降混流分辨率；分发层回源限流 + 边缘缓存预热；播放层执行 L0-L4 降级阶梯并在 RTC 失败时退回 CDN。成本上用「出口流量 + 转码 + 存储」三本账做峰值预估。
</details>

<details>
<summary><b>8. 【挑战】产品要上线 4K 超清权益，你如何用数据判断该不该做、定价多少？</b></summary>

先估算渗透率与观看时长：4K 码率约为 1080p 的 3-4 倍，出口流量按「渗透率 × 时长」放大；再用 68-03 的成本模型算出每人每月的增量成本，加上存储与转码增量。决策标准是「增量收入 ≥ 增量成本 × 安全系数」，并设置灰度与降级兜底（网络不达标自动回落 1080p）。若渗透率低但战略价值高，可先做小范围权益验证，而不是全量开放。
</details>

## 68.7 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 所有场景都上 RTC | 单位成本是 CDN 的数倍，规模一大直接失控 | 按延迟预算选型，围观走 CDN |
| 2 | 用 HLS 做低延迟直播 | 分片天然 10s 级延迟，运营话术全部失效 | 低延迟用 FLV/LL-HLS，连麦用 RTC |
| 3 | 承诺「零延迟」 | 物理与编码决定下限，承诺即违约 | 明确延迟预算与「互动区/围观区」 |
| 4 | 播放器写死单一码率 | 网络一变就卡死，无法自愈 | 多档位 + 客户端选档 + 降级阶梯 |
| 5 | 降级一次跳到底 | 画质断崖，用户直接退出 | 一次一档，快降慢升 |
| 6 | 网络刚恢复就升档 | 临界点反复横跳，画质闪烁 | 连续 N 个健康窗口才升，加滞回 |
| 7 | 降级阈值硬编码在包内 | 不同地区/机型水土不服 | 阈值服务端下发，可按人群灰度 |
| 8 | 只做网关限流 | 真实用户与攻击流量一起被挡 | 接入/房间/回源三层限流 |
| 9 | 源站承担智能决策 | 源站被打穿，全站雪崩 | 源站只做硬保护，决策放边缘与端 |
| 10 | 转码档位照抄竞品 | 为无人观看的档位持续付费 | 按真实观看分布裁剪档位 |
| 11 | 只看总账单不看结构 | 找不到成本上涨的真实原因 | 拆出口/转码/存储/信令四本账 |
| 12 | 回放默认永久保留 | 存储长尾成本逐年累积 | 按业务分层设置保留期 |
| 13 | 忽略跨境回源成本 | 多区域直播利润被带宽吃掉 | 先算回源，再决定多地转码 |
| 14 | RTC 失败无兜底 | 连麦一挂，整场直播黑屏 | 3 秒内自动退回 CDN 并提示 |
| 15 | 只监控在线人数 | 卡顿与降级无人感知，投诉才暴露 | 首帧/卡顿率/降级率/起播成功率全采集 |
