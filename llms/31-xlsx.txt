## 31.1 心智模型与选型

### 31.1.1 概念解析

一份 `.xlsx` 本质是 ZIP 容器，里面装着工作表 XML、共享字符串、样式表和关系文件。SheetJS 把整包解析成三层对象，理解这三层比背 API 更重要：

| 层次 | 对象 | 关键字段 |
| --- | --- | --- |
| 工作簿 | `WorkBook` | `SheetNames`、`Sheets`、`Workbook.WBProps.date1904` |
| 工作表 | `WorkSheet` | 以 `A1` 地址为键的稀疏表、`!ref`、`!merges`、`!cols`、`!rows` |
| 单元格 | `CellObject` | `t`、`v`、`w`、`f`、`z`、`s` |

`t` 是值类型：`s` 文本、`n` 数字、`b` 布尔、`d` 日期、`e` 错误、`z` 空。`v` 是原始值，`w` 是 Excel 显示出来的格式化文本，`f` 是公式原文，`z` 是数字格式串，`s` 是样式对象。**只认 `v` 会丢掉显示语义，只认 `w` 会把数字当文本**，导入时两者都要有策略。

工作表是**稀疏**的：没有值的单元格根本不存在，`worksheet['B2']` 可能返回 `undefined`。范围靠 `!ref` 描述（如 `A1:D101`），但 `!ref` 只是编辑器的矩形假设，可能包含大量空行，不能直接当真实数据量。合并单元格只在左上角保存值，`!merges` 记录零基的起止行列。

选型上，社区版 SheetJS 与 ExcelJS 的分工非常清晰：

| 维度 | SheetJS CE 0.18 | ExcelJS |
| --- | --- | --- |
| 格式覆盖 | xls、xlsx、xlsb、ods、csv 等 | 主要是 xlsx、csv |
| 读 xlsx | 整包读入内存，支持 `dense` | 支持流式 reader |
| 写样式 | 不支持字体/颜色/边框，仅 `!cols`、`!rows`、`z` | 完整样式、图片、条件格式 |
| 公式 | 只存 `f` 与缓存 `v`，不计算 | 同样不计算，但可写结果 |
| 流式写 | Node 下可把工作表流式写成 CSV/HTML | 有 streaming writer |
| 适用 | 通用导入、数据导出、无样式报表 | 模板保真、复杂样式、大文件流式 |

### 31.1.2 典型应用场景

- 后台列表导出：把查询结果直接映射为多 Sheet 工作簿，前端生成 Blob 下载
- 批量导入：解析用户上传的 xlsx/csv，归一化、校验、回显错误行号
- 模板填充：读取财务/人事模板，替换指定单元格后回写
- 数据交换：服务端生成 CSV 给对账系统，前端预览前几行
- 大文件分析：只读表头与少量样例行，或把解析卸载到 Worker

### 31.1.3 可运行代码示例

先用最小的代码把三层对象看清楚。注意 `!ref` 是字符串范围，`!merges` 是零基坐标，单元格要判空：

```ts
import * as XLSX from 'xlsx';
const workbook = XLSX.read(buffer, { type: 'buffer', cellDates: true });
const sheetName = workbook.SheetNames[0];
const worksheet = sheetName === undefined ? undefined : workbook.Sheets[sheetName];
if (worksheet === undefined) throw new Error('空工作簿');
console.log(worksheet['!ref']); // "A1:C4"，只是范围假设
console.log(worksheet['!merges']); // [{ s: { r: 0, c: 0 }, e: { r: 0, c: 2 } }]
const cell = worksheet['B2'];
console.log(cell?.t, cell?.v, cell?.f); // "n" 128 "B1*2" 或 undefined
```

实验室把「对象数组 → 多 Sheet 工作簿」「工作簿 → 字节流」「字节流 → 对象数组」串成了三个函数，后文示例都复用它们：

```ts
import { bufferToRows, exportRowsToWorkbook, workbookToBuffer } from './src/index.js';
const workbook = exportRowsToWorkbook([
    { name: '订单', rows: orders },
    { name: '汇总', rows: summary, columns: ['指标', '数值'] },
]);
const bytes = workbookToBuffer(workbook);
const rows = bufferToRows(bytes, { sheetName: '订单' });
```

### 31.1.4 最佳实践

- 把 `WorkBook` 当**传输层**：进出业务代码前先转成普通对象数组，不要让单元格对象渗透到领域层
- 任何来自用户的表格都先过 `normalizeCellValue` 与 `validateRows`，再入库
- 选型先问「要不要保真样式」「要不要流式」，两个都要就优先 ExcelJS，否则 SheetJS 更轻
- 固定 SheetJS 版本并关注安全公告：npm 上的 0.18.5 已停更，官方新版本通过自有 CDN 分发

### 31.1.5 自测题

<details>
<summary><b>1. 【基础】SheetJS 的 Workbook、Worksheet、Cell 三层对象分别承载什么信息？</b></summary>

Workbook 承载 SheetNames、Sheets 映射与文档级属性；Worksheet 是以 A1 地址为键的稀疏单元格表，附带 `!ref`、`!merges`、`!cols` 等元信息；Cell 承载单个格子的 `t` 类型、`v` 原始值、`w` 显示文本、`f` 公式、`z` 格式与 `s` 样式。三层各管一层语义，不要把 Cell 直接当业务数据。
</details>

<details>
<summary><b>2. 【进阶】为什么工作表说「稀疏」，`!ref` 为什么不能直接当作真实数据行数？</b></summary>

没有值的单元格不会创建对象，读取不存在的地址只会得到 undefined，所以是稀疏结构。`!ref` 只是编辑器记录的矩形范围，删除行、格式化整列、复制粘贴都会把它撑大，可能包含成千上万空行。可靠的数据量应通过遍历真实单元格或 `sheet_to_json` 后过滤空行得到。
</details>

<details>
<summary><b>3. 【挑战】一个需求既要导入 50 万行 xlsx，又要导出带品牌色和合并表头的报表，如何选型与拆分？</b></summary>

导入与导出应拆成两条技术路径：导入用 SheetJS（`dense: true` + Worker + 行数上限）或服务端流式读取；导出报表若必须保留样式与合并，选 ExcelJS 的 streaming writer，或在服务端用模板引擎生成。不要指望社区版 SheetJS 同时满足「大文件流式读」和「完整样式写」，这两个恰是它的能力边界。
</details>

## 31.2 入门

### 31.2.1 概念解析

读文件只有一步：`XLSX.read(data, options)`。`data` 可以是 `Buffer`、`Uint8Array`、`ArrayBuffer` 或 base64 字符串；浏览器上传场景先用 `await file.arrayBuffer()` 拿到二进制，再以 `type: 'array'` 读。读出来的工作簿不会自动变成数组，需要 `XLSX.utils.sheet_to_json`。

`sheet_to_json` 有两种模式：

- 默认对象模式：第一行作表头，返回 `Record<string, unknown>[]`，适合业务数据
- `header: 1`：返回二维数组（AoA），保留列顺序、允许重复表头与无表头数据

写方向对应 `json_to_sheet`、`aoa_to_sheet` 和 `book_append_sheet`。**`json_to_sheet` 只拿第一行对象的键当表头**，后续行多出来的字段会被静默丢弃；这是导入导出里最常见的数据丢失源。实验室的 `exportRowsToWorkbook` 先做键的并集，或由调用方显式传 `columns`，从根上规避这个问题。

### 31.2.2 典型应用场景

- 把接口返回的 JSON 列表导出成单 Sheet 报表
- 把二维数组（如数据库查询结果）原样写成表格
- 读取用户上传的表格并转成对象数组，交给表单或接口

### 31.2.3 可运行代码示例

AoA 适合「有表头但列名重复」或「纯矩阵」；对象数组适合「字段明确」的业务数据。两者可以互转：

```ts
import * as XLSX from 'xlsx';
const aoa = [['姓名', '年龄'], ['张三', 30]];
const worksheet = XLSX.utils.aoa_to_sheet(aoa, { cellDates: true });
const objects = XLSX.utils.sheet_to_json<{ 姓名: string; 年龄: number }>(worksheet, { defval: null, raw: true });
const matrix = XLSX.utils.sheet_to_json<unknown[]>(worksheet, { header: 1, defval: null });
console.log(objects[0]?.['姓名'], matrix[1]?.[1]); // "张三" 30
```

多 Sheet 导出的完整链路，直接用实验室函数，注意每张表独立声明列顺序：

```ts
import { bufferToRows, exportRowsToWorkbook, workbookToBuffer } from './src/index.js';
const workbook = exportRowsToWorkbook([
    {
        name: '明细',
        columns: ['订单号', '金额', '下单时间'],
        rows: [
            { 订单号: 'A-001', 金额: 128, 下单时间: new Date(2026, 9, 20, 10, 30) },
            { 订单号: 'A-002', 金额: 256, 下单时间: null },
        ],
    },
    { name: '说明', rows: [{ 版本: 'v1', 生成时间: '2026-10-21' }] },
]);
const bytes = workbookToBuffer(workbook);
const detail = bufferToRows(bytes, { sheetName: '明细' });
console.log(detail[0]?.['金额'], detail[0]?.['下单时间'] instanceof Date); // 128 true
```

### 31.2.4 最佳实践

- 统一用 `sheet_to_json` 的 `defval: null`，否则缺失字段是 undefined，校验时容易漏判
- 需要原始类型就传 `raw: true`；需要 Excel 显示文本就传 `raw: false` 并接受字符串
- 不要用 `json_to_sheet` 直接写多行异构对象，先并集列或显式声明 `columns`
- 导出函数接受 `readonly` 数组，内部不改输入；实验室的 `SheetDefinition` 就是这种契约

### 31.2.5 自测题

<details>
<summary><b>4. 【基础】`sheet_to_json` 默认模式与 `header: 1` 分别返回什么？</b></summary>

默认模式把第一行当表头，返回以列名为键的对象数组；`header: 1` 返回二维数组，第一行原样保留。前者适合字段明确的业务数据，后者适合矩阵、重复表头或需要保留列顺序的场景。两种模式都可配 `defval` 与 `raw`。
</details>

<details>
<summary><b>5. 【进阶】`json_to_sheet` 为什么会导致「后面的列消失」？如何修复？</b></summary>

它只读取第一行对象的键作为表头，后续对象里新增的键不会补列。修复方式有两种：先遍历所有行做键的并集再生成表头，或显式传入完整列顺序后逐行映射成 AoA。实验室的 `exportRowsToWorkbook` 采用前者，同时允许 `columns` 覆盖。
</details>

<details>
<summary><b>6. 【进阶】`workbookToBuffer` 与 `bufferToRows` 往返时，为什么要保持 `cellDates` 一致？</b></summary>

写日期时 `cellDates: true` 让日期写成 `d` 类型单元格，读回时同样的选项才会还原成 Date；任何一侧缺失，日期都可能变成 Excel 序列号（如 45432）。类型契约要在读写两端同时声明，不能只改一端。
</details>

## 31.3 进阶

### 31.3.1 概念解析

**CSV 不是「逗号分隔的字符串」这么简单**。它没有类型、没有工作表，靠三条约定存活：UTF-8 BOM 让 Excel 认出编码；CRLF 作为 RFC 4180 的行结束符；字段内的逗号、引号、换行必须用双引号包裹，内部引号双写。少一条就会出现中文乱码、列错位或整行吞并。实验室的 `exportCsv` 默认带 BOM 与 CRLF，`parseCsv` 能处理引号、字段内换行与 CRLF/LF/CR。

**公式**在文件里是「公式文本 + 缓存值」两部分。SheetJS 社区版不会计算，写入时只给 `f` 不给 `v`，预览或下游读取就会得到空值；正确做法是同时写 `v`，或由服务端先算好。读取时 `f` 是否存在取决于选项（默认会带出），但业务代码不应依赖重新计算。

**日期**是 Excel 的历史包袱：序列号以 1899-12-30 为原点（为了兼容 1900 年不存在的 2 月 29 日），且存在 1904 日期系统。`cellDates` 决定读写时是否转成 JS Date；但 Excel 存的是「墙上时间」，没有时区，跨时区用 `toISOString` 会漂移。只关心日期时，写成 `YYYY-MM-DD` 文本反而更稳。

**合并单元格**只保留左上角的值，其余位置是空。导入时若不做「向右/向下填充」，按行读取会得到大量空值；导出时若给合并区域每个格都赋值，Excel 打开后只显示左上角，容易误以为数据丢了。

### 31.3.2 典型应用场景

- 对账文件导出 CSV 给第三方系统，必须可控分隔符与换行
- 报价单写入公式，同时提供缓存值供前端预览
- 考勤/排期导入，日期列同时存在 Date、序列号与文本三种形态

### 31.3.3 可运行代码示例

CSV 往返：BOM 在文本开头，解析时自动剥离；数字文本默认不转 number，避免工号前导零丢失：

```ts
import { exportCsv, normalizeCellValue, parseCsv } from './src/index.js';
const csv = exportCsv(
    [{ 姓名: '张三, "工程师"', 工号: '00123', 备注: '第一行\n第二行' }],
    { delimiter: ',', eol: '\r\n', bom: true },
);
console.log(csv.charCodeAt(0) === 0xfeff); // true
const table = parseCsv(csv);
const age = normalizeCellValue(table[1]?.[1], { coerceNumericStrings: true });
```

公式与缓存值：`f` 是给 Excel 看的，`v` 是给不计算的读者看的，两者要一起写：

```ts
import * as XLSX from 'xlsx';
import { workbookToBuffer } from './src/index.js';
const worksheet = XLSX.utils.aoa_to_sheet([['数量', '单价', '金额'], [2, 56.5, null]]);
worksheet['C2'] = { t: 'n', f: 'A2*B2', v: 113 };
const workbook = XLSX.utils.book_new();
XLSX.utils.book_append_sheet(workbook, worksheet, '报价');
const bytes = workbookToBuffer(workbook);
```

日期写入与读回：显式 `cellDates`，并接受「Excel 只存墙上时间」这一事实：

```ts
import { bufferToRows, exportRowsToWorkbook, workbookToBuffer } from './src/index.js';
const bytes = workbookToBuffer(
    exportRowsToWorkbook([
        { name: '排期', rows: [{ 任务: '上线', 日期: new Date(2026, 9, 21, 9, 30) }] },
    ]),
);
const [row] = bufferToRows(bytes);
console.log(row?.['日期'] instanceof Date); // true
```

合并单元格：只写左上角，范围用零基坐标声明；读取时按需填充：

```ts
import * as XLSX from 'xlsx';
const worksheet = XLSX.utils.aoa_to_sheet([['部门', null, '姓名'], [null, null, '张三'], ['研发', null, '李四']]);
worksheet['!merges'] = [{ s: { r: 0, c: 0 }, e: { r: 1, c: 1 } }];
```

### 31.3.4 最佳实践

- CSV 导出固定 BOM + CRLF；面向欧洲 locale 时把分隔符做成配置，而不是硬编码逗号
- 解析 CSV 后先归一化再做类型校验；不要用 `Number()` 直接强转整列
- 公式单元格始终补 `v`；不要在浏览器里承诺「实时计算 Excel 公式」
- 日期导出优先「日期单元格 + 明确格式」或「ISO 文本」，二选一并在接口文档写死
- 合并表头在导入侧做填充展开，在导出侧只写左上角并登记 `!merges`

### 31.3.5 自测题

<details>
<summary><b>7. 【基础】CSV 为什么默认要带 UTF-8 BOM？BOM 会影响解析吗？</b></summary>

BOM 是 `\uFEFF`，Excel 靠它识别文件是 UTF-8，否则中文在部分 Windows 环境会按本地编码解释成乱码。解析时 BOM 会变成第一个字段的隐形前缀，所以 `parseCsv` 要在入口剥离它，避免表头变成「\uFEFF姓名」。
</details>

<details>
<summary><b>8. 【进阶】一个单元格同时有 `f` 和 `v`，`w` 又是什么？为什么社区版必须自己保证 `v`？</b></summary>

`f` 是公式原文，`v` 是缓存的计算结果，`w` 是按数字格式渲染后的显示文本。SheetJS 社区版没有公式计算引擎，不会在写入时求值，所以只写 `f` 的文件在预览或程序读取时拿不到结果。写入方必须提供正确的 `v`，或让 Excel 打开后重算。
</details>

<details>
<summary><b>9. 【进阶】为什么同一天的时间用 `toISOString` 写进 Excel 会「差 8 小时」？如何避免？</b></summary>

`toISOString` 输出 UTC，而 Excel 日期单元格存的是没有时区的墙上时间，SheetJS 按本地时间解释。东八区的 09:30 会变成 01:30。避免方式：用本地年月日时分秒构造 Date 或直接格式化成 `YYYY-MM-DD HH:mm:ss` 文本；跨时区传输时在接口层明确约定时区，不要依赖单元格。
</details>

## 31.4 精通

### 31.4.1 概念解析

**样式是社区版最大的边界**。`cell.s` 可以赋值，但社区版写 xlsx 时会忽略字体、颜色、边框、对齐；能保留的主要是数字格式 `z`、列宽 `!cols`、行高 `!rows`。如果交付物要求品牌色、条件格式或图片，选 ExcelJS 或服务端模板，别在 SheetJS 上反复试。

**大文件的核心矛盾是内存**。xlsx 是 ZIP，社区版读取必须整包解压后在内存里建对象树，10 万行乘以几十列很容易到几百 MB。可用手段按性价比排序：限制文件大小与行数 → `sheetRows` 只读前 N 行做预览 → `dense: true` 降低对象开销 → 把解析放进 Worker 避免冻结主线程 → 服务端流式或分片处理。社区版没有真正的 xlsx 流式读取，这一点要提前告知产品。

**Worker 卸载**的关键是只传二进制、只回精简结果。把 `ArrayBuffer` 用 transferable 移交，避免结构化克隆整份数据；Worker 里解析完只回传行数组或统计信息，不要把 `WorkBook` 对象回传，否则克隆成本可能超过解析本身。

### 31.4.2 典型应用场景

- 报表要求列宽、行高、千分位，但不要求配色
- 后台导入几十万行，页面不能卡死，还要显示进度
- 下载按钮生成 xlsx，需兼容 Safari 的 Blob 行为

### 31.4.3 可运行代码示例

社区版能做的格式控制：列宽、行高与数字格式；`s` 只保留在内存里，写出即丢：

```ts
import * as XLSX from 'xlsx';
const worksheet = XLSX.utils.aoa_to_sheet([['金额'], [128000]]);
const header = worksheet['A1'];
if (header) {
    header.s = { font: { bold: true } }; // 社区版写出时被忽略
    header.z = '0.00';
}
worksheet['!cols'] = [{ wch: 18 }];
worksheet['!rows'] = [{ hpt: 24 }];
```

### 31.4.4 最佳实践

- 样式需求先做能力确认：只需要列宽/行高/数字格式，SheetJS 够用；要颜色边框就换库
- 大文件入口设三道闸：文件字节上限、`sheetRows` 预览上限、导入总行数上限
- Worker 里完成「解析 + 归一化 + 校验」，主线程只收结果，避免二次遍历
- 解析完主动释放引用（置空 workbook、关闭 Worker），SPA 长驻页面尤其重要
- 浏览器下载统一封装成 `downloadBlob`，内部负责创建与延迟回收 URL

能保留数字格式 `z`、列宽 `!cols`、行高 `!rows` 等结构信息；字体、颜色、边框、填充、对齐等单元格样式写在 `cell.s` 里也会在写出时被忽略。需要完整样式就改用 ExcelJS 或服务端模板。

`WorkBook` 是深层嵌套的普通对象，`postMessage` 需要结构化克隆全部单元格与元信息，克隆耗时和内存峰值都可能超过解析。协议应只回传业务需要的最小结果，例如 `{ rows, issues, sheetNames }`，最好用 transferable 的 TypedArray 或纯数组；进度用独立的小消息汇报，不要中途回传半成品工作簿。

## 31.5 实战

### 31.5.1 概念解析

**模板导出**的流程是「读模板 → 改单元格 → 写回」。模板里的合并、列宽、数字格式可以保留，但社区版会丢掉字体颜色等样式；因此「模板保真」是选型问题，不是 API 问题。改单元格时直接赋值 `{ t, v }` 比改 `w` 可靠，日期用 Date 或文本要统一。

**导入校验**要把「归一化」和「业务规则」分开：`normalizeCellValue` 负责空值、日期、数字与空白，`validateRows` 负责必填、类型、长度、范围、正则与自定义规则。错误信息带 Excel 行号（表头是第 1 行），用户才能定位。

**安全**有两类。第一类是公式注入：CSV 没有类型，用户写的 `=HYPERLINK(...)`、`+cmd`、`@SUM(...)` 会被 Excel 当公式执行，导出时必须前置单引号或强制文本。第二类是资源耗尽：xlsx 是 ZIP，几 MB 的压缩包可以解压出几 GB XML，必须在解压前限制文件大小，解压后限制行数与列数，别把 `!ref` 当真实范围。

### 31.5.2 典型应用场景

- 月度报表模板：固定表头与合并区域，只替换数据区
- 批量导入员工/商品：校验手机号、金额、枚举值，返回逐行错误
- 对外导出 CSV：用户输入不可信，需中和公式并限制体积

### 31.5.3 可运行代码示例

### 31.5.4 最佳实践

- 模板导出前先确认「样式是否属于验收标准」，是就选 ExcelJS，不要事后返工
- 校验规则集中声明，前端与后端共用同一份字段规则，错误码与行号保持一致
- 导出 CSV 默认 `sanitizeFormulas: true`；确需保留公式时在受控白名单内显式关闭
- 上传入口同时检查扩展名、MIME、字节数、行数与列数，任何一项超限都拒绝
- 对 `!ref` 保持怀疑：真实行数以解析结果为准，空行在入库前过滤

<details>
<summary><b>13. 【基础】模板导出的标准三步是什么？社区版在哪一步会丢样式？</b></summary>

读取模板、修改目标单元格、写出新文件。社区版在写出阶段丢弃字体、颜色、边框等 `cell.s` 样式；读取阶段可以带 `cellStyles`，但写不回去。合并、列宽、行高与数字格式通常可以保留。

<details>
<summary><b>14. 【进阶】为什么要把归一化与业务校验分成两个函数？错误行号如何计算？</b></summary>

归一化处理「值的形态」（空字符串、无效日期、NaN、空白），业务校验处理「值是否合法」（必填、范围、正则）。分开后规则可复用、可测试，错误也能精确归因。行号按 Excel 视角计算：表头第 1 行，数据第一条是第 2 行，所以索引加 2。
</details>

<details>
<summary><b>15. 【挑战】一个 3 MB 的 xlsx 解压后可能有多大？上传入口应设置哪些防线？</b></summary>

ZIP 高压缩比下，3 MB 可能膨胀到数百 MB 甚至 GB 级 XML。防线包括：压缩包字节上限、解压后总大小上限（服务端检查 ZIP 条目）、工作表数与行列数上限、解析行数上限，以及在 Worker/独立进程中解析并设置超时。浏览器端还可先用 `bookSheets` 只读表名做快速拒绝。
</details>

### 实战案例：模板文件回填导出

财务每月下发一份固定的「渠道对账」模板：标题行、合并表头、预设数字格式的样例行一应俱全，运营只需要在数据区追加行。与其让人手工复制粘贴，不如读入模板后自动定位表头行、克隆样例行的数字格式并逐行回填。注意社区版「读入再写出」能保住合并、列宽与数字格式，字体颜色必然丢失，样式保真属于选型问题而非代码问题。

```ts
import * as XLSX from 'xlsx';
import { workbookToBuffer } from './src/index.js';

function fillReconcileTemplate(bytes: ArrayBuffer, rows: readonly Record<string, unknown>[]): Uint8Array {
    const workbook = XLSX.read(bytes, { type: 'array', cellDates: true });
    const worksheet = workbook.Sheets['渠道对账'];
    if (worksheet === undefined) throw new Error('模板缺少「渠道对账」工作表');
    const ref = worksheet['!ref'];
    if (ref === undefined) throw new Error('模板数据区为空');
    const matrix = XLSX.utils.sheet_to_json<unknown[]>(worksheet, { header: 1, defval: null });
    const headerIndex = matrix.findIndex((line) => line?.includes('渠道'));
    if (headerIndex < 0) throw new Error('未找到含「渠道」的表头行');
    const cols = ['日期', '渠道', '金额'].map((field) => {
        const c = (matrix[headerIndex] ?? []).indexOf(field);
        if (c < 0) throw new Error(`模板缺少「${field}」列`);
        return { field, c, z: worksheet[XLSX.utils.encode_cell({ r: headerIndex + 1, c })]?.z };
    });
    rows.forEach((row, index) => {
        cols.forEach(({ field, c, z }) => {
            const value = row[field];
            const cell: XLSX.CellObject = typeof value === 'number'
                ? { t: 'n', v: value, z }
                : { t: 's', v: String(value ?? '') };
            worksheet[XLSX.utils.encode_cell({ r: headerIndex + 1 + index, c })] = cell;
        });
    });
    const range = XLSX.utils.decode_range(ref);
    range.e.r = Math.max(range.e.r, headerIndex + rows.length);
    worksheet['!ref'] = XLSX.utils.encode_range(range);
    return workbookToBuffer(workbook);
}
```

实现要点与取舍：

- 直接用 `json_to_sheet` 新建工作表替换模板表，`!cols`、`!merges` 与数字格式会整体清零——格式挂在「工作表对象」上而不在数据里，必须读入模板后就地写单元格
- 探测表头用 `header: 1` 加 `includes`，不要假定表头固定在第 1 行，财务模板常见大标题行与两行合并表头
- 踩坑：给超出 `!ref` 的地址赋值不会落盘，数据区扩展后必须扩大 `range.e.r` 并把 `encode_range` 的结果写回 `!ref`，否则最后几行在文件里凭空消失
- 从样例行克隆的是数字格式 `z`，这是社区版唯一能写回的「格式」；模板若要求品牌色与边框，本方案不成立，换 ExcelJS 打开模板

### 实战案例：表头别名容错的导入映射

同一张「渠道回款表」，微信渠道导出的表头叫「金额（元）」，支付宝叫「Amount」，内部系统叫「金额」。导入功能不能要求用户先改表头，正确姿势是用一张别名映射表把各种叫法归一化成业务字段，再按映射到的下标取值。缺列时错误信息要直接点名缺的是哪个字段、接受哪些写法，用户才知道怎么改。

```ts
import * as XLSX from 'xlsx';

const ALIASES = {
    渠道: ['渠道', 'Channel'],
    金额: ['金额', '金额（元）', '金额(元)', 'Amount'],
    回款日: ['回款日', '回款日期', 'Date'],
} satisfies Record<string, readonly string[]>;

type Field = keyof typeof ALIASES;

function readPaymentRows(bytes: ArrayBuffer): Record<Field, unknown>[] {
    const workbook = XLSX.read(bytes, { type: 'array', cellDates: true });
    const worksheet = workbook.Sheets[workbook.SheetNames[0] ?? ''];
    if (worksheet === undefined) throw new Error('空工作簿');
    const matrix = XLSX.utils.sheet_to_json<unknown[]>(worksheet, { header: 1, defval: null });
    const header = (matrix[0] ?? []).map((name) => String(name).trim());
    const columnOf = {} as Record<Field, number>;
    (Object.keys(ALIASES) as Field[]).forEach((field) => {
        const index = header.findIndex((name) => ALIASES[field].includes(name));
        if (index < 0) throw new Error(`缺少必填列「${field}」，表头可以是：${ALIASES[field].join(' / ')}`);
        columnOf[field] = index;
    });
    return matrix.slice(1).map((line) => {
        const row = {} as Record<Field, unknown>;
        (Object.keys(columnOf) as Field[]).forEach((field) => {
            row[field] = line?.[columnOf[field]] ?? null;
        });
        return row;
    });
}
```

实现要点与取舍：

- 踩坑：按列下标（`line[3]`）硬编码映射，用户在中间插一列「备注」后整表错位且无任何报错；列的锚点永远是表头名，不是位置
- 归一化只做「`trim` 加别名精确匹配」，不上模糊匹配；`findIndex` 命中即停，同一张表同时出现「金额」和「Amount」时取靠前者，更严格的做法是导入前增加一条重复列告警
- 错误信息同时给出字段名与全部可接受写法，用户不用翻文档；把别名表做成后端下发的配置，新增渠道不用发版
- 表头还可能有全角/半角括号、不可见空白，`trim` 之后再对不上，再考虑全半角归一化，不要一上来就正则

### 实战案例：多 Sheet 对账合并

第三方对账文件常按渠道分 Sheet：「微信」「支付宝」「抖音」各一页，列名一致、行数不同。导入后要合并成总表，再按订单号聚合，与自家流水核对差异数，差异订单回显到错误面板。聚合本身用原生 `reduce` 加 `Map` 就够，不必为了一处聚合引入 lodash。

```ts
import * as XLSX from 'xlsx';

type PaymentRow = { channel: string; orderId: string; amount: number };

function readChannelSheet(worksheet: XLSX.WorkSheet, channel: string): PaymentRow[] {
    return XLSX.utils.sheet_to_json<Record<string, unknown>>(worksheet, { defval: null })
        .map((raw) => ({
            channel,
            orderId: String(raw['订单号'] ?? '').trim(),
            amount: Number(raw['金额'] ?? 0),
        }))
        .filter((row) => row.orderId !== '');
}

function reconcile(bytes: ArrayBuffer, ours: ReadonlyMap<string, number>): { total: number; diffOrders: string[] } {
    const workbook = XLSX.read(bytes, { type: 'array', cellDates: true });
    const names = new Set(workbook.SheetNames);
    const rows = ['微信', '支付宝', '抖音'].filter((name) => names.has(name))
        .flatMap((name) => {
            const worksheet = workbook.Sheets[name];
            return worksheet === undefined ? [] : readChannelSheet(worksheet, name);
        });
    if (rows.length === 0) throw new Error('对账文件没有可用的数据行');
    const theirs = rows.reduce<Map<string, number>>((acc, row) => {
        acc.set(row.orderId, (acc.get(row.orderId) ?? 0) + row.amount);
        return acc;
    }, new Map());
    const diffOrders = [...theirs]
        .filter(([orderId, amount]) => Math.abs((ours.get(orderId) ?? 0) - amount) > 0.001)
        .map(([orderId]) => orderId);
    return { total: rows.length, diffOrders };
}
```

实现要点与取舍：

- 按 Sheet 名白名单读取，别默认吞掉全部工作表——对账文件常混有「说明」「封签」页；渠道名直接取 Sheet 名，总表才有维度可查
- 金额比较用误差阈值 `0.001` 而不是 `===`，分摊与浮点累加会出现 0.1 级偏差，等值比较必然误报
- 踩坑：`!ref` 尾部的空行会产出 `orderId` 为空串的脏行，聚合前必须过滤，否则差异数虚高；`sheet_to_json` 默认跳过全空行，但「只有格式没有值」的行不会跳
- `Number(raw['金额'])` 对「1,280.00」这类带千分位的文本会得到 NaN，真实项目这一步应交给实验室的 `normalizeCellValue` 归一化，示例刻意保持最小
- 数据量大时把这段合并搬进 Worker，主线程只收 `{ total, diffOrders }`，消息协议设计见 31.4

### 实战案例：导出前脱敏与权限裁剪

运营、财务、客服都有「导出」按钮，但客服不该带走完整手机号，谁都不该带走内部成本列。导出是数据出境的最后一道闸，列的取舍必须由「角色 → 列白名单」决定，而不是「界面上显示什么就导什么」。脱敏要在生成单元格之前完成，让原始值根本没有进入工作簿的机会。

```ts
import { type CellValue, exportRowsToWorkbook, workbookToBuffer } from './src/index.js';

type Role = 'agent' | 'finance';

const COLUMN_WHITELIST: Record<Role, readonly string[]> = {
    agent: ['姓名', '手机号', '成交金额'],
    finance: ['姓名', '手机号', '成交金额', '成本', '毛利'],
};

function maskPhone(phone: string): string {
    if (!/^1\d{10}$/.test(phone)) return '***';
    return phone.replace(/^(\d{3})\d{4}(\d{4})$/, '$1****$2');
}

function exportForRole(role: Role, rows: readonly Record<string, unknown>[]): Uint8Array {
    const columns = COLUMN_WHITELIST[role];
    const scoped = rows.map((row) => {
        const picked: Record<string, CellValue> = {};
        columns.forEach((column) => {
            const raw = row[column] as CellValue;
            picked[column] = column === '手机号' && typeof raw === 'string' ? maskPhone(raw) : (raw ?? null);
        });
        return picked;
    });
    return workbookToBuffer(exportRowsToWorkbook([{ name: '客户', columns, rows: scoped }]));
}
```

实现要点与取舍：

- 白名单按角色集中声明，导出函数只认白名单；「界面隐藏了成本列、导出却全量带出」是最典型的越权路径，截图看不见的字段在 xlsx 里全都看得到
- 踩坑：把全量 rows 直接交给导出器、以为传了 `columns` 就万事大吉——`json_to_sheet` 会把首行对象的所有键写成列，多余字段静默泄出；必须先 map 成白名单对象，让导出器只见到裁剪后的数据
- 脱敏发生在写单元格之前，比「导出后再删列」可靠，删除逻辑漏掉一列就是事故；成本、毛利这类列干脆不进白名单，值根本不参与生成
- 打码要有边界：非 11 位手机号（座机、带国际区号）若原样返回，打码形同虚设，本例统一退化为 `***`
- 前端裁剪只防「顺手导出」，防恶意导出要靠服务端限流、水印与导出审计，别把前端当安全边界

### 实战案例：分批读取超大 CSV

历史订单归档是几十万行的 CSV，产品要求「打开即预览、导入有进度条」。一次性 `XLSX.read` 加整表 `sheet_to_json` 会让主线程阻塞数秒、内存峰值翻倍，可行折中是：解析成工作表后按行区间分段转换，配合进度回调并在段间让出事件循环。预览与全量导入走同一条链路，只读前几段就是预览。

```ts
import * as XLSX from 'xlsx';

const CHUNK_ROWS = 5000;

export async function readLargeCsv(bytes: ArrayBuffer, onProgress?: (percent: number) => void): Promise<Record<string, unknown>[]> {
    const workbook = XLSX.read(bytes, { type: 'array', dense: true, cellDates: true });
    const worksheet = workbook.Sheets[workbook.SheetNames[0] ?? ''];
    if (worksheet === undefined) throw new Error('空工作簿');
    const ref = worksheet['!ref'];
    if (ref === undefined) return [];
    const end = XLSX.utils.decode_range(ref).e.r;
    const headRow = XLSX.utils.sheet_to_json<unknown[]>(worksheet, {
        range: XLSX.utils.encode_range({ r: 0, c: 0 }, { r: 0, c: 9 }),
        header: 1,
    })[0] ?? [];
    const headerNames = headRow.map((name) => String(name));
    const rows: Record<string, unknown>[] = [];
    for (let start = 1; start <= end; start += CHUNK_ROWS) {
        const stop = Math.min(start + CHUNK_ROWS - 1, end);
        const chunk = XLSX.utils.sheet_to_json<Record<string, unknown>>(worksheet, {
            range: XLSX.utils.encode_range({ r: start, c: 0 }, { r: stop, c: 9 }),
            header: headerNames,
            defval: null,
        });
        rows.push(...chunk);
        onProgress?.(Math.round((stop / end) * 100));
        await new Promise((resolve) => setTimeout(resolve, 0)); // 让出事件循环，进度条才有机会重绘
    }
    return rows;
}
```

实现要点与取舍：

- 内存峰值的大头在 `XLSX.read` 一次性解析，分段 `range` 压低的是「转行对象」阶段的峰值与 GC 压力；要根治内存得换服务端流式解析，本方案解决的是主线程长阻塞与进度不可见
- 踩坑：分段时不显式传 `header` 数组，`sheet_to_json` 会把每段第一行当表头，第二段开始键名整段错乱；先用首行取表头，再让每段都按同一套列名映射
- 段间 `setTimeout(0)` 让出事件循环，进度回调才有机会触发重绘；搬进 Worker 时把回调换成 `postMessage` 汇报，其余逻辑不变
- 列上限（示例 10 列）与段大小要一起定：段越大单次转换越久，进度颗粒度越粗；`range` 的列越界没有副作用
- 返回的 `rows` 在导入完成前全量驻留，别再复制一份做校验，校验应该流过一段算一段

### 进阶技巧：区间操作三件套与 !ref 重算

任意矩形区域的遍历与修改都靠 `decode_range`、`encode_cell`、`encode_range` 这组互逆操作，比如给全表数字列统一补上千分位格式：

```ts
import * as XLSX from 'xlsx';
const worksheet = XLSX.utils.aoa_to_sheet([['指标', '数值'], ['GMV', 128000]]);
const ref = worksheet['!ref'];
if (ref !== undefined) {
    const range = XLSX.utils.decode_range(ref);
    for (let r = range.s.r; r <= range.e.r; r++) {
        for (let c = range.s.c; c <= range.e.c; c++) {
            const cell = worksheet[XLSX.utils.encode_cell({ r, c })];
            if (cell !== undefined && cell.t === 'n') cell.z = '#,##0.00';
        }
    }
}
```

要点：

- `decode_range` 把 `!ref` 拆成零基起止坐标，`encode_cell`/`encode_range` 反向拼回地址，清值、补格式、扫描异常值都靠这组三件套
- 踩坑：给超出 `!ref` 的地址赋值不会落盘——格子确实挂在工作表对象上，但写出时按范围裁掉；新增行列后必须扩大 `range.e.r`/`range.e.c`，把 `encode_range` 的结果写回 `!ref`
- 社区版写不出边框颜色，「给汇总行加边框」做不到时退而求其次：用 `【合计】` 文本前缀做视觉标记、用能写回的数字格式 `z`，或改由 ExcelJS/服务端模板交付样式
- 稀疏表遍历先判格子存在再读 `t`，`worksheet['B2']` 完全可能是 `undefined`
- 逐格 `encode_cell` 有字符串拼接开销，十万格级别放 Worker 或低频时机执行，别在渲染路径里做

### 进阶技巧：sheet_add_aoa 追加汇总行

给已生成的报表追加汇总行，用 `sheet_add_aoa` 配 `origin: -1` 定位到「当前 `!ref` 末行的下一行」，不必手算行号：

```ts
import * as XLSX from 'xlsx';
const worksheet = XLSX.utils.aoa_to_sheet([['城市', '销售额'], ['杭州', 128000], ['上海', 256000]]);
XLSX.utils.sheet_add_aoa(worksheet, [['合计', 384000]], { origin: -1 });
console.log(worksheet['!ref']); // A1:B4，sheet_add_aoa 已把新行并入范围
```

要点：

- `origin: -1` 相对追加比手算 `'A' + (rows.length + 2)` 抗表头与标题行变动；`origin` 也接受 `'A5'` 字符串与 `{ r, c }` 对象，绝对定位会覆盖既有格子，慎用
- `sheet_add_aoa` 收尾会重算 `!ref`（旧范围与本次写入求并集），不用手工扩展；但用绝对 `origin` 跳行追加时，中间空行也会并进 `!ref`，下游遍历前记得过滤空行
- 值为 `undefined` 的格子直接跳过不落地；想让 `null` 落成占位空格需要 `sheetStubs: true`，否则同样跳过
- 汇总数值在 JS 里算好随 `v` 写入；想带公式就要同时给 `f` 与缓存值，理由见 31.3 的公式小节
- 追加行不会继承上方行的数字格式，金额合计记得显式给 `z`（如 `'#,##0.00'`）

### 进阶技巧：dense 模式与内存

`dense: true` 让解析器把工作表从「地址 → 单元格」的稀疏对象换成按行存储的数组结构，大文件下的解析速度与内存占用都有可观改善，但行为差异要先知道：

```ts
import * as XLSX from 'xlsx';
const workbook = XLSX.read(buffer, { type: 'array', dense: true, cellDates: true });
const worksheet = workbook.Sheets[workbook.SheetNames[0] ?? ''];
if (worksheet === undefined) throw new Error('空工作簿');
const rows = XLSX.utils.sheet_to_json<Record<string, unknown>>(worksheet, { defval: null });
console.log(Array.isArray(worksheet)); // true：dense 表按行存储，worksheet['B2'] 取不到值
```

要点：

- 收益集中在「解析大文件后整体转行」这一段；读出来还要逐格按地址修改的场景（模板回填、区间操作）不要开 dense，地址访问会全部失效
- 踩坑：dense 模式下 `worksheet['B2']` 返回 `undefined`，逐格代码要么改走 `sheet_to_json`/`sheet_to_csv` 等官方工具，要么保持默认稀疏模式，别混用两套访问方式
- dense 只在读取方向收益最大；写方向的 utils 仍生成稀疏表，导出侧的内存优化要靠分批构造 AoA 或改走 CSV 流
- `dense` 的内部结构在 0.18 与后续版本间有差异，锁定版本使用，并通过工具函数访问，不直接依赖内部行数组

## 31.6 综合自测题

<details>
<summary><b>16. 【进阶】请描述一条从「用户上传 xlsx」到「入库」的完整安全链路？</b></summary>

校验扩展名与 MIME → 限制字节数 → 在 Worker 中解析（`dense`、`sheetRows` 上限）→ 只取需要的 Sheet → `bufferToRows` 转对象数组 → `normalizeCellValue` 归一化 → `validateRows` 校验并收集行号 → 过滤空行、限制总行数 → 业务层二次校验 → 入库。全程不信任 `!ref`、不执行公式、不把工作簿对象传入领域层。
</details>

<details>
<summary><b>17. 【进阶】同一份数据分别导出 xlsx 与 CSV，为什么 CSV 更需要防公式注入？</b></summary>

xlsx 可以显式把单元格写成 `t: 's'` 文本，Excel 不会把它当公式；CSV 没有类型信息，所有字段都是文本，Excel 打开时会重新识别以 `= + - @` 开头的内容并求值。因此 CSV 导出必须前置单引号或强制引号包裹，且不能只依赖前端预览。
</details>

<details>
<summary><b>18. 【挑战】产品要求「10 万行导出不卡顿、还能显示进度」，给出前端架构方案与失败降级？</b></summary>

方案：主线程只负责收集数据与调度；用 Worker 分批构造 AoA 并写入工作簿（或分批生成 CSV），通过小消息汇报进度；最终把 `ArrayBuffer` 移交主线程生成 Blob 下载。失败降级：超过阈值改为服务端异步导出（任务 ID + 轮询/通知），或先导出 CSV 流。要点是不要让 `WorkBook` 在主线程反复扩容，也不要把全部数据一次性结构化克隆给 Worker。
</details>

<details>
<summary><b>19. 【挑战】团队要统一表格技术栈，你会用哪些问题快速判断选 SheetJS 还是 ExcelJS？</b></summary>

四问：是否需要保留或生成完整样式（颜色、边框、图片、条件格式）？是否需要读取超大文件并流式处理？是否需要多种格式（xls/ods）与成熟的解析容错？团队能否接受两套 API 与包体成本？样式优先选 ExcelJS，通用导入导出与格式覆盖优先 SheetJS；两者都不擅长公式计算，复杂计算放服务端。
</details>

## 31.7 本章避坑清单

| 坑 | 后果 | 避法 |
| --- | --- | --- |
| 用 `json_to_sheet` 直接写异构对象 | 第一行之后的字段静默丢失 | 先并集列或显式传 `columns` |
| 读写两端漏传 `cellDates` | 日期变成 45xxx 序列号 | 读写统一 `cellDates: true` |
| 用 `toISOString` 写日期 | 东八区时间少 8 小时 | 用本地墙上时间或格式化文本 |
| 改模板后直接另存 | 品牌色、边框消失 | 样式保真场景改用 ExcelJS/服务端模板 |
| 合并区域每个格都赋值 | 打开只剩左上角，误判数据丢失 | 只写左上角并登记 `!merges` |
| 公式只写 `f` 不写 `v` | 预览空白，下游读到空值 | 同时写缓存值，或服务端先计算 |
| 指望 SheetJS 计算公式 | 值永远不更新 | 计算放服务端或让 Excel 打开重算 |
| CSV 不写 BOM | Excel 中文乱码 | 开头写 `\uFEFF` |
| 直接导出用户输入到 CSV | 公式注入，可能触发外链或命令 | 前置单引号，默认 `sanitizeFormulas` |
| 主线程直接 `read` 大文件 | 页面冻结甚至 OOM | 限制大小 + Worker + `sheetRows`/`dense` |
| 把 `!ref` 当真实行数 | 空行撑爆循环与入库 | 以解析结果为准，过滤空行并设行数上限 |
| 工作表名超 31 字符或含 `[]:*?/\` | 写入报错或被截断 | 命名前校验并统一生成规则 |
| 信任上传的 xlsx 体积 | ZIP 炸弹耗尽内存 | 限制压缩包与解压后大小、行列数、超时 |
