> 表单引擎的本质是**把表单从代码变成数据**：一张表单不再是一个个手写的 `<el-form-item>`，而是一份可序列化的 JSON。渲染器、校验器、联动引擎都是这套数据的「解释器」。设计的关键取舍只有一个：**Schema 表达力封顶在哪**——表达力太弱覆盖不了业务，太强就变成了图灵完全的脚本语言，低代码退化回「代码」，平台化价值归零。

## 38.1 表单 Schema：一份 JSON 描述一张表单

### 38.1.1 概念解析

Schema 是整个引擎的契约，字段级结构覆盖四类信息：

| 信息 | 字段 | 说明 |
| --- | --- | --- |
| 身份 | `key / type / label` | key 全表单唯一，是提交字段名 |
| 数据 | `defaultValue / options` | 初始值与枚举选项 |
| 规则 | `required / rules` | 校验规则（38.4） |
| 联动 | `visibleWhen / disabledWhen` | 结构化条件（38.3） |

第一道关卡是 **Schema 自检**：非法 Schema（key 重复、select 无 options、联动引用不存在的字段）必须在**装载时**报错，而不是渲染到一半崩掉。低代码平台把「配置错误」从运行时事故变成构建期问题，靠的就是这道自检。

### 38.1.2 核心代码

```ts
// 文件: examples/38-01-form-schema.ts
export interface FieldSchema {
    key: string;              // 提交时的字段名（全表单唯一）
    type: FieldType;
    label: string;
    required?: boolean;
    defaultValue?: unknown;
    options?: FieldOption[];  // select 专用
    rules?: FieldRule[];
    visibleWhen?: Condition;  // 不满足则整枝（连值一起剔除）
    disabledWhen?: Condition; // 可见但不可编辑
    colSpan?: 1 | 2;          // 布局
}

/** Schema 自检：构建期拦住非法配置。返回错误列表，空数组 = 合法 */
export function validateSchema(schema: FormSchema): string[];
```

> 运行方式：`npx tsx examples/38-01-form-schema.ts`。

### 38.1.3 应用实践

- **Schema 要带版本号**：`schemaVersion` 进 JSON，草稿恢复、灰度发布、回滚都靠它（38.5 演示旧版本草稿自动作废）。
- **key 命名跟后端字段对齐**：Schema 的 key 就是提交体字段名，命名歧义在 Schema 层解决，别留给提交管道做映射。
- **一张业务表单的 JSON 应在 1KB 量级**：超了说明该拆子表单或该把枚举抽成字典接口。

## 38.2 渲染器：Schema → 组件树

### 38.2.1 概念解析

渲染器是「Schema 解释器」，三个职责对应三段代码：

1. **类型映射**：`type → 组件`，查一张**组件注册表**。新增字段类型 = 注册一个组件，渲染器零改动——这是开闭原则在表单引擎里的落点；
2. **联动求值**：`visibleWhen/disabledWhen` 对当前值求值，产出节点的 visible/disabled 标记；
3. **属性注入**：label/placeholder/值/options 全部注入节点 props。

渲染产物对应 Vue/React 侧一段固定模板：

```html
<component :is="node.component" v-show="node.visible" :disabled="node.disabled" v-bind="node.props" />
```

框架差异被压缩到这一个模板里，引擎逻辑全部框架无关——这也是手写框架（第 27 册）讲过的 VNode 思想：**渲染 = 数据到数据**。

### 38.2.2 核心代码

```ts
// 文件: examples/38-02-form-renderer.ts
/** 组件注册表：新增字段类型 = 注册一个组件，渲染器零改动 */
export const componentRegistry: Record<string, string>;

export function renderForm(schema: FormSchema, values: Record<string, unknown>): RenderNode[];
/** 值收集：带 defaultValue 的字段自动初始化 */
export function initValues(schema: FormSchema, preset?: Record<string, unknown>): Record<string, unknown>;
```

> 运行方式：`npx tsx examples/38-02-form-renderer.ts`（import 了 38-01，属跨文件示例）。

### 38.2.3 应用实践

- **visible=false 的节点仍产出**：让框架层决定怎么渲染（v-if/v-show），渲染器不做 DOM 决策；但**值收集必须剔除不可见字段**（38.5 双保险）。
- **注册表支持业务自定义组件**：引擎只带通用字段，业务专属组件（如「部门选择器」）走注册表注入，引擎代码不分支。
- **渲染器不校验**：校验独立成引擎（38.4），渲染器只管「长什么样」——职责单一才能被不同业务复用。

## 38.3 联动引擎：显隐 / 禁用 / 值联动

### 38.3.1 概念解析

三种联动，复杂度递增：

1. **显隐联动**（visibleWhen）：字段出不出现。语义必须是「整枝」——字段不可见时**值一并剔除**，否则提交体里混着用户看不见的值，成为脏数据头号来源；
2. **状态联动**（disabledWhen）：字段在但不可编辑（如审批人不可改金额）；
3. **值联动**（effects）：字段变化派生其他字段值（里程 × 单价 → 金额）。

联动的头号工程陷阱是**环**：A 派生 B、B 又派生 A，无防护时无限震荡。解法是**单向流 + 变更收敛**：维护「本轮已处理」集合，同源同目标的联动只执行一次；整体最多收敛 N 轮（N = 字段数），超限即认定配置成环，抛错给 Schema 自检。

### 38.3.2 核心代码

```ts
// 文件: examples/38-03-form-linkage.ts
export interface EffectRule {
    watch: string;                       // 触发源字段
    when: Condition;
    effect:
        | { type: "clear"; target: string }
        | { type: "derive"; target: string; compute: (v: unknown, all: Record<string, unknown>) => unknown };
}

export function resolveLinkage(schema, effects, rawValues):
    { visible: Set<string>; values: Record<string, unknown>; touched: string[] };
```

> 运行方式：`npx tsx examples/38-03-form-linkage.ts`。

### 38.3.3 应用实践

- **联动轨迹要可观测**：`touched` 记录每一步「谁清了谁、谁派生了谁」，排查「为什么金额自己变了」全靠它。
- **derive 必须幂等**：同一输入派生同一输出，收敛判定依赖这个性质。
- **禁止在联动里发请求**：联动是纯计算，副作用（级联下拉的 options 拉取）用「字段值变化 → 触发 action」的事件机制，与联动引擎分离。

## 38.4 校验引擎：内置规则与自定义注册表

### 38.4.1 概念解析

校验引擎消费 `required + rules`，产出 `字段 → 错误消息[]` 的聚合结果。两条设计规矩：

1. **custom 规则走注册表**：Schema 是 JSON，函数没法序列化——Schema 里只存规则 id（`"value": "phone-cn"`），函数在注册表里。注册表查不到的 id 按**失败**处理（默认拒绝原则，与 37.3 的策略 DSL 一脉相承）；
2. **聚合而非短路**：提交场景一次报出所有错误；实时反馈场景复用同一个 `validateField`，全量与单字段是同一实现的两粒度调用，不会出现「实时校验和提交校验结论不一致」。

一个容易被忽略的细节：**不可见字段跳过校验**——用户没机会填的字段不参与必检，否则「隐藏字段的必填错误」永远消不掉，表单卡死在提交前。

### 38.4.2 核心代码

```ts
// 文件: examples/38-04-form-validation.ts
/** custom 规则注册表：规则 id → 判定函数（Schema JSON 里只存 id） */
export const customValidators: Record<string, (v: unknown, all: Record<string, unknown>) => boolean>;

/** 校验单个字段（实时反馈复用） */
export function validateField(field, value, all): string[];
/** 全量校验：跳过不可见字段 */
export function validateForm(schema: FormSchema, values: Record<string, unknown>): ValidateErrors;
```

> 运行方式：`npx tsx examples/38-04-form-validation.ts`。

### 38.4.3 应用实践

- **复杂结构校验接 Zod**（第 33 册）：字段级规则管「单格」，整表结构（数组长度、联合类型）用 Zod schema 收口，Zod 的错误树映射回字段 key。
- **错误消息进 Schema 不进组件**：文案跟规则走，组件只渲染 `errors[key]`，多语言改造时只动 Schema。
- **服务端校验是最终裁决**：前端校验全部可被绕过（第 36/37 册的防越权原则），后端必须用同一套规则重放校验。

## 38.5 提交管道：裁剪 → 校验 → 脏检查 → 草稿

### 38.5.1 概念解析

Schema 表单的提交是一条固定管道，每步都是纯函数：

1. **裁剪**：不可见字段从提交体剔除（联动引擎已清值，此处双保险）；
2. **校验**：全量值参与（联动条件依赖完整上下文），有错终止并聚焦第一个错误字段；
3. **脏检查**：与初始快照 `JSON.stringify` 对比，产出增量 patch——编辑场景只提交变更字段，并发冲突面更小；
4. **草稿恢复**：localStorage 快照带 `schemaVersion`，版本不一致即作废——Schema 改版后旧草稿里的字段结构对不上，强行恢复是「半新半旧」脏数据。

### 38.5.2 核心代码

```ts
// 文件: examples/38-05-form-submit.ts
export function pruneInvisible(schema, values): Record<string, unknown>;
export function diffValues(initial, current): Record<string, unknown>;   // 增量 patch
export function saveDraft(schemaVersion, formName, values): void;
export function loadDraft(schemaVersion, formName): { ok: true; values } | { ok: false; reason: "none" | "stale" };

export function submitForm(schema, initial, current, mode: "full" | "patch"): SubmitResult;
```

> 运行方式：`npx tsx examples/38-05-form-submit.ts`。

### 38.5.3 应用实践

- **草稿节流**：输入事件 500ms 防抖后存草稿，`beforeunload` 兜底再存一次。
- **patch 模式要后端配合**：增量提交要求后端支持部分更新语义（只改 patch 里的字段），全量/增量模式由业务定，引擎两个都给。
- **提交成功即清草稿**：残留草稿会在下次打开时盖掉新数据。

## 38.6 物料协议与平台化

### 38.6.1 从表单引擎到低代码平台

表单引擎只是第一块拼图。平台化还需要三套协议：

| 协议 | 回答的问题 | 本章对应物 |
| --- | --- | --- |
| 物料协议 | 一个字段组件怎么被平台识别（属性面板、事件、插槽） | componentRegistry + FieldSchema |
| 数据源协议 | options/默认值怎么从接口拉取、怎么缓存 | 联动引擎外的 action 机制 |
| 页面协议 | 表单块怎么嵌进页面（与表格、图表编排） | FormSchema 的容器化扩展 |

### 38.6.2 平台化的三条红线

1. **逃生舱必须有**：任何 Schema 都覆盖不了的场景（花式联动、动态 options），提供「自定义代码块」出口，否则业务被迫绕路，平台变成阻力；
2. **Schema 变更可回滚**：版本号 + 变更审计，发布出错一键回退上一版；
3. **别追求 100% 低代码**：80% 场景用 Schema、20% 场景写代码是健康状态；追求全覆盖的最后都做成了难用的 IDE。

## 38.7 自测题

1. 为什么「字段不可见时必须清值 + 提交剔除」要双保险？只做其中一处会出什么问题？

<details><summary>查看答案</summary>

只清值不剔除：提交体里出现值为 null 的不可见字段，后端可能把 null 当合法值覆盖已有数据。只剔除不清值：字段隐藏期间旧值仍留在表单状态里，重新显示时「幽灵旧值」复活（用户以为重填了实际是旧值）。两处都做：值状态干净 + 提交体干净。
</details>

2. 联动引擎的防环为什么用「已处理集合」而不是限制执行次数？

<details><summary>查看答案</summary>

限制次数（如最多跑 10 轮）只是延迟爆炸：环大一点（5 字段互派）时 10 轮内可能仍在震荡，输出不稳定且不可复现。已处理集合从语义上保证「同源同目标只派生一次」，结果确定性可复现；配合轮数上限作为兜底（超限 = 配置成环，应报错而非默默收敛）。
</details>

3. custom 校验规则为什么走注册表（Schema 存 id）而不是把函数序列化进 Schema？

<details><summary>查看答案</summary>

函数无法安全序列化：存字符串源码再 eval 回来，等于让配置数据获得任意代码执行能力——谁能写 Schema 谁就能在所有打开表单的用户浏览器里执行代码（XSS 级漏洞）。注册表模式下 Schema 只是数据，函数在受代码评审管控的注册表里，攻击面消失。
</details>

4. 全量校验和实时校验为什么要复用同一个 validateField？

<details><summary>查看答案</summary>

两套实现必然漂移：实时说合法、提交时报错（或反之），用户困惑且信任崩塌。同一实现两粒度调用（全量 = 对每个可见字段调 validateField），规则改动一处生效，「实时结论」与「提交结论」天然一致。
</details>

5. 草稿恢复为什么必须校验 schemaVersion？直接恢复旧草稿会发生什么？

<details><summary>查看答案</summary>

Schema 改版后字段结构可能变化（key 改名、字段删除、类型变更），旧草稿的值集与新 Schema 对不上：恢复出「半新半旧」的数据，轻则字段错位，重则把已废弃字段提交给后端。版本不一致即作废（或做显式迁移），保证草稿永远与当前 Schema 同构。
</details>

## 38.8 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 非法 Schema 直接进渲染器 | 渲染中途崩，用户看到半张表单 | 装载期 validateSchema 自检，错误列表直接暴露 |
| 字段 key 不唯一 | 提交体字段互相覆盖，数据静默丢失 | 自检强制 key 唯一，重复即拒绝装载 |
| 新字段类型改渲染器 if-else | 引擎膨胀，业务组件无法接入 | 组件注册表，注册即用 |
| 不可见字段的值参与提交 | 用户看不见的值覆盖后端数据 | 清值 + 裁剪双保险 |
| 不可见字段参与必填校验 | 「隐藏字段必填错误」永远消不掉，表单卡死 | 校验跳过不可见字段 |
| 联动无防环 | A↔B 互派生无限震荡，页面卡死 | 已处理集合 + 轮数上限，超限报错 |
| 联动里直接发请求 | 副作用不可控，引擎不可测 | 联动纯计算，副作用走 action 事件 |
| custom 规则序列化进 Schema | 配置数据获得代码执行能力 | 规则 id + 注册表，未知 id 按失败处理 |
| 实时校验与提交校验两套实现 | 结论漂移，用户信任崩塌 | 复用 validateField 单实现 |
| 草稿不校验 schemaVersion | Schema 改版后恢复出脏数据 | 版本不一致即作废或显式迁移 |
| 提交成功不清草稿 | 下次打开旧草稿盖掉新数据 | 成功即清，失败保留 |
| 追求 100% 低代码 | 复杂场景被迫绕路，平台变阻力 | 逃生舱自定义代码块 + Schema/代码混用 |
