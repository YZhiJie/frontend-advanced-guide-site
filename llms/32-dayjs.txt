日期看起来只是「把时间格式化成字符串」，真到业务里却处处是边界：月末加一个月、闰年、跨时区展示、夏令时切换、服务端渲染时区错配、测试里取当前时间导致 CI 跨天失败。Day.js 的价值不在于 API 有多全，而在于它提供了一个**稳定、可组合、可注入时间基准**的日期运算层。本章按「心智模型 → 入门 → 进阶 → 精通 → 实战」推进，每节保持概念、场景、代码、最佳实践、自测五段式。

## 32.1 心智模型与学习路线

### 32.1.1 概念解析

Day.js 的核心是一个**不可变包装器**：`dayjs()` 返回的 `Dayjs` 对象内部持有原生 `Date`，但对外暴露的所有变换方法（`add`、`subtract`、`startOf`、`endOf`、`utc`、`tz`、`locale`）都返回**新对象**，不修改原对象。这与 `Date` 的 `setMonth`、`setDate` 原地修改形成根本区别，也是它能安全用于状态管理、函数式组合与并发请求的前提。

另一个核心设计是**薄核 + 插件**。核心包只负责解析、格式化、加减、比较与本地时区能力，官方宣传约 2KB（gzip）；`utc`、`timezone`、`customParseFormat`、`relativeTime`、`duration`、`isBetween`、`isoWeek`、`advancedFormat` 等能力全部以插件形式按需注册。插件通过 `dayjs.extend()` 扩展原型与命名空间，注册是全局的、有顺序依赖的，因此必须收敛到单一入口。

学习路线可以按四层递进：

| 阶段 | 要解决的问题 | 关键能力 |
| --- | --- | --- |
| 入门 | 把字符串安全地变成日期，再稳定地输出 | ISO 解析、`customParseFormat` 严格解析、格式化 token、加减与 `startOf`/`endOf` |
| 进阶 | 判断先后、区间、周期与工作日 | `isBefore`/`isSame`/`isBetween`、插件注册、周起始与 ISO 周、财政周 |
| 精通 | 跨时区、夏令时、多语言与包体 | `utc`/`timezone`、偏移与 DST、`locale`/`relativeTime`/`duration`、按需加载 |
| 实战 | 在 SSR、测试与业务接口里保持确定性 | 注入 `now`、显式时区、固定基准时间、边界用例回归 |

原生 `Date` 的坑几乎是前端日期的「原罪」：月份从 0 开始、对象可变、字符串解析行为依赖引擎、只有本地时区与 UTC 两种视角、`getTimezoneOffset()` 的正负号与直觉相反。Day.js 没有改变底层时间模型，而是用统一 API 把这些坑隔离在包装器内部。

### 32.1.2 典型应用场景

- 列表与详情页的时间展示：统一格式化、相对时间（「3 小时前」）、多语言切换。
- 表单与导入：对外部字符串做严格解析，拒绝 `2023-02-29` 这类溢出日期。
- 权限与营销：判断优惠券、试用期、会话是否落在有效区间。
- 考勤与财务：工作日计算、月初月末、财政周/账期。
- 国际化协作：把 UTC 存储的时间按用户 IANA 时区展示。

### 32.1.3 可运行代码示例

不可变性最直观的验证方式，是观察原对象在链式调用后是否保持不变：

```ts
import dayjs from 'dayjs';

const base = dayjs('2024-01-31T10:00:00');
const nextMonth = base.add(1, 'month');
const monthStart = base.startOf('month');

console.log(base.format('YYYY-MM-DD HH:mm')); // 2024-01-31 10:00
console.log(nextMonth.format('YYYY-MM-DD')); // 2024-02-29（闰年）
console.log(monthStart.format('YYYY-MM-DD')); // 2024-01-01
console.log(base.isSame(nextMonth)); // false
console.log(Object.is(base, nextMonth)); // false
```

对照原生 `Date`：`new Date(2024, 0, 31).setMonth(1)` 会原地改掉原对象，且月份从 0 开始，后续所有引用一起漂移。

### 32.1.4 最佳实践

- 模块边界只传 ISO 8601 字符串或毫秒时间戳，`Dayjs` 对象只在纯函数内部流转。
- 业务函数不要隐式调用 `dayjs()` 取当前时间，把 `now` 作为参数注入，测试才能固定基准。
- 在项目里建唯一的 `dayjs-setup.ts`：集中 `extend` 插件、设置默认 locale，再统一导出 `dayjs`。
- 存储层统一 UTC 或时间戳，展示层才做时区换算与格式化。
- 把「日期运算」和「展示文案」分开：运算返回 `Dayjs`/数字，展示才调用 `format`/`from`。

</details>

## 32.2 入门：解析、格式化与边界加减

### 32.2.1 概念解析

**解析**有三条路径，安全性依次递增：ISO 8601 字符串（如 `2024-02-29T10:30:00+08:00`）由 Day.js 自行解析，行为稳定；非 ISO 字符串（如 `2024/02/29 10:00`）会落到原生 `Date` 的宽松解析，跨引擎可能不一致；`customParseFormat` 插件配合第三个参数 `true` 做严格解析，格式与日期任一不合法都返回 `Invalid Date`，这是表单与导入场景的唯一正确选择。

需要注意一个容易误解的细节：仅日期形式的 ISO 字符串（`2024-02-29`）会被当作**本地时区**的零点，而带 `Z` 或偏移量的字符串表示一个确定瞬间，展示时会换算到本地时区。

**格式化**由 token 表驱动，常用 token 如下：

| token | 含义 | 示例 |
| --- | --- | --- |
| `YYYY` / `YY` | 四位 / 两位年份 | `2024` / `24` |
| `MM` / `M` | 补零 / 不补零月份 | `02` / `2` |
| `DD` / `D` | 补零 / 不补零日期 | `09` / `9` |
| `dddd` | 星期全名（受 locale 影响） | `星期一` |
| `Z` / `ZZ` | 偏移量 | `+08:00` / `+0800` |
| `X` / `x` | 秒级 / 毫秒级时间戳 | `1700000000` |

**加减与边界**的核心规则是「日历运算会夹取到目标月最后一天」：1 月 31 日加一个月得到 2 月 29 日（闰年）或 2 月 28 日（平年）；3 月 31 日减一个月得到 2 月 29 日；2 月 29 日加一年得到次年 2 月 28 日。`startOf`/`endOf` 把时间对齐到单位边界，`endOf('month')` 会给出 `23:59:59.999`，`daysInMonth()` 直接返回当月天数。

### 32.2.2 典型应用场景

- 后端返回的 ISO 时间在前端展示，需要统一格式与本地化星期。
- 表单只允许 `DD/MM/YYYY`，必须拒绝 `31/02/2024` 与 `29/02/2023`。
- 报表选择「本月」「上月」时，需要可靠的月初、月末与天数。
- 订阅、账单、试用期按「日历月/年」递推，不能按固定 30 天或 365 天。

### 32.2.3 可运行代码示例

先看解析的三条路径及严格模式对非法日期的拦截：

```ts
import dayjs from 'dayjs';
import customParseFormat from 'dayjs/plugin/customParseFormat.js';

dayjs.extend(customParseFormat);

console.log(dayjs('2024-02-29T10:30:00+08:00').toISOString()); // 2024-02-29T02:30:00.000Z
console.log(dayjs('2024-02-29').format('YYYY-MM-DD HH:mm')); // 2024-02-29 00:00（本地零点）
console.log(dayjs('29/02/2024', 'DD/MM/YYYY', true).isValid()); // true
console.log(dayjs('29/02/2023', 'DD/MM/YYYY', true).isValid()); // false
console.log(dayjs('2024/02/29', 'YYYY-MM-DD', true).isValid()); // false（分隔符不匹配）
```

格式化时字面量要放进方括号，如 `YYYY [年] M [月] D [日] dddd`；`Z`/`ZZ` 输出偏移量，`X`/`x` 输出秒级/毫秒级时间戳。

月末、闰年与单位边界的组合，是日期代码最容易翻车的地方：

```ts
import dayjs from 'dayjs';

console.log(dayjs('2024-01-31').add(1, 'month').format('YYYY-MM-DD')); // 2024-02-29
console.log(dayjs('2023-01-31').add(1, 'month').format('YYYY-MM-DD')); // 2023-02-28
console.log(dayjs('2024-03-31').subtract(1, 'month').format('YYYY-MM-DD')); // 2024-02-29
console.log(dayjs('2024-02-29').add(1, 'year').format('YYYY-MM-DD')); // 2025-02-28
console.log(dayjs('2024-02-10').daysInMonth()); // 29
console.log(dayjs('2024-02-10').endOf('month').format('YYYY-MM-DD HH:mm:ss.SSS')); // 2024-02-29 23:59:59.999
```

### 32.2.4 最佳实践

- 外部输入一律走 ISO 或 `customParseFormat` 严格解析，禁止依赖「浏览器能解析」的宽松格式。
- 只要出现「月末再加月」的需求，先明确语义：是「同一天号」还是「目标月最后一天」，必要时先 `startOf('month')` 再运算。
- 不要用 `format` 后的字符串相互比较，格式化会丢精度、受 locale 与时区影响。
- 存储与传输保持 ISO UTC 或时间戳，`format` 只发生在展示层。
- 格式化 token 里的中文、斜杠、冒号等字面量要放进方括号，避免 token 冲突。

## 32.3 进阶：比较、插件与周体系

### 32.3.1 概念解析

**比较**有三个层次：`isBefore`/`isAfter` 比较瞬间先后；`isSame` 在不传单位时比较毫秒，传 `'day'`/`'month'` 等单位时只比较对应粒度；`isBetween` 由插件提供，默认开区间 `()`，可通过第四个参数指定 `'[]'`、`'[)'`、`'(]'`。比较时务必显式写出单位，否则「同一天不同时刻」会被判为不相等。

**插件体系**的关键事实：`dayjs.extend(plugin)` 修改的是模块级共享的 `Dayjs` 原型与命名空间，注册一次全局生效；`timezone` 依赖 `utc`，必须后注册；在函数或渲染过程中反复 `extend` 不会报错，但会让依赖关系散落、增加心智负担。工程上应把注册收敛到单一 setup 模块。

**周体系**有两套口径：`day()` 中周日为 0，`startOf('week')` 受 locale 的 `weekStart` 影响（`zh-cn` 从周一开始，`en` 从周日开始）；`isoWeek` 插件提供 ISO 8601 口径——周一为一周开始、包含 1 月 4 日的那周为第 1 周。财政周/账期通常不是自然周，需要以「财政年起始月 + 周偏移」自行定义，不能直接拿 `week()` 交差。

### 32.3.2 典型应用场景

- 优惠券、试用期、会话过期：判断当前时刻是否落在区间内，边界日是否包含。
- 报表筛选：按天/周/月比较，而不是比较格式化字符串。
- 迭代与排期：ISO 周、季度、财政周编号。
- 考勤与结算：工作日区间、周末排除、跨月周期。

### 32.3.3 可运行代码示例

比较 API 的单位与区间开闭，决定了边界日是否会被算进去：

```ts
import dayjs from 'dayjs';
import isBetween from 'dayjs/plugin/isBetween.js';

dayjs.extend(isBetween);

const now = dayjs('2024-06-15T12:00:00');
const start = dayjs('2024-06-01');
const end = dayjs('2024-06-30');

console.log(now.isAfter(start)); // true
console.log(now.isBefore(end)); // true
console.log(now.isSame('2024-06-15T23:59:59', 'day')); // true
console.log(now.isBetween(start, end)); // true（默认开区间）
console.log(start.isBetween(start, end, 'day', '[]')); // true（闭区间）
console.log(start.isSame(end, 'month')); // true
```

插件注册的顺序与位置同样重要：`dayjs.extend(utc)` 之后才能 `dayjs.extend(timezone)`，反过来 `tz` 会行为异常；两者都应放在唯一的 setup 模块里，而不是散落在组件中。

周起始、ISO 周与自定义财政周需要分别计算：

```ts
import dayjs from 'dayjs';
import isoWeek from 'dayjs/plugin/isoWeek.js';

dayjs.extend(isoWeek);

console.log(dayjs('2024-01-01').day()); // 1，周一
console.log(dayjs('2024-01-01').isoWeek()); // 1，ISO 第 1 周
console.log(dayjs('2024-01-01').startOf('isoWeek').format('YYYY-MM-DD')); // 2024-01-01

function fiscalWeek(input: string, fiscalStartMonth: number): string {
    const d = dayjs(input);
    const fiscalYear = d.month() + 1 >= fiscalStartMonth ? d.year() : d.year() - 1;
    const fiscalStart = dayjs(`${fiscalYear}-${fiscalStartMonth}-01`).startOf('week');
    const week = Math.floor(d.startOf('day').diff(fiscalStart, 'day') / 7) + 1;
    return `${fiscalYear}-W${String(week).padStart(2, '0')}`;
}

console.log(fiscalWeek('2024-03-15', 2)); // 2024-W7（财政年从 2 月开始）
```

### 32.3.4 最佳实践

- `isSame`、`isBefore`、`isBetween` 一律显式传单位与开闭规则，不要依赖默认值。
- 比较「是不是同一天」用 `isSame(..., 'day')`，不要比较 `format('YYYY-MM-DD')` 字符串。
- 插件注册集中在 `dayjs-setup.ts`，按依赖顺序 `utc` → `timezone`，并写注释说明依赖。
- 自然周与财政周分开建模：自然周用 `isoWeek`/locale，财政周显式保存「起始月 + 周编号规则」。
- 周末与节假日不要混为一谈：`businessDaysBetween` 只排除周末，节假日需要额外的日历表。

不传单位时比较的是毫秒时间戳，同一天不同时刻也会判为不同；传 `'day'` 只比较日期粒度。`isBetween` 默认是开区间 `()`，起点和终点当天都不算，需要包含边界时显式传 `'[]'` 或 `'[)'`。

`timezone` 依赖 `utc` 提供的 UTC 模式与偏移能力，顺序反了会导致 `tz` 行为异常或直接不可用。`extend` 修改的是全局原型，重复调用虽不报错，但会让注册时机与依赖关系分散，容易在 SSR、微前端或按需加载场景出现「某处能用、某处不能用」，因此应集中到唯一入口。

</details>

## 32.4 精通：时区、DST、本地化与包体

### 32.4.1 概念解析

**UTC 与时区**要区分三个概念：绝对瞬间（instant）、UTC 表示、某 IANA 时区的墙上时间。`dayjs.utc(input)` 把输入解释为 UTC 并进入 UTC 模式；`.tz('Asia/Shanghai')` 把同一瞬间换算到目标时区；`.utcOffset()` 返回分钟数，**东正西负**，与原生 `getTimezoneOffset()` 的正负号相反。`dayjs.tz('2024-03-10 09:00', 'America/New_York')` 则是把「墙上时间」解释为某时区的本地时间，两者语义不同。

**DST（夏令时）**带来两类异常：不存在的本地时间（春季拨快，如纽约 3 月 10 日 02:30 不存在）与重复的本地时间（秋季拨慢，01:30 出现两次）。Day.js 会把不存在的墙上时间顺延到有效时刻，重复时刻则按实现选择一个偏移。更重要的是：`add(1, 'day')` 是日历日运算，跨 DST 可能只有 23 或 25 小时；`add(24, 'hour')` 是绝对时长，跨 DST 后墙上时间会偏移一小时。另外，`.tz()` 对象的偏移在构造时缓存，`add`/`subtract` 之后要再调用 `.tz(zone, true)` 才会按新偏移归一化，否则会显示错误的 `-05:00`。

**本地化**分三层：`locale` 控制月份/星期/相对时间文案；`relativeTime` 插件提供 `fromNow`/`from`/`to`/`humanize`；`duration` 插件提供时长对象的拆分与格式化。`dayjs.locale()` 是全局设置，SSR 下多请求并发会互相污染，实例级 `.locale()` 更安全。

**包体**方面，核心约 2KB，插件与 locale 各自增加几百字节到 1KB 不等；静态 `import 'dayjs/locale/zh-cn'` 会进入首包，多语言站点应按需动态加载。若只需要格式化、不需要日期运算，原生 `Intl.DateTimeFormat` 往往更划算。

**与原生 Date、Temporal 的分工**可以这样看：

| 能力 | 原生 Date | Day.js | Temporal |
| --- | --- | --- | --- |
| 不可变运算 | 否，需手动克隆 | 是 | 是 |
| 时区/墙上时间 | 仅本地与 UTC | `utc` + `timezone` 插件 | `ZonedDateTime` 原生建模 |
| 日历运算 | 手写且易错 | `add`/`startOf` 等 | `PlainDate` + `Duration` |
| 解析严格性 | 引擎相关 | `customParseFormat` | ISO 解析严格 |
| 生产可用性 | 始终可用 | 稳定、生态成熟 | 仍需 polyfill/运行时支持 |

Temporal 是方向，但在 Node 24 与主流浏览器全面落地前，Day.js 仍是业务里更稳妥的默认选择；把日期逻辑收敛到自己的适配层，将来替换成本才可控。

### 32.4.2 典型应用场景

- 跨国 SaaS：服务端存 UTC，前端按用户 profile/cookie 中的 IANA 时区展示。
- 会议与排期：把「纽约 9 点」的墙上时间保存为瞬间，再换算到参会者时区。
- 多语言站点：切换语言时同时切换月份、星期与相对时间文案。
- 倒计时/时长展示：把毫秒差拆成天、时、分、秒，处理过期状态。
- SSR/SSG：避免服务端本地时区与浏览器时区不一致导致的 hydration mismatch。

### 32.4.3 可运行代码示例

同一瞬间在不同时区的表示，以及偏移量随 DST 变化：

```ts
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc.js';
import timezone from 'dayjs/plugin/timezone.js';

dayjs.extend(utc);
dayjs.extend(timezone);

const instant = dayjs.utc('2024-03-10T07:00:00Z');
console.log(instant.tz('Asia/Shanghai').format('YYYY-MM-DD HH:mm Z')); // 2024-03-10 15:00 +08:00
console.log(instant.tz('America/New_York').format('YYYY-MM-DD HH:mm Z')); // 2024-03-10 03:00 -04:00
console.log(instant.tz('America/New_York').utcOffset()); // -240
```

DST 前后做「加一天」与「加 24 小时」，且 `tz` 对象的偏移在构造时缓存，运算后必须重新归一化：

```ts
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc.js';
import timezone from 'dayjs/plugin/timezone.js';

dayjs.extend(utc);
dayjs.extend(timezone);

const beforeDst = dayjs.tz('2024-03-09 12:00', 'America/New_York');
// add 后偏移仍是缓存的 -05:00，必须 .tz(zone, true) 重新归一化
const nextDay = beforeDst.add(1, 'day').tz('America/New_York', true);
console.log(beforeDst.utcOffset()); // -300
console.log(nextDay.format('YYYY-MM-DD HH:mm Z')); // 2024-03-10 12:00 -04:00
console.log(nextDay.diff(beforeDst, 'hour')); // 23
console.log(beforeDst.add(24, 'hour').tz('America/New_York').format('HH:mm Z')); // 13:00 -04:00
```

本地化与时长：`dayjs.extend(duration)` 后，`dayjs.duration(diff)` 可拆分天/时/分/秒并 `humanize()`（依赖 `relativeTime`）；`dayjs.locale('zh-cn')` 是全局设置，实例级 `.locale('en')` 更适合 SSR。locale 按需加载用白名单 `() => import('dayjs/locale/zh-cn.js')`，不要静态引入全部语言。SSR 场景用 `dayjs.utc(iso).tz(userZone).format(...)` 显式传时区，服务端只输出 UTC/ISO，客户端再本地化。

### 32.4.4 最佳实践

- 服务端进程时区固定为 UTC（`TZ=UTC`），但代码仍要显式传 `timeZone`，不要依赖进程默认值。
- 时区标识使用 IANA 名称（`Asia/Shanghai`），不要用 `GMT+8` 这类固定偏移，后者无法正确表达 DST。
- 需要「墙上时间」时用 `dayjs.tz(wallTime, zone)`；需要「绝对瞬间」时用 ISO 带 `Z`/偏移的输入。
- 跨 DST 的「加一天」用 `add(1, 'day')`，倒计时/缓存 TTL 的「24 小时」用毫秒或 `add(24, 'hour')`，两者不要混用。
- 多语言站点按需动态加载 locale；SSR 下用实例级 `.locale()` 或请求作用域，避免全局污染。
- 用 `Intl.DateTimeFormat` 做一次性格式化、用 Day.js 做日历运算；两者都显式传 `timeZone`。

`dayjs.utc(input)` 把输入解释为 UTC 并进入 UTC 模式，适合处理绝对瞬间；`dayjs.tz(wallTime, zone)` 把一段墙上时间解释为指定时区的本地时间。`utcOffset()` 返回分钟，东半球为正、西半球为负，例如东八区是 `480`，纽约夏令时是 `-240`，与原生 `getTimezoneOffset()` 相反。

<details>
<summary><b>11. 【进阶】纽约 2024-03-09 12:00 加一天，为什么直接 `add` 后偏移量仍是 `-05:00`？正确写法与结果是什么？</b></summary>

`.tz()` 构造时缓存偏移，`add(1, 'day')` 只做时间戳与日历字段运算，不会重新查询 IANA 规则，因此仍显示 `-05:00`。正确写法是 `beforeDst.add(1, 'day').tz('America/New_York', true)`：保持墙上时间 12:00 并重新计算偏移，得到 3 月 10 日 12:00 `-04:00`，实际经过 23 小时。绝对 24 小时则先 `add(24, 'hour')`，再 `.tz(zone)` 归一化为 13:00。

<summary><b>12. 【挑战】SSR 页面在服务端显示「6 月 15 日」，浏览器 hydration 后变成「6 月 16 日」，如何定位与修复？</b></summary>

先确认服务端是否用 `dayjs()`/本地时区格式化 UTC 时间，而浏览器按用户时区渲染，同一瞬间跨了日期边界。修复原则：服务端只输出 ISO/UTC 或时间戳；展示时显式使用用户 IANA 时区（从 cookie/请求头获取）；无法拿到用户时区时，先在服务端渲染 UTC 或占位，客户端 `onMounted`/`useEffect` 后再格式化；同时给服务端进程设 `TZ=UTC`，避免机器默认时区漂移。
</details>

## 32.5 实战：把日期能力封装成确定性函数

### 32.5.1 概念解析

实战的目标不是「会用 API」，而是把日期能力封装成**输入明确、输出稳定、可测试**的函数。实验室包 `@fag/dayjs-lab` 的七个导出覆盖了业务里最常见的七类需求：

| 导出 | 职责 | 确定性来源 |
| --- | --- | --- |
| `formatRange` | 日期区间展示，自动排序、同日折叠 | 两个日期入参 |
| `businessDaysBetween` | 闭区间工作日计数，排除周末 | 起止日期入参 |
| `monthBounds` | 月初、月末与当月天数 | 目标日期入参 |
| `toUserTimezone` | 把瞬间换算到 IANA 时区 | 输入 + 显式时区 |
| `humanizeFromNow` | 中文相对时间 | 目标时间 + 注入 `now` |
| `parseStrict` | 严格解析，失败返回 `null` | 输入 + 格式 |
| `countdownParts` | 倒计时拆分，过期归零 | 目标时间 + 注入 `now` |

这些函数的共同设计约束是：不读系统时钟、不依赖进程时区、不修改全局 locale（setup 模块除外）、错误输入显式抛 `RangeError` 或返回 `null`。

### 32.5.2 典型应用场景

- 报表页展示「2024-06-01 ~ 2024-06-15」，同日活动只显示一天。
- 考勤/结算计算工作日，跨周末与月末都要稳定。
- 管理后台按用户时区展示操作时间，避免客服与用户看到不同日期。
- 活动倒计时拆成天/时/分/秒，过期后统一显示「已结束」。
- 列表里的「3 天前」用固定 `now` 做快照测试，避免文案随真实时间漂移。

### 32.5.3 可运行代码示例

实验室函数的调用方式与返回值：

```ts
import {
    businessDaysBetween,
    countdownParts,
    formatRange,
    humanizeFromNow,
    monthBounds,
    parseStrict,
    toUserTimezone,
} from './src/index.js';

const now = '2024-06-15T12:00:00Z';

console.log(formatRange('2024-06-15', '2024-06-01')); // 2024-06-01 ~ 2024-06-15
console.log(monthBounds('2024-02-10').days); // 29
console.log(businessDaysBetween('2024-06-03', '2024-06-07')); // 5
console.log(toUserTimezone(now, 'Asia/Shanghai').format('YYYY-MM-DD HH:mm')); // 2024-06-15 20:00
console.log(humanizeFromNow('2024-06-14T12:00:00Z', now)); // 1 天前
console.log(parseStrict('2024-02-29', 'YYYY-MM-DD')?.format('YYYY-MM-DD')); // 2024-02-29
console.log(countdownParts('2024-06-18T15:30:45Z', now)); // 3 天 3 小时 30 分 45 秒
```

配套测试用 `node:test` + `node:assert/strict`，把月末、闰年、工作日、时区、严格解析失败、相对时间与倒计时都固定成可回归用例；运行命令见章首。

### 32.5.4 最佳实践

- 函数签名显式列出 `now`/基准时间，禁止在库内部调用 `dayjs()`。
- 模块出口优先返回字符串、数字或普通对象，避免把 `Dayjs` 实例泄漏给不相关层。
- 非法输入用 `RangeError` 或 `null` 表达，并在类型上写清楚（如 `Dayjs | null`）。
- 时区参数必填，不提供「跟随系统」的默认值。
- 测试覆盖闰年 2 月、平年 2 月、跨周末、反向区间、DST 切换日、严格解析失败与过期倒计时。
- 库代码不写 `console.log`，副作用只有顶层的插件注册与 locale 设置。

### 实战案例：跨时区会议日程生成

跨国团队的排期页要把同一场会议展示给不同时区的参会者，并标出「对该参会者而言是否是非工作时间」，方便主持人避开深夜档。会议在存储层只有一个字段：UTC 开始瞬间；本地时间与非工作时间标记都必须在展示层换算之后产生。任何一端把「墙上时间」写进存储，全链路的时间语义就失真了。

```ts
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc.js';
import timezone from 'dayjs/plugin/timezone.js';

dayjs.extend(utc);
dayjs.extend(timezone);

interface AttendeeView {
    zone: string;
    localLabel: string;
    offHours: boolean;
}

function meetingViews(utcStart: string, zones: string[]): AttendeeView[] {
    const start = dayjs.utc(utcStart);
    if (!utcStart.endsWith('Z') || !start.isValid()) {
        throw new RangeError('会议开始时间必须是带 Z 的 UTC ISO 字符串');
    }
    return zones.map((zone) => {
        const local = start.tz(zone);
        const hour = local.hour();
        return {
            zone,
            localLabel: local.format('YYYY-MM-DD HH:mm Z'),
            offHours: hour < 9 || hour >= 18,
        };
    });
}

console.log(meetingViews('2024-06-15T09:00:00Z', ['Asia/Shanghai', 'America/New_York']));
// 上海：2024-06-15 17:00 +08:00，offHours 为 false
// 纽约：2024-06-15 05:00 -04:00，offHours 为 true
```

实现要点与取舍：

- 存储恒用 UTC：接口与数据库只保存带 `Z` 的 ISO 瞬间，`tz()` 只出现在生成展示数据的这一层。踩坑点：把「纽约的墙上时间字符串」直接存库，纽约服务器与上海服务器用 `dayjs()` 解析会得到两个不同的瞬间，会议提醒自然就错开了几个小时。
- 「是否非工作时间」按换算后的本地 `hour()` 判定，不要用 UTC 小时或服务器进程的小时。
- 同一场会议在不同时区可能落在不同日期，`localLabel` 必须带日期；只给 `HH:mm` 会让跨日参会者错过会议。
- 时区用 IANA 名称并做白名单校验，非法名称会让 `tz()` 抛 `RangeError`；「9 点到 18 点」的工作时间口径将来要按地区配置，所以判定规则收在函数里，而不是写进展示模板。

### 实战案例：账单周期生成与月末钳制

订阅制按「日历月」出账：签约日是 1 月 31 日，之后每期都应落在「与签约日相同的日号」，目标月没有该日号时取月末。直接把上一期结果继续 `add(1, 'month')` 会发生日号漂移：1 月 31 日被夹取成 2 月 29 日之后，后续各期永久变成 29 日。正确做法是永远从签约锚点出发计算第 N 期，并用 `daysInMonth()` 显式钳制。

```ts
import dayjs, { type Dayjs } from 'dayjs';

// 第 N 期账单日：保持锚点日号，目标月天数不足时钳制到月末
function addMonthsClamped(anchor: Dayjs, months: number): Dayjs {
    const anchorDay = anchor.date();
    const target = anchor.add(months, 'month').startOf('month');
    return target.date(Math.min(anchorDay, target.daysInMonth()));
}

function billingSchedule(anchorDate: string, periods: number): string[] {
    const anchor = dayjs(anchorDate);
    if (!anchor.isValid() || periods < 1) {
        throw new RangeError('锚点日期不合法或期数小于 1');
    }
    return Array.from({ length: periods }, (_, i) =>
        addMonthsClamped(anchor, i + 1).format('YYYY-MM-DD'),
    );
}

console.log(billingSchedule('2024-01-31', 4));
// ['2024-02-29', '2024-03-31', '2024-04-30', '2024-05-31']：日号保持 31，不足则钳制
console.log(dayjs('2024-01-31').add(1, 'month').add(1, 'month').format('YYYY-MM-DD'));
// 2024-03-29：夹取结果成了新基准，日号从 31 漂移成 29（踩坑）
```

实现要点与取舍：

- 防漂移的关键是「每期从锚点重算」：夹取会改写日号，把夹取结果当作下一期的输入，31 日就永久退化为 28/29 日——这是连环 `add` 最经典的坑，上面的第二行输出就是反例。
- 先 `startOf('month')` 归到目标月 1 日，再用 `date(Math.min(...))` 设日号，不依赖 `add` 的隐式夹取行为；`daysInMonth()` 必须调用在目标月上，不是锚点月。
- 「保持日号、月末钳制」（本案例）与「每月最后一天出账」（`endOf('month')`）是两种语义，从 3 月起各期日期完全不同，接口命名要把两者区分开。
- 输出用 `YYYY-MM-DD` 纯日期字符串，出账时刻由展示层补充，避免 `23:59:59.999` 这类边界噪音泄漏进业务表。

### 实战案例：服务端时钟偏差校正

秒杀开始时刻、优惠券有效期都以服务端为准，但用户手机时钟快 3 分钟，就会看到「已开始」却提交被拒，或倒计时提前归零。下单、登录这类接口顺带返回服务器时间后，前端算出一次偏差 `offset`，之后所有「现在」都用「客户端时间 + offset」得出，与服务端口径对齐。

```ts
import dayjs, { type Dayjs } from 'dayjs';

// 纯函数：偏差 = 服务器时间 - 客户端时间，可单测
function computeClockOffset(serverNowMs: number, clientNowMs: number): number {
    return serverNowMs - clientNowMs;
}

// 工厂：返回「已校正的 now」；rawNow 可注入，测试不必碰真实时钟
function createSyncedNow(offsetMs: number, rawNow: () => number = () => Date.now()): () => Dayjs {
    return () => dayjs(rawNow() + offsetMs);
}

const offset = computeClockOffset(
    Date.parse('2024-06-15T12:00:00Z'),
    Date.parse('2024-06-15T12:03:00Z'), // 客户端时钟快 3 分钟
);
const now = createSyncedNow(offset, () => Date.parse('2024-06-15T12:04:00Z'));
console.log(now().toISOString()); // 2024-06-15T12:01:00.000Z
console.log(now().isBefore('2024-06-15T12:00:00Z')); // false：与服务端口径一致，秒杀已开始
```

实现要点与取舍：

- 要保存的是偏差而不是「服务器此刻」：`offset` 是相对量，页面常驻几分钟仍适用；把响应里的服务器时间直接存起来当 `now` 用，几分钟后就过期了——这是最常见的踩坑点。
- `Date.now()` 是 UTC 毫秒，本身不受系统时区设置影响：时区配错影响的是「墙上时间字符串」的解析与展示，用显式 IANA 时区解决；系统时钟被改快改慢影响的是 epoch 本身，只能靠 `offset` 校正，两类问题不要混为一谈。
- 一次请求有网络延迟，`serverNow` 更接近「服务器发出响应」的时刻；精确做法是在请求前后各采样一次推算，普通业务接受半个 RTT 的误差即可。
- 把「取原始时间」做成可注入参数，单测不用动真实系统时钟。

### 实战案例：自然月账期与合同到期提醒

考勤与结算按「跨过几个自然月」计算账期，合同系统还要做「到期前 30 天」提醒。`diff('month')` 内部按「锚点满月」近似后取整，大月小月场景与财务口径对不上；提醒若用区间判断会每天重复触发，用「当日相等」判断则停机当天会漏发，取舍需要提前想清楚。

```ts
import dayjs, { type Dayjs } from 'dayjs';

// 「跨过几个自然月」：只看年月差，不受大月小月影响
function calendarMonthsBetween(start: Dayjs, end: Dayjs): number {
    return (end.year() - start.year()) * 12 + (end.month() - start.month());
}

function contractReminder(contractEnd: string, now: Dayjs, aheadDays: number): string | null {
    const deadline = dayjs(contractEnd).startOf('day');
    if (!deadline.isValid() || deadline.isBefore(now.startOf('day'))) {
        return null; // 非法输入或已过期，静默跳过
    }
    const remindDay = deadline.subtract(aheadDays, 'day');
    if (now.isSame(remindDay, 'day')) {
        return `合同 ${deadline.format('YYYY-MM-DD')} 到期，剩余 ${aheadDays} 天`;
    }
    return null;
}

console.log(calendarMonthsBetween(dayjs('2024-01-31'), dayjs('2024-03-30'))); // 2
console.log(dayjs('2024-03-30').diff(dayjs('2024-01-31'), 'month')); // 1：不满 2 个整月，按满月近似取整
console.log(contractReminder('2024-06-20', dayjs('2024-05-21T09:00:00'), 30)); // 合同 2024-06-20 到期，剩余 30 天
console.log(contractReminder('2024-06-20', dayjs('2024-05-22T09:00:00'), 30)); // null
```

实现要点与取舍：

- 结算类需求先定口径：「跨过几个自然月」用 `year * 12 + month` 手算，「满了几个月」才接近 `diff` 的语义。踩坑点：`2024-01-31` 到 `2024-03-30`，边界口径是 2，`diff` 取整后是 1，两套口径混用会直接算错账。
- 「提前 N 天提醒」用 `isSame(remindDay, 'day')` 保证幂等，同一天重复跑批不会发多条通知；代价是当天停机就漏发，兜底方案是记录「上次已提醒日」，补跑时检查 `remindDay` 是否晚于它。
- 比较前先 `startOf('day')` 归零，避免 `now` 带时刻导致 `isBefore` 在边界日误判（到期当天不算过期）。
- 非法输入返回 `null` 还是抛错要在接口文档写清楚，本例选择静默跳过，由调用方决定是否补录。

### 进阶技巧：手写一个 Day.js 插件

```ts
import dayjs from 'dayjs';
import type { Dayjs, PluginFunc } from 'dayjs';

declare module 'dayjs' {
    interface Dayjs {
        fiscalQuarter(fiscalStartMonth?: number): number;
    }
}

// 财政季度：fiscalStartMonth 为财政年起始月，2 月起则 2~4 月为 Q1
export const fiscalQuarter: PluginFunc = (_option, dayjsClass) => {
    dayjsClass.prototype.fiscalQuarter = function (this: Dayjs, start = 1): number {
        const offset = (this.month() + 1 - start + 12) % 12;
        return Math.floor(offset / 3) + 1;
    };
};

dayjs.extend(fiscalQuarter);
console.log(dayjs('2024-03-15').fiscalQuarter(2)); // 1
console.log(dayjs('2024-01-15').fiscalQuarter(2)); // 4：11 月才进入新财年，1 月仍属 Q4
```

- 插件是 `(option, dayjsClass, dayjsFactory) => void` 形态的函数：`extend` 调用它并把方法挂到 `dayjsClass.prototype`；实例方法里用 `this` 前先标注 `this: Dayjs`。
- 用 `declare module 'dayjs'` 做 declaration merging，让 TypeScript 认识新方法，否则运行时能跑、编译期报错。
- 插件必须无副作用：不在模块顶层改原型或全局 locale，一切改动发生在 `extend` 的调用栈内；不 import 业务代码、不持有可变模块状态，未注册的插件才能被 tree-shake 出包。
- 有依赖的插件要写明注册顺序（`utc` → `timezone`），并收敛到 setup 模块集中注册，插件内部不要重复 `extend` 依赖。

### 进阶技巧：测试中的时间控制

```ts
import dayjs from 'dayjs';
import utc from 'dayjs/plugin/utc.js';
import { afterEach, expect, it, vi } from 'vitest';

dayjs.extend(utc);
afterEach(() => vi.useRealTimers());

it('假时钟下倒计时不会漂移', () => {
    vi.useFakeTimers();
    vi.setSystemTime(new Date('2024-06-15T12:00:00Z'));
    const target = dayjs.utc('2024-06-15T12:05:00Z').valueOf();
    expect(target - Date.now()).toBe(300_000);
    vi.advanceTimersByTime(60_000);
    expect(target - Date.now()).toBe(240_000);
});
```

- 分工：自己的纯函数（`humanizeFromNow`、`countdownParts`）已经注入 `now`，直接传固定时间即可，不需要假时钟；假时钟留给「内部隐式读时钟、不便改签名」的遗留代码与组件用例。
- API 对应：Vitest 用 `vi.useFakeTimers()` + `vi.setSystemTime()`，Jest 用 `jest.setSystemTime()`，node:test 用 `t.mock.timers.enable({ apis: ['Date'] })`；假时钟会同时冻结 `setTimeout`/`setInterval`，用 `advanceTimersByTime` 推进。
- 「昨天」「上个月」这类相对断言不要拿 `dayjs().subtract(1, 'day')` 去撞真实时钟：CI 恰好跑到月末或跨年的那一秒，快照就随机失败；先固定「现在」，再构造相对值。
- `afterEach` 恢复真实时钟，避免污染同文件其他用例；CI 里再叠加 `TZ=UTC` 消掉机器时区变量。

### 进阶技巧：ISO 周与跨年周编号

```ts
import dayjs from 'dayjs';
import advancedFormat from 'dayjs/plugin/advancedFormat.js';
import isoWeek from 'dayjs/plugin/isoWeek.js';
import weekOfYear from 'dayjs/plugin/weekOfYear.js';

dayjs.extend(isoWeek);
dayjs.extend(advancedFormat);
dayjs.extend(weekOfYear);

const crossYear = dayjs('2024-12-30'); // 周一，ISO 口径属于 2025 年第 1 周
console.log(crossYear.year()); // 2024（自然年）
console.log(crossYear.isoWeekYear()); // 2025（ISO 周年）
console.log(crossYear.format('YYYY ww')); // 2024 01：自然年配周号，跨年周撞车（踩坑）
console.log(crossYear.format('GGGG WW')); // 2025 01：周年配 ISO 周，唯一可查
```

- 默认 `week()` 是 locale 口径（`en` 从周日开始），`isoWeek` 插件才是 ISO 8601 口径（周一开始、包含 1 月 4 日的那周为第 1 周），两者编号经常差 1。
- 周年与周号必须同口径配对：ISO 用 `GGGG WW`（对应 `isoWeekYear` + `isoWeek`），locale 用 `gggg ww`（需要 `weekYear` + `weekOfYear` 插件）；拿 `YYYY` 拼周号，跨年周会落到错误的年份，报表按周聚合直接查不到数据。
- 大小写不能混搭：`gggg` 是 locale 周年、`GGGG` 是 ISO 周年，`gggg` 配 `WW` 会拼出两套口径的杂交编号。
- 对外输出用 `GGGG-WW` 形式（如 `2025-W01`）并在接口文档注明口径；内部运算继续用 `Dayjs` 对象，不要拿周字符串反解日期。

## 32.6 综合自测题

<details>
<summary><b>16. 【基础】从「传输、存储、运算、展示」四个环节，说明 Day.js 在日期工程中的推荐数据形态。</b></summary>

传输用 ISO 8601 字符串（带 `Z` 表示瞬间）或毫秒时间戳；存储统一 UTC/时间戳，避免本地时区写入；运算在 `Dayjs` 对象上进行，且函数注入基准时间；展示才按用户 IANA 时区格式化，并明确 locale。核心原则是「瞬间用 UTC，墙上时间带时区，展示才本地化」。
</details>

<details>
<summary><b>17. 【进阶】对 `2024-01-31` 连续执行三次 `add(1, 'month')`，结果是什么？如果业务要求「每月都取最后一天」，应该怎么写？</b></summary>

连续执行会得到 `2024-02-29` → `2024-03-29` → `2024-04-29`，日号在第一次夹取后永久变成 29，产生漂移。若要求「每月最后一天」，应保存原始日期或每月重新计算：`dayjs('2024-01-31').add(n, 'month').endOf('month')`，并注意 `endOf` 会把时间对齐到 `23:59:59.999`，展示前再按需截断。
</details>

<details>
<summary><b>18. 【挑战】为一个跨国业务设计日期模块，要求服务端、浏览器、测试三端结果一致，写出关键约束与目录结构。</b></summary>

关键约束：①全链路存 UTC 瞬间；②所有展示函数必传 IANA 时区；③库函数注入 `now`，禁止隐式系统时钟；④服务端 `TZ=UTC` 且不依赖默认时区；⑤locale 与插件集中在 setup 模块，SSR 使用实例级 locale；⑥测试固定 `now` 并覆盖闰年、月末、DST、周末与跨年。目录可分 `setup.ts`（插件/locale 注册）、`timezone.ts`（换算与用户时区解析）、`calendar.ts`（月界/工作日/财政周）、`format.ts`（展示与相对时间）、`parse.ts`（严格解析），测试与实现同构。
</details>

<details>
<summary><b>19. 【挑战】团队准备从 Moment.js 迁移到 Day.js，或进一步评估 Temporal。你会如何制定迁移策略与验收标准？</b></summary>

先盘点调用面：解析、格式化、时区、相对时间、duration、locale、插件扩展；建立适配层，业务代码只依赖自有 API，避免直接散落 `dayjs` 调用。迁移按模块灰度，重点回归月末、闰年、DST、locale 文案与严格解析行为；用固定时间快照测试对比迁移前后输出。Temporal 可作为适配层的下一实现：其 `ZonedDateTime`/`PlainDate`/`Duration` 语义更清晰，但需确认运行时支持与 polyfill 体积，未全面落地前不直接替换生产依赖。
</details>

## 32.7 本章避坑清单

| 坑 | 后果 | 避法 |
| --- | --- | --- |
| 业务函数内部直接调用 `dayjs()` | 结果随真实时钟漂移，测试跨天失败 | 显式注入 `now` 或基准时间 |
| 依赖非 ISO 字符串解析 | 不同引擎结果不一致或 `Invalid Date` | 用 ISO 8601 或 `customParseFormat` |
| 严格解析忘记第三个参数 `true` | `2023-02-29` 被悄悄溢出成 3 月 1 日 | 外部输入一律严格解析 |
| 月末直接 `add(1, 'month')` | 31 日被夹取到 28/29 日 | 先明确语义，必要时 `startOf('month')`/`endOf('month')` |
| 连续按月递推不复位日号 | 日号从 31 漂移到 29 再到 29 | 保存原始日号，每次从基准重建 |
| 用格式化字符串比较日期 | 丢精度、受 locale/时区影响 | 用 `isBefore`/`isAfter`/`isSame` 比瞬间 |
| `isSame` 不传单位 | 同一天不同时刻被判为不等 | 明确传 `'day'`/`'month'` 等单位 |
| `isBetween` 默认开区间 | 起止边界日漏算 | 显式传 `'[]'` 或 `'[)'` |
| 插件未 `extend` 就调用方法 | 运行时 `undefined is not a function` | setup 模块统一注册并导出 |
| `timezone` 先于 `utc` 注册 | `tz` 行为异常或不可用 | 严格按 `utc` → `timezone` 顺序 |
| 把 `utcOffset()` 当 `getTimezoneOffset()` | 正负号颠倒，时区计算反向 | 记住 Day.js 东正西负 |
| 静态引入全部 locale | 首包体积膨胀 | 按需动态 `import()` locale |
| SSR 使用服务器本地时区格式化 | hydration mismatch、日期差一天 | 服务端存/传 UTC，展示显式传时区 |
| 跨 DST 用 `add(24, 'hour')` 当一天 | 墙上时间偏移一小时 | 日历日用 `add(1, 'day')` |
| `tz` 对象 `add` 后偏移未更新 | 跨 DST 显示错误偏移与时间 | 再调用 `.tz(zone, true)` 归一化 |
| 测试依赖真实时间与机器时区 | CI 在月末/跨时区随机失败 | 固定 `now` + 显式 IANA 时区 |

> **下一步**：把本章的七个函数当作项目日期模块的最小骨架，先固定「输入形态、时区来源、`now` 注入」三条契约，再逐步补上节假日、财政周与 locale 按需加载。日期代码的质量不取决于 API 背得多熟，而取决于边界用例是否被固定成测试。
