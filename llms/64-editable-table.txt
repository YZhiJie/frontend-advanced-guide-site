## 64.1 虚拟滚动内核：固定与动态行高

### 概念解析

万行表格直接渲染 = 万级 DOM 节点 = 滚动掉帧、内存爆炸。虚拟滚动的思路只有一句话：**只渲染视口内（加少量缓冲区）的行，用一个总高度的占位元素撑起滚动条**。

固定行高是 O(1) 的算术问题：

```text
firstVisible = floor(scrollTop / rowH)
visibleCount = ceil(viewportH / rowH)
渲染窗口     = [firstVisible - overscan, firstVisible + visibleCount + overscan)
占位上偏移   = start × rowH，总高 = total × rowH
```

`overscan`（视口外多渲染的行数）是体验关键：快速滚动时浏览器还没来得及执行 JS，缓冲区的行先顶上，避免白屏。典型值 3-10，权衡内存与流畅。

动态行高（展开行、自适应文本）把除法变成了查找问题：**前缀和 + 二分**。维护 `offsets[i] = 第 i 行顶部偏移`，首个可见行 = 第一个「底部偏移 > scrollTop」的行，二分定位 O(log n)。行高变化时（展开/收起）增量更新受影响之后的前缀和。

动态行高带出一个隐蔽体验问题：**滚动锚定**。视口上方的行突然变高（如异步图片加载完成撑开行），会把当前可视内容往下推，用户视线被打断。解法：上方行高变化时给 `scrollTop` 加等量补偿——变化发生在视口下方则无需处理。浏览器的 CSS `overflow-anchor` 能处理简单场景，虚拟滚动里要自己算。

### 完整代码示例

```typescript
// 文件: examples/64-01-virtual-scroll.ts（核心节选）
class DynamicHeightIndex {
  private offsets: number[]; // 前缀和:offsets[i] = 第 i 行顶部偏移
  firstVisible(scrollTop: number): number {
    // 二分:第一个"底部偏移 > scrollTop"的行
  }
  updateHeight(index: number, newH: number) {
    const delta = newH - this.heights[index];
    for (let i = index + 1; i < this.offsets.length; i++) this.offsets[i] += delta;
  }
}
// 滚动锚定:变化在视口上方才补偿 scrollTop
function anchorCompensation(changedIndex, delta, firstVisible) {
  return changedIndex < firstVisible ? delta : 0;
}
```

> 运行方式：`npx tsx examples/64-01-virtual-scroll.ts`（固定窗口、前缀和二分定位、行高变更重算、锚定补偿，共 10 组硬断言）。

### 最佳实践

- ✅ 能固定行高就固定：产品设计期争取统一行高（省略号截断 + hover 展开浮层），O(1) 与 O(log n) 的差距在十万行下肉眼可感；
- ✅ 横向也虚拟化：列数超 50 时左右方向同样只渲染可视列（AG Grid 的 column virtualization）；
- ⚠️ 虚拟滚动破坏浏览器的页内查找（Ctrl+F 只能找到已渲染的行）与屏幕阅读器导航——需要自实现表格内搜索，并向辅助技术暴露完整行列语义（`aria-rowcount`）；
- ❌ 不要在虚拟滚动行内用 `position: sticky` 做行内悬浮元素——行 DOM 会被回收重建，sticky 状态错乱；表头 sticky 在滚动容器上做单层即可。

## 64.2 编辑态状态机与脏检查

### 概念解析

单元格编辑的 bug 几乎全是**状态迁移失控**：保存中又点了编辑、校验失败后 UI 卡在转圈、网络错误后草稿丢失。把单元格建模为显式状态机，非法迁移直接抛错：

```text
view ──点击──→ editing ──提交──→ validating ──通过──→ saving ──成功──→ view
                 │                    │                 │
                 └──Esc──→ view       └──失败──→ error ←┘
                                                │
                                          修改重试 / 放弃
```

三条设计纪律：

1. **saving 态禁止再进 editing**：保存请求在途时用户又双击编辑，响应回来时会把新输入冲掉。状态机直接拒绝该迁移，UI 上表现为保存中单元格锁定；
2. **error 态保留草稿**：校验失败/网络失败都要保住用户输入，error → editing 是「改完重试」，error → view 是「放弃修改」——放弃要有二次确认；
3. **状态在数据层不在 DOM**：React/Vue 重渲染、虚拟滚动回收行 DOM，都不应丢失编辑态——状态以 `(rowId, colKey)` 为键存在表格 store，与 DOM 生命周期解耦。

**脏检查与增量提交**：批量编辑场景（改 200 行再统一点保存）只提交脏格子。实现要点：首次编辑时快照原值，draft 与原值 `Object.is` 对比，**改回原值的不算脏**（A→B→A 不提交）。提交成功后基线推进（draft 转正），失败则草稿保留。这套机制与 38 册表单提交管道的脏检查是同型设计。

### 完整代码示例

```typescript
// 文件: examples/64-02-cell-editor.ts（核心节选）
const TRANSITIONS: Record<CellState, CellState[]> = {
  view: ["editing"],
  editing: ["validating", "view"],
  validating: ["saving", "error"],
  saving: ["view", "error"],      // 在途时不允许回 editing
  error: ["editing", "view"],
};
class DirtyTracker {
  dirtyEntries() {
    // 只产出 Object.is(原值, 草稿) 为 false 的格子;A→B→A 自动净除
  }
}
```

> 运行方式：`npx tsx examples/64-02-cell-editor.ts`（状态机合法/非法迁移、脏检查净除、提交基线推进、TSV 粘贴填充，共 12 组硬断言）。

### 最佳实践

- ✅ 一行一个「行级状态」比一格一个状态省内存：同行多格编辑合并为行草稿；
- ✅ 撤销栈（45 册）以「格子变更」为最小单位，Ctrl+Z 逐格回退；
- ❌ 不要在失焦（blur）时静默提交——用户切窗口查资料回来发现值被改了一半；失焦只暂存草稿，提交永远是显式动作（回车/勾选/保存按钮）。

## 64.3 Excel 式交互：键盘导航与粘贴填充

### 概念解析

B 端表格的真实用户是**把 Excel 当母语的人**。交互对标清单：

| 交互 | Excel 行为 | 表格实现要点 |
| --- | --- | --- |
| 方向键/Tab | 移动活动单元格 | 焦点模型以 (row, col) 管理，虚拟滚动时先滚动到再聚焦 |
| Enter | 确认并下移 | editing 态确认 = 提交 + 焦点下移一行 |
| Esc | 取消编辑 | editing → view，丢弃草稿 |
| F2 / 双击 | 进入编辑 | 与单击选中区分 |
| Ctrl+C/V | 复制粘贴矩形区域 | 剪贴板是 TSV 格式，粘贴按矩形填充 |
| 填充柄拖拽 | 右下角拖出序列/复制 | 识别拖拽方向，序列填充（1,2,3…）或值复制 |

**粘贴是投入产出比最高的功能**。剪贴板从 Excel 复制出来的是 TSV（制表符分隔列、换行分隔行），解析有三个坑：Windows 的 CRLF 归一、复制器自带的末尾换行要剥离（否则多出一空行）、单元格内换行在 Excel 里会带引号包裹（完整实现要处理引号转义）。填充语义：以活动单元格为锚点，数据矩形向右下铺开；行不够时按产品语义决定自动追加行或截断，列越界一律截断。

类型转换是粘贴的另一半：TSV 全是字符串，`"123"` 要进数字列、`"2024-01-01"` 要进日期列——用列定义里的解析器逐格转换，转换失败的格子标红进 error 态（64.2 状态机复用），不阻塞其他格子。这一层与 33 册 Zod 的边界校验天然衔接。

### 完整代码示例

```typescript
// 文件: examples/64-02-cell-editor.ts（核心节选）
function parseTSV(text: string): string[][] {
  return text.replace(/\r\n?/g, "\n").replace(/\n$/, "")
    .split("\n").map((line) => line.split("\t"));
}
// 锚点矩形填充：行可扩展,列越界截断
function pasteRegion({ anchor, data, maxCol, rowCount, extendRows }): CellKey[] { /* ... */ }
```

> 运行方式：`npx tsx examples/64-02-cell-editor.ts`

### 最佳实践

- ✅ 粘贴前预览影响范围（高亮将被覆盖的矩形区域），大批量覆盖给确认弹窗；
- ✅ 复制时带表头可选：很多用户要的就是「连表头一起拷给同事」；
- ⚠️ 虚拟滚动下粘贴的目标行可能未渲染——操作数据层而非 DOM，填充后滚动到受影响区域起点；
- ❌ 不要忽略只读列：粘贴矩形覆盖到只读列（如 ID）时跳过该列并提示，静默写入只读列是数据事故。

## 64.4 校验与增量提交

### 概念解析

表格校验的三个层级，成本和体验各不相同：

| 层级 | 时机 | 成本 | 拦截力 |
| --- | --- | --- | --- |
| 单元格级 | 单格提交时（回车/失焦显式提交） | 低 | 格式错误就地拦截 |
| 行级 | 行内所有格子完成时 | 中 | 跨字段约束（开始日期 < 结束日期） |
| 表级 | 批量提交前 | 高 | 业务规则（合计=100%、唯一性） |

**校验失败的可视化要支持「跳到第一个错误」**：200 行批量提交返回 15 个错误，用户不该自己滚动找——提供错误导航（上一个/下一个），点击直接滚动定位到错误单元格并进入 editing 态。虚拟滚动下这意味着先计算目标行偏移、滚动、等渲染完成、再聚焦——数据层 focus 队列按序执行。

批量提交的管道设计（与 38 册表单管道同型）：`收集脏格子 → 表级校验 → 类型转换 → 增量提交（只发脏数据）→ 逐格确认`。服务端返回逐格结果（部分成功是常态），成功的格子基线推进，失败的进 error 态附服务端消息。增量提交的价值在并发编辑场景：只发改过的格子，别人同时改的其他行不受影响，冲突面最小。

### 最佳实践

- ✅ 校验规则用 Zod schema 声明式定义（33 册），单元格/行/表三级复用同一套 schema 片段；
- ✅ 服务端错误逐格映射回来，格式 `{ rowId, colKey, message }[]`，前端按键入 error 态；
- ⚠️ 批量提交中编辑其他行要小心：提交快照与当前草稿分离，在途期间新编辑进入下一批次；
- ❌ 不要整表回重拉刷新来「同步服务端状态」——200 行编辑后全表闪烁 + 滚动位置丢失是体验灾难，逐格确认即可。

## 64.5 自测题

<details>
<summary><b>1. 【基础】虚拟滚动的基本三要素是什么？overscan 的作用与代价是什么？</b></summary>

三要素：总高占位（撑起滚动条让滚动比例正确）、窗口计算（只渲染视口附近的行）、偏移定位（窗口内行用 transform/padding 顶到正确位置）。overscan 是视口外多渲染的行数：作用是防快速滚动白屏——浏览器滚动事件与 JS 渲染之间有时差，缓冲区先顶上。代价是内存与渲染成本线性增加，典型值 3-10 行，触屏惯性滚动场景取大值。
</details>

<details>
<summary><b>2. 【基础】动态行高为什么要用前缀和 + 二分，不能直接累计遍历吗？</b></summary>

直接遍历累计是 O(n)——每次滚动事件都扫一遍，十万行下每帧都卡。前缀和数组 offsets[i] 记录第 i 行顶部偏移，「第一个底部偏移 > scrollTop 的行」是单调序列上的查找问题，二分 O(log n) 解决。滚动是每帧触发的高频事件，从 O(n) 降到 O(log n) 是能不能用的差别。行高变化时增量更新受影响之后的前缀和即可，不必全量重算。
</details>

<details>
<summary><b>3. 【基础】为什么单元格 saving 状态要禁止迁移到 editing？不放行会发生什么？</b></summary>

保存请求在途时用户双击进入编辑，用户开始输入新值；此时保存响应返回，把服务端确认的旧值写回单元格——用户正在输入的新值被冲掉，或 UI 显示与内部状态分裂。状态机拒绝 saving → editing 迁移，配合 UI 上保存中锁定（灰底/spinner），把竞态在状态层消灭。这是「状态机显式化」价值的典型体现：不用状态机，这个 bug 以「偶发数据被覆盖」的形式出现，排查成本极高。
</details>

<details>
<summary><b>4. 【进阶】脏检查为什么「改回原值不算脏」（A→B→A）？实现上要注意什么？</b></summary>

用户把价格 100 改成 120 又改回 100，语义上这一格没有变化，提交它是浪费——且并发场景下会与他人对同格的真实修改产生伪冲突。实现：首次编辑时快照原值入 original 表，每次输入更新 draft 表，dirtyEntries 只产出 Object.is(original, draft) 为 false 的键。注意：① Object.is 对 NaN 与 -0 的语义与 === 不同，数值列用 Object.is 更稳；② 对象/数组值要做深比较或序列化比较，引用不等不代表内容不等；③ 提交成功后 draft 转正为新的 original（基线推进），不能清空 original 否则下次编辑失去对照。
</details>

<details>
<summary><b>5. 【进阶】虚拟滚动与编辑态为什么必须解耦？解耦的具体做法是什么？</b></summary>

虚拟滚动会回收视口外行 DOM 并复用（或销毁重建）。如果编辑态（草稿值、校验错误）存在 DOM 或组件实例上，滚动出去再回来编辑态就丢了。解耦做法：编辑状态以 (rowId, colKey) 为键存在表格数据层 store，行组件只是 store 的渲染投影——行滚出视口 DOM 销毁，滚回来从 store 重新水合。同理，错误高亮、选中态、展开态都必须数据层化。判定标准：任何「滚动出去再回来还在」的状态，都不许存在 DOM 上。
</details>

<details>
<summary><b>6. 【进阶】Excel 粘贴的 TSV 解析有哪些坑？类型转换失败应该怎么处理？</b></summary>

解析三坑：① CRLF/LF 换行归一（Windows/Mac 混源）；② 复制器自带末尾换行要剥离，否则多出空行覆盖数据；③ 单元格内含换行时 Excel 用引号包裹（"line1\nline2"），完整解析要处理引号状态机。类型转换：TSV 全是字符串，按列定义的解析器（数字/日期/枚举）逐格转换。失败处理原则是不阻塞：失败格进 error 态标红、附原因，其余格子正常填充；全部失败才整体回滚。最忌「一格格弹窗报错」——粘贴 100 行弹 30 个窗是反人类设计。
</details>

<details>
<summary><b>7. 【挑战】设计 10 万行 × 100 列的可编辑表格技术方案，要求编辑/粘贴/校验全支持，给出分层架构。</b></summary>

五层设计：① 数据层——行数据存外部 store（不入组件树），编辑态/选中态/错误态以 (rowId, colKey) 键值存储；② 虚拟化层——行列双向虚拟滚动，行高固定优先，动态行高用前缀和 + 二分 + 锚定补偿；③ 渲染层——行组件 memo 化，格子用 data 属性 + 事件代理而非每格绑定监听器，DOM 节点复用池；④ 交互层——焦点模型 (row,col) 数据化，键盘导航/TSV 粘贴/填充柄都操作数据层后同步滚动；⑤ 提交层——DirtyTracker 脏检查（A→B→A 净除）+ Zod 三级校验 + 增量提交逐格确认。性能预算：渲染窗口 ≤ 50 行 × 20 列，滚动帧预算 16ms 内窗口计算 + diff，大数据操作（排序/筛选）下沉 Worker（18 册）。组件库自研到这个量级才划算，否则在 AG Grid 企业版与 VxeTable 之间按预算选型。
</details>

<details>
<summary><b>8. 【挑战】多人同时编辑同一张服务端表格（非协同编辑，各自提交），前端如何最小化冲突？</b></summary>

四层防线：① 增量提交——只发脏格子而非整行整表，冲突面从行级缩到格级；② 版本随行——每行带 version，提交带 baseVersion，服务端发现版本漂移返回该格最新值（56 册冲突处理同型）；③ 冲突呈现——失败格进 error 态并展示「服务端当前值 vs 你的提交值」双栏，给「采用服务端 / 强制覆盖 / 再编辑」三选项，绝不静默覆盖；④ 变更推送——他人提交成功的格子通过 WS 推送到本地，视口内直接更新并闪烁提示，视口外数据层更新、滚动到时自然呈现；正在编辑的格子收到他人推送不打断编辑，只在格角标提示冲突酝酿中。核心思想与 56 册离线同步一致：基线版本 + 幂等 + 冲突三选一。
</details>

## 64.6 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 万行直接全量渲染 | 万级 DOM 卡死滚动 | 虚拟滚动：总高占位 + 窗口渲染 + overscan |
| 2 | overscan 设为 0 | 快速滚动白屏 | 视口外多渲 3-10 行缓冲 |
| 3 | 动态行高用遍历累计定位 | 滚动每帧 O(n)，十万行卡死 | 前缀和 + 二分 O(log n) |
| 4 | 忽略滚动锚定 | 上方行变高把用户视线推走 | 视口上方行高变化时 scrollTop 等量补偿 |
| 5 | 编辑态存在 DOM/组件实例 | 虚拟滚动回收后编辑内容丢失 | 编辑态以 (rowId,colKey) 存数据层 store |
| 6 | saving 中允许再编辑 | 保存响应冲掉用户新输入 | 状态机拒绝 saving→editing，UI 锁定 |
| 7 | 校验失败丢草稿 | 用户输入付诸东流 | error 态保草稿，修改重试/显式放弃 |
| 8 | 失焦静默提交 | 切窗口查资料回来值被改 | 失焦只存草稿，提交显式触发 |
| 9 | 脏检查不处理改回原值 | A→B→A 伪提交，与他人修改伪冲突 | Object.is 对比原值，回改自动净除 |
| 10 | TSV 不处理 CRLF 与末尾换行 | Windows 粘贴错位、多一空行 | 换行归一 + 末尾换行剥离 |
| 11 | 粘贴直写 DOM | 虚拟滚动下目标行未渲染丢数据 | 操作数据层，填充后滚动到锚点 |
| 12 | 粘贴覆盖只读列 | ID 列被静默篡改 | 矩形内跳过只读列并提示 |
| 13 | 类型转换失败整批回滚 | 100 行粘贴因 1 格全废 | 逐格 error 标红不阻塞，全部失败才回滚 |
| 14 | 批量提交整表回拉刷新 | 全表闪烁 + 滚动位置丢失 | 逐格确认基线推进，失败格进 error |
| 15 | 虚拟滚动忽略辅助技术 | Ctrl+F 失效、读屏器迷路 | 自实现表内搜索 + aria-rowcount 完整语义 |

---

> **可编辑表格速查**：虚拟滚动三要素 + 前缀和二分（64.1）→ 编辑状态机五态 + 脏检查净除（64.2）→ TSV 粘贴矩形填充（64.3）→ 三级校验 + 增量提交逐格确认（64.4）。记住判定标准：任何「滚动出去再回来还在」的状态都不许存在 DOM 上。[返回总目录](./README.md)
