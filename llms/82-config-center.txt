## 82.1 配置中心的三层模型：全局 / 租户 / 用户

### 概念解析

企业 SaaS 的配置天然分三层：

| 层级 | 谁设置 | 例子 | 覆盖范围 |
| --- | --- | --- | --- |
| 全局 global | 平台运维 | 默认主题、上传大小上限、功能总开关 | 所有租户 |
| 租户 tenant | 租户管理员 | 租户主题、租户级功能开关、品牌 Logo | 该租户所有用户 |
| 用户 user | 终端用户 | 个人语言、时区、界面密度 | 仅该用户 |

合并优先级：**user > tenant > global**。但有一个关键陷阱——**对象类型字段要深合并，不能整体覆盖**。

比如 `features` 字段：全局开了 `{a:true, b:false, c:true}`，租户只改了 `b:true`，用户只改了 `c:false`。如果整体覆盖，租户那层会把 `a` 和 `c` 覆盖掉。正确做法是每层只覆盖自己显式设置的 key，其余继承上层。

另一个陷阱：**`undefined` 和 `null` 语义不同**。`undefined` 表示"这层不设置，继承上层"；`null` 表示"这层显式清空"。合并时 `undefined` 要跳过，`null` 要生效。

### 完整代码示例

```ts
// 文件: examples/82-01-config-center.ts（节选：三层合并）
export function mergeConfig(layers: ConfigLayers): AppConfig {
  const merged: any = { ...layers.global };
  for (const layer of [layers.tenant, layers.user]) {
    for (const key of Object.keys(layer) as (keyof AppConfig)[]) {
      const val = (layer as any)[key];
      if (val === undefined) continue; // undefined = 不覆盖
      if (typeof val === "object" && !Array.isArray(val)) {
        merged[key] = { ...(merged[key] || {}), ...val }; // 深合并
      } else {
        merged[key] = val;
      }
    }
  }
  return merged as AppConfig;
}
```

> 运行方式：`npx tsx examples/82-01-config-center.ts`

### 应用实践

- **配置 Schema 要校验**：用 [Zod](./33-zod.md) 定义配置的类型和约束，下发到前端前做校验，防止后台配错导致前端崩溃；
- **敏感配置不下发前端**：API Key、数据库连接串这类配置只存服务端，前端配置中心只放 UI 相关和功能开关；
- **配置与代码分离**：不要把功能开关硬编码在 `if (tenantId === 'xxx')` 里，全部走配置中心，否则租户多了维护不动。

## 82.2 配置的下发、缓存与启动门禁

### 概念解析

配置下发的标准流程：

1. **启动时拉取**：应用初始化时请求 `/api/config`，拿到合并后的完整配置；
2. **缓存到本地**：存入 localStorage 或 IndexedDB，下次启动先用缓存渲染，再后台拉新（避免白屏）；
3. **版本校验**：缓存带版本号，拉到新配置时对比版本，有变化才更新；
4. **启动门禁**：如果配置加载失败，不能让应用以"半残"状态运行——要么用上次缓存，要么展示"配置加载失败"的降级页。

### 应用实践

- **首屏用缓存配置渲染**：配置接口慢的时候，用户看到的是上次的配置而不是白屏。后台拉到新配置后热更新；
- **配置加载失败要有兜底**：网络错误时用上次缓存 + 顶部提示"配置可能不是最新"；彻底没缓存时展示降级页并提供重试；
- **配置变更审计**：谁在什么时候改了什么配置，全部记录。配置错误导致的线上事故，审计日志是第一排查线索。

## 82.3 特性开关与灰度发布

### 概念解析

特性开关（Feature Flag）是配置中心最常用的能力——控制某个功能对哪些用户可见。灰度发布的核心是**按用户 ID 稳定分桶**：

- 同一个用户永远落在同一个桶（哈希取模），刷新页面、换设备都不变；
- 比例从 1% → 10% → 50% → 100% 逐步放大，观察监控无异常再全量；
- 白名单用户（内部测试、VIP）无论比例都直接命中。

判定优先级：`enabled === false` → 直接关闭 > 白名单 → 直接命中 > 比例分桶。

### 完整代码示例

```ts
// 文件: examples/82-01-config-center.ts（节选：特性开关）
export function isFeatureOn(flag: FeatureFlag, userId: string): boolean {
  if (!flag.enabled) return false;
  if (flag.whitelist?.includes(userId)) return true;
  if (flag.rolloutPercentage === undefined || flag.rolloutPercentage >= 100) return true;
  if (flag.rolloutPercentage <= 0) return false;
  const hash = stableHash(userId);
  return (hash % 100) < flag.rolloutPercentage;
}
```

### 应用实践

- **哈希要稳定且均匀**：用用户 ID 的字符串哈希（不要用随机数），保证同一用户每次结果一致。哈希算法要分布均匀，避免大量用户挤在同一个桶；
- **灰度比例只增不减**：上线后比例从低到高逐步放。如果要回滚，直接 `enabled: false` 关闭，不要把比例从 50 调回 10——因为哈希分桶不变，调回比例只会让一部分用户突然用不了，体验割裂；
- **开关要及时清理**：功能全量上线稳定后，把特性开关从代码里删掉。遗留的开关会让代码充满 `if (flag)` 分支，维护成本越来越高。

## 82.4 配置变更实时生效与版本回滚

### 概念解析

配置中心不是"改了重新部署"，而是**运行时动态生效**。实现方式：

- **发布-订阅**：前端订阅配置变更事件（SSE 或 WebSocket），配置中心发布新版本时推送通知，前端热更新；
- **版本链**：每次配置变更产生一个新版本，带变更人、变更时间、变更说明。版本历史可查、可回滚；
- **回滚产生新版本**：回滚不是"删除新版本"，而是"把旧版本的内容重新发布为新版本"，这样回滚操作本身也留痕，审计完整。

### 完整代码示例

```ts
// 文件: examples/82-01-config-center.ts（节选：版本与回滚）
export class ConfigCenter {
  publish(config: AppConfig, by: string, changelog: string): ConfigVersion {
    const v = { version: this.versions.length + 1, config: { ...config }, changedBy: by, changedAt: Date.now(), changelog };
    this.versions.push(v);
    this.current = { ...config };
    this.listeners.forEach((fn) => fn(this.current)); // 通知订阅者
    return v;
  }

  rollback(version: number, by: string): ConfigVersion {
    const target = this.versions.find((v) => v.version === version);
    if (!target) throw new Error(`版本 ${version} 不存在`);
    return this.publish(target.config, by, `回滚到版本 ${version}`); // 回滚 = 重新发布
  }
}
```

### 应用实践

- **配置变更要灰度**：重要配置变更先推给内部租户/白名单用户验证，再全量推送。直接全量推错配置会影响所有用户；
- **前端订阅要防抖**：配置中心可能短时间内多次推送，前端合并后只应用最后一次，避免中间态闪烁；
- **回滚要快**：配置事故的 MTTR（平均恢复时间）取决于回滚速度。配置中心要提供"一键回滚到上一版本"的能力，而不是让运维手动改配置。

## 82.5 自测题

<details>
<summary><b>1. 【基础】三层配置合并时，对象类型字段为什么要深合并？</b></summary>

如果整体覆盖，租户层只改了 `features.b`，会把全局的 `features.a` 和 `features.c` 覆盖丢失。深合并保证每层只覆盖自己显式设置的 key，其余继承上层。例如全局 `{a:true, b:false, c:true}`，租户 `{b:true}`，合并后 `{a:true, b:true, c:true}`，而不是 `{b:true}`。
</details>

<details>
<summary><b>2. 【进阶】灰度发布为什么要用用户 ID 哈希分桶，而不是随机？</b></summary>

随机分桶会导致用户每次刷新页面结果不同——一会看到新功能一会看不到，体验割裂。用用户 ID 稳定哈希分桶，同一个用户永远落在同一个桶，结果可预期。比例调整时，已命中的用户继续命中，只新增一部分用户，体验平滑。
</details>

<details>
<summary><b>3. 【进阶】为什么回滚要产生新版本而不是删除旧版本？</b></summary>

三个原因：① 审计完整——回滚操作本身也要留痕（谁回滚的、回滚到哪个版本、为什么）；② 不可逆——如果回滚后又想回到回滚前的版本，版本链里还有记录；③ 并发安全——删除版本可能导致其他正在引用该版本的请求出错。所以回滚 = 把目标版本的内容重新发布为新版本。
</details>

<details>
<summary><b>4. 【挑战】特性开关全量上线后为什么要及时删除？</b></summary>

遗留的特性开关会让代码充满 `if (flag)` 分支，每个分支都要测试、维护、排查问题。开关越多，代码的状态空间越大（N 个开关有 2^N 种组合），测试覆盖率和可维护性急剧下降。所以功能全量稳定后，删除开关和它对应的死代码，保持代码简洁。
</details>

## 82.6 本章避坑清单

| 场景 | 高频坑 | 一句话避法 |
| --- | --- | --- |
| 对象配置覆盖 | 租户改一个 feature，全局的其他 feature 全丢 | 对象类型深合并（只覆盖显式设置的 key），不整体覆盖 |
| undefined 语义 | 把"不设置"和"清空"混为一谈 | `undefined` = 不覆盖（继承上层），`null` = 显式清空，合并时跳过 undefined |
| 敏感配置泄露 | 把 API Key、数据库连接串下发到前端 | 前端配置中心只放 UI 配置和功能开关，敏感配置只存服务端 |
| 灰度分桶不稳定 | 用随机数分桶，用户刷新结果变 | 用用户 ID 稳定哈希分桶，同一用户永远同一桶 |
| 灰度回滚方式错 | 把比例从 50 调回 10 来回滚 | 回滚直接 `enabled: false` 关闭，不调比例（比例只增不减） |
| 开关不清理 | 功能全量后开关留在代码里 | 全量稳定后删除开关和死代码，避免状态空间膨胀 |
| 配置变更无审计 | 谁改了配置查不到 | 每次变更记录变更人、时间、变更说明，支持版本历史查询 |
| 回滚不留痕 | 回滚直接覆盖当前版本 | 回滚 = 把旧版本重新发布为新版本，回滚操作本身也进版本链 |
| 首屏白屏 | 等配置接口返回才渲染 | 启动先用缓存配置渲染，后台拉新配置热更新 |

## 82.7 面试问答

<details>
<summary><b>【L2】配置中心为什么要分全局/租户/用户三层？合并时要注意什么？</b></summary>

**回答框架**：① 三层职责：全局（平台默认）、租户（租户定制）、用户（个人偏好）；② 合并优先级 user > tenant > global；③ 关键注意：对象类型（如 features）要深合并不能整体覆盖，否则租户改一个 feature 会把全局的其他 feature 覆盖掉；④ undefined 和 null 语义不同（undefined=不覆盖，null=清空）。

**评分要点**：三层职责和优先级正确；知道对象要深合并；知道 undefined/null 区别。

**加分项**：提到用 Zod 做配置 Schema 校验；提到敏感配置不下发前端。
</details>

<details>
<summary><b>【L3】一个新功能要灰度上线，从 1% 到 100% 怎么设计特性开关？回滚怎么做？</b></summary>

**回答框架**：① 特性开关三要素：enabled、rolloutPercentage、whitelist；② 分桶用用户 ID 稳定哈希（同一用户永远同一桶），白名单直通；③ 比例从 1%→10%→50%→100% 逐步放大，每步观察监控；④ 回滚直接 enabled=false 关闭，不要把比例调回去（比例只增不减，否则部分用户突然用不了）。

**评分要点**：知道稳定哈希分桶；知道比例逐步放大；知道回滚用 enabled=false。

**加分项**：提到全量稳定后删除开关；提到开关要带变更审计；提到内部测试先走白名单。
</details>

<details>
<summary><b>【L2】配置变更怎么实时生效？为什么回滚要产生新版本？</b></summary>

**回答框架**：① 实时生效：配置中心发布新版本时通过 SSE/WebSocket 推送通知，前端订阅后热更新；② 回滚产生新版本：回滚不是删除旧版本，而是把旧版本内容重新发布为新版本，这样回滚操作本身也留痕（谁回滚的、为什么），且版本链完整可追溯。

**评分要点**：知道发布-订阅推送；知道回滚产生新版本而非删除。

**加分项**：提到前端订阅要防抖（多次推送只应用最后一次）；提到配置变更要先灰度再全量；提到首屏用缓存配置渲染避免白屏。
</details>

<details>
<summary><b>【L3】配置中心把一个错误的配置推给了所有用户，导致页面崩溃，怎么快速恢复？</b></summary>

**回答框架**：① 一键回滚到上一版本（配置中心必须支持）；② 回滚产生新版本推送，前端订阅后自动恢复；③ 事后复盘：为什么配置校验没拦住？为什么没灰度就全量推？④ 改进：配置变更前用 Zod 校验 + 先推白名单/内部租户验证 + 灰度比例逐步放大。

**评分要点**：知道一键回滚是第一动作；知道复盘要找根因（校验缺失、没灰度）。

**加分项**：提到配置变更的 MTTR 指标；提到回滚操作也要审计；提到前端用上次缓存配置兜底。
</details>
