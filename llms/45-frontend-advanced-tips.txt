## 45.1 调试技巧：把问题看清楚

调试的效率不取决于你打了多少 `console.log`，而取决于「从现象到证据」的路径有多短。下面四组技巧的共同点是：**先让证据可复现、可对比、可回放，再谈定位**。

### 45.1.1 console 的五个被低估的能力

多数人只用 `console.log`，但控制台真正的价值在结构化输出：

```js
// 1. 表格：数组对象一眼对齐，还能指定只显示哪些列
console.table(rows, ["sku", "qty", "price"]);

// 2. 分组：把一次请求链路的日志折叠成一组
console.groupCollapsed("结算链路");
console.log("校验库存");
console.log("计算优惠");
console.groupEnd();

// 3. 计时：成对出现，标签必须一致
console.time("renderList");
renderList();
console.timeEnd("renderList");

// 4. 计数：循环/事件里快速确认触发次数
console.count("scroll");
console.countReset("scroll");

// 5. 断言：条件不成立时打印堆栈，但不会中断执行
console.assert(total === expected, "总价对不上", { total, expected });
```

DevTools 控制台还有几个只在控制台里存在的命令，值得记住：

| 命令 | 作用 | 典型场景 |
| --- | --- | --- |
| `$0` / `$1` | 引用当前/上一个在 Elements 面板选中的节点 | 临时改样式、查事件监听 |
| `$_` | 上一次表达式的结果 | 连续加工同一个值 |
| `copy(obj)` | 把对象序列化到剪贴板 | 把现场数据贴进工单 |
| `monitorEvents($0, "click")` | 打印节点事件 | 确认事件是否真的触发、冒泡到哪 |
| `getEventListeners($0)` | 列出节点上注册的监听器 | 排查重复绑定、匿名函数解绑失败 |
| `debug(fn)` / `undebug(fn)` | 给函数下断点 | 第三方库内部函数也能断 |

> ⚠️ 最大的坑：`console.log(obj)` 打印的是**对象引用**，你在控制台展开时看到的是「展开那一刻」的值，不是打印那一刻的值。要留证据必须 `structuredClone(obj)` 或 `JSON.parse(JSON.stringify(obj))` 做快照——示例 `45-01` 专门演示了这个差异。

### 45.1.2 断点四件套：条件、日志、DOM、请求

只会按 F8 单步，等于只用了一半的调试器。四类断点各有明确分工：

1. **条件断点**：右键行号 → Add conditional breakpoint，填 `user.id === "u-42"`。循环十万次只停一次，比单步高效得多。
2. **日志点（Logpoint）**：不暂停，只往控制台打印表达式，例如 `"order=" + order.id + " status=" + status`。适合高频路径，避免断点把时序打乱。
3. **DOM 断点**：Elements 面板右键节点 → Break on → subtree modifications / attribute modifications / node removal。专治「谁把我节点删了/改了」。
4. **请求断点**：Sources → XHR/fetch Breakpoints，按 URL 片段拦截。能拿到发起请求的完整调用栈，比在 Network 面板猜谁调的更直接。

另外两个习惯能省大量时间：

- **Blackbox Script**：把 node_modules 或框架源码加入黑盒，单步时自动跳过，调用栈只留业务代码；
- **`debugger` 要有开关**：写成 `if (window.__DEBUG__) debugger;`，否则生产环境一开控制台就断住。

### 45.1.3 网络面板的三个救命功能

| 功能 | 怎么用 | 解决什么问题 |
| --- | --- | --- |
| Copy as fetch | 请求右键 → Copy → Copy as fetch | 把线上请求原样搬到控制台重放，保留 header/token/body |
| Block request URL | 请求右键 → Block request URL | 模拟 CDN/接口挂掉，验证降级与重试是否真的生效 |
| Local Overrides | Sources → Overrides → 选本地目录 | 不改后端就改响应/JS/CSS，复现边界数据（空列表、超大数、500） |

排查顺序建议固定为：**Network 看请求是否发出 → Response 看服务端返回 → Timing 看卡在哪一段 → Console 看前端异常**。不要一上来就翻代码。

### 45.1.4 性能与内存：从火焰图到三快照

- **Performance 面板**：录制一次交互，先看 Main 轨道有没有超过 50ms 的长任务；再用 Bottom-Up 按「自身耗时」排序，找真正的热点函数，而不是被调用栈吓到。
- **Coverage**：Cmd/Ctrl + Shift + P → Show Coverage，录一次页面，红色是未执行的 JS/CSS。首屏加载了整包组件库时，这个面板最有说服力。
- **Rendering**：打开 Paint flashing / Layout Shift Regions / Frame Rendering Stats，肉眼确认「哪里在重绘、哪里在抖」。
- **Memory 三快照法**：操作前拍一张 → 执行一次可疑操作 → 再拍一张 → 对比两张快照的 Delta。重点看 Detached DOM tree 与持续增长的对象；只拍一张快照几乎看不出泄漏。

长任务与 INP 的归因可以结合 [25.9 性能度量](./25-prod-ready-web-apis.md) 里的 `PerformanceObserver`；本册不再重复采集代码。

## 45.2 线上自愈：版本、缓存与失败恢复

发版之后最危险的状态不是「新版本有 bug」，而是**用户停在一个半旧半新的页面里**：HTML 是旧的、chunk 已被覆盖、接口契约又变了。下面四件事能把这类故障收敛成「最多刷新一次」。

### 45.2.1 版本检测：别让用户永远停在旧页面

构建时生成一个 `version.json`（或 `/api/version`），内容至少包含 `buildId`、`version`、`releasedAt`。页面侧做三件事：

```ts
// 轮询：5 分钟一次 + 页面重新可见时补一次
const res = await fetch("/version.json", { cache: "no-store" });
const next = await res.json();
if (next.buildId !== current.buildId) showUpdateToast();
```

三个细节决定它是否可靠：

- **`cache: "no-store"`** 和 CDN 的 `Cache-Control: no-store` 必须同时有，否则你永远读到缓存里的旧版本；
- **用 `buildId` 判断，不要用 semver**：同一次发版的多个构建号、回滚、CDN 边缘节点不同步，semver 都不够用；
- **只提示，不自动刷新**：用户可能正在填表单。把「刷新」交给用户确认，或者在有未保存内容时先存草稿。

### 45.2.2 chunk 加载失败：只自动刷新一次

路由懒加载的 chunk 文件名带 hash，发版后旧 hash 会被清掉，用户点击旧入口就会 `Failed to fetch dynamically imported module`。处理分两层：

```ts
// Vite 会把预加载失败派发成 vite:preloadError
window.addEventListener("vite:preloadError", (event) => {
  event.preventDefault();
  if (reloadOnce()) location.reload();
});

// 动态 import 也要兜底（不是所有构建器都有 preloadError）
import("./OrderList.vue").catch((error) => {
  if (isChunkLoadError(error) && reloadOnce()) location.reload();
  else showFatalError(error);
});
```

`reloadOnce()` 必须带**冷却时间 + 持久化标记**（`sessionStorage`），否则坏版本会让页面无限刷新。经验值：10 秒冷却；同一会话最多自动刷新 2 次；仍失败就展示「加载失败，请稍后重试」的兜底页，而不是继续刷。

### 45.2.3 Service Worker 更新：等待、提示、接管

有 SW 的站点还多一层版本：新 SW 装好后默认停在 `waiting`，不会立刻接管。推荐流程（与 [18.5.6](./18-worker-messaging.md) 一致）：

1. 监听 `registration.updatefound`，发现 `installed` 且 `navigator.serviceWorker.controller` 存在 → 说明有 waiting 版本；
2. 提示用户「有新版本」，用户确认后 `registration.waiting.postMessage({ type: "SKIP_WAITING" })`；
3. SW 内 `self.skipWaiting()`，页面监听 `controllerchange` → **只刷新一次**（用一个布尔标记防止重复触发）。

不要无条件 `skipWaiting`：新旧页面混跑时，旧页面可能继续请求已被新 SW 删掉的缓存，出现「部分资源 404」。另外注册时加 `updateViaCache: "none"`，避免浏览器用 HTTP 缓存挡住 `sw.js` 的更新检查。

### 45.2.4 缓存头矩阵：hashed 资源与 HTML 分开

| 资源 | 推荐策略 | 原因 |
| --- | --- | --- |
| HTML / `version.json` | `no-cache`（或 `max-age=0, must-revalidate`） | 每次都要回源确认，否则用户永远拿不到新入口 |
| 带 hash 的 JS/CSS/图片 | `public, max-age=31536000, immutable` | 文件名变了就是新资源，可以放心长缓存 |
| 接口 GET | `private, no-cache` 或业务自定义短 TTL | 用户态数据不能被 CDN 公共缓存 |
| 接口写操作 | `no-store` | 防止中间层缓存 POST 响应 |

不要把「HTML 不缓存」理解成「所有资源都不缓存」：真正的最佳实践是**入口短缓存、带指纹的静态资源长缓存**。发版异常时，回滚 HTML + version.json 即可，旧 chunk 还在 CDN 上。

### 45.2.5 完整示例：版本守卫

```ts

class UpdateGuard {
  check(current: VersionInfo, fetcher: () => Promise<VersionInfo>):
    Promise<"same" | "update" | "throttled" | "error">;    // 轮询节流 + 更新判断
  canReloadOnChunkError(error: unknown, now?: number): boolean; // 冷却期内拒绝刷新
}
```

> 运行方式：`npx tsx examples/45-02-version-guard.ts`（验证更新检测、轮询节流、chunk 刷新只放行一次，以及普通业务错误不会触发刷新）。

**边界**：自动刷新会丢失未提交的表单与滚动位置。正确做法是把「刷新」做成用户可见的提示，或在刷新前把草稿写入 `sessionStorage`；对多标签页场景，最好只让一个标签页执行刷新，其余标签页收到 `BroadcastChannel` 消息后再提示。

## 45.3 交互手感：乐观更新、撤销与快捷键

用户感知的「快」，往往不是接口快，而是**界面先响应**。这一节处理三个高频手感问题：操作要不要等、错了能不能退、键盘能不能用。

### 45.3.1 乐观更新的三种状态

一次乐观更新要显式维护三种状态，而不是「先改再祈祷」：

| 状态 | UI 表现 | 数据 |
| --- | --- | --- |
| `pending` | 立即显示成功态 + 轻微 loading/禁用 | 本地快照 + 请求中 |
| `confirmed` | 去掉 loading，以服务端返回为准 | 服务端版本号/更新时间 |
| `rolled-back` | 恢复操作前快照 + 错误提示 | 回到 `before` |

三个实现要点：

1. **同步应用乐观状态**：不要放在 `await` 之后，否则用户仍要等一个 tick 才看到变化；
2. **串行提交**：同一实体的并发写会让 `before` 快照互相污染；用队列串行，或给每次写带 `updatedAt` 做冲突检测；
3. **回滚要有守卫**：只有「当前状态仍是本次乐观结果」时才回滚，否则会把后来者的修改一起抹掉。

React 19 的 `useOptimistic` 已经封装了这套语义（见 [4.1](./04-frameworks.md)）；框架无关的场景可以按示例 `45-03` 的 `OptimisticStore` 写。

### 45.3.2 撤销/重做栈

撤销有两种实现：

- **命令模式**：记录 `do/undo` 两个函数，内存小、适合富文本/画布；
- **快照模式**：每次成功操作后存整份状态，实现简单、适合表单/列表这类小状态。

无论哪种，都要遵守三条语义：

- **只记录成功操作**：失败/回滚的操作不能进历史，否则用户撤销时会「撤到一个从未存在过的状态」；
- **新操作清空 redo 栈**：这是所有编辑器的标准行为；
- **限制历史长度**：`past` 超过 50 条就丢弃最旧的，避免长会话内存增长。

高频输入（打字、拖拽）还要做**合并**：300ms 内的连续修改算一个事务，否则用户要按几十次撤销才能退回一句话。

### 45.3.3 快捷键作用域

快捷键系统最容易出的不是「没绑上」，而是「绑太多」：输入框里按 `/` 触发了全局搜索、弹窗里按 `Esc` 同时关了弹窗和页面。最小实现要包含：

```ts
type Shortcut = {
  combo: string;              // 用 event.code 还是 event.key 要统一
  when?: () => boolean;       // 作用域：弹窗打开、焦点不在输入框
  run: (event: KeyboardEvent) => void;
};

// 统一入口：只有真正处理了才 preventDefault
if (!isTyping(event.target) && match(event, shortcut)) {
  event.preventDefault();
  shortcut.run(event);
}
```

三个约定：

- **优先 `event.code`**：`event.key` 受键盘布局与输入法影响（`/` 在德语键盘上是 `Shift+7`）；
- **输入框/可编辑区域默认不劫持**，除非显式声明 `allowInInput`；
- **`Esc` 只关最上层**：用栈管理弹层，别让每个组件都监听全局 `Esc`。

可访问性底线见 [15 册](./15-accessibility-i18n.md)：快捷键必须可发现（菜单/提示里写出来），并且不能是唯一操作路径。

### 45.3.4 拖拽的 4px 阈值与指针捕获

一个不抖的拖拽排序，核心只有四步：

1. `pointerdown` 记录起点，**不要立刻进入拖拽**；
2. 指针移动超过 **4px** 才判定为拖拽，避免点击被误判；
3. 调用 `element.setPointerCapture(event.pointerId)`，指针移出元素甚至移出窗口仍能收到事件；
4. 拖动时用占位元素撑住布局，松手再提交顺序；同时提供「上移/下移」按钮作为键盘替代。

```css
.drag-handle {
  touch-action: none; /* 阻止移动端拖拽时页面滚动 */
  cursor: grab;
}
```

拖拽的动画细节（FLIP、列表重排）见 [29 册](./29-rxjs.md) 与 [10.3](./10-browser-rendering.md)，这里只强调边界：**没有键盘替代的拖拽排序，等于把一部分用户挡在门外**。

### 45.3.5 完整示例：乐观更新与撤销栈

```ts
// 文件: examples/45-03-optimistic-undo.ts
class OptimisticStore {
  get(): State;
  replace(next: State): void;                 // 撤销/重做回放用
  mutate(options: {
    optimistic: (state: State) => State;      // 同步应用，UI 立刻变化
    commit: () => Promise<State>;             // 串行提交，服务端返回即权威
  }): Promise<State>;                         // 失败回滚到 before
}

class UndoStack<S> {
  push(next: S): void;                        // 只记录成功状态
  undo(): S;                                  // 弹出 past，压入 future
  redo(): S;                                  // 反向回放
  readonly canUndo: boolean;
  readonly canRedo: boolean;
}
```

> 运行方式：`npx tsx examples/45-03-optimistic-undo.ts`（验证成功入栈、失败回滚、撤销/重做，以及新操作清空 redo 栈）。

**边界**：乐观更新只适合「失败可回滚、冲突可检测」的操作。支付、扣库存、发消息这类**不可逆写**不要乐观，应该用「提交中」状态 + 幂等键；否则用户看到成功、服务端却失败，比慢一点更糟。

## 45.4 CSS 技巧：少写 JS 的现代 CSS

这一节的原则是：**能用声明式 CSS 解决的，就不要用 JS 计算坐标和尺寸**。下面六个技巧都有明确的浏览器支持边界，统一用 `@supports` 做渐进增强，不支持时退回可用的旧方案。

### 45.4.1 Anchor Positioning：浮层跟着锚点走

以前做 tooltip/dropdown，要用 JS 读 `getBoundingClientRect()`、监听滚动与 resize、再处理视口翻转。CSS Anchor Positioning 把这套逻辑下沉给浏览器：

```css
.trigger {
  anchor-name: --invite;
}

.tip {
  position: absolute;
  position-anchor: --invite;
  top: anchor(bottom);
  left: anchor(left);
  margin-top: 8px;
}

/* 不支持时退回普通绝对定位，至少位置可用 */
@supports not (position-anchor: --invite) {
  .tip { top: calc(100% + 8px); left: 0; margin-top: 0; }
}
```

**边界**：截至 2026 年，Chromium 支持最完整，Safari/Firefox 仍在推进；因此它适合「增强体验」而不适合「唯一交互路径」。关键浮层仍要保证在降级方案下可点、可读。示例 `45-04` 同时给了支持与降级两套 CSS。

### 45.4.2 @scope：样式作用域不再靠长类名

BEM 的本质是用命名约定模拟作用域。`@scope` 让浏览器真正按 DOM 子树隔离：

```css
@scope (.card) {
  .badge { color: var(--brand); }
  :scope { border-color: var(--line); }
}
```

它解决两个老问题：组件内的 `.badge` 不会污染外部；你也不需要给每个选择器加 `.card-` 前缀。**边界**：老浏览器会忽略整段 `@scope`，所以基础样式仍要先写一份普通选择器版本。

### 45.4.3 light-dark() 与 field-sizing：两行 CSS 省两段 JS

```css
:root {
  color-scheme: light dark;
  --bg: light-dark(#f8fafc, #0b1220);
}

textarea {
  field-sizing: content;   /* 随内容长高 */
  min-height: 2.6em;
  max-height: 10em;
}
```

`light-dark()` 让主题色跟随 `color-scheme`，不用 JS 判断系统主题；`field-sizing: content` 让 textarea 自动长高，省掉「监听 input → 改 height → 处理滚动条」那套代码。**边界**：`field-sizing` 支持面较窄，必须给 `@supports not` 的固定高度降级；`light-dark()` 也要求先声明 `color-scheme`。

### 45.4.4 hidden="until-found"：可被页内查找的折叠内容

普通 `hidden` 的内容连 Ctrl/Cmd + F 都搜不到；`hidden="until-found"` 会保留在浏览器的查找索引里，命中时触发 `beforematch`：

```html
<p id="faq" hidden="until-found">折叠的帮助说明……</p>
<script>
  faq.addEventListener("beforematch", () => { faq.hidden = false; });
</script>
```

适合 FAQ、帮助中心、长表单里的「展开更多」。**边界**：隐藏期间内容不在无障碍树里；如果它是关键说明，仍要提供显式展开按钮，不能只依赖页内查找。示例 `45-04` 同时演示了手动展开与 `beforematch`。

### 45.4.5 打印样式：把网页变成可交付的文档

打印不是「加个 `@media print` 隐藏导航」就完了，真正影响可读性的是分页与链接：

```css
@media print {
  @page { margin: 12mm; }
  .no-print { display: none !important; }
  section { break-inside: avoid; }       /* 卡片不要被劈成两页 */
  a[href^="http"]::after {               /* 纸面上补出链接地址 */
    content: " (" attr(href) ")";
    font-size: 10pt;
  }
}
```

再加两条：`print-color-adjust: exact` 保留品牌色块（否则浏览器会省墨）、`break-after: page` 控制章节分页。**验证方式只有一个**：用浏览器的「打印预览」逐页看，不要靠猜。

### 45.4.6 content-visibility：长列表只渲染看得见的部分

```css
.row {
  content-visibility: auto;
  contain-intrinsic-size: auto 44px;  /* 给屏外元素一个占位高度 */
}
```

浏览器会跳过屏外元素的布局与绘制，首屏成本大幅下降。**边界**：不要用在上方首屏内容（反而增加切换成本）；必须给 `contain-intrinsic-size`，否则滚动条长度会跳；对需要精确 `offsetTop` 的虚拟滚动，仍需 JS 方案（见 [10.4](./10-browser-rendering.md)）。

```html

<!-- 直接双击打开：锚点定位 + @scope + light-dark + field-sizing
     + hidden="until-found" + content-visibility + 打印样式 -->
```

> 运行方式：用浏览器直接打开 `examples/45-04-css-tricks.html`；点「打印本页」看分页与链接展开，用 Ctrl/Cmd + F 搜索「前庭敏感」验证 `beforematch`。

## 45.5 工程防呆：配置、开关与缓存键

最后一组技巧不直接面向用户，但决定事故率：**配置错了要在启动时炸，而不是在用户点击时炸；开关要稳定，缓存键要可预测**。

### 45.5.1 启动配置校验：一次说清所有问题

运行时配置（`window.__CONFIG__`、`/config.json`）最常见的失败是「少一个字段，页面白屏，控制台只有一句 undefined」。正确做法是：

1. 为每个字段声明校验器（非空字符串、HTTP URL、端口范围……）；
2. **收集全部错误再抛**，不要让用户改一个重启一次；
3. 错误信息里带字段名与收到的值，但**不要打印密钥**；
4. 校验失败就停在启动页，明确告诉运维缺什么。

`readConfig` 的返回值是强类型配置，业务代码不再需要 `as`。**边界**：构建期能注入的配置优先在构建期校验（Vite 的 `import.meta.env` 在构建时就被替换），运行时校验只负责部署差异部分。

### 45.5.2 Feature Flag：稳定分桶 + kill switch

一个可靠的开关至少要有四个字段：

```ts
type Flag = {
  key: string;
  percentage: number;        // 0 = 全关（kill switch），100 = 全开
  allow?: readonly string[]; // 白名单，内部账号先行
  owner?: string;            // 谁负责清理
};
```

分桶**不能用 `Math.random()`**，否则同一用户刷新一次就可能从 A 组跳到 B 组，实验结论全废。用 `hash(flagKey + salt + userId) % 100` 的稳定哈希（示例 `45-05` 用 FNV-1a），保证：

- 同一用户永远落在同一侧；
- 扩量时（10% → 30%）已命中的用户不会掉出去；
- 不同开关用不同 salt，避免「开了 A 的用户必然开 B」的正交性雪崩（见 [43.5](./43-business-scenes.md)）。

**边界**：涉及权限、计费、数据可见性的开关必须在服务端判定，前端 flag 只能控制展示；开关上线时就要约定**清理日期**，否则三年后没人敢删。

### 45.5.3 缓存键：顺序无关、作用域明确

缓存击穿的常见原因是键不稳定：`{page:1,status:"paid"}` 与 `{status:"paid",page:1}` 生成了两个键。正确做法是**稳定序列化**（键排序、嵌套递归），再拼上作用域与版本：

```ts
cacheKey("orders", { page: 1, status: "paid" }, 2);
// orders@v2:{"page":1,"status":"paid"}
```

三条规则：

- **作用域**：多租户/多用户系统必须带 `tenantId`/`userId`，否则 A 用户会读到 B 用户的缓存；
- **版本**：数据结构变更时提升 `version`，老缓存自然失效，不用写迁移；
- **不缓存的东西**：带权限的一次性 token、错误响应（除非明确做负缓存且 TTL 很短）、含密钥的参数。

### 45.5.4 交付前检查：五条能拦住大事故的清单

发版前固定过一遍：

1. **sourcemap** 只上传监控平台，不部署到公网；
2. **`debugger` / 高频 `console.log`** 已剥离（用构建插件或 ESLint 规则）；
3. **`version.json`** 可访问且 `no-store`，HTML 不被 CDN 长缓存；
4. **首屏 chunk** 没有把整包组件库/图表库打进来（用构建分析器看体积）；
5. **关键开关的默认值**是「关闭」：配置服务挂了，功能降级而不是全量放开。

### 45.5.5 完整示例：启动防呆

```ts
// 文件: examples/45-05-config-guard.ts
class ConfigError extends Error { readonly issues: readonly string[]; }

function readConfig<T extends object>(
  raw: Record<string, unknown>,
  schema: { [K in keyof T]: (value: unknown) => value is T[K] },
): T;                                                        // 一次列出全部问题

function stableStringify(value: unknown): string;            // 键排序 + 递归
function cacheKey(scope: string, params: object, version?: number): string;

function isEnabled(flag: Flag, userId: string): boolean;     // 白名单优先 + 稳定分桶
function bucketOf(flagKey: string, userId: string, salt?: string): number;
```

> 运行方式：`npx tsx examples/45-05-config-guard.ts`（验证配置一次报 3 个错、30% 灰度在 5000 个用户上命中约 30%、缓存键与参数顺序无关）。

## 45.6 自测题

1. 为什么 `console.log(obj)` 不能作为事故现场的证据？应该怎么改？

<details><summary>查看答案</summary>

因为它打印的是对象引用，控制台里展开时看到的是「展开那一刻」的值；对象后续被修改，你看到的就不是打印时的状态。用 `structuredClone(obj)` 或序列化后的副本打印，才能固定现场。示例 `45-01` 的 `snapshot()` 就是这个作用。
</details>

2. 页面一直开着，服务端发了新版本。为什么推荐「提示用户刷新」而不是检测到就 `location.reload()`？

<details><summary>查看答案</summary>

用户可能正在填表单、看视频或进行支付，强制刷新会丢失未提交内容，甚至打断关键流程。正确做法是提示 + 让用户确认；如果有未保存草稿，先落盘。自动刷新只适合 chunk 加载失败这种「页面已经不可用」的场景，而且必须有冷却与次数上限。
</details>

3. 乐观更新的回滚为什么不能简单地把字段「取反」？

<details><summary>查看答案</summary>

因为失败的可能不是最后一次操作，期间还可能有别的修改；取反会抹掉后来者的合法变更。正确做法是回到「本次操作前」的快照，并且只在当前状态仍是本次乐观结果时回滚；并发写要串行化或用版本号做冲突检测。
</details>

4. `hidden="until-found"` 和普通 `hidden` 的核心差别是什么？它适合什么场景？

<details><summary>查看答案</summary>

普通 `hidden` 的内容不参与页内查找；`until-found` 会保留在查找索引里，命中时先触发 `beforematch`，页面可以借此展开内容。适合 FAQ、帮助说明这类「默认折叠但希望被搜到」的内容。它不适合关键信息，因为隐藏期间内容不在无障碍树里。
</details>

5. 为什么 Feature Flag 的百分比分桶绝对不能用 `Math.random()`？

<details><summary>查看答案</summary>

随机数每次调用都不同，同一用户刷新页面就可能从实验组跳到对照组，指标无法归因，扩量时也无法保证「已命中的人不掉出去」。必须用稳定哈希（如 `hash(flagKey + salt + userId) % 100`），保证同一用户在同一 salt 下永远落在同一桶。
</details>

## 45.7 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 用 `console.log` 打印对象当证据 | 展开时对象已变，误判现场 | `structuredClone` / 序列化快照后再打印 |
| 循环里无节制 `console.log` | 控制台卡死、日志淹没关键信息 | 用日志点/条件断点，或环形缓冲只留最近 N 条 |
| 生产环境保留 `debugger` | 用户一开控制台页面就断住 | `if (__DEBUG__) debugger;` 或构建期剥离 |
| 版本检测不带 `no-store` | 永远读到 CDN/浏览器缓存的旧版本 | `version.json` 与 fetch 同时禁缓存 |
| 用 semver 判断是否发版 | 回滚、多构建号、CDN 不同步时判断失真 | 以 `buildId` 为准，semver 只做展示 |
| 检测到新版本就强制刷新 | 丢失表单、打断支付 | 提示用户确认；有草稿先落盘 |
| chunk 失败无限自动刷新 | 坏版本让用户陷入刷新死循环 | 冷却时间 + 会话次数上限 + 兜底错误页 |
| 无脑 `skipWaiting` | 新旧页面混跑，旧页面请求已删缓存 | 用户确认后 `SKIP_WAITING` + `controllerchange` 只刷一次 |
| HTML 与 hashed 资源同一缓存策略 | 要么用户拿不到新入口，要么回滚失效 | HTML 短缓存，带 hash 资源长缓存 |
| 乐观更新放在 `await` 之后 | 用户仍要等一个 tick 才看到反馈 | 同步应用乐观状态，再异步提交 |
| 失败时简单取反字段 | 抹掉并发操作，状态错乱 | 回到操作前快照 + 只回滚本次操作 |
| 把失败操作也压入撤销栈 | 撤销到「从未存在过」的状态 | 只记录成功的操作 |
| 快捷键监听全局且不判断焦点 | 输入框里按 `/` 触发搜索、`Esc` 连关多层 | 作用域 + 输入态判断 + 弹层栈 |
| 拖拽不设阈值 | 点击被误判成拖拽，列表乱序 | 4px 阈值 + `setPointerCapture` + 键盘替代 |
| 拖拽样式漏 `touch-action: none` | 移动端拖拽时页面跟着滚 | 拖拽手柄显式声明 `touch-action` |
| 用 `@scope`/Anchor Positioning 当唯一方案 | 不支持浏览器整块样式失效 | `@supports` 降级 + 关键路径不依赖新特性 |
| 打印只用 `display:none` 藏导航 | 卡片跨页断裂、外链无法追溯 | `@page` + `break-inside` + 链接地址展开 |
| 屏外列表直接 `content-visibility` | 滚动条长度跳动、定位错乱 | 配 `contain-intrinsic-size`，首屏不用 |
| 配置校验遇错即抛 | 运维改一个字段重启一次 | 收集全部问题一次性报错 |
| 用 `Math.random()` 做灰度 | 用户分组漂移，实验结论作废 | 稳定哈希分桶 + 白名单 + kill switch |
| 缓存键不排序参数 | 同一语义生成多个键，缓存击穿 | 稳定序列化 + 作用域 + 版本号 |
| 前端 flag 控制权限/计费 | 改个本地存储就能越权 | 安全判定必须放服务端 |
| sourcemap 部署到公网 | 源码与内部接口暴露 | 只上传监控平台，按 release 管理 |
