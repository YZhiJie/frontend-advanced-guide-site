## 67.1 B 端询盘型网站链路：从落地页到线索入库

### 概念解析

询盘（inquiry）是 B 端最典型的「一页网站 + 一套表单」业务：制造业官网、SaaS 官网、展会落地页都长这样。链路只有五段，但每一段都有独立的失败模式：

| 段 | 做什么 | 失败模式 | 谁负责 |
| --- | --- | --- | --- |
| 获客 | SEO / 投放 / 展会二维码 | 渠道归因丢失，投放无法优化 | 前端（UTM 采集）+ 后端（落库） |
| 落地页 | 价值主张 + 信任背书 + 表单 | 首屏慢、移动端表单难填 | 前端 |
| 提交 | 校验、反垃圾、防重复 | 误拦真客户 / 放过机器人 | 前端 + BFF |
| 入库 | 去重、分配、打标 | 同一客户被 5 个销售跟进 | 后端 + CRM |
| 跟进 | SLA、提醒、回收 | 线索躺着没人管 | CRM / 业务系统 |

**框架选型**（先决定「买什么」，再决定「写什么」）：

| 能力 | 可以直接用 | 什么情况必须自研 |
| --- | --- | --- |
| 表单渲染 | Ant Design ProComponents、Formily、react-hook-form | 字段与步骤需要运营在后台配置（走 38 册低代码） |
| 基础校验 | Zod / Yup / Valibot | 条件必填随业务分支变化（框架表达力不够） |
| 反垃圾 | 云 WAF、人机验证（Turnstile/hCaptcha） | 需要按行业特征调权重、要可解释理由 |
| 归因 | 各投放平台自带报表 | 需要首触/末触双归因并与 CRM 对齐 |
| 线索分配 | CRM 自带轮询/规则引擎 | 分配规则与订单、合同、区域强耦合 |

一句话原则：**通用能力买现成，业务规则自己写**。把业务规则塞进表单库的 `rules` 里，三个月后没人敢改。

### 典型应用场景

- **制造业官网询盘**：字段多、必填少，客户更愿意留电话而不是填长表单；
- **SaaS 免费试用**：轻表单 + 邮箱验证，重点是反垃圾与试用额度；
- **展会/线下扫码**：移动端单手填写，字段必须压到 6 个以内；
- **跨境询盘**：国家/区号/时区差异，手机号不能只按大陆规则校验。

### 完整代码示例

链路的前端核心是「一次提交要产出四样东西」：校验结果、垃圾分、归因、可跟进的标准化数据。下面这段就是 67-01 的主干：

```typescript
// 文件: examples/67-01-inquiry-form.ts（核心节选）
function validate(raw: RawInquiry): Validated {
  const errors: FieldError[] = [];
  const push = (field: string, code: FieldError["code"], message: string) =>
    errors.push({ field, code, message });
  // 硬必填:没有就无法跟进
  if (!raw.company?.trim()) push("company", "required", "请填写公司名称");
  // 条件必填:境内要手机号,定制要预算
  if (raw.country === "CN" && !raw.phone?.trim()) push("phone", "required", "境内询盘需填写手机号");
  // 反垃圾只影响路由,不阻塞提交
  const domain = raw.email?.split("@")[1]?.toLowerCase() ?? "";
  let spamScore = 0;
  if (DISPOSABLE.has(domain)) spamScore += 25;
  return { ok: errors.length === 0, errors, spamScore, attribution: attribute(raw.touches) };
}
```

> 运行方式：`npx tsx examples/67-01-inquiry-form.ts`（字段三层校验、条件必填、反垃圾四信号、首触/末触归因，共 10 组硬断言）。

### 最佳实践

- ✅ 把「转化率」拆成三段漏斗埋点：落地页曝光 → 表单开始填写 → 提交成功，卡在哪一段一目了然；
- ✅ 表单首屏只放 3-5 个字段，其余进「第二步」或用渐进式披露，移动端尤其明显；
- ✅ 提交成功页给出明确下一步（多久联系、联系谁），比「提交成功」四个字更能安抚客户；
- ✅ UTM 参数在落地页写入 sessionStorage，跨页跳转不丢，提交时一并带上；
- ❌ 不要把「选填」做成必填来提高线索质量——那只会把线索赶走；
- ❌ 不要在前端做最终校验就完事，BFF 必须重放同一套规则（前端校验是体验，服务端校验才是事实）。

## 67.2 询盘表单：字段分层、条件校验与反垃圾

### 概念解析

**字段分三层**，这是 B 端表单最重要的一张表：

| 层 | 定义 | 例子 | 校验强度 |
| --- | --- | --- | --- |
| 硬必填 | 没有它就无法跟进 | 公司名、联系人、邮箱 | 提交阻断 |
| 条件必填 | 随分支变化 | 境内→手机号；定制→预算 | 提交阻断（仅命中分支时） |
| 选填 | 只影响线索质量 | 需求描述、职位、行业 | 永不阻断 |

**条件必填必须写成函数，不要写成静态 Schema**。因为「境内要手机号」这条规则的输入是另一个字段的值，Zod 的 `superRefine` 能表达，但一旦分支超过三条，可读性会迅速崩塌。推荐做法：Schema 管格式，函数管分支。

**反垃圾看四个信号**，且只用于「路由」不用于「拒绝」：

1. 一次性邮箱域名（`mailinator`、部分免费邮箱）；
2. 需求描述中的外链数量；
3. 同一 IP 的提交频率（一分钟 ≥ 3 次）；
4. 手机号与邮箱雷同、长串大写等脚本特征。

关键设计：**垃圾分 0-100，≥ 60 进人工队列，绝不直接丢弃**。误杀一个真实大客户，损失远大于放过十个机器人。

**去重口径**要先定，再写代码：

- 企业线索：`公司域名 + 联系人`；
- 个人线索：`手机号`；
- 跨渠道同一人：以「最近一次有效提交」为主记录，历史触点合并到归因里。

### 典型应用场景

- **高客单价制造/集成**：预算与需求描述决定跟进优先级，属于条件必填；
- **跨境业务**：手机号规则按国家分派，不能一刀切 11 位；
- **投放落地页**：垃圾提交占比可能超过 30%，反垃圾评分直接影响销售人效。

### 完整代码示例

```typescript
// 文件: examples/67-01-inquiry-form.ts（核心节选）
// 条件必填:随业务分支变化,写成函数而不是静态 Schema
if (raw.type === "custom") {
  if (raw.budgetCents === undefined) push("budget", "required", "定制需求需给出预算区间");
}
// 归因:首触回答「从哪来」,末触回答「谁促成」
function attribute(touches: Touch[]) {
  const sorted = [...touches].sort((a, b) => a.at - b.at);
  return {
    first: sorted[0].channel,
    last: sorted[sorted.length - 1].channel,
    campaign: sorted[sorted.length - 1].campaign,
  };
}
```

> 运行方式：`npx tsx examples/67-01-inquiry-form.ts`（含境外手机号放行、未勾选隐私阻断、垃圾分封顶等 10 组断言）。

### 最佳实践

- ✅ 校验时机分工：格式类在失焦时校验，必填类在提交时汇总报错，避免用户刚点进第一个空字段就飘红；
- ✅ 错误信息带修复动作（「邮箱格式不正确，示例 name@company.com」），而不是只报「格式错误」；
- ✅ 提交按钮做「提交中锁定 + 幂等键」，防连点产生两条线索；
- ✅ 反垃圾理由要存库，销售看到「疑似机器人」时能判断是否误判；
- ⚠️ 隐私合规：勾选框必须默认不勾选、可撤回、文案写清用途，否则线索再多也抵不过一次处罚；
- ❌ 不要用 `required` 属性做唯一校验：它拦不住空格、全角字符和脚本提交。

## 67.3 大额资金操作：状态机、审批分级与幂等执行

### 概念解析

资金操作和普通表单的分界线是：**它不能「差不多对」**。三个硬约束必须先立住：

**① 金额只用整数分。** 浮点 `0.1 + 0.2 !== 0.3` 是常识，但在资金域里差 1 分就是事故。所有入参出参都是 `number` 整数分，展示层才用 `Intl.NumberFormat` 转成元。

**② 状态机必须显式。** 八个状态，迁移表写死，非法迁移直接抛错：

```text
draft → pending_review → approved → executing → success
                          ↓            ↓
                       rejected      failed → pending_review（重试）
draft/approved/pending_review → cancelled
```

```mermaid
stateDiagram-v2
    [*] --> draft
    draft --> pending_review: 申请人提交
    draft --> cancelled: 申请人撤回
    pending_review --> approved: 达成分级审批人数
    pending_review --> rejected: 审批人驳回
    pending_review --> cancelled: 申请人撤回
    approved --> executing: 携带幂等键执行
    approved --> cancelled: 撤回
    executing --> success: 网关返回成功
    executing --> failed: 网关返回失败
    failed --> pending_review: 查单确认后重提
    failed --> cancelled: 放弃本次操作
    success --> [*]
    rejected --> [*]
    cancelled --> [*]
```

**③ 审批分级随金额变。** 一档金额一档审批人，这是唯一建议硬编码的规则：

| 金额（元） | 审批人数 | 额外要求 |
| --- | --- | --- |
| < 50 万 | 1 | 财务岗 |
| 50 万 ~ 500 万 | 2 | 至少一位财务岗 |
| ≥ 500 万 | 3 | 必须含合规岗 |

其余风控（黑名单、限额、地区限制）放服务端，前端只做体验层拦截。

**幂等是资金操作的生死线。** 设计要点：

- 幂等键由**客户端在进入执行页时生成**（UUID v7），随请求带上；
- 服务端以「幂等键」建唯一索引，重复请求返回首次结果，而不是再扣一次；
- 网关超时 ≠ 失败：超时后必须先查单，再决定「重试」还是「置为未知」；
- 审计轨迹记录每次迁移的「谁、何时、从哪到哪、依据什么」，只追加不修改。

### 典型应用场景

- **对公转账/代付**：金额大、审批链长、失败必须查单；
- **保证金/退款**：需要「原路退回」与幂等，防重复退款；
- **批量代发工资**：单笔小但总量大，失败要能按批次重试而不是整批重来。

### 完整代码示例

```typescript
// 文件: examples/67-02-fund-operation.ts（核心节选）
const TRANSITIONS: Record<FundState, FundState[]> = {
  draft: ["pending_review", "cancelled"],
  pending_review: ["approved", "rejected", "cancelled"],
  approved: ["executing", "cancelled"],
  executing: ["success", "failed"],
  failed: ["pending_review", "cancelled"],
  success: [], rejected: [], cancelled: [],
};
execute(id, idempotencyKey, gateway) {
  const existing = this.byIdempotencyKey.get(idempotencyKey);
  if (existing) return { replayed: true, ...this.get(existing) }; // 重放返回首次结果
  // ...
}
```

> 运行方式：`npx tsx examples/67-02-fund-operation.ts`（500 万以上三审含合规、自审拦截、重复审批拦截、幂等重放不再扣款、审计轨迹完整，共 12 组硬断言）。

### 最佳实践

- ✅ 申请人、审批人、执行人三个角色分离，任何两人不得重合（双人复核原则）；
- ✅ 审批页面展示「影响范围」：本次操作会动到哪些账户、余额变化多少，而不是只给一个金额；
- ✅ 执行结果三态：成功 / 失败 / 未知。未知必须进人工查单队列，不能默认失败重试；
- ✅ 所有时间以服务端时间为准，前端时钟只用于展示；
- ⚠️ 审批通过后金额不可改：要改就撤回重新走流程，否则审批记录与实际金额对不上；
- ❌ 不要用「再点一次」来重试：没有幂等键的重试就是重复扣款；
- ❌ 不要把状态放在前端内存里当作事实来源，刷新即丢；状态以服务端返回为准，前端只做乐观展示。

## 67.4 多步骤 KYC：声明式步骤机与补件回流

### 概念解析

KYC（了解你的客户）表单通常有 5-10 步、两三种主体类型、随时可能被审核员打回补件。硬编码 `if (step === 3)` 的写法会在第三次需求变更时崩溃。

**声明式步骤机**把每一步描述成数据：

```typescript
interface StepDef {
  id: StepId;
  applies: (s: KycState) => boolean;   // 分支:个人/企业走不同步骤
  fields: string[];                    // 本步必填字段
  docs: DocId[];                       // 本步必传材料
  after: StepId[];                     // 前置步骤,决定「能否点进去」
}
```

由此可以自动算出三样东西：**进度百分比、下一步、阻塞项**。再加一条规则，补件体验就成立了：

> **被驳回的步骤永远排在最前。** 用户点进来第一眼就该看到「哪里被打回、为什么」，而不是从头再走一遍已完成的步骤。

```mermaid
flowchart TD
    A["开始填写"] --> B{"主体类型"}
    B -- 个人 --> C["基本信息"]
    B -- 企业 --> D["基本信息"]
    C --> E["证件信息"]
    D --> F["企业资质"]
    F --> G["实际受益人"]
    E --> H["地址与账单"]
    G --> H
    H --> I["补充材料"]
    I --> J{"审核结果"}
    J -- 通过 --> K["提交成功"]
    J -- 驳回 --> L["补件：仅重走被驳回步骤"]
    L -.回到对应步骤.-> E
```

几个容易忽略的细节：

- **草稿自动保存**：每一步完成即写服务端草稿，换设备可续填；
- **分步校验**：只校验当前步，不要一进页面就把所有步骤的错误全抛出来；
- **材料预览**：上传后立刻显示缩略图与「重新上传」，减少审核来回；
- **最小必要**：只收合规要求的字段，多收一项就是多一份泄露风险与转化损失。

**框架 vs 自研**：

| 能力 | 现成方案 | 自研触发条件 |
| --- | --- | --- |
| 步骤导航 | AntD Steps、Formily StepForm | 步骤需按主体类型动态增删 |
| 文件上传 | 云存储直传 SDK | 需要活体检测、证件 OCR、材料合规校验 |
| 身份核验 | 第三方 KYC 服务商（证件 OCR + 活体 + 黑名单） | 行业有特殊规则，或需要与自有风控打通 |
| 审核工作台 | 通用后台 | 补件原因、SLA、双人复核与自有工单强耦合 |

### 典型应用场景

- **开户/入驻**：个人与企业两套分支，企业多出「受益人」与「董事会决议」；
- **跨境收款**：不同国家适用规则不同，步骤集合随国家变化；
- **高风险行业**：审核员驳回率高，补件回流是高频路径，必须优先设计。

### 完整代码示例

```typescript
// 文件: examples/67-03-kyc-stepper.ts（核心节选）
const status = rejected.length
  ? "supplement"                       // 被驳回:补件优先
  : locked
    ? "locked"                         // 前置未完成:不可进入
    : missingFields.length === 0 && missingDocs.length === 0
      ? "done"
      : "todo";
// 补件永远排在最前,否则用户会在已完成步骤里反复打转
const next = supplements[0] ?? steps.find((x) => x.status === "todo")?.id ?? null;
```

> 运行方式：`npx tsx examples/67-03-kyc-stepper.ts`（企业/个人分支、前置锁定、补件回流、证件过期硬阻塞、进度 100%，共 13 组硬断言）。

### 最佳实践

- ✅ 进度条按「已完成步骤 / 当前分支总步骤」算，个人与企业各自 100%，不要用固定分母；
- ✅ 补件页置顶审核原因与示例图，用户一次改对，减少平均补件轮次；
- ✅ 上传即压缩、即校验（大小/格式/清晰度），别等提交后才说「照片不清晰」；
- ✅ 证件到期时间是硬阻塞，提前 30 天在列表页提醒；
- ⚠️ 敏感材料（证件、银行流水）必须加密存储、最小权限访问、访问留痕，前端不得缓存到 localStorage；
- ❌ 不要把整份 KYC 数据塞进 URL 或前端日志，一次误上报就是一次数据泄露；
- ❌ 不要让用户「从头再填」：已完成步骤的数据必须保留，补件只重走被驳回那一步。

## 67.5 对账报表：整数分、差异定位与虚拟窗口

### 概念解析

对账的本质是**两个账本逐笔比对**：平台侧（自己的订单）与渠道侧（支付/银行流水）。输出不是「差多少」，而是「差在哪几笔、为什么差」。

**差异必须分类**，否则无法定位：

| 差异类型 | 含义 | 常见原因 |
| --- | --- | --- |
| `only_platform` | 平台有、渠道无 | 渠道漏单、跨日结算 |
| `only_channel` | 渠道有、平台无 | 补单、历史订单 |
| `amount` | 金额不等（带差额方向） | 优惠、手续费、部分退款 |
| `currency` | 币种不一致 | 多币种配置错误 |
| `duplicate` | 单号重复 | 重复推送、幂等失效 |

**三条合计校验**，任何一条不成立都不能标「已平」：

1. 平台合计 = Σ 平台明细；
2. 渠道合计 = Σ 渠道明细；
3. 平台合计 − 渠道合计 = 已知差异之和（手续费 + 退款 + 跨日），差异要能被解释。

```mermaid
flowchart LR
    P["平台明细：整数分"] --> C["按单号建立索引"]
    Q["渠道明细：整数分"] --> C
    C --> D{"逐笔比对并分类"}
    D --> E1["单边账：only_platform"]
    D --> E2["单边账：only_channel"]
    D --> E3["金额差：带差额方向"]
    D --> E4["币种差：currency"]
    D --> E5["重复单号：duplicate"]
    E1 --> T{"三条合计校验"}
    E2 --> T
    E3 --> T
    E4 --> T
    E5 --> T
    T -- 通过 --> OK["标记账期已平"]
    T -- 不通过 --> FIX["生成差异工单并下钻明细"]
```

**金额解析的三个坑**：

- 字符串带千分位、货币符号、全角空格 → 解析前统一清洗；
- 小数位超过两位 → **直接报错**，不要四舍五入（会把脏数据变成「看起来对」）；
- 科学计数法/浮点入参 → 一律拒绝，只收整数分。

**万行差异怎么展示**：先筛选（只看差异 / 只看某类差异），再虚拟滚动。虚拟滚动内核见 64 册，本章只补「窗口切片」这一层：

```text
first = floor(scrollTop / rowHeight)
start = max(0, first - overscan)
end   = min(total, first + viewportRows + overscan)
```

### 典型应用场景

- **日终对账**：T+1 跑批，差异进工单，次日必须处理完；
- **实时对账**：支付回调后即时比对，差异秒级告警；
- **多渠道路由**：同一笔订单可能经过多个支付通道，需要按通道分别对账；
- **财务导出**：差异表要能导出 Excel 并带审计口径（谁在何时确认了哪几笔）。

### 完整代码示例

```typescript
// 文件: examples/67-04-reconciliation.ts（核心节选）
function toCents(input: string | number): number {
  if (typeof input === "number") {
    if (!Number.isInteger(input)) throw new Error(`金额含小数,请传整数分: ${input}`);
    return input;
  }
  // 清洗千分位/货币符号,小数位超过两位直接报错
}
let matched = 0;
for (const [id, row] of p.map) {
  const other = c.map.get(id);
  if (other && other.currency === row.currency && other.amountCents === row.amountCents) matched++;
}
```

> 运行方式：`npx tsx examples/67-04-reconciliation.ts`（整数分解析、浮点拒绝、五类差异、合计差额、重复单号、虚拟窗口切片，共 13 组硬断言）。

### 最佳实践

- ✅ 差异表默认按「金额绝对值降序」，财务先看大额；
- ✅ 每笔差异提供「确认 / 挂起 / 转工单」三个动作，并记录处理人；
- ✅ 合计差额必须能下钻到具体明细，不能只给一个总数；
- ✅ 对账结果落快照：同一账期重复跑批要与历史结果可比对，防「越跑越乱」；
- ⚠️ 跨日/时区边界要显式声明账期口径（自然日还是 24 小时滚动），否则永远对不平；
- ❌ 不要在前端把金额转成浮点再相加，也不要 `toFixed` 后再比较；
- ❌ 不要用「合计相等」代替逐笔核对：两笔错账互相抵消后合计仍然相等。

## 67.6 自测题

<details>
<summary><b>1. 【基础】为什么 B 端询盘表单要把字段分成「硬必填 / 条件必填 / 选填」三层？</b></summary>

三层的校验强度完全不同：硬必填缺失就无法跟进，必须阻断；条件必填只在命中业务分支时阻断（如境内要手机号、定制要预算）；选填只影响线索质量，永不阻断。把选填当必填会直接压低转化率，把条件必填写成静态必填会让另一部分客户无法提交。
</details>

<details>
<summary><b>2. 【基础】反垃圾评分为什么「只影响路由、不阻塞提交」？</b></summary>

垃圾判定一定有误杀。直接拒绝会把真实大客户挡在门外，损失远大于放过几个机器人。正确做法是给 0-100 的分数并把理由入库，高分进人工队列，由人做最终判断；同时前端仍保留人机验证等低成本拦截。
</details>

<details>
<summary><b>3. 【基础】资金操作为什么必须用整数分而不是浮点元？</b></summary>

二进制浮点无法精确表示 0.1、0.2 这类十进制小数，累加会产生 1 分甚至更多的偏差；资金域差 1 分就是账务事故。统一用整数分参与运算，只在展示层用 `Intl.NumberFormat` 转成元，可以彻底消除这类误差。
</details>

<details>
<summary><b>4. 【进阶】大额资金操作中，「幂等键」应该由谁生成、放在哪里、服务端怎么用？</b></summary>

由客户端在进入执行页时生成（推荐 UUID v7），随执行请求一起提交。服务端以幂等键建唯一索引：首次请求落库并执行，重复请求命中索引后直接返回首次结果，不再触发扣款。超时场景必须先查单再决定重试，避免「超时即重试」造成重复执行。
</details>

<details>
<summary><b>5. 【进阶】为什么 KYC 的「补件步骤」必须排在最前？如果按顺序回到第一步会发生什么？</b></summary>

补件时用户唯一要处理的是被驳回的那一步。若按固定顺序回到第一步，用户会在已完成的步骤里反复点击、反复看到「已完成」，既浪费时间又容易误改已通过的数据。把 supplement 状态优先级提到最高，并在页面置顶驳回原因，可以把补件轮次压到最低。
</details>

<details>
<summary><b>6. 【进阶】对账时「平台合计 = 渠道合计」能证明账平了吗？为什么？</b></summary>

不能。两笔方向相反的错账（如 A 单平台多 100 元、B 单平台少 100 元）会让合计仍然相等。必须先逐笔比对并分类差异（单边账、金额差、币种差、重复单号），再用合计差额校验作为第二道防线，同时要求差额能被手续费、退款、跨日等已知项解释。
</details>

<details>
<summary><b>7. 【挑战】设计一套「询盘 → 资金 → KYC → 对账」都能复用的高风险操作底座，需要哪几个公共能力？</b></summary>

四层公共能力：① 状态机内核（显式迁移表 + 守卫 + 只追加审计轨迹），资金、KYC 审核、对账工单都能复用；② 幂等与防重（客户端幂等键 + 服务端唯一索引 + 超时查单）；③ 金额与口径（整数分、币种、账期、时区统一在边界层收敛）；④ 可观测与告警（成功率、差异数、补件轮次、审批时长进入监控大盘）。再往外是权限与脱敏（最小必要、字段级授权、访问留痕）。
</details>

<details>
<summary><b>8. 【挑战】业务方要求「询盘表单加 12 个字段提升线索质量」，你如何用数据而不是直觉回应？</b></summary>

先给三段漏斗基线（曝光 → 开始填写 → 提交成功）与各字段的放弃率，再做 A/B：只加 3 个高价值字段，对比提交率与线索合格率。用「合格线索数 = 提交量 × 合格率」作为目标函数，而不是「字段数量」。若必须收全量信息，用两步表单或提交后补全，把长表单移出转化关键路径。
</details>

## 67.7 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 把选填字段设成必填 | 转化率断崖下跌，线索变少 | 字段分三层，选填永不阻断 |
| 2 | 条件必填写成静态 Schema | 分支一多就无法维护，误拦客户 | 格式用 Schema，分支用函数 |
| 3 | 垃圾提交直接丢弃 | 误杀真实大客户且无从申诉 | 评分 + 理由入库，高分进人工队列 |
| 4 | 只存末次归因 | 高估收割渠道，品牌投放被砍 | 首触与末触双归因都存 |
| 5 | 金额用浮点元运算 | 累加出现分位偏差，账务事故 | 全链路整数分，展示层才格式化 |
| 6 | 资金状态散落在组件里 | 刷新丢失、非法迁移无人拦 | 服务端状态机 + 前端只做展示 |
| 7 | 审批人可与申请人重合 | 自审自批，内控失效 | 角色分离 + 自审硬拦截 |
| 8 | 无幂等键就重试执行 | 重复扣款、重复退款 | 客户端幂等键 + 服务端唯一索引 |
| 9 | 网关超时当失败直接重试 | 实际已成功，二次扣款 | 超时先查单，未知进人工队列 |
| 10 | 审批通过后修改金额 | 审批记录与执行金额不一致 | 撤回重走流程，禁止就地改额 |
| 11 | KYC 固定分母算进度 | 个人/企业进度永远不到 100% | 按当前分支步骤数计算 |
| 12 | 补件让用户从头再填 | 补件轮次与流失率双双上升 | 补件步骤置顶，仅重走被驳回步 |
| 13 | 敏感材料缓存到 localStorage | 一次 XSS 即批量泄露 | 加密存储 + 最短留存 + 访问留痕 |
| 14 | 对账用合计相等判定已平 | 正负错账互抵，掩盖真实差异 | 逐笔分类比对 + 合计差额双重校验 |
| 15 | 金额字符串四舍五入入库 | 脏数据被洗成「看起来对」 | 小数位超两位直接报错 |

---
