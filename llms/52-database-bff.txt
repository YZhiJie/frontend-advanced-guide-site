## 52.1 关系模型与索引：接口慢在哪

### 概念解析

一个接口的耗时通常由四段构成：网络、应用逻辑、数据库、序列化。前端能感知的是总耗时，但排查时要能拆开。

**关系模型的三件事**：

1. **主键**：唯一标识一行，建议用无业务含义的自增 ID 或 UUID；业务编号（手机号、订单号）不适合做主键，因为会变；
2. **外键/关联**：订单表存 `user_id`，用户信息在用户表；跨表取数要么 JOIN，要么批量查后在内存拼装；
3. **范式**：减少冗余、避免更新异常；但报表/列表页常做「反范式」冗余（如订单快照存商品名），以读性能换一致性维护成本。

**索引**是查询性能的第一杠杆：

| 索引类型 | 适用 | 注意 |
| --- | --- | --- |
| 主键索引 | 按 id 查 | 聚簇索引，范围查询友好 |
| 普通索引 | 高频过滤字段 | 区分度低的字段收益小 |
| 联合索引 | 多条件组合查询 | 遵循最左前缀；范围条件会截断后续列 |
| 唯一索引 | 业务唯一约束 | 插入冲突要处理 |
| 覆盖索引 | 查询列都在索引里 | 避免回表，读性能最好 |

**最左前缀**的例子：联合索引 `(tenant_id, status, created_at)`，能命中 `tenant_id`、`tenant_id + status`、三者全有；不能单独命中 `status` 或 `created_at`。范围条件（`created_at > ?`）之后的列无法继续用于精确匹配。

**分页**：

- `OFFSET/LIMIT` 深分页会扫描并丢弃前 N 行，页码越大越慢；
- 游标分页（`WHERE id < last_id ORDER BY id DESC LIMIT n`）稳定且可利用索引，适合信息流；
- 前端要接受「游标分页不能跳页」，这是体验与性能的交换。

### 典型应用场景

- 列表页慢：先看是否深分页、是否缺联合索引；
- 详情页慢：是否 N+1、是否回表、是否重复序列化；
- 搜索页慢：是否用 `LIKE '%x%'` 导致全表扫描；
- 统计页慢：是否实时聚合大表，能否预计算/缓存。

### 可运行代码示例

示例 52-01 用假数据库统计查询次数，直观展示 N+1 与批量加载的差距。

```typescript
// 文件: examples/52-01-n-plus-one.ts（核心节选）
const orders2 = await db2.getOrderPage(20);
const userIds = [...new Set(orders2.map((o) => o.userId))];
const users = await db2.getUsers(userIds);
const userMap = new Map(users.map((u) => [u.id, u]));
```

> 运行方式：`npx tsx examples/52-01-n-plus-one.ts`（N+1 为 21 次查询，批量 + 去重后为 2 次，结果一致）。

### 最佳实践

- ✅ 接口设计阶段就明确「查询形状」：一次请求要查哪几张表、走什么索引；
- ✅ 深分页改游标；列表默认按索引列排序，避免 `ORDER BY` 随机字段；
- ⚠️ 联合索引不是越多越好：每个索引都会增加写入成本与存储；
- ❌ 不要用 `SELECT *` 取全表字段——序列化、网络、内存都为此付费。

## 52.2 SQL、ORM 与 N+1

### 概念解析

ORM 让代码更好写，但会把「查询形状」藏起来。常见陷阱：

| 陷阱 | 表现 | 修复 |
| --- | --- | --- |
| N+1 | 列表 20 条 → 21 次查询 | 批量查询 + 内存 join，或用 `include`/`join` 一次取回 |
| 懒加载 | 模板/序列化时触发额外查询 | 显式 `select`/`include`，禁止隐式懒加载 |
| 全量字段 | 查了 30 列只用 3 列 | `select` 指定字段 |
| 无索引过滤 | 查询条件走全表 | 按最左前缀建索引 |
| 事务过长 | 锁持有时间长，连接池耗尽 | 事务内只放必须原子化的操作 |
| 批量过大 | `IN (...)` 上千个 id | 分片（如 500 一批） |

**N+1 的本质是「循环里访问关联数据」**。修复不是加缓存，而是把「逐个查」改成「批量查 + 内存拼装」：

1. 先查主表，拿到关联 id；
2. 去重后批量查关联表（必要时分片）；
3. 用 `Map` 在内存做 join；
4. 结果与逐条查完全一致。

**事务与幂等**：前端要理解「接口可能重试」，所以写接口必须支持幂等键；事务只保证原子性，不保证「用户只点了一次」。

### 典型应用场景

- 订单列表带用户名/商品名：批量 join；
- 详情页带评论数/点赞数：聚合查询或冗余计数；
- 批量导入：分片 + 事务边界；
- 支付回调：幂等键 + 唯一索引防重复入账。

### 可运行代码示例

示例 52-01 还演示了「大批量按 500 分片」和「懒加载被重复访问放大」两种情况。

```typescript
// 文件: examples/52-01-n-plus-one.ts（核心节选）
const CHUNK = 500;
let fetched = 0;
for (let i = 0; i < ids.length; i += CHUNK) {
  fetched += (await db3.getUsers(ids.slice(i, i + CHUNK))).length;
}
```

> 运行方式：`npx tsx examples/52-01-n-plus-one.ts`（分片查询次数、懒加载触发次数均有断言）。

### 最佳实践

- ✅ 列表接口一律批量取关联数据，禁止在循环里 `await`；
- ✅ 批量 `IN` 查询分片，避免 SQL 过长与数据库参数上限；
- ⚠️ ORM 的 `include` 可能生成巨大 JOIN，数据量大时反而慢，要对比执行计划；
- ❌ 不要在事务里做 HTTP 调用、发消息、等用户输入——会长时间占用连接与锁。

## 52.3 BFF 的职责与分层

### 概念解析

BFF（Backend for Frontend）不是「再写一个后端」，而是**为特定前端裁剪与聚合数据**的一层。它的价值在四个边界：

| 职责 | 说明 | 不做什么 |
| --- | --- | --- |
| 聚合 | 一次请求合并多个下游服务 | 不承载核心业务规则 |
| 裁剪 | 只返回页面需要的字段 | 不做复杂计算/报表 |
| 适配 | 把下游错误码映射成前端可处理的结构 | 不吞错、不伪造成功 |
| 会话 | 统一鉴权、租户、灰度上下文 | 不保存长期业务数据 |

**分层建议**：

```text
页面 → BFF（聚合/裁剪/鉴权）→ 领域服务 → 数据访问（ORM/SQL）→ 数据库
```

BFF 的接口要遵守三条契约：

1. **稳定**：字段只增不删，删除走版本；
2. **可解释**：错误结构统一（`code`/`message`/`traceId`/`retryable`）；
3. **可观测**：每次聚合记录下游耗时与失败率，慢在哪一目了然。

**GraphQL 也是一种 BFF 形态**：由前端声明字段，服务端按需返回。它解决了「字段裁剪」，但也带来复杂度（N+1、权限、缓存）。团队没有相应基础设施时，REST + BFF 聚合更稳。

### 典型应用场景

- 首页：同时聚合推荐、公告、用户信息、购物车数量；
- 移动端弱网：裁剪字段、压缩图片 URL、减少请求数；
- 多端复用：Web/小程序/App 各自 BFF，共享领域服务；
- 灰度发布：BFF 根据用户分桶调用不同版本的下游。

### 可运行代码示例

BFF 聚合的关键是「并行 + 超时 + 降级」，而不是串行 `await`。下面是一个最小聚合器：并行请求、单点超时、失败返回部分数据。

```typescript
// 文件: src/bff/home-aggregator.ts —— 虚拟工程文件
async function aggregate(userId: string) {
  const tasks = [
    withTimeout(userService.profile(userId), 300),
    withTimeout(noticeService.latest(), 200),
    withTimeout(cartService.count(userId), 200),
  ];
  // allSettled:任何一个失败都不拖垮整个首页
  const [profile, notice, cart] = await Promise.allSettled(tasks);
  return {
    profile: profile.status === "fulfilled" ? profile.value : null,
    notice: notice.status === "fulfilled" ? notice.value : [],
    cartCount: cart.status === "fulfilled" ? cart.value : 0,
    degraded: [profile, notice, cart].some((r) => r.status === "rejected"),
  };
}
```

> 运行方式：BFF 聚合依赖服务端环境；查询形状与缓存可用 `npx tsx examples/52-01-n-plus-one.ts`、`examples/52-02-cache-aside.ts` 验证。

### 最佳实践

- ✅ 聚合用 `Promise.allSettled` + 单点超时，失败返回可降级的部分数据；
- ✅ 统一错误结构并带 `traceId`，前端能上报、后端能串联；
- ⚠️ BFF 不要变成「第二个业务后端」——核心规则仍应在领域服务；
- ❌ 不要在 BFF 里做长事务或大批量写操作。

## 52.4 缓存与一致性

### 概念解析

缓存能救读性能，也会引入一致性问题。先掌握三种失效场景：

| 问题 | 现象 | 对策 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，每次都打库 | 缓存空值（短 TTL）+ 参数校验 |
| 击穿 | 热点 key 过期瞬间并发回源 | 单飞（SingleFlight）+ 逻辑过期 |
| 雪崩 | 大量 key 同时过期或缓存整体失效 | TTL 加随机抖动 + 多级缓存 + 熔断 |

**Cache-Aside 的标准流程**：

1. 读：先读缓存，命中返回；未命中查库，回填缓存；
2. 写：先写数据库，再**删除**缓存（不是更新缓存）；
3. 为什么删而不是改：并发写时「更新缓存」可能把旧值写回去，删除让下一次读自然回源。

**一致性级别**要写进需求：强一致（交易、库存）通常不做缓存或只做短 TTL；最终一致（商品详情、榜单）可以接受秒级延迟。

**单飞（SingleFlight）**：同一 key 的并发未命中，只允许一个请求回源，其余等待同一结果。这是防击穿最直接的手段。

### 典型应用场景

- 商品详情：Cache-Aside + TTL 抖动；
- 热点榜单：逻辑过期 + 后台异步刷新；
- 库存：不强依赖缓存，或用 Redis 原子扣减 + 数据库最终落账；
- 用户会话：Redis 存储，设置滑动过期。

### 可运行代码示例

示例 52-02 验证四件事：并发未命中只回源一次、TTL 内命中、过期后重载、空值短缓存防穿透。

```typescript
// 文件: examples/52-02-cache-aside.ts（核心节选）
async run<T>(key: string, task: () => Promise<T>): Promise<T> {
  const existing = this.inflight.get(key);
  if (existing) return existing as Promise<T>;
  const p = task().finally(() => this.inflight.delete(key));
  this.inflight.set(key, p);
  return p;
}
```

> 运行方式：`npx tsx examples/52-02-cache-aside.ts`（10 个并发只回源 1 次、TTL 过期重载、空值缓存、写后失效）。

### 最佳实践

- ✅ TTL 加 10%~20% 随机抖动，避免批量同时过期；
- ✅ 热点 key 用单飞或逻辑过期，防止击穿；
- ⚠️ 「先更库再删缓存」仍可能读到旧值（删缓存前的读），对强一致场景要用版本号/延迟双删；
- ❌ 不要把缓存当数据库：缓存丢失必须能回源恢复。

## 52.5 自测题

<details>
<summary><b>1. 【基础】什么是 N+1 查询？为什么它比「一次大查询」慢？</b></summary>

N+1 是「查 1 次主表，再在循环里为每条记录查 1 次关联表」，总查询次数为 N+1。每次查询都有网络往返、解析、执行开销，N 越大延迟线性增长；批量查询把 N 次往返压成 1 次（或分片后的少数几次），总耗时显著下降。
</details>

<details>
<summary><b>2. 【基础】联合索引 `(tenant_id, status, created_at)` 能命中哪些查询条件？</b></summary>

能命中 `tenant_id`、`tenant_id + status`、`tenant_id + status + created_at`（最左前缀）。单独用 `status` 或 `created_at` 不能命中。若 `status` 是范围条件，后续 `created_at` 通常只能用于过滤而不能继续精确匹配索引顺序。
</details>

<details>
<summary><b>3. 【进阶】为什么深分页 `LIMIT 100000, 20` 很慢？如何优化？</b></summary>

数据库需要扫描并丢弃前 100000 行，页码越大成本越高。优化方式：游标分页（带上一页最后一条的 id/时间）、延迟关联（先用覆盖索引取 id 再回表）、或业务上限制最大页数。
</details>

<details>
<summary><b>4. 【进阶】Cache-Aside 为什么是「更新数据库后删除缓存」而不是「更新缓存」？</b></summary>

并发写时，两个请求更新缓存的顺序可能与数据库提交顺序不一致，导致旧值覆盖新值；删除缓存让下一次读自然回源，减少不一致窗口。删除仍可能被「删除前的读」回填旧值，强一致场景需配合版本号、延迟双删或直接不缓存。
</details>

<details>
<summary><b>5. 【进阶】缓存穿透、击穿、雪崩分别是什么？各给一个对策。</b></summary>

穿透：查不存在的数据，每次都打库 → 缓存空值 + 参数校验；击穿：热点 key 过期瞬间并发回源 → 单飞/逻辑过期；雪崩：大量 key 同时过期或缓存整体故障 → TTL 抖动 + 多级缓存 + 熔断降级。
</details>

<details>
<summary><b>6. 【挑战】一个首页接口聚合了 5 个下游服务，其中一个经常超时，如何保证首页可用？</b></summary>

并行调用（`Promise.allSettled`）而不是串行；每个下游单独超时（如 200~300ms）；超时的模块返回降级数据（空列表、默认值、上次缓存）；响应标注 `degraded` 供前端展示「部分内容加载失败」；同时记录下游耗时与失败率，推动服务方治理。核心模块可设更长的超时与重试，非核心模块快速失败。
</details>

<details>
<summary><b>7. 【挑战】BFF 与「再写一个后端」的边界在哪里？</b></summary>

BFF 只做面向特定前端的聚合、裁剪、协议适配、会话透传，不承载核心业务规则、不长事务、不保存长期业务数据。领域规则、库存扣减、支付状态机应在领域服务；BFF 可以降级、可以缓存短 TTL 数据，但不能成为第二个事实来源。
</details>

<details>
<summary><b>8. 【挑战】前端如何判断一个接口慢是「前端渲染」还是「后端查询」？</b></summary>

用浏览器 Network 面板看 TTFB 与下载耗时：TTFB 高说明服务端处理慢；下载慢说明响应体过大/网络差。再看服务端 trace（`traceId`）拆分 BFF、下游、数据库耗时；对比「同样接口在 curl 下的耗时」排除前端因素。最后用 Performance 面板看前端是否在解析/渲染大 JSON 上耗时。
</details>

## 52.6 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 循环里 `await` 查关联表 | N+1，列表页随数据量线性变慢 | 批量查询 + 内存 join |
| `IN` 查询不分片 | SQL 过长、参数超限、锁范围大 | 按 500 左右分片 |
| 用 `SELECT *` | 传输与序列化浪费，索引覆盖失效 | 只选需要的列 |
| 深分页用大 OFFSET | 越翻越慢 | 游标分页 |
| 联合索引顺序随意 | 最左前缀失效，索引白建 | 按查询条件与区分度设计 |
| 事务里做 HTTP 调用 | 连接与锁长时间占用 | 事务只包原子写操作 |
| 写接口无幂等键 | 重试导致重复扣款/重复入账 | 幂等键 + 唯一索引 |
| 更新缓存而不是删缓存 | 并发下旧值覆盖新值 | 写库后删缓存 |
| TTL 全部相同 | 同一时刻集体过期，雪崩 | 加随机抖动 |
| 热点 key 无单飞 | 过期瞬间并发回源打垮数据库 | SingleFlight / 逻辑过期 |
| 缓存空值不设 TTL | 数据恢复后长期读不到 | 空值短 TTL |
| BFF 承载核心业务规则 | 多端规则分叉，难以维护 | 规则下沉领域服务 |
| 聚合接口串行调用下游 | 总耗时等于各段之和 | 并行 + 单点超时 |
| 下游失败直接抛 500 | 首页整体不可用 | 降级返回部分数据 |
| 错误结构不统一 | 前端无法区分可重试与致命错误 | 统一 `code`/`retryable`/`traceId` |
