## 23.1 事件循环、浏览器渲染与页面加载（重点章）

### Q1 ⭐ 事件循环的完整流程是什么？宏任务和微任务如何划分？

**答案要点**：
- **宏任务（macrotask）**：script 整体代码、setTimeout/setInterval、I/O、UI 交互事件、postMessage、**DOMContentLoaded/load 等生命周期事件的派发**
- **微任务（microtask）**：Promise.then/catch/finally、queueMicrotask、MutationObserver、process.nextTick（Node，优先级高于 Promise）
- **单轮循环**：取一个宏任务执行 → 执行完后**清空全部微任务队列**（含执行中新产生的微任务）→ 浏览器判断是否渲染 → 进入下一轮
- 关键认知：微任务**插队**，宏任务**排队**。`Promise.resolve().then` 永远比同级的 `setTimeout(fn, 0)` 先执行

> **⚠️ 常见误区（本人踩过）**：「执行一个宏任务**之前**会先清空所有微任务」——结果对、因果反了。清空动作挂在**上一个宏任务的结尾**，而非下一个宏任务的开头；首个宏任务（script 整体执行）开始时队列本来就是空的，不存在"清空"动作。这个区别影响两点判断：① 渲染发生在微任务清空**之后**、下一个宏任务**之前**（误区模型容易把渲染错排到微任务之前）；② 微任务中注册的新微任务会在**同一次清空**中继续执行（清空制），这正是微任务死循环卡死页面的根源（见 Q8）。
>
> **面试标准话术**：每个宏任务执行**完成后**，引擎立即清空整个微任务队列（包括清空过程中新产生的微任务），然后浏览器判断是否渲染，再取下一个宏任务。

> **追问防线：第一个执行的是宏任务还是微任务？**——永远是**宏任务（script 整体求值）**，这是由微任务的产生方式决定的：微任务只能由代码执行产生（Promise.then / queueMicrotask / MutationObserver 回调），页面加载时队列为空，所以必须先有宏任务跑代码，才谈得上微任务。**没有代码执行就没有微任务**。推论：任何输出题中同步代码必最先跑完。边界：defer/module 脚本的第一个任务仍是"该模块求值"（宏任务，只是入队推迟到解析完成后）；MutationObserver 需先有 DOM 变化，永不可能最先；Node 的 process.nextTick 优先级虽高于 Promise，但也要等当前代码段执行完才跑。

> **代码示例**：

```js
// 这段 script 的求值就是第一个宏任务，同步代码是它的执行过程
queueMicrotask(() => console.log('③ 微任务'))  // 代码执行后才产生微任务
setTimeout(() => console.log('⑤ 宏任务'), 0)   // 入队下一个宏任务

Promise.resolve().then(() => console.log('④ 微任务'))

console.log('① 同步')
console.log('② 同步')
// 输出：① ② ③ ④ ⑤
```

> **逐行拆解**：①② 最先——它们是第一个宏任务的执行过程；③④ 是执行过程中产生的微任务，在 script 执行完后统一清空（注册顺序即执行顺序）；⑤ 是下一轮宏任务。注意 `queueMicrotask` 虽然写在第一行，**注册得再早的微任务也必须等同步代码跑完**——它能赢的只有同为队列产物的后来者。

### Q2 ⭐⭐ 事件循环与浏览器页面渲染的调用顺序是什么？

**答案要点**（必须能画出时序）：
```
一个宏任务执行完（含：script、事件回调、定时器回调、DOMContentLoaded/load 监听器）
   ↓
清空微任务队列（Promise.then / MutationObserver / queueMicrotask）
   ↓
浏览器判断是否需要渲染（通常对齐 60Hz 屏幕刷新，即每 16.7ms 一次渲染机会）
   ↓ 需要渲染时：
requestAnimationFrame 回调执行（渲染之前）
   ↓
样式计算（Style）→ 布局（Layout）→ 绘制（Paint）→ 合成（Composite）
   ↓
渲染完成，空闲时执行 requestIdleCallback 回调
   ↓
下一个宏任务
```
- **渲染不是每个宏任务后都发生**：如果上一个宏任务执行很快、距上次渲染不足 16.7ms，浏览器会跳过本轮渲染；如果宏任务耗时 200ms，渲染被阻塞，页面掉帧
- **rAF 的时机**：在下一帧渲染**之前**执行，适合做动画——每帧只执行一次，比 setTimeout 动画更省且不掉帧
- **微任务在渲染之前**：所以微任务里修改 DOM，会在同一次渲染中生效，用户看不到中间态

### Q3 ⭐⭐ DOMContentLoaded、load、beforeunload 的区别与触发时机？

**答案要点**：
- **DOMContentLoaded（DCL）**：HTML 全部解析完成 + 所有 defer 脚本执行完毕即触发。**不等待**：图片、iframe、async 脚本
- **load**：页面**所有资源**（图片、样式表、iframe、async 脚本）全部加载完成后触发，必在 DCL 之后
- **beforeunload / pagehide**：页面即将卸载时触发；移动端及 bfcache（前进后退缓存）场景推荐用 pagehide，beforeunload 会阻止 bfcache 生效
- **关键机制**：DCL 和 load 都**作为宏任务**进入事件循环派发——它们的监听器执行时，同样遵循"宏任务 → 清空微任务 → 可能渲染"的规则
- 工程用途：DCL 用于尽早初始化交互（不用等图片）；load 用于依赖完整资源的操作（如读取图片真实尺寸、等所有 iframe 就绪）

### Q4 ⭐⭐ script 的三种加载方式：普通 / defer / async

| 维度 | 普通脚本 | defer | async |
|---|---|---|---|
| 下载 | 遇到即下载，**阻塞解析** | 并行下载，不阻塞 | 并行下载，不阻塞 |
| 执行时机 | 下载完立即执行，**阻塞解析** | HTML 解析完成后、**DCL 之前** | 下载完立即执行（随时，执行时阻塞解析） |
| 执行顺序 | 按书写顺序 | **按书写顺序** | **不保证**（谁先下载完谁先跑） |
| 与 DOMContentLoaded | 必在 DCL 前 | DCL **等待** defer 执行完 | 关系不确定（可能在 DCL 前也可能后） |

- **高频陷阱**：`defer`/`async` **只对外部脚本（带 src）生效**，内联脚本写这两个属性会被浏览器静默忽略
- 现代替代：`type="module"` 的脚本**默认就是 defer 行为**（并行下载、解析后按序执行），module + async 则类似 async
- 选型口诀：依赖 DOM 或互相有依赖的用 defer；独立第三方脚本（统计、广告）用 async；module 时代基本告别手动 defer

### Q5 ⭐⭐ CSS 会影响 DOMContentLoaded 吗？（进阶区分题）

**答案要点**（三层结论，缺一不可）：
1. **CSS 不阻塞 DOM 解析**：HTML 解析器构建 DOM 树不等样式表
2. **CSS 阻塞其后的脚本执行**：脚本可能读取样式（getComputedStyle/offsetWidth），必须等 CSSOM 就绪——所以 defer/普通脚本前面若有未加载完的 CSS，脚本被推迟，**DOMContentLoaded 被间接推迟**
3. **CSS 阻塞渲染**：首屏 paint 需要 DOM + CSSOM 合成渲染树，CSS 没加载完页面不绘制（否则会闪无样式内容 FOUC）

**一句话版**：CSS 不阻塞解析、阻塞渲染、阻塞后续脚本——DCL 本身不等 CSS，但会被"CSS 卡住的脚本"连累。

### Q6 ⭐⭐⭐ 综合执行顺序题（含 DOMContentLoaded）

```html
<!DOCTYPE html>
<html>
<head>
    <script src="defer.js" defer></script>    <!-- defer.js 内容：console.log('defer') -->
    <script src="async.js" async></script>    <!-- async.js 内容：console.log('async')，假设下载很快 -->
    <script>
        console.log('sync')
        document.addEventListener('DOMContentLoaded', () => console.log('DCL'))
        window.addEventListener('load', () => console.log('load'))
        Promise.resolve().then(() => console.log('micro'))
        requestAnimationFrame(() => console.log('rAF'))
    </script>
</head>
<body><img src="big.png"></body>
</html>
```

**参考答案**（async 在解析期间下载完成的常见情形）：
```
sync → micro → async → defer → DCL → rAF（首帧渲染前）→ load
```

**逐步拆解**：
1. head 内联脚本作为一个宏任务执行：打印 sync，注册监听器，Promise 微任务入队，rAF 入队
2. 脚本结束 → 清空微任务：打印 **micro**
3. async.js 先下载完，立即执行：打印 **async**（顺序不保证，本题假设它快于解析完成）
4. HTML 解析完成 → 执行 defer.js：打印 **defer**
5. 派发 DOMContentLoaded（宏任务）：打印 **DCL**
6. 首帧渲染前执行 rAF：打印 **rAF**
7. big.png 加载完成 → 派发 load（宏任务）：打印 **load**

**⭐ 进阶追问**：如果再加一句 `setTimeout(() => console.log('timeout'), 0)`，timeout 一定在 DCL 后吗？
> **不一定**。setTimeout(0) 在内联脚本执行时入队计时，DCL 在解析完成时入队派发——谁先执行取决于"解析剩余 HTML 花的时间"和"定时器到点时间"哪个先。小页面解析快，DCL 通常先；大页面/慢设备上 timeout 可能先。**两者顺序无规范保证**——能答出这个不确定性，比背一个固定顺序更加分。

### 页面加载完整执行顺序图 ⭐（白板必画）

**主线流程**（自上而下即时间顺序）：

`① 解析 HTML` → `② 执行 defer` → `③ DOMContentLoaded ★` → `④ 首帧渲染` → `⑤ load ★` → `⑥ 稳态事件循环`

| 阶段 | 发生什么 | 必背关键点 |
|---|---|---|
| ① HTML 流式解析 | 边下载边解析；普通 script 暂停解析执行；defer/async 后台并行下载 | CSS **不阻塞解析**，但**阻塞其后脚本执行与渲染** |
| ② defer 脚本按序执行 | 解析完成后、DCL 之前，按书写顺序执行，可访问完整 DOM | defer/async **只对外部脚本生效**，内联脚本写这俩属性被静默忽略 |
| ③ DOMContentLoaded ★ | 以**宏任务**派发 | 条件：解析完 + defer 执行完；**不等**图片/iframe/async |
| ④ 首帧渲染 | rAF → Style → Layout → Paint → Composite | 解析很快时可能与 ③ 交错，属浏览器调度自由 |
| ⑤ load ★ | 以**宏任务**派发 | 条件：**所有资源**（图片/CSS/iframe/async）就绪，必在 ③ 之后 |
| ⑥ 稳态事件循环 | 每轮：宏任务 → 清空微任务 → rAF → 渲染 → rIC → 下一宏任务 | DCL/load 的监听器同样走这套规则 |

> 白板默画：先写主线流程那一行箭头（①→⑥），再逐个阶段口头补「必背关键点」列；setTimeout(0) 与 ③ 的顺序无规范保证（见 Q6 追问）。

**记忆锚点**：两个生命周期事件（DCL/load）不是特殊通道，**它们就是宏任务**——一旦理解这点，它们与 setTimeout/事件回调的顺序问题全部可以用事件循环规则推导，不用背。

### Q7 ⭐ 经典输出题：写出执行顺序

```js
console.log(1)
setTimeout(() => console.log(2), 0)
Promise.resolve().then(() => console.log(3))
Promise.resolve().then(() => {
    console.log(4)
    setTimeout(() => console.log(5), 0)
})
new Promise(resolve => { console.log(6); resolve() }).then(() => console.log(7))
console.log(8)
```

**答案**：`1 6 8 3 4 7 2 5`

**拆解**：
1. 同步：1、6（Promise 构造函数同步执行）、8
2. 清空微任务：3、4（4 里面注册的 setTimeout 进入宏任务队列）、7
3. 渲染时机（此处无渲染内容）
4. 宏任务：2、5

### Q8 ⭐⭐ 为什么微任务可能导致页面卡死，而宏任务不会？

**答案要点**：
- 微任务队列是**清空制**——微任务里注册新的微任务会被同一轮继续执行，循环注册微任务将永远阻塞，渲染和后续宏任务都得不到执行，页面卡死：

```js
// 死循环卡死页面
function loop() { Promise.resolve().then(loop) }
loop()
```

- 宏任务是**一轮一个**——setTimeout 递归循环每轮之间都有渲染机会，页面不卡但会持续占用：

```js
// 页面不卡，但任务持续执行
function loop() { setTimeout(loop, 0) }
loop()
```

- 延伸考点：大数据处理要**分片用宏任务**（setTimeout/scheduler.yield），让出渲染时机

### Q9 ⭐⭐ async/await 输出顺序题

```js
async function async1() {
    console.log('a')
    await async2()
    console.log('b')
}
async function async2() { console.log('c') }
console.log('d')
async1()
console.log('e')
```

**答案**：`d a c e b`

**关键认知**：`await` 后面的代码等价于包在 `.then` 里的微任务；`await async2()` 执行时，async2 同步执行打印 c，然后 `console.log('b')` 被挂入微任务队列，让出主线程继续同步代码 e，最后微任务 b

### Q10 ⭐ MutationObserver、rAF、setTimeout 的先后

```js
const div = document.createElement('div')
document.body.appendChild(div)
const observer = new MutationObserver(() => console.log('mutation'))
observer.observe(div, { attributes: true })
requestAnimationFrame(() => console.log('rAF'))
setTimeout(() => console.log('timeout'), 0)
div.setAttribute('data-x', '1')
console.log('sync')
```

**答案**：`sync → mutation → rAF → timeout`（rAF 与 timeout 在不同浏览器同帧场景下可能紧贴，但 mutation 必在 rAF 前）

**拆解**：MutationObserver 是微任务 → 渲染前清空微任务 → rAF 在渲染前执行 → setTimeout 是下一轮宏任务

### Q11 ⭐⭐ 长任务导致渲染卡顿的原理是什么？如何监控？

**答案要点**：
- 浏览器每 16.7ms 需要一次渲染机会，宏任务/微任务执行超过 50ms 即为**长任务（Long Task）**，阻塞渲染导致掉帧、输入无响应
- 监控手段：

```js
new PerformanceObserver(list => {
    for (const entry of list.getEntries()) {
        console.log('长任务耗时:', entry.duration)
    }
}).observe({ entryTypes: ['longtask'] })
```

- 治理方向：拆分长任务（时间切片）、计算移入 Web Worker、减少单帧 DOM 操作

## 23.2 作用域、闭包与提升

### Q12 ⭐ var / let / const 的区别？

**答案要点**：
- var：函数作用域、变量提升（提升后值为 undefined）、可重复声明、无暂时性死区
- let/const：块级作用域、提升但处于**暂时性死区**（TDZ，声明前访问报 ReferenceError）、不可重复声明
- const：声明时必须初始化，引用不可重新绑定（对象内容可改）
- 循环中的经典差异：var 循环 + setTimeout 全打印同一个值（共享绑定）；let 每次迭代创建新绑定

### Q13 ⭐ 闭包是什么？有什么用？有什么坑？

**答案要点**：
- 定义：函数 + 其词法作用域的引用组合，内层函数持有外层变量使其不被 GC
- 用途：数据私有化（模块模式）、柯里化、防抖节流的状态保存、回调中保留上下文
- 坑：循环中闭包共享变量、闭包持有大对象导致内存无法释放（内存泄漏高频来源）

### Q14 经典题：以下代码输出什么？如何修改使其输出 0 1 2？

```js
for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 0)
}
```

**答案**：输出三个 3（var 共享同一个绑定，回调执行时循环已结束）

**修复方案**（能说出 3 种以上）：
1. `for (let i = ...)` —— 块级作用域每轮新绑定
2. IIFE 包裹：`(function(j){ setTimeout(() => console.log(j), 0) })(i)`
3. setTimeout 第三参数传值：`setTimeout(j => console.log(j), 0, i)`
4. bind 预设参数：`setTimeout(console.log.bind(null, i), 0)`

## 23.3 this 指向

### Q15 ⭐ this 的四种绑定规则及优先级？

**答案要点**（按优先级从低到高）：
1. **默认绑定**：独立函数调用，this 指向全局对象（严格模式下为 undefined）
2. **隐式绑定**：`obj.fn()`，this 指向调用点对象 obj
3. **显式绑定**：call/apply/bind 指定 this
4. **new 绑定**：构造函数调用，this 指向新创建的对象
- 例外：箭头函数**无自己的 this**，捕获定义时外层作用域的 this，且无法被 call/apply 改变
- 经典坑：`const fn = obj.fn; fn()` —— 隐式绑定丢失，退化为默认绑定

### Q16 输出题：

```js
const obj = {
    name: 'obj',
    fn: function() { console.log(this.name) },
    arrow: () => console.log(this.name)
}
const { fn, arrow } = obj
fn()    // ?
arrow() // ?
```

**答案**：均输出 undefined（浏览器非严格模式下 fn 输出 window.name 即空字符串 ''；严格模式 fn 报错）
- fn 解构后独立调用 → 默认绑定
- arrow 定义在对象字面量层（该层无函数作用域），this 指向外层（全局/模块层），不指向 obj

## 23.4 原型与继承

### Q17 ⭐ 原型链是什么？`__proto__`、prototype、constructor 的关系？

**答案要点**：
- 每个对象有内部属性 `[[Prototype]]`（通过 `__proto__` 访问），指向其构造函数的 `prototype`
- 查找属性时沿原型链向上，直到 `Object.prototype`（其 `__proto__` 为 null，链终点）
- `Fn.prototype.constructor === Fn`；`实例.__proto__ === Fn.prototype`；`Fn.prototype.__proto__ === Object.prototype`
- 函数也是对象：`Fn.__proto__ === Function.prototype`

### Q18 ⭐ new 操作符做了什么？手写实现

**答案要点**：
1. 创建一个新对象，原型指向构造函数的 prototype
2. 将构造函数的 this 绑定到新对象并执行
3. 构造函数返回对象则用之，否则返回新对象

```js
function myNew(Constructor, ...args) {
    const obj = Object.create(Constructor.prototype) // 1. 新对象，原型指向构造函数 prototype
    const result = Constructor.apply(obj, args)      // 2. 执行构造函数，this 指向新对象
    return (result !== null && typeof result === 'object') ? result : obj // 3. 构造函数返回对象则用之，否则用新对象
}
```

### Q19 ES6 class 与 ES5 构造函数继承的区别？

**答案要点**：
- class 是语法糖，底层仍是原型继承，但更严格：
  - class 声明不存在提升（TDZ）
  - class 内部默认严格模式
  - 子类构造函数必须调 super 才能用 this（ES5 寄生组合继承无此限制）
  - class 的方法不可枚举
- `super()` 在子类中创建 this 绑定；ES5 中是父类构造函数.call(this) 赋予属性

## 23.5 类型系统与隐式转换

### Q20 ⭐ typeof / instanceof / Object.prototype.toString 的区别与缺陷？

**答案要点**：
- typeof：识别原始类型（除 null，typeof null === 'object' 是历史 bug）；typeof 函数为 'function'；对数组/日期/正则都返回 'object'
- instanceof：沿原型链判断构造函数，**跨 iframe/Realm 失效**（不同全局环境的 Array 不是同一个）
- `Object.prototype.toString.call()`：最可靠，返回 `[object Array]` 等精确类型
- 现代补充：Array.isArray、Number.isNaN（与全局 isNaN 的区别：不做隐式转换）

### Q21 ⭐ == 的隐式转换规则？经典题

**答案要点**：
- 规则：同类型直接比；null == undefined（且只与彼此相等）；数字与字符串比 → 字符串转数字；布尔参与 → 转数字；对象与原始值比 → 对象 ToPrimitive（先 valueOf 后 toString）
- 经典输出：

```js
[] == ![]        // true（![] → false → 0；[] → '' → 0）
[] == []         // false（引用不同）
null == undefined // true
null == 0        // false（null 只等于 undefined）
NaN == NaN       // false
'1' == true      // true（'1'→1, true→1）
```

- 工程建议：一律 ===，需要宽松判断 null/undefined 时用 `x == null` 这一种例外

## 23.6 异步编程

### Q22 ⭐ Promise 三种状态与链式调用的关键规则？

**答案要点**：
- pending → fulfilled / rejected，状态不可逆
- then 返回**新 Promise**：回调返回普通值则新 Promise 以该值 fulfilled；返回 Promise 则跟随其状态；抛错则 rejected
- catch 之后还能 then——异常被捕获后链恢复
- Promise.all / allSettled / race / any 的区别：全成才成 / 全部落定 / 先到先得（含失败） / 第一个成功

### Q23 ⭐ 手写 Promise.all

完整可运行实现（含 allSettled / race / any 四件套）见 [examples/23-01-promise-all.ts](./examples/23-01-promise-all.ts)：

```typescript
// 文件: examples/23-01-promise-all.ts
export function promiseAll<T>(promises: Iterable<T | PromiseLike<T>>): Promise<T[]> {
    return new Promise((resolve, reject) => {
        const arr = Array.from(promises);
        const results = new Array<T>(arr.length);
        let done = 0;
        if (arr.length === 0) return resolve(results);
        arr.forEach((p, i) => {
            Promise.resolve(p).then(
                (val) => {
                    results[i] = val;          // 按原下标保序
                    if (++done === arr.length) resolve(results);
                },
                reject,                       // 任一失败立即整体失败
            );
        });
    });
}
```

> 运行方式：`cd examples && npx tsx 23-01-promise-all.ts`

**高频追问**：allSettled 用 `.finally` 统一计数；race 直接 for...of 注册；any 全部失败时抛 `AggregateError`（ES2021，旧环境需降级）。

### Q24 async/await 的错误处理与并发？

**答案要点**：
- await 的 reject 会抛异常，需 try/catch 或 `.catch()` 捕获，否则向上冒泡为 unhandledrejection
- 并发陷阱：`await a(); await b()` 是串行；无依赖时应 `await Promise.all([a(), b()])`
- forEach 中 await 不生效（回调各自独立），串行用 for...of，并行用 map + Promise.all

## 23.7 深浅拷贝

### Q25 ⭐ 深拷贝方案对比？手写一个处理循环引用的深拷贝

**答案要点**：
- `JSON.parse(JSON.stringify())`：丢失 undefined/函数/Symbol，Date 变字符串，RegExp 变 {}，**循环引用直接抛错**
- `structuredClone()`：原生深拷贝，支持循环引用、Date/Map/Set，不支持函数和 DOM 节点
- 手写（WeakMap 处理循环引用），完整实现见 [examples/01-21-deep-clone.ts](./examples/01-21-deep-clone.ts)：

```js
function deepClone(obj, map = new WeakMap()) {
    if (obj === null || typeof obj !== 'object') return obj
    if (map.has(obj)) return map.get(obj)        // 循环引用返回已拷贝副本
    if (obj instanceof Date) return new Date(obj)
    if (obj instanceof RegExp) return new RegExp(obj.source, obj.flags)
    const clone = Array.isArray(obj) ? [] : {}
    map.set(obj, clone)                          // 先登记再递归，保证循环引用能找到
    for (const key of Object.keys(obj)) {
        clone[key] = deepClone(obj[key], map)
    }
    return clone
}
```

> 运行方式：`cd examples && npx tsx 01-21-deep-clone.ts`

## 23.8 防抖节流与高频手写

### Q26 ⭐ 防抖与节流的区别？手写实现

**答案要点**：
- 防抖 debounce：事件停止触发 n 秒后才执行最后一次（搜索联想、窗口 resize）
- 节流 throttle：n 秒内最多执行一次（滚动监听、按钮防连点）

完整实现（含立即执行版、定时器版）见 [examples/01-20-debounce-throttle.ts](./examples/01-20-debounce-throttle.ts)：

```js
function debounce(fn, wait) {
    let timer = null
    return function(...args) {
        clearTimeout(timer)
        timer = setTimeout(() => fn.apply(this, args), wait)
    }
}

function throttle(fn, wait) {
    let last = 0
    return function(...args) {
        const now = Date.now()
        if (now - last >= wait) {
            last = now
            fn.apply(this, args)
        }
    }
}
```

> 运行方式：`cd examples && npx tsx 01-20-debounce-throttle.ts`

- 追问：防抖的立即执行版（leading edge）、节流的定时器版（trailing 保证最后一次也执行）

### Q27 ⭐ 手写 call / apply / bind

完整实现见 [examples/01-11-mybind.ts](./examples/01-11-mybind.ts)：

```js
Function.prototype.myCall = function(context = window, ...args) {
    const key = Symbol('fn')
    context[key] = this            // 把函数挂到目标对象上，形成隐式绑定
    const result = context[key](...args)
    delete context[key]
    return result
}
// apply 仅参数改为数组；bind 返回包装函数且不立即执行：
Function.prototype.myBind = function(context, ...preset) {
    const fn = this
    return function(...args) {
        return fn.apply(context, [...preset, ...args])
    }
}
```

```js
function myInstanceof(obj, Constructor) {
    let proto = Object.getPrototypeOf(obj)
    while (proto !== null) {
        if (proto === Constructor.prototype) return true
        proto = Object.getPrototypeOf(proto)
    }
    return false
}
```

```js
function flat(arr, depth = 1) {
```

## 23.9 数组与对象操作

### Q30 map / filter / reduce / forEach 的区别？forEach 能中断吗？

**答案要点**：
- map 返回新数组（等长映射）、filter 返回筛选新数组、reduce 聚合任意值、forEach 只遍历无返回
- forEach **不能用 break/return 中断**（return 只跳过当前次）；需要中断用 for...of / for 循环 / some / every
- reduce 不传初始值的坑：空数组抛错；首元素当初值

### Q31 数组去重的 N 种方式？

**答案要点**：
1. `[...new Set(arr)]` —— 最简单，引用类型按引用去重
2. `arr.filter((x, i) => arr.indexOf(x) === i)`
3. 对象数组按 key 去重：`Object.values(arr.reduce((m, x) => (m[x.id] = x, m), {}))` 或 Map
4. 含 NaN 的场景：Set 可去重 NaN，indexOf 找不到 NaN（需 findIndex + Number.isNaN）

## 23.10 ES6+ 特性

### Q32 箭头函数与普通函数的区别（能说出 5 条）？

**答案要点**：
1. 无自己的 this（捕获定义层 this）
2. 不能用作构造函数（new 报错）
3. 无 arguments 对象（用 rest 参数替代）
4. 无 prototype 属性
5. 不能用作生成器（无 yield）
6. 不适用场景：对象方法、原型方法、需要动态 this 的事件回调

### Q33 解构赋值的常见坑？

**答案要点**：
- 默认值只在值为 **undefined** 时生效（null 不触发）
- 对象解构 `const { a } = null` 抛 TypeError；数组解构要求右边可迭代
- 剩余参数必须是最后一个：`const [a, ...rest] = arr`

### Q34 Proxy 能拦截什么？与 Object.defineProperty 对比？

**答案要点**：
- Proxy 可拦截 13 种操作：get/set/has/deleteProperty/ownKeys/apply/construct 等
- 优势：监听新增/删除属性、数组索引与 length、惰性代理（无需初始化递归）、可拦截对象级操作（in、delete、keys 枚举）
- defineProperty 局限：只能监听已有属性的 get/set，Vue2 因此需要 $set 和数组方法重写
- 不可逆：Proxy 一旦创建无法撤销拦截（除 Proxy.revocable）

## 23.11 内存与垃圾回收

### Q35 V8 的垃圾回收机制？

**答案要点**：
- **新生代**（小而频繁）：Scavenge 算法，From/To 两个空间复制交换，存活两次晋升老生代
- **老生代**：标记-清除（Mark-Sweep）+ 标记-整理（Mark-Compact）防内存碎片；增量标记 + 惰性清理减少停顿

3. 未解绑的 EventBus / 订阅

5. 闭包长期持有大数据

## 23.12 综合手写题

### Q37 实现一个简易 EventEmitter

完整实现见 [examples/01-22-event-bus.ts](./examples/01-22-event-bus.ts)：

```js
class EventEmitter {
    constructor() { this.events = {} }
    on(name, fn) { (this.events[name] ||= []).push(fn); return this }
    off(name, fn) {
        if (!fn) delete this.events[name]
        else this.events[name] = (this.events[name] || []).filter(f => f !== fn)
        return this
    }
    emit(name, ...args) { (this.events[name] || []).slice().forEach(fn => fn(...args)); return this }
    once(name, fn) {
        const wrapper = (...args) => { this.off(name, wrapper); fn(...args) }
        return this.on(name, wrapper)
    }
}
```

</details>

> **结语**：JS 面试的核心是"把运行时机制讲清楚"——事件循环、作用域链、原型链、this 绑定、Promise 状态机，这五条主线串起了 80% 的高频题。把每道输出题的每一步都讲明白，把手写题的每个边界（空数组、循环引用、this 丢失）都覆盖到，面试就从"背答案"变成"推机制"。

## 23.14 本章避坑清单

> 把本章散落在各节的原则收口成一份可检索清单，按日常出现频率排序；详情回上方对应小节。

| 场景 | 高频坑 | 一句话避法 |
| --- | --- | --- |
| `var` 与 TDZ | 以为 `var` 不提升、`let` 随便用 | `var` 声明提升但值为 `undefined`；`let`、`const` 有 TDZ，声明前访问直接抛 `ReferenceError` |
| 输出题 | 事件循环输出题的宏微任务顺序背反 | 同步代码跑完 → 清空微任务队列（含微任务里新注册的）→ 一轮一个宏任务，轮间才有渲染 |
| 闭包捕获 | 循环里绑事件，回调都读到同一个终值 | `var` 共享同一变量，改用 `let`（每轮独立绑定）、IIFE、`forEach` 闭包锁定当前值 |
| 解构默认值 | 传了 `null` 却期望默认值兜底 | 默认值只在值为 `undefined` 时生效，`null` 不触发兜底，需显式判空 |
| `this` 绑定 | `const fn = obj.fn; fn()` 里 `this` 丢了 | 隐式丢失退化成默认绑定；用 `bind`、箭头函数固定 `this`，箭头函数没有自己的 `this` |
| 千分位格式化 | 只处理正整数，负数、小数、大数出错 | 先分离符号与小数部分，整数段从右往左每三位插逗号，`toLocaleString` 可兜底 |
| 柯里化 | 空参调用与参数截断的边界没处理 | 累积参数达到原函数 `length` 才执行，显式处理调用时传 `0` 个参数的分支 |
| 内存泄漏 | 监听、定时器、闭包持有大对象没释放 | 成对写 `removeEventListener`、`clearInterval`，组件卸载时置空引用 |
