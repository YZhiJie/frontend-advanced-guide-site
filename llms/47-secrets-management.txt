## 47.1 密钥分级与「前端无秘密」全景

### 47.1.1 概念解析

**前端无秘密**：任何被打包进产物、被浏览器下载的代码，都是公开代码。不要在前端源码里写任何不可公开的值——包括「反正用户也看不懂」的密钥。

但这不意味着前端不能跟第三方 API 交互。先建立**分级模型**，再谈「谁可以出现在前端」：

| 类型 | 典型例子 | 泄漏后果 | 前端可见？ |
| --- | --- | --- | --- |
| **publishable 公开密钥** | Stripe publishable key、Sentry DSN、带 referrer 限制的 Google Maps key | 可被刷配额，但无致命权限 | ✅ 可以出现在前端，但须加限制策略 |
| **restricted 受限密钥** | 带 HTTP Referrer 限制且含 IP 白名单的 CDN token | 泄漏后受域名/IP 约束，仍有被滥用风险 | ⚠️ 可出现在前端，但限制策略是底线 |
| **server-only 绝不下船** | AWS AK/SK、支付 secret、数据库密码、GitHub PAT、JWT 签名密钥 | 直接导致服务失陷或资金损失 | ❌ 绝不进入前端包、日志、产物 |

关键认知：**server-only 密钥的前端处理原则是「BFF 代理」**。凡是需要 server-only secret 才能完成的请求，一律由 BFF（或 Serverless Function）代发；前端只接收 BFF 返回的公开结果、签名 URL、或短期 STS 凭证。

### 47.1.2 密钥流向全景图

```mermaid
graph LR
    A[Vault / 云密钥服务] -->|动态签发/轮换| B[CI/CD 安全注入]
    B -->|server-only| C[服务端 / BFF]
    B -->|publishable| D[构建期注入]
    C -->|签名 URL / STS / 业务结果| E[浏览器前端]
    D -->|VITE_ 等公开前缀| E
```

#### 前端可见密钥的最小清单

前端产物中**只应出现**以下两类信息：

1. **publishable key**：Stripe publishable key、Sentry DSN、公开分析 SDK key（且已在第三方后台加了 referrer 限制）；
2. **运行期下发的公开配置**：API 域名、功能开关、埋点采样率——不含任何 secret。

一切 else 都在 server-only 区，禁止出现在前端包内。

### 47.1.3 最佳实践

- ✅ 团队文档第一页就写「前端无秘密」——不是技术问题，是纪律问题；
- ✅ 新成员 onboarding 走密钥申领流程，禁止微信/钉钉发密钥；
- ⚠️ publishable key 也必须加限制策略（referrer、IP、用量上限），不要因为是「可公开」就裸奔；
- ❌ 不要把 `.env.local` 改名成 `.env.local.bak` 就以为 git 看不见——后缀不是 `.gitignore` 的逻辑，文件名不含 `.local` 照样被追踪。

## 47.2 本地开发：.env 体系与团队分发

### 47.2.1 概念解析

本地开发是密钥泄漏的**高发阶段**：为了方便调试，开发者倾向于把密钥直接写进代码、console.log 打印、截图发到群里。

正确的 `.env` 文件体系分三层：

| 文件 | 用途 | 是否入 git |
| --- | --- | --- |
| `.env` | 公共默认值（如 `APP_NAME`、`DEFAULT_LOCALE`） | ✅ |
| `.env.local` | 个人密钥、本地数据库密码 | ❌ |
| `.env.{development,staging,production}` | 环境特化配置（如 API 域名） | ✅（但只放公开值） |

**`.gitignore` 基线**：

```gitignore
.env.local
.env.*.local
!.env.example
```

同时放一个 **`.env.example`**（去掉真实值、只留 key 名和注释），新成员复制改名后自己填值——这是唯一入仓库的环境文件。

### 47.2.2 框架差异与注入前缀

| 框架 | 暴露前缀 | 说明 |
| --- | --- | --- |
| Vite | `VITE_` | 只有 `VITE_` 前缀的变量会出现在 `import.meta.env` |
| Next.js | `NEXT_PUBLIC_` | 同上；其余变量只在 Node 服务端可见 |
| Create React App | `REACT_APP_` | 历史遗留，新项目建议切到 Vite / Next.js |
| dotenv (Node) | 无 | 全部加载到 `process.env`，需自行隔离 secret |

**核心原理**：这些前缀不是魔法——构建工具在打包时做**字符串替换**。如果密钥进了 `import.meta.env.VITE_PAY_SECRET`，产物里就会有一行明文 `sk_live_xxxx`。

### 47.2.3 团队分发规范

密钥分发走**正式通道**，禁止走 IM：

- **1Password / Bitwarden 团队金库**：成员按角色授权，离职即回收；
- **Vault dev 角色**：开发机启动时自动拉取短期凭证（15min~1h），过期需重新认证；
- **CI 动态注入**：CI job 用 OIDC 向云厂商换临时 token，本地开发不用长期 AK。

### 47.2.4 最佳实践

- ✅ `.env.example` 同步更新——新增必填配置时，不更新 example = 新成员启动必炸；
- ✅ 本地启动前跑一次 `git status`，确认没有误新增 `.env.*`；
- ⚠️ `console.log(process.env)` 在 SSR 阶段等于把全量密钥打到服务端日志；
- ❌ 不要把密钥写在 `README.md` 的「快速开始」命令里——README 是公开的。

## 47.3 注入方案：构建期 vs 运行时与启动门禁

### 47.3.1 概念解析

前端项目的密钥注入分两条路，本质差异是「值出现在产物里还是运行时才拿到」：

| 方式 | 原理 | 适用 key 类型 | 风险 |
| --- | --- | --- | --- |
| **构建期注入** | 构建工具字符串替换：`import.meta.env.VITE_XXX` → 直接替换为值 | publishable key | 值打包进产物，任何人 view-source 可见 |
| **运行时注入** | 页面加载后，从 `window.__ENV__` / `config.json` / BFF 接口读取 | 公开配置、publishable key | 仍需网络层保护（CORS / referrer） |

**Build once, deploy many**：同一份产物要跑在 dev/staging/prod 三环境时，**必须用运行时注入**。否则每次切环境都要重新打包，既慢又容易把 dev 密钥打到 prod 产物里。

### 47.3.2 运行时注入四路

```typescript
// 文件: src/config/runtime-config.ts —— 虚拟工程文件
// ---- 1. SSR / 容器注入:window.__ENV__ ----
const runtime = (typeof window !== 'undefined' && (window as any).__ENV__) || {};

// ---- 2. 构建后替换:nginx envsubst ----
// 产物中保留占位符 `API_BASE_URL=${API_BASE_URL}`
// entrypoint 脚本用 envsubst 替换后启动 nginx

// ---- 3. 服务端 BFF 下发 /config.json ----
// 前端先请求 /api/config,拿到当前环境的公开配置(不含 secret)

// ---- 4. 请求级短期凭证:签名 URL / STS ----
// 后端生成预签名 URL 给前端直传 OSS,前端全程不碰 AK/SK
```

### 47.3.3 启动门禁：缺配置就拒启动

运行时注入的代价是「配置缺失要到运行时才暴露」。启动门禁在应用入口一次性校验所有必填配置，**三处错误一次报完**（而不是炸一个修一个）：

```typescript
// 文件: examples/47-02-env-guard.ts（此处为核心节选,完整版含全部断言）
// Schema 校验三要素:
//   required / pattern / enum / transform;
//   secret 字段在启动快照中自动脱敏;
//   校验通过后 Object.freeze(config),禁止运行期篡改。
const config = validateEnv(SCHEMA, process.env);
console.log('启动快照:', snapshotOf(SCHEMA, config)); // PAY_SECRET=sk_l****(已脱敏)
```

> 运行方式：`npx tsx examples/47-02-env-guard.ts`（坏配置一次聚合 3 处错误，全绿后脱敏快照 + 冻结对象）。

### 47.3.4 最佳实践

- ✅ 前端产物中只保留 publishable key 和公开域名；所有 server-only 走 BFF 代理；
- ✅ 启动门禁把 `undefined` 和空字符串一视同仁——空字符串同样会导致下游请求带 `Authorization: Bearer ` 这种尴尬头部；
- ⚠️ `window.__ENV__` 在 HTML 中写明文，爬虫也能读到，只能放 publishable 配置；
- ❌ 不要把「构建期注入」当安全手段——任何进 `import.meta.env` 的值都会在产物里全文可搜。

## 47.4 泄漏防控工具链：扫描、脱敏与应急响应

### 47.4.1 扫描三阶：本地 → CI → 平台

密钥泄漏 80% 来自「误提交进 git」。三道防线：

1. **本地 pre-commit**：gitleaks / git-secrets / truffleHog 拦截在提交前；
2. **CI 门禁**：trivy secrets / semgrep secrets / 自建扫描器（见示例 47-01）在 PR 合并前扫；
3. **GitHub Push Protection**：组织级开启后，GitHub 会在 push 时实时拦截高置信度 secret。

扫描器的核心原理是**模式库 + 白名单 + 非零退出**：

```typescript
// 文件: examples/47-01-secret-scanner.ts（此处为核心节选,完整版含全部断言）
// 模式库覆盖 AWS AKIA / OpenAI sk- / GitHub ghp_ / JWT / 私钥块 / 通用赋值;
// 白名单放行 process.env / import.meta.env / 文档占位符(xxxx);
// 命中即非零退出,扫描报告本身也做截断预览,不携带完整密钥。
```

> 运行方式：`npx tsx examples/47-01-secret-scanner.ts`（虚拟仓库扫描命中 4 处泄漏，白名单文件无误报，报告预览截断）。

### 47.4.2 日志脱敏：两道闸门

密钥泄漏的第二大通道是**日志与监控上报**。异常堆栈的 `context`、fetch 拦截器、甚至 `console.log` 都可能带密钥。

脱敏策略分两道闸门：

1. **key 名单**：字段名含 `password`/`token`/`secret`/`authorization` 等，整体打码；
2. **value 模式**：字符串值匹配 JWT / 手机号 / 身份证 / API token，全局替换。

```typescript
// 文件: examples/47-03-log-redactor.ts（此处为核心节选,完整版含全部断言）
// 脱敏规则:短串全遮,长串留前 3 后 3(如 sk_l…wX9)——既安全又可用于排查对账;
// 递归遍历嵌套对象/数组,循环引用安全退出;
// 演示 console 包装层与 fetch 上报前脱敏。
```

> 运行方式：`npx tsx examples/47-03-log-redactor.ts`（嵌套对象递归脱敏、console 包装拦截、循环引用不炸）。

### 47.4.3 应急响应：先止血，再整容

发现密钥进了 git 历史后，「删掉重新提交」毫无意义——历史里还在。必须按**泄漏事件**处置：

1. **撤销/禁用旧密钥**（止血）——让旧密钥立即失效；
2. **签发新密钥并全量轮换**——所有调用方切到新密钥；
3. **清洗 git 历史**（整容）——用 `git filter-repo` / BFG 从历史中抹掉密钥，协作者强制重克隆；
4. **审计与复盘**——调用日志排查是否已被利用，流程补丁落地。

**顺序铁律**：必须先撤销轮换再清洗历史。顺序反了等于在「密钥仍在公网历史里裸奔」的期间没有任何保护。

```typescript
// 文件: examples/47-04-leak-response.ts（此处为核心节选,完整版含全部断言）
// 定级:P0(支付/云 AK) vs P1(仓库 token/JWT);
// 双密钥并行轮换:old-only → dual-active → new-only → old-revoked,禁止硬切换;
// 每步带 owner 与验收标准,处置单可审计、可复盘。
```

> 运行方式：`npx tsx examples/47-04-leak-response.ts`（P0 定级、四步处置单顺序验证、双密钥并行状态机）。

### 47.4.4 最佳实践

- ✅ 扫描器非零退出是硬门禁——发现即拦，不允许「先合并再补」；
- ✅ 日志脱敏用「留头尾」而不是全星号——全遮的日志等于没记，留头尾可以在安全审计时做唯一性排查；
- ✅ git 历史清洗后，**所有协作者必须强制重克隆**——因为旧提交哈希已变，`git pull` 会冲突；
- ⚠️ 补偿动作里「 revoke 旧密钥」必须在「生成新密钥」之前？不，一般是先签发新密钥确保服务不中断，再 revoke 旧密钥；但 revoke 必须在清洗历史之前完成；
- ❌ 不要把密钥写在异常 message 里：`throw new Error('调用失败，token=sk_live_xxx')`——错误上报直接带走。

> 📖 **延伸阅读**：同样的「先止血、再修复、后复盘」节奏也适用于依赖漏洞，见 [66.5 高危漏洞修复 SOP](./66-dependency-governance.md#_66-5-高危漏洞修复-sop)。

## 47.5 CI/CD 与云端密钥服务

### 47.5.1 概念解析

CI/CD 是密钥的**高密接触点**：构建、测试、部署每一步都需要凭证，且这些凭证往往拥有高权限（云资源全读写）。

现代 CI 的演进路线是「**从静态 secret 到无密钥（keyless）**」：

| 阶段 | 做法 | 风险 |
| --- | --- | --- |
| 1.0 明文硬编码 | 密钥写在 CI yaml / 仓库文件 | 最高 |
| 2.0 CI secrets | GitHub Actions secrets / GitLab CI variables | 中等（泄露后需手动轮换） |
| 3.0 环境隔离 + OIDC | 环境级 secrets + OIDC 连接云厂商，用短期 token 替代长效 AK | 低（token 自动过期） |

### 47.5.2 GitHub Actions 密钥管理

```yaml
# 文件: .github/workflows/deploy.yml —— 虚拟工程文件
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production            # ✅ 环境级 secret,可配 required reviewers
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/deploy-role
          aws-region: ap-northeast-1
      # 不再需要 aws-access-key-id / aws-secret-access-key —— OIDC 换短期 token
```

Actions secrets 的自动 **masking** 会把 secrets 的 stdout 输出替换成 `***`，但仍需防范：

- 第三方 actions 的供应链攻击（只 pin 可信动作版本，不用 `@master`）；
- `env` 里把 secret 传给不可信脚本；
- 构建产物中意外打包了 secret（`build.sourcemap: 'hidden'` + CI 上传后删除，见 46.6）。

### 47.5.3 Vault 与 KMS

- **HashiCorp Vault**：BFF 用 AppRole / Kubernetes auth 登录，动态签发数据库凭证或云 AK，自带 TTL 和自动续期。前端永远不与 Vault 直接通信；
- **AWS Secrets Manager / Parameter Store**：Secret 加密存储，BFF 用 IAM 角色读取；
- **KMS 信封加密**：密钥本身用 KMS 加密后存在配置中心，应用启动时解密——即使配置文件被拖走，没有 KMS 权限也解不开。

### 47.5.4 最佳实践

- ✅ CI 用 OIDC 替代长效 AK——这是 keyless 落地的最低成本动作；
- ✅ 环境级 secrets 配 required reviewers——生产部署必须人工审批；
- ⚠️ `secrets: inherit` 会让子 workflow 拿到全部 secrets，按需传参；
- ❌ 不要把 secret 当 `outputs` 传给后续 job——outputs 是明文的。

## 47.6 第三方 Key 的前端防护

### 47.6.1 概念解析

前端不可避免要使用第三方服务（地图、支付、埋点、AI），这些服务通常提供两类 key：

- **server-side secret**：绝对不发前端；
- **client-side publishable key**：设计为可公开，但仍需**防御纵深**。

### 47.6.2 公开 key 的防御纵深

| 层级 | 手段 | 配置位置 |
| --- | --- | --- |
| 1. referrer 限制 | 第三方后台绑定允许调用的域名 | 服务商控制台 |
| 2. IP 白名单 | 限制请求来源 IP（适合 BFF 出口固定 IP） | 服务商控制台 |
| 3. 用量上限 + 告警 | 设置每日/每月调用上限，超限自动熔断 | 服务商控制台 |
| 4. 速率限制 | 单用户/IP 级别限流 | 服务商控制台 / 网关层 |
| 5. 短期凭证 | 后端签发 15min 有效期的签名 URL / token | 自建 BFF |
| 6. BFF 代理 | 前端不持 key，所有请求经 BFF 转发 | 自建 BFF |

**Stripe 案例**：前端用 `publishable key` 创建 PaymentElement，但真正的支付 secret（`PaymentIntent` 的创建和确认敏感操作）由 BFF 完成。前端只拿到一个一次性的 `client_secret`，即使泄漏也只能用于本次支付。

**OSS 案例**：前端直传文件不持 AK/SK，后端生成**预签名 URL**（含临时 token 和过期时间），前端把文件 PUT 到这个 URL 即可。

### 47.6.3 最佳实践

- ✅ 第三方 key 一律在控制台加 referrer 限制——这是「零成本」的第一道墙；
- ✅ 高敏感操作（支付、删除、大额转账）必须经 BFF，前端只持「任务 ticket」；
- ⚠️ 公开 key 也要定期轮换——不要把「publishable」当成「永恒不变」；
- ❌ 不要把第三方 secret key 放在前端做「服务端签名」——浏览器里的签名等于把密钥送给用户。

## 47.7 自测题

1. 为什么「前端无秘密」是一条纪律而非技术选择？publishable key 和 server-only secret 的本质区别是什么？

<details><summary>查看答案</summary>

前端产物（JS/CSS/HTML）在发布后任何人都可以 view-source 或下载分析。任何写进源码、打包进产物的值都是公开的。publishable key 设计为可公开，且通过服务商后台的 referrer/IP/用量限制做了防御纵深；server-only secret 拥有致命权限（如云资源全读写、支付能力），一旦公开等于服务失陷。两者的区别不是「能不能被看到」，而是「被看到后能不能造成不可控损失」。
</details>

2. `.env.local` 和 `.env.example` 的分工是什么？`.gitignore` 应该怎么写？

<details><summary>查看答案</summary>

`.env.local` 放个人密钥和本地数据库密码，**绝对不入 git**；`.env.example` 放所有必填 key 的「空壳」（去掉真实值、保留 key 名和注释），作为新成员的复制模板，**必须入 git**。`.gitignore` 基线：`.env.local`、`.env.*.local` 忽略，`!.env.example` 放行。
</details>

3. 构建期注入（`import.meta.env`）和运行时注入（`window.__ENV__`）分别适合什么场景？为什么不能全部用构建期注入？

<details><summary>查看答案</summary>

构建期注入适合 publishable key（本来就可公开），构建工具在打包时做字符串替换，产物里直接出现值。运行时注入适合需要「Build once, deploy many」的场景——同一份产物跑在 dev/staging/prod 多环境时，运行时注入可以在不重新打包的情况下切换配置。全部用构建期注入会导致：①每环境重新打包，效率低；②容易把 dev 密钥打到 prod 产物里；③server-only secret 会打包进产物公开泄露。
</details>

4. 密钥泄漏应急响应为什么必须「先撤销/轮换，再清洗 git 历史」？顺序反了会怎样？

<details><summary>查看答案</summary>

因为 git 历史是公开的（或至少在团队/CI 中可访问），密钥一旦进入历史即视为「已泄漏」。如果先清洗历史再撤销密钥，清洗过程需要时间（尤其是大仓库、多协作者），在此期间攻击者仍可从历史中提取密钥并调用 API——相当于在「裸奔」期间没有任何保护。正确顺序：先让旧密钥失效（止血），再慢慢清洗历史（整容）。示例 47-04 完整演示了四步处置单与双密钥并行轮换状态机。
</details>

5. 扫描器为什么要加「白名单」？如果扫描器误报率太高会有什么后果？

<details><summary>查看答案</summary>

白名单用来放行合法的「类密钥」文本：示例占位符（`xxxx`）、环境变量引用（`process.env.XXX`）、测试夹具。没有白名单，扫描器会频繁误报，开发者很快就会学会「绕过」或「忽略」扫描结果（狼来了效应），最终真正的高危泄漏也会被埋没在噪音中。扫描器的有效性 = 检出率 × (1 - 误报率)。
</details>

6. 日志脱敏用「留头尾」（如 `sk_l…wX9`）比全星号（`***`）好在哪里？

<details><summary>查看答案</summary>

全星号完全丢失了字段的身份信息，排查问题时无法区分「这是哪个 key 的 token」「这是哪个用户的 JWT」。留头尾在保持安全（无法完整还原）的同时，保留了字段类型（以 `sk_` 开头的是 Stripe key，以 `eyJ` 开头的是 JWT）和唯一性标识（尾部几位可用于审计对账）。示例 47-03 的 mask 策略：短串全遮，长串留前 3 后 3。
</details>

7. CI/CD 用 OIDC 连接云厂商替代长效 AK 的核心优势是什么？前端项目如何受益？

<details><summary>查看答案</summary>

OIDC 的核心优势是「**无长期凭证**」：CI job 运行时向云厂商的 STS 服务申请短期 token（通常 1 小时），job 结束后 token 自动失效。即使 CI 日志被拖走，里面的 token 也已经过期。前端项目受益在于：部署流程不再需要人工管理 AK/SK 的轮换，且 CI secrets 中不再需要存储高权限云凭证，降低了泄露面。
</details>

8. 前端使用第三方 publishable key 时，最少应该做哪三层防护？

<details><summary>查看答案</summary>

① **referrer 限制**：在服务商控制台绑定允许调用的域名，防止其他站点盗刷；② **用量上限 + 告警**：设置每日/每月调用上限，超限自动熔断并触发告警；③ **BFF 代理高敏感操作**：支付确认、删除、大额转账等操作由后端代发，前端只持一次性 ticket 或预签名 URL。条件允许时，再加 IP 白名单和短期凭证。
</details>

## 47.8 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 把 server-only secret 写进前端代码 | 打包后全网公开，直接服务失陷 | 前端无秘密，secret 走 BFF 代理 |
| `.env.local` 误提交进仓库 | 个人密钥永久留在 git 历史 | `.gitignore` 基线 + pre-commit 扫描 |
| 用构建期注入放 server-only secret | 产物里全文可搜，等于公开 | server-only 用运行时 BFF 代理或容器注入 |
| 启动时不校验环境变量 | `undefined` 打到生产环境才炸 | schema 启动门禁：必填/格式/枚举/类型转换 |
| 启动日志打印完整密钥 | 日志平台成密钥分发平台 | 快照脱敏：secret 字段只露前 4 位 |
| 扫描器无白名单 | 误报刷屏，开发者免疫，真泄漏漏网 | 放行 `process.env`、占位符、测试夹具 |
| 扫描器命中后仍可合并 | 扫描器沦为摆设 | 非零退出硬门禁，发现即拦 |
| 泄漏后先删文件再补提交 | git 历史里还在，等于没处理 | 按「撤销→轮换→清史→审计」四步走 |
| 密钥硬切换（直接 revoke 旧 key） | 调用方未切新 key，线上大面积 401 | 双密钥并行期：old + new 同时有效 → 全切 → revoke |
| 异常 message 里带密钥 | 错误上报直接带走 secret | 错误上下文只放 id，敏感字段走脱敏器 |
| console.log 打印完整对象 | 对象里可能嵌套密钥 | 生产环境关闭 debug log，或包装 console 走 redact |
| CI 用长效 AK | 日志/产物泄露后长期有效 | OIDC 换短期 token，自动过期 |
| GitHub Actions secrets 全 job 继承 | 子 workflow 拿到不需要的高权限 | 按需传参，不用 `secrets: inherit` |
| 第三方 publishable key 裸奔 | 被竞品/爬虫盗刷配额 | referrer 限制 + 用量上限 + 告警 |
| 公开 key 永不轮换 | 一旦泄漏无法止损 | 即使是 publishable key 也要有轮换策略 |
| 把密钥写在 README/文档命令里 | README 是公开的，等于发推文 | 文档只写 `cp .env.example .env.local`，密钥走金库 |
| 前端做「服务端签名」 | 浏览器里的签名 = 把密钥送给用户 | 签名永远在服务端完成 |
