## 78.1 选型的第一性原理：约束、证据与可逆性

### 概念解析

选型不是「找到最强的技术」，而是**在约束下找到最不坏、且能退出的技术**。大多数失败选型不是选错了技术，而是三件事没做：

1. **没澄清需求**：把「要一个图表库」当成需求，真实需求是「5 万个数据点的折线图 + 钻取 + 导出 + 低端机不卡」；需求不清，候选清单一定跑偏。
2. **没区分约束与偏好**：个人熟悉度、社区热度、技术新奇感是偏好；合规、端支持、性能预算、团队存量、交付窗口是约束。偏好可以加权，约束必须一票否决。
3. **没算退出成本**：只算「接进来要几天」，没算「三年后换掉要几个月」。选型的真实成本 = 引入成本 + 迁移成本 + 认知成本 + 机会成本。

**选型三问**（任何候选都要回答）：

| 问题 | 追问 | 典型反例 |
| --- | --- | --- |
| 不引入会怎样？ | 原生 API、已有依赖、自研 20 行能不能解决？ | 为一个日期格式化引入 3 个库 |
| 最坏情况是什么？ | 停维护、许可证收紧、核心维护者离开、框架大版本不兼容 | 选了一个单人维护的闭源编辑器内核 |
| 什么条件会让结论反转？ | 哪个假设一变，冠军就易主？ | 「以后可能要 SSR」直接选了最重的方案 |

**约束分层**建议写进团队选型规范：

| 层级 | 内容 | 处理方式 |
| --- | --- | --- |
| 硬约束 | 许可证可用性、信创/国密要求、目标浏览器与端、性能预算、上线窗口、团队存量技术栈 | 一票否决，不参与打分 |
| 软约束 | 生态成熟度、类型体验、包体、文档质量、招聘供给、维护活跃度 | 加权打分，权重来自当下项目 |
| 个人偏好 | 熟悉度、审美、社区热度、技术新奇感 | 只能作为证据的一部分，不能单独决定 |

**七步决策流程**：

1. **需求澄清**：把形容词换成可测指标（数据量、并发、设备档位、交付日期、合规等级）；
2. **硬约束筛选**：先砍掉不合格的，避免在后面用分数「救」一个根本不能用的方案；
3. **候选 2~4 个**：必须包含「原生 / 自研 / 已有依赖」基线，否则容易误以为「只有引库一条路」；
4. **对称打分**：同一维度、同一证据标准、同一量纲；每个分数旁边写证据，禁止「A 的长板比 B 的短板」；
5. **敏感性检查**：逐个维度把权重翻倍，看冠军是否反转；易反转的维度就是评审最该挑战的假设；
6. **限时试点（spike）**：1~2 天，用 3 个真实场景（最复杂、最边角、最像线上）验证，量体积、测边界；
7. **ADR + 复审 + 退出预案**：把决策、备选、反转条件、复审日期写进仓库，而不是留在聊天记录里。

**可逆性比「最优」更重要**。贝索斯把决策分成「双向门」与「单向门」：能低成本退回的是双向门，应该快速试；换框架、换组件库、换状态层是单向门，必须慢。判断可逆性看三个信号：

- 第三方 API 是否只出现在适配层，还是泄漏到业务代码；
- 数据与状态是否能导出/迁移，还是被私有格式锁死；
- 升级是否跟得上大版本，还是已经冻结在旧版本。

**ADR（Architecture Decision Record）** 是选型的留痕方式。最小模板：

```markdown
# ADR-0001：选择 Vue 3 + Pinia 作为中后台技术栈

## 状态
已接受（2026-10-31）· 复审日期：2027-04

## 背景与约束
- 团队 8 人，7 人有一年以上 Vue 经验；历史系统 30 万行 Vue 2；
- 交付窗口 4 个月；无 SSR/RSC 需求；需适配国产浏览器与内网部署；
- 组件库候选：Element Plus / Ant Design Vue；许可均为 MIT。

## 决策
采用 Vue 3（Composition API）+ Vite + Pinia + Element Plus；不引入 Nuxt。

## 备选与不选理由
- React 19 + Next.js：SSR 能力更强，但团队迁移与招聘成本高，当前无真实 SSR 需求；
- Angular：强规范适合大型多团队，但学习曲线与人才供给不匹配 4 个月窗口。

## 后果与反转条件
- 若 12 个月内出现强 SEO / RSC / 国际化协作需求，重新评估 Nuxt 或 Next.js；
- 若组件库升级阻塞超过 2 个迭代，触发替代方案评审；
- 退出预案：状态与请求层通过 adapter 隔离，替换预估 6 人周。
```

### 典型应用场景

- **新项目起步**：硬约束少、可逆性高，适合快速试点，但要把 ADR 与退出预案一次做对；
- **存量系统升级**：先算迁移成本，再谈技术优劣；「团队存量」通常直接决定结论；
- **合规敏感项目**：政企、金融、出海，许可证与数据合规是硬约束，必须在候选阶段筛掉；
- **多团队协作**：选型要能被非作者维护，文档、类型、约定比「设计优雅」更重要。

### 可运行代码示例

下面的核心逻辑来自 [78-01-selection-matrix.ts](./examples/78-01-selection-matrix.ts)：硬约束先行、加权矩阵、逐维敏感性检查，并输出「结论在什么条件下反转」。

```typescript
// 文件: examples/78-01-selection-matrix.ts（核心节选）

// 1) 硬约束一票否决：不参与打分，先砍掉根本不能用的方案
type Constraint = { name: string; reject: (o: Option) => boolean };

// 2) 加权矩阵：权重来自当下约束，分数必须带证据
const weighted = (o: Option) =>
  criteria.reduce((sum, c) => sum + c.weight * o.scores[c.name], 0);
```

> 运行方式：`npx tsx examples/78-01-selection-matrix.ts`（硬约束筛选 + 加权矩阵 + 逐维敏感性 + 反转条件，共 5 组硬断言）。

### 最佳实践

- ✅ **先写约束，再写候选**：约束清单没定之前，任何对比表都是「先有结论后找理由」；
- ✅ **每个分数带证据**：实测数据、官方文档、issue 记录、试点结果，禁止凭印象打分；
- ✅ **保留「不引入」基线**：原生 / 自研 / 已有依赖要和其他候选同台打分；
- ✅ **做敏感性检查**：冠军只领先 0.1 分时，要明确写出「哪个权重变化会反转」；
- ✅ **决策落 ADR**：背景、备选、后果、反转条件、复审日期，一个都不能少；
- ⚠️ 不要用 star 数、下载量、别人都在用作为唯一证据——它们是生态信号，不是适配性证据；
- ⚠️ 不要把「以后可能要」当成硬需求：为假想需求引入最重方案，是最常见的过度设计。

## 78.2 框架选型：Vue 3、React 19、Angular 与元框架

### 概念解析

框架选型不是「原理考试」的延伸，而是**团队、组件库、招聘、迁移成本**的综合决策。原理差异决定上限，工程约束决定下限，而日常痛苦几乎都来自下限。

先补齐 [4.8](./04-frameworks.md#_4-8-框架对比与选型) 的对比表，把「选型相关」的维度展开：

| 维度 | Vue 3 | React 19 | Angular | 选型含义 |
| --- | --- | --- | --- | --- |
| 心智模型 | 响应式自动追踪 | UI = f(state)，手动优化 | DI + 装饰器 + Signals | 决定新人上手速度与代码风格 |
| 更新粒度 | 组件级 + 编译期优化 | 组件级 + Compiler | 信号级 | 决定性能调优的工作量分布 |
| 状态方案 | Pinia（官方） | Zustand / Redux Toolkit / Jotai（社区） | Service + Signals | 状态层越分散，选型与规范成本越高 |
| 元框架 | Nuxt 3/4 | Next.js（App Router / RSC） | Angular SSR | SSR 不是框架自带，必须连同元框架一起选 |
| SSR / RSC | Nuxt SSR / SSG | Next.js RSC / ISR / 边缘 | Angular SSR | RSC 是 React 独有能力，但也是迁移成本 |
| 类型体验 | 良好（`<script setup>` + TS） | 良好（TSX） | 最强（TS 原生、DI 可推导） | 大型多团队尤其看重 |
| 组件库生态 | 国内最全（Element Plus、Ant Design Vue） | 最大（AntD、MUI、shadcn/ui） | 官方 Material + 企业内建 | 组件库往往绑定框架，换框架=换组件库 |
| 招聘供给 | 国内充足 | 全球最多、国内充足 | 相对少、偏大型企业 | 长期人力成本与交付风险 |
| 包体基线 | 较小 | 中等 | 较大 | 低端机/弱网项目要纳入预算 |
| 适用场景 | 中小到中大型 B 端、C 端 | 中大型、强 SSR/RSC、国际化协作 | 大型企业级、强规范多团队 | 与团队规模、规范强度强相关 |

**五条硬规则**：

1. **团队存量技术栈 > 框架本身差异**（[4.8](./04-frameworks.md#_4-8-框架对比与选型) 已给出结论）。30 万行 Vue 2 的团队换 React，收益是「理论更优」，成本是「半年交付空窗 + 全员重学 + 招聘重建」。
2. **组件库绑定决定一半选型**。Vue 项目换 React，真正的工作量不是重写页面，而是重写组件库适配、主题、权限、表格、表单、国际化（见 [49.1](./49-component-library.md#_49-1-组件库选型与版本基线)）。
3. **招聘与人才供给是长期成本**。框架选型的隐性账单在第二年才出现：招不到人、现有成员不愿学、外包质量不可控。
4. **SSR/RSC 必须是真实需求**。「以后可能要做 SEO」不足以支撑 Next.js 的复杂度；真有需求时，也要区分 SSG、ISR、RSC、边缘渲染的成本差异（见 [第十三部分](./13-ssr-meta-frameworks.md)）。
5. **国产生态与信创是硬约束**。政企项目要核对国产浏览器/WebView、内网离线部署、国密改造（见 [74.2](./74-xinchuang-guomi.md#_74-2-国密算法前端落地-sm2-sm3-sm4-与密钥红线)），框架本身的「国际主流」不等于「环境可用」。

**场景判定表**（先按约束筛，再按偏好选）：

| 场景 | 推荐路线 | 关键理由 | 反方风险 |
| --- | --- | --- | --- |
| 存量 Vue 2/Vue 3 团队做 B 端中后台 | Vue 3 + Vite + Pinia + Element Plus / Ant Design Vue | 迁移成本最低，组件库与招聘匹配 | 海外生态与部分前沿方案跟进较慢 |
| 全新项目，强 SEO / 内容 / 国际化协作 | React 19 + Next.js（App Router） | RSC、ISR、边缘与生态最完整 | 生态碎片化、版本升级与心智负担 |
| 大型多团队、强规范、DI 与 TS 深度使用 | Angular（Standalone + Signals） | 约定强、可替换人、类型与 DI 适合大团队 | 学习曲线陡、人才供给少、包体偏大 |
| 内容站 / 营销页 / 低 JS 预算 | Astro 或 SvelteKit | 岛屿架构、默认少 JS、首屏好 | 复杂交互生态弱于三大框架 |
| 跨端 / 桌面 / 小程序 | 先定端形态，再定框架（见 [70.1](./70-desktop-app-tauri.md#_70-1-桌面端形态坐标-electron-tauri-cef-webview2-选型矩阵)） | 端能力抽象层比框架更重要 | 为「一套代码多端跑」牺牲体验 |

**迁移成本拆解**（面试与立项都要能说清）：

| 成本项 | 典型工作量 | 常被低估的原因 |
| --- | --- | --- |
| 页面与组件 | 30%~40% | 以为「语法差不多」就能平移 |
| 状态与请求层 | 20% | 响应式 vs 手动订阅的模型差异 |
| 组件库与主题 | 20% | 表格、表单、权限、国际化的隐性适配 |
| 构建与部署 | 10% | SSR/SSG、缓存、CDN、灰度全部重做 |
| 测试与回归 | 10% | 快照、E2E、视觉回归基线全部失效 |
| 招聘与培训 | 长期 | 不在项目排期里，但决定第二年成本 |

面试回答按 [76.2](./76-mobile-office-interview.md#_76-2-定向题库-五大域二十题通关) 的结构：**约束 → 候选 → 取舍 → 反方风险 → 反转条件**。只说「Vue 简单、React 生态好」是背书，不是选型。

### 典型应用场景

- **中后台**：优先组件库成熟度、表格/表单能力、权限体系与主题定制深度；
- **C 端内容/电商**：优先首屏、SSR/SSG、缓存与 CDN、国际化；
- **政企内网**：优先国产浏览器兼容、离线部署、国密与等保要求；
- **多团队大型系统**：优先规范强度、可替换人、类型约束与目录边界。

### 可运行代码示例

框架矩阵的完整实现见 [78-01-selection-matrix.ts](./examples/78-01-selection-matrix.ts)。示例刻意把「团队存量」权重设为 0.30，把「SSR」设为 0.10：Vue 以 4.00 领先 React 3.85；把 SSR 权重翻倍后 React 反超为 4.35。敏感性检查同时会报出「生态成熟度」「招聘供给」两个可反转维度——这正好说明**结论对多个假设都敏感，其中 SSR 是真实需求信号，生态与招聘则取决于团队所处阶段**，评审要逐个挑战这些假设，而不是只盯总分。

```typescript
// 文件: examples/78-01-selection-matrix.ts（核心节选）
// 敏感性检查：逐个维度权重 ×2，冠军易主即说明该假设最脆弱
for (const c of criteria) {
  const doubled = criteria.map((x) =>
    x.name === c.name ? { ...x, weight: x.weight * 2 } : x,
  );
  const next = rank(doubled)[0];
  if (next !== champion) reversal.push(`${c.name} 权重翻倍 → ${next}`);
}
```

> 运行方式：`npx tsx examples/78-01-selection-matrix.ts`。把 `criteria` 与 `scores` 换成你项目的真实约束与证据，矩阵才有效；直接照抄别人的权重等于没做选型。

### 最佳实践

- ✅ **先确认「换框架」是不是真问题**：很多痛点其实是状态层、组件库或构建链的问题，换框架是过度反应；
- ✅ **框架与元框架一起选**：选 React 就必须同时决定 Next.js / Remix / Vite SPA，SSR 成本在这一步产生；
- ✅ **把组件库纳入同一张矩阵**：框架与组件库是绑定决策，分开选会出现「框架合适、库不合适」的死局；
- ✅ **写清反方风险**：任何推荐都要附一条「它在什么情况下会害你」；
- ⚠️ 不要用「前端趋势报告」替代团队约束：趋势描述的是平均项目，不是你的项目；
- ⚠️ 不要在交付窗口内做框架迁移：迁移是单向门，应该独立立项、独立排期。

## 78.3 npm 库选型：从「有没有」到「该不该」

### 概念解析

npm 生态有 300 万+ 包，「找得到」从来不是问题，「该不该引」才是。选库的第一原则是**原生优先**：平台能力已经覆盖的，不要为省 20 行代码引入一个长期维护负担。

| 需求 | 原生能力 | 仍需库的场景 |
| --- | --- | --- |
| 日期格式化 / 相对时间 | `Intl.DateTimeFormat`、`Intl.RelativeTimeFormat` | 复杂时区运算、日历、RRULE（见第 75 册） |
| 数字 / 货币 / 单位 | `Intl.NumberFormat` | 高精度小数、会计舍入、汇率 |
| 深拷贝 | `structuredClone` | 需要保留类实例/循环引用的特殊语义 |
| 请求与取消 | `fetch` + `AbortController` | 缓存、重试、并发去重、乐观更新（TanStack Query 类） |
| URL 解析 | `URL` / `URLSearchParams` | 复杂查询串嵌套、签名 |
| 唯一 ID | `crypto.randomUUID()` | 有序 ID、短 ID、分布式 ID |
| 数组/对象工具 | `Array.prototype.at/flat/group`、`Object.groupBy` | 深层路径、复杂集合运算（优先 `es-toolkit`） |
| 表单校验 | 原生约束校验 + 少量手写 | 跨字段、异步校验、schema 复用（Zod/Valibot） |

### 找库操作步骤详解（从需求到候选入围）

选库不是打开 npm 搜第一个就装。一条可复核的链路是：**需求关键词化 → 多渠道发现 → 指标初筛 → 元数据复核 → 入围六维评估**。前五步是「找人」，六维评估是「面试」——不要跳过找人直接面试，否则你只会面试到 SEO 做得好的包。

**第 0 步：先做原生与已有依赖体检**。即上方「原生优先对照表」——能被平台能力或已有依赖覆盖的，直接结束，不进入下面的检索。

**第 1 步：把业务需求翻译成检索关键词**。关键词要覆盖**通用词**、**框架限定词**、**能力限定词**三组，只搜中文会错过英文生态：

| 业务表达 | 检索关键词方向 |
| --- | --- |
| 做一个表单 | `form validation`、`form schema`、`react form`、`vue form` |
| 处理时间 | `date`、`datetime`、`timezone`、`calendar` |
| 画图表 | `chart`、`data visualization`、`graph` |
| 虚拟滚动 | `virtual list`、`virtual scroll`、`windowing` |
| 状态管理 | `state management`、`store` |

**第 2 步：多渠道发现候选**，不要只依赖一个来源：

| 渠道 | 用途 | 怎么用 |
| --- | --- | --- |
| `npm search <kw>` | 快速列出相关包 | `npm search chart --long` 看描述与版本 |
| [npms.io](https://npms.io) | 按 quality / popularity / maintenance 三项评分排序 | 搜关键词，按 quality 降序，过滤 maintenance < 0.5 |
| [npmtrends.com](https://npmtrends.com) | 对比多个包的下载趋势与季节性 | 把 3~5 个候选放进去，看 12 个月走势是否平稳/上升 |
| GitHub Topics / `awesome-*` | 发现社区维护的清单 | `awesome react hooks`、`awesome csv` |
| 框架官方文档与周边推荐 | 官方背书的生态位 | React docs、Vue Awesome、Next.js examples |
| 已有项目 / 同行 lockfile | 看团队与同行在用什么 | `pnpm why <pkg>` 或查同行开源项目的 `package.json` |

**第 3 步：用指标做硬初筛**，在进入六维评估前砍掉明显不合格的。npms.io 给出三项 0~1 分：

| 指标 | 含义 | 淘汰线 |
| --- | --- | --- |
| quality | README 完整度、测试、license、类型声明、CI | < 0.5 直接淘汰 |
| maintenance | 最近发布、commit 频率、issue 响应 | < 0.4 或最近发布 > 18 个月淘汰 |
| popularity | 下载量、被多少项目依赖 | 不是越高越好，但 < 0.2 且无知名使用者要警惕 |

下载量看**周下载**而不是总下载（总下载被历史累积扭曲），并结合 npmtrends 看趋势：平稳上升 > 平稳 > 下降。

**第 4 步：用 `npm view` 读取包元数据**。registry 是事实来源，比 README 可靠：

```bash
# 关键元数据一次读完
npm view <pkg> name version license repository.url \
  homepage bugs.url time.modified maintainers \
  dependencies peerDependencies deprecated dist.unpackedSize
```

重点核对：

| 字段 | 看什么 | 危险信号 |
| --- | --- | --- |
| `license` | 必须能对应到 LICENSE 正文 | `SEE LICENSE IN ...` 没点进去、`UNLICENSED` |
| `deprecated` | 是否已废弃 | 有值直接淘汰，除非有明确 fork 替代 |
| `time.modified` | 最近更新时间 | 超过 18 个月未更新要查维护者是否离场 |
| `maintainers` | 维护者数量 | 单人维护且无组织背书，风险高 |
| `peerDependencies` | 宿主版本约束 | 强迫升级整个框架版本 |
| `dist.unpackedSize` | 包本身大小 | 不等于 gzip 体积，但可做量级判断 |

**第 5 步：GitHub 仓库复核**。维护现状的真相在仓库，不在 npm 页面：

| 看什么 | 合格信号 | 危险信号 |
| --- | --- | --- |
| 最近 commit | 近 6 个月内有活动 | 超过 1 年无 commit |
| Open issue 处理 | 有 triage、有回复、有 milestone | issue 无人响应、维护者失踪 |
| Release / tag | 有规律的版本发布 | 只有一个初始版本 |
| 安全 | 有 SECURITY.md、Dependabot、CI 通过 | 无安全策略、CI 长期红 |
| 依赖 | Dependabot / Renovate 在跑 | 依赖全是 3 年前的旧版 |

**第 6 步：形成 2~4 个入围候选，进入六维评估**。经过上面五步，通常能把 10+ 个候选砍到 2~4 个。入围的包再用下方的**六维评估模型**做对称打分，并跑 [78-02-lib-fit-evaluator.ts](./examples/78-02-lib-fit-evaluator.ts) 输出 `adopt / pilot / review / reject / block`。

> 一个反例：只在 `npm search` 里按下载量排序选第一个，往往选中的是「SEO 做得好但维护停滞」的包；用上面六步，能在引入前就发现它 `maintenance` 分低、`deprecated`、单人维护。

**操作步骤配套清单**：

- ✅ **先搜英文关键词，再搜中文**：npm 生态以英文为主，中文结果覆盖不全；
- ✅ **下载量交叉验证周趋势**：单看绝对值会被刷量或历史累积误导；
- ✅ **`npm view` 比 README 可信**：README 可以过期，registry 元数据是发布时写死的；
- ✅ **单人维护不一定不能用**：但必须有适配层隔离 + 退出预案（见下方「引入方式也是设计」）；
- ✅ **发现候选后再跑 `pnpm why <pkg>`**：确认没有被已有依赖间接引入，避免重复能力。

**六维评估模型**（与 [66.2](./66-dependency-governance.md#_66-2-依赖准入-评分、硬门槛与白名单审批) 的五维风险评分互补：那边防「坏包」，这边判「合不合」）：

| 维度 | 看什么 | 高分证据 | 低分信号 |
| --- | --- | --- | --- |
| 需求契合度 | API 能否直接表达需求，是否需要 hack/fork | 官方示例覆盖你的核心场景 | 关键能力要靠 issue 里的 workaround |
| 维护与治理 | 发布节奏、维护者数量、issue 响应、安全记录 | 近 6 个月有发布、多人维护、OpenSSF/ Socket 评分健康 | 一年未发布、单人维护、长期 issue 未响应 |
| 体积与性能 | gzip 体积、tree-shaking、副作用、SSR 兼容 | ESM、`sideEffects: false`、可摇树 | CJS/ESM 双包、全量引入、polyfill 膨胀 |
| 类型与 DX | TS 类型质量、文档、示例、错误信息 | 类型完整、泛型可推导 | `any` 遍布、文档只有 README |
| 可替换性 | API 面大小、深导入、是否泄漏第三方类型 | 可封装在 adapter 后 | 业务代码到处 `import` 内部路径 |
| 合规 | 许可证、传递依赖许可、资源许可 | 宽松许可 + 依赖树干净 | 许可未知、copyleft、含非商用素材（见 78.4） |

**体积要实测，不要只看 Bundlephobia**。Bundlephobia 给的是发布包的最小体积，不等于你项目的增量：

- 真实增量 = 被打进 chunk 的模块 + 重复依赖 + polyfill + 运行时副作用；
- 用 `vite-bundle-visualizer`、`source-map-explorer`、`size-limit` 看打包后的实际变化；
- 注意 CJS/ESM 双包导致的重复实例（React 双份、Moment 多语言全量）；
- 注意 `peerDependencies` 版本冲突会迫使你升级整个生态。

**引入方式也是设计**：

```typescript
// 文件: src/lib/chart.ts —— 用适配层隔离第三方，业务只依赖自己的接口
// 1) 动态导入：非首屏能力不进主包
export async function loadChart() {
  const { init } = await import('echarts/core');
  return init;
}

// 2) 适配层：第三方类型不泄漏到业务组件，替换时只改这一层
export interface ChartPort {
  render(el: HTMLElement, option: unknown): void;
  resize(): void;
  dispose(): void;
}
```

**什么时候不该引库**（六条否决线）：

| 情形 | 判断 | 替代 |
| --- | --- | --- |
| 原生 20~30 行能稳定实现 | 引入成本 > 自研成本 | 自研并加测试 |
| 只在一个页面用一次、生命周期短 | 长期维护价值低 | 局部实现 / 动态加载 |
| 已有依赖能覆盖 80% 需求 | 重复能力会推高包体与认知成本 | 扩展现有依赖 |
| 包体超过该页面预算 | 性能是硬约束 | 换轻量方案 / 服务端处理 |
| 许可证不明或非商用 | 合规是硬约束 | 替换 / 商业授权（78.4） |
| 维护者已离场 / 长期无发布 | 未来安全修复无人接 | 换活跃替代 / 自研内核 |

**限时试点（spike）** 的最小清单：

1. 用 3 个真实场景写最小 demo：最复杂的那个、最边角的那个、最像线上的那个；
2. 记录 3 个体积数字：单独引入、按需引入、替换现有方案后的增量；
3. 记录 3 个失败点：文档没写的、类型不对的、SSR/低端机出问题的；
4. 给出退出成本：替换需要改几处、是否有适配层、候选替代是谁。

**品类速查**（截至 2026 年的主流候选起点，仍须按上面的六维复核）：

| 品类 | 常见候选 | 许可提示 |
| --- | --- | --- |
| 状态管理 | Pinia（Vue）、Zustand / Redux Toolkit / Jotai（React） | 均为 MIT |
| 请求与缓存 | TanStack Query、SWR | MIT |
| 表单与校验 | React Hook Form、TanStack Form、VeeValidate + Zod/Valibot | MIT |
| 日期 | Day.js、date-fns、Temporal polyfill | MIT / Apache-2.0，注意 polyfill 体积 |
| 图表 | ECharts、AntV G2/G6、D3、Chart.js | Apache-2.0 / MIT，注意扩展包 |
| 表格 | TanStack Table（headless）、AG Grid Community | AG Grid 企业版为商业授权，需单独核对 |
| 富文本 | TipTap（ProseMirror）、Lexical、Slate | MIT，注意扩展与协作服务另有许可 |
| 拖拽 | dnd-kit | MIT |
| 虚拟列表 | TanStack Virtual、vue-virtual-scroller | MIT |
| 工具集 | es-toolkit、lodash-es | MIT，优先 ESM 可摇树版本 |

### 典型应用场景

- **首屏敏感页面**：先算体积预算，再选库；能动态加载的绝不进主包；
- **长期维护的核心能力**：优先可替换性与社区治理，而不是「功能最多」；
- **一次性活动页**：允许更激进的轻量方案，但许可证仍不可放宽；
- **多团队共享基建**：选型要能被非作者维护，文档与类型比 API 优雅更重要。

### 可运行代码示例

完整实现见 [78-02-lib-fit-evaluator.ts](./examples/78-02-lib-fit-evaluator.ts)：六维加权评分 + 六条硬门槛（原生可替代、重复能力、废弃、许可、体积超预算、安装脚本），输出 `adopt / pilot / review / reject / block`。

```typescript
// 文件: examples/78-02-lib-fit-evaluator.ts（核心节选）

// 硬门槛先于分数：体积超预算、许可不可商用、已有同类能力，都不允许「靠高分救回来」
if (c.nativeAlternative) return reject(c, '原生能力已覆盖');
if (c.duplicateOfExisting) return reject(c, '重复能力，推高包体与认知成本');
if (c.license === 'strong-copyleft' || c.license === 'unknown')
  return block(c, '许可不可商用或未知，转 78.4 判定');
if (c.gzipKb > c.budgetKb) return reject(c, `体积 ${c.gzipKb}KB 超预算 ${c.budgetKb}KB`);
```

> 运行方式：`npx tsx examples/78-02-lib-fit-evaluator.ts`（六维评分 + 六条硬门槛 + 四级决策，共 6 组硬断言）。

### 最佳实践

- ✅ **先写「不引入」基线**：原生 / 自研 / 已有依赖同台比较，避免「只有引库」的假两难；
- ✅ **用适配层隔离**：第三方 API 只出现在 adapter，替换时改一处而不是全站 grep；
- ✅ **锁版本 + 锁传递依赖**：新库引入后跑一次 `pnpm why`，确认没有把重依赖带进来；
- ✅ **把试点结论写进 ADR**：体积数字、失败点、退出成本，评审时才有事实可依；
- ⚠️ 不要按 GitHub star 选库：star 是历史热度，不是维护现状与适配性；
- ⚠️ 不要为了「统一技术栈」强行引入框架不擅长的库：跨框架通用库通常意味着两边都不最优。

## 78.4 开源许可证：商用可用性速判

### 概念解析

**开源不等于免费商用，npm 上架不等于开源。** 前端尤其容易踩坑，因为：

1. **打包即复制**：把库打进 bundle 再发给浏览器，在版权法意义上就是「分发副本」，GPL 类义务会被触发；
2. **SaaS 也可能触发**：AGPL-3.0 的第 13 条把「通过网络交互使用」视为触发条件，纯 SaaS 也逃不掉；
3. **传递依赖同样受约束**：你只审了直接依赖，GPL 可能藏在第 5 层；
4. **资源另有许可**：字体、图标、插画、地图数据、示例数据集，往往不跟随代码仓库的主许可证；
5. **AI 生成/复制粘贴也有许可**：从 Stack Overflow 复制的代码是 CC BY-SA，可能污染你的代码库。

**信息源优先级**（冲突时以更权威者为准，并记录风险）：

1. 仓库根目录的 `LICENSE` / `LICENCE` / `COPYING` 正文（事实来源）；
2. `package.json` 的 `license` 字段（可能是 `SEE LICENSE IN <file>`，必须点进去）；
3. npm registry 页面 / `npm view <pkg> license` 的元数据（可能过期）；
4. 上游官网 FAQ / 商业授权页面；
5. 直接向上游维护者书面确认（保留邮件/issue 记录）。

**许可证分级表**：

| 类型 | 代表 | 能否商用 | 主要义务 | 前端注意 |
| --- | --- | --- | --- | --- |
| 宽松 | MIT、ISC、BSD-2/3-Clause、Apache-2.0 | ✅ 可以 | 保留版权与许可文本；Apache 另有专利授权、NOTICE、标注修改 | 最容易合规，但仍不能删除版权声明 |
| 弱 copyleft | LGPL-2.1/3.0、MPL-2.0、EPL-2.0 | ⚠️ 有条件 | 修改过的库文件需开源；LGPL 需允许重新链接 | 前端打包近似静态链接，LGPL 风险显著上升 |
| 强 copyleft | GPL-2.0/3.0、AGPL-3.0 | ❌ 通常不可 | 衍生作品需同许可开放源码；AGPL 网络交互即触发 | 前端 bundle 即分发；SaaS 也触发 AGPL |
| 源码可见但非 OSI | SSPL、BUSL-1.1、Elastic License 2.0、Commons Clause | ❌ 默认不可 | 限制托管服务/商业使用，需购买商业授权 | 常见于数据库、编辑器、监控类产品 |
| 非商用 | CC-BY-NC(-SA)、PolyForm Noncommercial、“personal use only” | ❌ 不可 | 仅限非商业用途 | 图标、插画、模板、数据集高发 |
| 未知/无许可 | `UNLICENSED`、无 LICENSE、版权声明缺失 | ❌ 视为不可 | 默认「保留所有权利」 | npm 私有包默认就是 `UNLICENSED` |

**商用判定流程**：

```mermaid
flowchart TD
    A[发现依赖或资源] --> B{有明确许可证?}
    B -- 无 --> Z[阻断: 视为保留所有权利]
    B -- 有 --> C[核对 LICENSE 正文]
    C --> D{OSI 认可的开源许可?}
    D -- 否 --> E{源码可见或非商用?}
    E -- 是 --> F[阻断: 需商业授权或替换]
    D -- 是 --> G{宽松许可?}
    G -- 是 --> H[放行: 保留声明与 NOTICE]
    G -- 否 --> I{强 copyleft?}
    I -- 是 --> J{是否分发或网络交互?}
    J -- 是 --> K[阻断: 同许可开源或购买商业授权]
    J -- 否 --> L[内部使用: 法务确认后可用]
    I -- 否 --> M[弱 copyleft: 是否修改或静态打包?]
    M -- 是 --> N[法务评审: 开源修改部分或替换]
    M -- 否 --> O[放行: 保留声明并隔离]
```

**几个必须搞清的概念**：

| 概念 | 含义 | 前端判定要点 |
| --- | --- | --- |
| 分发 | 把副本交给第三方 | 浏览器 bundle、离线包、桌面安装包都算分发 |
| 衍生作品 | 基于原作品修改/组合形成的新作品 | 静态打包 + 修改通常被视为衍生；单纯的动态链接争议较小 |
| 网络交互 | 用户通过浏览器/API 远程使用 | AGPL 明确触发；GPL 是否触发取决于是否分发，需法务判断 |
| 双许可 | `MIT OR GPL-3.0` 或商业授权二选一 | `OR` 可选宽松分支；`AND` 必须同时满足两者 |
| 修改 | 改动库源码或补丁 | Apache 需标注修改；GPL/MPL 修改部分需开源 |
| 内部使用 | 只在公司内部使用、不对外分发 | GPL 一般不触发分发义务，但 AGPL 网络交互仍可能触发 |

**SPDX 表达式**要会读：`MIT OR Apache-2.0` 表示二选一，选 MIT 即可；`MIT AND GPL-3.0` 表示两项义务都要满足，前端分发场景通常只能放弃；`GPL-2.0-only WITH Classpath-exception-2.0` 表示带例外条款，需按例外原文判断。不要看到「MIT」就以为整包都是 MIT——一个包可能包含多份不同许可的资源。

**资源类许可**单独核对：

- **字体**：SIL OFL 1.1 允许商用嵌入，但不得单独售卖字体、需保留许可、可能保留字体名；方正/汉仪等商业字体需授权（[74.2](./74-xinchuang-guomi.md#_74-2-国密算法前端落地-sm2-sm3-sm4-与密钥红线) 也提到这条红线）；
- **图标**：不同图标集许可差异大，有的要求署名，有的是 CC-BY-NC；
- **插画/图片**：免费图库也要看商用范围、署名要求、人物肖像权；
- **地图/地理数据**：国内地图需审图号，不能只看法务许可；
- **示例数据/数据集**：学术数据集常禁止商用或要求引用。

**常见误区**：

| 误区 | 事实 |
| --- | --- |
| 「GitHub 公开 = 可以免费用」 | 公开仓库可能没有许可证，默认保留所有权利 |
| 「npm 上架 = 开源」 | npm 只是分发渠道，`UNLICENSED` 包同样可以上架 |
| 「MIT 就可以删掉版权声明」 | MIT 的核心义务就是保留版权与许可声明 |
| 「只在内部用就没事」 | AGPL 的网络交互条款可以让内部 SaaS 也触发 |
| 「买了商业授权就覆盖所有场景」 | 要看授权范围：版本、子公司、托管服务、再分发，常有限制 |

> ⚠️ 本节是工程判定方法，不构成法律意见。涉及 GPL/AGPL、商业授权、字体/地图、出海数据合规时，最终结论必须由法务确认并留档。

### 典型应用场景

- **引入新依赖前**：先跑一遍许可证判定，再进选型矩阵；
- **发布/交付前**：生成 SBOM 与许可证清单，作为交付物的一部分；
- **融资/并购尽调**：能 5 分钟内回答「用了哪些 copyleft」；
- **政企/金融项目**：许可证与信创、国密、等保一起作为硬约束。

### 可运行代码示例

完整实现见 [78-03-license-compat.ts](./examples/78-03-license-compat.ts)：按 SPDX 标识分类，结合分发形态（SaaS / 浏览器 bundle / 仅内部）、是否修改、链接方式，输出 `allow / allow-with-obligations / legal-review / deny` 与义务清单。

```typescript
// 文件: examples/78-03-license-compat.ts（核心节选）

// 同一个许可证，分发形态不同，结论可能完全相反
if (id === 'AGPL-3.0') {
  if (ctx.distribution === 'saas' || ctx.distribution === 'browser-bundle')
    return deny('AGPL 网络交互/分发触发源码开放义务');
  return review('内部网络使用仍可能触发，需法务确认');
}
```

> 运行方式：`npx tsx examples/78-03-license-compat.ts`（许可证分类 + 分发形态 + 修改/链接上下文 + 双许可 OR/AND，共 7 组硬断言）。

### 最佳实践

- ✅ **引入前判定，而不是发布前补救**：许可证是选型的硬约束，不是事后补丁；
- ✅ **以 LICENSE 正文为准**：`package.json` 字段只作线索，冲突时以正文与官方 FAQ 为准；
- ✅ **区分直接与传递依赖**：跑 `pnpm licenses list`，把整棵依赖树都纳入判定；
- ✅ **把义务清单化**：保留声明、NOTICE、标注修改、开源修改部分，逐条落到交付检查表；
- ✅ **不确定就升级法务**：工程侧给出事实与选项，法务给出结论，双方都留痕；
- ⚠️ 不要把「开源」当成「免费」的同义词：OSI 开源许可也允许收费，商业授权与开源并不矛盾；
- ⚠️ 不要用「改个包名/删掉 LICENSE」规避许可：这是侵权，不是合规。

## 78.5 商用合规落地：扫描、门禁与法务留痕

### 概念解析

许可证治理如果只靠「引入时看一眼」，一定会在第 200 个依赖时失控。可落地的做法是把**判定、扫描、门禁、留痕**串成闭环，并与 [66 册](./66-dependency-governance.md#_66-2-依赖准入-评分、硬门槛与白名单审批) 的依赖治理共用一套流程。

**第一步：能自动扫描**。常用手段：

```bash
# 1) 列出整棵依赖树的许可证（pnpm 原生）
pnpm licenses list --json > licenses.json

# 2) 逐包检查许可证与版权声明（license-checker-rsc 是 license-checker 的维护分支）
npx license-checker-rsc --summary --production

# 3) 生成 SBOM（CycloneDX），把许可证、版本、哈希、依赖关系一起归档
npx @cyclonedx/cyclonedx-npm --output-file sbom.cdx.json

# 4) 通用 SBOM 工具（可选，适合多语言仓库）
syft . -o cyclonedx-json > sbom.cdx.json
```

**第二步：策略化门禁**。把许可证分成三档，写进 CI：

| 档位 | 许可类型 | 门禁动作 |
| --- | --- | --- |
| allow | MIT、ISC、BSD、Apache-2.0 | 自动通过，保留声明 |
| review | LGPL、MPL、EPL、双许可需选分支 | 必须登记用途、链接方式、是否修改，法务评审 |
| deny | GPL、AGPL、SSPL、BUSL、Elastic、CC-BY-NC、未知/无许可 | 默认阻断，只能通过「商业授权」或「豁免」放行 |

**第三步：例外机制**。没有例外机制的门禁会被绕过；有例外机制但没期限的门禁会形同虚设。豁免登记至少包含：

| 字段 | 说明 |
| --- | --- |
| 包名 / 版本 | 精确到版本，避免升级后自动继承豁免 |
| 许可证 | SPDX 标识 + LICENSE 链接 |
| 使用方式 | 直接/传递、静态/动态、是否修改、分发形态 |
| 引入人 / 评审人 | 责任人，不能是「团队」 |
| 豁免理由 | 为什么必须用、替代方案与成本 |
| 到期日 | 最长 6~12 个月，到期自动回到 deny |
| 退出计划 | 替换、购买授权或下线功能的时间点 |

**第四步：SBOM 与应急**。每次发布归档一份 SBOM，出事后能 5 分钟内回答「我们有没有用这个包、什么版本、什么许可」。这与 [66.4](./66-dependency-governance.md#_66-4-持续监测-审计、sbom-与漏洞情报) 的漏洞应急共用同一份物料清单。许可证事件同样需要响应：上游改许可、包被收购、维护者变更、商业授权条款调整，都要触发复审。

**法务协作材料包**（提交给法务时一次给全，避免来回）：

1. 包名、版本、仓库地址、LICENSE 全文链接；
2. 使用方式：直接/传递、静态打包/动态链接、是否修改；
3. 分发形态：浏览器 bundle、桌面安装包、SaaS、仅内部；
4. 业务必要性：替代方案、替换成本、下线影响；
5. 已采取的措施：隔离、适配层、保留声明、NOTICE；
6. 期望结论：可用 / 需授权 / 必须替换，以及需要的回复时限。

**与依赖治理的分工**：

| 问题 | 归属 | 章节 |
| --- | --- | --- |
| 这个包安全吗？会不会投毒？ | 供应链安全 | [66.2](./66-dependency-governance.md#_66-2-依赖准入-评分、硬门槛与白名单审批) |
| 这个包适合我们吗？ | 选型 | 78.3 |
| 这个包能商用吗？ | 合规 | 78.4 / 78.5 |
| 出事了多快修？ | 应急 | [66.5](./66-dependency-governance.md#_66-5-高危漏洞修复-sop) |

三条线共用 lockfile、SBOM、白名单与复审节奏，但结论不能互相替代：安全通过不等于许可可用，许可可用也不等于选型合适。

### 典型应用场景

- **CI 每次 PR**：新增依赖触发许可证 diff，deny 直接失败；
- **发布门禁**：SBOM + 许可证清单随版本归档；
- **季度复审**：豁免到期、上游许可变更、无使用记录的依赖清理；
- **尽调/审计**：导出许可证清单与处置记录，按包回答来源与义务。

### 可运行代码示例

完整实现见 [78-04-license-gate.ts](./examples/78-04-license-gate.ts)：汇总依赖清单、按策略分级、处理传递依赖、校验豁免是否过期，并输出可读报告与退出码。

```typescript
// 文件: examples/78-04-license-gate.ts（核心节选）

// 传递依赖的 copyleft 会向上传染：直接依赖是 MIT，也不能放过第 5 层的 GPL
for (const d of deps) {
  const verdict = classify(d);
  if (verdict === 'deny' && d.direct) blocked.push(d);
  if (verdict === 'deny' && !d.direct) blocked.push({ ...d, reason: '传递依赖传染' });
}
// 豁免必须有到期日：过期即回到 deny，避免「一次豁免，永久放行」
if (ex && ex.expiresAt < today) blocked.push({ ...d, reason: '豁免已过期' });
```

> 运行方式：`npx tsx examples/78-04-license-gate.ts`（策略分级 + 传递依赖传染 + 豁免到期 + 退出码，共 5 组硬断言）。

### 最佳实践

- ✅ **许可证清单进 CI**：与 lockfile 同源，新增依赖必须显式通过或登记豁免；
- ✅ **豁免带 owner 与到期日**：没有期限的豁免等于没有门禁；
- ✅ **SBOM 随版本归档**：发布物、SBOM、许可证清单三件套一起留痕；
- ✅ **季度复审上游变更**：许可证收紧、包被收购、维护者变更都要重新判定；
- ✅ **法务材料一次给全**：减少往返，也避免「口头同意、没有记录」；
- ⚠️ 不要只扫直接依赖：`pnpm licenses list` 默认就是整棵树，别自己写脚本只读 `package.json`；
- ⚠️ 不要把「devDependencies」完全忽略：构建期嵌入产物的代码同样会进入分发物，需按实际打包结果判断。

## 78.6 自测题

<details>
<summary><b>1. 【基础】为什么说「团队存量技术栈」通常优先于框架本身的差异？</b></summary>

**答案**：框架差异影响的是「理论上限」，团队存量影响的是「交付下限」。换框架的真实成本包括页面重写、状态与请求层重构、组件库与主题重做、构建部署重来、测试基线失效、招聘与培训，通常以半年为单位；而框架之间的能力差异，在大多数业务里可以通过规范、组件库和架构分层弥补。除非现有框架触发了硬约束（如端支持、合规、性能上限），否则迁移的收益很难覆盖成本。选型应先问「不换会怎样」，再问「换哪个」。

</details>

<details>
<summary><b>2. 【基础】MIT 与 Apache-2.0 都能商用，关键差异是什么？</b></summary>

**答案**：两者都是宽松许可，但 Apache-2.0 多了三件事：① 明确的专利授权（以及专利报复条款），对专利敏感的业务更友好；② 若上游提供 NOTICE 文件，分发时必须保留；③ 修改过的文件需要标注修改。MIT 更短，只要求保留版权与许可声明，不包含显式专利条款。两者都允许商用、修改、再分发，也都不要求开源你的衍生代码；但都不能删除版权声明。

</details>

<details>
<summary><b>3. 【基础】为什么「npm 上架」不等于「开源可商用」？</b></summary>

**答案**：npm 只是分发渠道，不是许可证。一个包完全可以以 `UNLICENSED` 上架——这表示「保留所有权利」，默认不可商用；也可能是源码可见但非 OSI 认可的许可（SSPL、BUSL、Elastic License、CC-BY-NC），限制商业使用或托管服务。判断依据是 LICENSE 正文与 SPDX 标识，不是「能不能 npm install」，也不是「GitHub 是否公开」。

</details>

<details>
<summary><b>4. 【进阶】GPL 与 AGPL 的关键区别是什么？纯前端 SaaS 会不会触发？</b></summary>

**答案**：GPL 的触发点是「分发」——把衍生作品副本交给第三方；AGPL 在第 13 条额外规定「通过网络与用户交互使用」也视为触发，必须向这些用户提供对应源码。纯前端项目把库打进 bundle 发给浏览器，本身就是分发，GPL 通常会触发；SaaS 即使不分发二进制，只要用户通过网络交互使用，AGPL 也会触发。因此前端引入 GPL/AGPL 库通常按「阻断」处理，除非购买商业授权、替换，或经法务确认的隔离方案。

</details>

<details>
<summary><b>5. 【进阶】直接依赖是 MIT，但传递依赖里有 GPL，应该怎么处理？</b></summary>

**答案**：许可证义务看最终分发物，不看依赖层级。打包后 GPL 代码与你的代码共同构成一个分发物，传染性仍然成立。处理顺序：① 用 `pnpm why` 定位是哪条依赖链带进来的；② 看能否通过 `overrides` 换掉上游版本或改用替代包；③ 评估是否真的需要该功能，能否去掉；④ 若必须保留，走法务评审或购买商业授权；⑤ 在 SBOM 与白名单里登记结论。不能因为「不是我直接装的」就放过。

</details>

<details>
<summary><b>6. 【进阶】如何判断一个 npm 库「值不值得引」？给出可执行步骤。</b></summary>

**答案**：① 需求澄清：把形容词换成可测指标（数据量、设备档位、性能预算、交付时间）；② 先问原生/已有依赖/自研能不能覆盖，保留「不引入」基线；③ 选 2~4 个候选，按六维评估：需求契合度、维护治理、体积性能、类型 DX、可替换性、合规；④ 硬门槛先筛：许可不可商用、体积超预算、废弃、重复能力直接淘汰；⑤ 1~2 天试点，用 3 个真实场景验证并量体积；⑥ 写 ADR：结论、备选、失败点、退出成本、复审日期；⑦ 引入后用适配层隔离并锁版本。

</details>

<details>
<summary><b>7. 【挑战】业务坚持要引入一个 AGPL 的图表库，给出至少三条方案与取舍。</b></summary>

**答案**：方案一，购买商业授权：最直接，成本可预期，但要注意授权范围（版本、子公司、SaaS、再分发）与续费；方案二，替换为宽松许可的同类库（ECharts、D3、Chart.js 等）：无法律风险，但要评估功能缺口、迁移成本与性能；方案三，功能降级或服务端出图：用自研/服务端渲染生成静态图，牺牲交互性；方案四，隔离部署（独立服务/独立进程）并让法务确认边界：工程复杂度高，且 AGPL 的「网络交互」边界未必能靠进程隔离规避，不能自行拍板。推荐顺序通常是「替换 → 购买授权 → 降级 → 隔离」，并把成本、工期、风险写进 ADR。

</details>

<details>
<summary><b>8. 【挑战】设计一个许可证门禁与例外机制，如何避免它形同虚设？</b></summary>

**答案**：① 门禁与 lockfile 同源，每次 PR 对新增依赖做许可证 diff，deny 直接失败；② 策略分 allow/review/deny 三档，review 必须登记使用方式与责任人；③ 豁免必须有 owner、理由、退出计划和到期日，到期自动回到 deny，禁止「永久白名单」；④ 豁免审批与代码评审分离，避免引入人自己批自己；⑤ SBOM 随版本归档，季度复审上游许可变更与无使用记录的依赖；⑥ 指标化：豁免数量、平均存续时长、逾期未处理数量，纳入架构健康度；⑦ 与依赖安全门禁共用流程，避免两套白名单互相漂移。

</details>

## 78.7 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 用 star 数、下载量、趋势报告替代项目约束 | 选出「平均项目最优、你的项目最差」的方案 | 先写硬约束与可测需求，再做对称打分 |
| 2 | 把个人熟悉度当成选型依据 | 团队换手后无人能维护，长期成本失控 | 熟悉度只能作为一项证据，且权重要透明 |
| 3 | 为「以后可能要」的重需求选最重方案 | 过度设计，交付延期，复杂度永久留存 | 只对真实需求付费，假想需求留到 ADR 复审 |
| 4 | 框架与组件库分开选 | 框架合适但组件库不匹配，返工重做 | 框架、组件库、元框架放进同一张矩阵 |
| 5 | 迁移只算页面重写 | 低估状态层、组件库、测试、招聘成本 | 按六项成本拆解，迁移独立立项 |
| 6 | 为 20 行代码引入一个长期依赖 | 包体、漏洞面、升级负担全部增加 | 原生优先，保留「不引入」基线 |
| 7 | 只看 Bundlephobia 的单包体积 | 忽略重复依赖、polyfill、双包实例，线上反而更大 | 用打包分析工具看真实增量 |
| 8 | 第三方 API 直接泄漏到业务代码 | 替换时全站 grep，退出成本失控 | 用 adapter 隔离，类型不外泄 |
| 9 | 引入后不跑 `pnpm why` | 重依赖与重复版本被悄悄带进来 | 新依赖必须检查传递依赖与体积 |
| 10 | 把「npm 上架」当成「开源可商用」 | 引入 `UNLICENSED` 或非商用许可，法律风险 | 以 LICENSE 正文与 SPDX 标识判定 |
| 11 | 只审直接依赖的许可证 | 第 5 层 GPL 通过传递依赖传染 | 扫描整棵依赖树，SBOM 归档 |
| 12 | 认为 SaaS 不分发就与 AGPL 无关 | AGPL 网络交互条款直接触发 | SaaS 场景按 AGPL 阻断或购买授权处理 |
| 13 | 豁免没有 owner 与到期日 | 白名单越滚越大，门禁形同虚设 | 豁免登记 owner、理由、退出计划与到期日 |
| 14 | 忽略字体、图标、插画、数据集许可 | 主许可证是 MIT，素材却是非商用 | 资源单独核对许可，保留授权凭证 |
