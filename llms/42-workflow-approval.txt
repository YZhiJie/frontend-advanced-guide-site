## 42.1 审批单状态机：迁移守卫与审计轨迹

### 42.1.1 概念解析

审批单本质是一台**状态机**：状态有限（draft/pending/approved/rejected/withdrawn/cancelled）、迁移有向、非法迁移一律拒绝。三个设计决策：

- **迁移表是唯一事实来源**：`TRANSITIONS[from]` 列出合法去向，所有流转必须过 `canTransition`——直接改 `state` 字段的代码都是 bug 温床；
- **每次迁移落审计**：谁（by）、何时（at）、从哪到哪、备注（comment）。审批追溯的全部素材就是这条 history；
- **终态用空数组封死**：`approved`/`cancelled` 的迁移表是 `[]`，任何后续操作天然抛错——不需要额外的「终态判断」分支。

rejected 和 withdrawn 都可以回到 pending（修改重提），但二者语义不同：**驳回**是审批人主动退回（带驳回理由），**撤回**是发起人主动收回（有窗口限制，见 42.3）。

### 42.1.2 核心代码

```ts
// 文件: examples/42-01-approval-state-machine.ts
export const TRANSITIONS: Readonly<Record<ApprovalState, readonly ApprovalState[]>>;
export function canTransition(from: ApprovalState, to: ApprovalState): boolean;
/** 所有流转走 go()：守卫 → 审计 → 改状态，三步不可拆 */
export class ApprovalDoc {
  submit(by: string): void;
  approve(by: string, comment?: string): void;
  reject(by: string, comment: string): void;
  withdraw(by: string): void; // 内部校验 only starter
  resubmit(by: string): void;
}
```

> 运行方式：`npx tsx examples/42-01-approval-state-machine.ts`。

### 42.1.3 应用实践

- **逻辑时钟代替时间戳**：示例用自增序号做 `at`，顺序确定、可断言；真实系统落时间戳 + 序号双字段（时间给人看，序号给排序用）；
- **审计不可变**：history 只 append 不修改；前端时间线组件（头像 + 动作 + 时间 + 意见）就是渲染这条数组；
- **状态机前后端各一份**：前端用它控制按钮显隐（草稿显示提交/删除、审批中显示撤回），服务端用它做权威校验——前端只管体验，后端才是守门员。

## 42.2 会签、或签、权重票与条件路由

### 42.2.1 概念解析

多人节点的三种判定语义，差别全在「否决怎么算」：

| 模式 | 通过条件 | 否决语义 |
| --- | --- | --- |
| 会签 all | 全员同意 | **一票否决**（一人拒绝即 rejected） |
| 或签 any | 任一人同意即过 | 全员否决才否（一人拒绝流程继续等） |
| 权重票 weight | Σ同意权重 ≥ 阈值 | 剩余全投同意也够不到阈值 → **提前判负** |

权重票的提前判负是常被漏掉的细节：`agreeSum + remaining < threshold` 时结果已定，继续等人投票只会让流程假死等待。

**条件路由（排他网关）**按规则顺序匹配第一条满足条件的分支，**无条件的规则是默认兜底**。两条纪律：条件必须是纯函数（同样的变量必须同样的结果）；兜底必须放最后——顺序敏感是网关规则的天然属性，不是 bug。

### 42.2.2 核心代码

```ts
// 文件: examples/42-02-countersign-routing.ts
export class CountersignNode {
  vote(signerId: string, v: "agree" | "reject"): void; // 重复投票/非签人抛错
  status: "pending" | "passed" | "rejected";           // 短路评估：能出结果立即出
}
export interface RouteRule { to: string; when?: (vars: Vars) => boolean }
export function route(rules: readonly RouteRule[], vars: Vars): string; // 无兜底且未命中 → 抛错
```

> 运行方式：`npx tsx examples/42-02-countersign-routing.ts`。

### 42.2.3 应用实践

- **产品语义要对齐**：「或签一票否决」还是「或签全员否决才否」，各 OA 实现不同——钉钉或签是一人拒绝即拒绝。语义错了，用户觉得系统「抽风」；
- **投票不可改**：`votes` 一旦写入不允许覆盖，改票走「撤销重发」的显式流程，否则审计对不上；
- **网关条件引用流程变量**：`amount > 5000` 里的 `amount` 来自 42.5 的 ProcessVariables——变量是网关的数据源，留痕是审计的前提。

## 42.3 撤回、驳回与加签

### 42.3.1 概念解析

三个改变流程走向的操作，各自的「窗口」和「落点」是设计核心：

- **撤回 withdraw**：窗口 = **首个审批人处理之前**（钉钉式语义）。判定条件是「除发起步骤外，任何审批任务都不曾有处理动作」——只看「当前节点」会漏掉已走过的节点；
- **驳回 returnTo**：落点 = 指定历史节点（最常见退回发起节点）。实现要点是**截断**：丢弃落点之后的所有步骤，把落点任务重置为 waiting，流程从落点重新走。不截断就会留下幽灵任务；
- **加签 addSigner**：在当前节点临时插入处理人（前加签插名单头/后加签追加尾部）。会签语义下新签人**必须同意**节点才能出——否则加签形同虚设。

三个操作都要落审计（谁在哪个节点做了什么），否则「这单为什么回到发起人」永远说不清。

### 42.3.2 核心代码

```ts
// 文件: examples/42-03-withdraw-return-addsign.ts
export class FlowRuntime {
  act(assignee, action: "approve" | "reject", comment?): void; // 全员同意才流转
  withdraw(by): { ok: boolean; reason?: string };               // 撤回窗口守卫
  returnTo(stepIndex, by, comment?): { ok: boolean; reason?: string }; // 截断 + 重置
  addSigner(mode: "before" | "after", assignee, by): { ok: boolean; reason?: string };
  readonly auditLog: string[]; // 三类操作全部留痕
}
```

> 运行方式：`npx tsx examples/42-03-withdraw-return-addsign.ts`。

### 42.3.3 应用实践

- **撤回失败要给出路**：返回值带 reason（「审批人已处理，不可撤回」），前端据此提示「可联系审批人驳回」——直接弹「操作失败」是体验灾难；
- **驳回可退回到发起人或任意历史节点**：退到中间节点（如「财务复核」）用于补材料后继续走，比退回发起人重走全程成本低；
- **加签后节点展示要标注**：`task.added` 标记加签插入的处理人，时间线上区分「原节点成员」和「临时加签」——审计时这是重要信息。

## 42.4 流程定义：JSON 校验与模拟执行

### 42.4.1 概念解析

审批引擎的核心资产不是代码，是**流程定义**——一份可存储、可版本化、可校验的 JSON。节点五类：`start` / `userTask` / `exclusiveGateway`（排他网关）/ `parallelGateway`（并行网关）/ `end`。

**装载期校验**（与第 38 册 Schema 自检同思想）：错误在发布前暴露，而不是运行到一半无路可走。六条结构规则：

1. 节点 id 不重复；
2. start 恰好 1 个；
3. start 可达全部节点（BFS，抓孤儿）；
4. 非 end 节点必须有后继；
5. end 不能有出边；
6. 排他网关**恰好一个默认分支**——所有分支都带条件时，条件全 false 就卡死。

**模拟执行**（simulate）在校验通过后按变量走一遍流程输出路径，是流程发布前的「干跑」：产品经理配置完流程，先用测试变量跑一遍看路径对不对，再发布上线。

### 42.4.2 核心代码

```ts
// 文件: examples/42-04-flow-definition.ts
export function validateFlow(nodes: readonly FlowNode[]): { ok: boolean; errors: string[] };
export function simulate(nodes: readonly FlowNode[], vars: Vars, maxSteps?): { path: string[]; error?: string };
// FlowNode: { id, kind, name?, assignee?, next?, branchConditions? }
```

> 运行方式：`npx tsx examples/42-04-flow-definition.ts`（示例含合法流程的双路径模拟 + 一份坏流程的 6 类错误全量报出）。

### 42.4.3 应用实践

- **并行网关要 fork/join 配对**：parallelGateway 分叉后必须汇合（join），join 等所有分支到达才放行——教学示例取第一后继简化，真实引擎要做令牌合并；
- **死循环防御**：simulate 带 maxSteps，网关条件写错（如回边条件恒真）时超限报错，而不是模拟器挂死；
- **定义要有版本**：流程定义改版后，已在途的审批单按旧版本走完（版本快照跟着单子走），新单走新版——和第 38 册草稿 schemaVersion 作废是同一思想的反面（这里要保留旧版，不能作废）。

## 42.5 节点表单权限与流程变量

### 42.5.1 概念解析

审批表单和普通表单（第 38 册）的核心差别：**权限跟着节点走**。同一张表单，发起节点全可编辑，审批节点只能看或改个别字段。四级字段权限：

- **hidden**：不可见，提交体里**裁 key**（不出字段名，而不是置 null——与第 37 册出口脱敏同原则：置 null 仍泄露「存在该字段」，且 null 可能覆盖服务端已有值）；
- **read**：只读，值照常带出（审批人要看上下文）；
- **edit**：可改（如总监调整费用）；
- **required**：必填校验。

未在权限表里的字段**默认 hidden**——默认拒绝原则（第 37 册），新增字段不会意外泄露给审批节点。

**流程变量**（ProcessVariables）：发起时注入 + 节点处理中写入，驱动 42.4 的网关条件。每次写入留痕（谁、在哪个节点、改成什么）——审计时能回答「days 从 3 变 5 是谁干的」。

### 42.5.2 核心代码

```ts
// 文件: examples/42-05-form-perm-variables.ts
export type FieldPerm = "hidden" | "read" | "edit" | "required";
/** 按节点权限解析表单：hidden 裁 key 出提交体，required 缺失进 violations */
export function resolveNodeForm(fields, perm: NodeFormPerm, values): ResolveResult;
export class ProcessVariables {
  set(key, value, by, node): void; // 写入留痕
  snapshot(): Readonly<Record<string, unknown>>; // 喂给网关条件
}
```

> 运行方式：`npx tsx examples/42-05-form-perm-variables.ts`。

### 42.5.3 应用实践

- **前端权限只管体验，服务端必须二次校验**：审批人把只读字段改成可编辑发请求，前端拦不住——服务端按同一份权限表校验提交体（第 37 册字段白名单的服务端实现）；
- **敏感字段对审批链路也隐藏**：薪资等级这种字段对全部审批节点 hidden，只有 HR 节点可见——审批流不是权限的免检通道；
- **变量变更有事件语义**：审批中改 urgent 变量会影响后续路由，留痕让「流程为什么走了总监」可解释——解释不了的流程会被业务方当成 bug 报障。

## 42.6 工程实践

### 42.6.1 引擎选型与前端职责

- **能买不造**：标准行政审批用钉钉/飞书审批包零代码解决；复杂流程（BPMN、人工+自动混合、长事务）后端上 Flowable/Camunda/Temporal——自研引擎只在与业务强耦合的领域值得；
- **前端三件套**：流程设计器（渲染定义 JSON + 拖拽编排）、审批表单（resolveNodeForm 按节点渲染）、时间线（history 渲染轨迹）。三件套的共同输入都是「定义 + 数据」，不含引擎判定逻辑；
- **判定逻辑只在一处**：状态迁移、会签判定、网关路由全部在服务端；前端的状态机/网关代码用于按钮显隐和路径预览，不做权威判定。

### 42.6.2 运行时配套

1. **超时与催办**：节点配 SLA（如 48h），到点自动催办（IM 推送，第 39 册通道），超时限自动通过/转交/升级——审批流最大的卡点是「没人处理」；
2. **代理与转交**：休假期间的审批代理要在流程定义外配（人员维度），与节点 assignee 解析时合并；
3. **审计与回放**：history + 变量留痕 = 完整回放素材；疑难单据排查时按审计序号重演一遍；
4. **在途兼容**：流程定义升级时在途单按旧版本快照走完——定义表带 version 字段，审批单创建时冻结版本号。

## 42.7 自测题

1. 为什么 approved 是终态（迁移表空数组），而 rejected/withdrawn 可以回 pending？

<details><summary>查看答案</summary>

rejected/withdrawn 是「中间受挫态」：单子内容还会修改重提，业务上允许再来一轮；approved 是业务结论已生效（钱已付、资源已批），再流转会破坏外部一致性（已发的钱不能靠改状态收回，要走反向单据）。用空迁移表封死终态，让「终态不可再操作」成为结构保证而不是每个方法里的 if。
</details>

2. 会签 all 和或签 any 的否决语义有什么不同？权重票「提前判负」的条件是什么？

<details><summary>查看答案</summary>

会签 all 一票否决——任一人 reject 节点立即 rejected（结果已定，不用等其他人）；或签 any 只在全员否决时才 rejected，任一人同意即通过。权重票提前判负：agreeSum + 剩余未投票权重之和 < threshold，此时即使剩余全投同意也达不到阈值，继续等待只会假死。
</details>

3. 撤回窗口为什么判定「除发起步骤外无任何处理动作」而不是「当前节点没人处理」？

<details><summary>查看答案</summary>

线性流程走到第 3 个节点时，「当前节点没动」但前两个节点已经处理过——审批人已经投入了判断成本、可能已发出通知。此时撤回会让历史审批作废却无痕，通知错乱。钉钉式语义把窗口收紧到「首个审批人处理前」，一旦有任何审批动作就只能走「驳回」这个有审计、有理由的路径。
</details>

4. 排他网关为什么强制恰好一个默认分支？没有会发生什么？

<details><summary>查看答案</summary>

条件分支是业务写死的谓词，变量千奇百怪的取值可能让所有条件同时为 false（如负数金额、空字符串）。没有默认分支时网关无路可走，审批单卡死在中间节点，用户看到「转圈」。强制默认分支把「兜底」变成定义层必须声明的结构，装载期校验就能拦住，而不是运行期报障。
</details>

5. hidden 字段为什么裁 key 而不是置 null 提交？

<details><summary>查看答案</summary>

两个原因：① 置 null 仍向审批人（及网络抓包）泄露「存在 salary 这个字段」——字段名本身就是信息；② null 会作为提交值覆盖服务端已有数据，若服务端没按权限过滤，hidden 字段会被 null 清空。裁 key 是第 37 册出口脱敏的同一原则：不可见的字段在提交体里根本不存在。
</details>

## 42.8 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 直接改 state 不走迁移表 | 非法状态出现，审计断链 | 所有流转过 canTransition + 落 history |
| 状态迁移不落审计 | 「谁同意的」永远说不清 | 每次迁移记录 who/when/from/to/comment |
| 或签实现成一票否决 | 一人误点全单报废 | 或签 = 任一同意即过、全员否决才否 |
| 权重票不提前判负 | 必输的流程等全员投完 | agreeSum + remaining < threshold 即判负 |
| 允许投票后改票 | 审计记录与结果对不上 | 投票不可覆盖，改票走显式撤销重发 |
| 排他网关无默认分支 | 条件全 false 流程卡死 | 装载期强制恰好一个默认分支 |
| 网关条件含副作用 | 规则顺序影响执行结果 | 条件纯函数 + 兜底放最后 |
| 撤回只判当前节点 | 历史节点已处理仍可撤，通知错乱 | 判「除发起步骤外无任何处理动作」 |
| 驳回不截断后续步骤 | 幽灵任务残留，重走后重复审批 | 截断到落点，落点任务重置 waiting |
| 加签人不纳入会签判定 | 加签形同虚设，走了个过场 | 会签语义全员同意（含加签人） |
| 流程定义发布前不校验 | 运行到一半无路可走 | 装载期校验：孤儿/后继/网关默认分支/end 出边 |
| hidden 字段置 null 提交 | 泄露字段存在 + 覆盖服务端值 | 裁 key，提交体里根本不出 |
| 只读权限只做在前端 | 审批人改包绕过越权写 | 服务端按同一权限表二次校验提交体 |
| 流程变量写入不留痕 | 「变量谁改的」无法解释 | 变更记录 by/node/value，随审计可回放 |
