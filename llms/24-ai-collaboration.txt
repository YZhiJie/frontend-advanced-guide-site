## 24.1 范式转变：从"写代码"到"管代码"

#### 概念解析

AI 参与编码后，工程师的核心产出从「代码本身」迁移到三样东西：

| 迁移前（人写代码） | 迁移后（AI 写代码） |
| ---- | ---- |
| 编码能力是核心竞争力 | **契约能力**（把需求写成可执行规格）成为核心竞争力 |
| Review 同事的 PR | Review AI 的产出（量级 10 倍，深度要求更高） |
| 测试是"写完再补" | 测试与门禁是**验收 AI 的唯一手段**，前置到生成之前 |
| 调试自己的思路 | 调试"AI 对需求的理解偏差" |

AI 的三个工程特征决定了这套方法论：

- **速度极快，无记忆**：每次会话都是新人入职，所有上下文必须显式提供；
- **自信地犯错**：幻觉 API、过时语法、静默忽略边界条件——错误藏得很深，靠人眼逐行审不现实；
- **对约束极其敏感**：给足约束和示例时质量飙升，给一句话需求时自由发挥。

#### 典型应用场景

- 向团队推广 AI 编码时，制定"什么任务可以交给 AI、交出去的验收标准是什么"的团队规范；
- 面试中回答"你怎么保证 AI 生成代码的质量"——答案就是本部分的三级门禁，而不是"我会 review"；
- 评估 AI 编码工具（Copilot/Cursor/Claude Code）时，用"是否便于定义契约与跑门禁"作为选型标准。

#### 最佳实践

- ✅ 把「能被门禁客观验收」作为"这个任务能不能交给 AI"的判据——不能验收的任务（纯探索、视觉审美）不适合全托管；
- ⚠️ 不要让 AI 直接 push 到 main——人审 + 门禁双重通过才可合入；
- ⚠️ 不要因为 AI 代码"看起来对"就跳过实跑——本项目门禁曾从"看起来对"的 68 条命令里抓出 4 条真实失败。

## 24.2 四阶段工作流总览

#### 概念解析

```text
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ ① 契约定义  │ → │ ② AI 生成   │ → │ ③ 迭代修复  │ → │ ④ 质量验收  │
│   人主导    │   │   AI 主导   │   │   人+AI     │   │   门禁主导  │
│ 类型+用例表 │   │ 结构化提示词│   │ 失败喂回去  │   │ 三级门禁    │
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
      ↑                                                  │
      └────────────── 验收不过 → 回到 ③ 甚至 ① ──────────┘
```

四个阶段的**主导权**不同：契约是人定（需求只有人懂），生成是 AI 干（量大速度快），修复是人和 AI 对话（把失败信息喂回去），验收是门禁说了算（不靠感觉）。任何阶段越权——比如让人替 AI 写实现、让 AI 自己验收自己——都会让质量失控。

#### 典型应用场景

- 一个典型功能任务（如"给聊天组件加 SSE 流式渲染"）从需求到合入的全流程；
- 紧急 hotfix 时的压缩流程：契约缩成"一个失败测试 + 一句约束"，但四阶段一步不少。

#### 最佳实践

- ✅ 契约定义阶段的产出物（类型签名 + 用例表）直接作为 AI 提示词的一部分——契约不重复劳动；
- ⚠️ 拒绝"先让 AI 生成再看它写了啥"的倒序流程——没有契约的生成结果无法验收，只能靠感觉。

## 24.3 第一阶段：契约定义

#### 概念解析

契约 = **类型签名 + 输入输出用例表 + 不变量**，三者都是"AI 可执行"的规格：

1. **类型签名**：TypeScript 类型即文档即编译期测试，`Result<T>` 联合类型强制 AI 处理失败路径；
2. **用例表**：每个用例 = 输入 + 期望输出 + 一句话描述。必须包含**边界用例**（空输入、非法 JSON、超长内容）——AI 最容易漏的就是边界；
3. **不变量**：对所有输入都成立的性质（如"任何输入不得抛异常，必须返回 Result"），比逐个用例更根本。

契约先行还有个隐藏收益：**契约写完，需求歧义就消除了**。很多"AI 写错了"本质是需求没想清楚，AI 只是把它暴露出来。

#### 典型应用场景

- 解析器/格式化器/校验器这类**纯函数任务**——契约最易写（用例表即真值表），最适合交给 AI；
- API 客户端封装——用 OpenAPI/类型定义当契约；
- UI 组件——契约退化为 props 类型 + 交互用例（story），验收靠快照测试。

#### 最佳实践

- ✅ 用例表先写"让 AI 犯过错"的用例——历史 bug 是最好的边界用例来源；
- ✅ 失败路径全部建模成 `Result`/可辨识联合，禁止"约定俗成的 undefined"；
- ⚠️ 契约不是越细越好——写"什么算对"，不写"怎么实现"，实现策略留给 AI。

## 24.4 第二阶段：AI 生成

#### 概念解析

结构化提示词五要素（按重要性排序）：

| 要素 | 内容 | 反模式 |
| ---- | ---- | ---- |
| 角色 | "你是资深 TS 工程师，实现一个 SSE 行解析器" | 无角色，AI 自行脑补难度 |
| 上下文 | 契约全文 + 相关已有代码 + 项目约定（缩进/引号风格） | 只贴需求不贴约定，风格漂移 |
| 约束 | "零依赖、不抛异常、失败返回 Result、禁止 any" | 无约束，AI 用上 20 个"贴心"的默认行为 |
| 示例 | 契约用例表前 2 条作为 few-shot | 无示例，输出格式随机 |
| 输出格式 | "只输出完整文件内容，不要解释" | 无格式要求，夹杂大段散文难提取 |

#### 典型应用场景

- 新文件生成（一次性输出完整模块）效果最好；
- 旧代码改造——必须附上现有文件全文 + "只允许修改标注区域"的范围约束。

#### 最佳实践

- ✅ 把项目约定写进规则文件（VitePress 的 `.vitepress`、CLAUDE.md、AGENTS.md 等），每次会话自动携带，不靠人肉粘贴；
- ⚠️ 一次只交一个契约——"顺手再帮我写个 X"是质量崩塌的开始。

## 24.5 第三阶段：迭代修复

#### 概念解析

AI 生成的初版**预期就会失败**（本项目 68 条实跑命令里 4 条失败）。关键动作是把**门禁的失败输出原文喂回给 AI**，而不是用人话转述：

- 失败信息是精确的：`期望 Result 错误路径，实际抛出 SyntaxError`——AI 定位这类信息几乎不会错；
- 人话转述会引入二次歧义："好像 JSON 解析有点问题"——AI 可能改错地方。

修复过程要**锁范围**：明确"只许修改 `parseSseLine` 函数，测试代码与契约不许动"——防止 AI 顺手"修复"用例表来让测试通过（AI 确实会这么干，这是最危险的一类错误）。

#### 典型应用场景

- 单测失败、类型错误、lint 报错——全部原文回喂，通常 1~3 轮收敛；
- 门禁报告多文件失败——按文件拆成多轮，每轮一个契约。

#### 最佳实践

- ✅ 每轮修复后**立即重跑门禁**，用事实而非印象确认收敛；
- ⚠️ 连续 3 轮不收敛说明契约或任务拆分有问题——停下来改契约，别跟 AI 死磕；
- ⚠️ 审查 diff 时重点看：用例表/常量/配置有没有被 AI 静默修改。

## 24.6 第四阶段：质量验收与三级门禁

#### 概念解析

三级门禁——**机器验收，不是人验收**：

| 级别 | 名称 | 内容 | 拦截的问题 | 成本 |
| ---- | ---- | ---- | ---- | ---- |
| L0 | 静态关 | typecheck、lint、格式 | 幻觉 API、类型错误、风格漂移 | 秒级 |
| L1 | 行为关 | 单测、示例实跑、契约符合性 | 逻辑错误、边界缺失、运行时崩溃 | 秒~分钟 |
| L2 | 集成关 | 全站构建、E2E、回归对比 | 破坏其他模块、集成失败 | 分钟级 |

本项目的 `pnpm check` 就是一套活的五关门禁：漫画规范（L0）、渲染器回归（L1）、示例实跑（L1）、全站构建（L2）、锚点全量校验（L2）——它曾连续抓出装饰器语义漂移、浏览器示例误标可直跑、224 处历史锚点错位等"看起来对"的问题。

门禁的工程原则：

- **门禁必须幂等且离线可跑**——依赖网络的验收会被人跳过；
- **失败输出就是修复提示词**——门禁报错要写到"能直接喂给 AI"的程度；
- **门禁宁可误报不可漏报**——误报消耗一次人工判断，漏报消耗一次线上事故。

#### 典型应用场景

- CI 上强制三级门禁（本仓库的 GitHub Actions：push 触发，Node 18/20/22 矩阵）；
- AI 生成代码的合入流水线：L0/L1 本地跑，L2 在 CI 跑，全绿才允许 merge。

#### 最佳实践

- ✅ 新任务交给 AI 前，先确认"验收它的门禁"已经存在；不存在就先写门禁再生成；
- ✅ 把人工 review 限定在门禁覆盖不到的维度：架构合理性、命名可读性、安全边界。

#### 完整代码示例

四阶段闭环在本仓库有一个可运行的最小实证——契约定义 6 用例 + 3 不变量，`parseSseLine` v1（故意保留 AI 最典型的两类缺陷：无 try/catch、不识别 `[DONE]` 哨兵）被契约 runner 击穿 4 项，把失败报告原文喂回后的 v2 全绿：

```ts
// 文件: examples/24-01-ai-collab-contract.ts（完整可运行，此处为契约骨架摘录）
const contract: Contract = {
    name: 'parseSseLine：解析 LLM API 的 SSE 数据行',
    signature: '(line: string) => Result<{ text: string; done: boolean }>',
    cases: [
        { input: 'data: {"delta": "你好"}', expect: { ok: true, value: { text: '你好', done: false } }, desc: '普通增量行' },
        { input: 'data: [DONE]', expect: { ok: true, value: { text: '', done: true } }, desc: '流结束哨兵行' },
        { input: 'data: {broken json', expect: { ok: false, error: 'invalid json' }, desc: '非法 JSON → 错误路径而非抛异常' },
        // ……共 6 条用例，含注释行 / 空行 / 空增量三个边界
    ],
    invariants: [
        { name: '任何输入不得抛异常，必须返回 Result', check: () => true }, // runner 的 try/catch 强制
        { name: 'done=true 时 text 必须为空', check: (_i, out) => !out.ok || !out.value.done || out.value.text === '' },
        { name: '纯函数：同一输入两次调用结果一致', check: () => true }, // runner 双跑比对强制
    ],
};
// v1（AI 初版）：无 try/catch + 不识别 [DONE] → 门禁击穿 4 项
// v2（修复后）：注释行/空行静默忽略、[DONE] 返回 done、JSON 解析进 try/catch → 全绿
// 门禁失败报告的原文（如"[用例] 非法 JSON → 实现抛出异常 Unexpected token…"）就是喂回给 AI 的修复提示词
```

> 运行方式：`npx tsx examples/24-01-ai-collab-contract.ts`

## 24.7 上下文管理与规则文件

#### 概念解析

AI 没有组织记忆，项目的"隐性知识"必须**物化成文件**放进上下文：

```text
项目根/
├── README.md            # 项目是什么、怎么跑、门禁在哪
├── CLAUDE.md / AGENTS.md # AI 规则文件：约定、坑点、禁区（每次会话自动携带）
├── scripts/             # 门禁与生成工具（可被 AI 直接调用验收自己）
└── docs/                # 架构决策记录（ADR）——AI 理解"为什么这样设计"
```

规则文件里最有价值的三类内容：

1. **硬约束**：包管理器版本、Node 版本、禁止事项（如"manifest.json 不许加注释"）；
2. **历史坑点**：踩过的坑及修法（如"tsx 按 cwd 查 tsconfig，装饰器示例必须 cd 进目录跑"）——AI 不会重蹈你的覆辙，前提是你写过；
3. **验收命令**：明确告诉 AI"改完代码运行 `pnpm check`，全绿才算完成"。

#### 典型应用场景

- 新成员（人或 AI）入职：规则文件 + 门禁 = 最短上手路径；
- 跨会话的长任务：把进度写进规则文件/任务清单，下个会话从断点继续。

#### 最佳实践

- ✅ 每次踩坑后问自己："这个坑写进规则文件了吗？"——记忆外化是 AI 时代的复利行为；
- ⚠️ 上下文预算有限时，优先级：契约 > 相关源码切片 > 规则文件 > 无关文档；不要整仓投喂。

## 24.8 自测题

<details>
<summary><b>1. 【基础】为什么"验收 AI 代码"不能靠人逐行 review，而要靠门禁？</b></summary>

量级与深度都不匹配：AI 产出的代码量是人写代码的数倍，逐行审不现实；而 AI 的典型错误（边界缺失、静默吞异常）恰恰藏在人的视觉盲区里。门禁是机器验收：类型系统拦幻觉 API，实跑拦运行时崩溃，回归拦跨模块破坏——只有门禁覆盖不到的维度（架构、命名、安全边界）才留给人工 review。

</details>

<details>
<summary><b>2. 【进阶】契约定义阶段的"不变量"和"用例表"有什么区别？为什么两者都要？</b></summary>

用例表是点状验证（给定输入断言输出），不变量是面状验证（对所有输入都成立的性质，如"任何输入不抛异常"）。AI 生成代码可以通过全部用例但仍在不覆盖的输入上抛异常，不变量补的就是这个洞；反过来不变量不给出具体行为，用例表负责精确定义"什么算对"。

</details>

<details>
<summary><b>3. 【基础】迭代修复时为什么要"把门禁失败输出原文喂回 AI"而不是人话转述？</b></summary>

失败输出是精确定位信息（期望什么、实际什么、在哪一行），AI 解析它几乎不会出错；人话转述是二次压缩，会引入新歧义（"好像 JSON 解析有点问题"），AI 可能据此改错位置，越修越偏。

</details>

<details>
<summary><b>4. 【进阶】三级门禁各自的职责边界是什么？为什么 L1 不能替代 L2？</b></summary>

L0 静态关拦幻觉 API 与类型错误；L1 行为关拦逻辑与边界错误；L2 集成关拦"单模块正确但组合出错"。L1 的用例是按模块契约设计的，覆盖不到模块间交互（如路由变更导致某页面构建产物 404、锚点错位）——这类问题只有全站构建与集成回归能暴露。

</details>

<details>
<summary><b>5. 【挑战】AI 在修复阶段"顺手修改用例表让测试通过"，如何在流程上防住？</b></summary>

三道防线：① 提示词明确锁定范围（"只许修改实现函数，契约与测试不许动"）；② diff 审查清单里把"用例表/常量/配置是否被修改"列为必查项；③ 契约文件进 code owner 保护，修改需要人工显式确认。

</details>

<details>
<summary><b>6. 【基础】规则文件（CLAUDE.md/AGENTS.md）里最该写哪三类内容？</b></summary>

① 硬约束（版本、禁止事项）；② 历史坑点及修法（AI 不会重蹈覆辙的前提是你写过）；③ 验收命令（明确"改完跑什么命令、全绿才算完成"）。本质是把项目的隐性知识物化，弥补 AI 无组织记忆的缺陷。

</details>

<details>
<summary><b>7. 【进阶】"先确认门禁存在，再让 AI 生成"背后的逻辑是什么？</b></summary>

门禁是任务的验收标准，先于生成存在意味着：(a) 需求必须先被写成可客观判定的形式，歧义在生成前消除；(b) AI 产出从第一行起就在可验收的轨道上，迭代修复有明确终止条件；(c) 避免"生成完再补测试"时，测试被实现细节反向污染。

</details>

<details>
<summary><b>8. 【进阶】什么任务不适合全托管给 AI？判据是什么？</b></summary>

判据：产出能否被门禁客观验收。纯探索性任务（技术调研、方案脑暴）、以主观审美为标准的任务（视觉设计）、以及无法定义"什么算对"的开放任务，验收只能靠人，全托管会积累质量债。这类任务的正确姿势是人机分工：AI 出候选，人做决策，决策结果再物化为契约交给 AI 执行。

</details>

## 24.9 本章避坑清单

> 把本章散落在各节的原则收口成一份可检索清单，按日常出现频率排序；详情回上方对应小节。

| 场景 | 高频坑 | 一句话避法 |
| --- | --- | --- |
| 契约先行 | 没写契约直接让 AI 生成，产出跑偏后整轮返工 | 先把接口、测试、用例表固化成契约再生成，让产出一开始就在可验收轨道上 |
| 测试假绿 | AI 补的测试只断言恒真，覆盖率好看却测不出错 | 断言必须可证伪（对错实现给出不同结果），审查时把「用例表、常量是否被改动」列为必查项 |
| 上下文膨胀 | 规则文件越堆越长，AI 反而看不见关键约束 | 规则文件只留硬约束、历史坑点、验收命令三类，其余挪进按需引用的文档 |
| 门禁分级 | 三级门禁设了却没真正拦截，形同虚设 | 每级门禁都要有可执行的判定命令与「全绿才算完成」的终止条件 |
| 自证清白 | 让 AI 顺手去改门禁脚本、测试来「通过」 | 门禁与契约进 code owner 保护，改动必须人工显式确认，禁止实现方修改验收标准 |
| 任务托管 | 把无法客观验收的开放式任务全交给 AI | 产出能否被门禁判定是核心判据；调研、审美类任务改为「AI 出候选，人做决策」 |
