## 70.1 桌面端形态坐标：Electron / Tauri / CEF / WebView2 选型矩阵

### 概念解析

8.4 节给出了 Electron 的最小可运行骨架（主进程 + 预加载 + contextBridge）。真实项目里的第一个难题不是「怎么写」，而是「选哪个壳」。四条主流路线的本质差异在于**渲染引擎从哪来、系统能力由谁提供**：

| 路线 | 渲染引擎 | 系统能力层 | 安装包体积 | 内存占用 |
| --- | --- | --- | --- | --- |
| **Electron** | 自带完整 Chromium | Node.js 主进程 | ~150MB 起步 | 高（每个窗口一套 Chromium 开销） |
| **Tauri** | 操作系统自带 WebView | Rust 核心进程 | ~10MB 量级 | 低（复用系统 WebView） |
| **CEF** | 嵌入式 Chromium（你控制版本） | 宿主 C++ 进程 | ~80MB | 高 |
| **WebView2** | Windows 自带 Edge WebView2 | 宿主 .NET/C++ 进程 | 几乎为 0（运行时系统预装） | 低 |

关键约束逐条看：

1. **包体积**：Electron 把 Chromium 打进包里，「小而美」工具类应用发出去 200MB 很难向用户交代；Tauri 与 WebView2 复用系统组件，包体一个数量级地小。
2. **跨端一致性**：Electron 自带 Chromium = 三端渲染结果像素级一致；Tauri 是「三端三个 WebView」（macOS 的 WKWebView、Windows 的 WebView2、Linux 的 WebKitGTK），CSS 兼容性问题会回来找你。
3. **系统能力深度**：Tauri 的 Rust 核心可以直接调一切 OS API，性能敏感的非核心模块还能就地用 Rust 重写（衔接第 71 册）；Electron 走 Node + 原生模块（N-API），生态更全但跨进程开销大。
4. **团队栈**：Electron 对纯前端团队零门槛；Tauri 要求团队里至少有一人能读写 Rust；WebView2 绑定 .NET 生态；CEF 绑定 C++。
5. **分发渠道**：政企内网 Windows 专用场景，WebView2 运行时由系统/镜像预装，几乎零部署成本；要进 macOS App Store 则各路线都要过公证与审核（见 70.4）。

**一句话决策**：三端一致 + 纯前端团队 → Electron；体积敏感 + 有 Rust 能力 → Tauri；已有 C++ 客户端要内嵌 Web 页面 → CEF；政企 Windows-only 内网 → WebView2。

把「团队画像」翻译成「结论」的决策表（示例的决策器就是这张表的可运行版）：

| 团队栈 | 体积预算 | 系统能力需求 | 跨端要求 | 推荐 |
| --- | --- | --- | --- | --- |
| React/Vue 纯前端 | 宽松（≥150MB） | 常规（文件/通知/窗口） | 三端一致是硬指标 | **Electron** |
| 前端 + 有人懂 Rust | 紧张（≤30MB） | 深（串口/驱动/高性能计算） | 三端但接受 WebView 差异 | **Tauri** |
| .NET/C# | 紧张 | 常规 | 仅 Windows | **WebView2** |
| C++ 存量客户端 | 无所谓 | 极深（已用 C++ 实现） | 跟随存量客户端 | **CEF** 嵌入 |
| 任何栈 | 极紧张（≤10MB） | 常规 | 仅 Windows 政企内网 | **WebView2**（运行时系统预装） |

注意决策表里没有出现「想用新框架」这一列——技术偏好不是约束，约束才是。

### 典型应用场景

- **企业办公套件 / IDE 级产品**：窗口多、交互重、三端体验必须一致，且团队以前端为主——VS Code、飞书、Slack 都选 Electron，一致性收益大于体积代价；
- **轻量桌面工具 / 托盘常驻 IM 辅助端**：体积和内存是核心卖点，团队有 Rust 能力——典型 Tauri 场景；
- **政企内网办公插件**：只跑 Windows、客户机器受管控、安装包要走 U 盘分发——WebView2 几乎是唯一正解；
- **存量 C++ 客户端的界面现代化**：十年历史的 C++ 桌面客户端不想重写，把新模块用 Web 技术做——CEF 嵌入。

### 可运行代码示例

下面把「团队画像 → 加权打分 → 推荐理由」的决策过程做成可运行决策器：六个维度（包体积/内存/生态/系统能力/团队栈/跨端一致性）静态评分，团队栈匹配按画像动态给分，硬约束（要求跨端但候选只能跑 Windows）直接总分打折：

```ts

function deriveWeights(p: TeamProfile): Record<Dimension, number> {
  return {
    bundle: p.bundleBudgetMB <= 30 ? 3 : p.bundleBudgetMB <= 100 ? 2 : 1,
    memory: p.isIntranetOnly ? 2 : 1, // 内网老机器多，内存敏感
    ecosystem: p.teamStack === "react-ts" || p.teamStack === "vue-ts" ? 3 : 1,
    systemApi: p.needDeepSystemApi ? 3 : 1,
    teamFit: 2, // 团队栈永远是重要约束：学习成本直接折算成排期
    crossPlatform: p.needCrossPlatform ? 3 : 1,
  };

```

### 最佳实践

1. **按约束选型，不按热度选型**。Tauri 热度高不代表适合：团队没有 Rust 能力、产品重度依赖 Chromium 独有 API（如复杂的 `chrome.*` 调试能力），选 Tauri 就是给自己挖坑。
2. **Electron 仍是正解的三个信号**：① 三端视觉一致性是硬指标；② 依赖只在 Chromium 上验证过的复杂前端能力（大型表格 canvas 渲染、复杂打印）；③ 团队没有系统语言储备。三条中两条就别折腾。
3. **Tauri 立项前先验证系统 WebView 差异矩阵**：把产品的核心页面在 WKWebView / WebView2 / WebKitGTK 各跑一遍，特别是 CSS（`backdrop-filter`、滚动条样式）、音视频编解码、剪贴板行为——差异在立项阶段发现是选型问题，在交付前发现是事故。
4. **混合架构是常见终态**：外壳保持 Electron 不动，把 CPU 密集的独立工具进程用 Rust 写（通过子进程或 sidecar 调用）——拿到 Rust 的性能收益，不动主架构。
5. **把选型结论写成 ADR**：记录当时的约束（团队栈、体积预算、系统能力清单），半年后新人质疑「为什么不用 X」时，翻文档而不是重开一轮辩论。

## 70.2 Tauri 2 架构与 Rust 命令桥

### 概念解析

**进程模型对比**：Electron 是「Node 主进程 + 每窗口一个 Chromium 渲染进程」的多进程架构；Tauri 是「一个 Rust 核心进程 + 系统 WebView」，前端代码跑在 WebView 里，所有系统能力通过 IPC 向 Rust 侧申请。Tauri 2 里窗口抽象是 `WebviewWindow`（一个窗口里可以挂多个 WebView），创建、聚焦、关闭窗口都是 Rust 侧的对象操作。

**命令桥（invoke / command）**是前端与 Rust 的唯一通道：

- Rust 侧用 `#[tauri::command]` 标注函数，参数与返回值经 serde 走 **JSON 序列化**——这是边界，意味着函数、类实例、`Date`、`Map`、`BigInt` 都过不去（70.3 的示例会实跑验证）；
- 前端侧 `invoke("read_text_file", { path })` 返回 Promise，Rust 侧返回 `Result<T, E>` 时，`Err` 会变成前端的 reject——**错误传递约定必须在团队内统一**：建议 `Err` 一律是结构化对象（带 `code` 与 `message`），而不是裸字符串，否则前端无法按错误码分支处理；
- **事件总线**是反向通道：Rust 侧 `emit("download://progress", payload)`，前端 `listen()` 订阅。事件分全局级与窗口级（`emit_to("main", ...)`），多窗口应用必须想清楚事件的作用域；
- **TS 类型对齐**：前端手写的 invoke 参数类型与 Rust 结构体迟早漂移，工程化解法是用 tauri-specta 之类的工具从 Rust 定义自动生成 TS 绑定，纳入 CI 检查。

**序列化边界的性能含义**：每次 invoke 都是一次 JSON 序列化 + 反序列化。传几 KB 的配置没问题；传 500MB 文件内容就是灾难——大负载要走分片通道（Tauri 2 的 Channel / 自定义流式协议），invoke 只传句柄与偏移量。

**事件作用域**是多窗口应用最容易踩的坑：`emit` 默认全局广播，A 窗口的下载进度会推到 B 窗口。实践上按「事件归属」选择通道：

| 事件归属 | 正确通道 | 例子 |
| --- | --- | --- |
| 属于某个窗口 | `emit_to("窗口label", ...)` | 该窗口的下载进度、表单校验结果 |
| 属于整个应用 | 全局 `emit` | 主题切换、账号登出广播 |
| 属于一次任务 | Channel（随 invoke 建立的一对一通道） | 一次大文件哈希计算的进度流 |

### 典型应用场景

- 配置读写、窗口管理、文件对话框等**小载荷、请求-响应**式调用 → invoke/command；
- 下载进度、键盘录制、系统托盘状态变化等**持续推送** → 事件总线；
- 大文件哈希计算、视频转码进度等**大载荷 + 进度** → invoke 启动任务 + 事件推进度 + 结果落盘后只传路径。

### 核心代码示例

Rust 侧命令与结构化错误（虚拟项目文件，不进 examples/）：

```rust
// 文件: src-tauri/src/lib.rs —— 命令定义与错误约定
use serde::Serialize;

#[derive(Serialize)]
#[serde(tag = "code", content = "message")]
pub enum BridgeError {
    #[serde(rename = "NOT_FOUND")]
    NotFound(String),
    #[serde(rename = "PERMISSION_DENIED")]
    PermissionDenied(String),
}

#[tauri::command]
async fn read_text_file(path: String) -> Result<String, BridgeError> {
    // 安全校验：拒绝路径穿越（与 8.4 的目录白名单同源）
    if path.contains("..") {
        return Err(BridgeError::PermissionDenied("路径穿越被拒绝".into()));
    }
    std::fs::read_to_string(&path).map_err(|_| BridgeError::NotFound(path))
}

#[tauri::command]
fn get_app_version() -> String {
    env!("CARGO_PKG_VERSION").to_string()
}
```

前端侧收敛封装——所有 invoke 调用点集中在一个模块，业务代码不直接接触 `@tauri-apps/api`：

```ts
// 文件: src/lib/desktop.ts —— 前端 invoke 封装层（类型由 tauri-specta 生成后可去掉手写部分）
import { invoke } from "@tauri-apps/api/core";
import { listen } from "@tauri-apps/api/event";

export interface BridgeError {
  code: "NOT_FOUND" | "PERMISSION_DENIED";
  message: string;
}

export const desktop = {
  getAppVersion: () => invoke<string>("get_app_version"),
  readTextFile: (path: string) => invoke<string>("read_text_file", { path }),
  onDownloadProgress: (cb: (percent: number) => void) =>
    listen<number>("download://progress", (e) => cb(e.payload)),
};
```

> 运行方式：Rust 命令桥需要完整 Tauri 工程（`npm create tauri-app` 脚手架）才能真跑；其逻辑内核——类型安全 invoke、序列化边界、错误约定——见 70.3 的可运行示例。

### 最佳实践

1. **命令即 API**：命名动词化（`read_text_file` 而非 `file`），语义稳定后不轻易改签名；命令集合就是你的「桌面端 OpenAPI」，值得像后端接口一样评审。
2. **大负载不走 invoke payload**：超过几 MB 的数据走 Channel 分片或落盘传路径。一个反例：截图命令直接返回 base64 大图，UI 线程在 JSON 解析上卡 2 秒。
3. **事件加命名空间**：`download://progress`、`window://focus` 这种带域前缀的命名，避免多窗口应用里全局事件互相串台；卸载组件时记得 `unlisten()`。
4. **类型生成进 CI**：tauri-specta 生成的 `bindings.ts` 提交进仓库，CI 里重新生成并 `git diff --exit-code`——前后端契约漂移直接拦在合入前。
5. **invoke 封装层是唯一调用点**：业务代码里出现 `@tauri-apps/api` 的 import 即为评审红灯——这层封装同时是 70.6 多端共用的适配点。

## 70.3 IPC 安全模型：能力清单、CSP 与深链攻击面

### 概念解析

桌面端安全模型的核心问题：**跑在 WebView 里的前端代码，能向系统层要多少权力？**

Tauri 2 的答案是 **capabilities（能力清单）**：在配置文件里按窗口声明它允许调用的命令与插件，未声明的调用在 IPC 边界直接被拒。与 Electron 的对照：

| 维度 | Electron | Tauri 2 |
| --- | --- | --- |
| 隔离机制 | `contextIsolation: true` + 预加载脚本 `contextBridge` 最小暴露 | capabilities 按窗口授权命令/插件/事件 |
| 默认姿态 | 靠开发者自觉（8.4 的安全三件套） | 默认拒绝，逐项开通 |
| 授权粒度 | 预加载脚本里写什么暴露什么 | 配置文件声明，可按窗口差异化 |
| 文件系统 | Node `fs` 全量（需自写白名单校验） | fs 插件 + scope 限定目录/通配 |
| 失效场景 | 预加载脚本暴露面过大（如转发任意通道） | capabilities 图省事全开 |

**CSP（内容安全策略）** 在桌面端同样生效且更该收紧：Tauri 的 `tauri.conf.json` 可配置 CSP，生产环境至少做到 `default-src 'self'`、禁 `unsafe-eval`、禁远程脚本源——桌面端加载远程页面等于把系统能力的攻击面开放给任何被劫持的 CDN。

**深链与自定义协议**是被低估的攻击面。应用注册 `myapp://` 协议后，任何网页都能通过 `location.href = "myapp://import?url=..."` 唤起你的应用并递上参数——这些参数是**不可信输入**：直接拼进文件路径就是路径穿越，直接拼进 Shell 命令就是命令注入，直接当 URL 发起请求就是 SSRF 的桌面版。处理深链的第一行代码必须是参数校验。

### 典型应用场景

- 多窗口应用：主窗口需要文件读写，「关于」窗口只需要展示版本号——capabilities 按窗口收窄；
- 第三方内容展示窗口（如OAuth 登录页）：只给导航能力，禁一切命令；
- 注册自定义协议做「网页一键唤起客户端导入文件」——深链参数必须过校验器。

### 可运行代码示例

示例把 IPC 边界的三道防线做成可运行内核：**① 能力 allowlist 拦截 → ② 序列化边界校验（函数/Date/Map/循环引用一律拒绝）→ ③ 结构化错误传递**。关键节选：

```ts
// 节选：examples/70-03-ipc-bridge.ts 的 invoke 四道关卡
return async function invoke<K extends keyof CommandTable>(
  cmd: K,
  args: CommandTable[K]["args"],
): Promise<CommandTable[K]["result"]> {
  if (!cap.allow.includes(cmd)) {
    throw new PermissionDeniedError(`窗口 ${windowLabel} 未声明能力 ${String(cmd)}`);
  }
  assertNoCircular(args);   // 先环检测，否则递归校验在循环引用上栈溢出
  assertSerializable(args); // JSON 边界：函数/Date/Map/BigInt 都过不去
  const result = rustHandlers[cmd](args as never); // Rust 侧返回 Result 风格结构
  if (!result.ok) throw Object.assign(new Error(result.error.message), { code: result.error.code });
  return result.data;
};
```

> 运行方式：`npx tsx examples/70-03-ipc-bridge.ts`

### 最佳实践

1. **默认拒绝、逐项开通**：新建窗口的 capabilities 从空清单开始，用到什么加什么；评审时把 capabilities 文件当安全敏感文件对待（改动需安全相关同事会签）。
2. **fs scope 收到最小**：能限定 `$APPDATA/**` 就不要给 `$HOME/**`；下载目录单独授权，不跟配置目录混用。
3. **生产环境不加载任何远程页面**：前端产物打进安装包；CSP 里不留 `https:` 源。这一条同时规避了「CDN 被劫持 → 客户端变肉鸡」的整条攻击链。
4. **深链参数当不可信输入**：先过 zod 之类的校验器（协议名、字段类型、长度、字符集），再进业务逻辑；涉及文件路径的一律 resolve 后做白名单前缀检查。
5. **高危能力二次确认**：截图、录屏、读取全盘文件这类命令，即使用户侧窗口有权限，也应在 Rust 侧加一次性确认弹窗或速率限制——防止前端 XSS 时能力被静默滥用。

## 70.4 自动更新与发布：签名、灰度、回滚与内网分发

### 概念解析

Web 端发布是「刷新即新版」，桌面端发布是一条**有状态的链路**——每个用户的客户端可能停在任意旧版本上，更新体系要回答四个问题：

1. **怎么保证包是真的**：Tauri updater 用 minisign（ed25519）对安装包签名，公钥编译进客户端，下载后先验签再应用——验签失败的包直接丢弃。**签名私钥必须离线保管**，CI 只在签名机/密钥管理服务里接触它（私钥治理见第 47 册）。
2. **怎么过操作系统的门**：macOS 要求公证（notarization），未公证的包装到用户机器上 Gatekeeper 直接拦；Windows 上 EV 代码签名证书决定 SmartScreen 是放行还是弹红色警告。这两步是发布流水线的固定工位，不是可选优化。
3. **怎么控制爆炸半径**：灰度发布——更新清单里带 `rolloutPercent`，客户端用设备 ID 的稳定哈希分桶决定是否命中（与 59 册的采样同理：**必须稳定哈希，不能随机**，否则同一台设备每次检查都反复横跳）。出问题时回滚的是「更新清单」而不是客户端——把服务端清单指回旧版本即可止血。
4. **政企内网怎么办**：客户机器出不了网，updater 的默认实现全部失效。工程化解法是**离线包 + 内网更新服务器**：管理员把签名后的安装包与静态清单文件（一个 JSON）放进内网任意静态服务器（Nginx/IIS 都行），客户端 updater 的端点指向内网地址——验签逻辑不变，只是源变了。

**增量/差分更新**：全量包 100MB、差分包 8MB，对内网带宽和下载时长是数量级优化。思路与 bsdiff 同源：服务端对新旧版本安装包算二进制差分，客户端下载差分包后在本地合成新包，合成后再过一次验签。注意差分是**版本对**的——从 v2.1 升到 v2.4 的差分包与 v2.3 → v2.4 的不是同一个，服务端要为主流旧版本各准备一条差分链，太旧的版本直接回退全量。

更新清单（latest.json）的典型形态——客户端拿到的全部决策依据都在这一个文件里：

```json
// 文件: latest.json —— 更新服务器下发的静态清单（示例）
{
  "version": "2.4.0",
  "notes": "修复托盘菜单偶现不响应；优化大文件导出内存占用",
  "pub_date": "2026-10-28T02:00:00Z",
  "rolloutPercent": 30,
  "platforms": {
    "darwin-aarch64": {
      "url": "https://update.example.com/v2.4.0/app-aarch64.app.tar.gz",
      "signature": "dW50cnVzdGVkIGNvbW1lbnQ6...",
      "sha256": "9f2c..."
    },
    "windows-x86_64": {
      "url": "https://update.example.com/v2.4.0/app-x64-setup.nsis.zip",
      "signature": "dW50cnVzdGVkIGNvbW1lbnQ6...",
      "sha256": "3b7a..."
    }
  }
}
```

客户端的检查逻辑因此是无状态的：拉清单 → 比版本 → 灰度分桶 → 下载 → 验签 → 应用。每一步的失败都有明确的终态（见示例的状态机），不存在「更新到一半不知道该怎么办」的中间态。

### 典型应用场景

- SaaS 桌面端：每周一版，灰度 5% → 30% → 100%，靠清单回滚止血；
- 政企交付：半年一版离线大包 + 内网更新服务器发补丁包；
- 强合规行业：更新包必须客户内部安全团队审计后才允许上架内网服务器——清单与包分离部署正好满足「包先审、清单后放」的流程。

### 可运行代码示例

示例实现完整状态机 `idle → checking → downloading → verifying → ready → applying`，外加两条支路：验签失败 → `failed` → `rolled-back`；灰度未命中 → 回 `idle`。状态机的价值在于**非法迁移直接抛错**——`idle` 永远不可能直接跳到 `applying`：

```ts
// 节选：examples/70-02-update-state-machine.ts 的迁移表
const TRANSITIONS: Record<UpdateState, UpdateState[]> = {
  idle: ["checking"],
  checking: ["idle", "downloading"], // 无更新/灰度未命中 → 回 idle
  downloading: ["verifying", "failed"],
  verifying: ["ready", "failed"],
  ready: ["applying", "idle"],
  applying: ["done", "failed"],
  failed: ["rolled-back"],
  "rolled-back": ["idle"],
  done: [],
};
```

> 运行方式：`npx tsx examples/70-02-update-state-machine.ts`

### 最佳实践

1. **清单与包分离部署**：清单（JSON）走可秒级回滚的通道（对象存储 + CDN，短缓存），安装包走大文件通道。止血操作 = 改一个 JSON，而不是撤回一批二进制。
2. **验签失败也要上报**：验签失败可能是下载损坏，也可能是中间人投毒——这是安全信号，不是普通错误，应走独立告警（接 59 册的分级上报）。
3. **差分包设阈值**：差分包体积超过全量 60% 就放弃差分直接发全量——差分合成有失败率和 CPU 成本，省不了多少流量时不值得。
4. **回滚预案要预演**：「把清单指回旧版本」这个操作每个季度至少演练一次；止血按钮的存在感和可用性同等重要（59.5 的 SOP 在桌面端同样成立）。
5. **内网更新服务器静态化**：一个 Nginx 托管的目录（清单 JSON + 签名包）就够了——不要为内网更新写动态服务，每多一个服务就多一份客户的运维负担。

## 70.5 桌面端系统能力：多窗口、托盘与全局快捷键

### 概念解析

这一节是桌面端与 Web 端体验差异最大的地方——浏览器里没有托盘、没有全局快捷键、窗口状态不归你管。Tauri 的这些能力以官方插件形式提供，逐项看工程化要点：

| 能力 | 插件/机制 | 工程化要点 |
| --- | --- | --- |
| **多窗口与窗口状态恢复** | `WebviewWindow` API + window-state 插件 | 退出时持久化位置/尺寸/最大化态，重启恢复；**必须校验恢复坐标仍在当前屏幕可见区域内**——用户拔掉外接屏后窗口恢复到不可见区域是经典 bug |
| **托盘** | tray-icon 插件 | 托盘是「关闭主窗口 ≠ 退出应用」语义的家：托盘菜单承载退出/显示主窗/状态指示；macOS 与 Windows 的图标规范不同（模板图 vs 彩色图） |
| **开机自启** | autostart 插件 | 默认关闭、设置页给用户开关；macOS 的登录项与 Windows 注册表 Run 键由插件抹平 |
| **全局快捷键** | global-shortcut 插件 | 注册要处理冲突（被别的应用占用时优雅降级并在设置页标红）；**快捷键必须可配置**，写死的 `Ctrl+Shift+K` 迟早跟用户的心头好撞车 |
| **本地文件访问** | fs 插件 + scope | scope 白名单目录（见 70.3）；大文件读写走流式，不整读进内存 |
| **打印** | WebView 打印 + 原生静默打印 | 打印管线本身（分页、套打、PDF 导出）与 Web 端完全同源，直接复用第 65 册的方案；桌面端独占的是「静默打印」——绕过系统对话框直接出纸，只对可信模板开放 |
| **截图/剪贴板** | 系统 API 封装 | 截图是高危能力（见 70.3 的二次确认）；剪贴板注意类型协商（文本/HTML/图片）与敏感信息残留 |

### 典型应用场景

- 截图贴图工具：全局快捷键唤起 + 托盘常驻 + 多窗口（每个贴图一个窗口）；
- 企业 IM：托盘闪烁提醒 + 开机自启 + 窗口状态记忆；
- 收银/仓储终端：静默打印小票、扫码枪（键盘流）全局监听。

### 核心代码示例

窗口状态恢复的关键逻辑——持久化与可见区域校正（虚拟文件，演示逻辑）：

```ts
// 文件: src/lib/window-state.ts —— 窗口状态持久化与可见区域校正
export interface WindowState {
  x: number;
  y: number;
  width: number;
  height: number;
  maximized: boolean;
}

/** 恢复前校正：状态落盘时的屏幕布局可能已经变了（外接屏被拔掉） */
export function clampToVisibleArea(
  state: WindowState,
  screens: { x: number; y: number; width: number; height: number }[],
): WindowState {
  const visible = screens.some(
    (s) =>
      state.x >= s.x - state.width + 100 && // 至少露出 100px，用户才拖得回来
      state.x <= s.x + s.width - 100 &&
      state.y >= s.y &&
      state.y <= s.y + s.height - 100,
  );
  // 不在任何屏幕可见区域内 → 回退到主屏居中
  return visible ? state : { ...state, x: 100, y: 100 };
}
```

对应的 capabilities 声明（按窗口最小授权）：

```json
// 文件: src-tauri/capabilities/main.json —— 主窗口能力清单（节选）
{
  "windows": ["main"],
  "permissions": ["core:window-default", "fs:allow-appdata-read", "fs:allow-appdata-write"]
}
```

### 最佳实践

1. **窗口状态恢复必做可见性校验**（上面的 `clampToVisibleArea`）：这是桌面端复现率极高的投诉来源——「我昨天接显示器用过，今天笔记本上应用打不开了」。
2. **托盘承载应用生命周期**：「关闭主窗口」的默认行为要在产品层面定义清楚（退出 vs 最小化到托盘），并在首次关闭时给用户选择权；托盘菜单永远保留一个「完全退出」。
3. **全局快捷键三件套**：可配置 + 冲突检测 + 冲突时的降级提示；注册失败不能 crash，更不能静默吞掉。
4. **开机自启默认关**：政企客户的 IT 部门对「擅自开机自启」的软件极度敏感，自启项要进设置页、可审计。
5. **静默打印只对可信模板开放**：第 65 册的套打模板 + 桌面端静默打印是仓储/收银场景的黄金组合，但模板源必须本地校验，不能让任意页面触发「不出对话框直接打印 100 页」。

## 70.6 与 Web 端共用代码与可观测性

### 概念解析

企业级桌面端几乎从来不是孤立产品——它和一个 Web 端共用账号体系、业务逻辑甚至整个前端代码库。工程化要解两件事：

**① 渲染层共享分层**。正确的分层是三层：UI 组件库（纯展示，双端共用）→ 业务逻辑层（hooks/store，双端共用）→ **端适配层**（端相关能力的唯一出口）。铁律：业务代码里不允许出现 `window.__TAURI__` 之类的环境判断——所有端差异收敛到适配层。能力探测与降级的完整方法论接[第 73 册多端架构](./73-multi-end-architecture.md)，本章只给桌面端的适配形态。

**② 可观测性差异**。桌面端的崩溃与埋点和 Web 端有本质不同：

| 维度 | Web 端 | 桌面端 |
| --- | --- | --- |
| 崩溃形态 | 单进程 JS 异常 | 两类：渲染层 JS 异常 + Rust 核心 panic（整个应用闪退） |
| 捕获机制 | `window.onerror` / `unhandledrejection` | 上述 + Rust panic hook（落盘崩溃日志，下次启动时上报） |
| 上报时机 | `sendBeacon` 页面卸载兜底 | 应用退出不保证有网络 → 本地持久队列，下次启动批量补报 |
| 版本维度 | 版本基本无意义（随时最新） | **客户端版本号是所有上报的必填维度**——错误聚类必须按版本切分 |
| 埋点差异 | 会话内实时上报 | 桌面端会话长（挂机几天），要按事件时间窗聚合而非按会话 |

崩溃双通道：渲染层沿用 69 册的埋点 SDK；Rust 侧 panic hook 把崩溃栈写入本地文件，下次启动时检测并上报——这是桌面端独有的「尸体报告」机制，流程是：

1. Rust panic hook 触发 → 把崩溃栈 + 版本号 + 最后 N 条事件写入本地崩溃文件；
2. 下次启动时检测到崩溃文件存在 → 上报 → 上报成功后删除文件；
3. 同版本的崩溃文件按指纹聚合（59.3 的指纹规则同样适用），看板上按「版本 × 崩溃指纹」出闪退率。

这套机制能回答 Web 端不存在的问题：「2.3.0 在 macOS 上的闪退率是 2.4.0 的 5 倍」——没有它，桌面端闪退只能靠用户投诉发现。

### 典型应用场景

- 同一套 React 代码同时发 Web 版与桌面版：文件导出在 Web 端降级为浏览器下载，桌面端走原生保存对话框 + fs 插件；
- 桌面端闪退率统计：Rust panic 日志 + 渲染层错误聚合成同一个 issue 看板；
- 长会话应用（监控大屏客户端）：按小时窗口聚合埋点，避免单会话几万条事件。

### 核心代码示例

端适配层的最小形态——能力探测按 API 存在性、不按 UA（虚拟文件，演示分层）：

```ts
// 文件: src/lib/platform.ts —— 端适配层：业务代码只依赖这个接口
export interface FileSaver {
  saveText: (name: string, content: string) => Promise<void>;
}

/** 探测的是「能力是否存在」，不是「我是谁」——UA/平台字符串判断是脆弱之源 */
export function detectFileSaver(): FileSaver {
  const tauri = (window as unknown as { __TAURI__?: unknown }).__TAURI__;
  if (tauri) {
    // 桌面端：走 Rust 命令（真实实现调 70.2 的 desktop 封装）
    return {
      saveText: async (name, content) => {
        const { desktop } = await import("./desktop");
        await desktop.writeConfig({ key: name, value: content });
      },
    };
  }
  // Web 端降级：Blob 下载
  return {
    saveText: async (name, content) => {
      const url = URL.createObjectURL(new Blob([content], { type: "text/plain" }));
      const a = document.createElement("a");
      a.href = url;
      a.download = name;
      a.click();
      URL.revokeObjectURL(url);
    },
  };
}
```

### 最佳实践

1. **适配层要薄**：只做「能力探测 + 转发」，不掺业务逻辑；端相关的 `if` 只允许出现在适配层。
2. **探测能力不探测平台**：`(window as any).__TAURI__` 存在 → 有桌面能力；UA 里有没有 "Windows" 不该影响任何代码路径。
3. **崩溃双通道缺一不可**：只接渲染层 SDK，Rust panic 闪退永远不在看板上；只接 panic hook，渲染层的白屏型错误（JS 异常但进程活着）看不到。
4. **桌面端埋点用本地持久队列**：事件先落盘（SQLite/文件），联网时批量上报——`sendBeacon` 那套「页面卸载时兜底」在桌面端语义完全不同，别照搬。
5. **版本号是桌面端上报的第一公民**：release 聚合、按版本灰度看错误率——没有版本维度的桌面端监控等于没有。

## 70.7 自测题

<details>
<summary><b>1. 【基础】Tauri 与 Electron 在进程模型和包体积上的核心差异是什么？</b></summary>

**答案**：Electron 自带完整 Chromium 与 Node.js，是「Node 主进程 + 每窗口一个 Chromium 渲染进程」的多进程架构，安装包 ~150MB 起步；Tauri 复用操作系统自带的 WebView（macOS WKWebView / Windows WebView2 / Linux WebKitGTK），系统能力由一个 Rust 核心进程提供，安装包 ~10MB 量级。代价：Tauri 的跨端渲染一致性取决于三个系统 WebView 的差异，Electron 则三端像素级一致。

</details>

<details>
<summary><b>2. 【基础】Tauri 2 的 capabilities（能力清单）解决什么安全问题？</b></summary>

**答案**：解决「WebView 里的前端代码能向系统层要多少权力」的问题。capabilities 按窗口声明允许调用的命令与插件，未声明的调用在 IPC 边界直接被拒——默认拒绝、逐项开通。它对应 Electron 里 contextIsolation + contextBridge 最小暴露的思路，但用配置文件把授权显式化、可按窗口差异化，避免「预加载脚本图省事暴露整个 ipcRenderer」的失效场景。

</details>

<details>
<summary><b>3. 【基础】自动更新为什么必须先验签再应用？验签失败应该怎么做？</b></summary>

**答案**：安装包经过网络下载，可能被中间人篡改或投毒——不验签就应用等于把「在用户机器上执行任意代码」的权力交给网络链路上的每一跳。Tauri updater 用 minisign（ed25519）签名，公钥内置在客户端。验签失败必须丢弃安装包、保留旧版本（回滚），并把失败作为安全信号上报告警——它可能是下载损坏，也可能是真实的攻击。

</details>

<details>
<summary><b>4. 【进阶】为什么函数、Date、Map 不能通过 IPC 边界传递？正确的做法分别是什么？</b></summary>

**答案**：Tauri 的 invoke 走 JSON 序列化边界，JSON 只有 null/布尔/数字/字符串/数组/纯对象六种形态。函数没有序列化语义（跨进程执行的是数据不是代码）；Date 序列化后变成字符串、类型丢失；Map/Set 根本不在 JSON 模型内。正确做法：函数不下发（改为下发数据让对端重新绑定行为）、Date 显式 `toISOString()`、Map/Set 转成数组或普通对象。此外大整数用字符串、空值用 null 而非 undefined（后者会被 JSON 静默丢弃）。

</details>

<details>
<summary><b>5. 【进阶】灰度门控为什么必须用设备 ID 的稳定哈希，而不是每次检查时 Math.random？</b></summary>

**答案**：与 59 册的采样同理：随机数导致同一台设备每次检查结果不同——上午命中灰度升了新版，下午没命中又被清单指回旧版，客户端在两个版本间反复横跳，监控曲线也被打散。稳定哈希（如取设备 ID 哈希的首字节对 100 取模）保证同一台设备的判定结果恒定，灰度比例扩大时只会单向纳入新设备，不会把已升级的设备踢出去。

</details>

<details>
<summary><b>6. 【进阶】注册自定义协议（深链）给桌面应用带来哪些攻击面？如何收敛？</b></summary>

**答案**：注册 `myapp://` 后任何网页都能唤起应用并递参数，这些参数是不可信输入：① 拼进文件路径 → 路径穿越；② 拼进 Shell 命令 → 命令注入；③ 当 URL 直接请求 → 桌面版 SSRF；④ 协议参数触发的动作本身（如「导入并执行配置」）可能被诱导点击武器化。收敛：深链入口第一行做 schema 校验（zod 之类，校验字段类型/长度/字符集）；路径参数 resolve 后做白名单前缀检查；高危动作加用户确认弹窗；绝不把深链参数拼进命令行。

</details>

<details>
<summary><b>7. 【挑战】设计一个政企内网（客户端完全无外网）的桌面应用分发与更新方案。</b></summary>

**答案**：方案要点：① 签名流程不变——在能联网的构建侧完成 minisign 签名与 macOS 公证，私钥离线保管（第 47 册）；② 交付物是「签名安装包 + 静态清单 JSON」的离线介质，由客户管理员审计后放进内网静态服务器（Nginx 目录即可，不写动态服务）；③ 客户端 updater 端点指向内网地址，验签、状态机、灰度逻辑原样复用——只是源换了；④ 清单与包分离：包先审、清单后放，止血 = 管理员把清单指回旧版本；⑤ 差分包按客户主流旧版本预生成，太旧的版本回退全量；⑥ 版本号与崩溃上报走客户内网自己的收集端或定期导出，监控维度不变。关键取舍：内网环境没有「实时灰度」，灰度颗粒度退化为「按部门/批次放清单」。

</details>

<details>
<summary><b>8. 【挑战】同一套 React 代码要同时发 Web 版与 Tauri 桌面版，如何设计能力探测与降级架构，使业务代码零环境判断？</b></summary>

**答案**：三层分层：① UI 组件库与 ② 业务逻辑层（hooks/store）双端完全共用，不允许 import 任何端相关 API；③ 端适配层是唯一的差异出口——定义能力接口（如 `FileSaver`、`Printer`、`Updater`），每个接口提供桌面实现（走 70.2 的 desktop 封装）与 Web 降级实现（Blob 下载、浏览器打印、提示「请访问网页版更新」）。探测按 API 存在性（`window.__TAURI__` 是否存在）而非 UA 字符串。注入方式：应用入口处探测一次，把实现集合放进依赖注入容器（Context 或简单模块单例），业务代码只面向接口编程。评审红线：业务代码里出现 `__TAURI__`、UA 判断、`process.platform` 一律打回——端相关的 `if` 只允许存在于适配层。

</details>

## 70.8 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **按热度选 Tauri，立项后才验证系统 WebView 差异** | WKWebView/WebKitGTK 的 CSS、编解码、剪贴板差异在交付前爆发 | 立项第一周把核心页面在三端 WebView 各跑一遍，差异矩阵进 ADR |
| 2 | **invoke 传大文件/大 JSON** | JSON 序列化卡死 UI 线程（500MB 文件直接白屏） | 大负载走 Channel 分片或落盘传路径，invoke 只传句柄 |
| 3 | **capabilities 图省事全开** | 能力清单形同虚设，前端 XSS 直接升级成系统级 RCE | 默认拒绝、逐项开通，capabilities 改动走安全评审 |
| 4 | **更新签名私钥进代码仓库或 CI 明文变量** | 私钥泄漏 = 任何人都能签发「合法」更新包投毒 | 私钥离线保管，CI 只接触签名后的产物（第 47 册） |
| 5 | **灰度判定用 Math.random** | 同一设备版本反复横跳，监控曲线被打散 | 设备 ID 稳定哈希分桶，灰度扩大只单向纳入 |
| 6 | **窗口状态恢复不校验可见区域** | 用户拔掉外接屏后窗口恢复到不可见区域，「应用打不开了」 | 恢复前校正坐标，不在任何屏幕内则回退主屏居中 |
| 7 | **深链参数不校验直接拼路径/命令** | 路径穿越、命令注入——网页一句 `location.href` 就能打穿客户端 | 深链入口先过 schema 校验，路径 resolve 后白名单前缀检查 |
| 8 | **把 sendBeacon 埋点方案直接搬到桌面端** | 桌面端长会话 + 弱网/离线场景下大量数据丢失 | 本地持久队列 + 联网批量补报，崩溃走 panic hook 落盘 + 下次启动上报 |
