## 74.1 信创环境全景：国产 CPU、OS 与浏览器格局

### 概念解析

「信创」（信息技术应用创新）是把 IT 基础设施从芯片到应用软件换成自主可控体系的工程。对前端来说，要先看清整条栈，才知道工作量落在哪一层：

| 栈层 | 代表产品 | 对前端的真实影响面 |
| --- | --- | --- |
| **CPU** | 鲲鹏（ARM）/ 飞腾（ARM）/ 海光（x86）/ 龙芯（LoongArch）/ 兆芯（x86） | **几乎透明**——浏览器屏蔽了指令集差异；仅在 WASM SIMD、多线程密集型任务上有性能差 |
| **OS** | 银河麒麟 / 统信 UOS / 中科方德 | 字体库存（无微软雅黑）、打印子系统默认值、外设驱动与 SDK 形态（见 74.4） |
| **浏览器** | 奇安信可信 / 红莲花 / 360 信创版 / UOS 自带浏览器 | **影响最大**：Chromium 内核版本陈旧 + 国密 TLS 支持（见 74.3） |
| **办公外设** | 高拍仪 / 身份证读卡器 / UKey / 打印机 | ActiveX 时代结束，走「本地服务 + WebSocket」或浏览器插件（见 74.4） |

**核心认知**：「信创适配」对前端 = 浏览器内核适配 + 字体/外设适配 + 离线交付。CPU 架构是标书里的关键词，不是你的工作量来源——招标书写「支持鲲鹏/飞腾/海光」，翻译成前端语言只是「页面要跑在 ARM 机器上的旧版 Chromium 内核浏览器里」。

**信创浏览器内核为什么旧**：信创浏览器多在固定版本 Chromium 上做国密算法改造与安全加固，每升级一次内核都要重新过一遍安全测评与合规认证，周期长、成本高，于是版本保守。主流 Chrome 已迭代到 126+ 时，交付现场的信创浏览器内核常见 86~110 区间——这意味着 `structuredClone`（94+）、`Array.prototype.findLast`（97+）、CSS 容器查询（105+）、`:has()`（111+）都可能缺席。

常见交付组合与内核量级速查（以厂商公告为准，此处给数量级感觉）：

| 组合 | 典型内核区间 | 前端要点 |
| --- | --- | --- |
| 麒麟 V10 + 奇安信可信 | Chromium 86~110 | 国密 TLS 直连；可选链需按 target 转译 |
| UOS + 红莲花 / UOS 自带浏览器 | Chromium 90~110 | 字体兜底链必须含 Noto/文泉驿 |
| Windows + 360 信创版 | Chromium 86~108 | 信创版与普通 360 是两条产品线，勿混 |
| App 内嵌 WebView（政企 App） | 随 ROM 冻结，40~90 都有 | 用户无法自行升级，准备极简降级页 |

**「多浏览器多终端适配」在政企语境的真实含义**：C 端互联网的多浏览器适配 = Chrome/Safari/Edge 最新三个大版本；政企 = **厂商白名单里的固定版本组合**，验收按「指定环境清单」逐项过。三个结构性差异：

1. **版本冻结**：不能要求客户升级浏览器——升级要厂商出包、客户信息中心审批，以季度计；
2. **环境异构**：麒麟+奇安信、UOS+红莲花、Windows+Chrome、App 内 WebView 在同一张验收单上混部；
3. **无外网**：一切公网资源默认不可达（见 74.4 离线部署）。

对照表把这个差异说透：

| 维度 | C 端多浏览器适配（60 册） | 政企信创适配（本册） |
| --- | --- | --- |
| 目标集合 | 主流浏览器最近 N 版 | 白名单固定版本组合 |
| 升级假设 | 用户自动升级 | 版本冻结，按季度审批 |
| 网络环境 | 公网可达 | 内网离线，外链全死 |
| 适配证据 | 监控分桶 + 灰度 | 验收矩阵逐项签字 |
| 兜底手段 | 优雅降级 | 降级 + 离线包回滚 |

### 典型应用场景

- 运营商移动办公：内网 PC（麒麟+奇安信）跑审批管理端，外网手机 App 内 WebView 跑移动审批（73 册的多端架构在这里落地）；
- 政务大厅柜台系统：高拍仪拍材料 + 读卡器读身份证 + 套打回执单，三件套全在信创终端上；
- 要客/密讯类场景：国密 TLS 通道 + UKey 挑战签名登录（74.2/74.3）。

环境探测的第一课：**UA 只做画像初判，能力结论必须落到特性检测与版本阈值规则库**。示例 74-02 用一个「内核版本 < 阈值 → 命中风险 → 降级策略」的兼容清单，对三个典型环境出报告：

### 最佳实践

- ✅ 立项第一件事是拿到**客户环境清单**（OS 版本 × 浏览器 × 内核版本 × 外设型号），钉进验收矩阵；拿不到书面清单的项目，交付期必然返工；
- ✅ 内核版本以**厂商公告/交付文档**为准，不要拿 UA 猜——信创浏览器 UA 随版本迭代变化，74-02 的 UA 识别只是画像初判；
- ✅ 信创适配工作量估算公式：**内核版本差 × 新特性使用量 + 外设 SDK 数量 + 字体/打印项数**——内核差是最大的乘数项；
- ❌ 不要把 C 端「用户会自动升级」的假设带进政企——版本冻结环境里，「要求客户升级浏览器」等于宣布项目延期。

## 74.2 国密算法前端落地：SM2 / SM3 / SM4 与密钥红线

### 概念解析

国密（商用密码）是国家密码管理局发布的密码算法标准族（GM/T、GB/T）。前端需要建立的对照认知：

| 算法 | 类型 | 对标国际算法 | 前端典型场景 |
| --- | --- | --- | --- |
| **SM2** | 非对称（椭圆曲线） | RSA / ECDSA+ECDH | 登录挑战签名、密钥协商、UKey 身份认证 |
| **SM3** | 杂凑（256 bit） | SHA-256 | 报文完整性校验、口令散列、离线包指纹（74-01 实现） |
| **SM4** | 分组对称（128 bit） | AES | 接口报文加密、本地敏感数据加密 |
| **SM9** | 标识密码 | IBC | 邮箱地址即公钥场景，前端基本不直接碰 |
| **ZUC** | 流密码 | SNOW 3G | 4G/5G 空口加密，与前端无关 |

**关键问题：前端要不要自己实现？** 按场景分层：

- **摘要/完整性（SM3）**：纯 JS/TS 可实现（74-01 就是百行级实现），生产优先用 sm-crypto 等成熟库；
- **报文加解密（SM4）**：小报文用 sm-crypto；大附件、批量数据考虑 WASM 加速——第71册的边界成本方法论（调用开销 + 数据搬运）在这里直接适用；
- **私钥签名（SM2）**：**永远不在前端做**，见下方密钥红线。

**JS 实现 vs WASM 实现的权衡**：

| 维度 | sm-crypto（纯 JS） | WASM（Rust 国密 crate） |
| --- | --- | --- |
| 包体积 | min+gzip 后数十 KB | wasm 二进制通常 200 KB+，按需异步加载 |
| SM4 吞吐 | 小报文（< 10 KB）无感知 | MB 级数据显著占优（SIMD + 无 GC） |
| 工程成本 | npm 直装 | 需要 Rust 工具链与加载状态机（[第71册](./71-rust-wasm.md)） |
| 适用 | 登录挑战、小报文加密、验签 | 大附件加密、批量验签、离线包全量校验 |

政企场景的真实画像是：**90% 的调用是登录挑战与小报文**，纯 JS 足够；只有「大文件加密上传」「批量验签」这类任务才值得为 WASM 付工具链成本。

**密钥管理红线**（衔接 [第47册「前端无秘密」](./47-secrets-management.md#_47-1-密钥分级与「前端无秘密」全景)）：

1. **私钥永不出安全介质**：SM2 私钥在 UKey/密码机内生成、保存、运算，前端只能通过 SKF 中间件/浏览器插件**调用签名动作**，永远拿不到私钥字节；
2. **前端只碰会话密钥**：SM4 会话密钥由 SM2 密钥协商产生，存活于页面内存，关闭即销毁——不落 localStorage，不进日志（47 册结论）；
3. **口令不裸奔**：口令散列必须加盐，且优先在服务端完成；前端 SM3（口令）只是减少明文传输，不构成存储安全。

**库的真实使用形态**（以 sm-crypto 为例，演示 API 手感，非本册可运行示例）：

```ts
// sm-crypto 的典型用法(演示 API 形态;生产务必确认所用版本经密评)
import { sm2, sm3, sm4 } from "sm-crypto";

// SM3:报文完整性指纹
const digest = sm3('{"文号":"政发〔2026〕12号"}');

// SM4:会话密钥加密报文(ECB 模式演示;生产按密码应用方案选 CBC/GCM 并管理 IV)
const sessionKey = "0123456789abcdeffedcba9876543210"; // 来自 SM2 密钥协商,仅存内存
const cipher = sm4.encrypt("密讯正文", sessionKey);
const plain = sm4.decrypt(cipher, sessionKey);

// SM2:验签/公钥加密可在前端做(只碰公钥);签名私钥永远不进前端
// const ok = sm2.doVerifySignature(msg, sig, publicKey);
```

**SM2 密钥协商落地时序**（UKey 登录 + 会话密钥建立）：

1. 页面请求登录 → 服务端生成挑战随机数 R 下发；
2. 前端把 R 交给 SKF 中间件 → UKey 内 SM2 私钥对 R 签名（私钥不出 UKey）→ 返回签名值；
3. 前端上送「证书 + 签名值」→ 服务端验签、校验证书链，建立会话；
4. 会话密钥由双方按 SM2 密钥交换协议各自算出（前端侧由中间件完成），页面内存持有，关闭即销毁。

### 典型应用场景

- 密讯/量子密讯类 IM：消息体 SM4 加密 + SM2 密钥协商 + SM3 完整性校验；
- 公文流转：公文摘要 SM3 存证上链，任何改动指纹即变；
- 统一认证登录：服务端下发挑战随机数 → UKey 内 SM2 签名 → 服务端验签，前端全程只见「签名结果」。

### 可运行代码示例

SM3 的算法结构与 SHA-256 同族：512 位分组、8 个 32 位寄存器、64 轮压缩，但布尔函数、常量与置换不同。示例 74-01 用纯 TypeScript 实现完整算法，并用国标 GB/T 32905-2016 附录向量自校验：

```typescript
// 文件: examples/74-01-sm3-hash.ts（核心节选）
const IV = [0x7380166f, 0x4914b2b9, 0x172442d7, 0xda8a0600, 0xa96f30bc, 0x163138aa, 0xe38dee4d, 0xb0fb0e4e];
// GB/T 32905-2016 附录示例 1:SM3("abc")
assert(sm3Hex("abc") === "66c7f0f462eeedd9d1f2d46bdc10e4e24167c4875cf2f7a2297da02b8f4ba8e0", "国标向量不匹配");
// 场景演示:公文报文金额被篡改一位,摘要指纹天差地别
```

> 运行方式：`npx tsx examples/74-01-sm3-hash.ts`。

### 最佳实践

- ✅ 生产用**经过密码测评的库/厂商 SDK**（sm-crypto 或集成商提供的密评组件）——74-01 是教学级实现，用来理解算法结构与做兜底校验，不用于生产保护真实数据；
- ✅ 国密改造先拿**密码应用方案**（密评/密改文档）：哪条链路要国密、用什么套件、密钥从哪来，方案里都有定义——前端不要自己设计密码协议；
- ✅ 上 WASM 前先按第71册方法论算边界成本：单次调用耗时 vs 数据搬运开销，小报文上 WASM 是负收益；
- ❌ 不要把 SM2 私钥放进前端代码、配置或 localStorage——那等于把公章扫描件群发给每个用户。

## 74.3 国密 TLS 与双证书体系

### 概念解析

国密 TLS（TLCP，GB/T 38636）是把 TLS 握手中的算法套件替换为国密算法的传输层协议（如 `ECC-SM4-SM3` 套件）。它与国际 TLS 最显著的工程差异是**双证书体系**：

| 证书 | 职责 | 关键用法 |
| --- | --- | --- |
| **签名证书** | 身份认证（类似普通 TLS 服务器证书） | KeyUsage = Digital Signature |
| **加密证书** | 握手时加密预主密钥（密钥交换） | KeyUsage = Key Encipherment |

RSA 时代一张证书兼任签名与密钥交换，国密拆成两张——服务器要同时部署并正确下发两张证书及中间 CA 链。

**浏览器支持现状**：

| 浏览器 | 国密 TLS（TLCP） |
| --- | --- |
| 奇安信可信 / 红莲花 / 360 信创版 / 密信浏览器 | ✅ 内置支持 |
| Chrome / Edge / Firefox | ❌ 不支持 |

由此产生两种部署形态：

```mermaid
flowchart LR
    A[普通 Chrome<br/>外网/Windows 终端] -->|标准 TLS| GW[国密网关<br/>协议卸载/转换]
    B[国密浏览器<br/>信创终端] -->|TLCP 双证书| S[业务服务]
    GW -->|国密 TLCP| S
```

① 信创终端装国密浏览器**直连**国密服务；② 前面架**国密网关**做协议转换，普通浏览器走标准 TLS 也能访问。**前端代码两种形态下同一份**——差异全部收敛在网关与运维侧。

**前端要懂什么**：基本不用实现 TLS，但要会排查「只有信创浏览器打不开」类工单：

- **证书链不完整**：双证书 + 中间 CA 少发一张 → 国密浏览器报证书不受信任，而走网关的 Chrome 正常——现象极具迷惑性；
- **协议/套件不匹配**：服务端只开 TLCP，普通浏览器直连 → 握手失败（`ERR_SSL_VERSION_OR_CIPHER_MISMATCH`）；
- **双证书配反**：签名/加密证书用途挂错 → 握手失败；
- **常规项**：证书过期、CN 与域名不匹配——同普通 TLS。

排查命令（运维协作时前端要能看懂输出）：

```bash
# 查看服务端实际下发的证书链(国密端口同理)
openssl s_client -connect oa.example.gov.cn:443 -servername oa.example.gov.cn
# 检查证书用途:签名证书应为 Digital Signature,加密证书应为 Key Encipherment
openssl x509 -in server-sign.crt -noout -text | grep -A1 "Key Usage"
```

**「只有信创浏览器打不开」排查 SOP**（按嫌疑度排序）：

| 顺序 | 检查项 | 判定方法 | 责任方 |
| --- | --- | --- | --- |
| 1 | 走网关还是直连 | 问清访问入口/查看 DNS 与端口 | 运维 |
| 2 | 证书链完整性 | `s_client` 输出数证书张数：双证书 + 中间 CA 应齐全 | 运维/CA |
| 3 | 双证书用途 | `Key Usage` 一张签名一张加密，挂反即握手失败 | 运维/CA |
| 4 | 协议与套件 | 普通 Chrome 直连只开 TLCP 的端口必失败——确认形态设计 | 架构 |
| 5 | 常规项 | 证书过期、CN 与域名不匹配、系统时间错误 | 运维 |
| 6 | 页面层 | 通道通了之后的白屏/报错，才回到 60.5 的前端排查 SOP | 前端 |

前端的边界很清楚：**通道问题（1~5）转运维，页面问题（6）才是前端**。拿 74-02 的环境画像报告随工单一起转，能把「环境不清」的往返沟通省掉一大半。

### 典型应用场景

- 等保三级系统密评（密码应用测评）改造：对外门户经国密网关，对内办公系统信创终端直连；
- 交付现场工单：「Windows 上能开、麒麟上打不开」——按上面四类嫌疑逐项排。

### 最佳实践

- ✅ 排查第一句先问「**这位用户走的是网关还是直连**」——两种形态故障面完全不同，混为一谈会浪费半天；
- ✅ 证书到期监控接入监控告警体系（[第59册](./59-monitoring-observability.md)），**双证书两张都要监控**；
- ✅ 国密改造 = 整站 HTTPS 化，页面里的 http 资源（含 `ws://127.0.0.1` 本地外设服务）会触发混合内容拦截——与 74.4 的外设一节联动处理；
- ❌ 不要在页面 JS 里探测「是否国密 TLS」来切业务逻辑——同一份页面在两种通道下都必须能跑。

## 74.4 信创环境兼容实战：字体、外设、老旧内核与离线部署

### 概念解析

信创现场的高频坑集中在四类，逐一给出工程化解法。

**(1) 字体渲染差异与内嵌字体**

麒麟/UOS 默认没有「微软雅黑」「苹方」，直接写死 `font-family: "Microsoft YaHei"` 会静默掉到系统默认衬线/无衬线，排版全面漂移。解法三层：

- 兜底链写全：`font-family: -apple-system, "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", "WenQuanYi Micro Hei", sans-serif`；
- 表格金额数字不齐：加 `font-variant-numeric: tabular-nums` 强制等宽数字；
- 内嵌字体保证一致性时**注意版权红线**：方正/汉仪字体商用需授权（政企项目是字体公司维权高发区），常用合规选项是思源黑体（OFL 许可），用 fonttools 的 pyftsubset 做子集化——全量中文字体 10 MB+，按项目文案子集化后通常几百 KB，配合 `font-display: swap` 避免不可见闪烁。

内嵌字体与子集化的工程配置（示意）：

```css
/* 子集化后的内嵌字体声明:woff2 单格式即可,信创 Chromium 全部支持 */
@font-face {
  font-family: "SHSC-Subset";
  src: url("./fonts/shsc-subset.woff2") format("woff2");
  font-display: swap; /* 先出兜底字体,加载完成再换,避免白字等待 */
}
body {
  font-family: "SHSC-Subset", "Noto Sans CJK SC", "WenQuanYi Micro Hei", sans-serif;
}
```

**(2) 打印与高拍仪/读卡器等外设**

打印与套打的方法论在 [第65册](./65-print-report.md#_65-3-套打-毫米级定位模板)（mm 级定位、分页确定性）；信创的增量差异是打印机驱动与浏览器默认缩放——套打模板必须支持**现场校准偏移量**。

外设 SDK 的形态已经换代：ActiveX/NPAPI 死了，主流方案是厂商在终端装**本地服务**，页面通过 `ws://127.0.0.1:16888` 这类本地 WebSocket 调用设备。由此产生信创现场第一坑：**HTTPS 页面连 `ws://` 被混合内容（Mixed Content）策略拦截**，高拍仪「点了没反应」。三种解法：

| 解法 | 说明 | 约束 |
| --- | --- | --- |
| 厂商提供 wss + 本地证书 | 本地服务起 `wss://` 并签本地域名证书 | 采购技术要求里必须写明，否则厂商默认只给 ws |
| 内网页面用 HTTP | 纯内网无公网证书时整站 http | 与国密 HTTPS 化方向冲突，需客户安全部门认可 |
| 走厂商浏览器插件 | 奇安信/红莲花支持扩展机制 | 每个浏览器厂商各装一套，维护成本高 |

本地 ws 服务的连接生命周期、重连状态机与 [第50册](./50-bluetooth-hardware.md) 的硬件通信方法论完全同构，直接复用。典型调用时序：

```mermaid
sequenceDiagram
    participant P as 页面
    participant S as 本地服务 ws://127.0.0.1:16888
    participant D as 高拍仪/读卡器
    P->>S: 连接 + 握手(带厂商鉴权 token)
    S-->>P: 握手成功/服务版本号
    P->>S: openDevice / capture 指令
    S->>D: 驱动调用
    D-->>S: 图像数据(分包)
    S-->>P: 组包后的 base64/二进制帧
    Note over P,S: 断连 → 指数退避重连(50 册状态机)<br/>超帧 → 提示「请检查设备服务是否启动」
```

**(3) 输入法冲突**

中文输入法的组合态（拼音中间串）会触发 input 事件：搜索联想/防抖若不判 `e.isComposing`（或监听 `compositionstart`/`compositionend`），用户打「北京」两个字的拼音过程中会发出十几次请求。信创自带输入法（麒麟拼音等）与浏览器的组合事件时序与 Windows 微软拼音有差异——**以事件为准，不做任何时序假设**。

**(4) 老旧内核的 polyfill 与构建目标**

内核版本钉死后，整条构建链从这一个数字推导：

- `.browserslistrc` 写交付环境最低内核（如 `Chrome >= 86`），Vite `build.target` 同步 `chrome86`，CSS 由 autoprefixer 自动补前缀；
- **语法层**（可选链 `?.`、空值合并 `??`）构建期转译即可；**API 层**（`structuredClone`、`Array.prototype.at`）运行期 core-js 按需 polyfill；**CSS 层**（容器查询、`:has()`）只能降级——74-02 的规则库就是这三层的清单化；
- 慎用 `@vitejs/plugin-legacy` 双产物：信创浏览器是「现代但旧版」的 Chromium，不是 IE，SystemJS 遗留产物纯属增加故障面——**单产物 + 精确 target** 是正确姿势。

构建配置落地（示意）：

```bash
# .browserslistrc —— 以验收矩阵的最低内核为准
Chrome >= 86
```

```ts
// vite.config.ts 关键项(示意)
export default {
  build: { target: "chrome86", cssTarget: "chrome86" }, // 语法与 CSS 都钉到同一内核
};
```

```bash
# 字体子集化进 CI:按项目文案提取字符集,思源黑体全量 10MB+ → 子集后数百 KB
pyftsubset SourceHanSansSC-Regular.otf \
  --text-file=project-glyphs.txt --flavor=woff2 --output-file=shsc-subset.woff2
```

**(5) 内网离线部署与升级**

政企内网默认无公网，交付形态是**离线包**：

- **资源本地化**：一切外链全死——CDN 的 Vue/组件库、谷歌字体、高德/天地图公网瓦片、`fetch` 写死的公网接口，上线即「静默坏」（样式崩、脚本报错、地图空白，而且浏览器要等超时才报错，排查体验极差）。地图走内网瓦片服务或离线瓦片包；
- **离线包结构**：zip 产物 + manifest（每文件路径 + 摘要指纹；信创验收若要求国密，指纹算法直接用 74-01 的 SM3）+ 部署脚本 + **回滚包**；
- **构建与依赖**：外网构建机构建产物进内网；如需内网构建，npm 私服（Nexus/Verdaccio）或 node_modules 整体打包（[第66册](./66-dependency-governance.md) 的依赖治理在此叠加）；
- **版本灰度**：政企按「单位/批次」升级，静态资源带内容 hash、index.html 不缓存（与 [第53册](./53-nginx-deploy.md) 缓存策略一致），升级公告 + 现场回滚预案是交付件的一部分。

一次规范的离线包交付流程：

1. 外网构建机产出 dist → 跑 74-03 资源本地化审计（零致命/零高才放行）；
2. 生成 manifest（路径 + 摘要指纹）→ 打包 zip（含部署脚本、回滚说明）；
3. 介质带进内网（U 盘/摆渡系统）→ 部署机先跑完整性校验；
4. 校验通过 → 备份当前版本（= 回滚包）→ 部署新版本 → 冒烟用例过一遍；
5. 试点单位观察一个版本周期 → 按批次推广，监控（59 册）盯错误分桶。

### 典型应用场景

- 政务大厅柜台三件套：高拍仪 + 身份证读卡器 + 套打回执，全部跑在麒麟 + 奇安信终端；
- 运营商内网办公：离线包季度升级，按地市分公司分批灰度；
- 财务报表页：麒麟终端上数字列对不齐——`tabular-nums` 一行解决。

### 可运行代码示例

「资源本地化审计 + 离线包完整性校验」可以做成 CI 里的机械检查。示例 74-03 模拟一份刚从 CI 下来的 dist：审计揪出外链脚本/样式（致命）、外链字体/瓦片/外联接口（高）、外链图片（中）；manifest 校验揪出拷贝丢失、内容篡改、来历不明混入三类问题：

```typescript
// 文件: examples/74-03-offline-deploy-check.ts（核心节选）
const AUDIT_RULES = [
  { re: /<script[^>]+src=["'](https?:\/\/[^"']+)["']/g, severity: "致命", kind: "外链脚本" },
  { re: /(https?:\/\/[^\s"']*(?:tile|is\.autonavi\.com|tianditu\.gov\.cn)[^\s"']*)/g, severity: "高", kind: "外链地图瓦片" },
  // ...

// 受损包拦截:缺失[index-abc.js] 篡改[index-abc.css] 混入[patch-hotfix.js]
```

> 运行方式：`npx tsx examples/74-03-offline-deploy-check.ts`。

### 最佳实践

- ✅ 交付清单写死「**最低内核版本**」并要求厂商书面确认——后续 browserslist、polyfill、验收用例全部从这一个数字推导；
- ✅ 外设采购技术要求里写明「必须支持 wss 或提供本地证书方案」——签约后补不了这一条，混合内容问题就成死结；
- ✅ 离线包升级三步走：完整性校验通过 → 备份当前版本（=回滚包）→ 部署新版本；
- ✅ 字体子集化进 CI：文案变更时自动重新子集化，避免新增字变成「豆腐块」；
- ❌ 不要在内网项目留任何 `cdn.jsdelivr.net` / `fonts.googleapis.com` 引用——把 74-03 的审计规则挂进 CI，让外链在构建期就红。

## 74.5 等保与政企合规的前端清单

### 概念解析

等保 2.0（网络安全等级保护）三级是政企项目的常见门槛。前端不需要背测评条款，但要能把条款翻译成前端控制点：

| 等保要求域 | 前端落地点 | 衔接章节 |
| --- | --- | --- |
| 身份鉴别（双因子） | 口令 + 短信/OTP/UKey 第二因子；连续失败锁定提示 | [36 册](./36-auth-system.md)、74.2 UKey 签名 |
| 会话管理 | 无操作超时自动登出；登出清空内存与本地存储 | [07 册会话体系](./07-security.md) |
| 安全审计 | 操作留痕五要素、字段级 diff、防抵赖编号 | [63 册审计日志](./63-audit-log.md#_63-1-审计五要素与前端职责) |
| 数据保护（展示侧） | 身份证/手机号/银行卡按层级差异化脱敏 | [72.4 列级脱敏](./72-org-hierarchy-permission.md#_72-4-列级与字段级管控-白名单与脱敏) |
| 剩余信息保护 | 退出/关页清理敏感缓存；localStorage 不存业务事实 | [47 册](./47-secrets-management.md)、[56 册](./56-offline-cache.md) |
| 恶意代码防范 | CSP、SRI、依赖治理与漏洞修复 | [7.4 前端安全清单](./07-security.md#_7-4-前端安全清单)、[66 册](./66-dependency-governance.md) |
| 数据防泄漏（威慑） | 明水印：工号+姓名+时间平铺，防拍照外发 | 本节 |

**会话超时**的实现要点（等保常见要求 15 分钟无操作登出）：

```ts
// 会话超时:活动探测 + 到期登出(要点节选)
const IDLE_LIMIT = 15 * 60 * 1000; // 等保常见阈值:15 分钟
let lastActive = Date.now();
for (const ev of ["click", "keydown", "mousemove"]) {
  window.addEventListener(ev, () => (lastActive = Date.now()), { passive: true });
}
setInterval(() => {
  if (Date.now() - lastActive > IDLE_LIMIT) logout("会话超时,请重新登录");
}, 30_000);
// 与后端联动:接口返回 401 同样触发登出——双侧会话必须一致
```

**双因子**的前端要点：第一步口令校验通过后进入「待二次验证」中间态，**此时不下发业务 token**；第二因子（短信/OTP/UKey 挑战签名）通过后才发正式 token。中间态页面刷新要能回到该状态而不是直接登录成功。

**页面水印**的实现要点：canvas 生成平铺底纹（转 dataURL 作 background-image）或绝对定位 DOM 网格；内容 = 工号 + 姓名 + 日期时间；挂 MutationObserver 监听水印节点被控制台删除后立即重建（与 [第59册](./59-monitoring-observability.md) 的 DOM 监听同源思路）；打印场景是否带水印上纸，回到 65 册按单据类型单独决策。实现骨架：

```ts
// 明水印实现骨架(要点节选)
function makeWatermark(user: { id: string; name: string }): string {
  const c = document.createElement("canvas");
  c.width = 220; c.height = 140;
  const ctx = c.getContext("2d")!;
  ctx.rotate(-20 * Math.PI / 180);
  ctx.font = "14px sans-serif";
  ctx.fillStyle = "rgba(0,0,0,0.08)"; // 关键:足够淡不扰阅读,放大可辨认
  ctx.fillText(`${user.name} ${user.id}`, 10, 90);
  ctx.fillText(new Date().toLocaleDateString(), 10, 112); // 含日期防旧截图复用
  return c.toDataURL("image/png");
}
// 挂到满屏 fixed 容器做平铺背景,pointer-events:none 不挡交互;
// MutationObserver 盯住容器,被删立即重建(防控制台去水印)
```

**安全加固检查表**（验收前自查）：CSP 响应头开启；外链资源 SRI 校验；生产环境 sourcemap 不公网可达；console 无敏感数据输出；localStorage 无 token 明文（47 册结论：token 走 httpOnly Cookie 或内存）；调试接口/mock 开关全部关闭。

### 典型应用场景

- 等保三级测评前 3 个月：按本节清单逐项自查打勾，别等测评机构开不符合项再返工；
- 要客系统：页面水印 + 敏感查询页「身份证默认掩码，查看完整值需二次鉴权并记审计日志」（63 册留痕闭环）；
- 长表单场景：超时登出前必须弹确认并暂存草稿——用户填了 20 分钟表单被静默登出，是政企客诉第一名。

### 最佳实践

- ✅ 合规清单**左移**：立项时把本节表格贴进需求基线，而不是测评前补；
- ✅ 水印内容含**实时时间**并定期刷新，防止「一张旧截图无限复用」；
- ✅ 脱敏在服务端做（72.4 的列级管控），前端只做展示兜底——「前端脱敏」不构成数据保护，接口返回明文抓包即泄漏；
- ✅ 超时登出与后端会话过期**双侧联动**：前端到点登出，后端 token 同时失效，任何一侧单独超时都会造成「页面能点、接口全 401」的僵尸态；
- ❌ 不要做「禁用右键/禁用 F12」式加固——挡不住任何真正的攻击者，只挡住正常用户和验收人员的耐心。

<details>
<summary><b>1. 【基础】信创栈 CPU / OS / 浏览器三层中，前端工作量主要集中在哪一层？为什么 CPU 架构（鲲鹏/飞腾/海光）差异对前端基本透明？</b></summary>

**答案**：工作量集中在**浏览器层**——信创浏览器基于固定版本 Chromium 做国密改造，内核陈旧（常见 86~110）导致新语法、新 API、新 CSS 缺席，74.4 的 polyfill 与构建目标都由此推导。CPU 透明的原因：浏览器是屏蔽指令集的沙箱，前端代码跑在 JS 引擎与渲染引擎之上，ARM 与 x86 的差异被完全吸收；只有 WASM SIMD、多线程密集计算等极限场景才有可感知性能差。OS 层居中：字体库存、打印子系统、外设 SDK 形态三类差异需要处理（74.4）。

</details>

<details>
<summary><b>2. 【基础】SM2 / SM3 / SM4 分别对标哪些国际算法？各自在前端的典型用途是什么？</b></summary>

**答案**：SM2 是非对称椭圆曲线算法，对标 RSA / ECDSA+ECDH，前端用于登录挑战签名与密钥协商（私钥在 UKey 内，前端只调签名动作）；SM3 是 256 位杂凑算法，对标 SHA-256，用于报文完整性校验、口令加盐散列、离线包指纹（74-01 实现了它）；SM4 是 128 位分组对称算法，对标 AES，用于接口报文与本地敏感数据加密。速记：SM2 管「身份与换钥匙」，SM3 管「指纹」，SM4 管「锁内容」。

</details>

<details>
<summary><b>3. 【基础】国密 TLS 的双证书是哪两张？各自承担什么职责？</b></summary>

**答案**：**签名证书**与**加密证书**两张。签名证书负责身份认证（KeyUsage = Digital Signature），相当于普通 TLS 服务器证书的角色；加密证书负责握手阶段加密预主密钥完成密钥交换（KeyUsage = Key Encipherment）。RSA 时代一张证书兼任两个职责，国密体系拆成两张——服务器必须同时部署并正确下发两张证书加中间 CA 链，少一张或配反用途都会导致国密浏览器握手失败。

</details>

<details>
<summary><b>4. 【进阶】为什么 SM2 签名私钥绝不下发到前端 JS？政企 UKey 登录场景前端如何完成「签名」动作？</b></summary>

**答案**：两个层面。① 为什么不下发：前端环境不可信——代码、存储、内存都可被用户与恶意脚本读取（47 册「前端无秘密」），私钥一旦落进 JS 就等于把身份凭证群发给所有访问者，整个身份体系崩塌；且密评要求私钥不出安全介质。② UKey 场景怎么签：私钥在 UKey 内生成并保存，签名运算也在 UKey 内完成；前端的角色是「调用签名动作」——通过厂商 SKF 中间件/浏览器插件，把服务端下发的挑战随机数传给 UKey，取回签名结果上送服务端验签。全程前端只见输入与输出，永远接触不到私钥字节。会话密钥同理只存内存、关闭即销毁。

</details>

<details>
<summary><b>5. 【进阶】HTTPS 页面调用本地高拍仪服务 `ws://127.0.0.1:16888` 被浏览器拦截，根因是什么？给出三种可行解法。</b></summary>

**答案**：根因是**混合内容（Mixed Content）策略**：HTTPS 页面发起明文 ws/http 子资源请求会被现代浏览器拦截，本地回环地址虽有一定豁免讨论，但各信创浏览器实现不一致，不能依赖。三种解法：① 厂商本地服务升级为 `wss://` 并签发本地域名证书——最干净，采购技术要求阶段就要写明；② 纯内网场景整站退回 HTTP——与客户安全部门确认，且与国密 HTTPS 化方向冲突，谨慎选用；③ 改用厂商浏览器插件/扩展通道（奇安信、红莲花均提供扩展机制）——绕开页面网络栈，代价是每个浏览器厂商各维护一套。签约后才发现厂商只支持 ws，是政务大厅项目的经典死结。

</details>

<details>
<summary><b>6. 【进阶】政企内网部署为什么必须做「资源本地化审计」？列出四类最容易漏检的隐性外链。</b></summary>

**答案**：内网默认无公网，任何外链资源上线即「静默坏」，且浏览器要等连接超时才报错，现场排查体验极差——所以要在 CI 用规则库机械扫描（74-03）。最易漏检的四类隐性外链：① **CSS 里的字体** `url(https://fonts...woff2)`——藏在样式文件深处，index.html 扫描漏掉；② **JS 里拼的地图瓦片模板**（高德 `is.autonavi.com`、天地图）——运行时逐瓦片请求，页面本身能开、地图区域空白；③ **写死的公网接口** `fetch("https://api...")`——联调环境残留；④ **第三方 SDK 二级加载**（统计/客服 SDK 初始化后再拉外部脚本）——一级域名本地化后二级请求仍出网。审计规则必须覆盖 html/css/js 三类文件与「引用方式 × URL 特征」两个维度。

</details>

<details>
<summary><b>7. 【挑战】为「麒麟+奇安信 / UOS+红莲花 / Windows+Chrome / App 内 WebView」四类环境设计一套信创验收矩阵：覆盖哪些维度、如何分级、怎么自动化？</b></summary>

**答案**：矩阵按「环境 × 能力维度」组织——

| 能力维度 | 验收内容 | 分级标准 |
| --- | --- | --- |
| 内核能力 | 74-02 规则库命中项（语法/API/CSS 三层） | P0：核心流程可用；P1：有降级但体验受损；P2：明确功能隐藏 |
| 国密通道 | TLCP 直连与网关两种形态各跑通核心流程 | 证书链/双证书/协议版本逐项过 |
| 字体外设 | 字体兜底链渲染、高拍仪/读卡器/套打全流程 | 外设走 wss 或插件通道逐项验收 |
| 离线交付 | 资源本地化审计零致命项、manifest 校验通过 | 74-03 进 CI，红即拦 |
| 合规项 | 超时登出、双因子、脱敏、水印 | 按 74.5 清单逐项打勾 |

自动化三层：① 构建期——browserslist 钉最低内核 + 本地化审计 + polyfill 清单生成；② CI——Playwright 按内核版本分桶跑核心流程（09 册），74-02/74-03 作为门槛脚本；③ 现场——74-02 报告贴进验收工单，环境问题先出画像再排查。关键原则：矩阵的每一格都要回答「不满足时业务怎么降级」，而不是只标「支持/不支持」。

</details>

<details>
<summary><b>8. 【挑战】设计政企离线包升级方案：完整性校验、按单位灰度、回滚机制；并解释为什么 index.html 与带 hash 静态资源的缓存策略必须不同。</b></summary>

**答案**：升级方案四件套——

① **离线包结构**：zip 产物 + manifest（路径 + 摘要指纹，信创验收用 SM3 即 74-01）+ 部署脚本 + 回滚包。② **完整性校验**：部署前跑 74-03 的 verifyPackage——缺失（拷贝不完整）、篡改（hash 不匹配）、混入（manifest 之外文件）三类问题先拦截再部署。③ **按单位灰度**：政企按「单位/批次」升级——先一个试点单位跑一个版本周期，监控（59 册）无异常再分批推广；版本号与升级公告随包交付。④ **回滚机制**：部署前备份当前版本目录，回滚 = 指回备份，目标 5 分钟内完成（59.5 的止血标准）。

缓存策略不同的原因：带内容 hash 的资源（`index-abc.js`）文件名随内容变化，可以强缓存一年——内容变则文件名变，天然防脏缓存；index.html 是资源引用入口，必须每次回源校验（`no-cache`），否则用户拿到旧 HTML 引用已被替换掉的旧 chunk，直接白屏（59.5 的 chunk 404 事故在内网离线包场景同样成立，且内网没有 CDN 缓冲，故障面更集中）。

</details>

## 74.7 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **拿 C 端 evergreen 假设做信创设计** | 客户浏览器版本冻结，「要求升级」= 项目延期 | 立项即拿客户环境清单，验收矩阵按厂商公告内核版本钉死 |
| 2 | **自实现国密算法上生产** | 未经密评验收不过，且自实现易有安全缺陷 | 生产用密评过的库/厂商 SDK；74-01 仅作教学与兜底校验 |
| 3 | **SM2 私钥下发前端 JS/localStorage** | 私钥泄漏 = 身份体系崩塌 | 私钥永不出 UKey/密码机，前端只调签名动作、只见签名结果 |
| 4 | **内嵌方正/汉仪字体没买授权** | 字体公司律师函（政企项目高发） | 思源黑体（OFL）子集化，或走正式采购授权 |
| 5 | **HTTPS 页面连 `ws://127.0.0.1` 外设** | 混合内容拦截，高拍仪「点了没反应」 | 采购技术要求写明 wss+本地证书；或厂商插件通道 |
| 6 | **防抖不判 `isComposing`** | 中文输入法拼音中间态触发请求风暴 | 监听 `compositionstart`/`compositionend`，以事件为准不做时序假设 |
| 7 | **内网残留 CDN/谷歌字体/公网瓦片外链** | 上线即样式崩/地图空白，且超时才报错难排查 | 74-03 资源本地化审计进 CI，外链构建期就红 |
| 8 | **离线包不做完整性校验** | 拷贝不全/版本混入，现场白屏责任不清 | manifest 摘要校验（SM3/sha256）+ 备份即回滚包 |
| 9 | **把前端脱敏当数据保护** | 接口返回明文，抓包即泄漏 | 服务端做列级脱敏（72.4），前端只是展示兜底 |
| 10 | **超时登出直接跳转丢表单** | 用户 20 分钟表单全丢，客诉第一名 | 登出前弹确认 + 草稿暂存（内存/加密），双侧会话联动失效 |
