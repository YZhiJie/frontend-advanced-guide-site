## 87.1 什么是设计系统：不止是组件库

### 概念解析

设计系统是一个**完整的产品设计语言体系**，包含四层：

| 层级 | 内容 | 例子 |
| --- | --- | --- |
| **设计令牌（Tokens）** | 颜色、间距、圆角、字体、阴影的最小单元 | `--primary: #2563eb` |
| **组件（Components）** | 基于令牌构建的可复用 UI 单元 | Button、Input、Table |
| **模式（Patterns）** | 组件组合成的常见交互模式 | 表单校验、空状态、加载态 |
| **文档（Docs）** | 使用指南、设计原则、贡献流程 | Storybook + 使用文档 |

很多团队以为"做了组件库 = 有了设计系统"，其实只做了第二层。没有令牌层，组件的颜色间距是硬编码的，换肤要改每个组件；没有文档，组件没人会用；没有治理，组件库半年就失控。

### 应用实践

- **设计系统要从令牌开始**：先定令牌，再做组件。顺序反了会导致组件里散落硬编码的色值；
- **设计和开发共享同一份令牌**：Figma 里的变量和代码里的 CSS Variables 是同一份，设计改一个值，代码自动同步；
- **设计系统是产品，不是项目**：要有负责人、有版本、有迭代计划，不是"做完就放着"。

## 87.2 设计令牌的三层架构

### 概念解析

设计令牌分三层，每层职责不同：

```
原始令牌（Primitive）    语义令牌（Semantic）     组件令牌（Component）
┌─────────────────┐    ┌─────────────────┐     ┌─────────────────┐
│ blue600: #2563eb │───▶│ primary: blue600 │────▶│ button.bg: primary │
│ gray50: #f9fafb  │───▶│ background: gray50 │──▶│ card.bg: background │
│ radius-md: 6px   │───▶│ radius.button: md │──▶│ button.radius: ...  │
└─────────────────┘    └─────────────────┘     └─────────────────┘
```

- **原始令牌**：不可再分的基础值（`blue600: #2563eb`），无语义，是"原子"；
- **语义令牌**：给原始令牌赋予业务含义（`primary: blue600`），组件引用这层。**换肤只改这层**；
- **组件令牌**：语义令牌在特定组件上的应用（`button.background: primary`），允许同一语义在不同组件上取不同值。

三层的价值：**改一个原始值，所有引用它的语义和组件令牌自动更新；换肤只改语义层，组件代码不动**。

### 完整代码示例

```ts
// 文件: examples/87-01-design-system-tokens.ts（节选：三层令牌）
export const primitiveTokens = {
  color: { blue600: "#2563eb", gray50: "#f9fafb", gray900: "#111827" },
  radius: { md: "6px", lg: "12px", full: "9999px" },
};

export const semanticTokens = {
  color: {
    primary: primitiveTokens.color.blue600,
    background: primitiveTokens.color.gray50,
  },
  radius: {
    button: primitiveTokens.radius.md,
    card: primitiveTokens.radius.lg,
  },
};

export const componentTokens = {
  button: { background: semanticTokens.color.primary, borderRadius: semanticTokens.radius.button },
  card: { background: "#ffffff", borderRadius: semanticTokens.radius.card },
};
```

> 运行方式：`npx tsx examples/87-01-design-system-tokens.ts`

### 应用实践

- **命名用小写 + 点分隔**：`color.primary.hover`，不用大写、不用连字符。和 CSS Variables（`--color-primary-hover`）转换方便；
- **间距令牌用 4px 基准**：`0, 4, 8, 12, 16, 24, 32, 48`，不要出现 13px、17px 这种非基准值。间距一致性是设计系统最直观的体现；
- **颜色令牌不要直接给组件用**：组件里写 `bg-primary`，不要写 `bg-blue-600`。否则换品牌色时要全局搜替换。

## 87.3 组件设计原则

### 概念解析

设计系统的组件要遵循四个原则：

1. **一致性（Consistency）**：相同的交互模式在所有页面表现一致。比如所有按钮的 hover 效果、所有弹窗的关闭方式；
2. **可组合（Composable）**：组件是原子，通过组合构建复杂界面，而不是通过继承。Button + Icon 组合，不是 IconButton 继承 Button；
3. **可访问（Accessible）**：键盘可达、焦点可见、ARIA 属性完整。见 [15 册可访问性](./15-accessibility-i18n.md)；
4. **可定制（Customizable）**：通过 props 和 className 覆盖，而不是 fork 组件。shadcn/ui 的拷贝源码模式是极端的可定制（见 [84 册](./84-shadcn-radix-ui.md)）。

### 应用实践

- **组件 API 要稳定**：一旦发布，不要轻易改 prop 名或删除 prop。改了要走 deprecation 流程（先标 deprecated，下个大版本再删）；
- **默认值要合理**：组件的默认 props 应该是最常用的场景。比如 Button 的默认 variant 是 `default`，不是 `destructive`；
- **不要做"上帝组件"**：一个组件不要试图覆盖所有场景。如果发现 prop 超过 10 个，考虑拆成多个组件或用组合模式。

## 87.4 设计系统的治理与演进

### 概念解析

设计系统最大的失败模式是**失控**——组件越来越多、prop 越来越乱、没人维护。治理是关键：

- **版本化**：设计系统用语义化版本（SemVer）。改 bug 是 patch，加功能是 minor，破坏性变更是 major；
- **废弃流程**：废弃的组件/prop 先标 `@deprecated`，文档说明替代方案，保留至少一个大版本再删除；
- **贡献流程**：新组件要经过设计评审 + 代码评审 + 无障碍检查才能入库。不能谁想加就加；
- **使用度量**：统计每个组件的使用频率。长期没人用的组件考虑移除，避免维护负担。

### 应用实践

- **用 Storybook 做文档**：每个组件有独立的 story，展示所有状态（默认、hover、disabled、错误），配上使用说明；
- **设计令牌变更要评审**：令牌是全局影响的，改一个颜色可能影响几十个组件。变更令牌要走变更评审，不能随手改；
- **定期清理**：每季度 review 一次组件库，移除长期不用的、合并功能重复的。设计系统要"减脂"，否则会越来越臃肿。

## 87.5 自测题

<details>
<summary><b>1. 【基础】设计令牌为什么要分三层？组件直接用原始令牌不行吗？</b></summary>

分三层是为了换肤和维护。如果组件直接用 `blue600`，换品牌色时要全局搜索替换所有 `blue600`。有了语义层，组件用 `primary`，换肤只改语义层的 `primary: blue600 → primary: green600`，组件代码不动。组件层则允许同一语义在不同组件上取不同值（如按钮圆角和卡片圆角不同）。
</details>

<details>
<summary><b>2. 【进阶】为什么间距要用 4px 基准，不能出现 13px、17px？</b></summary>

间距一致性是设计系统最直观的体现。如果页面上出现各种不规则的间距值，视觉上会显得"不整齐"。4px 基准（0/4/8/12/16/24/32/48）让间距有节奏感，也方便开发者选择——选间距时从基准序列里挑，不用纠结"用 13 还是 14"。
</details>

<details>
<summary><b>3. 【进阶】设计系统为什么需要版本化和废弃流程？</b></summary>

设计系统是被多个业务方依赖的产品。如果随意改 prop 名或删组件，会导致所有使用方代码崩溃。语义化版本让使用方知道升级风险：patch 安全、minor 有新功能、major 有破坏性变更。废弃流程（先标 deprecated 再删除）给使用方缓冲时间去迁移。
</details>

<details>
<summary><b>4. 【挑战】设计系统最常见的失败模式是什么？怎么避免？</b></summary>

失控——组件越来越多、prop 越来越乱、没人维护、没人用。避免方法：① 贡献流程——新组件要经过设计+代码+无障碍评审；② 使用度量——统计组件使用频率，移除长期不用的；③ 定期清理——每季度 review，合并重复、移除过时；④ 有负责人——设计系统是产品不是项目，要有 owner 和迭代计划。
</details>

## 87.6 本章避坑清单

| 场景 | 高频坑 | 一句话避法 |
| --- | --- | --- |
| 组件直接用原始色值 | 组件里写 `bg-blue-600`，换肤要全局改 | 组件用语义令牌 `bg-primary`，换肤只改语义层 |
| 间距无基准 | 页面出现 13px、17px 等不规则间距 | 用 4px 基准序列（0/4/8/12/16/24/32/48） |
| 命名不规范 | `PrimaryColor`、`color-primary` 混用 | 统一小写 + 点分隔：`color.primary` |
| 上帝组件 | 一个组件 15 个 prop，试图覆盖所有场景 | 拆成多个组件或用组合模式，prop 控制在 10 个以内 |
| 无废弃流程 | 直接删组件/改 prop，使用方代码崩溃 | 先标 `@deprecated` + 替代方案，保留一个大版本再删 |
| 无使用度量 | 组件库越来越臃肿，没人用的也留着 | 统计组件使用频率，长期不用的移除 |
| 令牌变更无评审 | 随手改一个颜色，影响几十个组件 | 令牌变更走变更评审，评估全局影响 |
| 只有组件没有文档 | 组件库做了但没人会用 | 用 Storybook 给每个组件配 story 和使用说明 |

## 87.7 面试问答

<details>
<summary><b>【L2】设计令牌为什么要分原始/语义/组件三层？直接用一层不行吗？</b></summary>

**回答框架**：① 原始层是原子值（blue600: #2563eb），无语义；② 语义层赋予业务含义（primary: blue600），组件引用这层；③ 组件层允许同一语义在不同组件取不同值（按钮圆角 md、卡片圆角 lg）。一层的话换肤要改每个组件的色值，三层的话换肤只改语义层，组件代码不动。

**评分要点**：知道三层职责；知道换肤只改语义层；知道组件层允许差异化。

**加分项**：提到 undefined/null 语义；提到命名规范（小写+点分隔）。
</details>

<details>
<summary><b>【L2】间距为什么要用 4px 基准？设计系统怎么保证一致性？</b></summary>

**回答框架**：① 4px 基准序列（0/4/8/12/16/24/32/48）让间距有节奏感，不会出现 13px、17px 这种不规则值；② 一致性靠令牌约束——所有间距从令牌取，开发者不用自己选；③ 组件库的 padding/margin/gap 全部引用 spacing 令牌。

**评分要点**：知道 4px 基准；知道用令牌约束保证一致性。

**加分项**：提到 8px 网格也是常见基准；提到圆角、字体大小也要有基准序列。
</details>

<details>
<summary><b>【L3】设计系统做了半年没人用、组件越来越乱，你怎么治理？</b></summary>

**回答框架**：① 诊断：没人用是因为没文档/不好用/找不到；乱是因为没贡献流程。② 治理四件套：版本化（SemVer）、废弃流程（先 deprecated 再删）、贡献流程（设计+代码+无障碍评审）、使用度量（统计使用频率，移除长期不用的）。③ 定期清理：每季度 review，合并重复、移除过时。④ 有 owner：设计系统是产品不是项目，要有负责人和迭代计划。

**评分要点**：知道诊断问题；知道治理四件套；知道定期清理和 owner。

**加分项**：提到用 Storybook 做文档；提到设计令牌变更要评审；提到用 metrics 看组件健康度。
</details>

## 87.8 代码审查清单

| 审查项 | 关注点 | 常见问题 | 建议 |
| --- | --- | --- | --- |
| 令牌分层 | 是否分原始/语义/组件三层 | 组件直接用原始色值 | 三层分离，换肤只改语义层 |

| 令牌变更 | 是否走评审 | 随手改颜色影响全局 | 令牌变更走变更评审 |
| 使用度量 | 是否统计使用频率 | 没人用的组件也留着 | 统计频率，长期不用的移除 |
