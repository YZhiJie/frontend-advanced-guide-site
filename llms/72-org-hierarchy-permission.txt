## 72.1 企业组织模型：部门树、岗位、编制与一人多岗

### 概念解析

政企/运营商系统的组织模型远比互联网公司的扁平团队复杂，先把五个实体分清：

| 实体 | 含义 | 权威来源 | 前端要点 |
| --- | --- | --- | --- |
| **部门树** | 行政主线：集团 → 事业部 → 部门 → 小组 | HR/主数据平台 | 只读消费，不自建 |
| **岗位** | 职责模板：客户经理、解决方案经理、交付经理 | HR | 权限挂在岗位上，不挂人 |
| **编制** | 岗位的核定人数（headcount），管「这个岗能有几个人」 | HR | 报表口径，权限不感知 |
| **虚拟团队** | 跨部门项目制组织（专项组、攻坚队），不占行政编制 | 业务系统 | 建模为**独立节点类型**，挂靠在某个部门下但独立授权 |
| **一人多岗** | 主岗 + 兼岗：区域经理兼某部门主管 | HR | 可见范围取各岗位**并集** |

**「分层分级」在政企/运营商语境里是两个正交维度**：

1. **组织分层**——集团/省公司/市公司/班组（或集团/事业部/部门），决定**数据可见范围**：市公司经理看本市，省公司看全省。
2. **业务分级**——要客分层（战略要客/重点要客/普通客户/长尾客户）与能力分级开放（运营商把实名核验、位置服务、消息触达等能力按渠道伙伴等级开放 API 与配额），决定**在同一可见范围内还能看多深、用什么能力**。

很多事故来自把两个维度揉成一个：用「组织层级」表达「客户等级」，部门一调整，要客的服务口径全乱。正确姿势是组织树上推范围（本章 72.2），业务分级上做条件（72.3 的 level/tag 谓词），两者在查询时组合。

要客分层落到前端是一张**服务等级矩阵**——层级不只是列表里的一个筛选项，它驱动入口、动作与审批链：

| 要客层级 | 数据可见性 | 专属能力 | 折扣审批链 |
| --- | --- | --- | --- |
| L1 战略要客 | 全集团可见，多部门联合服务 | 专属方案库、高层直通车入口 | 集团级审批 |
| L2 重点要客 | 事业部内共享 | 标准方案库、优先工单 | 事业部审批 |
| L3 普通客户 | 归属部门可见 | 标准产品目录 | 部门审批 |
| L4 长尾客户 | 仅归属人可见 | 自助服务入口 | 免审批（额度内） |

**组织树与权限树必须分离**。组织树是主数据，回答「谁归谁管」；权限树是授权视图，回答「这个角色能碰什么资源」。两者用「挂靠」连接（角色挂在组织节点上、节点挂在权限点上），而不是把权限码直接写进部门节点——否则一次部门合并就是一场权限迁移灾难。

虚拟团队是分离设计价值的最佳试金石。它和正式部门的差异必须建进模型，而不是靠前端特判：

| 维度 | 正式部门 | 虚拟团队 |
| --- | --- | --- |
| 来源 | HR 主数据 | 业务系统自建 |
| 成员关系 | 人事归属（唯一） | 项目归属（可多个，与主岗并存） |
| 数据范围 | 按行政线推导 | 独立授权，常配 `custom` 范围 |
| 生命周期 | 长期 | 有起止日期，到期自动解散并回收授权 |
| 报表口径 | 计入编制 | 不计编制，只计投入人天 |

### 典型应用场景

- 政企 CRM：要客按 L1-L4 分层，L1 战略要客全集团可见，L4 长尾客户只归属地可见；
- 运营商能力开放平台：渠道伙伴分金银铜三级，金级开放实名核验 API，铜级只开放基础查询；
- 一人多岗：HRBP 既归华东区行政线，又在「校招项目组」虚拟团队里，可见范围是两岗并集；
- 编制报表：HR 看编制数，业务看人头数，两个口径来自同一组织树的不同切片。

### 可运行代码示例

组织树用**物化路径**（每个节点存 `/d1/d11/d111/` 这样的全路径）建模，四种数据范围的推导、一人多岗并集见示例 72-01 的完整实现：

```ts
// 文件: examples/72-01-org-tree-scope.ts —— 节选
/** 一人多岗：可见集合 = 各岗位范围并集 */
function visibleDeptIds(map: Map<string, DeptNode>, emp: Employee): Set<string> {
  const out = new Set<string>();
  for (const pos of emp.positions) {
    for (const id of scopeOf(map, pos)) out.add(id);
  }
  return out;
}
```

> 运行方式：`npx tsx examples/72-01-org-tree-scope.ts`

输出四个角色的可见部门清单：王董事长（all）9 个部门全见；李总经理（dept_and_children）见事业部及下属两部；张经理（dept）只见大客户一部；陈 HRBP（dept + custom 两岗并集）见华东区、华南区、财务部三个不相邻的节点——**并集语义让跨条线兼岗天然成立**。

### 最佳实践

- ✅ 组织主数据单源：部门树、岗位、编制一律由 HR/主数据平台下发，前端不维护副本，更不允许业务库自己建一套「小组织树」；
- ✅ 虚拟团队建模为节点类型（`nodeType: "virtual"`），可以挂靠、可以独立授权、可以解散留痕；不要用「打标签」模拟，标签没有层级推导能力；
- ✅ 一人多岗取**并集**（与 35 册多角色取最大范围同一思想），取交集会让兼岗形同虚设；
- ❌ 不要把岗位层级（经理/总监）当数据范围依据——层级是汇报线，范围必须显式配置；
- ✅ 组织架构要**版本化**（按生效日期切片）：年底调整架构后，全年报表仍要按当时口径出数；
- ✅ 要客分层与能力分级的「级」都是枚举配置而非硬编码常量——层级定义会随经营口径调整，前端从配置读取。

## 72.2 层级可见范围推导：本级、下级与指定范围

### 概念解析

35 册定义了五种数据范围类型（`all` / `dept_and_children` / `dept` / `custom` / `self`），本章聚焦其中四种的组织树推导（`self` 退化为 owner 条件，见 72.3）：

| 范围 | 语义 | 推导方式 | 典型角色 |
| --- | --- | --- | --- |
| `dept`（本级） | 只看本部门直属数据 | 节点自身 | 部门经理 |
| `dept_and_children`（本级及下级） | 整棵子树 | 子孙集 | 事业部总经理 |
| `custom`（指定范围） | 显式列举的部门集合，可互不相邻 | 集合枚举 | 审计、HRBP、虚拟团队 |
| `all`（全部） | 全组织 | 恒真 | 集团领导、超管 |

推导的两个基本运算是**祖先链**与**子孙集**，三种存储模型的取舍直接决定前端怎么玩：

| 模型 | 子孙集查询 | 节点移动成本 | 存储 | 前端适用性 |
| --- | --- | --- | --- | --- |
| 邻接表（只存 parentId） | 递归/CTE，O(子树) 多次查询 | O(1) 改一行 | 最小 | 小树一两次递归还行，大树憋死 |
| **物化路径**（存全路径） | `path LIKE '/d1/d11/%'` 一次索引扫描 | 重写整棵子树的 path | 每节点 O(深度) | **前端最友好**：前缀匹配同步可算，无需请求 |
| 闭包表（存所有祖先-后代对） | 一次 JOIN | 删旧对插新对，行数爆炸 | 最大（O(N·深度)） | 后端强一致场景的标配，前端消费其产物 |

经验结论：**后端闭包表保强一致，前端物化路径做本地推导**。后端下发时带上每个节点的 path，前端拿到后祖先链（路径切分）与子孙集（前缀过滤）都是零请求的同步计算——人员选择器、部门级报表预过滤、面包屑渲染全用它。

组织树的前端缓存策略：**大树绝不整树加载**。十万节点的集团组织，首屏只拿根 + 用户祖先链（保证面包屑和默认展开），其余按展开懒加载；以 `path` 为索引做本地检索。增量更新只有三类事件——新增、移动、撤销，其中**移动最贵**：物化路径模型下要重写整个子树的 path，下发增量时必须把「受影响子树根」带全，让前端整子树替换，而不是只发改动的那个节点。

三类增量事件的前端处理口径：

| 事件 | 载荷 | 前端处理 | 坑 |
| --- | --- | --- | --- |
| 新增节点 | 节点全量字段（含 path） | 直插索引，父节点 children 懒加载标记置脏 | 无 |
| **移动子树** | 子树根的新旧 path + 子树全部节点新 path | 整棵子树替换，连带刷新所有引用该子树的可见集合缓存 | 只发改动节点 → 后代 path 集体过期，子孙推导全错 |
| 撤销节点 | 节点 id + 生效日期 | 标记 `archived`，不物理删除；历史数据按映射表归父 | 直接删节点 → 历史行指向悬空 id，报表断链 |

组织架构调整（合并/拆分/划转）是范围推导的暗礁：节点撤销后历史数据上的 `deptId` 指向了不存在的节点。处理口径是「数据冻结 + 范围映射」——撤销节点的历史数据归属权移交父节点，查询时按撤销映射表改写条件。

### 典型应用场景

- 人员/部门选择器：懒加载 + 本地搜索，祖先链用于回显已选节点的完整路径；
- 部门级经营报表：经理打开报表默认带 `dept_and_children` 范围，前端用物化路径先预过滤可见行，减少无效请求；
- 架构调整窗口期：年末组织架构改版，新旧两套树并行一个月，查询按数据归属日期路由到对应版本；
- 跨组织协作审批：流程节点按「角色 + 祖先链」定位审批人（找某部门的直属上级），物化路径让这变成纯字符串操作。

### 可运行代码示例

物化路径的构建、子孙集前缀匹配、祖先链切分，完整实现与断言在 72-01：

```ts
// 文件: examples/72-01-org-tree-scope.ts —— 节选
/** 子孙集：物化路径前缀匹配，O(N) 全表扫；大树可换成闭包表或预计算索引 */
function descendants(map: Map<string, DeptNode>, deptId: string): string[] {
  const prefix = map.get(deptId)!.path;
  return [...map.values()].filter((n) => n.path.startsWith(prefix)).map((n) => n.id);
}
```

> 运行方式：`npx tsx examples/72-01-org-tree-scope.ts`

### 最佳实践

- ✅ 下发格式一次到位：`{ id, parentId, path, nodeType, version }`，path 由后端算好，前端只消费不拼接；
- ✅ 可见范围推导结果（部门 ID 集合）在会话内缓存为 `Set`，查询拼装、预过滤共用一份；
- ❌ 不要在前端用递归遍历取子孙——十万节点递归不仅慢，栈还可能炸；path 前缀匹配是平扫；
- ❌ 增量事件不要只发「变更节点」——移动事件必须携带子树根，否则前端子树 path 集体过期；
- ✅ 部门撤销走「冻结 + 映射」，不要物理删除节点——历史数据、审计、报表都要回指它。

## 72.3 行级数据权限：数据范围 DSL 与查询注入

### 概念解析

行级权限回答「这张表里你能看到哪几行」。范围类型只解决了部门维度，真实业务条件是多维组合：部门 + 要客层级 + 客群标签 + 归属人。硬编码每个场景的组合条件不可维护，需要一份**可序列化、可审计、前后端同构的数据范围 DSL**。

设计三原则（继承 37 册策略 DSL 的纪律）：

1. **封闭操作符集**：只有 `and/or/not/dept_in/level_gte/level_lte/tag_has/owner_eq`，未知操作符一律编译期拒绝——绝不支持任意表达式或 eval；
2. **可 JSON 序列化**：规则是数据不是代码，可以落库、下发、审计、版本化；
3. **变量位只有一个** `$self`：形如 `{ op: "owner_eq", value: "$self" }`，求值时绑定当前用户。变量越少，注入面越小。

四个条件维度对应本章的两条主线：`dept_in` 承接组织分层（72.2 推导出的可见集合是它的**合法值域**），`level/tag` 承接业务分级（要客分层、客群标签），`owner_eq` 兜底个人维度（35 册的 `self` 范围）。

**编译期越权校验**是本册 DSL 区别于通用 ABAC 的关键一环：规则里 `dept_in` 声明的部门必须 ⊆ 用户可见部门集合，否则这条规则本身就在放大权限——比如张经理把自己的查询规则写成 `{ op: "dept_in", value: ["d112"] }`（隔壁部门），必须在编译期打回，而不是等数据出来再比对。

**查询条件注入的位置**有三档：

| 注入点 | 做法 | 适用 |
| --- | --- | --- |
| BFF/网关 | DSL 编译为 SQL where 片段拼入查询 | 大多数业务系统 |
| ORM 拦截器 | 查询构造器统一追加条件，业务代码无感 | 大型单体内多模块 |
| 数据库行级安全（PG RLS 等） | 策略下沉到库 | 多应用共库、强合规 |

行级权限最容易失守的不是列表，而是**其他数据出口**。每个出口都要过同一份判定，形成口径矩阵：

| 数据出口 | 判定要求 | 经典翻车 |
| --- | --- | --- |
| 列表 | 查询注入 DSL 条件 | 最基本，一般不会漏 |
| 详情 | 单行重跑判定（该行 ∈ 可见集合） | 只鉴登录态 → 遍历 ID 拖表（IDOR） |
| 编辑/删除 | 同详情，且校验写操作落在范围内 | 能看不能改变成能看也能改 |
| 导出 | 独立链路重跑 DSL + 列级二次校验（72.4） | 复用列表接口但绕过范围拼装 |
| 搜索/聚合 | 命中结果与统计口径都过范围 | 列表没数据，聚合接口泄总数 |
| 分享/转交 | 接收方独立判定，不继承分享者范围 | 「我可见」被误当「他可见」 |

### 典型应用场景

- 要客列表：`(dept_in 可见集合) AND (level_gte 2) OR (owner_eq $self)`——重点以上要客按组织范围，长尾客户只管自己名下的；
- 政企合同查询：本部门合同全见，跨部门只见「参与人含我」的（owner 条件的变体）；
- 能力资源清单：金级伙伴可见的能力资源行 = 资源等级 ≤ 金级的子集；
- 审批待办：审批人可见的单据 = 待审单据 ∩ 数据范围，防止「审批流把人拉进来看到了不该看的全单」。

### 可运行代码示例

DSL 解析、编译期越权校验、条件组合求值、对模拟要客数据集过滤，完整实现见示例 72-02：

```ts
// 文件: examples/72-02-data-scope-dsl.ts —— 节选
case "dept_in": {
  // 越权组合拦截：声明的部门必须 ⊆ 用户可见集合，否则这条规则本身就在放大权限
  const illegal = rule.value.filter((d) => !ctx.visibleDepts.has(d));
  if (illegal.length > 0) {
    throw new Error(`越权组合被拒绝: dept_in 引用了可见范围外的部门 ${illegal.join(",")}`);
  }
  const allow = new Set(rule.value);
  return (row) => allow.has(row.deptId);
}
```

> 运行方式：`npx tsx examples/72-02-data-scope-dsl.ts`

输出里张经理的规则（`d111` 部门 + 重点以上要客）过滤出 c1、c3；而当他把 `dept_in` 偷换成 `d112` 时，编译期直接抛出「越权组合被拒绝」。

### 最佳实践

- ✅ **前后端分工红线**：前端跑 DSL 只做体验裁剪（列表预过滤、空态提示、导出按钮置灰），**安全边界永远在后端**——后端用同一份 DSL（或由其编译的 SQL）独立判定，绝不信任前端传来的过滤条件；
- ✅ **列表/详情/导出三场景口径一致**：列表过了 DSL 不代表详情安全——详情接口必须对单行重跑判定（否则遍历 ID 就是经典 IDOR）；导出走独立链路再过一遍（见 72.4）；
- ❌ 不要让前端提交 `deptIds` 数组给后端做过滤参数——那是把权限决策权交给了调用方，后端必须自己从身份推导；
- ✅ DSL 变更进版本号（见 72.5），前端预览结果与后端实际结果不一致时上报埋点，说明版本漂移；
- ❌ 不要在 DSL 里塞业务计算（金额汇总、折扣试算）——它是过滤谓词，不是脚本引擎。

## 72.4 列级与字段级管控：白名单与脱敏

### 概念解析

37.5 已经把字段级管控的两个独立问题讲透了：**能力问题**（能看哪些字段，白名单判定）与**形态问题**（看到的字段长什么样，脱敏器）。本章不重复其 sanitize 出口收口的论述，补两个组织语境下的增量：

**增量一：层级维度的差异化形态**。同一张表同一个字段，不同组织层级看到的形态不同——这是「分层分级」在列上的投影：

| 角色 | 手机号 | 年成交金额 | 银行卡 |
| --- | --- | --- | --- |
| 销售（本级） | 脱敏 `138****5678` | 不可见 | 不可见 |
| 销售主管（本级及下级） | 脱敏 | 区间化「10 万以上」 | 不可见 |
| 财务（指定范围） | 不可见 | 精确值（结算需要） | 只留后 4 位 |
| 客服 | 脱敏 + 姓名打码 | 不可见 | 不可见 |

落地为**字段策略矩阵**：`角色 × 字段 → { 不可见 / 明文 / 脱敏器名 }`，随策略下发，出口统一执行。

**增量二：导出链路的二次校验**。页面可读 ≠ 导出可拿——手机号为联络需要在页面脱敏展示，但导出成 Excel 外流是另一个风险等级。导出请求必须独立过一遍校验：申请字段 ⊆ 可读 ∩ 可导出，且导出内容仍走 sanitize（脱敏形态与页面一致）。37 册提醒过「导出是脱敏高危区」，本节把校验规则落成可运行代码。

常用脱敏器清单（展示脱敏一律不可逆；业务回显走单独解密接口 + 审计，不做「可逆脱敏」）：

| 数据 | 规则 | 示例 |
| --- | --- | --- |
| 手机号 | 前 3 后 4 | `138****5678` |
| 身份证 | 前 6 后 4 | `110101********7812` |
| 银行卡 | 只留后 4 | `**** **** **** 3445` |
| 金额 | 区间化 | `10 万以上` |
| 姓名 | 只留姓 | `张*` |

前端在列级管控里承担三件事（判定在后端，体验在前端）：

1. **渲染裁剪**：白名单外的列不渲染表头也不渲染单元格——整列消失，而不是留一列空壳提示「无权限」（后者泄露字段存在性）；
2. **脱敏占位交互**：脱敏值用统一样式（等宽、置灰、禁选中），复制按钮在脱敏字段上禁用或复制脱敏值——绝不允许「复制出明文」；
3. **差异解释**：同一张表不同角色列数不同，表头吸顶、列宽计算要按实际列集来，不能按全字段模板留白。

### 典型应用场景

- 要客 360 视图：销售看联系方式（脱敏），财务看结算账户（后 4 位），客服看姓名打码 + 脱敏手机；
- 经营报表导出：主管页面可看区间化金额，导出申请精确金额被二次校验拦下；
- 能力资源账单：伙伴只能导出自己等级内的资源用量字段。

### 可运行代码示例

白名单裁剪（白名单外字段**直接不出现**，不输出 null——防结构探测）、四种角色四种形态、导出二次校验，完整实现见示例 72-03：

```ts
// 文件: examples/72-03-field-masking.ts —— 节选
const illegal = requestedFields.filter((f) => !policy.readable.includes(f) || !allowed.has(f));
if (illegal.length > 0) {
  throw new Error(`导出二次校验拦截: 角色「${role}」无权导出字段 ${illegal.join(",")}`);
}
```

> 运行方式：`npx tsx examples/72-03-field-masking.ts`

输出里同一条客户记录，销售拿到 3 个字段、财务拿到另外 3 个字段（无手机号）；销售申请导出 `phone` 被拦——页面可见（脱敏形态）不代表导出放行。

### 最佳实践

- ✅ 出口收口：sanitize 只在一处（网关/BFF 序列化层）执行，组件里严禁散落 `replace` 私货；
- ✅ 白名单外字段**直接不输出**（37.5 的结论），前端渲染层对「缺失」与「脱敏」用两种 UI：缺失不渲染该列，脱敏渲染占位符；
- ✅ 导出三件事绑定：二次校验 + 文件水印（导出人/时间）+ 审计留痕（63 册五要素）；
- ❌ 不要给「可逆脱敏」留后门——前端拿到明文的一切理由（复制、核对）都应走专用解密接口并按次审计；
- ❌ 不要用 CSS 遮盖做脱敏（`blur`、遮挡层）——DOM 里仍是明文，DevTools 一扒就穿。

## 72.5 权限变更与一致性：缓存失效与增量推送

### 概念解析

权限系统的经典翻车现场：管理员 10:00 收窄了某人的数据范围，10:05 这人还能导出刚被收回的数据——**变更已生效，缓存不知道**。37.6 给出了「版本号 + 全量替换」的下发框架，本节展开完整的失效时序。

三种失效策略对比：

| 策略 | 时效 | 成本 | 适用 |
| --- | --- | --- | --- |
| TTL 定时刷新 | 最差（窗口期 = TTL） | 最低 | 低频变更、容忍分钟级延迟 |
| **版本号 + 按需对齐** | 请求时发现漂移即刷新 | 低 | 保底方案，必配 |
| **推送失效（WebSocket）** | 秒级 | 长连接 + 服务端推送编排 | 高敏场景（权限收窄、封禁） |

工程答案不是三选一：**推送做快路径，版本号做兜底，重连做补偿**。推送会丢（弱网、切后台、断线），所以每个数据请求携带本地权限版本号，服务端比对发现漂移时在响应头带回当前版本，客户端全量刷新；WebSocket 重连后第一件事是 resync，不能假设断线期间的推送都到了。

一次「收窄」变更的完整时序：

```mermaid
sequenceDiagram
    participant A as 管理员
    participant P as 权限中心
    participant W as 推送通道
    participant C as 客户端
    A->>P: 收窄范围（v1 → v2）
    P->>P: 版本 +1，落审计
    P->>W: 推送失效信号（userId + v2）
    Note over W,C: 弱网/切后台，推送丢失
    C->>C: 旧缓存 v1 继续体验层判定（越权窗口）
    C->>P: 数据请求（携带本地 v1）
    P->>P: 按 v2 判定：越权数据 403
    P-->>C: 响应头带回当前版本 v2
    C->>P: 全量刷新权限缓存
    Note over C: 缓存对齐 v2，窗口关闭
```

**多端一致性**：同一账号 PC、App、小程序三端在线（衔接 [第七十三部分 · 多端架构](./73-multi-end-architecture.md)），权限版本号是跨端的通用语言——任何一端发现漂移都独立刷新，不依赖「主端同步」。收窄类变更（收回权限）必须走推送快路径；放宽类变更可以容忍 TTL。

**变更审计**（衔接 63 册）：权限变更本身是最高危的审计对象——谁、何时、把谁的范围从 A 改成 B、审批单号，五要素齐全；前端职责是把「配置操作」与「生效确认」都埋点，变更单号贯穿配置中心、推送、客户端刷新三处日志，方便串链。

**越权攻防清单**：

| 攻击/事故面 | 原理 | 对策 |
| --- | --- | --- |
| 旧缓存越权 | 收窄后客户端仍用旧范围做体验层判定 | 版本漂移检测 + 服务端最终判定 |
| 推送伪造 | 客户端轻信推送内容，伪造「你已是超管」消息 | 推送只当「失效信号」，收到后**重新拉取**，绝不直接消费推送体里的权限内容 |
| 本地残留 | 权限缓存放 localStorage，退出后仍在 | 只放内存 store，登出即清（37.6 同款纪律） |
| 失效窗口攻击 | 知道 TTL 是 5 分钟，变更后猛刷接口 | 收窄走推送 + 服务端永远重新判定 |
| 切岗竞态 | 兼岗切换中两个范围的请求并发交错 | 切岗 = 会话级切换，整树缓存版本号一起换 |

### 典型应用场景

- 员工调岗：HR 生效时刻起，旧部门数据秒级不可见（推送 + 版本号双保险）；
- 要客回收：销售离职，名下要客划回公海，其移动端缓存立即失效；
- 渠道降级：金级伙伴违规被降铜级，高等级能力 API 的调用凭证即时吊销。

### 可运行代码示例

版本号 + 会丢消息的推送通道 + 客户端缓存的完整时序模拟——包括「旧缓存越权」的复现与修复链路，见示例 72-04：

```ts
// 文件: examples/72-04-permission-invalidation.ts —— 节选
/** 发起数据请求：带本地权限版本，让服务端有机会发现漂移 */
request(deptId: string): { status: number; drift: boolean } {
  const res = this.center.serve(this.userId, deptId, this.cache.version);
  if (res.permVersion !== this.cache.version) {
    this.cache = this.center.get(this.userId); // 版本漂移 → 全量刷新缓存
    return { status: res.status, drift: true };
  }
  return { status: res.status, drift: false };
}
```

> 运行方式：`npx tsx examples/72-04-permission-invalidation.ts`

时间线输出五幕：T1 登录缓存 v1 → T2 收窄为 v2 但推送丢失 → T3 旧缓存把已收回的部门判成可见（**越权复现**）→ T4 服务端按 v2 拒绝并暴露漂移、客户端全量刷新（**安全边界在后端**）→ T5 重连主动 resync 拉到 v3。

### 最佳实践

- ✅ 收窄类变更（收回、封禁、降级）必须走推送快路径 + 服务端强制重判，不接受 TTL 延迟；
- ✅ 推送体只带 `{ userId, version }` 失效信号，权限内容永远由客户端主动拉取——伪造推送只能造成多余刷新，造不成提权；
- ✅ 版本号单调递增、按用户独立；全局一个版本号会让任何变更都打爆全量客户端；
- ❌ 不要把权限缓存持久化到 localStorage/Cookie——跨会话残留 + 共享设备泄露双重风险；
- ✅ 版本漂移上报埋点：漂移率突增说明推送通道在丢消息，该修通道而不是加 TTL；
- ✅ 多端同账号时，每端独立维护自己的缓存与版本号——不做「主端代管」，简单且不会形成单点。

## 72.6 权限配置中心：矩阵、预演与灰度

### 概念解析

权限体系做到最后，瓶颈不在判定引擎而在**配置运营**：几百个角色 × 几十类资源 × 四种范围，靠改库表和口头对齐必然失控。配置中心三件套：

**一、可视化矩阵**。角色 × 资源 × 范围三维矩阵是主交互：行是角色，列是资源（客户/合同/能力资源/报表），单元格是数据范围档位。两个设计要点——单元格只暴露合法档位（`self` 不能配在报表资源上）；单元格 hover 出**推导预览**（这个角色在这个资源上实际可见的部门数/行数估算），让配置者所见即所得。

**二、变更预演（dry-run）**。高危变更（收窄某角色范围、调整部门挂靠）提交前必须回答「影响谁」。预演 = 用变更后的规则对现状跑一次推导，输出 diff：

```ts
// 预演核心：同一份推导函数跑变更前后两套规则，集合相减得影响面
interface ImpactReport {
  affectedUsers: number;        // 可见集合发生变化的用户数
  revokedDepts: string[];       // 被收回可见权的部门
  grantedDepts: string[];       // 新放开的部门
  estimatedRevokedRows: number; // 被收回的数据行数估算（按部门数据量汇总）
}

function dryRun(
  users: Employee[],
  before: (u: Employee) => Set<string>,
  after: (u: Employee) => Set<string>,
  deptRowCount: Map<string, number>,
): ImpactReport {
  const revoked = new Set<string>();
  const granted = new Set<string>();
  let affected = 0;
  for (const u of users) {
    const b = before(u);
    const a = after(u);
    let changed = false;
    for (const d of b) if (!a.has(d)) { revoked.add(d); changed = true; }
    for (const d of a) if (!b.has(d)) { granted.add(d); changed = true; }
    if (changed) affected++;
  }
  const estimated = [...revoked].reduce((sum, d) => sum + (deptRowCount.get(d) ?? 0), 0);
  return { affectedUsers: affected, revokedDepts: [...revoked], grantedDepts: [...granted], estimatedRevokedRows: estimated };
}
```

关键是 `before`/`after` 复用 72-01 的同一个 `visibleDeptIds`——**预演与运行时同一份推导逻辑**，否则预演结果没有可信度。预演报告进审计，审批人看着报告点同意。

**三、灰度发布与回滚**。权限变更的灰度与功能灰度不同——灰度对象是「规则版本」不是代码：新版本规则先对试点部门/白名单用户生效，其余人留在旧版本（双版本并行，按用户路由规则版本）。回滚 = 规则版本指针拨回上一快照，所以规则必须**全量快照版本化**，只存 diff 无法秒级回滚。

三件套串起来就是一条变更流水线，每个状态都有明确的前端形态：

`草稿（可编辑） → 预演（影响面报告） → 审批（报告留痕） → 灰度（双版本并行 + 漂移监控） → 全量（旧快照归档，可随时回滚）`

灰度期前端要多做一件事：把命中的规则版本随埋点上报，灰度组的报错率、空列表率、403 率与对照组对比——权限类灰度的「事故信号」不是白屏，而是**用户突然看不到自己该看的数据**。

### 典型应用场景

- 年末组织架构调整：预演「事业部拆分」对 300 个角色可见范围的影响，分批灰度切换；
- 要客分层标准修订：L2 线从年成交 50 万调到 100 万，预演多少客户降级、多少销售可见集合收缩；
- 新能力上线分级开放：先对金级伙伴放开，两周无投诉再放到银级；
- 合规避雷：监管要求「某类客户数据仅限总部可见」，配置中心按范围矩阵全量排查现有角色，一次性收编。

### 最佳实践

- ✅ 收窄类变更强制 dry-run + 双人复核（配置人 + 审批人），放宽类可以单人——风险不对称；
- ✅ 灰度期双版本并行要在版本号体系内表达（`ruleVersion` 与用户路由规则绑定），灰度比例本身也进审计；
- ❌ 不要只做「权限点开关」式灰度（新规则整体开/关）——真实灰度需要按部门/用户切片；
- ✅ 回滚快照连带组织树版本一起存：规则 v8 是按当时的组织树推导的，组织树变了旧规则可能推不出原样；
- ❌ 不要让配置中心直接写生产权限表——一切变更走「草稿 → 预演 → 审批 → 灰度 → 全量」流水线。

## 72.7 自测题

<details><summary><b>1. 【基础】四种数据范围（本级/本级及下级/指定范围/全部）各自的语义是什么？一人多岗时可见集合怎么计算？</b></summary>

本级 = 仅本部门直属数据；本级及下级 = 本部门为根的整棵子树；指定范围 = 显式枚举的部门集合（可互不相邻）；全部 = 全组织。一人多岗时对各岗位分别推导可见集合再取**并集**——兼岗必须带来范围放大，取交集会让兼岗形同虚设。见 72.1 与示例 72-01。
</details>

<details><summary><b>2. 【基础】物化路径模型下，取一个部门的祖先链和子孙集分别是什么操作？</b></summary>

祖先链：把该节点的 path（如 `/d1/d11/d111/`）按 `/` 切分去掉自身即得，零成本；子孙集：以该节点 path 为前缀做前缀匹配，一次全表扫或索引扫描（SQL 里是 `path LIKE '/d1/d11/%'`）。两个操作都是同步纯计算，这是物化路径对前端最友好的原因。见 72.2。
</details>

<details><summary><b>3. 【基础】行级数据权限中，前端与后端的分工红线是什么？</b></summary>

前端跑 DSL/可见集合只做**体验裁剪**——列表预过滤、空态提示、按钮置灰，减少必然失败的请求；**安全边界永远在后端**：后端必须从用户身份独立推导数据范围并注入查询条件，绝不信任前端提交的任何过滤参数（deptIds、scope 等）。前后端跑同一份 DSL，结果不一致以后端为准并上报漂移。见 72.3。
</details>

<details><summary><b>4. 【进阶】数据范围 DSL 的 dept_in 为什么要在编译期校验「声明部门 ⊆ 用户可见集合」？不校验会漏什么？</b></summary>

不校验时，知道规则格式的人（懂点前端/抓包改参数的内部用户）可以提交 `{ op: "dept_in", value: ["隔壁部门"] }`，规则本身就放大权限；如果后端只是把 DSL 编译成 where 片段而不校验值域，越权就直达数据层。编译期校验把「规则合法性」收敛到一处，且报错发生在配置/提交时刻而非数据泄露之后。这是「封闭 DSL」相对「裸传 SQL 片段」的核心收益。见 72.3 与示例 72-02。
</details>

<details><summary><b>5. 【进阶】导出场景的二次校验校验什么？为什么页面已经脱敏展示了还不够？</b></summary>

二次校验的是：申请导出的字段 ⊆（角色可读字段 ∩ 角色可导出字段），且导出内容仍走同一 sanitize。页面脱敏展示解决的是「看」的风险（肩窥、截图），导出是「批量带走」的风险——量级完全不同，所以导出许可要单独收窄（页面可看脱敏手机，导出不放行），并绑定水印与审计。经典事故模式正是「页面脱敏了，导出接口忘了」。见 72.4 与示例 72-03。
</details>

<details><summary><b>6. 【进阶】权限收窄后只靠 WebSocket 推送让客户端缓存失效，有什么漏洞？完整失效链路应该怎么设计？</b></summary>

推送会丢：弱网、切后台、断线期间消息直接消失，客户端拿旧缓存继续做体验层判定（示例 72-04 的 T3 就是复现）。完整链路三层：推送做快路径（秒级失效，但只带版本号当失效信号，不携带权限内容）；每个数据请求带本地权限版本号，服务端比对发现漂移即在响应中带回当前版本，客户端全量刷新（兜底）；WebSocket 重连后主动 resync（补偿断线窗口）。而无论前端哪一层失守，服务端都按当前版本独立判定——体验层越权可复现，数据层越权不可达成。见 72.5。
</details>

<details><summary><b>7. 【挑战】设计一个 dry-run：角色范围从「本级及下级」改为「本级」，如何估算影响面？需要覆盖哪些边界情况？</b></summary>

核心方法：用变更前后两套规则对**全体受影响用户**各跑一次可见范围推导（必须复用运行时同一份推导函数），集合相减得 revoked/granted 部门，再按各部门数据量汇总估算被收回的行数，输出影响用户数 + 收回部门清单 + 行数估算。边界：一人多岗用户可能因为另一岗仍有该部门而不受影响（逐用户推导而非逐角色）；虚拟团队挂靠节点在被收回子树里的，要单独提示；指定范围（custom）显式引用了被收回部门的用户不受影响但要列出；历史数据归属映射（已撤销部门）要按映射表折算；灰度期双版本并行时预演要区分试点组与非试点组两套口径。见 72.6。
</details>

<details><summary><b>8. 【挑战】列表接口已经按数据范围过滤，详情接口只鉴登录态没判数据范围，攻击路径是什么？如何系统性收口？</b></summary>

攻击路径是经典 IDOR：先正常翻列表拿到几行数据确认 ID 规律（自增 ID、雪花 ID 都可枚举），再用脚本遍历 ID 直接打详情接口——列表过滤完全无效，全表数据可拖。系统性收口三层：单资源访问（详情/编辑/删除）必须重跑数据范围判定（该行是否 ∈ 可见集合），最好由统一的「行级守卫」中间件完成而非各接口手写；列表与详情共用同一份 DSL/推导函数，杜绝两套口径；导出、打印、分享、搜索等**所有数据出口**逐个清点接入同一守卫——漏一个出口等于全漏。见 72.3。
</details>

## 72.8 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 把权限码/数据范围直接挂在部门节点上 | 部门合并、拆分变成权限迁移灾难 | 组织树与权限树分离，角色挂靠节点、节点映射权限点 |
| 一人多岗取交集 | 兼岗用户什么都看不到，倒逼管理员乱放权 | 各岗位可见集合取并集，与多角色取最大范围同一思想 |
| 只过滤列表、不判详情 | 遍历 ID 拖全表（IDOR），行级权限形同虚设 | 单资源访问统一过行级守卫，所有出口（详情/导出/分享）逐个清点 |
| 导出链路绕过 sanitize | 页面脱敏白做，批量明文外流 | 导出独立二次校验（可读 ∩ 可导出）+ 水印 + 审计 |
| 权限缓存放 localStorage | 登出残留、共享设备越权 | 只放内存 store，登出即清 |
| 把推送当可靠通道 | 断线丢消息，旧缓存长期越权 | 推送只当失效信号；请求带版本号兜底；重连 resync 补偿 |
| 物化路径移动节点只改自身 | 整棵子树 path 过期，子孙推导全错 | 移动 = 重写子树全部 path；增量事件携带子树根整子树替换 |
| DSL 支持任意表达式/eval | 规则注入 + 无法审计 | 封闭操作符集，未知即拒绝；dept_in 编译期校验值域 |
| 部门撤销直接物理删除 | 历史数据悬空、审计断链 | 冻结 + 归属映射，历史口径按生效日期版本化 |
