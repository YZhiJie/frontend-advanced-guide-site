## 69.1 埋点全景与事件模型

### 概念解析

埋点（tracking）是在用户行为路径上有计划地放置「探针」，把行为变成可分析的数据。它服务的不是技术而是决策：转化率为什么跌、新功能有没有人用、哪个渠道的用户质量高——这些问题的答案全部来自埋点数据。**埋点体系的质量上限，就是数据驱动决策的质量上限。**

埋点有三种采集路线，选型的本质是**研发成本、数据覆盖率、数据噪声**的三角权衡：

| 维度 | 代码埋点 | 全埋点（无埋点） | 可视化埋点 |
| --- | --- | --- | --- |
| 原理 | 业务代码里手动调 `track()` | SDK 自动拦截全部交互（点击/输入/路由） | 运营在页面上圈选元素，SDK 按选择器上报 |
| 数据精度 | 高（语义明确、属性完整） | 低（只有元素路径，无业务语义） | 中（语义靠圈选时人工命名） |
| 研发成本 | 高（每个事件写代码） | 零（接入即有数据） | 低（运营自助） |
| 数据噪声 | 低 | 极高（全量采集，存储与分析成本爆炸） | 中（页面改版后选择器失效） |
| 适用 | 核心漏斗、交易链路 | 冷启动探索、回溯分析（没埋也能查历史） | 运营活动页、低频长尾页面 |

**成熟团队的答案不是三选一，而是分层**：核心转化漏斗用代码埋点（精度优先），探索性分析用全埋点兜底（覆盖率优先），运营活动用可视化埋点（效率优先）。给一个经验比例：代码埋点覆盖 20% 最关键的事件、贡献 80% 的决策价值；全埋点与可视化埋点解决「没提前埋点怎么办」的存量问题，不解决「指标可信赖」的增量问题。

**事件五要素**是设计任何事件的检查清单，缺一个维度，分析时就会有一块拼不上：

| 要素 | 对应字段 | 说明 |
| --- | --- | --- |
| who | `uid` / `device_id` | 登录前用设备 ID，登录后 `identify` 绑定用户 ID，两条身份链要能合并 |
| when | `ts`（事件发生时间，非上报时间） | 批量上报时事件发生时刻早已过去，必须用发生时间 |
| where | `page` / `position` / `session_id` | 页面路径 + 页面内位置 + 会话标识（串联同一次访问的行为序） |
| what | `name` + 业务属性 | 事件名与业务参数（sku_id、amount 等） |
| how | `network` / `platform` / `app_version` | 环境上下文，定位「只在 4G 下复现」类问题时全靠它 |

**三类基础事件**构成骨架：`track`（自定义行为事件）、`identify`（身份绑定：匿名 ID → 用户 ID，登录瞬间调用，服务端做身份合并）、`pageview`（页面浏览，SPA 需手动埋，见 69.3）。

**公共参数**由 SDK 统一注入、所有事件强制携带，一张表定死字段与用途：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `app_version` | 构建期注入 | 发版归因：「3.2.0 转化率跌了」的定位入口 |
| `device_id` | SDK 首启生成并持久化 | 匿名身份、未登录漏斗 |
| `uid` | 登录后 `identify` 写入 | 登录用户行为链 |
| `session_id` | 30 分钟无活动切新会话 | 会话内行为串联、停留时长归属 |
| `network` | `navigator.connection` / 原生桥 | 「只在 4G 复现」类问题的归因维度 |
| `platform` / `os_version` | UA / 桥 | 多端口径对齐、兼容性问题圈定 |
| `screen_size` | `window.screen` | 响应式布局问题排查 |

公共参数与业务属性的边界要划死：业务属性写在事件 schema 里，公共参数写在 SDK 里，**业务属性禁止与公共参数撞名**（69-02 的注册表会拦下这种撞名）。

**事件 schema 与版本化治理**：每个事件是一份有版本号的契约（`submit_order_click@v1`）。属性只能新增、不能改义、不能删——改义就升版本（v2），服务端按版本号分流解析。原地改义是数据治理的头号事故源：同一个 `amount` 字段，上个月是「元」这个月是「分」，历史数据全部作废。

### 典型应用场景

- **移动办公 App 的审批漏斗**：`approval_detail_view` → `approval_pass_click` → `approval_pass_success`，三步全用代码埋点，每步带 `approval_id` / `template_id`；
- **新功能冷启动**：功能上线前没埋点，用全埋点回溯「上线后有多少人点过这个入口」，再决定要不要补代码埋点；
- **多端身份合并**：用户在 H5 领券（匿名 device_id）、登录 App 后使用（uid），`identify` 把两条身份链合并成一个用户旅程；
- **发版回归分析**：`app_version` 公共参数让「3.2.0 的转化率比 3.1.0 跌了 8%」这种对比成为可能。

### 可运行代码示例

事件 schema 注册表与装载期校验的完整实现见 69.5 节（示例 69-02），本节先看一个最小的事件模型骨架：

```ts
// 文件: examples/69-02-event-schema.ts（核心节选：事件五要素的代码形态）
interface EventSchema {
  name: string; // object_action 蛇形命名，如 submit_order_click
  version: number; // schema 演进靠版本号，禁止原地改义
  owner: string; // 负责人：数据对不上时找得到人
  desc: string;
  props: Record<string, PropSpec>;
}
```

> 运行方式：`npx tsx examples/69-02-event-schema.ts`

### 最佳实践

- ✅ 事件五要素写进埋点需求文档的模板表头（见 69.5），评审时逐列检查，缺列打回；
- ✅ `ts` 用事件发生时刻，不是入队时刻、更不是上报时刻——离线补发的事件到达服务端可能是几小时后；
- ✅ 匿名期也发事件（带 device_id），登录后靠 `identify` 合并——「登录前的浏览行为」是归因分析的金矿；
- ❌ 不要把全埋点当主力数据源：它的价值是「兜底与回溯」，拿它做核心指标会被噪声淹没；
- ❌ 不要让事件属性原地改义：单位、枚举值、粒度的变化都必须升版本号。

## 69.2 埋点 SDK 内核

### 概念解析

19.7 给出了批量队列的三层 flush 单点片段，本节把它扩展成**生产级内核的五个子系统**，每一层都对应一类真实事故：

| 子系统 | 解决的问题 | 关键设计 |
| --- | --- | --- |
| 队列 + 批量 + 节流 | 逐条上报打爆连接数 | 攒够 N 条立即发 + 定时器兜底发，请求数降一个量级 |
| 通道降级 | 页面卸载时普通 fetch 被掐断 | `sendBeacon` → `fetch keepalive` → 普通 fetch（降级细节见 25.10.3） |
| 失败重试 + 幂等 | 弱网丢数据、重试造成重复 | 失败回队首；客户端生成 `event_id`，服务端据此去重 |
| 离线持久化 | 杀进程/断电丢队列 | 每次入队落盘 localStorage（量大用 IndexedDB），启动时恢复 |
| 采样 | 大 DAU 下存储成本爆炸 | 按 uid 稳定哈希采样（与 59 册 Web Vitals 采样同源），同一用户结果恒定 |

**持久化选型**：队列落盘用 localStorage 还是 IndexedDB？事件量小（队列上限几百条）用 localStorage——同步 API 在卸载阶段也能写，代码简单；事件量大（全埋点开启时队列可能上万条）用 IndexedDB——容量按磁盘配额、不阻塞主线程（结构化仓储的完整封装见 19.9）。混合策略也常见：运行期写 IndexedDB，`visibilitychange → hidden` 时把队列头部关键事件同步镜像到 localStorage 兜底。

**通道降级链**的选型依据要记成一张表：

| 通道 | 卸载阶段可靠性 | 体积上限 | 能拿响应 | 适用 |
| --- | --- | --- | --- | --- |
| `sendBeacon` | 高（异步发出不阻塞卸载） | 约 64KB | 不能 | 页面卸载兜底的首选 |
| `fetch` + `keepalive` | 较高（卸载后仍可能完成） | 约 64KB（keepalive 限制） | 能（但卸载后来不及处理） | beacon 不可用/超限时的降级 |
| 普通 `fetch` | 低（卸载即被掐断） | 无 | 能 | 运行期常规批量上报 |

**幂等是重试的前提**：没有 `event_id`，失败重试和超时重发都会让服务端收到重复事件，报表虚高；有了 `event_id`，服务端一张去重表（或 Redis SETNX）就把重复投递拦下，客户端可以放心大胆地重试。**先设计幂等，再设计重试，顺序不能反。**重试节奏用指数退避（1s → 2s → 4s，封顶 30s），避免服务端抖动时被重试风暴二次打垮。

### 典型应用场景

- **电梯/地铁弱网环境**：移动办公用户在通勤路上打卡、审批，网络时断时续——失败回队 + 持久化保证「出站后数据补发，一条不丢」；
- **大促/全员日报高峰**：全员晚 8 点扎堆提交日报，采样 + 批量把上报 QPS 压到服务端可承受的范围；
- **合规审计要求数据完整**：审批类关键事件不采样、失败必重试，普通浏览事件可采样可丢弃——队列溢出时「丢最旧的非关键事件」；
- **崩溃场景的数据兜底**：App 闪退前队列里还有未发事件，靠落盘 + 重启恢复补发，否则「崩溃前的最后操作」这个最有价值的排查线索永远缺失（与 59 册的故障排查闭环衔接）。

### 可运行代码示例

```ts
// 文件: examples/69-01-tracking-sdk.ts（核心节选：失败回队首 + 幂等去重）
async flush(): Promise<void> {
  if (this.flushing || this.queue.length === 0) return;
  const batch = this.queue;
  this.queue = [];
  this.flushing = true;
  try {
    await this.transport(batch);
  } catch (err) {
    // 失败整批回队首，event_id 保证重发不产生服务端重复
    this.queue = [...batch, ...this.queue];
  } finally {
    this.flushing = false;
  }
}
```

> 运行方式：`npx tsx examples/69-01-tracking-sdk.ts`（五段演示：稳定采样、满批发送、失败重试 + event_id 幂等、进程重启恢复、通道降级链选路）

### 最佳实践

1. **采样用稳定哈希，不要用 `Math.random()`**：随机采样让同一用户「今天上报明天不上报」，留存、漏斗这类需要连续行为的分析全部失真（59.2 已详细论证）；
2. **采样要分层**：关键业务事件（支付、审批）永不采样，行为浏览事件按比例采样，在事件 schema 里标注采样级别；
3. **队列必须有上限**：长时间断网时无限堆积会撑爆内存和 localStorage 配额，超出上限丢最旧的非关键事件，并用 `stats.overflowDropped` 计数——对数时能解释缺口；
4. **失败重试要有退避**：连续失败按 1s/2s/4s 指数退避，避免服务端故障时被客户端重试风暴雪上加霜；
5. **`identify` 之后的历史事件要补绑 uid**：登录前入队的匿名事件，上报时应携带登录后的 uid + 原 device_id，服务端才能合并身份链。

## 69.3 声明式埋点与自动采集

### 概念解析

手动 `track()` 散落在业务代码里有三个顽疾：与业务逻辑耦合（重构时埋点被顺手删了）、写法不统一（一百个人写出一百种属性名）、无法批量审查。**声明式埋点**把「埋什么」从「业务逻辑」里抽出来，变成模板上的标注。

**`v-track` 指令设计**（Vue 为例，React 用高阶组件同理）：

```html
<button v-track:click="{ name: 'submit_order_click', props: { sku_id: sku.id } }">提交订单</button>
```

指令的核心实现只做三件事：解析配置、挂监听、转发给 SDK（19.7 的 `delegateClickTrack` 事件委托是底层雏形）：

```ts
// v-track 指令骨架（Vue 3）：配置挂元素上，一个全局委托监听所有点击
const vTrack: Directive<HTMLElement, { name: string; props?: Props }> = {
  mounted(el, binding) {
    const eventType = binding.arg ?? "click"; // v-track:click / v-track:exposure
    if (eventType === "exposure") {
      // 判定算法（50% 面积 + 500ms 停留 + 会话去重）复用 43.4 的 ExposureTracker
      exposureTracker.observe(el, () => sdk.track(binding.value.name, binding.value.props));
      return;
    }
    el.addEventListener(eventType, () => sdk.track(binding.value.name, binding.value.props));
  },
};
```

React 体系等价物是 `useTrack` Hook 或 `<Track>` 包裹组件，思路相同：埋点配置是组件的声明式输入，不是命令式调用。

**曝光埋点**的判定算法（可见面积 ≥50% + 停留 ≥500ms + 会话内去重）在 43.4 已完整实现，本章不重复，只做声明式封装：模板里写 `v-track:exposure="{ name: 'home_banner_exposure', props: { banner_id } }"`，指令内部把元素和回调交给 43.4 的 `ExposureTracker`，判定通过才触发 `track`。算法细节（IntersectionObserver 阈值、停留计时、去重 Set）回到 [43.4 节](./43-business-scenes.md#_43-4-曝光埋点-可见性判定与批量上报)查阅。

**SPA 的 pageview** 没有整页加载，必须在路由层手动埋。两个拦截位：① 底层 patch `history.pushState` / 监听 `popstate`（框架无关，全覆盖）；② 框架路由钩子（`router.afterEach`，语义更准，能拿到路由 meta 里的页面名）。生产上两个都要：钩子为主，patch 兜底（防止有人绕过路由直接改 history）。

**停留时长**不能算「两次 pageview 的时间差」——用户切后台半小时再回来，差值是 30 分钟但实际只看了 10 秒。正确做法是**心跳 + `visibilitychange`**：每 5 秒一跳，只在页面可见时累计；`hidden` 时停表，`visible` 时重置记账起点（iOS 上 `unload` 根本不触发，可见性事件的可靠性见 25.10.3）。

**全埋点的噪声边界**：全埋点采集一切交互，数据量大到「存不起、查不动、噪声淹死信号」。三条边界：① 全埋点数据只做回溯探索，不进核心指标看板；② 设置独立且更短的存储保留期（如 7 天热数据）；③ 自动采集要内置黑名单（输入框内容、长列表滚动等高频低价值事件不采）。还要给全埋点单独算一笔存储账：事件量通常是代码埋点的 50~100 倍，采集前先确认数仓愿意为此付费。

### 典型应用场景

- **列表卡片曝光 + 点击配对**：卡片 `v-track:exposure` + 按钮 `v-track:click`，CTR 在同一套声明式体系里闭环（口径对齐 43.4）；
- **框架升级埋点不丢**：业务迁移 Vue2 → Vue3 时，声明式标注不变，只重写指令实现；
- **审批单停留时长分析**：「这个审批模板平均要看 90 秒才能做决定」说明表单设计有问题——数据来自心跳埋点；
- **hybrid 容器**：WebView 里的 H5 与原生页跳转时，pageview 链路靠统一的路由拦截不断链。

### 可运行代码示例

SPA 路由 pageview 与停留时长心跳的纯逻辑模拟（虚拟时钟，可断言后台时间被剔除）：

```ts
// 文件: examples/69-03-spa-pageview.ts（核心节选：回前台时重置记账起点）
setVisible(visible: boolean): void {
  this.visible = visible;
  if (visible) this.lastTickAt = clock(); // 后台那段时间从「记账起点」里抹掉
}
```

> 运行方式：`npx tsx examples/69-03-spa-pageview.ts`（含 12s 正常停留、切后台 20s 剔除、3s 零头补记、后退链路 referer 四组断言）

### 最佳实践

1. **曝光与点击必须同一套 ID 体系**：点击事件带曝光序号或内容 ID，CTR 才能算到同一个可信基数上（43.4 已论证）；
2. **pageview 的 `referer` 取「上一页路径」而不是 `document.referrer`**：SPA 里 `document.referrer` 永远是站外来源，页面间来源链只能自己维护；
3. **心跳周期按精度需求定**：5s 是通用值；时长类指标只做大盘分析可以放宽到 15s 省流量；
4. **路由切换瞬间先结算旧页再起新页**：顺序反了，旧页的停留时长会算到新页头上；
5. ❌ 不要在 `beforeunload` 里结算停留时长：移动端它经常不触发，用 `visibilitychange → hidden` + 周期心跳兜底。

## 69.4 神策与友盟集成及二次开发

### 概念解析

JD 里的「神策/友盟集成与二次开发」不是把 SDK 脚本贴进 `index.html` 就完事，生产级集成有四层工作：

**① 初始化与 preset properties**：两家 SDK 都支持「预置属性」——初始化时注册 `app_version`、`channel`、`platform` 等，之后每个事件自动携带，等价于 69.1 公共参数的第三方实现。神策用 `registerPage`（Web）/ `registerSuperProperties`（小程序），友盟用 `registerGlobalProperty`。初始化时还要对齐身份体系：神策的 `login(uid)` 对应 69.1 的 `identify`，友盟的 `onProfileSignIn` 同理。

**② 插件机制**：神策 Web SDK 的 `use(pluginName, options)` 允许挂载自定义插件拦截事件流——在插件里可以做属性统一加工（如所有事件追加 `ab_variant` 实验分组）、敏感字段拦截（见 69.6）、事件白名单过滤。这是「二次开发」的主战场：不改 SDK 源码，用插件把公司级规范注进 SDK 管道。

**③ 自定义事件映射层**：业务语义与第三方字段之间要有一层适配，而不是业务代码直接调 `sensors.track('SubmitOrder', ...)`。映射层的价值在于：业务只认自己的蛇形事件名，换供应商时只改映射层：

```ts
// 业务语义 → 第三方字段的映射表示意
const eventMap: Record<string, { sensors?: string; umeng?: string }> = {
  submit_order_click: { sensors: "SubmitOrderClick", umeng: "submit_order" },
  home_banner_exposure: { sensors: "BannerExposure", umeng: "banner_expo" },
};
```

**④ 调试模式与埋点校验**：神策的 debug 模式（`show_log` + 服务端 debug 白名单）让事件只进调试库不进正式库；友盟有集成测试模式。上线前的校验要走固定流程，交给 QA 用工具做而不是研发肉眼：

1. 白名单设备开启 debug 模式，操作一遍埋点需求文档里的全部触发路径；
2. 抓包或 SDK 日志核对每个事件：事件名、属性齐全性、类型、公共参数；
3. 对照需求文档逐字段打勾，差异项提 bug 单（属性缺失和类型错误是两类最高频问题）；
4. 触发顺序验证：漏斗事件必须按 `view → click → success` 顺序到达，乱序说明有竞态。

**初始化时序**是集成的第一个坑：第三方脚本异步加载，业务代码在加载完成前调的 `track` 会全部丢失。标准解法：自家封装层先接住事件进内存队列，SDK 就绪回调里统一回放（这一点与 69.2 的内核队列天然兼容——SDK 未就绪就是 transport 未就绪）。

**多 SDK 并存的分发器设计**：公司常见「自研服务端 + 神策（行为分析）+ 友盟（渠道统计）」三家同收。业务代码只调一次自家 SDK 的 `track`，分发器按事件映射表扇出到各家；某家 SDK 加载失败（被广告拦截器干掉是常态）不能影响其他家，更不能抛错打断业务——分发器对每个下游 try/catch 隔离。

```ts
// 分发器骨架：业务只见 track 一次，下游隔离扇出
class Dispatcher {
  private sinks: Array<{ name: string; track: (n: string, p: Props) => void }> = [];
  track(name: string, props: Props): void {
    for (const sink of this.sinks) {
      try {
        sink.track(eventMap[name]?.[sink.name as "sensors"] ?? name, props);
      } catch (err) {
        console.warn(`[dispatcher] ${sink.name} 上报失败已隔离:`, err);
      }
    }
  }
}
```

### 典型应用场景

- **SDK 被广告拦截器屏蔽**：`sensorsdata.min.js` 在常见拦截规则里——自研分发层 + 自家域名代理转发，把第三方 SDK 的加载失败率从 15% 降到 2%；
- **灰度切换供应商**：新供应商先收 10% 流量的影子数据（只收不算），与旧供应商对数一致后再切正式；
- **事件属性统一追加实验分组**：用插件机制注入 `ab_variant`，不用改几百处业务埋点；
- **私有化部署的神策**：数据网关走内网，SDK 初始化时 `server_url` 指向自有域名，公网 SDK 直连要过安全评审。

### 核心代码

分发器与映射层的设计见上方代码块；事件装载期校验（映射表的合法性也可以复用同一套 schema 注册表）见示例 69-02。

> 运行方式：`npx tsx examples/69-02-event-schema.ts`

### 最佳实践

1. **永远不让业务代码直接 import 第三方 SDK**：所有调用收敛到自家封装层，这是「换供应商只改一处」和「拦截器屏蔽可兜底」的共同前提；
2. **第三方脚本异步加载 + 加载前事件入队**：SDK 未就绪时事件先进内存队列，就绪后回放——首屏事件丢一半是贴脚本式接入的标配事故；
3. **preset properties 与自家公共参数对齐**：同一字段两边命名不同（`app_version` vs `appVersion`）会让数仓 Join 时哭出来，接入第一天就定对照表；
4. **debug 模式按环境隔离**：测试环境全量进调试库，生产环境只给白名单设备开 debug，别把调试流量混进正式报表；
5. ❌ 不要直接改第三方 SDK 源码：升级版本时所有改动灰飞烟灭，一切定制走插件/映射层。

## 69.5 埋点规范与数据质量

### 概念解析

埋点体系的失败很少是技术失败，绝大多数是**治理失败**：事件名随心所欲（`click1`、`btn_click_new2`）、属性含义漂移、需求文档和代码两张皮。规范的落地路径是「文档模板 → 代码化校验 → 自动化测试 → 定期对数」四环。

**命名规范**：`object_action` 蛇形结构——`submit_order_click`、`home_banner_exposure`、`approval_pass_success`。三个硬规则：① 全小写蛇形，禁止大驼峰与拼音；② object 用名词、action 用预定义动词表（`click/view/exposure/submit/success/fail`，新动词要评审）；③ 禁止版本号进事件名（`xxx_v2` 是灾难，版本走 schema 的 version 字段）。

**埋点需求文档模板**（评审的输入物，缺列打回）：

| 列 | 示例 | 说明 |
| --- | --- | --- |
| 事件名 | `submit_order_click` | 过命名规范校验 |
| 触发时机 | 点击「提交订单」按钮且表单校验通过后 | 写清前置条件，歧义是埋错点的温床 |
| 属性 | `sku_id: string 必填；amount: number 必填（单位：分）` | 类型、必填、单位、枚举值 |
| 公共参数 | 默认全量携带 | 特殊追加才写 |
| 负责人 | 张三 | 数据对不上时找得到人 |
| 验收口径 | 与后端订单表当日提交数误差 < 1% | 对数标准事先约定 |

**装载期校验**：规范写进代码才会被执行——schema 注册表在「注册时」拦不合规定义，在「上报前」拦缺属性/类型错/公共参数缺失的事件（示例 69-02 完整实现）。开发环境校验失败直接报错阻断，生产环境降级为告警上报（不能因埋点 bug 打断业务）。

**单元测试与 e2e 断言**：单测用 mock transport 断言「点了这个按钮，队列里出现这个名字和这组属性的事件」；e2e 在真实流程里断言关键漏斗事件按序发出（`view` → `click` → `success`）。CI 里跑，埋点回归和功能回归同级。单测骨架：

```ts
// 埋点单测套路：注入数组收集器当 transport，断言队列内容而非网络请求
const sent: TrackEvent[] = [];
const sdk = new TrackingSDK({ transport: async (b) => void sent.push(...b), flushSize: 1 });
sdk.identify("u-test");
sdk.track("submit_order_click", { sku_id: "SKU-1", amount: 9900 });
await sdk.flush();
expect(sent[0]).toMatchObject({ name: "submit_order_click" });
expect(sent[0].props).toMatchObject({ sku_id: "SKU-1", amount: 9900 });
```

**与后端对数**：前端埋点说「提交订单点击 10000 次」，后端订单表说「创建订单 9500 条」——5% 的差是正常损耗（校验失败、网络中断），差 30% 就是埋点链路有洞。对数按「抽样比对 + 总量比对」两条腿：总量每日定时任务比，抽样挑具体 `order_id` 核对事件属性与订单字段一致性。

### 典型应用场景

- **大版本发版前的埋点回归**：e2e 跑核心漏斗，事件序列与属性快照对比基线，变更必须过评审；
- **新人接手半年后的考古**：注册表里的 `desc` + `owner` + 需求文档链接，让「这个事件是干嘛的」不用靠猜；
- **双端口径对齐会**：iOS/Android/Web 三方按同一份需求文档埋点，对数时按 `platform` 公共参数拆开比；
- **数据异常定位**：漏斗某步转化率突降——先查装载期校验告警（是不是这版发坏了），再查对数任务（是不是后端改了逻辑）。

### 可运行代码示例

schema 注册表两道关卡（注册拦截 + 上报前校验）的完整实现与演示：

```ts
// 文件: examples/69-02-event-schema.ts（核心节选：注册时拦截不合规定义）
if (!NAME_RE.test(schema.name)) {
  errors.push(`事件名「${schema.name}」不合规：必须是 object_action 蛇形命名`);
}
for (const p of Object.keys(schema.props)) {
  if (p in COMMON_PARAMS) {
    errors.push(`属性「${p}」与公共参数撞名，会被 SDK 注入值覆盖`);
  }
}
```

> 运行方式：`npx tsx examples/69-02-event-schema.ts`（合法注册、四类非法注册拦截、合法事件通过、三类非法上报拦截）

### 最佳实践

1. **校验规则宁可少而硬，不要多而软**：五条必拦的铁律（命名、撞名、缺负责人、版本回退、未注册）好过五十条只警告的建议；
2. **开发环境阻断、生产环境告警**：埋点代码的 bug 不能变成线上事故，但要在监控里能看见（接 59 册的错误上报）；
3. **对数指标进看板，差异超阈值告警**：「前端点击数 vs 后端订单数」的日环比差异超过阈值自动告警，比等运营发现快两周；
4. **需求文档与注册表同源**：注册表支持导出 Markdown 表格回填需求文档，消灭「文档和代码两张皮」；
5. ❌ 不要把命名规范停留在 Wiki：不被代码执行的规范，存活期不超过一个季度。

## 69.6 隐私合规与脱敏

### 概念解析

个保法与 GDPR 对埋点的要求可以归纳成四条工程红线，每条都有对应的代码形态：

**① 同意管理（Consent）**：「告知-同意」是采集的前置条件。工程实现是一个三态状态机：

```ts
// 同意状态机：unknown 时挂起（入队不上报），agreed 开闸补发，refused 清空永闭
type ConsentState = "unknown" | "agreed" | "refused";
function onConsentChange(state: ConsentState, sdk: TrackingSDK): void {
  if (state === "agreed") void sdk.flush(); // 补发挂起期间入队的事件
  if (state === "refused") sdk.disable(); // 清队列 + 落持久化标记 + 忽略后续一切 track
}
```

SDK 初始化前挂起所有采集（事件入队但不上报），用户在隐私弹窗点「同意」后才开闸；点「拒绝」则清空队列并永久关闭（localStorage 落标记）。**「拒绝后还在发数据」是监管通报里最高频的违规点。**

**② 最小化采集**：只收业务必需字段。手机号、身份证、精准地理位置默认不采；确需采集的字段要在隐私政策里逐项列明。「先全采了以后可能有用」在合规上直接违规，在成本上也是浪费。

**③ 敏感字段脱敏白名单**：反向思维——默认所有字符串属性都不可信，只有白名单里的字段允许原样上报；非白名单字段过脱敏函数（手机号保留前三后四、邮箱域名保留用户名打码）。URL 是重灾区：查询参数里的 `token`、`code` 要在采集前剥掉。

```ts
// 脱敏管线示意：白名单直通，其余按类型打码
function sanitize(key: string, value: unknown): unknown {
  if (FIELD_WHITELIST.has(key)) return value;
  if (typeof value !== "string") return value;
  if (/^1\d{10}$/.test(value)) return value.slice(0, 3) + "****" + value.slice(7);
  if (/^[^@\s]+@[^@\s]+$/.test(value)) return "***@" + value.split("@")[1];
  return value;
}
```

**④ 一键关闭开关**：监管检查与企业客户（尤其政企办公场景）会要求「完全关闭数据统计」。SDK 提供 `disable()`：停止一切采集与上报、清空本地队列、忽略后续所有 `track` 调用。开关状态本地持久化，且入口要在「设置」里可达——藏在代码里的开关等于没有。

桌面端（Tauri/Electron）的合规差异——设备指纹获取方式、系统级权限、离线队列的存储位置——见[第 70 册](./70-desktop-app-tauri.md)。

发行变体是政企/海外场景的常态，一套代码靠配置分叉而不是代码分叉：

| 变体 | sink 配置 | 同意弹窗 | 采集范围 |
| --- | --- | --- | --- |
| 国内标准版 | 自研 + 神策 + 友盟 | 首次启动弹一次 | 全量行为事件 |
| 政企版 | 仅自研（指向客户内网网关） | 按客户合同决定 | 只留审计必需事件 |
| 海外版（GDPR） | 自研 + 神策（关友盟） | 弹窗 + 可撤回 | 同意前零采集，敏感字段全脱敏 |

### 典型应用场景

- **政企版移动办公**：客户合同里写明「禁用第三方统计」——分发器摘掉神策/友盟 sink、自研上报切到客户内网网关，一套代码两个发行变体；
- **欧盟用户访问**：GDPR 要求可撤回同意 + 数据可删除，`disable()` + 服务端按 `device_id` 删除数据的接口要成套提供；
- **应用市场审核**：国内市场对「同意前采集」的检测是自动化的，启动后、弹窗前的任何网络请求都会被抓——SDK 必须严格惰性初始化；
- **URL 携带票据**：单点登录回调 URL 带 `ticket` 参数，pageview 采集前必须剥离，否则票据进了第三方服务器。

### 最佳实践

1. **同意状态机只有两态迁移**：`unknown → agreed / refused`，拒绝后再开启必须用户主动操作，不能代码里偷偷重置；
2. **脱敏在 SDK 管道里做，不靠业务自觉**：业务传什么就脱什么（69.4 的插件机制是天然挂点），白名单评审制；
3. **关闭开关要测试「关闭后零外发」**：e2e 里抓包断言拒绝同意后无任何埋点请求发出；
4. **合规字段清单跟隐私政策联动**：隐私政策里列的字段集合 = 代码里允许采集的字段集合，两者 diff 进 CI；
5. ❌ 不要在埋点属性里传「明文证件号/银行卡号」——即使服务端会脱敏，传输与第三方 SDK 日志环节已经泄了。

## 69.7 自测题

<details>
<summary><b>1. 【基础】事件五要素是谁、何时、何地、什么、如何——其中 ts 字段应该取什么时刻，为什么？</b></summary>

**答案**：取**事件发生时刻**，不是入队时刻更不是上报时刻。批量上报与离线补发会让事件到达服务端的时间远晚于发生时间（弱网场景可能差几小时），用上报时间会让行为序列、漏斗间隔、分时统计全部失真。服务端入库时通常另存 `receive_ts` 做数据质量监控（估算延迟分布），但分析口径一律用事件发生时刻 `ts`。

</details>

<details>
<summary><b>2. 【基础】事件命名为什么禁止出现版本号后缀（如 submit_order_v2_click）？schema 演进应该怎么做？</b></summary>

**答案**：事件名是分析口径的锚点，版本号进名字会让同一业务行为在报表里裂成两个事件，历史趋势断裂，看板要手动拼接。正确做法：事件名稳定，schema 带 `version` 字段；属性只能新增，单位/枚举/粒度的改义必须整体升版本（v1 → v2），服务端按版本号分流解析，新旧版本灰度期并存。

</details>

<details>
<summary><b>3. 【基础】为什么埋点 SDK 必须在隐私弹窗「同意」之前挂起所有采集？工程上怎么实现？</b></summary>

**答案**：个保法与应用市场审核都要求「告知-同意」是采集的前置条件，弹窗前的任何数据外发都会被自动化检测抓包通报。工程实现：SDK 初始化时默认挂起——`track` 调用只入队不上报；用户点「同意」后开闸补发；点「拒绝」则清空队列、持久化拒绝标记并永久关闭，此后所有 `track` 调用直接忽略。

</details>

<details>
<summary><b>4. 【进阶】失败重试为什么必须先有 event_id 幂等设计？没有它会出什么问题？</b></summary>

**答案**：重试的前提是「重复投递无害」。没有 event_id 时，超时重发、失败回队重发、网络层自动重试都会让同一事件到达服务端多次，报表虚高且无法事后去重（两条记录一模一样，无法判断是重复还是用户真的点了两次）。有了客户端生成的 event_id，服务端按它去重（去重表或 SETNX），客户端才能放心重试。顺序不能反：先幂等，再重试。

</details>

<details>
<summary><b>5. 【进阶】SPA 的停留时长为什么不能算「两次 pageview 的时间差」？正确方案是什么？</b></summary>

**答案**：时间差把「切后台」的时间也算进去——用户锁屏半小时再回来，差值 30 分钟但实际只看了 10 秒；且 iOS 上 `unload`/`beforeunload` 经常不触发，最后一页的时长直接丢失。正确方案是**心跳 + visibilitychange**：每 5 秒一跳，只在页面可见时累计；`hidden` 停表，`visible` 时重置记账起点把后台时间从时间轴抹掉；路由切换与卸载前结算（示例 69-03 演示了后台 20s 被完整剔除）。

</details>

<details>
<summary><b>6. 【进阶】多 SDK 并存（自研 + 神策 + 友盟）时，分发器为什么要对每个下游 try/catch 隔离？</b></summary>

**答案**：第三方 SDK 的不可控因素太多——被广告拦截器屏蔽导致加载失败、版本升级的 API 变更、对端服务抖动。不做隔离，一个 `sensors is not defined` 就能让后续所有 sink 收不到数据，甚至异常冒泡打断业务代码（用户在支付按钮上白点）。隔离后某家失败只影响自家数据流，配合映射层还能做到「换供应商只改一处」。本质是**把第三方依赖当作必然会失败的组件来设计**。

</details>

<details>
<summary><b>7. 【挑战】设计一套「埋点数据质量」的自动化防线，覆盖开发期、测试期、上线后三个阶段。</b></summary>

**答案**：

| 阶段 | 防线 | 机制 |
| --- | --- | --- |
| 开发期 | schema 注册表装载期校验 | 注册时拦命名违规/撞名/版本回退，上报前拦缺属性/类型错/公共参数缺失，开发环境报错阻断 |
| 测试期 | 单测 + e2e 断言 | 单测 mock transport 断言事件名与属性；e2e 断言核心漏斗事件序列与属性快照，CI 卡红线 |
| 上线后 | 对数 + 告警 | 总量对数（前端事件数 vs 后端业务表，日环比差异超阈值告警）+ 抽样比对（按 order_id 核对字段一致性）+ 生产校验降级为告警接监控系统 |

三环的共同原则：规范必须代码化，靠人 review 的规范撑不过一个季度。

</details>

<details>
<summary><b>8. 【挑战】公司要在政企版（合同禁第三方统计）与海外版（GDPR）同时发行同一套代码，埋点体系要做哪些设计？</b></summary>

**答案**：① 分发器架构：业务只调自家 SDK，sink 可插拔——政企版构建时摘掉神策/友盟 sink，自研上报指向客户内网网关；② 同意管理前置：GDPR 版启动先弹同意框，SDK 挂起等待，拒绝则 `disable()` 并支持撤回与按 device_id 删除数据；③ 最小化与脱敏白名单：敏感字段默认打码，白名单按发行版本配置（政企版可整体关闭行为采集只留审计必需事件）；④ 构建变体管理：事件映射表、preset properties、采样率按变体出配置，核心代码不分叉；⑤ 合规 e2e：抓包断言「拒绝后零外发」「政企版无任何第三方域名请求」，进 CI 防回归。

</details>

## 69.8 本章避坑清单

| # | 坑 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 逐条上报不批量 | 请求风暴拖慢页面、打爆连接 | 满 N 条即发 + 定时兜底 + 卸载 sendBeacon（19.7/25.10.3） |
| 2 | 重试不做幂等 | 重复事件进报表，数据虚高且无法事后去重 | 客户端生成 `event_id`，服务端按它去重 |
| 3 | 采样用 `Math.random()` | 同一用户时采时不采，漏斗与留存失真 | uid 稳定哈希，结果恒定（69-01） |
| 4 | 队列失败即丢/无限堆积 | 弱网数据缺口 / 内存与配额撑爆 | 失败回队首 + 队列上限丢最旧 + 丢弃计数 |
| 5 | 卸载用 `unload`/`beforeunload` | iOS 上根本不触发，末页数据全丢 | `visibilitychange → hidden` + `pagehide` + sendBeacon |
| 6 | 事件属性原地改义 | 历史数据全部作废，趋势断裂 | 只增不改，改义升 schema 版本号 |
| 7 | 业务代码直接调第三方 SDK | 换供应商全改、被拦截器屏蔽即失明 | 分发器 + 映射层收敛，下游 try/catch 隔离 |
| 8 | 停留时长算 pageview 时间差 | 切后台时间全计入，时长虚高一个量级 | 可见时心跳累计，回前台重置记账起点（69-03） |
| 9 | 规范只写在 Wiki | 三个月后与代码严重漂移 | schema 注册表装载期强制校验（69-02） |
| 10 | 隐私弹窗前就发数据 | 应用市场下架、监管通报 | 同意前挂起入队，拒绝后永久关闭 |
| 11 | 敏感字段靠业务自觉脱敏 | token/手机号进第三方日志 | SDK 管道统一脱敏 + 白名单评审制 |
| 12 | 全埋点数据进核心看板 | 噪声淹死信号，存储成本爆炸 | 全埋点只做回溯探索，短保留期 + 采集黑名单 |
