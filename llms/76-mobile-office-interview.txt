## 76.1 JD 拆解方法论：从招聘信息到能力权重表

### 概念解析

JD（Job Description）不是广告，是**面试官的出题范围**。一份 JD 里藏着四类信息，价值密度完全不同：

| 信息类别 | 在 JD 里的位置 | 面试含义 |
| --- | --- | --- |
| 硬性要求 | 岗位职责前 3 条、任职要求正文 | 一定会问，答不出直接挂 |
| 加分项 | 「优先」「了解 XXX 者加分」 | 区分度来源，答好了定级上浮 |
| 软技能 | 「沟通协作」「owner 意识」「抗压」 | 通过行为面试题旁敲侧击 |
| 隐含考点 | 字面没写、但由业务形态必然推出 | 高手与普通候选人的分水岭 |

**拆解方法 = 关键词频次 × 位置权重**。频次好理解：一个词出现 3 次比出现 1 次重要。位置权重更容易被忽略——同一个词，出现在「岗位职责第 1 条」和出现在「加分项最后一条」，含金量差一个量级：

- **板块权重**：标题 > 岗位职责 > 任职要求 > 加分项。岗位职责是公司掏钱请你来**做的事**，任职要求是他们**以为**需要的能力，加分项是**惊喜**。
- **条目位置衰减**：板块内部同样有序——HR 写 JD 时最重要的诉求会本能地放在前面，第 1 条的权重最高，往后逐条衰减。
- **同义词归并**：「数据上报」「埋点」「神策」是同一个能力域的不同说法，必须归并计数，否则频次被稀释。

**实操三读法**——把一份 JD 读三遍，每遍只干一件事：

1. **第一遍速读**：圈出所有技术名词与动词短语（「建设」「主导」「优化」「推动」），建立原始词表，不判断重要性；
2. **第二遍标注**：给每个词标注所在板块（职责/任职/加分）与条目序号，同义词归并到主词名下；
3. **第三遍量化**：按「频次 × 板块权重 × 位置衰减」打分排序，产出能力权重表——这张表就是复习计划本身，加权分高的词逐个准备 STAR 故事（76.3），低分词只需能讲清概念边界。

手工拆解十分钟即可完成一份 JD；下面的可运行示例把这套方法固化成代码，换一份 JD 只需替换内置文本。

### 应用实践：一份移动办公 JD 的完整拆解

以本系列对标的目标岗位为例（企业级移动办公前端，3 年+ 经验）：

> **高级前端工程师（企业级移动办公方向）**
>
> 【岗位职责】
> 1. 负责企业级移动办公产品（IM、审批、日程、文档）的前端架构设计与核心模块开发，覆盖 Web、PC 桌面端与移动 H5 多端；
> 2. 主导 PC 桌面端的架构升级与性能优化，推动 Rust 在端能力层的落地；
> 3. 建设前端埋点体系，制定埋点规范，提升埋点覆盖率与数据准确率，支撑产品数据化决策；
> 4. 负责分层分级权限体系（组织层级、数据权限）的前端落地，保障企业级安全合规；
> 5. 参与多端共用架构设计，抽象端能力差异，提升跨端代码复用率与一致性体验。
>
> 【任职要求】
> 1. 计算机相关专业本科及以上学历，3 年以上前端开发经验，有协同办公或企业级 SaaS 经验者优先；
> 2. 熟练掌握 Vue 或 React 技术栈及生态，理解框架原理，具备复杂状态管理与组件设计能力；
> 3. 熟悉前端工程化与性能优化，有大型单页应用架构设计经验；
> 4. 有埋点 SDK 或数据上报体系的设计落地经验，熟悉神策、友盟等第三方埋点平台者优先；
> 5. 具备良好的沟通协作能力与 owner 意识，能与产品、设计、后端高效协同。
>
> 【加分项】
> 1. 有 Electron 或 Tauri 桌面端开发经验，了解 Rust 语言；
> 2. 有数据权限、RBAC、ABAC 等权限模型落地经验；
> 3. 有 WASM、跨端渲染、信创环境适配经验；
> 4. 有开源贡献或技术博客。

**隐含考点**是这张表里最值钱的四行——字面上没写，但业务形态必然推出：

| JD 原文 | 隐含考点 | 为什么必考 |
| --- | --- | --- |
| 「支撑产品数据化决策」 | 数据质量闭环（规范代码化、与后端对账） | 只会调 `track` 的人撑不起「决策」二字，69.5 才是考点 |

| 「推动 Rust 落地」 | WASM 边界成本评估，而非 Rust 语法 | 前端岗不考 Rust 所有权，考你**什么时候不该用** WASM（71.3） |
| 「owner 意识」 | 跨团队推动规范落地、写 RFC 争取资源 | 34.5 的软素养——埋点规范和权限体系都是「要别人配合」的事 |

### 可运行代码示例

拆解方法论可以工具化：词典匹配做关键词提取（同义词归并），板块权重 × 条目位置衰减做加权打分，输出降序能力权重表并自动映射到本指南分册。核心打分逻辑：

```ts
// 文件: examples/76-01-jd-analyzer.ts —— 节选
const BLOCK_WEIGHT: Record<string, number> = {
  标题: 1.5,       // 标题是岗位定位的浓缩
  岗位职责: 1.2,   // 掏钱请你来做的事，权重最高
  任职要求: 1.0,   // 他们以为需要的能力
  加分项: 0.6,     // 惊喜项，区分度来源而非门槛
};

/** 条目位置衰减：板块内第 1 条权重最高，之后每靠后一条递减 15% */
function positionDecay(entryIndex: number): number {
  return 1 / (1 + 0.15 * entryIndex);
}
// 某关键词加权分 = Σ（该词在每行的命中次数 × 行所属板块权重 × 行内位置衰减）
```

> 运行方式：`npx tsx examples/76-01-jd-analyzer.ts`

实跑这份 JD 的输出有两点值得记住：**领域词「协同办公」总分最高**（8.23 分，渗透全部四个板块）——业务匹配度是隐性门槛，纯技术回答拿不到满分；**「埋点」在岗位职责命中 3 次得 2.77 分，挪到加分项同样 3 次只得 1.38 分**——位置即诚意，复习优先级就该按这个排序。

### 最佳实践：三岗差异与选岗建议

同一套 69~75 册能力储备，投递不同侧重的岗位时叙事重心完全不同。移动办公前端岗常见三种画像：

| 岗位画像 | JD 信号词 | 能力侧重 | 适合谁 | 叙事重心 |
| --- | --- | --- | --- | --- |
| **支撑型** | 「轻量版」「埋点」「数据上报」「内部工具」 | 埋点体系 + 工程化 + 数据质量 | 数据 sense 强、喜欢做基建和工具链的人 | 69 册为主：SDK 内核、规范代码化、对账闭环 |
| **成长型** | 「核心产品」「重构」「架构升级」「性能优化」 | 多端架构 + 桌面端 + 性能 | 想快速承担核心模块、接受高强度迭代的人 | 70/73 册为主：重构方法论、能力抽象层、绞杀者模式 |
| **业务型** | 「分层分级」「数据权限」「政企」「合规」 | 权限模型 + 组织树 + 信创合规 | 喜欢复杂业务建模、对 B 端业务有耐心的人 | 72/74 册为主：数据范围 DSL、行列级管控、国密适配 |

**选岗建议**：三年经验候选人优先投**成长型**——重构类项目最能沉淀可讲的 STAR 素材（76.3 模板二），且「核心产品」意味着资源与曝光；支撑型岗位天花板偏低但稳定，适合求稳；业务型岗位的权限与合规经验在政企/金融行业是稀缺资产，适合作为第二份工作的定向积累。三种画像都要求 69 册的埋点功底——**埋点是移动办公前端的通用入场券**。

**投递节奏**：同批投递不要超过三家，按「保底 → 目标 → 冲刺」排序，每场面试后先用 76.4 的复盘清单更新题库权重，再投下一家——面试本身就是最准的 JD 校准器，冲刺岗永远放在最后。

## 76.2 定向题库：五大域二十题通关

通用题库（第 23 册）解决「前端都会问什么」，本节解决「**这个岗位**会问什么」。20 题按 JD 五个能力域分组，每题统一五段式：**考点 → 答题框架 → 追问预判 → 评分点 → 深入阅读**。评分点给的是面试官心里的标尺——60 分是「知道有这么个东西」，80 分是「做过且能讲清取舍」，100 分是「能讲出数字、边界和教训」。

**练题方法**：每题先合上书自答并录音，再对照「答题框架」查漏，最后按「评分点」自评档位，回放录音检查口头禅与停顿。九成的候选人卡在 60→80 分档（知道但讲不清因果），而 80→100 分档的差距全部在「数字、边界、教训」三类细节上——这三类细节只能从真实项目或真实压测中来，背题背不出来。

### 第一组 埋点体系（Q1~Q5，对应第 69 册）

> 备考提示：本组是 JD 权重第二高、且三岗画像通吃的能力域，Q1 与 Q3 必须达到 100 分档。

#### Q1 设计一个前端埋点 SDK：队列、批量、失败重试与去重分别怎么做？

- **考点**：SDK 内核设计能力，本岗位第一高频题。
- **答题框架**：① 内存队列缓冲，满 N 条 + 定时器双触发批量发送 ② 失败回队首 + 指数退避重试 ③ `event_id` 客户端生成做幂等去重——**先幂等再重试**，顺序不能反 ④ 队列上限丢最旧 + 丢弃计数上报 ⑤ 页面卸载走 `sendBeacon` 兜底，队列落盘支持断电恢复。
- **追问预判**：「重复投递怎么防？」答 `event_id` + 服务端去重表；「弱网队列一直积压怎么办？」答上限 + 丢弃计数 + 采样降级。
- **评分点**：60 分 = 说出批量与重试；80 分 = 讲清「先幂等再重试」的因果顺序和 `sendBeacon` 兜底场景；100 分 = 补齐稳定哈希采样、持久化恢复、通道降级链，并主动给出丢弃率监控指标。
- **深入阅读**：[69.2 埋点 SDK 内核](./69-frontend-tracking.md#_69-2-埋点-sdk-内核)

#### Q2 曝光埋点怎么做到既不漏报也不重复上报？

- **考点**：可见性判定与生命周期管理。
- **答题框架**：① `IntersectionObserver` 判定可见性，约定阈值（如 50%）与持续时长（如 300ms）双条件 ② 元素级「已上报」标记防重复 ③ 列表复用场景用数据主键而非 DOM 节点做标记 ④ 批量聚合后统一上报，避免逐条请求风暴。
- **追问预判**：「虚拟列表里怎么办？」答标记挂在数据 id 上，滚动复用 DOM 不影响；「快速滑过算不算曝光？」答持续时长阈值过滤。
- **评分点**：60 分 = 知道 `IntersectionObserver`；80 分 = 讲清双条件与数据主键防重；100 分 = 说出 SPA 路由切换时的残留监听清理与批量聚合窗口设计。
- **深入阅读**：[69.3 声明式埋点与自动采集](./69-frontend-tracking.md#_69-3-声明式埋点与自动采集)

#### Q3 埋点数据质量怎么保障？从需求评审到数据对账的闭环怎么建？

- **考点**：体系化思维，区分「会埋点」和「建过埋点体系」。
- **答题框架**：① schema 注册表：事件名、属性、类型、枚举值全部登记 ② 装载期校验：未注册事件直接报错，规范从 Wiki 变成代码 ③ 单测/e2e 断言埋点触发 ④ 上线后与后端业务表对账，差异率超阈值告警 ⑤ 看板化：覆盖率、准确率、废弃事件清单。
- **追问预判**：「规范写了没人遵守怎么办？」答装载期强制校验——不合规的埋点根本进不了代码库。
- **评分点**：60 分 = 提到命名规范；80 分 = 讲出 schema 注册表 + 装载期校验的代码化手段；100 分 = 讲出对账闭环与量化指标（对账差异 < 0.5%）。
- **深入阅读**：[69.5 埋点规范与数据质量](./69-frontend-tracking.md#_69-5-埋点规范与数据质量)

#### Q4 SPA 的页面浏览与停留时长怎么统计？有哪些坑？

- **考点**：路由拦截与时间记账的边界处理。
- **答题框架**：① 路由守卫/全局 `history` 监听生成虚拟 pageview，`document.title` 与路径做页面标识 ② 停留时长用「可见时心跳累计」而非 pageview 时间差 ③ 切后台（`visibilitychange → hidden`）暂停计时，回前台重置记账起点 ④ 末页时长在卸载时用 `sendBeacon` 补发。
- **追问预判**：「时间差法错在哪？」答切后台时间全被计入，时长虚高一个量级；「`unload` 事件可靠吗？」答 iOS 上不触发，用 `pagehide` + `visibilitychange`。
- **评分点**：60 分 = 路由拦截出 pageview；80 分 = 心跳累计 + 可见性暂停；100 分 = 补齐末页补发与 iOS 兼容性边界。
- **深入阅读**：[69.1 埋点全景与事件模型](./69-frontend-tracking.md#_69-1-埋点全景与事件模型)

#### Q5 埋点怎么做隐私合规？用户点「同意」之前的数据怎么处理？

- **考点**：合规红线意识，政企客户的硬性要求。
- **答题框架**：① 「告知-同意」是采集前置条件，弹窗前 SDK 默认挂起——`track` 只入队不上报 ② 同意则开闸补发，拒绝则清空队列 + 持久化拒绝标记 + 永久关闭 ③ 敏感字段（手机号、token）在 SDK 管道统一脱敏，白名单评审制 ④ 不采集原则优先于脱敏。
- **追问预判**：「挂起期间队列满了呢？」答合规期数据宁可丢——这是红线不是技术问题。
- **评分点**：60 分 = 知道要先同意后采集；80 分 = 讲出挂起/开闸/永久关闭三态；100 分 = 主动提应用市场审核抓包检测与字段白名单制度。

### 第二组 桌面端工程（Q6~Q9，对应第 70 册）

> 备考提示：Q6 选型题几乎必问，回答时务必落到「本团队约束」而非泛泛对比。

#### Q6 Electron 和 Tauri 怎么选？

- **考点**：技术选型方法论，几乎必问。
- **答题框架**：① 包体与内存：Tauri 复用系统 WebView，包体从 ~180MB 降到 ~10MB 级，内存显著更低 ② 生态与成熟度：Electron 生态厚（VS Code/飞书验证过），Node API 直用；Tauri 生态年轻 ③ 团队结构：Tauri 的 Rust 侧需要 Rust 能力 ④ 系统 WebView 碎片化是 Tauri 最大隐性成本（Linux WebKitGTK 差异大）⑤ 结论：重 Node 生态/老项目选 Electron，新政企项目且对包体内存敏感选 Tauri。
- **追问预判**：「Tauri 的系统 WebView 不一致怎么办？」答 CSS/JS 兼容测试矩阵 + 能力检测降级，复用第 60 册的防御体系。
- **评分点**：60 分 = 说出「Tauri 用系统 WebView 所以小」；80 分 = 给出四维度对比并落到本团队约束；100 分 = 主动指出 WebView 碎片化成本与「包体小 ≠ 兼容省心」的取舍。
- **深入阅读**：[70.1 桌面端形态坐标](./70-desktop-app-tauri.md#_70-1-桌面端形态坐标-electron-tauri-cef-webview2-选型矩阵)

#### Q7 Tauri 的 IPC 安全模型了解吗？能力清单和 CSP 怎么配？

- **考点**：桌面端特有的攻击面认知。
- **答题框架**：① 前端调 Rust 走 `invoke`/command，command 是唯一受控入口 ② 能力清单（capabilities/allowlist）按窗口最小授权，文件系统、shell、HTTP 默认全关 ③ CSP 收紧 `script-src` 防 XSS 升级为 RCE——Web 端 XSS 只是弹窗，桌面端 XSS 可经 IPC 触达系统能力 ④ 深链与外部 URL 打开要过白名单校验。
- **追问预判**：「为什么桌面端 XSS 更危险？」答 IPC 桥把渲染进程漏洞放大成系统级 RCE。
- **评分点**：60 分 = 知道 command 桥；80 分 = 讲出最小授权与 XSS→RCE 升级链；100 分 = 补齐深链攻击面与 CSP 具体指令。
- **深入阅读**：[70.3 IPC 安全模型](./70-desktop-app-tauri.md#_70-3-ipc-安全模型-能力清单、csp-与深链攻击面)

#### Q8 桌面端自动更新怎么设计？签名、灰度、回滚怎么落地？

- **考点**：发布工程能力，企业分发场景的核心痛点。
- **答题框架**：① 更新清单（版本号 + 下载地址 + 哈希 + 签名）与安装包分离下发 ② 签名校验通过才允许安装，防供应链替换 ③ 灰度按用户/设备哈希分批放量，崩溃率阈值自动暂停 ④ 回滚保留上一版本安装包或支持版本钉住 ⑤ 政企内网环境走内网分发服务器，不依赖公网 CDN。
- **追问预判**：「差量更新要不要做？」答看包体——Tauri 包体小可全量，Electron 值得差量，但要处理增量校验失败的原子回滚。
- **评分点**：60 分 = 知道检查更新流程；80 分 = 讲出签名 + 灰度 + 回滚三件套；100 分 = 提到内网分发与更新状态机（下载中/待安装/失败回滚）。
- **深入阅读**：[70.4 自动更新与发布](./70-desktop-app-tauri.md#_70-4-自动更新与发布-签名、灰度、回滚与内网分发)

#### Q9 Web 端和桌面端代码怎么共用？差异能力怎么收口？

- **考点**：跨端架构意识，与 73 册互为表里。
- **答题框架**：① 业务层（页面、组件、状态）100% 共用 ② 差异能力（文件对话框、托盘、全局快捷键）抽象成「能力接口 + 端实现」的能力层 ③ 运行时探测当前端，注入对应实现 ④ 埋点与监控也要走同一套 SDK，仅公共参数里端标识不同。
- **追问预判**：「直接 `if (isTauri)` 散落各处行不行？」答三个月后就不可维护——差异必须收口到能力层。
- **评分点**：60 分 = 说出「业务共用、能力分端」；80 分 = 讲出能力抽象层 + 依赖注入；100 分 = 补上可观测性口径统一与依赖方向规则。
- **深入阅读**：[70.6 与 Web 端共用代码与可观测性](./70-desktop-app-tauri.md#_70-6-与-web-端共用代码与可观测性)

### 第三组 数据权限（Q10~Q13，对应第 72 册）

> 备考提示：本组的核心心法只有一句——「安全边界在服务端，前端管体验与配置」，四道题都是它的展开。

#### Q10 行级数据权限的前后端分工边界在哪？

- **考点**：权限体系的架构分层，最容易答跑偏的题。
- **答题框架**：① **边界结论先行**：行级过滤必须在服务端查询层完成，前端永不持有越权数据 ② 前端职责三件套：数据范围 DSL 的展示与配置 UI、按范围声明请求参数、无数据态的体面降级 ③ 服务端职责：DSL 解析 → 编译期越权校验 → 注入查询条件 ④ 前端做过滤只是体验优化（如列表禁用态），不是安全边界。
- **追问预判**：「前端过滤一遍省请求行不行？」答不行——接口抓包即越权，安全边界在服务端。
- **评分点**：60 分 = 知道前后端都要做权限；80 分 = 讲清「安全在服务端、体验在前端」的分工；100 分 = 说出 DSL 编译期校验与「前端永不持有越权数据」原则。
- **深入阅读**：[72.3 行级数据权限](./72-org-hierarchy-permission.md#_72-3-行级数据权限-数据范围-dsl-与查询注入)

#### Q11 一人多岗、部门树调整时，数据可见范围怎么推导？

- **考点**：组织模型理解力，B 端业务的核心复杂度。
- **答题框架**：① 部门树用物化路径建模，子孙集查询退化为前缀匹配 ② 四种范围语义：仅本人 / 本级 / 本级及下级 / 指定部门集合 ③ 一人多岗取**并集**，岗位撤销后范围即时收敛 ④ 部门树调整（拖拽/合并）触发范围重算与缓存失效。
- **追问预判**：「并集会不会越权放大？」答会，所以敏感岗要支持「按岗切换上下文」而非永久并集——能讲出这层就是加分。
- **评分点**：60 分 = 说出四种范围；80 分 = 讲清多岗并集与物化路径；100 分 = 主动分析并集放大的风险与收敛手段。
- **深入阅读**：[72.1 企业组织模型](./72-org-hierarchy-permission.md#_72-1-企业组织模型-部门树、岗位、编制与一人多岗) · [72.2 层级可见范围推导](./72-org-hierarchy-permission.md#_72-2-层级可见范围推导-本级、下级与指定范围)

#### Q12 列级/字段级管控怎么做？脱敏在前端还是后端？

- **考点**：字段级安全的工程实现。
- **答题框架**：① 列可见性用白名单模型——默认不可见，授权才下发字段 ② 脱敏在**服务端出口**做（如手机号 `138****1234`），前端拿到即脱敏态 ③ 前端职责：按字段权限渲染列、脱敏态不参与复制导出 ④ 导出/打印等旁路通道必须走同一套字段权限，否则列级管控形同虚设。
- **追问预判**：「前端脱敏有什么问题？」答接口返回原文，F12 即泄密——脱敏是数据出口问题不是渲染问题。
- **评分点**：60 分 = 知道列权限概念；80 分 = 讲清服务端出口脱敏 + 白名单模型；100 分 = 补上导出/打印旁路通道的管控。
- **深入阅读**：[72.4 列级与字段级管控](./72-org-hierarchy-permission.md#_72-4-列级与字段级管控-白名单与脱敏)

#### Q13 权限变更后，前端缓存的权限数据怎么保证一致？

- **考点**：缓存失效策略，权限系统最高频的线上事故源。
- **答题框架**：① 权限版本号/etag：响应头携带，前端比对不一致则整量刷新 ② 主动推送：权限变更事件经 WebSocket/轮询下达到端 ③ 写操作前服务端强制校验，前端缓存永远只是「乐观展示」④ 本地缓存 TTL 兜底，超过时限强制回源。
- **追问预判**：「只靠 TTL 行不行？」答权限是安全数据，收权必须即时生效——TTL 只能做兜底不能做主策略。
- **评分点**：60 分 = 提到缓存要失效；80 分 = 讲出版本号比对 + 事件推送双通道；100 分 = 点破「收权即时、授权可延迟」的不对称要求。
- **深入阅读**：[72.5 权限变更与一致性](./72-org-hierarchy-permission.md#_72-5-权限变更与一致性-缓存失效与增量推送)

### 第四组 多端架构（Q14~Q17，对应第 73 册）

> 备考提示：多端题的回答都要收尾到量化口径（复用率、新端接入成本），否则只是架构图背诵。

#### Q14 Web、PC、H5 三端共用一套代码，架构怎么分层？

- **考点**：分层架构与依赖规则，多端题的总纲。
- **答题框架**：① 四层：领域层（业务模型/逻辑，纯 TS 零端依赖）→ 应用层（用例/状态编排）→ 适配层（端能力抽象）→ 视图层（端相关组件）② 依赖规则：只允许上层依赖下层，领域层永不 import 端 API ③ 端入口做组装：注入对应端的能力实现 ④ 收益量化：三端业务代码复用率、新端接入成本。
- **追问预判**：「组件库要不要分端？」答基础组件共用 + 端差异组件走适配层插槽，不维护两套。
- **评分点**：60 分 = 说出分层概念；80 分 = 讲出四层模型与依赖方向规则；100 分 = 给出复用率量化口径与新端接入的验收标准。
- **深入阅读**：[73.2 分层架构与依赖规则](./73-multi-end-architecture.md#_73-2-分层架构与依赖规则)

#### Q15 端能力差异（摄像头、推送、文件系统）怎么抽象？

- **考点**：能力抽象层设计，多端架构的核心手法。
- **答题框架**：① 定义端无关的能力接口（如 `pickImage`、`notify`、`readFile`）② 每端一个实现包，接口签名与错误模型统一 ③ 运行时探测 + 依赖注入选定实现 ④ 能力缺失要有降级语义：接口返回「不支持」而非让业务 try/catch 崩溃 ⑤ 新增能力的流程：先补接口契约，再各端实现。
- **追问预判**：「各端能力参数不一致怎么办？」答接口取各端参数交集，端特有参数走 `extra` 透传字段但默认禁用。
- **评分点**：60 分 = 知道接口抽象；80 分 = 讲出统一错误模型与降级语义；100 分 = 补上「契约先行」的新增能力流程与 `extra` 取舍。
- **深入阅读**：[73.3 端能力抽象层设计](./73-multi-end-architecture.md#_73-3-端能力抽象层设计)

#### Q16 多端构建怎么做条件编译与产物矩阵？

- **考点**：构建工程化，「一套代码」到「N 个产物」的通路。
- **答题框架**：① 构建矩阵：端 × 环境（dev/staging/prod）× 渠道，用矩阵配置驱动而非手工脚本 ② 条件编译三手段：环境变量分支（粗粒度）、构建别名替换模块（中粒度）、`import.meta.glob` 按端收编（细粒度）③ 产物命名与版本号含端标识，可观测性数据据此分流 ④ CI 并行出包 + 产物体积门禁。
- **追问预判**：「运行时判断和编译期判断怎么选？」答能力探测用运行时，代码裁剪用编译期——编译期砍掉的代码不进包体。
- **评分点**：60 分 = 知道环境变量分端；80 分 = 讲出三手段的粒度差异；100 分 = 给出矩阵驱动 + 产物门禁的完整流水线。
- **深入阅读**：[73.4 构建矩阵与条件编译](./73-multi-end-architecture.md#_73-4-构建矩阵与条件编译)

#### Q17 怎么保证多端行为一致？测试策略是什么？

- **考点**：多端质量保障体系。
- **答题框架**：① 契约测试：能力层接口对每端实现跑同一套用例，行为漂移在 CI 拦截 ② 领域层纯 TS，单测零成本覆盖 ③ 视图层用截图/快照比对做视觉回归 ④ 端到端用同一套业务脚本驱动各端 runner（Playwright/WebdriverIO）⑤ 线上用埋点漏斗对比各端转化率，行为差异会自己浮出来。
- **追问预判**：「三端 UI 必须像素一致吗？」答不一致——一致性指**业务行为与数据口径**一致，视觉遵循各端平台规范。
- **评分点**：60 分 = 提到各端分别测试；80 分 = 讲出契约测试共享用例；100 分 = 补上「一致性」的准确定义与线上漏斗对账。

### 第五组 性能与兼容（Q18~Q20，对应第 71/60/74 册）

> 备考提示：Q18 是「Rust 优先」的正确打开方式——展示克制比展示热情更得分。

#### Q18 什么场景该引入 Rust/WASM？边界成本怎么算？

- **考点**：对「Rust 优先」这条 JD 的正确回应——考的不是热情是克制。
- **答题框架**：① 适用象限：CPU 密集 + 大数据量 + 算法可复用（大文件解析、加解密、压缩、文档渲染）② 边界成本：JS↔WASM 每次调用的序列化/拷贝开销，频繁小调用会把收益吃光 ③ 判定方法：先 profiling 确认热点，再做基准对比（纯 JS vs WASM）④ 工程成本：工具链、调试体验、CI 缓存都要计入 ⑤ 结论话术：「JD 写 Rust 优先，我理解是希望在端能力层有 Rust 判断力，而不是全量重写」。
- **追问预判**：「WASM 一定比 JS 快吗？」答不一定——边界开销与 JIT 优化的存在，让小任务 WASM 反而慢，必须基准验证。
- **评分点**：60 分 = 知道 WASM 适合计算密集；80 分 = 讲出边界成本与基准方法论；100 分 = 给出「先 profiling 后迁移」的决策流程并主动谈工程成本。
- **深入阅读**：[71.1 为什么前端要引入 Rust](./71-rust-wasm.md#_71-1-为什么前端要引入-rust-性能边界与适用象限) · [71.3 JS 与 WASM 的边界成本](./71-rust-wasm.md#_71-3-js-与-wasm-的边界成本-调用开销与数据搬运)

#### Q19 信创环境（国产 OS/浏览器）的前端适配怎么做？

- **考点**：政企合规场景的兼容性生存技能。
- **答题框架**：① 信创栈认知：麒麟/统信 OS + 国产 CPU + 基于 Chromium 的国产双核浏览器 ② 内核锁定：meta 标签指定 WebKit/Blink 内核，避免兼容模式掉进 IE 内核 ③ 防御三层：caniuse 契约层 + 构建转译垫片层 + 运行时特性检测降级层 ④ 国密改造：SM2/SM4 在端上的加解密走 WASM 或服务端 BFF，密钥不出服务端 ⑤ 私有化管理：依赖、字体、更新包全部内网可分发。
- **追问预判**：「国产浏览器和 Chrome 一样吗？」答内核版本普遍滞后数年，新 API 必须特性检测后降级。
- **评分点**：60 分 = 知道信创概念；80 分 = 讲出内核锁定 + 防御三层；100 分 = 补上国密改造的分工边界（端上 WASM vs 服务端）。
- **深入阅读**：[60.4 国产浏览器与 WebView 生存指南](./60-browser-compatibility.md#_60-4-国产浏览器与-webview-生存指南) · [第七十四部分 · 信创与国密合规](./74-xinchuang-guomi.md)

#### Q20 办公产品的大数据量场景（万人通讯录、十万条消息）性能怎么优化？

- **考点**：性能优化的组合拳，「性能优化」双板块命中的落点。
- **答题框架**：① 先测量：Performance 面板定位瓶颈在渲染、计算还是网络 ② 渲染层：虚拟滚动（定高/动态行高双算法）、分页 + 游标、时间分片渲染 ③ 计算层：搜索索引前置构建、Web Worker 搬离主线程、热点算法评估 WASM ④ 数据层：增量同步 + 本地缓存（IndexedDB）、接口聚合减少瀑布 ⑤ 组织树特殊优化：懒加载 + 物化路径本地推导 + 选中态与加载态分离。
- **追问预判**：「虚拟滚动行高不固定怎么办？」答动态行高双算法：预估高度 + 已渲染实测回填，滚动锚定防跳动。
- **评分点**：60 分 = 说出虚拟滚动；80 分 = 给出渲染/计算/数据三层组合拳；100 分 = 强调「先测量后优化」并给出量化目标（如长列表滚动帧率 ≥ 55fps）。
- **深入阅读**：[71.4 性能工程与体积优化](./71-rust-wasm.md#_71-4-性能工程与体积优化-基准方法学与编译开关) · [64 复杂可编辑表格（虚拟滚动双算法）](./64-editable-table.md)

## 76.3 STAR 项目叙事三模板：把经历讲成战力

STAR（情境 Situation → 任务 Task → 行动 Action → 结果 Result）不是话术模板，是**证据链结构**：情境证明问题真实，任务证明责任在你，行动证明方法专业，结果证明价值可量化。三个模板覆盖本岗位 JD 权重最高的三条主线，使用规则：**数字换成你的真实数据，讲不出的细节就删掉那一行**——面试官追问的方向永远是你语气最虚的地方。

**反面教材**：「我们团队做了一套埋点系统，用了主流技术栈，效果挺好的，领导很满意」——一句话踩四个坑：无个人边界（「我们团队」）、无技术细节（「主流技术栈」）、无量化（「挺好」）、无验证手段（「领导满意」）。STAR 的价值就是把这句话改写成四个可被追问、且追问后你都有话可讲的事实。

### 模板一 埋点体系从 0 到 1

| 要素 | 叙事要点 |
| --- | --- |
| **情境** | 产品迭代全靠拍脑袋，需求上线后无人知道有没有人用；历史埋点是各页面随手调第三方 SDK，事件命名混乱、数据对不上后端报表 |
| **任务** | 三个月内建立完整埋点体系：统一 SDK、统一规范、数据准确率可度量，支撑核心漏斗分析 |
| **行动** | ① 封装埋点 SDK 内核：批量队列、失败重试、`event_id` 幂等、卸载兜底（69.2） ② 建 schema 注册表，装载期强制校验，未注册事件进不了代码库（69.5） ③ 制定命名与属性规范，组织评审宣贯 ④ 与后端约定对账机制，每周比对业务表与埋点报表 |
| **结果** | 核心流程埋点覆盖率从约 30% 提升到 95%+；与后端对账差异率控制在 0.5% 以内；基于漏斗数据定位两个转化断点，改版后注册转化率提升 X% |

**可量化指标清单**（至少记住 3 个，宁少勿假）：埋点覆盖率、对账差异率、事件 schema 注册数、废弃事件清理数、上报量采样后降幅、数据需求平均交付周期。

**面试官想听到的细节**：先幂等再重试的因果顺序；「规范不代码化等于没有」的落地手段；对账是**和后端对**而非自说自话；采样用稳定哈希而非 `Math.random()`。

### 模板二 PC 桌面端重构

| 要素 | 叙事要点 |
| --- | --- |
| **情境** | 存量 Electron 客户端包体超 180MB、常驻内存 800MB+，政企客户投诉密集；全量更新每次发版消耗大量带宽，内网客户升级靠人工 |
| **任务** | 在不中断业务迭代的前提下完成桌面端架构升级，包体、内存、更新体验三线达标 |
| **行动** | ① 选型评估 Electron 优化 vs Tauri 迁移，用四维度矩阵（包体/内存/生态/团队）决策（70.1） ② 绞杀者模式渐进迁移：新模块走新架构，老模块逐一切流 ③ 差异能力收口到能力抽象层，业务代码与 Web 端共用（70.6） ④ 重建更新体系：签名清单 + 哈希灰度 + 崩溃率自动暂停（70.4） |
| **结果** | 安装包从 180MB 降至 25MB（-86%）；冷启动从 4.2s 降至 2.5s（-40%）；常驻内存降 50%+；灰度发布使更新故障工单下降 X% |

**可量化指标清单**：包体、冷启动耗时、常驻内存、崩溃率、更新成功率、灰度放量批次、迁移期间业务需求交付数（证明「不中断」不是口号）。

**面试官想听到的细节**：为什么不是「全量重写」（绞杀者模式与风险控制）；能力抽象层如何设计接口与降级语义；更新故障时的回滚预案；迁移期间如何与业务排期共存。

### 模板三 权限体系升级

| 要素 | 叙事要点 |
| --- | --- |
| **情境** | 政企大客户审计时发现越权访问案例：权限校验散落在各页面的 `if` 角色判断里，一人多岗、部门调整时权限不收敛，客户安全部门要求限期整改 |
| **任务** | 用一个季度把权限体系从「硬编码角色判断」升级为「分层分级数据权限」，支撑组织树变动与多岗场景，通过客户安全审计 |
| **行动** | ① 与后端对齐分工：行级过滤收归服务端查询注入，前端负责数据范围 DSL 的配置与展示（72.3） ② 组织树物化路径建模，四种可见范围语义 + 多岗并集（72.1/72.2） ③ 列级管控白名单化，脱敏收敛到服务端出口（72.4） ④ 权限版本号 + 事件推送双通道保证收权即时生效（72.5） ⑤ 配置中心支持权限预演：变更前可预览影响面（72.6） |
| **结果** | 越权类工单归零并通过客户安全复审计；权限配置从「改代码发版」变为「管理员自助配置」，平均生效时间从 3 天缩到 10 分钟；权限相关线上事故季度环比下降 X% |

**可量化指标清单**：越权工单数、权限配置化率（无需发版的变更占比）、权限生效时长、审计发现项数、收权生效延迟（秒级/分钟级）。

**面试官想听到的细节**：「前端永不持有越权数据」的边界原则；多岗并集的风险与「按岗切换上下文」的收敛设计；收权与授权的不对称时效要求；预演功能如何避免配置事故。

## 76.4 简历关键词映射与反问清单

### 概念解析

简历的唯一读者旅程是：**HR 用关键词筛 → 面试官用关键词问**。简历上的每个关键词都必须能向下钻三层：项目产出 → 量化指标 → 技术细节。只写关键词没有产出是「堆砌名词」，写了产出没有指标是「无法验证」，有了指标讲不出细节是「疑似包装」——三种死法见 76.6。

### 应用实践：JD 关键词三列映射表

以 76.1 的权重表为输入，逐词准备「关键词 → 项目产出 → 量化指标」的证据链：

| JD 关键词 | 项目产出（简历写法） | 量化指标 |
| --- | --- | --- |
| 埋点体系 | 自研埋点 SDK 与 schema 注册表，落地装载期校验与后端对账 | 核心流程覆盖率 95%+，对账差异 < 0.5% |
| Electron/Tauri | 主导桌面端 Tauri 迁移，能力抽象层收口端差异 | 包体 -86%，冷启动 -40%，内存 -50% |
| Rust 优先 | 大文件解析模块迁移 WASM，建立基准验证流程 | 解析耗时从 12s 降至 1.5s（8 倍） |
| 分层分级权限 | 落地数据范围 DSL 配置中心与行列级管控 | 越权工单归零，权限生效 3 天 → 10 分钟 |
| 多端架构 | 设计四层架构与能力抽象层，一套代码出三端 | 业务代码复用率 70%+，新端接入 2 周 |
| Vue/React | 复杂状态管理重构 / 组件库封装 | 核心页面渲染耗时 -35%，组件复用率 X% |
| 3 年+ / 协同办公 | 协作产品核心模块 owner 经历 | 负责模块 DAU、迭代频次、跨团队项目数 |
| 性能优化 | 万人通讯录虚拟滚动与 Worker 索引 | 长列表滚动 ≥ 55fps，搜索响应 < 100ms |
| 信创/国密 | 麒麟/统信环境适配与国产浏览器内核锁定 | 信创客户交付 N 家，兼容缺陷收敛 X 个 |

**使用规则**：没有真实数据的行**不要上简历**——改成「了解 XXX，完成过技术验证 demo」是诚实的降级写法，面试时反而赢得信任。

### 最佳实践：反问面试官的八个问题

反问不是客套，是**用专业问题完成双向尽调**——既判断团队水平，也展示你的关注点层次：

1. **团队分工**：「前端团队目前怎么分工？这个岗位入职后前三个月的落地目标是什么？」——判断岗位是开拓还是填坑。
2. **Rust 占比**：「JD 提到 Rust 优先，目前 Rust 在代码库的占比大概多少？是 WASM 方向还是 Tauri 端能力方向？」——一句话证明你读过 JD 且懂 71 册的两条路线之分。
3. **埋点自研还是神策**：「埋点体系是自研还是基于神策/友盟二次开发？数据准确率现状和目标是多少？」——决定你 69 册知识的用法是建设还是集成。
4. **权限现状**：「分层分级权限是从零建设还是改造存量？现在最大的痛点是模型还是一致性？」——判断模板三能讲几分。
5. **多端策略**：「多端是一套代码条件编译，还是各端独立迭代？为什么这样选？」——展示你关心取舍而非结论。
6. **信创要求**：「产品有信创/国密的合规要求吗？涉及哪些客户环境？」——政企客户的必答题，提前暴露适配工作量。
7. **发布节奏**：「发版节奏和灰度机制是怎样的？桌面端更新出问题怎么回滚？」——判断工程成熟度。
8. **价值衡量**：「团队怎么衡量前端工作的业务价值？有没有数据驱动的实例？」——把话题引向你准备好的埋点叙事。

**避雷**：首轮技术面别问薪资福利与加班强度（留给 HR 轮）；别问百度能答的问题（公司产品、融资轮次）；别问抬杠式问题（「你们为什么不用 React」）。

**面试后复盘清单**（结束后 15 分钟内完成，趁热才记得住）：

1. 记录所有没答好的题，按 76.2 的五段式补齐「答题框架 + 评分点」，沉淀回自己的题库；
2. 标记面试官追问最深的三个点——那就是下一场面试的重点准备区；
3. 更新示例 76-01 的关键词词典：本场新出现的高频词补进去，权重表会随面试场次越练越准；
4. 复盘反问环节：对方的回答暴露了什么团队信息，是否改变你的意向排序。

## 76.5 自测题

<details>
<summary><b>1. 【基础】STAR 四要素分别是什么？为什么「结果」必须量化？</b></summary>

**答案**：情境（Situation）、任务（Task）、行动（Action）、结果（Result）。结果量化是因为面试官无法用形容词验证真伪——「效果很好」无法追问，「对账差异率从 3% 降到 0.5%」天然引出「怎么算的、怎么对的账」的专业追问，而追问正是你展示细节储备的机会。量化的另一层作用是建立可信度锚点：一个经得起追问的数字，会让面试官默认你其他的表述也可信。

</details>

<details>
<summary><b>2. 【基础】JD 拆解时，为什么「加分项」不能当作可有可无？</b></summary>

**答案**：硬性要求决定「过不过」，加分项决定「定什么级」。候选人通过硬筛选后彼此拉不开差距，加分项（本 JD 中是 Rust/WASM/信创/开源）是区分度来源——面试官用它们判断你的技术半径与自驱力。准备策略与硬性要求不同：加分项不要求能干活，只要求能讲清「是什么、为什么、边界在哪」，投入产出比极高，每个词花两小时读对应分册的概念解析即可达标。

</details>

<details>
<summary><b>3. 【基础】回答技术选型题（如「Electron 和 Tauri 怎么选」）的标准结构是什么？</b></summary>

**答案**：四步：① 先给决策维度（包体/内存/生态/团队结构），证明你有框架而不是记答案 ② 逐维对比双方表现 ③ 落到具体约束给结论——「在我们的政企内网 + 包体敏感场景下选 Tauri」 ④ 主动补一个反方风险（Tauri 的系统 WebView 碎片化成本），证明结论经过权衡。只背对比表不给结论，或给了结论说不出适用边界，都只能拿 60 分。

</details>

<details>
<summary><b>4. 【进阶】为什么「先幂等再重试」这类因果顺序比罗列知识点更得分？</b></summary>

**答案**：罗列知识点证明「看过」，因果顺序证明「想过」。「先幂等再重试」压缩了一个完整推理：重试必然产生重复投递 → 重复无害的前提是幂等 → 所以幂等是重试的前置设计而非事后补丁。面试官通过这个顺序确认你理解系统的失败模式，而不是背了面试题。自查方法：每个技术点问自己「不做它会出什么问题」，能答出失败后果的知识才是真储备——这正是 69 册避坑清单的训练目标。

</details>

<details>
<summary><b>5. 【进阶】面试官追问「你们为什么自研埋点而不用神策」时，怎么答才不踩坑？</b></summary>

**答案**：切忌贬低第三方（「神策不好用」会暴露视野窄），正确结构是承认价值 + 给出约束：① 先认可神策在采集与分析侧的成熟度 ② 给出自研的真实约束——政企私有化部署禁止数据出内网 / 采购成本 / 需要与自研权限体系深度联动（事件级数据权限）③ 说明边界：分析侧仍考虑对接，自研的只是采集与治理层。这同时预埋了一个加分点——你知道「自研 vs 采购」的决策维度，而非技术原教旨主义。参考 69.4 的集成与二次开发模式。

</details>

<details>
<summary><b>6. 【进阶】简历写「负责权限体系重构」却没有量化指标，面试时会出现什么问题？怎么补救？</b></summary>

**答案**：问题是面试官失去追问抓手，只能用「你具体做了什么」从头审问，节奏完全被动；且无量化成果易被怀疑是挂名参与。补救三条路：① 回测数据——翻发布记录、工单系统、监控看板找改造前后的对比（越权工单数、权限相关发版次数、配置生效时长）② 换可验证的口径——「支撑 X 个部门 Y 个角色的迁移」「配置化率从 0 到 80%」这类结构性数字同样有效 ③ 实在没有数字就降级表述为「参与权限体系重构，负责数据范围 DSL 配置模块」，把光环换成可信度。

</details>

<details>
<summary><b>7. 【挑战】设计一个 90 秒的自我介绍，把埋点、桌面端、权限三段经历串成一条主线。</b></summary>

**答案**：主线必须是一条「能力进化弧」而不是三段流水账。示范骨架：① 15 秒定位——「三年企业级前端，主线是做数据驱动的基础设施」② 60 秒三段递进：埋点体系（0→1，学会**建规范并让规范自动生效**，给覆盖率与对账数字）→ 桌面端重构（学会**在约束下做取舍**，给包体/内存数字）→ 权限体系（学会**把安全边界翻译成工程分工**，给越权工单与生效时长数字）③ 15 秒收口：「三段经历的共性是把模糊的业务要求变成可度量、可落地的工程体系——这和贵司岗位 JD 里埋点、桌面端、分层分级三条线完全重合」。检验标准：每段都有数字，段与段之间有「学会了什么」的递进连接词。

</details>

<details>
<summary><b>8. 【挑战】被问到完全不会的问题（如「讲讲 Rust 的 Pin 类型」）时，设计一套不失分的应对话术，并说明为什么不能硬编。</b></summary>

**答案**：话术三段式：① 坦诚定界——「Pin 我没有深入研究过，我的 Rust 实践集中在 WASM 计算模块的边界优化上」 ② 关联已知——「我理解 Pin 解决的是自引用结构的移动安全问题，和我处理过的 JS↔WASM 内存所有权问题类似，都是『谁对这块内存负责』的问题」 ③ 给出学习路径——「如果要深入，我会从所有权与生命周期入手补这块」。不能硬编的原因：面试官追问能力必然强于你的编造能力，一个被戳穿的谎言会污染全部已答内容的可信度——面试的本质是可信度博弈，承认边界的候选人反而被标记为「可靠、可带」。定界话术的关键是**给出你真实的边界在哪**，而不是一句「不会」终结话题。

</details>
