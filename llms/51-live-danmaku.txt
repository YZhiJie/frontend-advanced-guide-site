## 51.1 直播链路全景与前端职责

### 概念解析

一场直播的技术链路可以拆成五段，前端主要接管后三段：

| 链路 | 关键角色 | 协议/技术 | 前端职责 |
| --- | --- | --- | --- |
| 采集 | 主播端 | 摄像头/麦克风、编码器 | 开播端预览、码率设置（如做主播端） |
| 推流 | 主播端 → 推流服务 | RTMP / SRT / WebRTC | 通常由原生或 SDK 完成 |
| 分发 | CDN / 边缘节点 | HLS / FLV / WebRTC | 选择播放协议、降级策略 |
| 拉流播放 | 观众端 | `<video>` + MSE / FLV.js / WebRTC | 起播、卡顿恢复、清晰度切换 |
| 实时互动 | 观众端 ↔ 业务服务 | WebSocket / SSE / HTTP | 弹幕、礼物、点赞、购物车、连麦信令 |

**播放协议怎么选**：

- HLS：兼容性最好，延迟通常 5~30 秒，适合不强调互动的场景；
- HTTP-FLV：延迟 1~3 秒，依赖 flv.js 与 MSE，适合大多数直播电商；
- WebRTC：延迟 < 1 秒，适合连麦、拍卖、强互动，但成本和复杂度最高。

**前端的核心职责不是「播放视频」，而是三件事**：

1. 让播放器在弱网下可恢复（卡顿检测、重试、降码率）；
2. 让互动消息「按可读速率」呈现（弹幕调度、礼物动画、点赞节流）；
3. 让交易状态与直播状态一致（商品上下架、库存、购物车、下单）。

### 典型应用场景

- 直播电商：直播间 + 商品卡 + 购物车 + 秒杀；
- 秀场/游戏直播：弹幕、礼物、排行榜、连麦；
- 教育直播：白板、举手、答题、回放；
- 企业直播：低延迟、权限、录制回放。

### 可运行代码示例

先把「消息 → 可渲染批次」的调度逻辑独立出来，才能在浏览器里用 `requestAnimationFrame` 驱动、在 Node 里用假时钟测试。示例 51-01 就是这个调度器。

```typescript
// 文件: examples/51-01-danmaku-scheduler.ts（核心节选）
frame(): Danmaku[] {
  this.queue.sort((a, b) => a.priority - b.priority || a.ts - b.ts);
  const batch = this.queue.splice(0, this.maxPerFrame);
  this.rendered.push(...batch);
  return batch;
}
```

> 运行方式：`npx tsx examples/51-01-danmaku-scheduler.ts`（礼物优先、聊天不被饿死、背压丢弃、峰值控制）。

### 最佳实践

- ✅ 播放与互动解耦：播放器卡顿不应阻塞弹幕，弹幕积压也不应拖慢播放；
- ✅ 协议选型写进产品需求：延迟目标决定 HLS/FLV/WebRTC，不要上线后再改；
- ⚠️ 移动端自动播放有策略限制，需 `muted` + 用户手势解锁；
- ❌ 不要在前端做「消息全量保序 + 全量渲染」——直播间消息量级不允许。

## 51.2 弹幕消息系统设计

### 概念解析

一条弹幕从发送到上屏，要经过「接入 → 校验 → 扩散 → 下发 → 调度 → 渲染」六步。前端能控制的是后三步，但必须理解前三步的语义，否则会出现「消息重复」「顺序错乱」「刷屏」。

**消息模型**至少包含：

| 字段 | 作用 | 注意事项 |
| --- | --- | --- |
| `id` | 幂等去重 | 服务端生成，重连补发时不变 |
| `roomId` | 房间隔离 | 切换房间要清空本地队列 |
| `userId` | 限流与展示 | 不要直接暴露敏感信息 |
| `seq` | 顺序与断点续传 | 单调递增，重连时带上最后 seq |
| `type` | 弹幕/礼物/系统/管控 | 不同类型走不同渲染通道 |
| `ts` | 排序与限流窗口 | 以服务端时间为准，客户端只做相对判断 |

**写扩散 vs 读扩散**（详见第 39 章）：弹幕房间人数多、消息生命周期短，通常用「读扩散 + 房间广播」；礼物/大额交易才需要写扩散保证可靠。

**四类治理手段**：

1. 幂等：按 `id` 去重，处理重连补发与多端同步；
2. 限流：按用户 + 时间窗限制发送频率，服务端为准，前端做预检；
3. 合并：连续相同文本合并计数，减少无意义渲染；
4. 审核：敏感词/风控在服务端完成，前端只展示「已拦截」状态。

### 典型应用场景

- 高人气直播间：消息速率数万条/秒，必须抽样/聚合展示；
- 礼物连击：同一用户短时间重复送礼，合并为「×N」；
- 断线重连：带 `lastSeq` 拉取增量，避免整屏丢失；
- 房管/禁言：管控消息优先于普通弹幕，且要即时生效。

### 可运行代码示例

示例 51-02 把幂等、限流、合并做成一条管线，并明确「限流不吞消息 id」——被限流的消息允许用户稍后重试。

```typescript
// 文件: examples/51-02-chat-pipeline.ts（核心节选）
accept(msg: ChatMessage): Result {
  if (this.seen.has(msg.id)) return { status: "duplicate" };

  const bucket = (this.windows.get(msg.userId) ?? []).filter(
    (t) => msg.ts - t < this.windowMs,
  );
  if (bucket.length >= this.maxPerWindow) {
    const retryAfter = this.windowMs - (msg.ts - bucket[0]);
    this.windows.set(msg.userId, bucket);
    return { status: "rate-limited", retryAfter };
  }
  bucket.push(msg.ts);
  this.windows.set(msg.userId, bucket);
  this.seen.add(msg.id);
  // ...合并逻辑
}
```

> 运行方式：`npx tsx examples/51-02-chat-pipeline.ts`（重连补发去重、单用户限流、重复文本合并、用户隔离）。

### 最佳实践

- ✅ 以服务端 `seq` 为准做增量同步，重连时先拉缺口再恢复实时流；
- ✅ 限流返回 `retryAfter`，前端给出「发送太频繁」而不是静默丢弃；
- ⚠️ 弹幕内容必须做转义/白名单，禁止直接 `innerHTML`；
- ❌ 不要在客户端做「最终审核」——绕过成本极低，审核必须在服务端。

## 51.3 高并发渲染治理

### 概念解析

弹幕卡顿的根因通常不是「消息太多」，而是**每条消息都触发一次布局/绘制**。治理思路是「减少渲染次数、降低单次成本、必要时降级」。

| 手段 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| 批量渲染 | 每帧最多渲染 N 条（如 4~8 条） | 帧率稳定 | 消息延迟增加 |
| 轨道调度 | 预先计算轨道，避免弹幕重叠 | 可读性 | 需要测量文本宽度 |
| transform 动画 | `translate3d` + `will-change` | 走合成层，避免重排 | 层过多会占显存 |
| 虚拟化 | 只保留屏幕内节点 | DOM 数量可控 | 实现复杂度 |
| Canvas 渲染 | 统一绘制到画布 | 万级弹幕可行 | 失去 DOM 可访问性 |
| Worker 解析 | 字节/JSON 解析放 Worker | 主线程不卡 | 通信成本 |
| 降级 | 关闭动画、合并消息、只显示礼物 | 保底可用 | 体验下降 |

**帧预算**是最重要的概念：一帧 16.7ms，渲染弹幕只能占其中一部分。示例 51-01 用「每帧最多 4 条 + 队列上限」把预算固定下来，溢出时丢低优先级旧消息，而不是让队列无限增长。

**CSS 动画 vs JS 动画**：位移动画优先用 CSS `transform` + `animation`，让合成器线程处理；需要动态计算（如轨道避让）时用 `requestAnimationFrame` 更新 `transform`，不要改 `left/top`。

### 典型应用场景

- 万人直播间：消息聚合 + 抽样展示；
- 弹幕雨：Canvas 渲染 + 对象池；
- 礼物特效：动画队列 + 优先级 + 可跳过；
- 低端机降级：检测帧率，自动关闭特效。

### 可运行代码示例

调度器的核心是「队列 + 每帧预算 + 溢出策略」。示例 51-01 还验证了「礼物优先但不饿死聊天」和「溢出时保留礼物」。

```typescript
// 文件: examples/51-01-danmaku-scheduler.ts（核心节选）
private evict(): void {
  let index = -1;
  for (let i = 0; i < this.queue.length; i++) {
    if (index === -1) { index = i; continue; }
    const cur = this.queue[i];
    const best = this.queue[index];
    if (cur.priority > best.priority || (cur.priority === best.priority && cur.ts < best.ts)) {
      index = i;
    }
  }
  if (index >= 0) {
    this.queue.splice(index, 1);
    this.dropped++;
  }
}
```

> 运行方式：`npx tsx examples/51-01-danmaku-scheduler.ts`（每帧 4 条、13 条消息分 4 帧消化、200 条突刺丢弃 150 条）。

### 最佳实践

- ✅ 用 `requestAnimationFrame` 驱动渲染循环，暂停时（页面隐藏）停止消费；
- ✅ 给动画元素加 `contain: layout paint` 或独立合成层，减少重排范围；
- ⚠️ `will-change` 不要滥用，动画结束后移除；
- ❌ 不要在滚动/动画回调里同步读取 `offsetWidth` 等布局属性——会强制同步布局。

## 51.4 互动与交易链路

### 概念解析

直播间的「互动」最终要落到交易，状态一致性比动画更重要：

| 功能 | 核心问题 | 前端策略 |
| --- | --- | --- |
| 点赞 | 高频点击、计数合并 | 本地乐观计数 + 批量上报 + 服务端校正 |
| 礼物 | 连击、余额、动画排队 | 连击合并、余额预扣、失败回滚 |
| 商品卡 | 上下架、库存、优惠 | 版本号/时间戳、失效态明确 |
| 购物车 | 多端同步、价格变化 | 服务端为准、冲突提示 |
| 秒杀 | 瞬时流量、超卖 | 按钮状态机、请求去重、排队反馈 |

**乐观更新 + 回滚**是互动功能的基本模式：先更新 UI 让用户有即时反馈，请求失败再回滚并提示。关键是**每次操作带幂等键**，避免重试造成重复扣款/重复送礼。

**购物车价格计算**与**秒杀按钮状态机**在第 43 章已有完整实现，本章不再重复，重点是把它们放进直播间的「实时状态」里：商品可能在下单瞬间下架，库存可能在你点结算时归零，UI 必须能表达「已失效」而不是只显示 loading。

### 典型应用场景

- 直播间挂车：讲解商品与购物车联动；
- 礼物连击：1 秒内连点 10 次，合并为一次动画 + ×10；
- 点赞雨：本地即时反馈，服务端异步汇总；
- 秒杀：倒计时、按钮禁用、排队、结果轮询。

### 可运行代码示例

点赞/礼物的「合并 + 批量上报」与弹幕调度同构：本地维护计数，定时 flush，失败回滚。下面是一个最小实现，重点看幂等键与回滚。

```typescript
// 文件: src/live/interaction.ts —— 虚拟工程文件
type Op = { key: string; type: "like" | "gift"; amount: number };

class InteractionBuffer {
  private pending = new Map<string, Op>();

  add(op: Op) {
    // 幂等键:同一业务操作重复点击只累计一次
    const prev = this.pending.get(op.key);
    this.pending.set(op.key, {
      ...op,
      amount: (prev?.amount ?? 0) + op.amount,
    });
    renderOptimistic(op);
  }

  async flush() {
    const ops = [...this.pending.values()];
    this.pending.clear();
    try {
      await api.batch(ops);
    } catch (e) {
      ops.forEach(rollback); // 失败回滚,并把错误交给 UI
      throw e;
    }
  }
}
```

> 运行方式：点赞与礼物逻辑需在浏览器/工程内运行；调度与限流可先用 `npx tsx examples/51-01-danmaku-scheduler.ts`、`examples/51-02-chat-pipeline.ts` 验证。

### 最佳实践

- ✅ 所有交易操作带幂等键，重试不会重复扣款；
- ✅ 价格、库存、上下架状态以服务端返回为准，前端只做展示与预校验；
- ⚠️ 乐观更新要有明确回滚路径，不能「失败了当没发生」；
- ❌ 不要用前端倒计时决定「能否下单」——时钟可被篡改，最终以服务端校验为准。

## 51.5 自测题

<details>
<summary><b>1. 【基础】HLS、HTTP-FLV、WebRTC 的延迟与适用场景有什么差异？</b></summary>

HLS 兼容性最好但延迟通常 5~30 秒，适合点播与弱互动直播；HTTP-FLV 延迟约 1~3 秒，依赖 MSE，适合直播电商；WebRTC 延迟可低于 1 秒，适合连麦、拍卖等强互动场景，但成本与复杂度最高。选型由产品的延迟目标决定。
</details>

<details>
<summary><b>2. 【基础】弹幕为什么要按 `id` 去重？重复通常来自哪里？</b></summary>

直播消息可能因断线重连补发、多端同步、服务端重试而重复。若不去重，同一条弹幕会多次上屏、礼物会重复计数。按服务端生成的 `id` 做幂等，是成本最低的兜底。
</details>

<details>
<summary><b>3. 【进阶】为什么不能「收到一条弹幕就渲染一条」？</b></summary>

高人气直播间消息速率远高于屏幕可读速率。逐条渲染会让每帧 DOM 操作和布局次数失控，导致掉帧、输入卡顿，甚至主线程堵塞。应按帧预算批量渲染，并对队列设上限，溢出时丢低优先级消息。
</details>

<details>
<summary><b>4. 【进阶】弹幕位移动画为什么优先用 `transform` 而不是 `left/top`？</b></summary>

`left/top` 会触发布局（layout）与绘制，每帧修改都可能导致整棵子树重排；`transform` 只影响合成，通常由合成器线程处理，帧率更稳。配合 `will-change: transform` 可提前提升为合成层，但动画结束后应移除。
</details>

<details>
<summary><b>5. 【进阶】点赞为什么要「本地乐观计数 + 批量上报」？直接每次点击发请求不行吗？</b></summary>

高频点击会产生大量请求，既浪费带宽又容易触发限流。本地乐观计数能给用户即时反馈，批量上报把多次点击合并为一次请求，服务端再做汇总校正。失败时回滚并提示，保证最终一致。
</details>

<details>
<summary><b>6. 【挑战】设计一个万人直播间的弹幕方案，要求低端机也不卡。</b></summary>

接入层用 WebSocket + `seq` 增量同步；消息层做幂等、限流、合并与抽样；渲染层按帧预算批量上屏，普通弹幕用 DOM/CSS transform，高密度场景切 Canvas；低端机通过帧率检测降级（关闭特效、合并消息、只保留礼物与系统消息）；页面隐藏时停止消费并清空队列；所有策略可配置，按房间热度动态调整。
</details>

<details>
<summary><b>7. 【挑战】直播间商品在用户点「立即购买」的瞬间下架了，前端应如何处理？</b></summary>

点击时携带商品版本号/时间戳发起下单；服务端返回「已下架/库存不足」时，前端立即把商品卡置为失效态，禁用购买按钮，给出明确原因与替代商品；若已进入支付流程，按订单状态查询结果，避免重复下单。核心是「服务端为准 + UI 能表达失效」，而不是只弹一个 toast。
</details>

<details>
<summary><b>8. 【挑战】弹幕队列溢出时，你会丢哪些消息？为什么？</b></summary>

优先丢「最旧的低优先级聊天」，保留礼物、系统公告、房管管控等高频价值消息；同优先级按时间淘汰最旧。理由是：旧聊天已经失去时效性，而礼物/管控消息与交易、秩序相关，丢失会造成用户投诉或合规问题。丢弃数量要可观测，便于评估容量。
</details>

## 51.6 本章避坑清单

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 逐条渲染弹幕 | 掉帧、主线程堵塞 | 按帧预算批量渲染 |
| 队列无上限 | 内存暴涨、延迟无限增长 | 设上限 + 溢出丢弃策略 |
| 用 `left/top` 做位移动画 | 每帧重排，低端机卡顿 | 用 `transform` + 合成层 |
| `will-change` 常驻 | 显存占用高、层爆炸 | 动画结束移除 |
| 弹幕直接 `innerHTML` | XSS、脚本注入 | 转义或纯文本节点 |
| 不做消息去重 | 重连后重复上屏、礼物重复计数 | 按 `id` 幂等 |
| 限流静默丢消息 | 用户以为发送成功 | 返回 `retryAfter` 并提示 |
| 前端做最终审核 | 可被绕过，合规风险 | 服务端审核 + 前端只展示状态 |
| 点赞逐次发请求 | 请求风暴、限流 | 合并 + 批量上报 |
| 交易操作无幂等键 | 重试导致重复扣款/送礼 | 每次操作带唯一键 |
| 用倒计时决定能否下单 | 客户端时钟可篡改 | 服务端校验为准 |
| 商品下架只弹 toast | UI 仍可点击，重复失败 | 置为失效态并禁用 |
| 页面隐藏仍消费队列 | 后台耗电、回来瞬间刷屏 | `visibilitychange` 暂停 |
| 切换房间不清队列 | 上个房间消息串台 | 房间维度隔离状态 |
| 播放卡顿与弹幕互相阻塞 | 一处卡死全页卡死 | 播放与互动解耦 |
