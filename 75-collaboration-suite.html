75.1 协同办公产品全景：八大件与复杂度地图 ​

概念解析 ​

移动办公产品不是「八个 App 拼盘」，而是一套账号、一套组织、一条消息总线上的八个域。先把八个域按前端最关心的三个维度打分（1=低，5=高），据此分配架构投入：

域状态同步复杂度实时性要求单页数据量级复杂度来源
IM554多端同步、离线追平、写扩散（39 册）
邮件213本质是异步列表，协议（IMAP/Exchange）在后端
日历日程423RRULE 展开、时区、例外日期（75.5）
视频会议552信令状态机、设备管理、弱网降级（75.3）
文档协同544CRDT 合并、离线编辑、版本快照（75.4）
云盘314大文件分片、秒传、树操作（40 册）
审批322流程状态机、条件路由（42 册）
通讯录325万级部门树、拼音搜索、可见范围（75.2）

评分怎么用：状态同步 ≥4 的域（IM/会议/文档）需要长连接 + 增量同步协议；实时性 ≥4 的域要预留信令通道与降级阶梯；数据量级 ≥4 的域（云盘/通讯录）必须懒加载 + 虚拟滚动。三个维度都低的邮件，用普通 REST 列表就够了——不要给邮件上 WebSocket，把复杂度预算花在该花的地方。

评分还直接决定性能预算的分配。工作台整机预算（首屏 JS、内存、长连接数）是有限的，按域切碎：

预算项高优先级域低优先级域约束手段
首屏 JS 体积IM、文档邮件、审批（路由级分包，进入才加载）模块联邦远程模块 + 按域懒加载
内存常驻IM 会话、文档协同 doc日程（窗口数据即用即弃）域切换时 dispose 重型对象
长连接全域共享一条网关——订阅/退订协议，禁私开连接
主线程算力文档绑定、视频布局日程 RRULE 展开丢 Worker重计算一律出主线程

跨域接力是工作台的日常形态，一个普通上午就是五域接力：9:00 日历提醒弹窗（日程）→ 点「入会」进入视频会议（会议）→ 会中共享一份需求文档共编（文档）→ 结论 @负责人 生成待办进 IM（IM）→ 会后纪要提交归档审批（审批）。接力的每一棒都是「带上下文的域间跳转」，接力不顺的体验投诉远多于单域功能缺陷——这就是为什么统一 deeplink 路由与上下文参数是工作台级的一等公民。

咬合出工作台的四个架构要点：

  1. 单条网关连接：八域共享一条 WebSocket（按域做消息路由与订阅），绝不能每域各开一条——移动端 8 条长连接的保活耗电与弱网重连风暴会直接拖垮整机体验。消息模型复用 39 册的 seq 游标与幂等去重。
  2. 统一组织与权限：所有域的「人」都来自 72 册的组织主数据；任何域渲染成员列表前过一遍可见范围。域内绝不自建「小通讯录」。
  3. 跨域跳转携带上下文：群里点文档链接 → 文档打开时带回会话上下文（从哪里来的、相关会议）；会议邀请卡片 → 一键入会。跳转协议用统一 deeplink 路由，参数签名防篡改。
  4. 徽章聚合收口：工作台的「待办数」= 各域徽章按 62 册归约模型汇总，单源展示，避免 IM 红点、审批红点、日程提醒各自为政互相打架。

典型应用场景 ​

  • 大厂套件：企业微信 / 钉钉 / 飞书 / Teams 的 Web 与桌面端工作台；
  • 政企私有化办公门户：八大件按客户采购清单裁剪装配，域可插拔；
  • 会议中分享文档、文档里 @人 触发 IM 通知、审批单关联日程——三个域在同一条用户路径上接力；
  • 移动端工作台首屏： badges 先行、卡片懒渲染，弱网电梯里先看到「有几个待办」再看到内容；
  • 桌面端常驻：长连接保活与多窗口状态同步（73 册多端架构的兄弟问题），徽章数跨窗口一致是底线。

核心代码示例 ​

工作台 Shell 的「域注册表」模式——每个域声明元数据，Shell 聚合徽章与路由，新增一个域不改 Shell 代码：

ts
// 域清单：声明式注册，Shell 只依赖这个接口
interface DomainManifest {
  key: string;                    // 域标识："im" | "mail" | "calendar" | ...
  title: string;                  // 工作台卡片标题
  entry: () => Promise<unknown>;  // 懒加载入口（微前端/模块联邦的远程模块）
  badgeTopic: string;             // 在统一网关上的未读订阅主题
  requiredScope?: string;         // 需要的权限码（72 册数据范围推导后判定）
}

class WorkbenchShell {
  private domains = new Map<string, DomainManifest>();
  private badges = new Map<string, number>();

  register(m: DomainManifest) {
    this.domains.set(m.key, m);   // 装配期注册，运行时只读
  }

  /** 统一网关收到未读推送后按主题归位，工作台总待办 = 各域之和（62 册归约模型） */
  onBadgePush(topic: string, unread: number) {
    this.badges.set(topic, unread);
  }

  get totalTodo(): number {
    return [...this.badges.values()].reduce((a, b) => a + b, 0);
  }

  /** 按权限过滤后渲染卡片：无权限的域直接不装配，而不是渲染后隐藏 */
  visibleDomains(hasScope: (s?: string) => boolean): DomainManifest[] {
    return [...this.domains.values()].filter((d) => hasScope(d.requiredScope));
  }
}

最佳实践 ​

  • ✅ 把「复杂度地图」画在需求评审会上：哪个域要长连接、哪个域要懒加载，由打分推导，不靠感觉；
  • ✅ 域间通信只走事件总线与 deeplink，不允许域 A 直接 import 域 B 的内部模块——否则裁装配（私有化只交付其中五个域）时会牵一发动全身；
  • ✅ 无权限的域「不装配」而非「渲染后隐藏」：少一次远程模块下载，也少一个越权面；
  • ✅ 私有化交付时把域清单做成构建期配置：装配哪些域 = 哪些远程模块进产物，裁剪在构建期完成而不是运行时 if-else；
  • ✅ 徽章总数要有上限展示（99+），八域未读全开的重度用户，精确数字只会制造焦虑；
  • ❌ 不要在工作台首页并发拉取八域的首屏数据——按可视区懒加载，首屏只取徽章数；
  • ❌ 不要让各域自定跳转协议：文档里打开日程链接若各写各的 URL 规则，跨端（Web/桌面/移动）必然对不齐。

75.2 组织通讯录与人员选择器 ​

概念解析 ​

通讯录是八大件的地基：IM 拉群、会议邀请、文档分享、审批选人——所有域最终都落到「选人」。而万级组织的通讯录前端有三个绕不开的难题：

① 树太大，不能全量加载。1 万人 × 平均 5 个字段 ≈ 数 MB JSON，首屏全量拉取在移动网络下就是事故。正解是按部门懒加载 + 成员分页：展开一个部门节点才拉它的直属子部门（一次给全，量级小）与直属成员（分页，20 人/页）。子部门与成员分开返回，因为两者的量级与翻页语义完全不同。

② 中文搜索必须带拼音。用户输入「zhangsan」「zs」「张三」都期望命中同一个人。索引建三路倒排：姓名原文（包含匹配）、全拼（前缀匹配）、首字母（前缀匹配）。1 万人 ≈ 3 万条索引项，纯前端内存索引完全可控（毫秒级扫描）；10 万级以上或受可见范围约束时，索引放服务端，搜索是接口而非本地过滤——示例 75-01 用「服务端索引 + 前端懒加载」模拟了生产形态。

③ 选择器状态横跨两个视图。用户在树里勾了一半部门、又切到搜索结果勾了几个人，已选集合必须全局唯一（按人员 id 去重）；级联全选部门 = 选中整棵子树的成员（含未加载的分页）；搜索命中后「回树定位」需要该成员的祖先链逐级展开。已选列表存的是人员快照，组织变动（调动/离职）时必须同步修正，否则提交审批单时部门对不上。

组织变更的增量同步：组织主数据按版本号演进（72.5 同款机制），前端缓存已加载节点，收到变更事件（member_move / member_leave / dept_rename）后只失效受影响的节点缓存，绝不整树重拉；旧版本事件按版本号幂等丢弃。可见范围过滤（你只能搜到/看到权限内的人）在服务端完成，前端不持有越权数据。

搜索索引放前端还是服务端，按数据量级与权限约束决策：

方案适用规模优点代价
前端全量索引< 1 万人、全员可见零网络延迟、离线可搜首屏要拉全量人员；越权数据上前端
服务端索引 + 接口搜索万级以上、有可见范围权限在服务端收口、前端零负担每次输入一次请求（需防抖 + 取消竞态）
混合：热部门前端索引常用联系人高频复搜高频路径秒出两套逻辑一致性要维护

政企场景几乎必然选服务端方案——72 册的可见范围推导结果因人而异，索引必须按「查询者」裁剪，前端拿到的任何全量数据都是泄露面。

树组件自身的渲染性能也要单独算账：懒加载解决的是「数据不要一次来」，虚拟滚动解决的是「DOM 不要一次渲染」。展开的节点多了（用户连开十个部门），扁平化可见节点 + 虚拟滚动（10 册/41 册同款方案），节点行高固定是虚拟化的前提；部门行的缩进用 padding 而非嵌套 DOM，扁平数组才能滚得动。

典型应用场景 ​

  • 会议邀请选人：级联选中整个事业部，再反选掉请假小组；
  • 审批流「选择下一级审批人」：搜索「wei」命中「张伟」，回树确认他是哪个部门的；
  • 组织架构月底调整：部门合并，前端收到 member_move 事件，局部刷新已展开节点；
  • 政企场景：按 72 册可见范围，市公司员工搜不到省公司其他部门的人；
  • IM 群聊「@所有人」之外的精确提醒：@面板就是通讯录选择器的内嵌形态，已选=被@的人；
  • 新员工入职第一天：通讯录是他唯一会主动打开的域——加载速度与搜索命中率直接决定办公套件的第一印象分。

function toPinyin(name: string) {
  const full = [...name].map((c) => PINYIN[c] ?? c).join("");
  const initials = [...name].map((c) => (PINYIN[c] ?? c)[0]).join("");
  return { full, initials };
}

/** 级联全选：选中部门 = 选中其全部子孙部门的全部成员 */
cascadeDept(deptId: string, check: boolean) {
  const prefix = `${deptId}-`; // id 自带层级前缀，等价于物化路径前缀匹配
  for (const m of DB.members) {
    if (m.deptId === deptId || m.deptId.startsWith(prefix)) {
      if (check) this.selected.set(m.id, m);
      else this.selected.delete(m.id);
    }
  }

最佳实践 ​

  • ✅ 树接口子部门与成员分字段返回：子部门一次给全（通常 <50），成员分页；混在一个列表里分页会让「展开部门」的交互语义混乱；
  • ✅ 拼音索引键全部小写化、查询词归一（trim + lowercase），「Zhang」「zhang 」同一命中；
  • ✅ 已选集合按人员 id 去重，快照字段（姓名/部门/头像）随变更事件更新——提交时刻以 id 为准、展示以快照为准；
  • ✅ 级联全选的计数交给服务端子树统计接口，前端不递归累加已加载缓存（缓存只是窗口，不是全集）；
  • ✅ 搜索输入做防抖（200ms）+ 请求竞态治理（AbortController 取消上一发），否则快速输入时旧响应覆盖新结果；
  • ✅ 搜索结果也要带「部门路径」副标题——同名同姓在万级组织里是常态，没有路径用户根本分不清两个「张伟」；
  • ❌ 不要把整棵组织树塞进 localStorage 做「离线缓存」——万级数据序列化一次就是几十毫秒主线程卡顿，且组织天天变，缓存命中率极低；
  • ❌ 不要在前端做可见范围过滤：越权数据一到前端就已经泄露（72 册的出口收口原则）。

75.3 WebRTC 视频会议前端 ​

概念解析 ​

68 册讲了媒体链路六段与 CDN/RTC 分发，本节只讲会议室端侧的四块：信令、设备、弱网降级、布局渲染。

信令通道与状态机。WebRTC 标准只规定媒体怎么传，不规定「怎么找到对方、怎么交换参数」——这层信令要自建（WebSocket + JSON 即可）。端侧状态机：

text
idle → joining → joined → negotiating → connecting → connected
                     ↑___________|（重协商）      ↘ closed

SDP/ICE 够用版：SDP 是一份「媒体能力清单」（我支持哪些编码、几路轨、收还是发），offer/answer 就是双方交换清单达成一致；ICE 是「找通路」——每个端收集自己的候选（host 本机 / srflx 公网映射 / relay 中转）发给对方，两边拿候选两两打洞。前端要理解的工程事实只有三条：

  1. ICE 候选可能比 offer/answer 先到（UDP 候选生成极快，信令消息在网关乱序）——候选必须进待决队列，远端描述就绪后按序补放；
  2. 信令消息会重复（重发、补投）——按 msgId 幂等去重，按 seq 检测缺口；
  3. 双发会撞车（glare）：双方都以为自己是主叫同时发 offer——用 perfect negotiation：约定 polite 端回滚本地 offer 接受对方，impolite 端无视对方 offer，冲突必解。

SDP 字段够用对照（不用背协议，认出这几行就能定位 80% 的协商问题）：

SDP 行含义排查时看什么
m=audio/video媒体轨道声明与端口轨道数对不对（少一路通常是 addTrack 时机晚了）
a=rtpmap编码列表（H.264/VP8/OPUS）双端交集为空 = 编码不兼容，黑屏无声
a=sendrecv 等方向位这路轨是发、收还是双向只收不发却声明 sendrecv，会白占解码资源
a=fingerprintDTLS 证书指纹与中继/ SFU 对不上时握手失败

设备管理：enumerateDevices 枚举摄像头/麦克风/扬声器 → getUserMedia 按 deviceId 约束采集 → devicechange 事件监听热插拔 → 切换时用 replaceTrack 换轨不断流（不重新协商）。扬声器输出切换用 setSinkId（仅 Chromium 系）；移动端听筒/扬声器切换没有 Web 标准，走 RTC 厂商 SDK 的原生能力。两个细节：未授权前 enumerateDevices 返回的设备 label 是空的（浏览器隐私策略），要先 getUserMedia 拿到权限再枚举；设备占用是排他的，前一个 MediaStream 的 track 不 stop()，下一个应用拿不到摄像头。

弱网降级阶梯：68.4 讲了平台侧的分层降级，端侧是执行细节——getStats 周期采样（rtt / 丢包率 / jitter），按阶梯逐档退让：1080p30 → 720p30 → 720p15 → 360p15 → 只收音频。两个原则：快降慢升（恶化立即降，恢复需连续 N 个健康窗口才升，防临界点抖动）、一次一档（不跳档，画质变化可预期）。发布侧降码率（sender.setParameters）与订阅侧降分辨率（SFU simulcast 选层）要分开决策。

多人布局与渲染性能：每路远端视频 = 一个解码器实例，移动端超过 6 路就开始发烫。画廊布局 N>16 必须分页；只给可视区域的 video 绑定流，翻页时复用 video 元素换绑 srcObject 而非销毁重建；演讲者布局下主画面订阅大流、缩略图订阅小流（simulcast 的意义就在这里）；屏幕共享一路高码率、人物视频集体降档。三种布局的资源画像对比：

布局大流路数小流路数适用场景端侧压力点
画廊（宫格）0~4其余全部讨论型会议，人人对等路数多 → 解码器总数爆炸
演讲者（主辅）1其余缩略图宣讲、培训主画面码率高，注意切大流的重协商
共享主导1 路屏幕共享（高码率）人物全小流评审、授课共享文字清晰度优先，人物可集体降档

布局切换时的「换绑不重建」原则同样适用于布局本身：video 元素池化，布局变化只改容器位置与 srcObject 绑定，避免解码器销毁重建带来的黑帧。

典型应用场景 ​

  • 企业晨会：20 人画廊视图分两页，发言者自动置顶；
  • 弱网通勤参会：地铁里从 720p 一路退到只收音频，出站后逐级回升；
  • 外设热切换：用户插上 USB 摄像头，会议中无感换轨；
  • 共享屏幕主导的设计评审：主画面给共享流 1080p，人物缩略图 180p。

可运行代码示例 ​

示例 75-02 用脚本化事件（无定时器无随机）模拟完整信令链路：双发 offer 撞车 → polite 端回滚 → answer 重复投递被 msgId 去重 → ICE 候选乱序先行进待决队列 → 描述就绪按序补放 → 建连；随后演示 12 个网络质量窗口下的降级阶梯决策：

ts
// 文件: examples/75-02-signaling-machine.ts —— 节选（降级阶梯决策）
feed(m: Metrics): string {
  if (!healthy(m)) {
    this.goodStreak = 0;
    if (this.level < LADDER.length - 1) {
      this.level++; // 不健康立即降一档（快降）
      return `指标恶化 → 降到 ${LADDER[this.level].label}`;
    }
    return `已在最低档 ${LADDER[this.level].label}，保持音频兜底`;
  }
  this.goodStreak++;
  if (this.level > 0 && this.goodStreak >= this.UPGRADE_AFTER) {
    this.level--; // 慢升：连续 3 个健康窗口才升一档（滞回）
    this.goodStreak = 0;
    return `回升到 ${LADDER[this.level].label}`;
  }
  return `健康(${this.goodStreak}/${this.UPGRADE_AFTER})，维持 ${LADDER[this.level].label}`;
}

最佳实践 ​

  • ✅ 信令层与媒体层解耦：信令只管状态机与消息治理，拿到描述和候选后交给 PeerConnection；把 addIceCandidate 直接绑在消息回调上（不做待决队列）是新手第一大坑；
  • ✅ polite/impolite 角色在进房时由服务端分配（通常后入房者 polite），不要客户端自报；
  • ✅ 设备切换一律 replaceTrack；只有换编码/加轨道才需要重新协商；
  • ✅ 进会前做设备自检页：枚举设备 → 试采 → 扬声器试音三步，把「听不到/看不见」拦截在会前，而不是会中互相喂喂喂；
  • ✅ devicechange 监听要在整个会议生命周期常驻：热插拔是常态（插拔耳机、切换蓝牙），设备列表变化要同步刷新设置面板；
  • ✅ 降级阈值服务端下发可按地区/机型灰度（68.4 的原则在端侧同样成立）；
  • ❌ 不要给每路远端流常驻一个 video 元素：不可见就解绑回收，解码器是稀缺资源；
  • ❌ 不要在 getStats 单次采样上就降档：指标必须进滑动窗口，毛刺不是趋势。

75.4 文档协同落地：Yjs 接入实战 ​

概念解析 ​

43.6 讲了 OT vs CRDT 的原理与 Yjs 三层结构（Y.Doc / 共享类型 / Provider+Awareness）——那里回答「为什么选 CRDT」，本节回答「接入之后怎么落地」。生产接入是六件事：

① 文档绑定：编辑器不直接改 DOM，改的是 Y 类型——CodeMirror 用 y-codemirror.next、ProseMirror/Tiptap 用 y-prosemirror，绑定层把编辑器操作翻译成 Y.Text 变更，也把远端变更翻译回编辑器视图。UndoManager 必须配 trackedOrigins 只撤本地操作，否则你会撤销掉同事刚打的一段字。

② Awareness 光标协同：光标位置、选区、用户名/颜色、在线状态走 awareness 通道——它不进文档数据、不持久化、不参与合并，丢失也无所谓。把光标写进文档数据是新手典型错误：文档会被光标移动刷爆，历史版本里全是噪音。

③ 离线编辑与合并：y-indexeddb 把文档与未同步的 update 持久化在本地，断网继续编辑；重连后双方交换 state vector，只补差量 update。合并不丢字是 CRDT 给的，但合并结果的可解释性是产品问题：两人同改一段，UI 上要用「协作冲突提示/版本对比」让用户看懂合并结果，而不是假装冲突不存在。

④ 版本快照：Y.Doc 的全部历史 update 可以编码成二进制存档；定时 snapshot（如每 15 分钟 + 每 500 次变更）+ 里程碑快照（发布/归档）。历史版本预览的正确姿势是新建一个临时 doc，apply 快照后只读渲染——绝不在当前协同 doc 上「回滚查看」，那会把回滚广播成一次新变更。

⑤ 性能上限：Yjs 是全内存模型，10 万字长文档的 update 历史会无限膨胀（每个删除字符都留墓碑标记）。三层缓解：

  • 服务端定期 squash：把历史 update 合并压平成单个 snapshot，老 update 归档；
  • 大文档拆 subdocument（Yjs 子文档）：按章/节懒加载，打开文档只拉当前章；
  • 编辑器分页/分块绑定：可视区之外的章节解绑，滚动到时再绑定。

⑥ 权限边界：读权限决定能否进 provider 房间（无读权限连 update 都收不到）；写权限在每次 update 落地时服务端校验；awareness 里的人员列表同样按读权限过滤——权限模型复用 37 册 ABAC 与 72 册数据范围，文档域不自建。

与 43.6 的分工对照，读完两边不迷路：

典型应用场景 ​

  • 需求文档评审共编：10 人同时改一份 PRD，awareness 显示谁在哪一节；

  • ❌ 不要忽视 GC 与 squash：上线三个月后的热门文档，update 体积能拖垮首次加载。

75.5 日程与会议室：RRULE、时区与冲突检测 ​

概念解析 ​

RRULE 重复规则（RFC 5545）：一条规则描述无限序列——FREQ=DAILY/WEEKLY/MONTHLY 定频率，INTERVAL 定间隔，COUNT/UNTIL 定边界，BYDAY（周几）、BYMONTHDAY（几号）定落点；EXDATE 删例外（清明调休跳过一次），RDATE 加例外。存储只存规则 + 首次开始时间（DTSTART），展示时按窗口展开——月视图只展开当月 42 格的窗口，绝不把未来三年的 occurrence 物化进数据库。编辑语义三分支：

用户操作数据层动作关键约束
仅此一次老规则加 EXDATE + 新建独立单次日程新事件与老系列互不知晓，删除互不影响
后续全部老规则截 UNTIL 到昨天 + 新规则从明天起新 DTSTART两个系列共享 seriesId 便于级联删除
全部改规则本体已产生的 EXDATE 是否保留要产品拍板（通常保留）

注意口径：COUNT 是先按规则计够次数、再被 EXDATE 剔除（与 rrule.js 一致）——所以「共 5 次、删掉 1 次例外」最终只剩 4 次，示例 75-03 的断言钉死了这个口径。

时区陷阱：日程必须「存 UTC + 存创建时区」，展开时按创建时区的墙钟逐日生成，再换算成 UTC——纽约每周一 9:00 的会，跨过夏令时后 UTC 从 14:00 变 13:00，但本地永远 9:00。若偷懒每次直接 +7×24h 的绝对时间，DST 切换后本地参会时间整体漂移一小时——这是日程系统最经典的线上事故。32.4 讲了 Day.js 跨时区的通用陷阱，本节是其在「重复规则展开」上的实战延伸。展示层按观看者时区渲染：北京同事看纽约同事的会，自动 +13 小时。

忙闲查询与冲突检测：会议室就是一个「资源日历」，忙闲 = 该资源在窗口内的所有预定区间；冲突 = 新区间与已有区间重叠（s < e2 && e > s2）。已定区间按开始时间排序后可提前 break，万级区间毫秒级出结果。冲突策略两档：强拦截（独占会议室）与弱提示（允许候补/超订，仅标红）。循环会议一次订半年 = 资源长期锁死，生产上要配「重复会议最长 3 个月 + 到期自动释放」的治理规则。

月/周视图渲染性能：月视图 42 格，事件条要跨天合并 + 层叠排布（lane assignment）；周视图时间轴用虚拟滚动只渲染可视小时窗；展开结果按「规则哈希 + 窗口 key」memo，切换月份不重算；千级规则的批量展开（全员忙闲视图）丢给 Web Worker，主线程只收结果。lane 分配是月视图独有的算法题：跨 3 天的会议在 3 个格子里必须是同一行，否则视觉上断成三条。贪心策略即可——按「开始早、时长长」排序，逐条找第一个整段都空闲的 lane 放入，都没有则新开 lane；超过格子最大行数的折叠成「+N 更多」，点开弹层看全量。折叠不是偷懒：一格硬塞 8 条事件条，格子高度爆炸，整月视图版式就毁了。

典型应用场景 ​

  • 每周一三五站会 + 清明调休 EXDATE 跳过；
  • 跨国团队周会：组织者纽约时区创建，北京同事日历上自动落在周一晚 21 点；
  • 订会议室：选择时间后实时标出冲突的循环周会，给「仍要预定（申请特批）」的弱提示路径；
  • 部门忙闲视图：50 人 × 各自规则展开聚合，Worker 后台算完再渲染；
  • 每月最后一天结账例会：BYMONTHDAY=31 自动跳过 2/4/6/9/11 月，绝不出现「4 月 31 日」;
  • 审批通过的会议室预定自动写入双方日程：42 册审批单状态流转到「通过」时触发日程域建事件——跨域接力的标准范式；
  • 领导驾驶舱式「全员忙闲热力图」：按部门聚合忙闲率，排会避开高峰——展开算力必须在 Worker/服务端，主线程只画格子。

可运行代码示例 ​

示例 75-03 实现 RRULE 子集（DAILY/WEEKLY/MONTHLY + INTERVAL + COUNT/UNTIL + BYDAY/BYMONTHDAY + EXDATE）与 Intl 双程修正的时区换算：

ts
// 文件: examples/75-03-rrule-schedule.ts —— 节选（墙钟 → UTC 换算与冲突判定）
/** 把「某时区的墙钟时间」换算成 UTC 毫秒；跨 DST 时第一程偏移可能不准，修正一次 */
function wallToUtc(timeZone: string, y: number, mo: number, d: number, h: number, mi: number): number {
  const guess = Date.UTC(y, mo - 1, d, h, mi);
  let utc = guess - tzOffsetMs(timeZone, guess);
  const off2 = tzOffsetMs(timeZone, utc);
  if (guess - off2 !== utc) utc = guess - off2; // 第二程修正（DST 切换前后偏移不同）
  return utc;
}

/** 冲突检测：occurrence 与该会议室已有预定做区间重叠判定（排序后提前 break） */
for (const s of occurrencesUtc) {
  const e = s + durationMin * 60_000;
  for (const b of list) {
    if (b.startUtc >= e) break;
    if (s < b.endUtc) out.push({ at: new Date(s), with: b.title });
  }
}

运行方式：npx tsx examples/75-03-rrule-schedule.ts

输出依次验证：每日站会 5 次 → 每周一三五 6 次 → 每月 31 号自动跳过 2/4/6/9/11 月 → EXDATE 剔除清明那次（COUNT=5 先计满再删，剩 4 次）→ 纽约周会跨 DST 后 UTC 从 14:00Z 变 13:00Z 而本地恒为 9:00 → 会议室冲突精确命中「预算评审」、忙闲区间按本地墙钟输出 14:00~15:00。

最佳实践 ​

  • ✅ 事件三字段缺一不可：UTC 起止 + 创建时区 + RRULE 原文；只存展开结果等于放弃例外编辑能力；
  • ✅ 展开永远按窗口惰性进行，窗口外不展开；「下一次提醒时间」也要按窗口滚动计算；
  • ✅ EXDATE/RDATE 用墙钟日期（2026-04-06）而非 UTC 时间戳——否则跨 DST 的例外会对错日；
  • ✅ 冲突提示里给出具体撞车的会议名与时间，「时间冲突」四个字等于没说；
  • ✅ 提醒时间统一在服务端按窗口预展开计算，各端（Web/移动/桌面）只消费提醒队列——各端各自展开规则，提醒时间必然对不齐；
  • ✅ 月视图切换月份时预取相邻两窗的展开结果，来回翻月不转圈；
  • ❌ 不要用「每天 +24h」的方式展开重复日程（DST 必漂）；也不要用本地 Date 的 setDate 在 UTC 场景下混算（32.4 的服务端渲染时区错配同款坑）；
  • ❌ 不要让循环会议无限期占用会议室资源：期限 + 到期释放 + 占用报表三件套缺一不可。

75.6 自测题 ​

1. 【基础】万级组织的通讯录为什么不能一次全量加载？懒加载的基本单位与分页策略是什么？

万级成员的 JSON 有数 MB，移动网络下首屏全量拉取就是事故，且 99% 的节点用户根本不会展开。懒加载基本单位是「部门节点」：展开时才拉取，直属子部门一次给全（单部门子部门通常 <50，无需分页），直属成员分页（20 人/页）——两者量级和翻页语义不同，必须分字段返回，混在一个列表里分页会让展开交互语义混乱。

2. 【基础】拼音搜索为什么要同时建「全拼」和「首字母」两路索引，而不是只建全拼？

用户输入习惯分两派：完整输入「zhangsan」用全拼前缀匹配；偷懒输入「zs」只能靠首字母索引。只建全拼时「zs」两个字的首字母无法命中（全拼键是 "zhangsan"，前缀匹配 "zs" 失败）。三路倒排（姓名原文包含匹配 + 全拼前缀 + 首字母前缀）各管一种输入习惯，1 万人约 3 万条索引项，内存可控。

3. 【基础】为什么 ICE 候选可能比 offer/answer 先到达对端？前端必须怎么处理？

ICE 候选是本地网络探测（host/srflx/relay）异步生成的，产生即通过信令通道发送；而信令通道（WebSocket 网关）不保证跨消息的全局有序——候选完全可能在远端描述（offer/answer）之前到达。WebRTC 规定描述未设置前不能 addIceCandidate，所以前端必须维护待决候选队列：描述未就绪时候选入队，setRemoteDescription 完成后按到达顺序补放。直接绑定回调丢进来就加，必抛异常或丢候选。

4. 【进阶】双发同时 offer（glare）时 perfect negotiation 如何解决冲突？polite 端与 impolite 端各自做什么？

双方都认为自己是主叫、同时发出 offer，两个 offer 在线上交错，若都接受对方则状态撕裂。perfect negotiation 约定角色：polite 端收到对方 offer 时回滚自己未完成的 offer（rollback），接受对方描述并回 answer；impolite 端则无视对方 offer，等自己的 answer。角色由服务端在进房时分配（通常后入房者为 polite），不能客户端自报——否则两个都自称 impolite，死锁。

5. 【进阶】Yjs 的 awareness（光标/在线状态）为什么独立于文档数据同步、且不做持久化？

awareness 是易失状态：光标位置每秒多次变化、离线即失效，没有合并价值也没有历史价值。若写入文档数据，一来文档被光标移动刷爆（每次移动都是一次变更广播），二来历史快照里全是光标噪音，三来 CRDT 合并毫无意义（最后写入者覆盖即可）。独立轻量通道传输、不进持久化、不参与合并、丢失无所谓——这正是它设计上的减法。UndoManager 同理要配 trackedOrigins，否则撤销栈会被远端输入污染。

6. 【进阶】重复日程跨夏令时为什么必须「按墙钟展开再换算 UTC」，而不能每次直接 +7×24h？

日程的语义是「本地时间每周一 9:00」，不是「每隔 168 小时」。夏令时切换后，同一墙钟 9:00 对应的 UTC 偏移变了（纽约 EST -5 → EDT -4）。若按绝对时间 +7×24h 展开，UTC 时刻不变，本地参会时间就从 9:00 漂成 10:00——全公司周一晨会集体「迟到」一小时。正确做法：RRULE 逐日生成的是创建时区的墙钟日期，每个日期单独用双程修正法换算成 UTC（示例 75-03 的 wallToUtc），UTC 自动平移（14:00Z→13:00Z）而墙钟恒定。

7. 【挑战】月底部门合并，人员选择器的已选列表、树缓存、搜索索引如何保持一致？请设计前端一致性方案。

四层联动：① 事件层：组织主数据按版本号发变更事件（member_move / member_leave / dept_rename），旧版本事件幂等丢弃，防乱序重投；② 缓存层：只失效受影响节点的缓存（from/to 两个部门），未受影响节点保留，绝不整树重拉；③ 已选层：已选列表存人员快照，member_move 时按 id 修正快照里的部门字段，member_leave 时自动移出已选并 toast 告知（不能静默消失，用户要知道人数变了）；④ 提交层：提交时以人员 id 为准回服务端校验（服务端按当前组织再校验一次可见性与有效性），前端快照仅供展示。断线重连后按版本号差量拉事件，版本漂移过大则整树失效降级全量。

8. 【挑战】10 万字级文档接入 Yjs 协同后出现首次加载慢、内存暴涨，给出分层治理方案。

三根导火索对应三层治理：① update 历史膨胀（每次键入都是一条 update，删除留墓碑）——服务端定期 squash：把历史 update 合并压平成单个 snapshot，老 update 归档冷存；新客户端进来先拉快照再补差量，首次加载从「回放百万条 update」变成「一次 apply + 少量差量」；② 全量文档驻内存——长文档拆 subdocument（按章/节），打开只拉当前章，滚动到再 load；编辑器分页/分块绑定，可视区外解绑；③ 墓碑与 GC——确认 gc: true 开启回收删除标记；协作密度高的热门文档单独监控 update 体积与 apply 耗时进 59 册监控体系。最后加一道产品闸：超过 N 万字的文档提示拆分，工程兜底不能替代信息架构。
