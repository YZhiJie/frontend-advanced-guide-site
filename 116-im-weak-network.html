本部分内容 ​

39 册讲 IM 的基本盘：消息状态机、ACK、seq 游标与未读数。这一册补上线后的另一半：弱网抖动、乱序重复、离线补发、多端已读与爆发流量下的渲染容量，与 39 册的分工是协议设计 vs 生产治理。读完你能给出可落地的重连参数、去重补拉、离线队列、已读游标与弱网监控方案，并解释重连风暴、消息重复、红点错乱的成因。

116.1 连接生命周期：握手、心跳与重连退避 ​

概念解析 ​

长连接的生命周期是握手 → 鉴权 → 心跳 → 关闭/重连。握手只证明「对端是 WS 服务」，不证明身份：先用业务接口换一次性 ticket 再建连，别把长期 token 放进 URL。

心跳是必需的：浏览器拿不到 TCP 状态，切网、进后台、NAT 超时都会造成半开连接，onclose 可能几分钟才触发。移动端通常 20~30s 发 ping，服务端 2~3 个周期未收到判死。iOS 后台会冻结 JS 定时器，回前台必须主动探测，不能等定时器补跑。

重连模型是指数退避 + 抖动 + 上限 + 稳定后归零：1s→2s→4s→…→30s，每次在区间内随机抖动，服务端才不会在同一秒收到全量握手。关闭码必须分类：1000 正常关闭不重连；1006 异常断开走退避；4001/4003 停止并刷新票据；4008/4009 按 Retry-After 退避或提示。握手成功就归零 attempt 会让「连上就断」永远停在 1s，应稳定存活 30s 后再归零。

核心代码（节选，完整文件见 examples/116-01-reconnect-backoff.ts） ​

ts
// 文件: examples/116-01-reconnect-backoff.ts
computeDelay(attempt: number, visibility: Visibility = this.visibility): number {
    const cfg = this.config;
    let raw = Math.min(cfg.maxMs, cfg.baseMs * Math.pow(cfg.factor, attempt));
    if (visibility === 'background') raw = Math.max(cfg.backgroundFloorMs, raw * cfg.backgroundMultiplier);
    raw = Math.min(cfg.maxMs, raw);
    const spread = raw * cfg.jitterRatio;
    return Math.min(cfg.maxMs, Math.round(raw - spread + this.rand() * spread * 2));
}

onClose(code: number, nowMs: number): number | null {
    if (code === 4001 || code === 4003) {
        this.state = 'closed'; // 鉴权失败：重连一万次也没用
        return null;
    }
    return this.onFailure(nowMs);
}

运行方式：npx tsx examples/116-01-reconnect-backoff.ts

应用实践 ​

某出海社交 IM 用户多在东南亚 3G 和 iOS 后台切换场景。网关扩容后客户端仍固定 1s 重连，20 万用户 30 秒内形成握手风暴，排队超时又触发更多重连，雪崩 40 分钟。修复：改指数退避 + ±30% 抖动 + 30s 上限；服务端握手限流并返回 4008 + Retry-After；监控按地区与网络类型看重连 QPS。

最佳实践 ​

  • 退避参数配置化并按版本灰度；上限参考服务端容量，不拍脑袋。
  • 抖动必须仍受上限约束，否则封顶形同虚设。
  • 回前台用 0~200ms 小抖动立即重试，别让用户盯着「连接中」。
  • onopen 不算成功，要等鉴权 ACK，否则会陷入「连上→被踢→再连」。

116.2 消息时序与去重：seq、客户端 msgId 与乱序 ​

概念解析 ​

IM 里三个 ID 职责必须分清：

ID生成方特性用途
clientMsgId客户端一次动作只生成一次，重试复用本地回显、上行幂等键
serverId服务端全局唯一去重、定位、撤回
seq服务端会话内单调递增排序、游标、补拉

排序只认 seq。 发送端时钟可能快 5 分钟，按 sentAtMs 排序会让消息来回跳。本地乐观消息没有 seq，应放在末尾（Infinity 占位），服务端确认后就地替换，不要删了再插——后者会让气泡闪烁、滚动跳动。

去重要双键：同一条可能 serverId 相同（服务端重发/多端同步），也可能 clientMsgId 相同（自己的重试从另一路径回来）。只按内容去重会误杀用户真的连发两句相同的话。

乱序要配空洞检测：收到 seq=4 而本地 lastSeq=1，说明 2、3 丢了，应记录空洞并触发 sync(2,3) 增量补拉，而不是干等。补回后仍按 seq 插入。

核心代码（节选，完整文件见 examples/116-02-message-order-dedup.ts） ​

ts
// 文件: examples/116-02-message-order-dedup.ts
applyServer(msg: ServerMessage): ApplyResult {
    if (this.seenServerIds.has(msg.serverId)) return { appended: 0, duplicates: 1, gaps: [] };
    const local = this.byClientId.get(msg.clientMsgId);
    if (local !== undefined && local.seq !== null) return { appended: 0, duplicates: 1, gaps: [] };
    const gaps = msg.seq > this.lastSeq + 1 ? [{ from: this.lastSeq + 1, to: msg.seq - 1 }] : [];
    if (local !== undefined) { local.seq = msg.seq; local.serverId = msg.serverId; } // 原位升级
    else this.items.push({ seq: msg.seq, serverId: msg.serverId, clientMsgId: msg.clientMsgId, text: msg.text, sentAtMs: msg.sentAtMs });
    this.seenServerIds.add(msg.serverId);
    this.lastSeq = Math.max(this.lastSeq, msg.seq);
    this.sortBySeq();
    return { appended: 1, duplicates: 0, gaps };
}

运行方式：npx tsx examples/116-02-message-order-dedup.ts

应用实践 ​

客户端 WS 上行 + 服务端至少一次投递：用户在电梯里 ACK 超时，重发同一 clientMsgId，重连后又从离线接口拉到同一条——双键去重就是为此准备。反例是按发送端时间戳排序，手机快 7 分钟的用户消息全插到顶部；重试时重生成 clientMsgId 则直接落两条，接收侧再按 serverId 去重也救不回来。

最佳实践 ​

  • clientMsgId 用「设备 ID + 本地自增 + 随机后缀」或 UUID，发送成功前绝不重生成。
  • seq 只由服务端分配，客户端不得自行推导；本地排序只是展示。
  • 多个空洞合并为 [min, max] 一次补拉，避免补拉风暴。
  • 去重集合有上限（最近 500 条或 24 小时），否则长会话内存无限涨。

116.3 弱网策略：超时、重发、离线队列与分级降级 ​

概念解析 ​

第一步是把失败分类，而不是统一 retry：

失败类型例子重试处理
瞬时网络错误超时、DNS 失败、1006是指数退避，受上限约束
服务端 5xx/过载502、503、4008是尊重 Retry-After，降并发
客户端 4xx403、参数非法、被拉黑否标失败、提示、进死信
业务冲突消息已撤回、会话解散否刷新状态，不再发

离线队列有四个约束：持久化（刷新/杀进程不丢）、幂等（同一消息只有一份）、保序（队头未成功不越过）、有界（条数/TTL 上限）。恢复发送必须串行：每会话同时只有一个 in-flight，否则「先发后到」直接破坏顺序。

超时预算：建连 5s（弱网 8~10s）、鉴权 3s、消息 ACK 10s；ACK 超时只代表不知道收没收到，重发必须带同一幂等键。

分级降级按网络质量给能力：

等级判定动作
L0 正常RTT < 300ms，丢包 < 1%自动下载图片/视频、已读、正在输入
L1 弱网RTT 300ms~1s 或丢包 5%~15%只自动下载缩略图，回执延迟
L2 极弱多次超时/连续失败纯文本优先，暂停媒体与预览
L3 离线onLine=false 或探测失败只读缓存 + 草稿入队，显式「待发送」

navigator.onLine 只表示有网络接口，连上未认证的 Wi-Fi 仍为 true；恢复发送前要做一次轻量探测。

核心代码（节选，完整文件见 examples/116-03-offline-queue.ts） ​

ts
// 文件: examples/116-03-offline-queue.ts
flush(nowMs: number): number {
    if (!this.online) return 0;
    let calls = 0;
    while (this.queue.length > 0) {
        const head = this.queue[0];
        if (head.nextRetryAtMs > nowMs) break;
        this.queue.shift(); calls += 1;
        const outcome = this.transport(head);
        if (outcome.ok) { this.sentIds.push(head.id); continue; }
        if (outcome.kind === 'permanent') { this.failedIds.push(head.id); continue; }
        head.attempts += 1;
        if (head.attempts >= this.maxAttempts) { this.deadIds.push(head.id); continue; }
        head.nextRetryAtMs = nowMs + this.retryDelayMs * head.attempts;
        this.queue.unshift(head); break; // 保序：队头没成功，后面的绝不先发
    }
    return calls;
}

运行方式：npx tsx examples/116-03-offline-queue.ts

应用实践 ​

印度、巴西预付费用户流量敏感：某 App 在 L1 只预载缩略图，L2 点击才加载，并降频已读、正在输入等信令，投诉明显下降。反例是把被踢出群的 403 也当瞬时错误，每 2 秒重试一夜，既耗电又把失败藏起来——用户以为发出去了。

最佳实践 ​

  • 队列落 IndexedDB，带 enqueuedAt 与 TTL；启动先恢复队列再拉离线消息。
  • 只重发「未确认」的消息，已 ACK 的再发只会制造重复。
  • 发送状态可见：等待、发送中、失败可重试、已进死信，别只画转圈。
  • 降级可回切：恢复后按 L3→L2→L1 逐级放开，别一次性下载全部积压图片。

116.4 多端同步与已读：游标合并与幂等回执 ​

概念解析 ​

已读的最小事实是「某会话、某设备、读到了哪个 seq」，不是「未读数减一」。

  • 游标：每会话每设备一个，服务端持久化，合并取最大值。
  • 未读是派生值：unread = max(0, lastSeq - mergedReadSeq)。维护可增减计数器，在多端、重复回执、乱序下必然漂移，最后出现负数或清不掉的红点。
  • 回执幂等：带 receiptId（或 deviceId + readSeq 作幂等键），重复消费只生效一次。
  • 只增不减：迟到回执接受但不回退。
  • 批量上报：进入 500 条未读的会话，只报一次 readSeq = lastSeq，不是发 500 条。

核心代码（节选，完整文件见 examples/116-04-read-receipt-reduce.ts） ​

ts
// 文件: examples/116-04-read-receipt-reduce.ts
markRead(receipt: ReadReceipt): ReadResult {
    const lastSeq = this.lastSeqByConversation.get(receipt.conversationId) ?? 0;
    const mergedBefore = this.mergedReadSeq(receipt.conversationId);
    if (this.seenReceipts.has(receipt.receiptId)) {
        return { changed: false, duplicated: true, mergedReadSeq: mergedBefore, unread: Math.max(0, lastSeq - mergedBefore) };
    }
    this.seenReceipts.add(receipt.receiptId);
    const cursors = this.deviceCursors(receipt.conversationId);
    if (receipt.readSeq <= (cursors.get(receipt.deviceId) ?? 0)) {
        return { changed: false, duplicated: false, mergedReadSeq: mergedBefore, unread: Math.max(0, lastSeq - mergedBefore) };
    }
    cursors.set(receipt.deviceId, receipt.readSeq);
    const mergedAfter = this.mergedReadSeq(receipt.conversationId);
    return { changed: true, duplicated: false, mergedReadSeq: mergedAfter, unread: Math.max(0, lastSeq - mergedAfter) };
}

运行方式：npx tsx examples/116-04-read-receipt-reduce.ts

应用实践 ​

WhatsApp Web 与手机共用游标：网页滚到底上报，手机同步后红点也消失。反例是未读计数器减一，多端同步两次就减两次，迟到回执还会加回；客服系统里红点永远清不完，坐席会重复回复。

最佳实践 ​

  • 清红点以打开时 lastSeq 为基线，回执回来后以服务端游标为准，不二次递减。
  • 滚动停止 300~500ms 再上报已读，别每滚一屏发一次。
  • 会话列表未读统一由「游标 + lastSeq」计算，不要各页面各存一份。

116.5 高并发前端：长列表、虚拟滚动与批量渲染 ​

概念解析 ​

IM 前端的高并发是瞬时消息爆发：大群 1 分钟 2000 条、重连补拉 3000 条，瓶颈通常是一次渲染太多。三个原则：

  1. 窗口化：只渲染可视区 + 上下 overscan 5~10 条；不等高消息缓存测量值并校正。
  2. 批量提交：一批消息合并到一次 rAF 更新，避免 1000 次响应式触发。Vue 3 超大数组用 shallowRef/markRaw，别让字段都变深层代理。
  3. 滚动锚定：顶部加载时用 scrollHeight 差值补偿 scrollTop，否则视口被弹走；到底部才吸底。
预算目标说明
单帧 JS< 8ms留一半给布局绘制
可视节点20~40 条超过 100 条就窗口化
首屏历史20~30 条上滚再增量拉

应用实践 ​

10 万人大群点开「999+」，旧实现一次渲染 3000 条，中端安卓白屏 2.3 秒并 ANR；改为只渲染 30 条 + 虚拟窗口 + 分页补拉 + 游标清零，首屏可交互 300ms。反例是每条消息 push 后重算全列表高度，主线程被 scrollHeight 反复打断，帧率跌到 10fps。

最佳实践 ​

  • key 用 serverId ?? clientMsgId，绝不用数组下标，否则插入历史会整列重渲染。
  • 滚动监听 passive + rAF 节流；高度测量集中到帧末，避免布局抖动。
  • 图片/视频用 IntersectionObserver 懒加载，占位高度先写死，加载后校正。

116.6 监控与压测：指标、弱网模拟 ​

概念解析 ​

弱网治理不能靠投诉驱动，要有分地区、分网络、分版本的指标：

指标健康线告警思路
连接成功率> 99%按地区看，< 95% 告警
重连频率< 1 次/用户/小时突增即可能发布或网关故障
重连耗时 P95/P99< 5s均值会掩盖长尾
心跳超时率< 0.5%与网络类型联动
发送成功率> 99.5%区分瞬时与永久失败
ACK 时延 P95< 2s弱网地区单独阈值
重复率/空洞恢复重复 < 1%，恢复 P95 < 3s重发、补拉接口是否健康

采集只上报状态迁移与聚合值，别每条消息打日志；维度控制在地区、网络、版本、前后台，userId 是高基数，不能当维度。

弱网模拟要覆盖高 RTT、丢包、断连、乱序/重复。DevTools 的 offline 与 throttling 只能模拟带宽/RTT，模拟不了 WS 层丢包与乱序，需要 toxiproxy、clumsy、tc netem 或服务端故障注入。测试矩阵：RTT 300ms + 丢包 20%、30s 断连、后台 5 分钟、补拉 3000 条。

应用实践 ​

雅加达灰度 5% 时重连频率从 0.6 跳到 4.2 次/小时，成功率仍有 98%；按网络拆分发现只有 3G 异常——心跳从 25s 改成 10s，弱网下心跳自身超时被误判死连接，回滚后恢复。反例是只看平均 ACK：800ms 很健康，P99 却 15s，那 1% 用户正是弱网地区的核心用户。

最佳实践 ​

  • 指标必带地区、网络、版本、前后台，否则无法区分客户端问题与区域网络问题。
  • 重连与发送失败要区分主动关闭、鉴权失败、网络失败，避免误导排障。
  • 告警可联动降级开关：重连率突增时暂停已读、正在输入等非关键信令。

116.7 自测题 ​

先自己作答，再展开参考答案。

1. 为什么重连必须加抖动？不加会怎样？【基础】

所有客户端同一秒重试会造成握手风暴，超时又触发下一轮。抖动打散尖峰，但仍受上限约束。

2. 为什么 onclose 不能作为断线唯一依据？【基础】

切网/后台/NAT 会造成半开连接，onclose 可能几分钟才触发。必须心跳 + 超时判定，回前台主动探测。

3. 关闭码 4001 和 1006 处理方式有何不同？【基础】

4001/4003 鉴权失败或被踢，停止重连并刷新票据；1006 异常断开可恢复，走退避。

4. clientMsgId、serverId、seq 各自解决什么问题？【基础】

clientMsgId 负责回显与上行幂等，serverId 负责定位去重，seq 负责排序/游标/补拉；三者不可替代。

5. 收到 seq=5 但本地 lastSeq=2，应该做什么？【进阶】

记录空洞 [3,4]，插入 5 并更新 lastSeq，同时补拉 sync(3,4)；多空洞合并区间。

6. 为什么已读要用游标而不是未读计数器？【进阶】

计数器会被多端与重复回执弄漂移；游标单调，unread = max(0, lastSeq - max(各端游标)) 可随时重算。

7. 离线队列为什么必须串行发送？【进阶】

并行会让先入队的消息后到并放大重复；串行保证队头成功后再发下一条，跨会话可并行。

8. 哪些错误不应该重试？举三类。【进阶】

鉴权/权限、参数/业务校验、明确 4xx（除 408/429）；重试不改变结果，只会耗电并隐藏失败。

9. 10 万人大群瞬间 2000 条消息，前端如何避免卡死？【挑战】

批量合并更新 + 虚拟滚动 20~40 条 + 历史分页 + shallowRef/markRaw，高度测量集中到帧末。

10. 如何验证弱网方案有效？给出测试矩阵与指标。【挑战】

模拟 RTT 300ms + 丢包 20%、断连、后台恢复、批量补拉；看连接成功率、重连/ACK P95/P99、重复率与空洞恢复耗时。WS 丢包乱序需代理或服务端注入。

116.8 本章避坑清单 ​

#坑点现象根因正确姿势
1固定间隔重连断网/发布后握手 QPS 暴涨所有客户端同一时刻重试指数退避 + 抖动 + 上限
2鉴权失败也重试连上即被踢，循环不断关闭码未分类4001/4003 停止，刷新票据
3只靠 onclose 判死切网后长期「假在线」，消息发不出半开连接无感知心跳 + 超时 + 回前台探测
4重试重新生成 clientMsgId同一条消息落库两次幂等键每次变化一次动作只生成一次，重试复用
5按时间戳排序时钟快的用户消息插到顶部跨设备时钟不可信只按服务端 seq 排序
6只按 serverId 去重自己的重试经离线接口回来又出现忽略 clientMsgId 路径双键去重
7超前 seq 不补拉会话中间永久缺几条没有空洞检测记录空洞并合并区间补拉
8所有失败统一重试403/参数错误无限重试，耗电刷日志未做瞬时/永久分类4xx 直接失败，瞬时才退避
9离线队列并行 flush消息后发先至、重复发送多请求并发争抢单会话串行，队头成功再发
10队列无上限离线一周攒数千条，恢复时卡死未设条数/TTL有界队列 + 超期死信
11未读用计数器减一红点变负、永远清不掉多端/重复回执重复递减游标 + 派生 unread，幂等回执
12一次渲染全部历史点开会话白屏数秒、ANRDOM 与布局成本爆炸虚拟滚动 + 分页 + rAF 批量

心法：弱网治理不是「加个重试」，而是把不可靠网络下的每种异常都变成可观测、可收敛的状态。连接要退避且可分类，消息要双键去重且按 seq 排序，发送要有界保序且分级失败，已读要用单调游标，渲染要有窗口和预算。做到这五点，重连风暴、重复消息、丢序与红点错乱才不会在用户量上来后集中爆发。
