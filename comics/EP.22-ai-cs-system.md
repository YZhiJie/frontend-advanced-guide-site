# EP.22 AI 客服系统

> 对应正文：[21-frontend-ai-interview.md](../21-frontend-ai-interview.md)（21.3 AI 客服系统：端到端系统设计）· 示例：`examples/14-03-tool-ui.tsx`、`examples/14-05-context-budget.ts`、`examples/11-06-state-machine.ts`

## 剧情回顾

- **第 1 格**：老板要求"三天上线一个能查订单的 AI 客服"，标签君准备把模型 API Key 直接写进前端开干。
- **第 2 格**：码叔拦住：Key 绝不能落前端！正确拓扑是浏览器 → **自有 BFF**（鉴权/限流/计费/审计/编排）→ 大模型与业务工具。
- **第 3 格**：像素酱画出消息状态机（sending/streaming/tool_wait/done/error/aborted）与历史分层（内存 → IndexedDB → 服务端权威）。
- **第 4 格**：码叔结案——写操作必须用户二次确认、输出要消毒防 XSS、读屏器要 aria-live、还要有转人工兜底。

## 知识点拆解

### 第 1 格 · 为什么不能浏览器直连模型

- API Key 暴露到前端 = 被盗刷，任何人都能 F12 拿走；
- 没有限流、按租户计费、审计日志、内容合规、Prompt 版本管理；
- 无法注入业务上下文（RAG 知识、订单数据），也无法在模型故障时切换供应商。

### 第 2 格 · BFF 编排时序

```text
用户 → POST /api/chat/stream（sessionId + messageId）
BFF：鉴权 → 组装上下文/RAG → 调模型
模型：tool_call（查订单）→ BFF 执行业务工具 → 结果回灌
BFF：SSE 事件流 queue/token/tool_call/usage/done
```

- 每条消息由客户端生成幂等 `messageId`，重连/重试不重复扣量；
- BFF 注入 `x-request-id` 串联全链路日志；
- 工具调用是**两段式**：模型提意图 → BFF 校验权限后执行 → 结果回灌续写。

### 第 3 格 · 状态机与历史分层

- 用显式状态机替代一堆布尔标志位，UI 按状态渲染（重试只在 error、停止只在 streaming）；
- 用户消息乐观上屏，失败就地变红可重试；
- 存储三层：运行态内存（zustand/pinia）→ IndexedDB 缓存最近会话 → 服务端唯一权威；localStorage 只放草稿；
- 发给模型的不是全量历史，而是按 token 预算裁剪后的上下文（system + 最近 N 条 + 更早的摘要）。

### 第 4 格 · 安全、体验与兜底

- 危险工具（下单/退款/改地址）必须用户二次确认，**模型不是授权主体**；每次调工具校验会话归属防 IDOR；
- 模型输出是不可信 HTML，Markdown 渲染必须消毒（详见 EP.24）；
- a11y：消息列表 `aria-live="polite"`、生成中 `aria-busy`、动画尊重减弱动效设置；
- 置信度低/连续负反馈/关键词命中 → 转人工，人工端复用同一套消息系统。

## 坑点清单

> 🔗 正文对照：[《21.7.3 常见误区总清单》](../21-frontend-ai-interview#_21-7-3-常见误区总清单)

1. Key 写进前端代码或环境变量（`VITE_` 前缀会打进包）；
2. 模型直接触发写操作：无二次确认、无权限校验；
3. 刷新页面进行中的回答就丢：流应可按 messageId 重新订阅/续传；
4. 错误一律 toast：网络断、限流、安全拦截应三类三话术，可就地重试；
5. 只存本地不存服务端：无法跨设备、无法审计与合规留存。

## 自测 3 题（含答案）

1. **一条消息从发送到回答完成经过哪些环节？**——乐观上屏 → BFF 鉴权编排 → RAG/工具两段式调用 → SSE 事件流 → 分帧解析 → rAF 渲染 → 持久化 → usage 计费；全程带幂等 ID 与 request-id。
2. **如何设计对话历史？**——服务端权威存储 + IndexedDB 缓存 + localStorage 草稿；游标分页、按会话懒加载；发给模型前按 token 预算裁剪，旧历史折叠为摘要。
3. **系统设计题怎么答才像有生产经验？**——先澄清需求与 SLA，再讲 BFF 拓扑、模型分级路由、工具权限、降级转人工、指标（解决率/TTFT/幻觉率）与成本，最后讲安全合规；不要一上来谈选型和微调。
