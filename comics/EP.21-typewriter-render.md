# EP.21 打字机渲染

> 对应正文：[21-frontend-ai-interview.md](../21-frontend-ai-interview.md)（21.2 打字机效果：从「能用」到「流畅」）· 示例：`examples/14-02-stream-chat.tsx`

## 剧情回顾

- **第 1 格**：标签君用 `setInterval` 每来一个 token 就 setState 一次，答案还没出完，页面已经卡成幻灯片，光标疯狂乱跳。
- **第 2 格**：码叔揭秘节奏算法——token 先入待渲染队列，`requestAnimationFrame` 每帧合批消费；积压多就加速、流结束快追平。
- **第 3 格**：像素酱实证三种方案：CSS `steps()` 适合固定横幅、setInterval 只配 Demo、rAF 队列才是流式 UI 的正解；切字还要按字形簇别切碎 emoji。
- **第 4 格**：码叔结案——别每帧全量解析 Markdown、自动滚动先贴底检测、停止就立即呈现全文。

## 知识点拆解

### 第 1 格 · 为什么逐字 setState 会卡

- token 到达频率可达 50~150 次/秒，每次 setState 都触发完整渲染管线；
- 若气泡里再做 Markdown 解析与高亮，CPU 被长任务占满 → 掉帧、输入框卡顿；
- 同步读 `scrollHeight` 再写滚动位置还会触发强制同步布局。

### 第 2 格 · 队列 + rAF 合批

```text
网络 token ──▶ 待消费队列 ──▶ rAF 回调：本帧取 N 字 ──▶ 一次 setState
```

- 一帧内到达的多个 token **合并成一次文本提交**；
- 自适应速度：`步长 = clamp(积压 / 追平时长, 1, 单帧上限)`，既跟得上流又有打字感；
- rAF 与刷新率对齐、切后台自动暂停；停止时取消 rAF 并一次性显示已到达全文。

### 第 3 格 · 三方案与字符粒度

| 方案 | 评价 |
| ---- | ---- |
| CSS `steps()` + width | 零 JS，但中文变宽字符崩版、不能接动态流 |
| setInterval 逐字 | 直观但后台漂移、与刷新不同步 |
| **rAF 队列消费** | 合批、可暂停/继续/中止，生产首选 |

- `str[i]` 按 UTF-16 码元切，会切碎 emoji 代理对；`for...of` 按码点，组合字形用 `Intl.Segmenter(granularity:'grapheme')`。

### 第 4 格 · 高级体验细节

- 光标用 `::after` + opacity 闪烁，只动合成层属性，并尊重 `prefers-reduced-motion`；
- Markdown 解析降频到 50~100ms 一次，流结束做终态渲染（详见 EP.24）；
- 贴底检测：距底 < 80px 才自动跟随，否则显示"新内容 ↓"按钮，不抢用户阅读位置。

## 坑点清单

> 🔗 正文对照：[《21.7.3 常见误区总清单》](../21-frontend-ai-interview#_21-7-3-常见误区总清单)

1. 每 token 一次渲染：长任务 + 掉帧，必须 rAF 合批；
2. 无脑 `scrollTop = scrollHeight`：用户上滑被强行拽回底部；
3. `str[i]` 切字：emoji 乱码，用码点/字形簇；
4. 停止后还在慢慢吐字：用户点停止应立即呈现全部已到达文本并清空队列。

## 自测 3 题（含答案）

1. **为什么 rAF 比 setInterval 更适合打字机？**——与屏幕刷新对齐不掉帧；后台标签页自动暂停不堆积爆发；一帧只提交一次，天然合批。
2. **网络突然吐来一大段时怎么办？**——按帧预算自适应加速（积压/追平时长，夹上单帧上限）；流结束允许快速追平，并提供"立即显示全部"，消费体验优先于打字形式。
3. **打字机有哪些重排陷阱？**——避免逐字改 width/height、避免读后立刻写造成强制同步布局；容器定宽、滚动在下一帧统一处理、光标只动 opacity。
