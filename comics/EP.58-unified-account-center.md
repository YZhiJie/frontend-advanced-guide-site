# EP.58 一个账号，全家通行

> 对应正文：[第四十四部分 · 多系统统一账号中心](../44-account-center.md)

## 剧情回顾

- **第 1 格**：标签君在 OA、CRM、工单、数据平台之间来回切换，改个密码要跑三个页面。四套系统各写一遍 `login.vue` / `register.vue` / `reset.vue`，一共 12 个页面，密码策略、错误文案、审计入口各有四份。
- **第 2 格**：码叔点破关键——身份只在一处产生，会话在各处短暂存在。业务系统只做三件事：302 到中心登录页、后端用 ticket 换用户信息、种下本地短会话。全局会话只存在中心域，ticket 60 秒、单次、绑定 appId。
- **第 3 格**：像素酱验证回跳安全。`redirect` 参数不能直接信任，必须 `new URL()` 解析后逐项校验 protocol、origin、path；`oa.example.com.evil.com` 与 `oa.example.com@evil.com` 都会被拦下，回调时还要核对 state。
- **第 4 格**：码叔结案——改密撤销其它端会话，重置撤销全部会话；找回入口无论账号是否存在都返回「已发送」。提示「该手机号未注册」等于免费提供账号枚举接口。

## 知识点拆解

### 第 1 格 · 四套账号的代价

```text
login.vue  register.vue  reset.vue
× 4 套系统 = 12 个页面
```

复制页面的成本不只是 12 个文件，而是四份会各自漂移的安全策略：

| 维度 | 各写一遍的后果 |
| ---- | ---- |
| 密码策略 | 有的要求 8 位，有的要求 12 位，用户困惑 |
| 错误文案 | 有的提示「密码错误」，有的提示「账号不存在」 |
| 验证码 | 有的发短信，有的不发，被刷成本不同 |
| 审计日志 | 四套格式，出事时拼不出完整时间线 |

账号数据也各存一份：员工离职后要在四个后台分别停用，漏一个就是遗留权限。

### 第 2 格 · 三层会话与一次性票据

```text
1. 302 → account.example.com/login?redirect=...
2. 后端 POST /sso/redeem { ticket } → 用户信息
3. Set-Cookie: 本地会话（30min）
```

| 层 | 存放位置 | 生命周期 | 作用 |
| ---- | ---- | ---- | ---- |
| 全局会话 | 中心域 HttpOnly Cookie | 空闲 2 小时 | 真正的「已登录」 |
| 一次性 ticket | URL 参数，60 秒 | 单次 | 中心 → 业务系统的换票凭证 |
| 本地会话 | 业务域 Cookie / JWT | 30 分钟 | 业务系统自己认的凭证 |

ticket 必须同时满足**单次消费**、**绑定 appId**、**短 TTL** 三个条件：只单次不绑定时，A 系统的票可换 B 系统会话；只绑定不设 TTL 时，泄露的票可长期复用。

完整实现见 [44-02-login-ticket.ts](../examples/44-02-login-ticket.ts) 与 [44-04-sso-slo.ts](../examples/44-04-sso-slo.ts)。

### 第 3 格 · 回跳白名单四道关

```ts
const u = new URL(redirect)
if (u.protocol !== "https:") reject()
if (u.origin !== app.origin) reject()
if (!pathOk(u.pathname)) reject()
```

四道关的顺序不能省：

1. **协议**：只允许 `https:`，挡掉 `javascript:` 与 `http:` 降级；
2. **userinfo**：`oa.example.com@evil.com` 的实际 host 是 `evil.com`，解析后 origin 不匹配即拦；
3. **origin**：精确比较，挡掉 `oa.example.com.evil.com` 这类后缀伪装；
4. **path**：只允许登记过的路径前缀，避免开放站内跳转被拿来做钓鱼落地页。

此外发起时生成随机 `state` 存进会话，回调时原样比对，防止登录 CSRF。八种攻击形态的完整用例在 [44-03-redirect-whitelist.ts](../examples/44-03-redirect-whitelist.ts)。

### 第 4 格 · 改密撤会话与防枚举

```text
changePassword → revoke all but current
resetPassword  → revoke ALL sessions
requestReset   → 假成功，防账号枚举
```

两个入口的安全语义不同：

| 入口 | 前置条件 | 会话处理 | 理由 |
| ---- | ---- | ---- | ---- |
| 修改密码 | 已登录 + 验旧密码 | 撤销除当前会话外全部 | 用户正在操作，保留当前体验 |
| 找回密码 | 手机验证码 | 撤销全部会话 | 账号可能已失陷，全部重新登录 |

重置令牌只存哈希、15 分钟、单次使用；找回入口无论手机号是否存在都返回「已发送」，避免把注册接口变成账号枚举器。实现见 [44-05-password-change-reset.ts](../examples/44-05-password-change-reset.ts)。

## 坑点清单

> 🔗 正文对照：[《44.8 本章避坑清单》](../44-account-center#_44-8-本章避坑清单)

1. **每套系统各写一遍身份页面**：策略与文案必然漂移。统一到账号中心，业务系统只保留接入代码。
2. **ticket 不设单次或不绑 appId**：票据被截获后可换任意系统的会话。三个条件必须同时满足。
3. **`redirect` 直接 `location.href`**：开放重定向，真域名把人送去钓鱼站。必须解析 URL 后逐项校验。
4. **只校验 origin 不校验 protocol**：`javascript:` 伪协议仍可能执行。协议、userinfo、origin、path 四道关缺一不可。
5. **改密后不撤会话**：旧设备上的会话继续有效，等于密码泄露后没止损。
6. **找回密码提示「账号不存在」**：免费提供账号枚举接口。统一返回「已发送」。

## 自测 3 题

**1. 为什么登录页的编排要「先检查锁定，再验密」？**

<details>
<summary>参考答案</summary>

如果先验密再查锁定，攻击者每次尝试都会触发一次真实的密码哈希计算与数据库比对，锁定形同虚设，还会给服务端带来无谓的 scrypt 计算开销。先检查失败计数与锁定截止时间，可在爆破进行到第 6 次时直接拒绝，不消耗验密资源；同时锁定时仍要返回与密码错误一致的文案，避免泄露「这个账号存在且已被锁」。

</details>

**2. 一次性 ticket 为什么必须同时满足「单次、绑定 appId、短 TTL」？**

<details>
<summary>参考答案</summary>

单次消费防止重放：票据被浏览器历史、日志或 Referer 泄露后无法二次使用。绑定 appId 防止横向越权：A 系统签发的票不能在 B 系统兑换，否则任意接入方都能拿到别家用户。短 TTL 把泄露窗口压到 60 秒内，即使前两条都被绕过，票据也很快失效。三者是正交的防线，缺一条都会留下可利用的缺口。

</details>

**3. 修改密码和重置密码在「撤销会话」上为什么策略不同？**

<details>
<summary>参考答案</summary>

修改密码是已登录用户在正常操作，且已经验证过旧密码，威胁模型是「其它设备可能已泄露」——因此撤销除当前会话外的全部会话，既止损又保留用户当前体验。重置密码发生在未登录场景，只能靠手机验证码证明身份，威胁模型应假设账号已经失陷——因此撤销全部会话（包括可能存在的攻击者会话），要求所有端重新用新密码登录。

</details>
