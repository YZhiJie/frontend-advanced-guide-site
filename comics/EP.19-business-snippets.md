# EP.19 业务片段百宝箱

> 对应正文：[19-business-snippets.md](../19-business-snippets.md)（声明式表单校验 / 输入格式化与提交锁 / 列表查询 URL 同步 / 类型安全存储 / 树结构 / 文件与剪贴板 / 埋点曝光 / 按钮级权限）· 示例：`examples/19-01-form-validation.ts` ~ `examples/19-08-permission.ts`

## 剧情回顾

- **第 1 格**：标签君发现三个项目的 utils 里躺着同一套 validatePhone / withSubmitLock——每开一个新项目就重抄一遍，连边界 bug 也一并抄走。
- **第 2 格**：码叔揭秘声明式校验：规则是"断言 + 文案"的数据，schema 可复用、可后端下发，校验引擎只有一份。
- **第 3 格**：像素酱实证 withSubmitLock：五连点支付只执行一次任务，锁在 finally 里释放，报错也不会锁死按钮。
- **第 4 格**：码叔结案——好片段三要素：纯函数、框架无关、边界齐全；并给出三条高频坑点。

## 知识点拆解

### 第 1 格 · 为什么要把业务逻辑沉淀成片段

- 表单校验、提交锁、倒计时这类逻辑**单个看都很小，但边界极多**：`0` 算不算空？报错了锁解不解？组件卸载定时器清不清？
- 每次重写都会把坑重新踩一遍；沉淀成"复制即可用"的片段，把边界处理一次性写对；
- 收录原则：带边界处理与坑点注释、核心逻辑写成框架无关的纯函数、DOM 操作与纯逻辑分离（可直接 `npx tsx` 验证 + 配单测）。

### 第 2 格 · 声明式表单校验

```ts
const schema = {
  phone: [required('请输入手机号'), pattern(/^1[3-9]\d{9}$/, '手机号格式不正确')],
  code: [required('请输入验证码'), length(6, 6, '验证码为 6 位数字')],
};
validateForm(form, schema);              // 提交时：收集所有字段错误
validateField('phone', form, schema);    // blur 时：只报当前字段第一条错误
```

- 每条规则 = `validate(value, form)` 断言 + `message` 文案；规则是数据，可 JSON 化由后端下发，动态表单天然支持；
- **blur 单字段、submit 全表**：避免用户没输完就满屏红字，提交时一次性标红所有问题；
- ⚠️ `required` 不能只判 falsy：`0`（数量）、`false`（开关）是合法值，只有 `null/undefined/''/空数组` 算空；
- 前端校验是体验不是安全，同一套规则服务端必须重放一遍。

### 第 3 格 · 提交防重锁

```ts
const submit = withSubmitLock(createOrder);
// 在途期间再次调用直接返回 undefined（本次点击被忽略）
```

- 锁在 `finally` 里释放：接口失败、组件抛错都必须解锁，否则按钮永久禁用；
- 前端锁 ≠ 幂等：两个标签页、弱网重试、消息重放仍可能产重复单，服务端要按业务幂等键（订单号 / requestId）去重；
- 倒计时同理：必须返回 `cancel()`，组件卸载或重新发送时清理定时器；且以**服务端响应成功**为准开始倒计时，不要点击即开始。

### 第 4 格 · 片段沉淀三原则

- **纯函数、框架无关**：React / Vue / 小程序都能接，可直接进 `src/utils` 配单测；
- **边界齐全**：并发、过期、越界、失败重试——happy path 之外的分支才是片段的价值所在；
- **DOM 与纯逻辑分离**：下载、剪贴板、IntersectionObserver 等 DOM 操作单独成层，纯逻辑可脱离浏览器验证；
- 附赠原则——列表查询状态放 URL：刷新不丢、链接可分享、前进后退天然可用；`page` 越界用 `Math.min(Math.max(1, page), totalPages)` 夹回。

## 坑点清单

> 🔗 正文对照：[《19.11 本章避坑清单》](../19-business-snippets#_19-11-本章避坑清单)

1. `required` 用 `!value` 判断：`0` 和 `false` 被误杀——只把 `null/undefined/''/空数组` 视为空；
2. 提交锁在 `then` 里释放：接口报错后按钮永久锁死——必须在 `finally` 释放；
3. 倒计时没有返回取消函数：路由切换后定时器仍在跑（内存泄漏）——卸载即 `cancel()`；
4. 查询状态只放组件 state：刷新 / 分享链接全丢——放 URL query，并用白名单过滤脏参数；
5. 把"隐藏无权限按钮"当权限控制：接口仍可被直接调用——前端隐藏是防误触，服务端鉴权才是防越权。

## 自测 3 题（含答案）

1. 声明式校验相比散落在回调里的 if-else，解决了哪三个问题？——**错误文案集中一处（产品改文案只动一处）、规则跨页面/跨端复用、schema 可序列化由后端下发支撑动态表单**。
2. `withSubmitLock` 为什么把解锁放在 `finally`？前端加了锁服务端还要幂等吗？——**业务抛错时 `then` 不执行会永久锁死按钮，`finally` 保证必释放；要，前端锁挡不住多标签页与网络重试，服务端必须按幂等键去重**。
3. 列表查询状态为什么推荐放 URL？数据被删光后页码越界怎么办？——**URL 即状态：刷新、分享、前进后退免费获得同一视图；用 total 算出 totalPages 后把 page 夹回合法区间，再以夹回后的页码重新请求**。
