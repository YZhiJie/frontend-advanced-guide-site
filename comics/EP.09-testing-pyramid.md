# EP.09 测试金字塔

> 对应正文：[09-testing.md](../09-testing.md)（9.1 测试金字塔与整体策略 / 9.2 单元测试与 Vitest / 9.5 Mock 策略与 MSW）· 示例：`examples/09-02-money.test.ts`、`examples/09-05-msw-handlers.ts`

## 剧情回顾

- **第 1 格**：标签君的项目没有自动化测试，改一行金额逻辑漏测 0 元单，上线显示 -0.00。
- **第 2 格**：码叔揭秘测试金字塔：单元多而快、集成居中、E2E 少而稳，越往上越贵越脆。
- **第 3 格**：像素酱实证"测行为不测细节"：单测守边界（0/负数/精度），组件测试用 `getByRole`。
- **第 4 格**：码叔结案——网络层用 MSW 拦截，CI 门禁强制执行，否则测试形同虚设。

## 知识点拆解

### 第 1 格 · 手工回归的极限

- 需求越多回归面越大，手工不可能覆盖所有路径和边界；
- 边界值（0、负数、空串、超长、精度）恰恰是 bug 高发区，也是最容易写进断言的；
- 自动化测试的核心价值：**让机器替你把回归跑一遍**。

### 第 2 格 · 测试金字塔

```
        /  E2E  \     少而稳（分钟级）
       / 集成测试 \    中等（组件/模块级）
      /  单元测试  \   多而快（毫秒级）
```

- **单元测试**：函数/工具层，毫秒级反馈，失败好定位，占比最大；
- **集成测试**：组件渲染、模块协作，性价比最高的一层；
- **E2E**：真实浏览器走完整用户路径，最接近真实但最慢最脆，只留关键路径。

### 第 3 格 · 测行为，不测实现

```ts
test('金额格式化边界', () => {
  expect(format(0)).toBe('0.00');      // 边界：0
  expect(format(-1)).toBe('-0.01');    // 边界：负数
});
// 组件测试：
getByRole('button', { name: '提交' });
```

- 断言「输入 → 输出」这个契约，而不是内部调了哪个私有方法；
- Testing Library 的哲学：**以用户视角查询元素**（role/name），重构内部实现测试照常通过。

### 第 4 格 · MSW 与 CI 门禁

- MSW 在**网络层**拦截请求，前后端联调场景不用起真服务，也能模拟 500/超时等异常；
- mock 原则：mock 掉外部依赖（网络/时间/随机），不 mock 被测系统自己；
- CI 强制跑测试 + 覆盖率门禁，不达标不能合并——否则再好的测试也会逐渐腐烂。

## 坑点清单

> 🔗 正文对照：[《9.11 本章避坑清单》](../09-testing#_9-11-本章避坑清单)

1. 测实现细节（内部 state、私有方法）：一重构测试全碎，维护成本反噬；
2. mock 过度：把被测逻辑也 mock 了，测试全绿但真实链路是坏的；
3. 测试不进 CI 门禁：只在本地想起来才跑，很快变成"永远挂着的测试"。

## 自测 3 题（含答案）

1. 测试金字塔三层各有什么特点？——**单元多而快、集成中等性价比高、E2E 少而稳覆盖关键路径，越往上越贵越脆**。
2. 为什么组件测试推荐 getByRole 而不是 testId？——**getByRole 以用户视角（可访问性语义）查询，测的是行为而非实现，重构不影响**。
3. MSW 和普通 mock 函数的区别？——**MSW 在网络层拦截真实请求，走完整的请求/响应链路；mock 函数只是替换单个函数调用**。
