# EP.11 设计模式实战

> 对应正文：[11-patterns-architecture.md](../11-patterns-architecture.md)（11.1 前端常用设计模式）· 示例：`examples/11-04-eventbus.ts`、`examples/11-05-command-undo.ts`、`examples/11-06-state-machine.ts`

## 剧情回顾

- **第 1 格**：标签君的项目模块像蜘蛛网：购物车直接调订单页和库存页，改一行崩三处。
- **第 2 格**：码叔揭秘 EventBus 发布订阅：发布者不认识订阅者，双方只认识事件名。
- **第 3 格**：像素酱实证状态机：三个布尔 8 种组合太多非法态，状态机只留合法迁移。
- **第 4 格**：码叔结案——命令模式把每步操作变成可撤销对象，undo/redo 自然生长出来。

## 知识点拆解

### 第 1 格 · 耦合之痛

```ts
cartModule.refresh(orderPage);   // A 直接认识 B
```

- 直接调用形成蜘蛛网：一个模块的签名变化沿依赖链传染；
- 判断标准：**新需求要改几个文件？** 改得越多，耦合越重；
- 解耦的通用思路：把「直接调用」换成「通过中介通信」。

### 第 2 格 · 观察者与发布订阅

```ts
bus.on('cart:changed', renderOrder);   // 订阅
bus.emit('cart:changed', cart);        // 发布
```

- **观察者模式**：主题直接持有观察者列表，1 对多通知，无中介；
- **发布订阅模式**：双方通过 EventBus 通信，互相不认识，可跨模块/跨页面；
- 代价：事件多了之后流向难追踪——事件名要有命名空间（如 `cart:changed`），数量要克制。

### 第 3 格 · 状态机

```ts
// ❌ 三布尔：2^3 = 8 种组合，一半非法
// ✅ 单一状态 + 显式迁移表
type State = 'idle' | 'loading' | 'success' | 'error';
machine.transition(state, event);  // 非法迁移直接报错
```

- 多个布尔标志位会产生「loading=true 且 error=true」这类不可能也不该存在的组合；
- 状态机把合法状态显式列出、迁移路径显式声明，**非法状态在类型层面就不存在**。

### 第 4 格 · 命令模式与撤销

```ts
interface Command {
  do(): void;
  undo(): void;
}
// 每次 push 进历史栈，undo 就 pop 反着执行
```

- 把操作封装成对象：执行 `do`、撤销 `undo`，编辑器/画布工具的 undo/redo 就这一个骨架；
- 其他前端高频模式：策略（表单校验规则）、适配器（多支付渠道）、单例（弹窗管理）。

## 坑点清单

> 🔗 正文对照：[《11.6 本章避坑清单》](../11-patterns-architecture#_11-6-本章避坑清单)

1. 布尔标志位组合爆炸：状态多了以后条件判断组合失控，用状态机收敛；
2. EventBus 事件泛滥：全局事件满天飞，出问题无从追踪——限定命名空间并控制数量；
3. 为模式而模式：三层抽象包一个 if，复杂度不减反增——模式是套路不是 KPI。

## 自测 3 题（含答案）

1. 观察者和发布订阅的核心区别？——**观察者主题直接通知观察者（无中介）；发布订阅经事件中心转发（双方解耦）**。
2. 为什么状态机比多个布尔标志好？——**状态机显式声明合法状态与迁移，非法状态在类型/运行时层面即被拒绝；布尔组合产生大量非法组合**。
3. 命令模式怎么实现 undo？——**把操作封装成 { do, undo } 对象压栈，撤销时弹栈执行 undo**。
