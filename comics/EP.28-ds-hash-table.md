# EP.28 哈希表一秒定位

> 对应正文：[22-frontend-data-structures.md](../22-frontend-data-structures.md)（22.4 哈希表：O(1) 的定位魔法）· 示例：`data-structures/examples/22-04-hash-table.ts`

## 剧情回顾

- **第 1 格**：标签君十万条通讯录用数组 `find` 查手机号，最坏扫完十万条，页面卡 3 秒，用户直接跑了。
- **第 2 格**：码叔揭秘——哈希函数把 key 算成桶下标，`h = (h * 31 + code) % capacity`，31 是质数经验值；冲突用链地址法挂小链。
- **第 3 格**：像素酱实证 `put("abc")`：哈希 96354 模 7 落进桶②，与已有键挂链；负载因子超过 0.75 就扩容 ×2 取质数重新哈希。
- **第 4 格**：码叔结案——JS 的 Object/Map/Set/WeakMap 骨子里都是哈希表；对象当键会被 toString 撞车，冲突扎堆会退化。

## 知识点拆解

### 第 1 格 · 顺序查找的天花板

- `find` 是线性扫描：平均 n/2 次比较，最坏 n 次，O(n)；
- 十万条数据每次查询都扫一遍，主线程长时间占用，页面掉帧；
- 数据量一大，"遍历找"这条路就走死了。

### 第 2 格 · 哈希函数与链地址法

```ts
function hash(key: string, capacity: number) {
  let h = 0
  for (let i = 0; i < key.length; i++) {
    h = (h * 31 + key.charCodeAt(i)) % capacity
  }
  return h
}
```

- **31 是质数经验值**：乘质数再取模，哈希值分布更均匀、冲突更少（JDK 的 String.hashCode 同款）；
- **桶（bucket）** = 底层数组的一个槽位，`hash % capacity` 直接算出下标，所以查改是均摊 O(1)；
- **冲突**：两个 key 算出同一桶号——链地址法在桶里挂一条小链，查找时桶内再逐个比对 key。

### 第 3 格 · put("abc") 走查与扩容

- `"abc"` → 逐字符 `h*31+code` → 96354；`96354 % 7 = 2`，落进桶②；
- 桶②已有 `"xyz"`（同模冲突），挂到链尾；
- **负载因子** = 元素数 / 桶数，超过 0.75 触发扩容：容量 ×2 后取质数（7→17），所有 key **重新哈希**搬迁；
- 扩容是 O(n) 的，但摊还到每次写入仍是 O(1)。

### 第 4 格 · JS 里的哈希表家族

- **Object**：键只能是 string/Symbol，对象键会被 `toString()` 成 `"[object Object]"` 互相覆盖；
- **Map**：任意类型键、保留插入序、有 `size`，频繁增删首选；
- **Set**：只有键没有值的哈希表，天然去重；
- **WeakMap/WeakSet**：键是弱引用，不阻止 GC 回收，适合给 DOM/对象挂私有数据。

## 坑点清单

> 🔗 正文对照：[《22.11 本章避坑清单》](../22-frontend-data-structures#_22-11-本章避坑清单)

1. 对象直接当 Object 键：`obj[{}]` 实际是 `obj["[object Object]"]`，不同对象键互相覆盖——要任意类型键就用 Map；
2. 哈希函数烂或容量不取质数：冲突扎堆，桶链变长，查找退化成 O(n)；
3. 忘记扩容：负载因子长期 1.0+，哈希表名存实亡；扩容时机一般设在 0.75；
4. 自定义对象当 Map 键却改了其参与哈希的字段：之后 `get` 永远找不到（可变 key 大坑）。

## 自测 3 题（含答案）

1. **哈希表为什么能 O(1) 定位？**——哈希函数把 key 算成底层数组下标，直接按地址访问，不用逐个比较；冲突用链地址法兜底，所以是均摊 O(1)。
2. **为什么哈希函数爱乘 31 这类质数？**——乘质数能打散哈希值的分布规律，配合质数容量取模，让 key 均匀落到各桶，显著减少冲突。
3. **Map 和 Object 怎么选？**——键是字符串且结构固定用 Object；键类型任意、频繁增删、需要插入序或 `size` 用 Map；要给对象挂数据又怕内存泄漏用 WeakMap。
