EP.06 HTTP 缓存与竞态 ​

对应正文：06-network.md（6.2 缓存策略详解 / 6.5 竞态处理与请求取消）· 示例：examples/06-01-cache-strategy.ts、examples/06-05-chunk-upload.ts

剧情回顾 ​

  • 第 1 格：标签君的列表每次都全量拉取 2MB，弱网下刷新要等好几秒。
  • 第 2 格：码叔揭秘强缓存——Cache-Control: max-age 时长内浏览器直接用本地副本，连请求都不发。
  • 第 3 格：像素酱实证协商缓存——带 If-None-Match 问服务器，内容没变返回 304 省流量。
  • 第 4 格：码叔结案——缓存之外还有竞态坑：旧响应后到覆盖新结果，要靠取消与序号治理。

知识点拆解 ​

第 1 格 · 没有缓存的代价 ​

  • 每次进页面都发完整请求，静态资源也全量下载；
  • 弱网环境下白屏/转圈时间被无限放大，用户直接流失；
  • 缓存是前端性能优化的第一杠杆：不发请求永远是最快的。

第 2 格 · 强缓存（Freshness） ​

http
Cache-Control: max-age=31536000
  • 时长内浏览器完全不发请求，直接读磁盘/内存副本；
  • 适合带 hash 指纹的静态资源（app.a3f9.js），内容变文件名就变；
  • no-cache 不是不缓存，而是"可以缓存但每次要协商验证"。

第 3 格 · 协商缓存（Validation） ​

http
If-None-Match: "abc123"   →   304 Not Modified
  • 浏览器带上上次的 ETag（内容指纹）问服务器；
  • 一致 → 304，无响应体，省流量；变了 → 200 返回新内容；
  • ETag 按内容生成，比 Last-Modified（秒级时间戳）更精确，一秒内多次修改也能识别。

第 4 格 · 竞态与缓存陷阱 ​

  • 搜索框快速输入时，先发出的请求可能后返回，旧结果覆盖新结果；
  • 治理三板斧：AbortController 取消上一个、请求序号只认最新、防抖合并输入；
  • index.html 是所有静态资源入口，一旦强缓存，新版本发布用户永远看不到。

坑点清单 ​

🔗 正文对照：《6.9 本章避坑清单》

  1. 搜索联想/筛选请求不处理竞态：旧响应后到覆盖新结果，界面显示错误数据；
  2. index.html 设置了长 max-age：发新版后用户仍停留在旧页面，报错找不到新 chunk；
  3. max-age 给得过长且无 hash 指纹：内容更新不及时，只能靠用户强刷。

自测 3 题（含答案） ​

  1. 强缓存和协商缓存的区别？——强缓存不发请求直接用本地副本；协商缓存发请求向服务器验证新鲜度，返回 304 或 200。
  2. no-cache 和 no-store 的区别？——no-cache 可缓存但每次协商验证；no-store 完全不缓存。
  3. 搜索输入的竞态怎么治理？——AbortController 取消上一请求 + 请求序号只渲染最新那次，必要时配合防抖。
