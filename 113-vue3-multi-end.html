第一百一十三部分 · Vue 3 单仓多端工程——PC Web + H5/PWA 一体化 ​

🧭 返回总目录｜上一篇：第一百一十二部分 · GraphQL 客户端实战——Schema、缓存与订阅｜关联章节：第七十三部分 · 多端共用架构 · 第八十八部分 · UniApp 跨端开发 · 第五十六部分 · 离线与本地缓存全景 · 第一百零二部分 · Element Plus / Vant 企业实战 · 第九部分 · 测试策略

本部分内容 ​

单仓多端的目标不是「少写一套页面」，而是同一份业务内核产出两个可独立发布、互不污染的产物：PC Web 要宽屏、鼠标、高信息密度；H5/PWA 要触控、窄屏、可安装、弱网可用。本册聚焦 Vue 3 + Vite 的落地：目录分层、构建矩阵、能力适配器、UI 分流、路由/状态复用、PWA 更新与双端 CI，目标业务复用 80%+、产物不串味。

113.1 目标与复用率期望 ​

概念解析 ​

单仓多端是一个业务模型、两套表现层、两个发布物。端差异只应出现在 adapters 与 ui-*，泄漏到 core 会让业务规则分叉。复用率按层统计：

层内容合理复用率说明
core 领域层定价、购物车、优惠、订单状态机90%+纯 TS，逐字节共享
services 接口层storage/share/payment 等契约100%只有类型与接口
composables表单、列表、请求编排70%~85%端差异用能力接口抹平
ui-pc / ui-h5页面、业务组件、交互40%~70%两套交互范式
adapters端能力实现≈0%端端不同是设计目的

真实场景：某海外 DTC 品牌的 Vue 3 商城，PC 承担商品对比、多步结账、地址簿；H5/PWA 承担投放页、一键结账与离线复购。两端共享定价、税费、优惠校验、购物车与订单状态机（约 80% 业务代码），UI 分别用 Element Plus 与 Vant。业务规则只改一处，UI 缺陷按端独立修。

反例：团队定下「复用率 95%」KPI，把 ProductList.vue 写成 el-table 与 van-list 双分支同时 import。H5 首屏 JS 从 210KB 涨到 320KB，CSS 变量互相覆盖；平板落入宽屏分支，得到小字号表格。运行时 if 不会删除另一端的 import。

应用实践 ​

  • 立项先定端角色：PC 做深度操作，H5 做消费与轻操作。
  • 业务域抽到 core，交互域允许两端独立。

最佳实践 ​

  • ✅ 复用率进 CI 报告（共享包被几个端 import），而不是喊口号。
  • ✅ 第一天就分 ui-pc / ui-h5，后期拆目录成本远高于建目录。

113.2 目录与分层 ​

概念解析 ​

按依赖方向切目录，而不是按页面切：

src/
  core/              # 纯 TS 领域逻辑，零 Vue、零 DOM
  services/          # 能力接口：storage/share/payment
  adapters/pc|h5/    # 各自实现，可碰平台 API
  composables/       # 共享 Vue 逻辑，只依赖 core + services
  ui-shared/         # 无 UI 库依赖：价格、评分、空态
  ui-pc/             # Element Plus 页面与组件
  ui-h5/             # Vant 页面与组件
  router/  stores/   # 共享守卫、路由表、Pinia store
  apps/pc|h5/        # main.ts、index.*.html、manifest

依赖铁律：ui/composables → core/services、core → services、adapters → services、apps → 全部。core 永不 import adapters，ui-pc 永不 import ui-h5。端能力通过接口注入：core 只声明「需要 storage」，由 apps 启动时放入实现。

为什么必须物理隔离？Code Review 拦不住「顺手 import 一个小工具」，一次顺手就可能把 Element Plus 拖进 H5 产物；目录隔离 + ESLint 才可靠。

应用实践 ​

  • @ui 别名按 mode 指向 ui-pc 或 ui-h5，业务代码只写 import X from '@ui/views/ProductDetail.vue'。
  • services 只放接口与错误类型，实现放 adapters，两端跑同一套契约测试。

最佳实践 ​

  • ✅ ESLint 禁止 ui-pc ↔ ui-h5、core → adapters。
  • ✅ apps 是唯一组装点：选 adapter、注入依赖、注册 UI 库。
  • ⚠️ ui-shared 只放无交互范式的组件；带布局或手势的不要硬共享。

113.3 构建矩阵 ​

概念解析 ​

把 mode 当作唯一输入：一个 mode 决定环境变量、入口 HTML、产物目录、PWA 开关、体积预算与 UI 别名。禁止业务代码再用 if (isPc) 选入口，否则构建结果依赖运行时，CI 无法静态校验。

mode入口产物PWA首屏 JS 预算（gzip）
pc-devindex.pc.htmldist/pc-dev否900KB
pc-prodindex.pc.htmldist/pc否520KB
h5-devindex.h5.htmldist/h5-dev否520KB
h5-prodindex.h5.htmldist/h5是260KB

只有 VITE_ 前缀会暴露给客户端，密钥绝不能写进 .env（见 66 册）。PWA 只在 h5-prod 开启；PC 装 SW 只会增加缓存排障成本。Vite 配置只需做三件事：loadEnv 读 mode、@ui 别名按端指向、rollupOptions.input 只放当前端入口。

产物校验不能只看「构建成功」：入口、预算、PWA 资源、串端依赖，每条都要成为 CI 硬门禁。完整实现见 examples/113-02-build-matrix.ts：deriveTarget 按 mode 推导，validateBuild 一次性返回全部违约项。

运行方式：npx tsx examples/113-02-build-matrix.ts

应用实践 ​

  • CI 矩阵跑 pc-prod 与 h5-prod，各自上传 artifact；预览环境按端生成 URL。
  • 产物一次构建、多区域 CDN 分发，不要按地区重复构建。
  • H5 面对弱网与低端机，预算必须比 PC 更紧；超预算直接 fail。

最佳实践 ​

  • ✅ mode 名与产物目录一一对应，路径带端标识，避免部署拷错。
  • ✅ 每端一个 HTML 入口，不要两端入口塞进同一次 rollupOptions.input。
  • ⚠️ .env.*.local 进 .gitignore；CI 用环境变量注入真实配置。

113.4 端能力抽象与条件编译 ​

概念解析 ​

端能力抽象 = 接口 + 两套实现 + 一个组装点。接口只暴露 end、storage、share、pay 等最小能力，业务层只依赖接口。

adapters/pc 用 Clipboard API 复制链接、二维码收银台；adapters/h5 优先 Web Share，失败降级复制，再失败给二维码；支付优先 App scheme，失败回落 hosted checkout。降级链写在 adapter 里。

能力PC 实现H5 实现降级
storagelocalStorage 5MBWebView 64KB + 内存双写容量失败返回 false
share复制链接Web Share → 复制 → 二维码不阻断分享
pay二维码收银台App scheme → hosted checkoutfallbackUrl

条件编译分两种：

  1. 构建期换实现（推荐）：@adapters 别名按 mode 指向 adapters/pc 或 adapters/h5，另一端代码不进产物。
  2. 运行期分支（谨慎）：if (import.meta.env.VITE_APP_END === 'pc') 只决定执行路径，不删除 import。小差异可用，隔离 UI 库必然失败。

端判定也不要只看 UA：maxTouchPoints > 0 且视口窄归 H5，触摸但宽视口归 PC。完整实现见 examples/113-01-capability-adapter.ts：detectEnd 做能力判定，createCapabilities 组装 storage/share/payment 的端实现。

运行方式：npx tsx examples/113-01-capability-adapter.ts

应用实践 ​

  • 存储：H5 WebView 的 localStorage 可能被系统清理，重要数据双写并接受容量失败返回值。
  • 分享：原生分享不可用时必须有复制/二维码兜底。
  • 支付：二维码、钱包、hosted checkout 三条路径都要有 fallbackUrl。

最佳实践 ​

  • ✅ 接口返回结果对象（{ channel, ok }），不把平台异常抛给业务层。
  • ✅ 两端 adapter 跑同一套契约测试，相同输入返回同构结构。
  • ⚠️ core 不 import 任何 adapter；端判断属于外层知识。

113.5 UI 分流 ​

概念解析 ​

PC 与 H5 的差异不是「字号小一点」，而是交互范式：PC 有 hover、右键、多列对照、快捷键；H5 有安全区、手势、44px 触控目标、单手操作。Element Plus 缩到手机或 Vant 拉到桌面，都会「能点但难用」。

维度Element Plus（PC）Vant（H5）
交互范式鼠标、hover、高密度触控、手势、单列卡片
按需体积约 80KB gzip约 40KB gzip
主题CSS 变量 --el-*CSS 变量 --van-*
典型组件表格、树、级联、日期范围底部弹层、步进器、轮播

共享设计令牌，不共享组件实现：品牌色、圆角、字号、间距抽成 token，构建期分别生成 --el-* 与 --van-*。按需引进入口按端切换 resolver（ElementPlusResolver 或 VantResolver），两者互斥。

反例：共享组件 DateRangePicker.vue 原在 ui-pc，H5 直接 import「省事」。Element Plus 日期组件把整条依赖链拖进 H5，首屏 JS 从 240KB 涨到 520KB。正确做法是把取值与校验抽到 composable，两端各自渲染。

应用实践 ​

  • H5 底部操作栏加 padding-bottom: env(safe-area-inset-bottom)；PC 不需要。
  • PC 表格与筛选器在 H5 降级为「卡片流 + 底部筛选抽屉」。
  • 主题按端产出：element-theme.css 与 vant-theme.css，token 源文件共享。

最佳实践 ​

  • ✅ 两个 UI 库绝不同时全量注册，resolver 互斥，CI 检查产物 import。
  • ✅ 移动端触控目标不小于 44×44px，PC 保留 hover/focus 可见态。
  • ⚠️ 不要用 display: none 隐藏另一端页面来「复用」。

113.6 路由 / 状态 / 请求复用 ​

概念解析 ​

路由的复用单位是业务名，不是 path。同一业务 PC 叫 /product/:id，H5 叫 /p/:id；两端路由表各写一份，name 保持一致，埋点、跳转、权限只认 name。

降级是路由表的硬职责：PC 专属的批量导入在 H5 跳首页并提示，而不是 404；旧链接跨端打开时用另一端的表识别再重建路径（/product/7 → /p/7），参数不能丢。完整实现见 examples/113-03-dual-route-table.ts：buildPath 按业务名生成路径并标记降级，matchPath 负责当前端匹配与旧链接重定向。

运行方式：npx tsx examples/113-03-dual-route-table.ts

状态与请求「内核共享、表现分端」：Pinia 领域 store 共享，UI 状态分端；持久化走 storage 能力接口。请求用同一个 client，baseURL 由 mode 注入，统一错误结构与 traceId；H5 超时更短、重试更积极。结账、领券、下单必须带幂等键。

关注点共享分端
路由业务 name、守卫path、视图、降级表
状态领域 storeUI 状态、持久化配额
请求client、错误结构、幂等键超时/重试策略

应用实践 ​

  • 守卫分三层：共享登录/权限、端能力守卫（PC-only 路由）、页面业务守卫。
  • 路由懒加载按端分包，避免 H5 拉到 PC 页面代码。
  • 埋点、AB、错误上报用业务名与模块名，不用路径。

最佳实践 ​

  • ✅ 路由 meta.ends 声明支持端，构建期扫描生成降级清单。
  • ✅ 旧链接重定向保留参数，目标必须能在当前端表里命中，防循环。
  • ⚠️ H5 用 history 模式必须配服务端 fallback，否则深链 404。

113.7 PWA 接入 ​

概念解析 ​

PWA 四件套：manifest、SW、更新策略、离线兜底页。收益是复购用户把 H5 装到主屏，二次打开跳过地址栏，弱网仍可浏览。

缓存必须分层，不能一把梭 CacheFirst：

资源策略理由
App Shell预缓存，版本化离线可打开，随 SW 更新
商品图片CacheFirst + 上限省流量，防爆存储
商品/库存 APINetworkFirst + 3s 超时价格库存必须新鲜
导航请求在线优先，失败回 offline.html不能钉死旧 HTML
POST/支付/下单绝不缓存重放会造成重复订单与资损

更新默认 registerType: 'prompt'：skipWaiting 会让新 SW 立即接管，旧页面可能加载新旧混合 chunk，造成白屏或样式错乱；用户在填地址/支付时被强制刷新会丢单。正确流程是「发现 → 提示 → 脏表单推迟 → 确认/保存后 SKIP_WAITING → controllerchange 只刷新一次」。状态机见 examples/113-04-pwa-update-state-machine.ts。

运行方式：npx tsx examples/113-04-pwa-update-state-machine.ts

应用实践 ​

  • manifest 含 name/short_name/start_url/scope/display/theme_color，图标给 192 与 512。
  • iOS Safari 不支持 beforeinstallprompt，引导「分享 → 添加到主屏幕」。
  • 安装提示第二次访问或完成下单后再弹。

最佳实践 ​

  • ✅ SW 只在 HTTPS（localhost 例外）生效，CI 用 Lighthouse 校验 manifest 与离线能力。
  • ✅ SW 版本写入构建号，线上缓存问题一眼定位。
  • ⚠️ 不缓存登录态、支付结果、个性化接口；设置过期与条目上限。

113.8 测试与 CI ​

概念解析 ​

多端测试重点不是「每页都写 E2E」，而是守住契约与产物：

层级测什么触发
单元core 定价/优惠/状态机每次提交
契约两端 adapter 同构、路由 name 齐全每次提交
组件ui-pc / ui-h5 各自渲染每次提交
构建双端产物、入口、PWA、体积门禁每次 PR
E2E登录→商品→购物车→结账合并前/夜间

CI 用矩阵任务跑 pc-prod 与 h5-prod，随后执行产物校验与双视口 Playwright。体积门禁要卡两端首屏 vendor、CSS 总量、首屏图片、SW 体积、单 chunk 上限；任一项超预算即 fail，并输出对比上一版的增量，防止「每次涨一点，半年翻倍」。

应用实践 ​

  • PR 跑「类型检查 + 双端构建 + 契约 + 体积门禁」，控制在 10 分钟；全量 E2E 放夜间。
  • 预览环境按端部署，产品验收两端各点一遍；测试数据保持一致。

最佳实践 ​

  • ✅ 契约测试复用同一组断言跑两个 adapter，新增能力时两端同时红。
  • ✅ 构建校验脚本与业务代码同仓同版本。
  • ⚠️ 不要只构建 H5 就宣布通过——串端组件库问题只有双端构建能暴露。

113.9 自测题 ​

先自己作答，再展开参考答案。

1. 为什么「一套代码」不等于 100% 复用？复用率怎么算？【基础】

复用率是分层指标：core/services 追求 90%~100%，ui 通常 40%~70%，adapters 接近 0% 且是设计目的。强行让 UI 100% 会双 UI 库进包、两头难用；整体 70%~85% 已健康。

2. 端判断为什么不能只依赖 UA？【基础】

UA 可伪造、可被精简，触摸笔记本与横屏平板会误判。更可靠的是能力与形态：maxTouchPoints > 0 且视口窄判 H5；触摸但宽视口归 PC。最终以能力探测（Web Share、原生桥）决定降级路径。

3. PC 与 H5 为什么不应共用同一个 UI 组件库？按需引入解决什么？【基础】

Element Plus 面向鼠标与高密度信息，Vant 面向触控与单列操作，尺寸、交互、无障碍目标不同。按需引入只解决体积，不解决范式；正确做法是组件分端、设计令牌共享。

4. 构建期别名切换与运行时 `if` 分支差别在哪？【进阶】

别名在打包阶段把 @adapters 指向另一套实现，另一端代码不进产物；运行时 if 只决定执行路径，两边 import 仍会打包。小逻辑可用运行时分支，UI 库、重依赖、端专属 SDK 必须构建期切换。

5. 路由为什么按业务 name 而不是 path 做跨端契约？【进阶】

path 是表现层细节，两端可完全不同；name 是业务唯一键，埋点、权限、跳转都认它。按 name 建表还能统一处理不支持路由降级与旧链接跨端重定向，避免 404 与参数丢失。

6. PWA 更新为什么默认 prompt 而不是自动 skipWaiting？【进阶】

自动 skipWaiting 让新 SW 立即接管，旧页面可能加载新旧混合 chunk，造成白屏或样式错乱；用户填表/支付时被强制刷新会丢数据。prompt 把更新时机交给用户，脏表单时推迟，保存或明确放弃后再激活。

7. Service Worker 缓存如何分层？哪些绝不能缓存？【挑战】

App Shell 预缓存并随版本更新；图片 CacheFirst 加上限；库存/价格 API 用 NetworkFirst 短超时；导航失败回离线页。POST、支付、下单、登录态、个性化接口绝不缓存，避免重放与资损；HTML 不能永久钉死。

8. 海外电商 PC + H5/PWA 单仓：哪些必须共享，哪些必须分开？【挑战】

共享定价/税费/汇率、购物车与优惠、订单状态机、库存规则、错误码、设计令牌、埋点事件名——影响金额与订单，必须唯一真相。分开 UI 组件与布局、path、adapter、构建入口与产物、PWA、交互状态。原则：出错会导致金额/库存/订单不一致就共享；只影响「看起来/点起来」就分端。

113.10 本章避坑清单 ​

#坑点现象根因正确姿势
1追求 UI 层 100% 复用两端都难用，CSS 越写越多桌面与触控是两套交互范式组件分端，只共享设计令牌
2H5 误引 PC 组件H5 首屏 JS 翻倍，出现桌面弹层样式ui-h5 import 了 ui-pc目录隔离 + @ui 别名 + CI 产物检查
3两个 UI 库同时全量注册包体暴涨，CSS 变量互相覆盖两个 app.use() 都在入口resolver 按端互斥，只注册一个库
4用 UA 判断端触摸笔记本/平板被当成 H5UA 可伪造且信息不全触摸能力 + 视口宽度 + 能力探测
5用运行时 if 隔离重依赖另一端代码仍在产物里if 不删除 import构建期别名切换或独立入口
6.env 里写密钥密钥随 VITE_ 前缀打进客户端误以为只有服务端能读密钥走服务端/CI 注入
7路由用 path 做跨端契约换端后深链 404、埋点断裂path 被当成业务标识用业务 name 建表，path 只是表现
8不支持的路由直接 404H5 打开 PC 专属链接白屏没有降级表FALLBACK 映射首页/提示页
9PWA 自动 skipWaiting用户填表时被强制刷新，丢单新 SW 立即接管旧页面registerType: 'prompt' + 脏表单守卫
10SW 缓存 POST/支付/HTML重复下单、旧页面永不更新缓存策略一刀切只缓存 GET 静态资源，HTML 在线优先

心法：多端工程的核心不是「写一套代码」，而是「让不该共享的东西各归其位」。业务内核共享到字节级，交互表现分端到目录级，产物用构建矩阵隔开——做到这三点，复用率自然上去，包体与体验也不会互相拖累。靠 if (isMobile) 维持的多端，最终会变成两端都不敢改的泥潭。
