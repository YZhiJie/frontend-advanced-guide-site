第三十四部分：架构师成长路线——从高级工程师到技术决策者 ​

导航

  • 返回总目录
  • 上一篇：Zod 运行时校验
  • 下一篇：附录 A 学习路线与自查清单
  • 示例路径：examples/34-01 ~ examples/34-05（零依赖，npx tsx 直跑）

本册定位：前 33 册回答「怎么把代码写好」，本册回答「怎么从写好代码走向做好技术决策」。架构师不是一个职级头衔，而是一组可以被训练的能力：在约束下做取舍（决策）、让系统允许变化（设计）、让约束自动生效（赋能）、让他人愿意同行（影响力）。本册把这组能力拆成可自评、可练习、可验收的路径图：34.1 能力模型与自评 → 34.2 技术决策方法论（trade-off 矩阵 + ADR）→ 34.3 架构设计实战（从 0 到 1 与从 1 到 100）→ 34.4 工程赋能（规范/脚手架/门禁）→ 34.5 软素养（写作/评审/RCA）→ 34.6 十二个月成长路径图。每节五段式：概念 → 场景 → 示例 → 最佳实践 → 自测题。

34.1 能力模型：架构师的三级跃迁 ​

34.1.1 概念解析 ​

高级工程师与架构师的核心差异，不在于代码写得更多，而在于负责的对象变了：前者对「一个模块的质量」负责，后者对「一群人能否长期高效地产出」负责。这个变化可以概括成三级跃迁——每一级都不是上一级的自然延续，而是工作重心的重新分配：

阶段核心命题时间分配（参考）关键产出常见卡点
P6/资深：把事做好交付出高质量的模块与功能写码 80% / 设计与沟通 20%难点攻坚、技术方案、Code Review只关注「我的模块」，看不到系统全局
P7/架构：把系统做好让系统在需求变化下保持低成本演进写码 40% / 设计、评审、排雷 60%分层与边界、选型决策、性能与稳定性兜底、技术债治理设计脱离业务阶段（过度设计或欠设计）
P8/总监级架构：把组织做好让多个团队在同一个技术方向上高效协作写码 10% / 规划、推动、授能 90%技术战略、跨团队规范、平台与工具链、人才梯队沉迷具体实现，不愿放手「自己写才放心」

三级跃迁对应的五维能力雷达（34.1.3 用它做自评）：

mermaid
graph TD
    A[技术深度<br/>一条线吃到机制层] --> F[架构师胜任度]
    B[技术广度<br/>33 册地图的全局视野] --> F
    C[工程赋能<br/>让约束自动生效] --> F
    D[决策判断<br/>约束下做取舍并沉淀] --> F
    E[影响力<br/>写作/评审/推动/带人] --> F

两个必须先纠正的误区：架构师 ≠ 不写代码——不写代码的架构师会失去对落地成本的判断力，写出的设计常年「图上合理、落地翻车」，合理的比例是保持 30%~40% 的时间在关键路径上写码（往往是基建、门禁、原型，而不是业务 CRUD）；架构师 ≠ 画架构图的——图只是决策的记录，没有 trade-off 分析与 ADR 支撑的图，在第一次需求变更时就会作废。

34.1.2 典型应用场景 ​

  • 自评定位：晋升答辩前、转架构岗前，用雷达表量化「下一级差距」，把「感觉还差点」变成可训练的具体维度。
  • 团队梯队盘点：Tech Lead 对组内成员做五维打分，为每人指定一期的单项提升抓手（每次只补一个维度）。
  • 招聘对标：面试架构师候选人时，五维对应五组面试题——深度看机制追问（10 册渲染管线），广度看选型理由，赋能看门禁设计，决策看 trade-off 复盘，影响力看文档与推动案例。

34.1.3 可运行代码示例 ​

下面的自评雷达把五维能力加权汇总：分数口径是 1=没碰过、3=能独立完成、5=能带别人做并沉淀方法，总分不重要，最短板与提升抓手才是输出重点。

ts
// 文件: examples/34-01-capability-radar.ts
// 架构师能力自评雷达：五维加权汇总 → 定位当前阶段 → 给出最短板的提升抓手。
// 权重与维度可按团队实际调整，但「先看最短板、再看总分」的读法不要变。

interface Dimension {
    name: string;
    weight: number; // 对架构师胜任度的贡献权重，总和为 1
    score: number;  // 自评 1~5：1=没碰过 3=能独立完成 5=能带人并沉淀方法
    hint: string;   // 低于 3 分时的提升抓手
}

const dimensions: Dimension[] = [
    { name: "技术深度", weight: 0.2, score: 3, hint: "吃透一条线（渲染/网络/编译器任选），能讲到机制层" },
    { name: "技术广度", weight: 0.15, score: 2, hint: "把全书地图按专项篇补齐，每册至少跑通一个示例" },
    { name: "工程赋能", weight: 0.25, score: 2, hint: "从一个 lint 规则或 CI 门禁做起，把团队规范变成机器检查" },
    { name: "决策判断", weight: 0.2, score: 1, hint: "下次选型用 34.2 的 trade-off 矩阵 + ADR 走完整流程" },
    { name: "影响力", weight: 0.2, score: 2, hint: "每季度产出一份 RFC 或复盘文档，先在小组内评审" },
];

const total = dimensions.reduce((s, d) => s + d.weight * d.score, 0);

console.log("=== 五维自评 ===");
for (const d of dimensions) {
    const bar = "█".repeat(d.score) + "░".repeat(5 - d.score);
    console.log(`${d.name.padEnd(4, "　")} ${bar} ${d.score}/5 × 权重${d.weight}`);
}
console.log(`加权总分：${total.toFixed(2)} / 5`);

const phase =
    total < 2.5 ? "资深工程师核心期：先把深度与广度补到 3 分"
    : total < 3.5 ? "架构过渡期：把赋能与决策提到 3 分以上"
    : "架构师胜任区：把优势维度沉淀成团队可复用的方法";

console.log(`阶段定位：${phase}`);

const weakest = [...dimensions].sort((a, b) => a.score - b.score)[0];
console.log(`当前最短板：${weakest.name} → ${weakest.hint}`);

运行方式：npx tsx examples/34-01-capability-radar.ts。

34.1.4 最佳实践 ​

  • 每次只补一个维度：五维齐头并进等于五维都不动，一个季度集中训练一个维度，用产出物（一次选型、一份 RFC、一个门禁）验收。
  • 深度优先于广度：没有一条吃透到机制层的线，广度只是名词清单；先在一条线上拿到「能讲清为什么」，再横向复制这种学习方式。
  • 用产出物自评，不用感觉自评：「我差不多会了」不可验收，「我给团队写过一版请求层并被三个项目复用」可以。
  • 职级体系只是参照：各家公司 P 序列含义不同，重点是把「下一级差距」翻译成具体维度，而不是追逐标题。

34.1.5 自测题 ​

1. 【基础】高级工程师与架构师的核心差异是什么？为什么「不写代码的架构师」做不好架构？

核心差异是负责对象：前者对一个模块的质量负责，后者对一群人能否长期高效产出负责。不写代码的架构师会失去对落地成本的体感——不知道一个接口抽象会让业务同学多写多少胶水代码，设计常年「图上合理、落地翻车」。合理比例是保持 30%~40% 时间在关键路径写码（基建、门禁、原型），而不是业务 CRUD。

2. 【基础】P7 阶段「把系统做好」的典型产出有哪些？它和 P6 的产出有什么本质区别？

分层与边界设计、技术选型决策与 ADR、性能与稳定性兜底方案、技术债的登记与偿还节奏。本质区别：P6 的产出物是「一次交付」，P7 的产出物是「让后续 N 次交付都变便宜的机制」——判断标准不是这次做了什么，而是团队下一次遇到同类问题时是否更快、更稳。

3. 【进阶】为什么本节建议「每次只补一个维度」？如果一个人的技术深度和影响力同时是短板，应该先补哪个？

因为每个维度都需要刻意练习与产出物验收，齐头并进时每个维度投入都不足，等于都不动。先补深度：深度是影响力的原料——没有一条能讲到机制层的线，写出的 RFC 缺乏说服力，评审发言没有分量；影响力本质是「被验证过的判断的累积」，而判断力来自深度。

34.2 技术决策方法论：trade-off 矩阵与 ADR ​

34.2.1 概念解析 ​

架构师的日常产出里，「决策」远多于「代码」。一个决策的质量取决于三件事：约束是否显式（时间、人力、风险偏好、团队熟悉度——很多「错误选型」其实是「没说清约束」）、选项是否对称比较（拿 A 的长板比 B 的短板是最常见的决策污染）、过程是否可追溯（半年后没人记得为什么选了它，于是下一次有人推翻重来）。对应两件工具：

加权 trade-off 矩阵——把候选方案与评估维度列成表，维度按当前项目的真实约束加权，加权总分排序。它的价值不在「算出分数」而在两个副作用：列维度的过程强迫你显式化约束（关心包体积还是关心类型体验？），打分的过程强迫你为每个分数找证据（体积差多少？实测过还是猜的？）。矩阵只组织思考，不代替思考。

ADR（Architecture Decision Record，架构决策记录）——一个决策一份短文档，五个字段一个不能少：背景（为什么现在要决策）、候选与取舍（每个选项的代价，而不只是优点）、结论（选了什么）、后果（接受什么损失、谁受影响）、状态（proposed / accepted / deprecated / superseded，被新决策取代时改状态而不是删除，保留演进史）。ADR 是「为什么当初这么定」的唯一事实来源——新人 onboarding、返工追责、决策复盘都靠它。

决策还有一条通用法则：先问可逆性（贝佐斯的 Type 1 / Type 2 之分）。可逆决策（引入一个库、换一个请求封装）快速试错、错了就改；不可逆决策（存储 schema、对外的 API 契约、微前端拆分边界）才值得花矩阵 + 评审的完整流程。把完整流程浪费在可逆决策上，和把拍脑袋浪费在不可逆决策上，是决策能力的两个极端失败。

34.2.2 典型应用场景 ​

  • 技术选型：状态库、请求层、构建工具、组件库——矩阵打分 + 敏感性检查（什么条件下结论会反转），结论落成 ADR。
  • 自研 vs 引入：用「维护成本 = 未来三年的修复与升级工时」参与打分，而不是只比较当下开发工时。
  • 重构立项：「值不值得重写」本身就是一次决策——先写 ADR 把现状痛点、迁移风险、预期收益显式化，多数「想重写」在这一步就被自己否掉了。
  • 决策复盘：事故或返工后回读 ADR，检查是约束变了（决策当时正确）还是当时漏了维度（方法论问题）——这两种失败的改进动作完全不同。

34.2.3 可运行代码示例 ​

第一段是加权矩阵：三个请求层候选方案 × 五个维度，最后做敏感性检查——找出最容易反转结论的维度，它是评审时最该被挑战的假设。

ts
// 文件: examples/34-02-tradeoff-matrix.ts
// 技术选型的加权 trade-off 矩阵：把「我觉得 A 好」变成「按当前约束算出来 A 高 0.6 分」。
// 分数必须来自实测或调研数据，权重必须来自当下项目的真实约束——矩阵只组织思考，不代替思考。

interface Option {
    name: string;
    scores: Record<string, number>; // 各维度得分 1~5，注释即证据
}

interface Criterion {
    name: string;
    weight: number;
}

// 维度与权重来自「当下」的约束：中后台、团队 6 人、已有 Pinia 经验、无 SSR 需求
const criteria: Criterion[] = [
    { name: "团队熟悉度", weight: 0.3 },
    { name: "类型体验", weight: 0.25 },
    { name: "缓存与竞态能力", weight: 0.2 },
    { name: "包体积", weight: 0.1 },
    { name: "生态与维护", weight: 0.15 },
];

const options: Option[] = [
    {
        name: "TanStack Query",
        scores: { 团队熟悉度: 2, 类型体验: 5, 缓存与竞态能力: 5, 包体积: 4, 生态与维护: 5 },
    },
    {
        name: "SWR",
        scores: { 团队熟悉度: 3, 类型体验: 4, 缓存与竞态能力: 4, 包体积: 5, 生态与维护: 4 },
    },
    {
        name: "自研请求层",
        scores: { 团队熟悉度: 5, 类型体验: 3, 缓存与竞态能力: 2, 包体积: 5, 生态与维护: 1 },
    },
];

const weighted = (o: Option) =>
    criteria.reduce((s, c) => s + c.weight * o.scores[c.name], 0);

console.log("=== 加权排序 ===");
const ranked = [...options].sort((a, b) => weighted(b) - weighted(a));
for (const o of ranked) {
    console.log(`${o.name.padEnd(14)} ${weighted(o).toFixed(2)}`);
}

// 敏感性检查：逐个维度把权重翻倍，看冠军是否易主——易主的维度就是最该被评审挑战的假设
console.log("\n=== 敏感性检查（该维度权重 ×2 后冠军是否反转）===");
const champion = ranked[0].name;
for (const c of criteria) {
    const alt = (o: Option) =>
        criteria.reduce(
            (s, x) => s + x.weight * (x.name === c.name ? 2 : 1) * o.scores[x.name],
            0,
        );
    const newBest = [...options].sort((a, b) => alt(b) - alt(a))[0].name;
    console.log(
        `${c.name}：${newBest === champion ? "不反转" : `反转 → ${newBest}`}`,
    );
}

运行方式：npx tsx examples/34-02-tradeoff-matrix.ts。

第二段把 ADR 做成数据结构并渲染成 Markdown——ADR 不需要任何工具，一个约定好的模板加一个目录就够了：

ts
// 文件: examples/34-03-adr.ts
// ADR（架构决策记录）：把「为什么当初这么定」变成可检索的资产。
// 重要不是工具，是五个字段一个都不能少；被取代时改状态而不是删除，保留演进史。

interface AdrOption {
    name: string;
    pros: string[];
    cons: string[];
}

interface Adr {
    id: string;
    title: string;
    status: "proposed" | "accepted" | "deprecated" | "superseded";
    supersededBy?: string;
    context: string;
    options: AdrOption[];
    decision: string;
    consequences: string;
}

const adr1: Adr = {
    id: "ADR-0001",
    title: "请求层选型：引入 TanStack Query 替代自研封装",
    status: "superseded",
    supersededBy: "ADR-0003",
    context: "自研请求层缓存与竞态逻辑 bug 率高（近两季度 6 个 P2 事故中 3 个源于此），维护投入约占一人季度工时的 40%。",
    options: [
        { name: "继续自研", pros: ["零依赖", "团队 100% 熟悉"], cons: ["缓存失效逻辑复杂度持续增长", "无社区测试覆盖"] },
        { name: "TanStack Query", pros: ["缓存/竞态/重试开箱即用", "类型推导完整"], cons: ["新概念学习成本", "包体积 +13KB gzip"] },
        { name: "SWR", pros: ["体积更小"], cons: ["mutation 与乐观更新能力弱", "团队无经验"] },
    ],
    decision: "引入 TanStack Query，自研层仅保留鉴权注入与埋点，通过封装层隔离。",
    consequences: "接受 13KB 体积与两周学习曲线；换取请求类 P2 事故清零目标；组件层代码不改（封装层兜底）。",
};

function render(adr: Adr): string {
    const lines = [
        `# ${adr.id}：${adr.title}`,
        `- 状态：${adr.status}${adr.supersededBy ? `（被 ${adr.supersededBy} 取代）` : ""}`,
        `## 背景`,
        adr.context,
        `## 候选与取舍`,
        ...adr.options.map(
            (o) => `- **${o.name}**：优点 ${o.pros.join("、")}；代价 ${o.cons.join("、")}`,
        ),
        `## 结论`,
        adr.decision,
        `## 后果`,
        adr.consequences,
    ];
    return lines.join("\n");
}

console.log(render(adr1));
console.log("\n// ADR-0002 落地半年后性能预算收紧 → ADR-0003 评估按需加载方案并取代本决策");

运行方式：npx tsx examples/34-03-adr.ts。

34.2.4 最佳实践 ​

  • 不可逆决策才上完整流程：换一个日期库用半天试错，改存储 schema 才写矩阵 + ADR + 评审；流程与决策的可逆性匹配。
  • ADR 写「代价」而不是「优点」：候选方案只有优点 = 没有做过真实比较；被接受的方案也必须写明「接受什么损失、谁受影响」。
  • 决策要设「复审日期」：写在 ADR 后果字段里（如「一年后或团队 >15 人时复审」），避免过时决策永久统治系统。
  • 用数据支撑分数：体积用 bundle 实测、性能用基准测试、维护成本用历史 bug 统计；拿不出数据的分数标成「待验证」并在评审里补测。

34.2.5 自测题 ​

4. 【基础】trade-off 矩阵的价值为什么「不在算出分数」？它真正提供的是什么？

因为分数本身是主观输入，换一批人打分结论就变。矩阵真正提供的是两个副作用：列维度强迫你显式化当前项目的真实约束（关心体积还是关心类型体验），打分强迫你为每个分数找证据（实测过还是猜的）。它是思考的组织工具，结论的正确性来自约束与证据的质量，不是来自加权求和。

5. 【基础】ADR 的五个必要字段是什么？为什么「被取代的 ADR」要改状态为 superseded 而不是删除？

背景（为什么现在决策）、候选与取舍（每个选项的代价）、结论、后果（接受的损失与影响面）、状态。删除会切断演进史：后人无法知道「为什么曾经那样定、后来为什么不那样了」，会把同样的错误再犯一遍，或在复盘时误判当时的决策质量。superseded + 指向新 ADR，保留了完整的决策链。

6. 【挑战】给「是否把单体前端拆成微前端」设计决策流程：它是可逆决策还是不可逆决策？矩阵的维度应该包含哪些？

偏不可逆：拆分边界一旦定了，团队协作方式、发布流程、依赖治理都跟着固化，回退成本极高。维度至少包括：团队规模与自治需求（人数少于两组通常不值得拆）、独立发布频率的真实差异、构建与部署复杂度增量、运行时性能损失（样式隔离与 JS 沙箱成本）、公共依赖重复加载体积、共享状态与通信成本、监控与排障链路变化。多数团队的正确结论是「先模块边界 + 独立构建，暂不做运行时微前端」——即用可逆的第一步探索不可逆的目标（参见 11.3）。

34.3 架构设计实战：从 0 到 1 与从 1 到 100 ​

34.3.1 概念解析 ​

11.4 已经给了应用内分层与组件设计的静态答案，本节补上时间维度：架构不是一次性画好的图，而是随业务阶段持续演进的决策序列。从 0 到 1 的关键词是「匹配业务阶段」——初创期唯一目标是快速验证，四层分层可以退化为「视图 + 一个 service 文件」，但有一条线不能破：视图不直接 fetch、接口契约有单一出口，因为这条线的修复成本随代码量线性增长，是后期所有重构的地基。从 1 到 100 的关键词是「腐化信号驱动的演进」——架构腐化不是突变而是漂移，及早识别信号、小步偿还，比重写便宜一个数量级。

五个必须响应的腐化信号（出现即立项治理，而不是等「有空再说」）：

信号表现治理动作
需求放大改一处配置要动五个文件边界划错，回收职责到单一出口
循环依赖ESLint import/no-cycle 报警成常态抽公共层或用依赖倒置断环
重复实现第三处出现「自己的防抖/请求/存储」基建层收口 + 门禁禁止再造
测试变难新模块写单测要 mock 五个全局依赖注入不足，副作用没有收口
新人卡点onboarding 两周才能提交第一行代码目录结构与文档过期，重构 + ADR 补课

演进式重构的标准打法是绞杀者模式（Strangler Fig）：不冻结旧代码做大爆炸重写，而是在旧系统的边界处立起新实现，用路由/开关把流量按比例切过去，验证稳定后逐段「绞杀」旧实现，最后删除。它的每一步都是可回滚的——这与 34.4 的灰度状态机是同一件事在两个层面的应用。

34.3.2 典型应用场景 ​

  • 新项目起步：定四层分层 + 按功能分目录 + 11.4组件三铁律，同时用 34.4 的门禁把「依赖只能自上而下」变成 CI 断言，而不是口头规范。
  • 存量系统接手：先跑 34.3.3 的依赖审计摸清现状（环数、越层数、最大扇出），产出「腐化地图」再排治理优先级——不摸现状就动手的重构，一半会中途放弃。
  • 单体拆分：先按业务域重组目录（可逆），再抽共享层为独立包（可逆），最后才是运行时微前端（不可逆）——三步中前两步往往已解决 80% 的痛点。

34.3.3 可运行代码示例 ​

把 11.4 的分层规则变成机器可检查的审计：反向依赖是违规，跨层直达是警告，循环依赖必须清零。

ts
// 文件: examples/34-04-dep-audit.ts
// 分层依赖审计：把「上层可依赖下层、下层绝不感知上层」变成可检查的规则。
// 真实项目里这份 import 映射来自 dependency-cruiser / eslint-plugin-import；
// 这里用数据演示检查逻辑本身——架构约束必须可执行，否则必然腐化。

type Layer = "views" | "features" | "services" | "infra";

// 层级秩：数值越大越靠上层；上层依赖下层（from.rank > to.rank）合法
const RANK: Record<Layer, number> = { infra: 0, services: 1, features: 2, views: 3 };

interface Dep {
    from: `${Layer}/${string}`;
    to: `${Layer}/${string}`;
}

const deps: Dep[] = [
    { from: "views/order", to: "features/order" }, // 正常：上层用业务层
    { from: "features/order", to: "services/order-api" }, // 正常
    { from: "services/order-api", to: "infra/request" }, // 正常
    { from: "views/order", to: "infra/request" }, // 跨层直达：方向对，但绕过了服务层（警告）
    { from: "infra/request", to: "features/cart" }, // 反向依赖：基建感知了业务（违规）
    { from: "features/cart", to: "features/order" }, // 同层互依：演变成环的温床（违规）
];

const layerOf = (mod: `${Layer}/${string}`): Layer => mod.split("/")[0] as Layer;

// 1) 反向依赖：低秩模块 import 高秩模块
// 2) 跨层直达：方向正确但跳层（views→infra），绕过中间层的封装
// 3) 同层互依：层内横向依赖，是循环依赖的前兆
const violations: string[] = [];
const warnings: string[] = [];
for (const { from, to } of deps) {
    const a = RANK[layerOf(from)];
    const b = RANK[layerOf(to)];
    if (a < b) violations.push(`反向依赖：${from} → ${to}（下层感知了上层）`);
    else if (layerOf(from) === layerOf(to)) violations.push(`同层互依：${from} → ${to}`);
    else if (a - b > 1) warnings.push(`跨层直达：${from} → ${to}（绕过中间层封装）`);
}

// 4) 循环依赖：DFS 找环（这里展示判定，真实项目交给 import/no-cycle）
const graph = new Map<string, string[]>();
for (const { from, to } of deps) {
    if (!graph.has(from)) graph.set(from, []);
    graph.get(from)!.push(to);
}
const cycles: string[] = [];
const seenCycles = new Set<string>();
for (const start of graph.keys()) {
    const stack: string[] = [];
    const visit = (node: string): void => {
        if (stack.includes(node)) {
            // 规范化：旋转到字典序最小的节点，同一个环只报告一次
            const path = [...stack.slice(stack.indexOf(node)), node];
            const nodes = path.slice(0, -1);
            const pivot = nodes.indexOf([...nodes].sort()[0]);
            const canon = [...nodes.slice(pivot), ...nodes.slice(0, pivot), nodes[pivot]].join(" → ");
            if (!seenCycles.has(canon)) {
                seenCycles.add(canon);
                cycles.push(canon);
            }
            return;
        }
        stack.push(node);
        for (const next of graph.get(node) ?? []) visit(next);
        stack.pop();
    };
    visit(start);
}

console.log(violations.length ? violations.map((v) => `✗ ${v}`).join("\n") : "✓ 无违规依赖");
console.log(warnings.length ? warnings.map((w) => `⚠ ${w}`).join("\n") : "✓ 无跨层直达");
console.log(cycles.length ? `✗ 检测到环：\n${cycles.map((c) => `  ${c}`).join("\n")}` : "✓ 无循环依赖");

运行方式：npx tsx examples/34-04-dep-audit.ts。

34.3.4 最佳实践 ​

  • 架构决策跟随业务阶段：验证期要快（允许扁平），增长期要稳（分层与门禁），成熟期要省（治理重复与债务）——脱离阶段谈「最佳架构」没有意义。
  • 先测后改：接手存量系统先补核心链路回归测试（9 册），再动结构；没有测试网的重构不是重构是赌博。
  • 每次重构带一个可量化的目标：「请求层迁移后请求类 bug 归零」「目录重组后新模块上手时间从 3 天降到 1 天」——不可验证的重构验收时必然扯皮。
  • 绞杀优先于重写：大爆炸重写冻结新需求的假设几乎从不成立，绞杀者模式的每一步都可以停下来而不留半成品。

34.3.5 自测题 ​

7. 【基础】从 0 到 1 的项目里，哪条架构底线即使在初创期也不能破？为什么？

视图不直接 fetch、接口契约有单一出口（服务层收口）。因为这条线的修复成本随代码量线性增长：视图直连接口后，接口一改要改 N 个组件，且请求逻辑（鉴权、竞态、缓存）散落各处无法统一治理。它不像分层全家桶那样有较高的前期成本，是「低成本高回报」的最小约束。

8. 【进阶】五个腐化信号里，「测试变难」为什么是最该优先响应的？

因为测试难度是依赖健康度的直接度量：模块需要 mock 五个全局才能测试，说明副作用散落、依赖注入缺失、模块边界模糊——这些正是其他四个腐化信号的共同根因。且测试变难会同时杀死重构的安全网，让后续所有治理动作风险陡增。先修可测性（副作用收口 + 依赖注入），其余腐化的治理成本会随之下降。

9. 【挑战】描述用绞杀者模式把「巨石中后台」逐步迁出旧构建体系的完整步骤，以及每一步的回滚出口。

①新旧页面共存：路由层按页面粒度切换新旧入口（回滚：路由开关）；②新页面用新体系开发，旧页面只修不新增（回滚：无冻结，随时恢复新增）；③逐页迁移：每页迁移走 34.4 的灰度状态机（影子对比 → 小流量 → 全量，回滚：流量比例归零）；④公共逻辑沉淀为双体系可用的独立包（回滚：包按版本回退）；⑤旧体系流量归零后删除（回滚：git revert 保留一个版本周期）。关键是不出现「冻结新需求」与「全量切换」两个高危动作。

34.4 工程赋能：让架构约束自动生效 ​

34.4.1 概念解析 ​

架构腐化的第一根因不是「设计不好」，而是约束只存在于文档和口头——新人没读过规范、赶工期的人选择了捷径、三个月后没人记得当初为什么。让约束存活的方式是把它下沉到三层，逐层提高「违反成本」：

mermaid
graph LR
    A[规范文档<br/>为什么 + 是什么] --> B[脚手架与工具<br/>默认就是对的]
    B --> C[门禁与 CI<br/>违反无法合入]
  • 规范文档：讲「为什么」（不写 why 的规范会被当成官僚流程绕过），放 wiki，链接进 ADR。
  • 脚手架与工具：项目模板默认带上 lint 配置、目录约定、请求层封装——让「照着做」比「自己搞」更省力，这是成本最低的约束方式。
  • 门禁与 CI：把不可协商的红线做成 CI 断言——依赖方向（34.3.3）、测试覆盖率下限、bundle 体积预算、避坑清单完整性。门禁是架构师的代码：它 7×24 小时值守，比任何人肉评审都稳定。

本站自身就是一个可参考的案例：16 关门禁把「避坑清单必须有收口小节」「示例必须可运行」「产物与正文必须同步」等内容约束全部机器化——这正是 v1.47.0 避坑清单收口（E18）到 v1.53.0 案例预览（E13）一路演进的核心思路：发现规则被反复违反 → 固化为门禁 → 规则从「靠自觉」变成「靠机器」。

迁移与重构的上线安全阀是灰度状态机：影子流量（只对比不生效）→ 按比例放量（1% → 10% → 50% → 100%，每步有推进守卫与回滚出口）→ 旧链路下线。守卫指标必须先于迁移定义（错误率、p95 时延），且回滚是自动触发而不是开会决定。

34.4.2 典型应用场景 ​

  • 团队规范落地：把「禁止视图层直接 fetch」写成 no-restricted-imports 规则进 CI，比在群里发十遍文档有效。
  • 性能预算守护：bundle 超预算即 CI 失败（本站 Lighthouse CI 的 a11y 硬预算就是此模式），性能不再「有空再优化」。
  • 重构灰度上线：请求层迁移用 34.4.3 的状态机推进，错误率超阈值自动回滚，负责人睡得着觉。
  • 文档防腐：示例代码块与落盘文件的一致性、产物 JSON 与正文同步——都交给门禁（本站第 3 关与第 12 关的做法）。

34.4.3 可运行代码示例 ​

一个最小灰度状态机：每个阶段有推进守卫（错误率与 p95 预算），守卫不过自动回滚。

ts
// 文件: examples/34-05-rollout.ts
// 灰度迁移计划：影子流量 → 按比例放量 → 全量 → 旧链路下线。
// 每步都有推进守卫（错误率 / p95 预算）与回滚出口——迁移没有回滚预案等于没有迁移方案。

interface Metrics {
    errorRate: number; // 出错请求占比
    p95Ms: number; // 95 分位时延
}

interface Phase {
    name: string;
    traffic: number; // 新链路承接的流量比例 0~1
    guard: { maxErrorRate: number; maxP95Ms: number };
}

const PLAN: Phase[] = [
    { name: "影子流量（只对比不生效）", traffic: 0, guard: { maxErrorRate: 0.001, maxP95Ms: 400 } },
    { name: "灰度 1%", traffic: 0.01, guard: { maxErrorRate: 0.005, maxP95Ms: 450 } },
    { name: "灰度 10%", traffic: 0.1, guard: { maxErrorRate: 0.005, maxP95Ms: 450 } },
    { name: "灰度 50%", traffic: 0.5, guard: { maxErrorRate: 0.003, maxP95Ms: 420 } },
    { name: "全量 100%", traffic: 1, guard: { maxErrorRate: 0.002, maxP95Ms: 400 } },
    { name: "旧链路下线", traffic: 1, guard: { maxErrorRate: 0.002, maxP95Ms: 400 } },
];

type Verdict = "advance" | "hold" | "rollback";

function judge(phase: Phase, metrics: Metrics): Verdict {
    const { maxErrorRate, maxP95Ms } = phase.guard;
    if (metrics.errorRate > maxErrorRate * 2 || metrics.p95Ms > maxP95Ms * 1.5)
        return "rollback"; // 显著恶化：立即回滚
    if (metrics.errorRate <= maxErrorRate && metrics.p95Ms <= maxP95Ms)
        return "advance"; // 全部达标：推进
    return "hold"; // 临界波动：原地观察一个观察窗
}

function rollout(label: string, metricsByPhase: Metrics[]): void {
    console.log(`\n=== ${label} ===`);
    for (const [i, phase] of PLAN.entries()) {
        const verdict = judge(phase, metricsByPhase[i]);
        const m = metricsByPhase[i];
        console.log(
            `${phase.name}  错误率 ${(m.errorRate * 100).toFixed(2)}% / p95 ${m.p95Ms}ms → ${verdict}`,
        );
        if (verdict === "rollback") {
            console.log(`↩ 已自动回滚至流量 0%，登记 RCA 后重新排期`);
            return;
        }
    }
    console.log("✓ 迁移完成");
}

// 场景一：健康迁移——每阶段指标达标，一路推进
rollout("健康迁移", PLAN.map((p) => ({ errorRate: p.guard.maxErrorRate * 0.6, p95Ms: p.guard.maxP95Ms * 0.8 })));

// 场景二：灰度 10% 时错误率飙到 1.2% → 守卫触发自动回滚
const spike = PLAN.map((p) => ({ errorRate: p.guard.maxErrorRate * 0.6, p95Ms: p.guard.maxP95Ms * 0.8 }));
spike[2] = { errorRate: 0.012, p95Ms: 380 };
rollout("异常迁移", spike);

运行方式：npx tsx examples/34-05-rollout.ts。

34.4.4 最佳实践 ​

  • 红线进门禁，建议进 lint 警告：把所有规则都设为 error 会导致门禁被绕过（--no-verify 合法化）；红线（依赖方向、安全、体积）阻断，风格类保持警告。
  • 门禁失败信息要教人怎么改：「依赖方向违规：infra 不得 import features，请把该逻辑上移到 services 或用依赖倒置」——门禁是教学工具不是罚款单。
  • 守卫指标先于迁移定义：灰度开始后才定「多少算异常」，必然演变成「出了事再调阈值」；指标和阈值在迁移方案评审时冻结。
  • 门禁也要定期复审：过时的门禁（早已不用的兼容检查）会稀释团队对门禁的敬畏，每季度清一次。

34.4.5 自测题 ​

10. 【基础】为什么「规范文档 → 脚手架 → 门禁」三层缺一不可？只有门禁会怎样？

只有文档：约束靠自觉，赶工期时必被绕过。只有脚手架：新代码默认正确，但存量代码与后期改动无约束。只有门禁：团队知道「不能做什么」但不知道「为什么」与「正确姿势是什么」，门禁沦为罚款单，催生绕过文化（--no-verify、copy 现网代码）。三层分别回答为什么、默认对、必须对。

11. 【进阶】灰度状态机中「hold（原地观察）」状态的价值是什么？如果没有它会发生什么？

hold 处理「临界波动」：指标未达标但也没显著恶化，立即推进风险大、立即回滚成本高（回滚本身有流量与状态切换成本）。没有 hold 就只有推进/回滚二元决策，团队会被迫在真实波动面前调宽阈值（守卫形同虚设）或频繁回滚（迁移永远完不成）。hold 给了一个显式的「观察窗」语义，把「再等等」从事故响应变成计划内动作。

34.5 软素养：技术写作、评审与推动 ​

34.5.1 概念解析 ​

架构师的产出最终都以「让他人理解并行动」为终点——技术深度决定你判断的对错，软素养决定你的判断能落地多少。三项基本功：

技术写作（RFC / 技术方案）。一份能被评审的方案有固定骨架：问题与约束（现状的量化痛点 + 时间/人力/风险边界）→ 目标与非目标（非目标防止范围蔓延，是最常被省略又最重要的一段）→ 方案与备选（主方案 + 至少一个被否掉的备选及否决理由）→ 迁移与回滚 → 度量（怎么算成功）。写不好方案的架构师，方案会在评审会上被「为什么不用 X」逐条击溃——不是因为 X 更好，而是因为方案没有预先回答。

技术评审。原则只有三条：对事不对人（评审代码与方案，不评审人）；先问约束再给方案（「你考虑过 X 吗」之前先问「当时的时间/人力约束是什么」，多数「低级设计」背后都有说不出的约束）；评审者给选项与代价，不替对方做决定（「建议改成 A 或 B，A 的代价是……」）。

事故复盘（RCA，Root Cause Analysis）。RCA 的产出不是「谁的锅」，而是「流程上哪里允许了这个错误发生」——blameless（不追责个人）不是宽容，而是因为追责个人会让下一次事故被隐藏。标准动作：时间线（客观事实）→ 根因（连问五层为什么，停在人或「疏忽」就是没问到底）→ 行动项（每个行动项必须有 owner 与期限，且优先落到流程/门禁而不是「大家小心」）。

影响力的正确积累方式是一致性 × 次数：判断被验证一次是运气，连续十次被验证就是信任；信任建立后，推动成本从「说服」降为「对齐信息」。

34.5.2 典型应用场景 ​

  • 跨团队技术推动：推动三个业务团队统一请求层——先写 RFC（含各自迁移成本评估），再逐团队评审吸收意见，最后用门禁与脚手架兜底，而不是靠行政命令。
  • 晋升答辩材料：五维雷达 + 三份代表性产出（一份 ADR、一次 RCA 驱动的流程改进、一个被多团队复用的基建），恰好覆盖 34.1 的能力模型。
  • 新人 onboarding：把 34.3 的腐化地图、34.4 的门禁清单、本目录的 ADR 索引整理成一页纸，新人两周内能独立提交。

34.5.3 可运行代码示例 ​

软素养没有运行时产物，本节给一份可直接套用的 RFC 骨架（虚拟项目文件，不落盘）：

markdown
// 文件: docs/rfcs/0007-unified-request-layer.md —— RFC 模板（结构比文笔重要）

# RFC-0007：统一请求层迁移方案（TanStack Query）

## 1. 问题与约束
- 现状（量化）：自研请求层近两季度贡献 3/6 个 P2 事故；维护占 0.4 人季
- 约束：迁移期间业务正常迭代（不停机窗口）；可用人力 1.5 人月；Q4 有大促封网

## 2. 目标与非目标
- 目标：请求类 P2 事故清零；新请求场景接入时间 < 10 分钟
- 非目标：不重写业务组件的数据消费代码（封装层兜底）；不更换状态管理库

## 3. 方案与备选
- 主方案：TanStack Query + 薄封装层（鉴权/埋点隔离），详见 ADR-0001
- 备选（已否决）：SWR——mutation 与乐观更新能力不足，ADR-0001 有完整比较
- 备选（已否决）：继续自研——缓存失效复杂度增长曲线不可持续

## 4. 迁移与回滚
- 步骤：34.4 灰度状态机（影子 → 1% → 10% → 50% → 100% → 旧层下线）
- 回滚：每阶段流量归零即回滚；封装层保证业务组件零改动

## 5. 度量
- 成功标准：迁移后一个季度请求类事故 ≤ 1；p95 时延不劣化（< 400ms）
- 复审日期：2027-Q2（团队规模或流量结构变化时提前）

34.5.4 最佳实践 ​

  • 非目标段永远要写：它把「顺便把 XX 也做了」挡在评审阶段，是范围蔓延的唯一防线。
  • 评审前 24 小时发出方案：会上首读的方案只会收到「措辞意见」，异步预读才能收到「结构意见」。
  • RCA 行动项优先落流程：「大家以后注意」不是行动项；「该场景加入门禁第 N 关」才是。
  • 小胜利先行：推动大改造前先交付一个两周可见的胜利（一个门禁、一次成功的灰度），信任比方案先到位。

34.5.5 自测题 ​

12. 【基础】RFC 里「非目标」段为什么是最常被省略又最重要的一段？

因为方案评审中最危险的失败不是方案不好，而是范围失控——评审者与阅读者会默认「既然要动这块，顺便把那块也解决了吧」。非目标显式声明本次不做什么，把范围蔓延挡在评审阶段；没有它，一个请求层迁移会在执行中被扩张成「请求层 + 状态管理 + 组件库升级」的巨石工程，最终全部延期。

13. 【进阶】技术评审中「先问约束再给方案」为什么重要？给出一句你会在评审开场说的话。

因为多数「低级设计」背后有外人看不见的约束（历史兼容、排期压力、上游团队协议）。不问约束就给方案，会让作者进入防御姿态、隐藏真实信息，评审退化为攻防；问了约束，讨论会转向「在给定约束下是否还有更优解」，作者也会主动暴露权衡。开场句示例：「这份方案的背景约束我理解得对吗——比如迁移必须在不封网的迭代里完成？在这个前提下我们再看有没有更优解。」

14. 【挑战】一次线上事故的 RCA 结论写到第三层就变成「工程师疏忽」，如何继续下钻？

「疏忽」是症状不是根因，继续问「为什么允许了疏忽发生」：为什么这类操作没有 checklist？为什么该场景没有自动化测试拦截？为什么发布流程允许跳过 review？为什么监控没有在用户受损前告警？每问一层都落到「流程/工具/门禁允许了它」——根因永远在系统而非个人。行动项对应改造：checklist、测试、门禁、告警阈值，且每项有 owner 与期限。

把前五节压成一张季度表——对照附录 A 的 12 周技术学习节奏，这是一份「管理半径 ×2」版本的进阶计划，每季度以一份可验收的产出物收官：

季度主题动作验收产出物
Q1补深度与广度短板按 34.1 雷达自评，选最短板集中训练；技术深度吃透一条线（推荐渲染或网络，对应 10 册 / 6 册）一次团队内技术分享（讲到机制层）+ 雷达复评提分
