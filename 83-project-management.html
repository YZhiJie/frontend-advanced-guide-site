第八十三部分 · 项目管理前端：看板、进度与协作 ​

🧭 返回总目录｜上一篇：第八十二部分 · 配置中心｜关联章节：第四十二部分 · 工作流与审批引擎 · 第六十二部分 · 消息通知中心 · 第六十四部分 · 复杂可编辑表格 · 第七十五部分 · 协同办公核心域

💡 本章特色：JD 把"项目管理"列为 AI 产品前端开发模块之一。项目管理前端的核心不是"画个看板"，而是让任务状态、进度、协作三件事实时、准确、可追溯。本章拆成四块：看板列迁移（状态机守卫，不能乱跳列）、任务进度聚合（子任务自动算 + 手动覆盖）、项目整体进度、成员工作负载（分配任务时推荐最闲的人）。配套示例 83-01-project-kanban.ts 跑通看板迁移、进度聚合、负载推荐。

83.1 项目管理数据模型：项目 / 任务 / 子任务 / 成员 ​

概念解析 ​

项目管理的核心实体：

实体关键字段说明
项目 Projectid, name, owner, members[], status顶层容器，有成员和权限
任务 Taskid, title, status, assignee, priority, dueDate, subtasks[]看板上的卡片
子任务 SubTaskid, title, done任务的细化，用于自动算进度
成员 Memberid, name, role项目成员，有角色权限

任务状态是看板列的基础：backlog（待规划）→ todo（待开始）→ in_progress（进行中）→ review（待评审）→ done（已完成）。

应用实践 ​

  • 任务要有优先级和截止日期：看板上按优先级排序，逾期任务标红提醒；
  • 子任务不是必选项：简单任务可以没有子任务，进度由状态决定（done = 100%，否则 0%）；
  • 权限按项目隔离：项目成员只能看自己项目的任务，跨项目的数据隔离走 72 册组织权限。

83.2 看板视图与拖拽换列 ​

概念解析 ​

看板是项目管理最直观的视图。拖拽换列是核心交互，但不能随便拖——任务状态迁移有规则：

  • backlog 只能到 todo（先规划再开始）；
  • todo 可以到 in_progress 或退回 backlog；
  • in_progress 到 review（做完了等评审）或退回 todo；
  • review 到 done（评审通过）或退回 in_progress（需修改）；
  • done 可以退回 review（发现问题返工）。

禁止跳列：不能从 backlog 直接拖到 done，否则"做没做"全靠自觉，看板失去管理意义。

完整代码示例 ​

ts
// 文件: examples/83-01-project-kanban.ts（节选：看板迁移）
export const KANBAN_TRANSITIONS = {
  backlog: ["todo"],
  todo: ["in_progress", "backlog"],
  in_progress: ["review", "todo"],
  review: ["done", "in_progress"],
  done: ["review"],
};

export function moveTask(task: Task, to: ColumnStatus): Task {
  if (!canMoveTo(task.status, to)) throw new Error(`非法看板迁移: ${task.status} → ${to}`);
  const updated = { ...task, status: to };
  if (to === "done") {
    updated.progressOverride = 100;
    updated.subtasks = updated.subtasks.map((s) => ({ ...s, done: true }));
  }
  return updated;
}

运行方式：npx tsx examples/83-01-project-kanban.ts

应用实践 ​

  • 拖拽要乐观更新 + 失败回滚：用户拖拽后立即在前端更新列，同时发请求。如果请求失败，把任务拖回原列并提示。不要等请求回来才更新，体验卡顿；
  • 拖拽时显示目标列高亮：合法的目标列高亮绿色，非法的目标列不响应（或标红提示"不能直接拖到这里"）；
  • 批量操作：列表视图下支持多选批量改状态、改负责人、改优先级，看板视图下拖拽是单任务操作。

83.3 任务进度与项目整体进度 ​

概念解析 ​

任务进度有两种计算方式：

  1. 子任务自动计算：完成的子任务数 / 总子任务数 × 100%。适合有明确拆分的任务；
  2. 手动覆盖：progressOverride 字段，用户手动填进度百分比。适合难以拆分子任务的任务（如"研究方案"）。

项目整体进度 = 所有任务进度的平均值。可以扩展为按优先级加权（高优先级权重更大），但简单平均已经够大多数场景用。

完整代码示例 ​

ts
// 文件: examples/83-01-project-kanban.ts（节选：进度计算）
export function taskProgress(task: Task): number {
  if (task.progressOverride !== undefined) return task.progressOverride;
  if (task.subtasks.length === 0) return task.status === "done" ? 100 : 0;
  const doneCount = task.subtasks.filter((s) => s.done).length;
  return Math.round((doneCount / task.subtasks.length) * 100);
}

export function projectProgress(tasks: Task[]): number {
  if (tasks.length === 0) return 0;
  const total = tasks.reduce((sum, t) => sum + taskProgress(t), 0);
  return Math.round(total / tasks.length);
}

应用实践 ​

  • 进度条和状态分离展示：进度条是数字（0~100%），状态是列（in_progress 等）。一个 in_progress 的任务进度可能是 30%，一个 review 的任务可能是 90%；
  • 子任务完成自动更新进度：勾选子任务时，任务进度实时重算，不用用户手动改；
  • 项目进度按权限范围算：管理者看全项目进度，成员只看自己负责的任务的进度汇总。

83.4 成员工作负载与任务分配 ​

概念解析 ​

分配任务时，管理者需要知道谁手上活最少。工作负载统计：

  • taskCount：总任务数（含已完成）；
  • activeCount：未完成的任务数（进行中 + 待办），这才是真实负载；
  • totalProgress：所有任务进度之和，反映"还剩多少工作量"。

推荐分配策略：把新任务分给 activeCount 最少的成员。如果多人一样少，再看 totalProgress。

完整代码示例 ​

ts
// 文件: examples/83-01-project-kanban.ts（节选：负载与推荐）
export function recommendAssignee(tasks: Task[], memberIds: string[]): string {
  const workload = computeWorkload(tasks);
  let best = memberIds[0];
  let minActive = Infinity;
  for (const id of memberIds) {
    const active = workload.get(id)?.activeCount ?? 0;
    if (active < minActive) { minActive = active; best = id; }
  }
  return best;
}

应用实践 ​

  • 负载要可视化：成员头像旁边显示"3 个进行中"的徽标，分配任务时一眼看出谁忙谁闲；
  • 考虑技能匹配：负载最低不一定最适合。可以扩展推荐逻辑，加入"成员技能标签与任务标签匹配度"作为第二排序键；
  • 任务分配要通知：分配/改派任务时，通过 62 册消息通知中心 给相关成员发通知。

83.5 自测题 ​

1. 【基础】为什么看板任务不能从 backlog 直接拖到 done？

如果允许跳列，"做没做"全靠自觉，看板就失去了过程管理意义。状态迁移有规则：backlog → todo → in_progress → review → done，每一步代表一个实质进展阶段。跳列会导致漏斗数据失真，无法准确评估项目健康度。

2. 【进阶】任务进度为什么要有"手动覆盖"机制？

有些任务难以拆分成明确的子任务（如"研究技术方案"、"设计架构"），无法用"完成子任务数/总数"算进度。这时允许用户手动填进度百分比（progressOverride），比硬拆子任务更合理。有子任务时自动计算，没有或不想拆时手动覆盖，两种方式互补。

3. 【进阶】为什么工作负载看 activeCount 而不是 taskCount？

taskCount 包含已完成的任务，不能反映当前工作量。一个成员有 20 个任务但 19 个已完成，和有 5 个任务全部进行中，显然后者更忙。所以负载看 activeCount（未完成任务数），taskCount 只用于历史统计。

4. 【挑战】拖拽换列为什么要乐观更新？

如果等服务端请求返回才更新列，用户拖拽后会看到任务"卡一下再动"，体验差。乐观更新是拖拽后立即在前端移动，同时发请求；请求失败再回滚到原列并提示。这样绝大多数成功场景体验流畅，少数失败场景有兜底。

83.7 面试问答 ​

【L2】看板的任务状态迁移为什么要做守卫？能从 backlog 直接拖到 done 吗？

回答框架：① 看板是有向状态机：backlog→todo→in_progress→review→done；② 不能跳列，跳列会让过程管理失效（lead 直接标 won，漏斗数据假）；③ 用 canMoveTo 守卫拦截非法迁移；④ done 可退回 review（返工），体现灵活性。

评分要点：知道状态机和迁移规则；知道不能跳列；提到守卫。

加分项：提到 done 自动把进度设 100%、子任务全标完成；提到拖拽乐观更新。

【L3】一个任务有 5 个子任务，用户勾选了 2 个，进度条应该显示多少？为什么？

回答框架：40%（2/5）。任务进度 = 已完成子任务数 / 总子任务数 × 100%。但如果有 progressOverride 手动覆盖则用手动值。设计原因：子任务完成情况是最客观的进度指标，比用户主观估的百分比更准。

评分要点：知道 2/5=40%；知道子任务自动算；知道有手动覆盖机制。

加分项：提到无子任务时按状态算（done=100%，否则 0%）；提到项目整体进度是所有任务进度的平均。

【L2】分配任务时怎么判断谁最闲？为什么不用总任务数？

回答框架：用 activeCount（未完成任务数）而不是 taskCount（总任务数）。因为已完成的任务不占当前工作量。一个成员 20 个任务但 19 个已完成，比 5 个全进行中的成员闲。推荐分配给 activeCount 最少的成员。

评分要点：知道用 activeCount；知道已完成不计入负载；知道推荐逻辑。

加分项：提到可加入技能匹配作为第二排序键；提到分配要通知当事人。

【L3】用户把任务从 in_progress 拖到 review，请求失败了，前端怎么处理？

回答框架：乐观更新 + 失败回滚。① 拖拽后立即在前端把任务移到 review 列；② 同时发 PUT 请求；③ 如果请求失败：把任务移回 in_progress 原列，弹出提示"更新失败，请重试"；④ 如果请求成功：什么都不做（已经在目标列）。这样绝大多数成功场景流畅，失败有兜底。

评分要点：知道乐观更新；知道失败回滚到原列；知道提示用户。

加分项：提到失败时记录错误日志便于排查；提到网络错误可自动重试一次；提到离线时把操作排队等联网再同步。
