第一百三十二部分 · 浏览器存储工程手册——选型、容量、迁移与安全 ​

本册把散落在 18 Worker 与跨上下文通信、19.9 IndexedDB 结构化仓储、25.10 存储配额、56 离线缓存、126 PWA 工程手册 里的存储知识收成一条完整链路：先选介质，再谈事务与迁移，最后处理配额、加密、性能与测试。

技术基线（2025-11）：Chrome/Edge 131+、Safari 18+、Firefox 133+；navigator.storage.estimate() 与 OPFS 已在三端可用，persist() 仍需用户参与度。示例分两类：纯 TS 逻辑用 npx tsx 实跑；依赖浏览器 API 的用独立 HTML，在 localhost 打开并在 DevTools 验证。

读法：132.1 用来做选型，132.4–132.8 是日常最常用的四类介质，132.9–132.10 是上线前必须补的安全与验收。

132.1 存储能力全景：先选介质，再谈实现 ​

浏览器没有“一个存储 API 解决所有问题”。把需求拆成六个约束，选型就变成排除法：

约束首选次选不要用
需要随请求发给服务端Cookie—localStorage（服务端读不到）
小体量、同步读、可丢失localStoragesessionStorageIndexedDB（异步，杀鸡用牛刀）
结构化数据、按字段查、要事务IndexedDBOPFS + SQLite WASMlocalStorage（无索引、5MB）
HTTP 响应 / 静态资源离线Cache StorageIndexedDBCookie（4KB）
大文件、二进制、顺序 IOOPFSIndexedDB BloblocalStorage（字符串 + 5MB）
跨标签页共享IndexedDB / BroadcastChannelSharedWorkersessionStorage（不跨 Tab）

七种介质的硬边界 ​

介质容量读写模型跨 Tab持久性事务
Cookie4KB/条，数量按域名限制同步，随请求发送共享可设 Expires无
localStorage每源约 5MB同步，阻塞主线程共享（storage 事件）除非用户清理无
sessionStorage每源约 5MB同步不共享（新标签复制 opener）关闭标签即清无
IndexedDB受整站配额约束，通常数百 MB～数 GB异步，事件/ Promise共享persist() 后较稳有
Cache Storage受整站配额约束异步共享随缓存策略无（按 Request/Response）
OPFS受整站配额约束主线程异步 / Worker 同步共享随源存储文件级
内存随页面同步不共享刷新即失无

一条经验：能被用户“清站点数据”清掉的，都不是可靠存储。关键数据必须服务端有副本，本地只做缓存与离线队列。

132.2 Web Storage 深水区：同步 API 的代价 ​

localStorage 的 API 只有五个方法，但生产事故都出在“以为它很简单”。

5MB 是每源，不是每个 key ​

localStorage 的配额按 origin 计算（协议 + 域名 + 端口），不是按 key。一个 key 写 4.9MB，其他 key 就没空间了；写入超限抛 QuotaExceededError，而且旧值保持不变，不会“写一半”。

ts
try {
  localStorage.setItem("draft", JSON.stringify(bigObject));
} catch (err) {
  if ((err as DOMException).name === "QuotaExceededError") {
    // 降级：先清可重建缓存，再重试一次，仍失败则转 IndexedDB/内存
  }
}

同步阻塞：大 JSON 会掉帧 ​

setItem/getItem 是同步的，序列化 + 磁盘写入都发生在主线程。一次写入 1MB JSON 在低端机上可能占用十几毫秒，放在输入事件或滚动回调里就是可见卡顿。三条纪律：

  1. 单条控制在几十 KB 以内，超过 100KB 改用 IndexedDB；
  2. 不在 input、scroll、mousemove 里同步写；
  3. 高频写入做防抖/批量，或挪到 Worker 通过消息回写（Worker 里没有 localStorage）。

只存字符串，且序列化有损 ​

Date、Map、Set、undefined、BigInt、循环引用都会在 JSON.stringify 时丢信息或抛错。需要保真时用结构化克隆（IndexedDB 原生支持）或显式编解码。

storage 事件只通知“别的页面” ​

当前写入页不会收到自己的 storage 事件；值没变化时多数浏览器也不触发。事件里能拿到 key/newValue/oldValue/url，但拿不到写入者身份。跨标签页同步的完整方案见 18 册模块 6，最小闭环：

ts
window.addEventListener("storage", (event) => {
  if (event.key !== "fag:cart") return;
  const next = event.newValue ? JSON.parse(event.newValue) : null;
  applyRemoteCart(next); // 只更新内存，不要再 setItem，避免回声
});

隐私模式与 SSR ​

Safari 隐私模式、部分 WebView、禁用第三方存储时，localStorage 可能在访问属性时就抛异常，而不是等到 setItem。封装里要 try/catch 包住“取 storage 对象”本身；SSR 下 window 不存在，必须延迟到 onMounted/useEffect 再读。

132.3 Cookie 作为存储介质：4KB 与请求头税 ​

Cookie 首先是传输机制，其次才是存储。把它当 KV 用之前先算三笔账：

  • 容量税：4KB/条（name + value + 属性），每域名约 50 条；超出的写入被静默丢弃。
  • 带宽税：同源请求默认携带，图片/接口/静态资源都带；一个 3KB 的 Cookie 会让每个请求多 3KB。
  • 安全税：JS 可读的 Cookie 在 XSS 下等同于明文；HttpOnly 才能挡住脚本读取。

属性边界 ​

属性作用生产建议
HttpOnly禁止 JS 读取会话凭证必须开
Secure仅 HTTPS 发送全站开；SameSite=None 时强制
SameSite=Lax顶层导航才发送默认值，大多数场景够用
SameSite=Strict跨站一律不发高敏操作；会影响从外链进入的登录态
SameSite=None跨站发送必须配 Secure，且受 ITP/第三方 Cookie 限制
Max-Age/Expires过期时间会话凭证短、刷新令牌可长但要有轮换
Domain/Path共享范围尽量窄；Domain=.example.com 会让子域全部可见
Partitioned（CHIPS）按顶层站点分区第三方嵌入场景，需 Secure + SameSite=None

何时不该用 Cookie 存业务数据 ​

购物车、草稿、离线队列都不该放 Cookie：容量小、每次请求都传、还没有事务。Cookie 只保留“服务端必须随请求拿到的小标记”（session id、CSRF token、灰度标记）。

与 token 存储的分工 ​

  • access token：内存变量（页面刷新即失），通过 Authorization 头发送；
  • refresh token：HttpOnly + Secure + SameSite=Lax/Strict Cookie，路径限定到刷新接口；
  • CSRF token：可读 Cookie + 请求头双提交，或 SameSite + Origin 校验；
  • 绝不要把长期 token 写 localStorage——XSS 一条 localStorage.getItem 就全拿走。

Cookie 属性与登出清理的完整实现见 36.8 Token 存储；CSRF 与 XSS 的攻防细节见 07.2。

132.4 IndexedDB 进阶：事务、索引、迁移与阻塞 ​

IndexedDB 的入门用法见 19.9，这里只讲生产里真正会出问题的四件事。

事务的生命周期 ​

事务在“没有待处理请求且回到事件循环”时自动提交；一旦 await 了外部 Promise（fetch、setTimeout），事务大概率已经提交，后续请求抛 TransactionInactiveError。规则：

  1. 事务内只 await IDB 请求本身（idb 库对自身请求做了保活）；
  2. 需要网络先取数据，再开写事务，不要把 fetch 放进事务；
  3. 一个事务尽量只做一类操作，失败时整体回滚更可控。

索引设计：把查询模式写进 schema ​

ts
const store = db.createObjectStore("orders", { keyPath: "id" });
store.createIndex("by-user-created", ["userId", "createdAt"]); // 复合索引
store.createIndex("by-status", "status", { unique: false });
  • 复合索引的字段顺序按“等值在前、范围在后”排；
  • 唯一索引写入冲突会 abort 整个事务，必须捕获 ConstraintError；
  • 索引不是越多越好：每个索引都增加写入成本与存储体积。

迁移：按 oldVersion 分段，不假设从 0 开始 ​

ts
const req = indexedDB.open("shop", 4);
req.onupgradeneeded = (event) => {
  const db = req.result;
  const tx = req.transaction!;
  if (event.oldVersion < 1) db.createObjectStore("orders", { keyPath: "id" });
  if (event.oldVersion < 2) tx.objectStore("orders").createIndex("by-user", "userId");
  if (event.oldVersion < 3) tx.objectStore("orders").createIndex("by-status", "status");
  if (event.oldVersion < 4) tx.objectStore("orders").createIndex("by-created", "createdAt");
};

onblocked：另一个标签页还开着旧版本 ​

升级被旧连接阻塞时，onblocked 触发，页面表现为“打开数据库一直不返回”。正确做法是监听并提示“请关闭其他标签页”，同时给旧连接加 db.onversionchange = () => db.close()，让旧页主动让路。

游标分页：after-key 而不是 offset ​

ts
const range = afterId ? IDBKeyRange.lowerBound(afterId, true) : undefined;
const req = store.openCursor(range);

offset 分页在数据插入/删除后会重复或跳条；after-key 分页稳定。配套纯逻辑示例：

132.5 封装层选型：原生、idb、Dexie、localForage ​

方案体积能力适合代价
原生 IDB0全部，但回调/事务样板多极简依赖、可控封装代码量大，易写错事务
idb~1KBPromise 化、类型友好大多数项目的默认选择仍需自己设计仓储与迁移
Dexie~25KB查询 DSL、版本升级、hooks、实时查询复杂查询、快速迭代包体与学习成本
localForage~10KB类 localStorage API、自动降级从 localStorage 平滑迁移只有 KV，无索引/事务

idb：把回调包成 Promise ​

ts
import { openDB } from "idb";

const db = await openDB("shop", 1, {
  upgrade(db) {
    const store = db.createObjectStore("orders", { keyPath: "id" });
    store.createIndex("by-user", "userId");
  },
});

await db.add("orders", order);
const list = await db.getAllFromIndex("orders", "by-user", userId);

Dexie：查询与迁移一体 ​

ts
import Dexie, { type Table } from "dexie";

class ShopDB extends Dexie {
  orders!: Table<Order, string>;
  constructor() {
    super("shop");
    this.version(1).stores({ orders: "id, userId, status, createdAt" });
    this.version(2).stores({ orders: "id, userId, status, createdAt, [userId+createdAt]" })
      .upgrade((tx) => tx.table("orders").toCollection().modify((o) => { o.synced = false; }));
  }
}

Dexie 的 version().upgrade() 比手写 onupgradeneeded 清晰，但注意：升级函数里不要做网络请求，也不要依赖外部可变状态。

localForage：只适合“从 localStorage 逃生” ​

它提供 getItem/setItem/removeItem 的异步版本，自动在 IndexedDB/WebSQL/localStorage 间降级。适合把已有的 localStorage 封装整体替换，不适合需要索引、游标、事务的新业务。

迁移路径 ​

  1. 先抽 Repository 接口（get/put/delete/queryPage），业务只依赖接口；
  2. 原生 → idb：替换实现，schema 不变；
  3. idb → Dexie：用 Dexie 的 version 声明对齐现有 schema，再逐表迁移；
  4. localStorage → IndexedDB：双读单写，读不到新库时回退旧 key，迁移完成后删旧 key。

132.6 版本迁移与破坏性变更 ​

存储迁移的难点不是“加字段”，而是“旧代码还在跑、新代码已经写了新格式”。

信封：版本 + 数据 + 时间 ​

ts
type Envelope<T> = { v: number; savedAt: number; data: T };

function read<T>(key: string, current: number, migrate: (data: unknown, from: number) => T): T | null {
  const raw = localStorage.getItem(key);
  if (!raw) return null;
  try {
    const env = JSON.parse(raw) as Envelope<unknown>;
    if (env.v > current) return null; // 旧代码读不懂新数据：放弃，别读坏
    return migrate(env.data, env.v);
  } catch {
    localStorage.removeItem(key);
    return null;
  }
}

三种破坏性变更的处理 ​

变更风险策略
字段改名旧数据读不到迁移函数里兼容旧名，新写只用新名
类型变化（string → object）运行时崩溃迁移时做形状判断，坏数据丢弃并上报
删除字段旧页面仍依赖先双写一个版本周期，再删；或按版本号分流

回滚：新版本写的数据，旧版本不能读坏 ​

发布回滚时，旧代码可能遇到更高版本的数据。必须显式判断 v > current 并放弃，而不是“尽力解析”。放弃后走默认值 + 服务端拉取，比读出半截对象安全。

双写与灰度 ​

大版本迁移用“双读单写”：新代码写新 key，读时先新后旧；旧代码继续写旧 key。等新版本覆盖率足够、旧 key 自然过期后再删除。不要在同一次发布里既改 schema 又删旧 key。

多标签页升级 ​

IDB 升级会阻塞旧连接；localStorage 迁移没有锁，两个标签页可能同时迁移。用 navigator.locks.request("fag:migrate", ...) 串行化，迁移完成后广播 storage/BroadcastChannel 让其他页重读。

132.7 配额治理：预算、分层淘汰与跨页协调 ​

先看预算，再决定写不写 ​

ts
const { usage = 0, quota = 0 } = await navigator.storage.estimate();
const ratio = quota > 0 ? usage / quota : 0;
const persisted = await navigator.storage.persisted();

estimate() 是整站口径，可能被舍入；quota 在隐私模式可能为 0。不要用 quota === 0 判断“没空间”，应视为“未知”，按保守策略处理。

分层淘汰，而不是 localStorage.clear() ​

层例子策略
可重建缓存HTTP 缓存、图片、列表快照最先清，按 LRU
离线队列待同步写操作第二清，但只清已成功/过期的
用户数据草稿、设置、收藏最后清，标记 pinned 的不自动清

同层按 lastUsed 升序淘汰；清理前用 navigator.locks 拿跨页锁，避免两个标签页同时删同一批。完整实现与断言：

QuotaExceededError 的处理顺序 ​

  1. 捕获异常，确认 name === "QuotaExceededError"；
  2. 清一层可重建缓存，重试一次；
  3. 仍失败则把非关键写入降级到内存，并提示用户；
  4. 关键写操作（订单、支付）不能只存本地，必须走服务端或明确失败。

persist() 的预期管理 ​

navigator.storage.persist() 不是“申请多少给多少”，而是“请求浏览器不要自动清理”。被拒是常态，尤其在非安装 PWA、访问量低的站点。UI 上不要承诺“永久保存”，要提供导出/备份。

132.8 OPFS 与文件型数据 ​

OPFS（Origin Private File System）是源私有的文件系统，适合大文件、二进制、WASM 数据库文件；不适合按字段查询的业务数据。

主线程：异步写 ​

ts
const root = await navigator.storage.getDirectory();
const dir = await root.getDirectoryHandle("frames", { create: true });
const file = await dir.getFileHandle("cache.bin", { create: true });
const writable = await file.createWritable();
await writable.write(new Uint8Array([1, 2, 3]));
await writable.close();

Worker：同步句柄 ​

createSyncAccessHandle() 只在 Worker 可用，省去每次 await 的微任务开销，适合日志批刷、音视频帧、顺序大文件：

js
const handle = await dir.getFileHandle("bench.log", { create: true });
const access = await handle.createSyncAccessHandle();
try {
  access.truncate(0);
  access.write(new TextEncoder().encode("line\n"), { at: 0 });
  access.flush();
} finally {
  access.close();
}

与 IndexedDB 的分工 ​

  • 要索引、事务、按字段查 → IndexedDB；
  • 要文件句柄、目录、顺序读写、字节偏移 → OPFS；
  • 要在浏览器里跑 SQL → OPFS 存数据库文件 + SQLite WASM/PGlite（见 133）。

边界 ​

OPFS 按源隔离，用户“清除站点数据”会一起删；容量受整站配额约束；Safari 对同步句柄的支持较晚，必须做特性检测与降级。文件句柄本身不持久化到重启（除非用 File System Access API 的用户授权句柄），不要把它当长期 ID。

132.9 加密与合规：能防谁、不能防谁 ​

前端加密常被误解为“XSS 解药”。先把威胁模型摆清楚：

攻击者加密有效原因
拿到设备/浏览器 profile 转储是没有口令派生不出密钥
同源 XSS否脚本能调用同一份解密函数
恶意扩展否可注入脚本读运行时明文
网络中间人无关HTTPS 已覆盖传输

AES-GCM 信封 ​

每次加密随机 12 字节 IV，口令用 PBKDF2 派生密钥，密文与 salt/IV 一起存；GCM 自带完整性校验。

ts
const salt = crypto.getRandomValues(new Uint8Array(16));
const iv = crypto.getRandomValues(new Uint8Array(12));
const key = await deriveKey(passphrase, salt);
const ciphertext = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, plaintext);

密钥放哪 ​

  • 口令派生：密钥只在内存，刷新即失，用户需重新输入；
  • 会话密钥：放内存/Session，绝不与密文同存 localStorage；
  • 不要硬编码在前端包：打包产物里的密钥等于公开。

合规删除 ​

GDPR/个人信息保护法要求“可删除”。删除时必须覆盖 localStorage、sessionStorage、IndexedDB、Cache Storage、OPFS，并通知 Service Worker 清缓存；只删数据库记录不够，浏览器可能还留着快照与备份。删除动作要可审计（记录时间、范围、结果），但日志本身不能含被删数据。

敏感数据的默认姿势 ​

能不落盘就不落盘；必须落盘时只存最小字段、加密、设 TTL，并在登出/切换账号时全清。Token 仍然走 HttpOnly Cookie，这条不被“加密存储”替代。

132.11 自测题 ​

1. localStorage 的 5MB 是每个 key 还是每个源？【基础】

每个源（origin）。同一个域名下所有 key 共享约 5MB，单个 key 写满会导致其他 key 写不进去；超限抛 QuotaExceededError，旧值保持不变。

2. 为什么不能在 `input` 事件里同步写大 JSON 到 localStorage？【基础】

setItem 是同步 API，序列化与磁盘写入都在主线程；大对象会造成掉帧、输入延迟。应防抖、批量，或改用 IndexedDB/Worker。

3. `storage` 事件为什么在当前写入页不触发？【基础】

它设计用于通知其他同源页面；当前页自己知道自己写了什么。相同值重复写入多数浏览器也不触发。

4. Cookie 的 `SameSite=None` 为什么必须配 `Secure`？【基础】

跨站发送的 Cookie 更容易被中间人窃取；浏览器强制要求 Secure（仅 HTTPS）才接受 SameSite=None。同时还要面对 ITP/第三方 Cookie 限制。

5. IndexedDB 事务里 `await fetch()` 为什么会失败？【进阶】

事务在事件循环回到空闲时自动提交；await 外部 Promise 会让事务失去活跃状态，后续请求抛 TransactionInactiveError。应先取数据，再开写事务。

6. 为什么分页要用 `after-key` 而不是 `offset`？【进阶】

offset 基于位置，数据插入/删除后同一位置的内容会变，导致重复或跳条；after-key 基于稳定排序键，翻页不重不漏。

7. 迁移时遇到 `version > current` 应该怎么办？【进阶】

放弃读取，返回 null 并走默认值/服务端拉取。旧代码强行解析新格式会读出半截对象，比重置更危险。

8. 为什么 `persist()` 被拒不能视为错误？【进阶】

它只是“请求浏览器不要自动清理”，是否批准取决于安装状态、站点参与度、浏览器策略。被拒是常态，关键数据必须有服务端副本与导出能力。

9. OPFS 的同步句柄为什么只能在 Worker 用？【挑战】

同步 IO 会阻塞调用线程；主线程阻塞会冻结 UI，所以规范只允许在 Worker 中使用 createSyncAccessHandle()。主线程只能用异步 createWritable()。

10. 前端 AES-GCM 加密能防住 XSS 吗？【挑战】

不能。同源脚本可以调用同一份解密函数、拿到运行时密钥。它只防“设备/存储转储泄露”；XSS 的根治是输出编码、CSP、依赖治理，凭证走 HttpOnly Cookie。

132.12 本章避坑清单 ​

#坑点现象根因正确姿势
1把 5MB 当单 key 上限写到第 N 个 key 突然失败配额按源共享统一预算，超 100KB 换 IDB
2在输入事件里写大 JSON输入卡顿、掉帧同步 API 阻塞主线程防抖/批量/IndexedDB
3用 localStorage 存 tokenXSS 一条脚本全拿走JS 可读HttpOnly Cookie
4Cookie 塞业务数据请求头暴涨、4KB 截断把传输机制当数据库只存小标记
5SameSite=None 不配 SecureCookie 被浏览器丢弃规范强制None + Secure
6sessionStorage 当跨 Tab 共享新标签读不到会话隔离BroadcastChannel/IDB
7事务里 await fetchTransactionInactiveError事务自动提交先取数再开事务
8升级不判断 oldVersion老库缺索引/重复建表假设从 0 开始分段迁移
9不处理 onblocked打开数据库一直转圈旧标签页占用提示关闭 + versionchange 自动 close
10用 offset 分页翻页重复/跳条数据变动导致位置漂移after-key 游标
11一次性 getAll()大表卡死/内存爆全量加载分页 + 懒加载
12单事务写一万条持锁久、失败全回滚事务过大分块 200–1000
13唯一索引冲突不捕获整个事务 abortConstraintError 未处理捕获并给出业务提示
14迁移遇到新版本强行解析读出半截对象/白屏没有回滚保护v > current 返回 null
15发布同时删旧 key回滚后数据全丢没有双写窗口双读单写 + 延后删除
16多标签页同时迁移数据被写两遍/覆盖没有跨页锁navigator.locks
17localStorage.clear() 清配额用户草稿也没了一刀切分层 LRU + pinned
18把 quota=0 当没空间隐私模式误判配额未知视为未知，保守处理
19前端加密当 XSS 解药仍然被盗同源脚本可解密防 XSS + HttpOnly
20只删 IndexedDB 记录合规删除不彻底多介质残留全介质清理 + 审计

心法：存储选型看约束，不看流行度；迁移先想回滚，再想升级；配额先留预算，再谈清理；加密先定威胁模型，再选算法。
