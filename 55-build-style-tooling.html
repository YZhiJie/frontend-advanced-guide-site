55.1 Vite：原生 ESM、预构建与产物切分 ​

概念解析 ​

Vite 的快来自「开发期不打包」：

阶段机制说明
冷启动原生 ESM + 按需编译浏览器直接请求模块，Vite 只转换被请求的文件
依赖预构建esbuild把 CommonJS/大量小模块的依赖合并、转为 ESM，缓存在 node_modules/.vite
热更新HMR基于模块图精确失效，只更新改动模块
生产构建RollupTree-shaking、代码分割、资源哈希
配置vite.config.tsbase、resolve.alias、optimizeDeps、build.rollupOptions

关键配置项：

ts
// 文件: vite.config.ts —— 虚拟工程文件
import { defineConfig } from "vite";

export default defineConfig({
  base: process.env.DEPLOY_BASE || "/",
  resolve: { alias: { "@": "/src" } },
  optimizeDeps: { include: ["lodash-es"] },
  build: {
    target: "es2020",
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom"],
        },
      },
    },
  },
});

为什么需要 optimizeDeps.include：某些依赖是动态导入或 CommonJS，Vite 扫描不到，运行时会临时预构建并触发页面 reload。显式 include 能避免「开发时突然整页刷新」。

base 与部署：子路径部署时必须设置 base，否则产物里的 /assets/... 会指向根路径。base 与路由 base、Nginx 回退路径要一起对齐（见第 53 章）。

典型应用场景 ​

  • 新项目：Vue/React + Vite 是默认选择；
  • 库开发：Vite library mode 产出 ESM/CJS；
  • 多页应用：rollupOptions.input 配多个入口；
  • 微前端：配合 Module Federation 或独立部署 + 运行时加载。

可运行代码示例 ​

示例 55-02 验证 base 规范化与资源 URL 解析，覆盖子路径、根路径、相对 base 与外部 URL。

typescript
// 文件: examples/55-02-vite-base-resolver.ts（核心节选）
function resolveAsset(url: string, base: string): string {
  if (!url || isExternal(url)) return url;
  const normalized = normalizeBase(base);
  if (url.startsWith("./") || url.startsWith("../")) return url;
  if (normalized === "./") return url.replace(/^\/+/, "./");
  return normalized + url.replace(/^\/+/, "");
}

运行方式：npx tsx examples/55-02-vite-base-resolver.ts（子路径、根路径、相对 base、外部 URL、HTML 引用）。

最佳实践 ​

  • ✅ 把 base、define、代理配置集中在一个 vite.config.ts，按环境注入；
  • ✅ 依赖预构建缓存异常时删除 node_modules/.vite 再启动；
  • ⚠️ manualChunks 不是越多越好，过度切分会增加请求数与缓存碎片；
  • ❌ 不要把 Node 专属模块（fs、path）打进浏览器产物——用 define/别名替换或改服务端实现。

55.2 Webpack：核心概念与迁移对照 ​

概念解析 ​

Webpack 的心智模型是「入口 → 依赖图 → loader 转换 → plugin 干预 → chunk 输出」：

概念作用Vite 对应
entry依赖图起点rollupOptions.input
output输出目录、文件名、publicPathbuild.outDir、base
loader单文件转换（ts/css/图片）Vite 内置/插件
plugin构建流程钩子（HTML、环境变量、压缩）Vite 插件
splitChunks公共依赖抽取manualChunks
cache持久化缓存Vite 依赖预构建缓存
Module Federation运行时共享模块需插件或独立方案

什么时候仍然需要 Webpack：

  1. 存量项目依赖大量 Webpack 专属 loader/plugin（如旧版 CSS Modules、特殊资源处理）；
  2. 需要 Module Federation 做微前端运行时共享；
  3. 构建流程与 CI/私有插件深度绑定，迁移成本高于收益。

迁移策略：不要「一次性换构建器」。先对齐产物（publicPath、环境变量、代理、别名），再逐项替换 loader/plugin，最后对比产物体积与首屏指标。

典型应用场景 ​

  • 企业存量系统：Webpack 4/5 + 自定义 loader；
  • 微前端：Module Federation 共享依赖；
  • 多页/多入口：复杂 chunk 编排；
  • 库打包：需要精细控制 externals 与 output。

可运行代码示例 ​

示例 55-01 用简化模型演示 splitChunks 的三类归属：vendor、common、entry，并验证「小于 minSize 的共享模块会在入口重复」。

typescript
// 文件: examples/55-01-split-chunks.ts（核心节选）
if (mod.kind === "vendor") {
  vendor.push(mod);
  continue;
}
if (mod.entries.length >= config.minChunks && mod.size >= config.minSize) {
  common.push(mod);
  continue;
}
for (const entry of mod.entries) {
  entryChunks.get(entry)?.push(mod);
}

运行方式：npx tsx examples/55-01-split-chunks.ts（vendor/common/entry 归属、体积差、阈值调参）。

最佳实践 ​

  • ✅ vendor 按「变更频率」分组：框架单独、UI 库单独、业务公共代码单独；
  • ✅ 开启持久化缓存（cache: { type: "filesystem" }），CI 复用；
  • ⚠️ splitChunks 的 minSize 调大能减少请求，但会让首屏 chunk 变大，要按指标权衡；
  • ❌ 不要在 loader 里做重计算（如每次构建都跑图像压缩），应放独立任务并缓存。

55.3 PostCSS：样式管线的插件顺序 ​

概念解析 ​

PostCSS 本身只做「解析 → 插件变换 → 生成」，能力来自插件。顺序决定结果：

顺序插件作用
1postcss-import合并 @import
2postcss-nesting / postcss-preset-env展开嵌套与新语法
3autoprefixer按 browserslist 补前缀
4tailwindcss（如使用）生成工具类
5cssnano压缩（仅生产）

为什么嵌套要在前缀之前：& .title 只有展开成真实选择器后，autoprefixer 才能正确判断作用范围；顺序反了可能留下 & 或前缀加到错误层级。

browserslist 是前缀的依据：last 2 versions、> 0.5%、not dead 决定要不要 -webkit-。不要「全部加前缀」——会增加体积，也可能引入已废弃语法。

Tailwind 与 PostCSS：Tailwind 作为 PostCSS 插件运行，扫描模板生成工具类；它解决「原子化样式」，与 CSS Modules/CSS-in-JS 是不同路线，不要在同一项目里混三套样式方案。

典型应用场景 ​

  • 组件库：SCSS/Less → PostCSS → 产出 CSS；
  • 老项目兼容：autoprefixer + postcss-preset-env；
  • 原子化：Tailwind + PostCSS；
  • 生产压缩：cssnano 只在 build 阶段启用。

可运行代码示例 ​

示例 55-03 实现「嵌套展开 → 自动前缀 → 压缩」三段管线，并验证顺序错误会残留 &。

typescript
// 文件: examples/55-03-postcss-pipeline.ts（核心节选）
const output = runPipeline(source, [flattenNesting, autoprefix({ webkit: true }), minify]);
assert(output.includes("-webkit-user-select:none;user-select:none"), "应补 -webkit- 前缀");
assert(output.includes(".card .title{margin:0 0 8px 0}"), "嵌套应展开为后代选择器");

const wrongOrder = runPipeline(source, [autoprefix({ webkit: true }), minify]);
assert(wrongOrder.includes("&"), "不先展开嵌套,压缩后仍会残留 &");

运行方式：npx tsx examples/55-03-postcss-pipeline.ts（嵌套、前缀、压缩、顺序依赖、幂等）。

最佳实践 ​

  • ✅ 插件顺序固定为「导入 → 语法 → 前缀 → 工具类 → 压缩」；
  • ✅ browserslist 写进 package.json，CI 与本地一致；
  • ⚠️ 开发环境不跑 cssnano，保留可读源码与 source map；
  • ❌ 不要同时用 CSS Modules、CSS-in-JS、Tailwind 三套方案解决同一类问题。

55.4 构建性能与产物治理 ​

概念解析 ​

构建治理看四个指标：冷启动、热更新、构建耗时、产物体积。对应手段：

指标手段
冷启动依赖预构建、减少入口、按需引入 UI 库
热更新缩小 HMR 范围、避免全局状态导致整页刷新
构建耗时持久化缓存、并行、减少 loader 链、外置大依赖
产物体积Tree-shaking、代码分割、压缩、资源优化、按需 polyfill

产物分析：

  • Vite：rollup-plugin-visualizer 生成 treemap；
  • Webpack：webpack-bundle-analyzer；
  • 看「哪个 chunk 最大、里面是谁、是否被重复打包」。

压缩与传输：JS/CSS 用 gzip/brotli，图片用 WebP/AVIF，字体子集化。压缩是「服务端/构建期」的事，不要在前端运行时做。

性能预算（budget）：给入口 JS、首屏 CSS、图片总量设上限，CI 超限即失败。预算比「事后优化」更能防止回退。

典型应用场景 ​

  • 大型后台：按路由懒加载，vendor 稳定缓存；
  • 移动端 H5：严格控制首屏体积与请求数；
  • 组件库：sideEffects: false + 按组件导出；
  • CI：构建耗时与产物体积双门禁。

可运行代码示例 ​

构建产物的路径与缓存策略是部署事故高发区。示例 55-02 与第 53 章的缓存策略可以组合成上线检查清单。

bash
# 文件: scripts/build-report.sh —— 虚拟工程脚本
pnpm build
npx vite-bundle-visualizer --open false
du -sh dist/assets/* | sort -h | tail -10
gzip -c dist/assets/*.js | wc -c

运行方式：示例脚本需在工程环境执行；路径解析可运行 npx tsx examples/55-02-vite-base-resolver.ts，切分逻辑可运行 examples/55-01-split-chunks.ts。

最佳实践 ​

  • ✅ CI 里跑产物分析并保存报告，按版本对比体积变化；
  • ✅ 路由级懒加载 + 稳定的 vendor 分组，兼顾首屏与缓存；
  • ⚠️ source map 生产环境上传监控平台后不要公开暴露；
  • ❌ 不要为了「构建快」关闭类型检查与 lint——应放到独立并行任务。

55.5 自测题 ​

1. 【基础】Vite 开发期为什么比 Webpack 启动快？

Vite 开发期不打包：浏览器通过原生 ESM 按需请求模块，Vite 只转换被请求的文件；依赖用 esbuild 预构建并缓存。Webpack 需要先构建完整依赖图再启动 dev server，项目越大启动越慢。

2. 【基础】`base` 配置错误会导致什么现象？

子路径部署时，产物中的资源 URL 会指向根路径，导致 JS/CSS/图片 404，页面白屏；路由 base 不一致还会让刷新子路由 404。base 要与构建、路由、Nginx 回退路径一起对齐。

3. 【进阶】`optimizeDeps.include` 解决什么问题？

某些依赖是动态导入或 CommonJS，Vite 启动扫描不到，运行到时才临时预构建并触发页面 reload。显式 include 让它们在冷启动阶段就被预构建，避免开发时突然整页刷新，也能固定依赖形态。

4. 【进阶】`splitChunks` 的 `minSize` 调大有什么利弊？

调大后小模块不再单独拆出，减少请求数，但会把更多代码塞进入口/公共 chunk，首屏体积变大、缓存粒度变粗。需要结合首屏指标与缓存命中率权衡，而不是一味追求「chunk 少」。

5. 【进阶】PostCSS 为什么必须「先展开嵌套,再加前缀」？

& 嵌套在选择器展开前不是一个真实选择器，autoprefixer 无法判断作用范围；顺序反了会残留 & 或把前缀加到错误层级。压缩也应放在最后，否则会破坏后续插件依赖的格式。

6. 【挑战】一个 Webpack 4 的老项目要迁到 Vite，你会怎么评估与实施？

先盘点 loader/plugin 与特殊资源处理，列出 Vite 无直接对应的项；对齐 publicPath/base、别名、环境变量、代理；用分支做「双构建」对比产物与首屏指标；逐项替换（SVG、CSS Modules、环境注入），保留回滚；最后清理 Webpack 配置。若依赖 Module Federation 或私有 loader 很深，迁移收益可能低于维护成本。

7. 【挑战】首屏 JS 从 300KB 涨到 900KB，如何定位与治理？

先用 bundle analyzer 看增量落在哪个 chunk、哪些模块被重复打包；检查是否引入全量 UI 库/图标库、是否把仅服务端用的依赖打进浏览器、是否缺少路由懒加载；再看 source map 确认具体文件。治理按收益排序：按需引入 → 路由分割 → 替换大依赖 → 移除重复副本 → 压缩与 brotli。最后加体积预算门禁防止回退。

8. 【挑战】如何设计一套「构建 + 样式 + 部署」的团队规范？

构建：统一 Vite（新项目）/Webpack（存量）边界，锁定 base、别名、环境变量、代理；样式：固定 PostCSS 插件顺序与 browserslist，禁止三套样式方案混用；产物：路由懒加载、vendor 分组、哈希资源 immutable、HTML no-cache；部署：Nginx 回退与缓存头、CI 产物分析、体积预算与构建耗时门禁；所有规范写成可执行的检查脚本，而不是文档口号。
