第一百二十八部分 · 快捷键与命令系统——从按键事件到可发现的命令面板 ​

本册定位是「交互基础设施层」：把键盘输入、快捷键注册、作用域治理与命令面板串成一套可维护的系统。快捷键作用域的基础模型见 45.3.3 快捷键作用域；命令面板与虚拟列表的性能协同见 10.4 高性能虚拟列表；乐观更新与命令执行状态可对照 05.5 服务端状态管理；表单输入焦点与校验可对照 85 React Hook Form 与 33 Zod。

技术基线（2025-11）：hotkeys-js 3.13+、mousetrap 1.6.5、react-hotkeys-hook 4.x、VueUse 12.x、React 18/19、Vue 3.5。库的大版本升级可能调整选项名，正文对不确定处均标注「以当前 changelog 为准」。

四个配套示例全部是纯 TS、零 DOM 依赖、node:assert 硬断言，可 npx tsx 实跑；React/Vue 片段标注为「项目内运行」。

128.1 心智模型：一次按键到底经过了什么 ​

快捷键系统的第一性问题不是「用哪个库」，而是「把物理按键翻译成业务意图」这条链路要经过哪些层。链路拆错，后面所有 bug 都在补丁上打补丁。

物理按键 → 键盘布局 → KeyboardEvent(key/code) → 修饰键状态 → 作用域与优先级 → 绑定匹配 → 命令执行 → preventDefault

key、code、keyCode：三个容易混的身份 ​

属性含义稳定性适用
event.key当前布局下的字符值，如 "k"、"K"、"ArrowUp"、"Process"受 Shift、CapsLock、输入法、键盘布局影响字符类快捷键（Ctrl+K）
event.code物理键位，如 "KeyK"、"Digit1"、"Space"与布局无关，但不同键盘尺寸可能缺失游戏、WASD、物理位置固定的操作
event.keyCode已废弃的数字码兼容旧代码，不建议新写只用于读旧库/旧代码

结论：业务快捷键用 key，物理位置语义用 code，永远不要用 keyCode 做新逻辑。key 在按住 Shift 时可能从 "k" 变成 "K"，所以匹配前统一小写。

修饰键：ctrlKey / metaKey / altKey / shiftKey ​

  • macOS 的「Command」对应 metaKey，Windows/Linux 的「Ctrl」对应 ctrlKey；
  • 行业惯例用一个抽象名 mod 表示「平台主修饰键」：mac → Meta，其他 → Ctrl；
  • 匹配时修饰键要完全一致：用户多按一个 Shift 不应命中无 Shift 的绑定，否则 Ctrl+K 会吞掉 Ctrl+Shift+K。

事件流：capture、bubble 与 preventDefault ​

keydown 从 window 捕获阶段向下到目标，再冒泡回 window。库通常在 document 上挂一个监听器，靠事件委托分发：

  • capture 阶段拦截：适合「全局优先」的快捷键（如 Esc 关闭最上层弹层），但容易抢走输入框的行为；
  • bubble 阶段拦截：适合业务快捷键，能先让输入框、编辑器处理；
  • preventDefault() 只在确实执行了命令时调用；无脑 preventDefault 会禁用浏览器/辅助技术快捷键（如 Ctrl+F、屏幕阅读器组合键）。

输入法与「按键不是字符」 ​

中文/日文输入法组合期间，keydown 的 key 可能是 "Process"，且 event.isComposing === true。此时不应触发单键快捷键；组合结束的 compositionend 之后才恢复。否则用户输入「nihao」时会被 n、i 等单键命令打断。

可编辑目标：输入框不是快捷键的敌人，但要区别对待 ​

目标单键（如 a、/）组合键（如 Ctrl+K）
input / textarea / select默认放行，交给输入通常允许（保存、打开面板）
contenteditable默认放行通常允许
普通元素 / body允许允许

这条差异必须写进注册表的 allowInInput 选项，而不是散落在每个 handler 里。

128.2 入门：不引库也能写出正确的快捷键 ​

先用 40 行原生代码把「归一化 + 匹配 + 豁免」跑通，后面看库才不会只记 API。

ts
// 文件: examples/128-01-key-normalize.ts（节选）
export interface Binding {
  key: string;
  mod?: boolean;  // 平台主修饰键：mac=⌘，其他=Ctrl
  ctrl?: boolean; // 字面 Ctrl
  meta?: boolean; // 字面 ⌘/Win
  alt?: boolean;
  shift?: boolean;
}

export function matchesBinding(binding: Binding, event: KeyLike, mac = isMac()): boolean {
  const e = normalizeEvent(event);
  const wantCtrl = Boolean(binding.ctrl) || Boolean(binding.mod && !mac);
  const wantMeta = Boolean(binding.meta) || Boolean(binding.mod && mac);
  return (
    e.key === binding.key.toLowerCase() &&
    Boolean(e.ctrl) === wantCtrl &&
    Boolean(e.meta) === wantMeta &&
    Boolean(e.alt) === Boolean(binding.alt) &&
    Boolean(e.shift) === Boolean(binding.shift)
  );
}

运行方式：npx tsx examples/128-01-key-normalize.ts（实跑；断言覆盖 mac/win 映射、多按 Shift 不命中、输入框豁免、快捷键展示格式）

最小可用监听器：

ts
// [浏览器] 项目内运行：全局单监听器 + 委托分发
const onKeyDown = (e: KeyboardEvent) => {
  if (e.isComposing || e.repeat) return;            // 输入法组合 / 长按重复
  if (isEditableTarget(e.target as HTMLElement) && !e.ctrlKey && !e.metaKey) return;
  if (!matchesBinding({ key: 'k', mod: true }, e)) return;
  e.preventDefault();                               // 只有命中才阻止默认行为
  openCommandPalette();
};
window.addEventListener('keydown', onKeyDown, { capture: false });
// 组件卸载 / HMR 时必须成对移除，否则开发环境会叠加多份 handler
// window.removeEventListener('keydown', onKeyDown);

三个细节决定这段代码是否「生产可用」：

  1. capture: false：让输入框先拿到事件；只有需要「全局优先」时才用 true，并配合更严格的豁免；
  2. e.repeat：长按会连续触发 keydown，命令类操作通常只执行一次；需要「长按加速」时才监听 repeat；
  3. 清理：addEventListener 与 removeEventListener 必须传同一个函数引用和相同的 capture 值，否则移除无效。

128.3 主流库怎么选、怎么真用 ​

选型表（按运行环境与需求） ​

库生态作用域序列键输入框豁免适合
hotkeys-js框架无关✅ setScope❌✅ filter老项目、非 React/Vue、需要极致轻量
mousetrap框架无关❌（只有 stopCallback）✅ 序列键✅ stopCallback需要 g i 序列键、老项目
react-hotkeys-hookReact✅ HotkeysProvider❌（底层 hotkeys-js）✅ enableOnFormTagsReact 项目首选
VueUse onKeyStrokeVue❌（自己维护）❌❌（自己判断）单点监听、组合式封装
VueUse useMagicKeysVue❌❌❌组合键按住状态（游戏、画布）

没有「全能冠军」。命令面板这种需要作用域 + 冲突治理的场景，库只提供底座，注册表仍要自己写（见 128.4）。

hotkeys-js：真实 API ​

ts
// [项目内运行] npm i hotkeys-js@3
import hotkeys from 'hotkeys-js';

// 1) 基础绑定：多个组合用逗号分隔；回调第二参是解析后的 handler
hotkeys('ctrl+s, command+s', (event, handler) => {
  event.preventDefault();
  saveDocument();
});

// 2) 作用域：只有当前 scope 的绑定生效
hotkeys('ctrl+k', 'editor', () => openPalette());
hotkeys.setScope('editor');
hotkeys.getScope(); // 'editor'

// 3) 输入框豁免：默认 filter 已经排除 input/textarea/select，
//    需要「输入框内也响应组合键」时自定义 filter
hotkeys.filter = (event) => {
  const target = event.target as HTMLElement;
  const tag = target?.tagName;
  return !(tag === 'INPUT' || tag === 'TEXTAREA' || tag === 'SELECT' || target?.isContentEditable);
};

hotkeys.unbind('ctrl+s, command+s');
hotkeys.isPressed(83); // 物理键 S 是否处于按下状态（keyCode 语义，慎用）

坑点：hotkeys.setScope 是单值不是栈，进入子作用域后要自己记住旧值再恢复；hotkeys.filter 是全局单例，多个模块各改一次会互相覆盖。

mousetrap：序列键是它的主场 ​

ts
// [项目内运行] npm i mousetrap
import Mousetrap from 'mousetrap';

Mousetrap.bind('mod+s', (e) => { e.preventDefault(); save(); });
Mousetrap.bind(['g i', 'g d'], (e, combo) => {
  if (combo === 'g i') goImports();
  if (combo === 'g d') goDefinition();
});
Mousetrap.bind('esc', closeTopLayer);

// 输入框豁免
Mousetrap.stopCallback = (_e, element) => {
  const tag = element.tagName;
  return tag === 'INPUT' || tag === 'TEXTAREA' || (element as HTMLElement).isContentEditable;
};
Mousetrap.unbind('mod+s');
Mousetrap.trigger('mod+s'); // 程序化触发
Mousetrap.reset();          // 清空全部绑定（SPA 切换路由时慎用）

Mousetrap 没有作用域概念，复杂应用需要自己在 stopCallback 或外层包一层作用域判断；mod 是它支持的平台主修饰键别名。

react-hotkeys-hook：React 项目首选 ​

tsx
// [项目内运行] npm i react-hotkeys-hook@4
import { useHotkeys, useHotkeysContext, HotkeysProvider } from 'react-hotkeys-hook';

function Editor() {
  useHotkeys(
    'mod+k',
    (e, handler) => {
      e.preventDefault();
      openPalette();
    },
    {
      enabled: !isModalOpen,
      preventDefault: true,
      enableOnFormTags: ['input', 'textarea'], // 默认不响应输入框
      scopes: ['editor'],
      splitKey: '+', // 绑定里含 "+" 时改分隔符
    },
    [isModalOpen],
  );
  return <div>...</div>;
}

function Shell() {
  const { enableScope, disableScope, activeScopes } = useHotkeysContext();
  // enableScope('editor') / disableScope('editor')
  return <HotkeysProvider initiallyActiveScopes={['global']}>...</HotkeysProvider>;
}

注意：第三个参数是 options，第四个才是依赖数组；把 enabled 写进依赖，否则闭包会读到旧值。react-hotkeys-hook 4.x 底层是 hotkeys-js，作用域是可叠加的（比原生库的单值 scope 好用），但升级大版本前仍要对照 changelog。

VueUse：单点监听与「按住状态」 ​

ts
// [项目内运行] npm i @vueuse/core
import { onKeyStroke, useMagicKeys, useActiveElement } from '@vueuse/core';

// 1) 单键监听：target 默认 window，passive 默认 true
const stop = onKeyStroke('ArrowUp', (e) => {
  e.preventDefault();
  moveUp();
}, { target: window, passive: false });

// 2) 多键共用回调
onKeyStroke(['ArrowUp', 'ArrowDown'], (e) => handleArrow(e.key), { passive: false });

// 3) 组合键按住状态：返回 ref，适合「Shift + 拖拽」「WASD」
const { shift, a, meta, ctrl_k } = useMagicKeys({
  passive: false,
  onEventFired(e) {
    if (e.key === 'k' && (e.metaKey || e.ctrlKey)) e.preventDefault();
  },
});
watchEffect(() => {
  if (shift.value && a.value) selectAll();
});

onKeyStroke 返回 stop()，组件卸载要调用；useMagicKeys 的键名用 ctrl_k 下划线拼接，具体命名以 VueUse 文档为准。VueUse 不提供作用域与冲突检测，复杂场景仍建议自建注册表。

128.4 进阶：作用域栈与冲突治理 ​

单页应用里，快捷键冲突几乎全部来自「多个界面同时认为自己拥有键盘」：编辑器、弹窗、命令面板、侧边栏。解法不是给每个 handler 加 if，而是建立作用域栈。

global
  └─ editor（进入编辑器）
       └─ modal（打开弹窗）
            └─ command-palette（再打开面板）

规则：

  1. 后入栈的作用域优先：Esc 先关面板，再关弹窗，最后才退出编辑；
  2. 同作用域内按 priority 排序：局部覆盖全局，不靠注册顺序碰运气；
  3. 可编辑元素默认豁免，除非注册时显式 allowInInput；
  4. 冲突要在开发期报警：同作用域 + 同 keys + 同 priority 注册两次，后者大概率永远不生效；
  5. 只有命中才 preventDefault：否则 Ctrl+F、Ctrl+R 等浏览器行为会被误吞。
ts
// 文件: examples/128-02-hotkey-registry.ts（节选）
resolve(e: HotkeyEvent): Registration | null {
  const keys = canonicalKeys(e);
  const editable = isEditable(e.target);
  const scopeRank = new Map(this.scopeStack.map((s, i) => [s, i]));
  const candidates = this.registrations
    .filter((r) => r.keys === keys)
    .filter((r) => r.allowInInput || !editable)
    .filter((r) => scopeRank.has(r.scope))
    .sort((a, b) => {
      const byScope = (scopeRank.get(b.scope) ?? 0) - (scopeRank.get(a.scope) ?? 0);
      return byScope !== 0 ? byScope : b.priority - a.priority;
    });
  return candidates[0] ?? null;
}

运行方式：npx tsx examples/128-02-hotkey-registry.ts（实跑；断言覆盖作用域优先、priority、输入框豁免、repeat、冲突检测）

工程化建议：

  • 注册即返回 disposer：const off = registry.register(...)，组件卸载调用 off()，比手工维护数组可靠；
  • 作用域用 push/pop 而不是 set：弹窗嵌套时 set('modal') 会丢失父作用域；
  • 重复进入同一作用域要幂等：栈里做去重，避免一次 pop 后仍然停留在该作用域；
  • 开发环境打印冲突：CI 里可把冲突数作为失败条件，防止新增快捷键悄悄覆盖旧命令。

128.5 命令系统：让能力「可发现、可禁用、可解释」 ​

快捷键只是命令的快捷入口，不是命令本身。成熟产品（VS Code、Linear、Notion）都有一张命令表：

ts
interface Command {
  id: string;                 // 稳定标识，用于埋点、菜单、快捷键绑定
  title: string;              // 面板里展示的人类可读名称
  category: string;           // 分组：编辑 / 视图 / 文件
  keybinding?: string;        // "mod+k"，展示时按平台格式化
  when?: (ctx) => boolean;    // 当前上下文是否可用
  run: (ctx) => void | Promise<void>;
}

when 条件：命令的「可见性」与「可用性」 ​

  • 可见性：不满足 when 的命令不出现在面板里，避免用户看到一堆灰项；
  • 可用性：命令出现在菜单里但置灰，需要向用户解释原因（如「未选中文本」）；
  • 两者不要混：when 管「是否展示」，enabled 管「是否可执行」，面板里可以展示但禁用。

when 不建议直接写任意函数（无法序列化、无法做权限审计）。VS Code 使用一套小型表达式语言（editorFocus && !inDebugMode）。业务里至少收敛成「上下文键值 + 谓词注册表」：

ts
type WhenExpr = (ctx: CommandContext) => boolean;
const when = {
  hasSelection: (c: CommandContext) => c.hasSelection,
  isEditing: (c: CommandContext) => c.isEditing,
  and: (...fs: WhenExpr[]): WhenExpr => (c) => fs.every((f) => f(c)),
  or: (...fs: WhenExpr[]): WhenExpr => (c) => fs.some((f) => f(c)),
  not: (f: WhenExpr): WhenExpr => (c) => !f(c),
};

模糊搜索：子序列匹配 + 位置加权 ​

命令面板的搜索不是全文检索，而是子序列匹配：查询 gip 可以命中 Git: Initialize Project。评分要点：

  1. 字符必须按顺序出现（子序列），否则不命中；
  2. 连续命中加分，git 应比 g...i...t 更靠前；
  3. 词首命中加分（空格、-、/ 后的首字母）；
  4. 标题越短，同等命中下越靠前，避免长描述霸榜；
  5. 中文场景可再加拼音首字母索引（fz → 复制），但不要把拼音硬编码进评分函数。
ts
// 文件: examples/128-03-command-system.ts（节选）
export function fuzzyScore(query: string, text: string): number {
  const q = query.trim().toLowerCase();
  if (!q) return 0;
  const t = text.toLowerCase();
  let score = 0, ti = 0, streak = 0;
  for (const ch of q) {
    const found = t.indexOf(ch, ti);
    if (found === -1) return -1;
    score += 1;
    if (found === ti) { streak++; score += streak * 2; }
    else streak = 0;
    if (found === 0 || /[\s\-_/]/.test(t[found - 1] ?? '')) score += 4;
    ti = found + 1;
  }
  return score - t.length * 0.01;
}

运行方式：npx tsx examples/128-03-command-system.ts（实跑；断言覆盖 when 过滤、模糊排序、平台化快捷键展示、重复 id 与键位冲突）

快捷键展示：不要在 UI 里硬编码 Ctrl ​

同一个命令在不同平台显示不同组合：

配置macOSWindows/Linux
mod+k⌘KCtrl+K
mod+shift+p⇧⌘PCtrl+Shift+P
alt+arrowup⌥↑Alt+↑

格式化函数要按 ⌃⌥⇧⌘ 的固定顺序输出（Apple 的规范顺序），而不是按配置字符串里的书写顺序。否则 mod+shift+p 会显示成 ⌘⇧P，和系统菜单不一致。

128.6 序列键：g i 这类「前缀 + 后续键」 ​

序列键（chord / multi-key）解决的是「单组合键不够用」：VS Code 的 g i、GitHub 的 g c。它的本质是一个带超时的前缀状态机：

按 g → 有以 g 开头的序列 → 进入 pending，等待 1s
  再按 i → 命中 g i → 执行并清空
  按了 x → 无匹配 → 清空
  超过 1s → 超时清空
ts
// 文件: examples/128-04-chord-sequence.ts（节选）
feed(key: string, now = Date.now()) {
  if (this.pending && now - this.pending.at > this.timeoutMs) this.pending = null;
  const keys = this.pending ? [...this.pending.keys, key.toLowerCase()] : [key.toLowerCase()];
  const hit = this.exact(keys);
  if (hit) { this.pending = null; return { type: 'matched', result: hit.run() }; }
  if (this.hasPrefix(keys)) { this.pending = { keys, at: now }; return { type: 'pending', keys }; }
  this.pending = null;
  return { type: 'none' };
}

运行方式：npx tsx examples/128-04-chord-sequence.ts（实跑；断言覆盖前缀、超时、非法后续键、单键与序列共存）

设计取舍：

  • 超时值：600~1000ms 是常见区间；太短用户来不及按第二个键，太长会让单键响应变迟钝；
  • 前缀与完整序列冲突：如果同时注册了 g 和 g i，按 g 后必须等待超时才执行单键，否则永远无法触发 g i。示例中的策略是「完整匹配优先」，因此单键 g 会立即执行，g i 永远不会命中——真实产品要么禁止这种共存，要么给单键也加超时；
  • 视觉反馈：进入 pending 后应在状态栏/面板显示「等待第二个键」，否则用户不知道系统在等什么；
  • 输入框豁免：序列键尤其容易和输入冲突，必须在可编辑目标里完全禁用。

128.7 无障碍、输入法与浏览器保留键 ​

无障碍（a11y） ​

  • 所有快捷键对应的功能都必须有可点击入口：快捷键是加速器，不是唯一路径；
  • 给可交互元素加 aria-keyshortcuts="Control+K"（使用 WAI-ARIA 的键名，不是 mod）；
  • 命令面板本身要能用键盘完整操作：↑/↓ 移动、Enter 执行、Esc 关闭、焦点陷阱与 aria-activedescendant；
  • 不要劫持屏幕阅读器常用组合键（如 Ctrl+Alt+方向键、Insert+...）；
  • 提供「快捷键一览」页面，并允许用户自定义/禁用。

输入法与组合事件 ​

ts
// [项目内运行] 输入法组合期间不要触发单键命令
input.addEventListener('keydown', (e) => {
  if (e.isComposing || e.key === 'Process') return;
  // 处理快捷键
});
input.addEventListener('compositionstart', () => { composing = true; });
input.addEventListener('compositionend', () => { composing = false; });

isComposing 在部分旧浏览器上不可靠，必要时用 compositionstart/end 自己维护标记。

浏览器保留键与系统冲突 ​

组合风险建议
Ctrl/Cmd + W、Ctrl/Cmd + T关标签页/新标签页，网页通常无法拦截不要占用
Ctrl/Cmd + N、Ctrl/Cmd + Shift + N新窗口/隐私窗口不要占用
Ctrl/Cmd + R、F5刷新不要占用
Esc退出全屏、关闭对话框可用于关闭自定义弹层，但要考虑全屏场景

另外，键盘布局会导致 key 变化：法语 AZERTY 键盘上 M 在物理 KeyM 位置但字符不同；德语键盘的 Z 与 Y 互换。字符类快捷键用 key 符合用户预期，物理操作（游戏）用 code。

128.8 性能、清理与源码级理解 ​

单监听器优于 N 个监听器 ​

每个 useHotkeys 若各挂一个 document 监听器，20 个快捷键就是 20 个 handler，每次按键全部执行一遍匹配。成熟库的做法是：

  1. 一个全局监听器（document 或 window），维护 Map<canonicalKeys, Registration[]>；
  2. 事件到达后先归一化，再 O(1) 查表；
  3. 只对命中的注册项排序（作用域 + priority），而不是每次全量排序；
  4. 未命中直接返回，不调用 preventDefault。

hotkeys-js 内部就是「解析组合 → 建立 key 映射 → 单监听器分发」；react-hotkeys-hook 在其上包了 React 生命周期与 scope 管理。理解这一点，就能解释为什么「注册 100 个快捷键」不会线性拖慢按键响应，而「100 个组件各自 addEventListener」会。

清理与 HMR ​

  • React：useEffect 返回 cleanup；StrictMode 下 effect 会执行两次，注册表必须幂等（重复注册同一 id 要覆盖或报错，不能叠加）；
  • Vue：onScopeDispose / onUnmounted 调用 stop()；
  • HMR：模块热替换时旧 handler 可能残留，开发环境可用 import.meta.hot.dispose(() => registry.clear())；
  • 路由切换：离开页面时 pop 作用域并解绑该页面的命令，否则「设置页的 Ctrl+S」会在首页继续生效。

一个容易忽略的成本：preventDefault 与被动监听 ​

keydown 默认不是 passive 的，可以 preventDefault；但 touchstart / wheel 等默认 passive，需要显式 { passive: false }。快捷键系统通常只监听 keydown，不受此影响；但「按住空格拖拽画布」这类交互会同时涉及 keydown 与指针事件，别把 passive: true 误加到需要阻止默认行为的监听上。

与虚拟列表/大列表的协同 ​

命令面板动辄几千条命令，渲染全部 DOM 会卡顿。做法与 10.4 高性能虚拟列表 一致：先过滤排序，再只渲染可视区。搜索输入要做 100~150ms 防抖，但键盘上下移动不能防抖；选中项用 aria-activedescendant 而不是真实焦点，避免滚动抖动。

128.9 自测题 ​

1. `event.key` 与 `event.code` 的本质区别是什么？各自适合什么场景？【基础】

key 是当前键盘布局与修饰键状态下的字符值（"k"/"K"/"ArrowUp"），受 Shift、CapsLock、输入法、布局影响；code 是物理键位（"KeyK"），与布局无关。字符类快捷键用 key，游戏/WASD/物理位置固定的操作用 code；keyCode 已废弃，不应在新代码中使用。

2. 为什么匹配快捷键时要求修饰键「完全一致」？【基础】

否则 Ctrl+K 也会命中 Ctrl+Shift+K，导致更具体的绑定被吞掉；同时用户多按 Shift 时执行了错误命令。正确做法是把 ctrl/meta/alt/shift 全部纳入比较，只有完全相等才命中。

3. `mod` 是什么？为什么界面展示不能硬编码 `Ctrl`？【基础】

mod 是平台主修饰键的抽象：macOS 映射 Meta（⌘），Windows/Linux 映射 Ctrl。界面展示必须按平台格式化，并遵循 macOS 的 ⌃⌥⇧⌘ 固定顺序；硬编码 Ctrl+K 会让 mac 用户看到错误提示。

4. 作用域为什么必须用栈而不是单值？【进阶】

弹窗可以嵌套（编辑器 → 弹窗 → 命令面板），单值 setScope 会丢失父作用域，关闭弹窗后无法恢复。栈结构支持 push/pop，且「后入栈优先」符合「最上层界面先响应」的直觉；重复进入同一作用域要做幂等去重。

5. 什么时候应该 `preventDefault`？无脑阻止会有什么后果？【进阶】

只在绑定真正命中并执行了命令时调用。无脑阻止会吞掉浏览器查找、刷新、辅助技术快捷键，降低可访问性；未命中时必须放行，让浏览器和输入控件处理。

6. 输入法组合期间为什么要跳过快捷键？如何检测？【进阶】

组合期间 keydown 的 key 可能是 "Process"，且用户是在输入文字，不是执行命令；触发单键快捷键会打断输入。可用 event.isComposing 或 compositionstart/end 维护标记，compositionend 后恢复。

7. 命令的 `when` 与 `enabled` 有什么区别？为什么不能混用？【挑战】

when 决定命令是否出现在面板/菜单（可见性），enabled 决定已出现的命令是否可执行（可用性）。混用会导致两种坏体验：不可用命令完全消失，用户不知道功能存在；或大量不可执行命令堆在面板里，没有解释。成熟产品会展示但置灰，并给出原因。

8. 序列键与单键共存时，为什么会出现「单键永远赢」或「单键延迟」？【挑战】

如果完整匹配优先，按 g 时若同时注册了单键 g，会立即执行单键，g i 永远无法触发；如果前缀优先，按 g 后必须等待超时才能确定不是序列，单键响应被延迟。产品必须二选一：禁止共存，或给单键也加超时并给出视觉反馈。

9. 为什么「每个组件各挂一个 document 监听器」是性能与正确性双重问题？【挑战】

性能上，每次按键要执行 N 个 handler 的匹配；正确性上，多个监听器都能 preventDefault，顺序取决于注册顺序，冲突不可控。成熟方案是单监听器 + 注册表 + 作用域优先级，按键时 O(1) 查表、只对命中项排序。

10. 键盘布局差异会怎样影响快捷键？产品应如何兜底？【挑战】

AZERTY、Dvorak、德语键盘等会改变 key 的字符值，甚至 Z/Y 互换；依赖字符位置的快捷键在不同布局下可能失效或错位。兜底方式：优先使用 code 做物理位置操作、提供快捷键自定义、在设置页展示实际按键并允许重置，同时对国际键盘做测试。
