第一百一十九部分 · 大型 Vue 3 双端项目实战——从需求到上线 ​

🧭 返回总目录｜上一篇：第一百一十八部分 · WebRTC 客户端实战｜关联章节：第一百一十三部分 · Vue 3 单仓多端工程 · 第一百一十四部分 · Vue Router 深度 · 第一百一十五部分 · 海外化工程 · 第一百一十六部分 · IM 弱网与高并发治理 · 第五十九部分 · 监控与可观测性

本部分内容 ​

前面各册拆开讲了多端目录、路由、海外化、IM、埋点与监控；这一册把它们装进一个能交付的项目：面向海外市场的 Vue 3 双端商城（PC Web + H5/PWA）。重点回答四个问题：需求怎么切、代码放哪里、双端差异怎么收口、上线凭什么敢发。四个示例覆盖脚手架生成、领域模型与 API 层、发布门禁、指标看板，均可实跑。

119.1 需求拆解与范围 ​

概念解析 ​

双端项目的第一个误区是「功能对等」：把 PC 的功能清单原样复制到 H5，再按 1.5 倍工时报价。真实约束是同一业务目标、两种使用场景——PC 做深度操作，H5 承接投放流量与即时决策。

拆解要产出三样东西：范围矩阵（行是模块，列是端、优先级、验收口径、依赖，没有验收口径不算拆完）、优先级（P0 缺了上不了线，P1 上线后两周补齐，P2 明确不做）、范围冻结线（T-10 个工作日冻结 P0，变更走变更单并评估双端 UI 成本）。

以海外家居 DTC「Loom & Oak」（PC 商城 + 投放落地 H5）为例：

模块PC WebH5 / PWA优先级验收口径
登录 / 账户全量，含设备管理短信 + 第三方登录P0成功率 ≥ 99.5%，refresh 失败自动回登录
列表 / 详情筛选、对比、多图单列信息流、分享深链P0首屏 LCP P75 ≤ 2.5s，深链参数不丢
购物车 / 结账多步、地址簿、发票单页、Apple/Google PayP0下单成功率 ≥ 98%，回跳可恢复
订单 / 售后批量操作、导出仅退款申请P1状态机无非法迁移
IM 客服入口独立工作台入口悬浮入口、半屏会话P1断线可重连，离线消息不丢

反例：某团队把「H5 也要商品对比」写进 P0，首屏多加载 180KB 组件，LCP 从 2.1s 涨到 3.6s，投放转化跌了 12%。

应用实践 ​

  • 每个 P0 配可量化验收：不是「支持支付」，而是「3DS 完成率 ≥ 98%，失败可重试且不重复扣款」。
  • 拆解时标出服务端与第三方依赖（支付、分享），它们排期最不可控。

最佳实践 ​

  • ✅ 范围矩阵与 P2「为什么不做」进项目 README，每周更新。
  • ⚠️ 不要用复用率倒推需求：先定体验，再定哪些代码共享。

119.2 架构分层与目录 ​

概念解析 ​

目录按依赖方向切，不按页面切：页面会重组，依赖方向不会。核心约束只有一条：业务规则只住 core，端差异只住 adapters 与 ui-*。core 一旦出现 window、localStorage 或 element-plus，这套代码就无法安全跑在另一端。

src/
  core/              # 纯 TS：定价、优惠、订单状态机、金额
  services/          # 能力契约：storage/share/payment/http
  adapters/pc|h5/    # 端能力实现，允许碰平台 API
  composables/       # 共享 Vue 逻辑，只依赖 core + services
  ui-shared/         # 无交互范式组件：价格、评分、空态
  ui-pc/  ui-h5/     # Element Plus / Vant 页面与组件
  router/ stores/    # 业务 name 路由表、Pinia 领域 store
  entries/pc.ts      # 唯一组装点：注入 adapter、注册 UI 库
  entries/h5.ts

物理隔离而不能只靠 Code Review：一次 import { ElMessage } from 'element-plus' 就会把整个组件库拖进 H5 产物。119-01 把纪律做成生成器：模块声明层级与依赖，生成前校验越层依赖、跨端引用、UI 库串端、依赖环与命名，任一违规直接抛错。

运行方式：npx tsx examples/119-01-project-scaffold.ts

生成器还会输出拓扑序、目录清单与双端入口，并把 ui-pc 模块的 target 锁成 ['pc']，保证 PC 组件不会进入 H5 产物——比构建后再看体积更早、更便宜。

应用实践 ​

  • entries 是唯一组装点：PC 注入 PC adapter 与路由，H5 注入 H5 版本，业务代码不判断端。
  • 新模块先声明 layer 与 deps 再写代码，生成器报错比线上串端便宜两个数量级。

最佳实践 ​

  • ✅ ESLint 同时禁止 core → adapters、ui-pc ↔ ui-h5 与跨端 UI 库导入。

119.3 数据层：API、状态与缓存 ​

概念解析 ​

数据层分四段，每段只做一件事：

层职责不该做的事
API clientURL、超时、取消、重试、traceId不懂业务字段
RepositoryDTO → 领域模型、错误归一、缓存不碰 UI 状态
Store（Pinia）领域状态、动作编排、跨页共享不直接发裸请求
View渲染与交互不吞错误、不猜字段

三个高频事故：金额用浮点（舍入直接造成资损，必须用最小单位整数）；错误只分成功/失败（UI 无法判断该重试、刷新还是重新登录）；取消当失败（切页 abort 进入错误上报会淹没监控）。

119-02 把三件事做实：DTO 映射、错误归一、带退避与取消穿透的 requestWithRetry，以及 TTL/单飞/标签失效/陈旧兜底的缓存。

运行方式：npx tsx examples/119-02-domain-api-layer.ts

缓存按资源的新鲜度价值定，不能一把梭 Cache-First：

资源策略TTL失效
商品详情内存 TTL + 陈旧兜底5 分钟价格/库存变更按 product 标签
首页 feed短 TTL + 单飞60 秒运营发布后按 feed 标签
用户资料内存 TTL10 分钟修改成功后主动失效
订单 / 支付结果不缓存—每次回源，避免展示过期状态

应用实践 ​

  • 列表页并发请求同一详情时，单飞把 N 次网关调用压成 1 次，这是弱网下最便宜的优化。
  • 重试只覆盖网络错误、429、5xx；401 先刷新 token 且只重试一次，409 交给用户刷新。

最佳实践 ​

  • ✅ 所有写操作带幂等键，重试与连点都不会产生重复订单。
  • ✅ 错误归一保留 requestId，客服能直接对到网关日志。

119.4 核心业务模块 ​

概念解析 ​

五个核心模块的共性不是「页面多」，而是失败路径比成功路径多。先列状态与失败路径，再写页面：

模块前端职责关键状态 / 失败路径双端差异
登录token 存取、刷新单飞、登出清理anonymous → authenticating → authenticated → refreshing；401 刷新失败即登出PC 设备管理、改密；H5 第三方登录
列表游标分页、去重、空态/错误态idle → loading → ready → empty → error；重复 key 按 id 去重PC 表格列设置；H5 无限滚动
详情预取、骨架屏、深链参数404 / 下架 / 区域不可售是三种不同页面PC 多图放大；H5 轮播 + 分享
支付发起、回跳、轮询、恢复created → redirecting → pending → paid / failed / refunded；只允许前进PC 3DS 跳转；H5 钱包 / Apple Pay
IM 入口懒连接、未读聚合、重连idle → connecting → open → reconnecting → closedPC 独立窗口；H5 半屏 + 轮询兜底

两条硬规则：支付状态只信服务端（回跳参数只作为「去查询」的信号，未知显示「确认中」）；IM 入口不要首屏连接（未读数走轻量轮询，时序见第一百一十六部分）。

应用实践 ​

  • 登录刷新用单飞：多个 401 同时到达只发一次 refresh，其余请求排队等结果。
  • 列表记录游标而非页码；支付回跳先「确认中」，轮询未知则提供「查看订单」。

最佳实践 ​

  • ✅ 每个模块先画状态机再写组件，非法迁移在领域层拒绝。

119.5 双端差异与降级 ​

概念解析 ​

端判断的正确顺序：构建期确定端 → 运行期探测能力 → 能力缺失走降级。不要用 UA 猜端：UA 可伪造、会被精简，触摸本与横屏平板都会误判。运行期只探测具体能力（navigator.share、pointer: coarse、存储配额）。

能力PCH5缺失时的降级
分享Web Share / 复制链接navigator.share，不支持则复制隐藏原生分享，保留复制
支付3DS 跳转 / 卡支付Apple Pay / Google Pay / 钱包 deep link钱包不可用回退卡支付
存储IndexedDBlocalStorage（配额小）只存 token 与草稿，图片不落库
上传大文件分片压缩后单请求超限提示，不静默失败
IMWebSocket 独立窗口WS + 轮询兜底后台暂停连接，回前台补拉

路由降级是硬职责：PC 专属路由（批量导入、发票管理）在 H5 打开应跳首页并提示，而不是 404；旧链接跨端打开按业务 name 重建路径，参数不能丢，详见第一百一十四部分。

反例（双端逻辑漂移）：PC 的优惠计算写在 CheckoutPc.vue 的 computed 里，H5 又抄一份并「顺手」改成满减可叠加。三个月后两人分别改需求，同一订单两端算出不同价格。根因不是谁写错，而是业务规则没有唯一归属——它必须住在 core/pricing。

应用实践 ​

  • 能力探测结果集中成 profile 对象，在 entries 启动时注入，页面只读不猜。

最佳实践 ​

  • ✅ 同一业务规则只允许一个实现，双端差异只体现在调用方式与展示。
  • ⚠️ 不要用媒体查询替代业务降级：屏幕窄不代表能力缺失。

119.6 质量：测试、监控与灰度 ​

概念解析 ​

质量不是「测得多」，而是在正确的层级测正确的东西：

层级测什么频率失败含义
单元core 定价、优惠、状态机、金额每次提交业务规则坏了
契约两端 adapter 同构、路由 name 齐全每次提交端能力接口漂移
组件ui-pc / ui-h5 各自渲染与交互每次提交单端 UI 回归
构建双端产物、入口、PWA、体积门禁每次 PR串端或预算超标
E2E登录 → 商品 → 购物车 → 支付回跳合并前 + 夜间主链路不可用

监控只盯三类信号：业务（下单/支付成功率）、性能（LCP/INP P75、JS 错误率）、依赖（支付网关、IM、CDN）。每类都要有 SLI、阈值与端/区域维度。

灰度是风险控制，不是发布仪式，批次与止损线提前定：

批次比例观察窗口止损条件
内部白名单1 小时任一 P0 报错
小流量1%2 小时支付成功率跌 1pp 或 JS 错误率 > 0.5%
扩量10% → 50%每档 4 小时LCP P75 恶化 20%
全量100%24 小时值守5 分钟内可决策回滚

应用实践 ​

  • 埋点用「业务名 + 模块名 + 端 + 区域」，不用 URL path，改路由不打断历史数据。
  • 灰度按用户 ID 哈希分桶，同一用户始终落在同一桶，避免体验闪烁。

最佳实践 ​

  • ✅ 契约测试复用同一组断言跑两个 adapter，新增能力时两端同时红。

119.7 上线与运维 ​

概念解析 ​

上线的本质是把不可逆操作变成可逆操作，三道闸门必须在发布前过：

闸门必检内容阻断条件
发布清单构建、单测、E2E、体积、兼容矩阵、埋点缺项或 unknown
回滚版本、CDN、SW、后端开关、数据迁移未演练或迁移不可逆
值守发布窗口、值班人、决策权无人能在 5 分钟内决策

反例（上线无回滚）：某团队周五晚全量发布新版结账页，未灰度、未准备回滚。20 分钟后支付成功率从 97% 掉到 61%，新版把 3DS 回跳参数解析错了；CDN 与后端同时变更，回滚花了 40 分钟，损失一个周末的投放预算。问题不在写错一行代码，而在没有任何止损路径。

119-03 把门禁做成可执行判定：必检项缺失、状态非 pass、体积超预算、分类无必检项全部阻断；可选检查失败只进告警。判定逻辑把「缺项」归一成 missing:<id>，把失败归一成 check:<id>，输出可直接贴进发布单。

运行方式：npx tsx examples/119-03-release-checklist.ts

应用实践 ​

  • 清单由 CI 生成，人工只补兼容矩阵与回滚演练这类机器判断不了的项。
  • 回滚方案写清楚：切回哪个版本、CDN 怎么刷、SW 怎么降级、后端开关怎么关。

最佳实践 ​

  • ✅ 每次发布都做回滚演练，哪怕只是预发环境。

119.8 作品集叙事与指标 ​

概念解析 ​

作品集最容易犯的错是「功能罗列」。面试官关心你如何决策、结果如何被度量。可复述的叙事是：背景与约束（海外 DTC 双端商城、投放占 60%）→ 关键决策（内核共享/UI 分端、支付只信服务端、哈希灰度）→ 结果（H5 LCP P75 4.1s→2.3s、支付成功率 94%→98.6%）→ 复盘（哪条决策被推翻、代价是什么）。

指标必须口径一致，否则数字不可比：

指标正确口径常见错误
转化漏斗逐级取交集，只有走完上一步才算进入下一步各步独立去重，跳步支付被算进转化
留存注册当天入组（cohort），第 N 天有任意活跃即留存分母混入非同期用户，留存被稀释
性能P75、nearest-rank、分端分路由用平均值掩盖长尾，样本不分端
异常最小样本量 + 相对跌幅阈值凌晨小样本波动触发告警

119-04 把漏斗、留存、性能 P75、阈值告警与环比异常检测算成可断言结果；漏斗逐级取交集，异常先过最小样本量再看相对跌幅。

运行方式：npx tsx examples/119-04-metrics-dashboard.ts

应用实践 ​

  • 作品集只放 2~3 个能讲清决策的项目，每个配架构图、指标曲线与复盘。

最佳实践 ​

  • ✅ 数字必须能追溯到埋点或监控，不能凭印象。

119.9 自测题 ​

先自己作答，再展开参考答案。

1. 双端项目为什么不能按「功能对等」拆需求？范围矩阵至少要有什么列？【基础】

同一业务目标在两种场景下价值不同：PC 适合深度操作，H5 承接投放与即时决策。功能对等会把 PC 重组件带进 H5，拖慢首屏。矩阵至少要有模块、端、优先级、验收口径、依赖；没有验收口径不算拆完。

2. 目录为什么按依赖方向切？`core` 引入 Vue 会怎样？【基础】

页面会重组，依赖方向稳定。按层切能把业务规则锁在 core、端差异锁在 adapters 与 ui-*。core 一旦引入 Vue/Pinia/DOM API，就无法在另一端复用，最终业务规则会被复制成两份。

3. DTO 为什么要映射成领域模型？金额为什么用最小单位整数？【基础】

DTO 是接口形状，字段与状态会随后端变化；领域模型是页面稳定依赖的契约，映射层负责校验、补默认值与派生字段。浮点金额存在舍入误差，会造成资损；最小单位整数运算精确，展示时再按币种精度格式化。

4. 哪些错误可自动重试？为什么取消不能当错误？【进阶】

可重试：网络错误、超时、429、5xx。不可重试：400/422、401/403、404、409 与业务拒绝；401 可先刷新 token 且只重试一次。取消是用户意图，不是服务异常；若当失败会触发无意义重试、污染错误率与告警。

5. TTL、单飞、标签失效、陈旧兜底各自解决什么？【进阶】

TTL 控制新鲜度；单飞让同一 key 的并发请求共享 Promise，避免列表页重复打网关；标签失效在数据变更后批量清缓存；陈旧兜底在回源失败且未超窗口时返回旧值，弱网不白屏。订单与支付结果永不缓存。

6. 端判断为什么不能只看 UA？正确顺序是什么？【进阶】

UA 可伪造、会被精简，触摸笔记本与横屏平板都会误判。正确顺序：构建期由 mode 确定端 → 运行期探测具体能力（navigator.share、pointer: coarse、存储配额）→ 缺失按降级矩阵回退。屏幕宽度只影响布局，不决定业务能力。

7. 发布门禁为什么「缺项」也要阻断？`unknown` 怎么算？【挑战】

缺项意味着没有证据证明通过，风险与失败等价；unknown（如兼容矩阵未确认）同理，不能按「差不多可以发」放行。缺项、非 pass、超预算、分类无必检项都应阻断；可选检查失败只进告警，避免门禁被无关项拖死。

8. 漏斗、留存与异常检测的口径陷阱分别是什么？【挑战】

漏斗必须逐级取交集，否则跳步支付会虚高转化；留存分母只能是注册当天入组的 cohort，不能混入非同期用户；异常检测先过最小样本量再看相对跌幅，否则凌晨小样本波动会持续误报，绝对跌幅也无法跨指标比较。

119.10 本章避坑清单 ​

#坑点现象根因正确姿势
1按「功能对等」拆双端需求H5 首屏被 PC 组件拖慢把端差异当复制粘贴范围矩阵 + 验收口径 + 范围冻结
2业务规则写在页面里两端算价/优惠不一致规则没有唯一归属规则只住 core，两端只调用
3金额用浮点差一分钱、对账失败浮点误差、精度写死 2 位最小单位整数 + 按币种格式化
4错误只分成功/失败所有错误都弹「稍后重试」没有错误分类归一 kind + retryable + requestId
5取消当失败上报错误率虚高、告警噪声abort 未独立建模独立错误类型，不重试不上报
6所有请求都自动重试重复下单、重复扣款POST 无幂等却重试写操作带幂等键，支付只查不重试
7支付回跳即置为已支付未扣款也显示成功信了前端回跳参数只信服务端查询，未知显示「确认中」
8用 UA 判断端平板/触摸本体验错乱UA 可伪造且被精简构建期定端 + 运行期能力探测
9PC 专属路由在 H5 直接 404用户丢失、客服工单增加路由表没有降级职责跳首页并提示，参数保留
10上线无回滚、无灰度故障持续数十分钟到数小时把发布当一次性动作检查清单 + 分批灰度 + 回滚演练

心法：双端项目的复杂度不在「写两套 UI」，而在「让业务规则只有一份、让失败可恢复、让结果可度量」。需求守住范围、架构守住依赖方向、数据守住金额与错误、上线守住回滚与灰度——这四道闸门守住了，项目才从「能跑」变成「敢上线」。
