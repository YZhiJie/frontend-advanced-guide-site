127.1 部署拓扑与选型决策 ​

先把「发布单元」定清楚 ​

发布工程的第一性问题不是「用什么工具」，而是「一次发布到底交付了什么」。前端常见发布单元只有三种：

发布单元典型形态回滚手段版本可见性
静态制品对象存储 / CDN / 静态托管平台切回上一份 index.html 与资源前缀URL 与 release 标记
容器镜像前端镜像、BFF 镜像、边缘容器回滚镜像 tag 或 kubectl rollout undo镜像 digest + OCI label
混合静态走 CDN，动态走 BFF两条链路分别回滚，必须版本对齐同一 release 写入两端

选型时先回答四个硬约束，再看成本：

  • 是否需要服务端能力：SSR、鉴权重写、WebSocket、私有网络访问。
  • 团队运维成熟度：有没有 7×24 值班、能不能读 K8s 事件与 Nginx 错误日志。
  • 合规边界：数据能否出私有网络、能否使用境外 CDN。
  • 发布频率与回滚时限：每天多次发布与每周一次发布，对审批与自动化的要求完全不同。

拓扑决策矩阵 ​

拓扑SSR长连接私有网络灰度分流运维成本适用场景
对象存储 + CDN否否弱弱最低纯静态 SPA、文档站、营销页
静态托管 + 边缘函数部分部分弱强低轻 SSR、AB 实验、边缘鉴权
Node BFF + Nginx强强强中中前端团队独立维护全栈
Kubernetes最强最强最强强最高多服务、弹性伸缩、平台团队
混合（CDN + 容器 BFF）强强强强中高大多数中大型业务

关键结论：没有平台团队时，K8s 本身就是最大的单点故障。运维成熟度低于 3 分（0~5）时，优先选择静态托管或「Nginx + 少量 Node 机器」，把 K8s 留到有专人负责之后。

配套示例把这张表变成可执行的决策器：硬约束先淘汰、再加权打分、最后做运维成本敏感性检查。

ts

  ssr: false,
  longConnection: true,

多环境与分支策略 ​

环境不是越多越好，而是每个环境必须回答一个不同的问题：

环境目的数据访问发布方式
dev本地/联调mock 或测试库内网开发者自起
preview每个 PR 的预览隔离的临时数据内网 + 分享链接平台自动创建
staging生产同构验收脱敏数据内网 + 白名单合并主干自动部署
production真实用户生产数据公网审批后发布

分支策略与环境的映射要固定下来，避免「分支名即环境」的随机性：

策略分支模型环境映射适合团队
Trunk-based只有主干 + 短命分支主干 → staging；tag → production有自动化测试与特性开关
GitHub Flow主干 + feature 分支PR → preview；合并 → staging；手动 → production大多数中小团队
GitFlowdevelop/release/hotfixdevelop → dev；release → staging；main → production版本周期长、需要并行维护

两条硬规则：

  1. 构建一次，晋级多次。同一份制品从 staging 晋级到 production，禁止在生产环境重新构建——否则「测过的」和「上线的」不是同一个东西。
  2. 环境差异只允许来自运行期配置。VITE_* 在构建期被内联，构建产物一旦按环境分叉，就无法晋级；需要按环境变化的值走运行期注入（见 47.3 注入方案）。

vercel.json ​

json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "vite",
  "buildCommand": "pnpm build",
  "outputDirectory": "dist",
  "cleanUrls": true,
  "trailingSlash": false,
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    },
    {
      "source": "/(index\\.html)?",
      "headers": [{ "key": "Cache-Control", "value": "no-cache" }]
    },
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "X-Frame-Options", "value": "DENY" }
      ]
    }
  ],
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

要点：

  • Vercel 的路由顺序是 重定向 → 响应头 → 文件系统 → 重写。静态文件命中时不会走 rewrites，所以 /(.*) → /index.html 不会吞掉 /assets/*。
  • cleanUrls 影响的是「是否允许省略 .html」，与 SPA 回退是两件事，不要用它代替 rewrites。
  • source 是路径模式而不是正则字面量；/(index\\.html)? 在 JSON 中需要转义反斜杠。

netlify.toml ​

toml
[build]
  command = "pnpm build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "22"

[[headers]]
  for = "/assets/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/index.html"
  [headers.values]
    Cache-Control = "no-cache"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

要点：Netlify 默认「静态文件优先」，只有未命中的路径才进入 redirects；status = 200 是重写（地址栏不变），301/302 才是重定向。需要强制覆盖静态文件时才加 force = true。

Cloudflare Pages：_headers 与 _redirects ​

text
# _headers（放在构建产物根目录）
/assets/*
  Cache-Control: public, max-age=31536000, immutable

/index.html
  Cache-Control: no-cache

/*
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
text
# _redirects
/*    /index.html   200

要点：

  • _headers 按「先精确后通配」匹配，同一响应会合并命中规则，同名头以后者为准。
  • _headers 不支持正则，只支持路径与 * 通配；复杂规则要交给边缘函数。
  • _redirects 的 200 表示 rewrite；静态资源是否优先于 rewrite 由平台路由决定，若发现资源被误重写，优先检查规则顺序与路径前缀。

wrangler.toml 用于直传（wrangler 3.28+/4.x）：

toml
name = "frontend-advanced-guide"
compatibility_date = "2025-01-01"
pages_build_output_dir = "dist"

[vars]
  VITE_API_BASE = "/api"

版本差异：更早的 Workers Sites 使用 [site] bucket = "./dist"，与 Pages 的 pages_build_output_dir 不是同一套配置；升级 wrangler 后不要混写。

GitHub Pages：base 与 404 的等价写法 ​

GitHub Pages 没有配置文件，等价能力靠三件事：

  1. base 路径：项目页地址是 https://<user>.github.io/<repo>/，Vite 必须设置 base: '/<repo>/'，否则所有绝对路径资源 404。
  2. 404 回退：把 index.html 复制为 404.html，未知路径由 Pages 的 404 文档接管，前端路由再解析 location.pathname。
  3. 禁用 Jekyll：产物根目录放 .nojekyll，避免下划线开头的资源被过滤。
ts
// vite.config.ts
export default defineConfig({
  base: process.env.GITHUB_PAGES_BASE ?? "/",
});
yaml
# .github/workflows/pages.yml（节选）
- run: pnpm build
  env:
    GITHUB_PAGES_BASE: /${{ github.event.repository.name }}/
- run: cp dist/index.html dist/404.html && touch dist/.nojekyll
- uses: actions/upload-pages-artifact@v3
  with:
    path: dist

平台限制要如实说明：GitHub Pages 不能下发自定义响应头，因此无法设置 HSTS、X-Frame-Options、immutable 缓存。生产站点要么在前面加 Cloudflare 之类的代理，要么接受这些缺口，不要假装配置过。

配套示例直接解析这四种平台的真实配置，并检查「回退、入口不缓存、资源长缓存、安全头、base」五件事是否等价。

ts
// 文件: examples/127-02-static-host-config-linter.ts

  const r = lint(f);
  assert.deepStrictEqual(r.errors, [], `${f.platform} 存在配置错误`);
}
const gh = lint(github);
assert(
  gh.errors.some((e) => e.includes("index.html")),
  "GitHub Pages 无法设置 no-cache，检查器必须报错而不是假装通过",

运行方式：npx tsx examples/127-02-static-host-config-linter.ts

127.3 对象存储与 CDN 发布 ​

桶策略与上传身份 ​

推荐「桶私有 + CDN 回源鉴权」，而不是「对象逐条 public-read」：

  • 关闭 ACL（S3 Object Ownership 设为 Bucket owner enforced），统一用桶策略授权。
  • CDN 通过 OAC（CloudFront）或服务端回源凭证读取私有桶，避免对象被直链盗刷。
  • 上传身份使用 CI 的 OIDC 临时凭证，禁止把长期 AK 写进仓库或构建机（见 47.5 CI/CD 与云端密钥服务）。

CORS 至少要覆盖「前端域名 + 需要的 method + 必要的响应头」：

json
[
  {
    "AllowedOrigins": ["https://app.example.com"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["Range", "If-None-Match"],
    "ExposeHeaders": ["ETag", "Content-Length", "Content-Range"],
    "MaxAgeSeconds": 86400
  }
]

不要写 AllowedOrigins: ["*"] 来「先跑通」：静态资源一旦带凭证或涉及私有桶，通配 CORS 会把权限边界抹平。

自定义域名与证书 ​

CDN证书要求注意事项
CloudFrontACM 证书必须签发在 us-east-1与业务区域无关；证书与分布绑定
Cloudflare通用 SSL 或上传自定义证书代理模式（橙云）下源站证书可用 Full (strict)
国内 CDN备案 + 证书托管域名备案是前置条件，不能事后补

缓存规则分层 ​

路径浏览器缓存CDN TTL发布时是否刷新原因
/assets/*（带哈希）1 年 immutable1 年否内容变则文件名变
/index.html、/no-cache0是入口必须每次校验
/sw.jsno-cache0是SW 更新必须回源
/manifest.webmanifest1 小时1 小时是图标/名称变更需短周期生效
/images/*（未哈希）30 天30 天是运营图替换按路径刷新
/api/*no-store不缓存否动态数据，缓存由 BFF 决定

发布顺序与刷新 ​

正确顺序只有一条：先资源、再入口、最后 SW。

  1. 上传新的哈希资源（旧 HTML 仍引用旧资源，此阶段零影响）。
  2. 覆盖 index.html，让新入口引用新资源。
  3. 覆盖 sw.js 与 manifest。
  4. 刷新 CDN 的 /、/index.html、/sw.js、/manifest.webmanifest，以及被替换的未哈希运营图。
  5. 预热首页与首屏关键资源。

反例是「先刷 HTML 再传资源」：CDN 已经返回新 HTML，但新资源还没上传，用户直接白屏。

        try_files $uri =404;

        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }

    error_log  /var/log/nginx/frontend.error.log warn;

为什么这样写 ​

  • 缓存头用 map 在 server 层注入：nginx 的 add_header 不会从父级继承——只要任意 location 里出现一个 add_header，server 层的全部 add_header 都会失效，安全头会一起消失。把分层规则集中到一个 map，location 里只写行为、不写头。
  • try_files $uri $uri/ /index.html 是 SPA history 回退；/assets/ 与 /index.html 用精确匹配，避免未知路径被误当成资源。
  • upstream keepalive 需要三件套：keepalive、proxy_http_version 1.1、proxy_set_header Connection ""。缺任何一个，连接复用都不生效。
  • /healthz 不写 add_header：一旦在 location 里写头，就会触发上面的继承问题。健康检查只需要状态码。
  • gzip_static 读取构建期生成的 .gz，避免每个请求现压缩；brotli 的四个指令需要 ngx_brotli 模块，未安装时 nginx -t 会直接报 unknown directive。

TLS 与证书续期 ​

bash
# 首次签发（webroot 模式，ACME 通道已在 80 端口放行）
certbot certonly --webroot -w /var/www/certbot \
  -d app.example.com --agree-tos -m ops@example.com --no-eff-email

# 续期并平滑重载
certbot renew --deploy-hook "nginx -t && nginx -s reload"
  • 用 systemd 的 certbot.timer 或 cron 每天跑一次 certbot renew；续期是幂等的，未到期不会重复签发。
  • --deploy-hook 里先 nginx -t 再 reload，配置写错时不会把线上打挂。
  • 证书路径必须指向 fullchain.pem，只给 cert.pem 会缺中间证书，部分 Android/旧客户端握手失败。

版本差异：http2 on; 需要 nginx ≥ 1.25.1；更早版本写 listen 443 ssl http2;。两者不要同时写，否则部分版本会告警或重复启用。

五条硬要求 ​

  1. 多阶段：构建工具、源码、node_modules 都不进运行镜像；只拷产物。
  2. 层缓存顺序：先拷 package.json + lockfile 并安装，再拷源码。反过来每次改一行代码都会重装依赖。
  3. 非 root：静态镜像用 nginx-unprivileged（uid 101），Node 镜像用内置 node 用户；同时 allowPrivilegeEscalation: false。
  4. HEALTHCHECK：镜像自身可自检，编排层与 docker run 都能看到健康状态。
  5. exec form CMD：["node", "server/index.js"] 让 Node 成为 PID 1，能收到 SIGTERM 做优雅退出；shell form 会让信号被 shell 吞掉。

127.6 Kubernetes 部署与编排 ​

工作负载 ​

完整清单见 examples/deploy/k8s/deployment.yaml，核心片段：

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: web
spec:
  replicas: 2
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app.kubernetes.io/name: frontend
      app.kubernetes.io/component: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: frontend
        app.kubernetes.io/component: web
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 101
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: web
          image: ghcr.io/example/frontend:0.0.0
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 256Mi
          startupProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 10
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - { name: tmp, mountPath: /tmp }
            - { name: nginx-cache, mountPath: /var/cache/nginx }
      volumes:
        - name: tmp
          emptyDir: {}
        - name: nginx-cache
          emptyDir: {}

要点：

  • maxUnavailable: 0 + maxSurge: 1：先起新 Pod 再停旧 Pod，容量不下降；代价是发布期间多占一份资源。
  • 三探针分工：startupProbe 只负责「启动慢」，成功后 readiness/liveness 才接管；readinessProbe 决定是否接流量，livenessProbe 决定是否重启。就绪探针不要和存活探针打同一个重接口。
  • readOnlyRootFilesystem: true 时，nginx 需要 /tmp 与 /var/cache/nginx 可写，用 emptyDir 挂载；否则容器会因写缓存失败反复重启。
  • resources.requests 决定调度，limits 决定上限；只写 limits 不写 requests，调度器会按 0 处理，节点过载时最先被驱逐。

Service 与 Ingress ​

yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend
  namespace: web
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: frontend
    app.kubernetes.io/component: web
  ports:
    - name: http
      port: 80
      targetPort: http
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
  namespace: web
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/proxy-body-size: 8m
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [app.example.com]
      secretName: frontend-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: bff, port: { number: 3000 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: frontend, port: { number: 80 } }
  • Service 的 selector 必须与 Pod template 的 labels 完全对得上，否则 Endpoints 为空，表现为 502/503。
  • Ingress 的 /api 必须排在 / 前面（更具体优先），并且不要把 /api 重写到 BFF 的根路径，除非 BFF 的路由就是这么设计的。
  • TLS 由 cert-manager 或云厂商证书服务接管；手工 Secret 只适合临时环境。

HPA ​

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: bff
  namespace: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: bff
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource

        name: cpu

  • minReplicas 不要低于 2；单副本时节点故障就是全站不可用。

127.7 CI/CD 流水线设计 ​

一条合格的发布流水线 ​

yaml
name: deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

concurrency:
  group: production-deploy
  cancel-in-progress: false

env:
  NODE_VERSION: "22"
  AWS_REGION: ap-southeast-1
  AWS_ROLE_ARN: arn:aws:iam::123456789012:role/github-actions-frontend-deploy
  S3_BUCKET: example-frontend-prod
  CDN_DISTRIBUTION_ID: EXXXXXXXXXXXXX
  PROD_URL: https://app.example.com

jobs:
  verify:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm test -- --run
      - run: pnpm exec tsc --noEmit

  build:
    needs: verify
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
        env:
          VITE_API_BASE: /api
          VITE_RELEASE: ${{ github.sha }}
      - run: grep -rq "${{ github.sha }}" dist
      - uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: dist
          retention-days: 30
          if-no-files-found: error

  deploy-prod:
    needs: [build]
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://app.example.com
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: dist
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ env.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Upload immutable assets first
        run: |
          aws s3 sync dist/assets "s3://${S3_BUCKET}/assets" \
            --cache-control "public,max-age=31536000,immutable"
      - name: Publish HTML entry
        run: |
          aws s3 cp dist/index.html "s3://${S3_BUCKET}/index.html" \
            --cache-control "no-cache"
      - name: Invalidate CDN
        run: |
          aws cloudfront create-invalidation \
            --distribution-id "${CDN_DISTRIBUTION_ID}" \
            --paths "/" "/index.html" "/sw.js"
      - name: Smoke test
        run: |
          for i in $(seq 1 60); do
            if curl -fsS "${PROD_URL}/" | grep -q "${{ github.sha }}"; then break; fi
            [ "$i" = "60" ] && exit 1
            sleep 5
          done
          curl -fsS -o /dev/null "${PROD_URL}/healthz"
          curl -fsSI "${PROD_URL}/index.html" | grep -qi 'cache-control: *no-cache'
      - name: Rollback on failure
        if: failure()
        run: |
          aws s3 cp "s3://${S3_BUCKET}/releases/${PREV_SHA}/index.html" \
            "s3://${S3_BUCKET}/index.html" --cache-control "no-cache"
          aws cloudfront create-invalidation \
            --distribution-id "${CDN_DISTRIBUTION_ID}" --paths "/" "/index.html"

完整版本（含 staging 晋级、current.txt 回滚指针、手动回滚入口）见 examples/deploy/github-actions/deploy.yml。

每一段为什么存在 ​

设计解决的问题不这样做会怎样
verify 矩阵 20/22兼容性与升级前置验证只测一个版本，用户环境炸了才发现
build 只跑一次制品唯一，避免矩阵产物分叉两个 Node 版本产出不同 bundle，测的和发的不是一份
upload-artifact + download-artifact部署不重新构建生产构建环境差异导致「测过但没发对」
environment: production + Required reviewers发布审批与审计任何人合并即上线，事故无人兜底
permissions: id-token: write + OIDC换取云临时凭证长期 AK 落盘，泄漏面无限大
concurrency + cancel-in-progress: false发布串行，不互相踩两次发布并发，资源与入口版本交错
grep release 标记确认新版本真的生效CDN 还没刷新就宣布成功
if: failure() 回滚失败自动止血等人工发现时用户已经白屏

GitHub 细节：Environment 的 Required reviewers 在公开仓库可直接使用；私有仓库需要 GitHub Pro/Team/Enterprise。若组织策略不允许，退化为「部署 job 前加人工 workflow_dispatch 审批」也比没有闸门好。

127.8 灰度、蓝绿与回滚 ​

Nginx 按比例灰度 ​

nginx
split_clients "${remote_addr}${http_user_agent}" $variant {
    5%      canary;
    *       stable;
}

upstream frontend_stable {
    server 10.0.1.10:8080;
    keepalive 32;
}

upstream frontend_canary {
    server 10.0.1.11:8080;
    keepalive 32;
}

server {
    listen 443 ssl;
    # ... TLS 与安全头同上

    location / {
        proxy_pass http://frontend_$variant;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
    }
}
  • split_clients 对字符串做哈希，同一 IP + UA 永远落同一桶，避免用户刷新时在版本间跳变。
  • 比例调整后 nginx -s reload 生效；已有连接不会被切断。
  • 灰度期间两套资源必须同时在线，且 index.html 与 assets 的版本要匹配；建议用 releases/<sha>/ 目录 + current 软链，回滚只切软链。

Kubernetes 灰度 ​

  • 滚动更新：maxUnavailable: 0 的 RollingUpdate 是「逐步替换」，不是按比例导流；它保证可用性，但不提供按用户分流。
  • 双 Deployment + 不同 Service：frontend-stable 与 frontend-canary 各自一个 Deployment，Ingress 按权重或 Header 分流。
  • ingress-nginx 的 canary 注解（如 nginx.ingress.kubernetes.io/canary-weight）在不同版本间有差异，且需要同一 host 下两个 Ingress 配合；上线前用目标集群版本实测，不要照抄博客。
  • 需要更完整的渐进式发布（暂停、分析指标、自动回滚）时，使用 Argo Rollouts 或 Flagger 这类 CRD；这属于平台能力，不在本册的标准资源范围内。

蓝绿 ​

蓝绿的本质是「两套完整环境 + 一个原子切换点」：

  1. 绿环境部署新版本，跑健康检查与冒烟。
  2. 边缘层（Nginx upstream、负载均衡后端组、DNS 权重）一次性切到绿。
  3. 蓝环境保留至少一个观察窗口，作为回滚目标。
  4. 观察窗口结束后再回收蓝。

Nginx 蓝绿用两个 upstream + reload 即可；容器平台用 Service selector 或 Ingress 后端切换；静态托管用平台 alias / promote 能力。

平台 alias 与回滚 ​

平台灰度/回滚能力注意
VercelPreview Deployment、Instant Rollback、Promote回滚是切 deployment 指针，不是重新构建
NetlifyDeploy Preview、Publish deploy、Rollback回滚同样切指针，旧 deploy 需保留
Cloudflare PagesPreview Deployment、Rollback与 Functions 版本一起回滚
对象存储 + CDN自己维护 current.txt 指针必须同时刷新 HTML 与 SW

与版本守卫、Source Map 联动 ​

  • 入口 HTML 注入 release（构建期 VITE_RELEASE），前端启动时上报；监控按 release 切片，才能判断「新版本是否更差」（见 45.2 线上自愈）。
  • Source Map 按 release 上传到错误平台，并与制品同源保存；回滚时错误平台也要能查到旧版本的 map（见 59.3 错误指纹聚合与分级上报）。
  • 不允许「Source Map 上传到 A 版本、代码发布 B 版本」：堆栈会解析到错误的源码行，排障直接失去意义。

curl 断言脚本 ​

bash
#!/usr/bin/env bash
set -euo pipefail
BASE="${BASE:-https://app.example.com}"
RELEASE="${RELEASE:?需要传入当前 release}"

assert_eq() { [ "$1" = "$2" ] || { echo "✗ $3（期望 $2，实际 $1）"; exit 1; }; }

code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/healthz")
assert_eq "$code" "200" "healthz"

curl -fsS "$BASE/" | grep -q "$RELEASE" || { echo "✗ 入口未指向 $RELEASE"; exit 1; }

code=$(curl -s -o /dev/null -w '%{http_code}' "$BASE/orders/123")
assert_eq "$code" "200" "SPA 回退"

curl -fsSI "$BASE/index.html" | grep -qi 'cache-control: *no-cache' || { echo "✗ 入口缓存头错误"; exit 1; }
curl -fsSI "$BASE/sw.js" | grep -qi 'cache-control: *no-cache' || { echo "✗ SW 缓存头错误"; exit 1; }

echo "✓ 冒烟通过：$BASE @ $RELEASE"

在 CI 里把「等待生效」写成有限次重试（例如 60 次 × 5 秒），不要用固定 sleep 120：CDN 生效时间不可预测，固定等待要么不够、要么浪费。

RUM 观察窗口 ​

窗口观察指标判定
0~5 分钟JS 错误率、白屏率、首屏 P75任一超基线 2 倍立即回滚
5~30 分钟接口错误率、P95、转化关键路径持续高于基线 1.5 倍则回滚
30~60 分钟长尾错误、按 release 切片确认无新增错误类型后关闭观察

观察窗口内保留旧版本制品与 Source Map，禁止清理；回滚后再观察至少 30 分钟。

回滚演练清单 ​

  • [ ] 回滚指令或按钮在 5 分钟内可执行，且不需要重新构建。
  • [ ] 回滚目标版本仍在制品库/CDN 上，未被生命周期策略删除。
  • [ ] 回滚后 index.html 与 assets 版本匹配，无 chunk 404。
  • [ ] Service Worker 已回滚或下发「自毁 SW」，旧缓存不会继续服务。
  • [ ] Source Map 能解析回滚后版本的堆栈。
  • [ ] 回滚后监控按 release 切片正常，告警静音规则已恢复。
  • [ ] 每次演练记录实际耗时，超过目标值要优化流程而不是改目标。

CDN 刷新顺序 ​

  1. 先确认新资源已上传并回源 200。
  2. 刷新入口 /、/index.html。
  3. 刷新 /sw.js、/manifest.webmanifest。
  4. 刷新被替换的未哈希资源（运营图、字体）。
  5. 不要刷新 /assets/*：哈希资源靠 URL 变化天然失效，刷了既慢又浪费配额。
  6. 刷新后预热首页与首屏关键 JS/CSS，避免第一批用户回源抖动。

127.10 自测题 ​

1. 静态托管、Node BFF、Kubernetes 三种拓扑的边界分别是什么？【基础】

静态托管只解决「文件分发」，没有服务端执行能力；Node BFF 补上 SSR、鉴权、聚合与长连接，但要自己承担进程、端口、发布与扩容；Kubernetes 在 BFF 之上提供调度、滚动、探针与弹性，但引入集群运维成本。选型的硬约束是 SSR/长连接/私有网络/合规，成本约束是团队运维成熟度与发布频率。

2. Vercel、Netlify、Cloudflare Pages、GitHub Pages 的 SPA 回退分别怎么写？【基础】

Vercel 用 rewrites 把未命中路径指向 /index.html；Netlify 用 [[redirects]] from = "/*" to = "/index.html" status = 200；Cloudflare Pages 用 _redirects 的 /* /index.html 200；GitHub Pages 没有配置能力，只能把 index.html 复制成 404.html，并正确设置 Vite base。四者的共同点是「200 重写而不是 301/302」。

3. 为什么发布顺序必须是「资源 → HTML → SW」？【进阶】

旧 HTML 引用旧资源，先上传新资源不会影响在线用户；随后切换 HTML，新入口引用已经就位的新资源；最后更新 SW，避免它在资源未就绪时按新清单缓存导致 404。反过来先刷 HTML 会出现「新入口 + 旧资源缺失」的白屏窗口。

4. nginx 的 `add_header` 继承陷阱是什么？本册如何规避？【进阶】

add_header 不会从父级继承：只要某个 location 里出现任意 add_header，server 层的全部 add_header 都不再生效。规避方式是把缓存策略收敛到一个 map $uri $cache_control，只在 server 层写一次 add_header Cache-Control $cache_control always，location 内不写任何 add_header。

5. 多阶段构建为什么能瘦身？层缓存顺序为什么重要？【进阶】

运行阶段只从构建阶段拷贝产物（如 dist/、server/），不携带编译器、源码与 devDependencies，镜像体积和攻击面都下降。层缓存方面，先拷 package.json 与 lockfile 再安装，源码变化不会击穿依赖层；如果先 COPY . . 再安装，每次改代码都会重装依赖。

6. K8s 的 `maxUnavailable: 0`、三探针、`readOnlyRootFilesystem` 分别解决什么问题？【挑战】

maxUnavailable: 0 保证滚动期间可用副本不下降，先起新 Pod 再停旧 Pod；startupProbe 保护慢启动应用不被 liveness 误杀，readinessProbe 控制是否接流量，livenessProbe 控制是否重启；readOnlyRootFilesystem 限制容器写根文件系统，但需要给 nginx 的 /tmp 与 /var/cache/nginx 挂 emptyDir，否则会因写缓存失败反复重启。

7. 为什么 CI 必须「构建一次、晋级多次」？OIDC 与审批各解决什么问题？【挑战】

同一份制品从 staging 晋级到 production，才能保证「测过的」就是「上线的」；每个环境重新构建会引入依赖、环境变量和构建缓存差异。OIDC 用短期凭证替代长期 AK，缩小泄漏面；environment + required reviewers 提供人工发布闸门与审计记录。两者一个管「凭证最小权限」，一个管「发布责任」。

8. 灰度 5% 的流量为什么不能每次请求重新随机？【挑战】

随机分流会让同一用户在 stable 与 canary 之间来回跳，既污染指标（同一用户会话跨版本），也可能触发资源版本不一致。split_clients 对 IP + UA 做哈希分桶，同一用户稳定落在同一桶；比例调整只改变桶的归属边界，不改变已落桶用户的稳定性。

9. 回滚后为什么还要保留旧版本制品与 Source Map，并观察 30 分钟？【挑战】

回滚只切入口，旧版本的哈希资源仍可能被已打开的页面、Service Worker 或 CDN 边缘节点引用，删除会导致 chunk 404；Source Map 用于解析回滚后仍在上报的旧版本堆栈。30 分钟观察窗口用于确认回滚本身没有引入新问题（例如指针切换错版本、SW 未回滚），并把告警口径从 canary 切回 stable。
